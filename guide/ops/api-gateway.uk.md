# API gateway для корпоративного Claude Code

> **Аудиторія**: платформні інженери та DevOps-команди, що розгортають Claude Code в організації.
>
> **Обсяг**: налаштування проксі-шару між клієнтами Claude Code та upstream моделі для централізованого контролю витрат, примусового дотримання бюджетів і видимості використання. Про оцінку вартості окремої сесії див. [observability.md](./observability.uk.md). Про керування MCP див. [enterprise-governance.md §3](../security/enterprise-governance.uk.md#3-процес-управління-mcp).

## TL;DR: приклади сторонніх gateway

Таблиця й налаштування нижче описують приклади LiteLLM та Portkey на цій сторінці. Вони не описують Claude apps gateway.

| Проблема | Приклад стороннього gateway |
|---------|-----------------|
| Немає розбивки витрат за командами | Віртуальні ключі з метаданими команди, агреговані на дашбордах |
| Розробники можуть викликати будь-яку модель | Allowlist моделей для кожного ключа (непогоджені виклики повертають 403) |
| Неконтрольовані витрати від агентів без нагляду | Термінальний бюджетний ліміт на ключ, щомісячне скидання, повертає 429 при досягненні |
| Стрибки витрат інтерактивних розробників | Телеметрія gateway може живити попередження, схвалення й перехід на дешевшу модель; саме поле бюджету такої політики не реалізує |
| Немає спільної телеметрії API | Маршрутизовані запити атрибутуються за псевдонімом ключа, командою, моделлю й токенами; логування корисного навантаження залежить від конфігурації |

**Підхід зі сторонніми gateway**: задайте `ANTHROPIC_BASE_URL` на кожній машині розробника, щоб вказувати на сумісний gateway замість `api.anthropic.com`. Наведені нижче приклади пересилають запити, додають налаштоване логування й примусове дотримання бюджету та видають віртуальні ключі, щоб ключ провайдера не мусив бути на машинах розробників.

## Актуальна first-party поверхня: Claude apps gateway

[Claude apps gateway](https://code.claude.com/docs/en/claude-apps-gateway) — це self-hosted gateway від Anthropic. Він постачається в бінарнику `claude` і запускається командою `claude gateway --config gateway.yaml`. Він розташований між клієнтами Claude Code та upstream. Його впорядкована конфігурація може маршрутизувати й перемикати запити при збої між п'ятьма задокументованими варіантами upstream-провайдерів: Anthropic API, Amazon Bedrock, Claude Platform on AWS, Google Cloud's Agent Platform та Microsoft Foundry.

Використовуйте його, коли організації потрібен self-hosted gateway, специфічний для Claude Code, з корпоративним SSO, доступом до моделей за групами ідентичності, доставкою managed settings і телеметрією OpenTelemetry Protocol. Gateway зберігає облікові дані upstream в інфраструктурі організації. Розробники автентифікуються через корпоративного постачальника ідентичності й отримують короткочасні bearer-токени замість облікових даних провайдера.

### Межа розгортання

Офіційний quickstart вимагає Claude Code v2.1.195 або новішої на хості gateway і машинах розробників, OIDC-постачальника ідентичності, PostgreSQL, облікових даних upstream і адреси gateway у приватній мережі. Вимога приватної адреси є контролем безпеки, бо довірений gateway може доставляти налаштування, що запускають команди на машинах розробників. Розмістіть його за внутрішнім балансувальником навантаження або VPN; не відкривайте як публічну кінцеву точку.

Задокументований потік входу — інтерактивний браузерний SSO. Потоку service-token для CI без нагляду немає, тож система CI без розробника, який схвалює device flow, мусить автентифікуватися безпосередньо в свого провайдера. Машина, де розробник увійшов, може використовувати наявну сесію gateway для `claude -p` та запусків Agent SDK відповідно до політики gateway.

### Що gateway контролює, а що ні

| Поверхня | Задокументована поведінка |
|---|---|
| Ідентичність і облікові дані upstream | Gateway автентифікує розробників через IdP, видає короткочасні bearer-токени (за замовчуванням одна година) і використовує облікові дані провайдера організації на боці upstream. |
| Політика моделей і клієнтів | Групи IdP зіставляються з allowlist моделей і managed settings. Запит до моделі, на яку немає дозволу, повертає `400`. Заблоковані managed settings не можна перевизначити локально. |
| Телеметрія | Gateway пересилає метрики OTLP із кількістю токенів, моделлю, ідентичністю й затримкою. Він не логує й не зберігає вміст промптів чи відповідей. Логи й трейси вмикаються окремо для кожного призначення й можуть містити команди та шляхи до файлів. |
| Площина даних Anthropic | Площина даних gateway нічого не надсилає Anthropic, якщо Anthropic API не налаштовано як upstream. |
| Інший трафік клієнта | Перевірки версій і завантаження все ще можуть іти безпосередньо від Claude Code до Anthropic і потребують окремої політики egress або задокументованих контролів несуттєвого трафіку. |

![Підписки користувачів оминають бюджети й атрибуцію gateway, тоді як CI, спільні агенти, заплановані воркфлоу та внутрішні сервіси проходять через централізовані ключі, квоти, allowlist моделей, fallback і observability](../images/gateway-visibility-boundary.webp)

Gateway не робить настільний застосунок, локальну файлову систему чи plugin автоматично безпечними. [Computer Use](../core/computer-use.uk.md) має окрему межу довіри робочого столу, а [поширення plugin](../ecosystem/plugin-distribution.uk.md) має окрему межу ланцюга постачання розширень.

### Перевірте перед розгортанням

Офіційний quickstart визначає три початкові перевірки: отримати документ виявлення OAuth, запросити авторизацію пристрою, потім завершити браузерний вхід. Вони послідовно перевіряють запуск, доступ до бази даних і перенаправлення до постачальника ідентичності. Успішний запуск gateway не є доказом того, що шлях інференсу upstream працює, бо деякі хмарні облікові дані розв'язуються лише при першому запиті. Виконайте дозволений тестовий запит через потрібний upstream і, якщо він завершується помилкою, дослідіть перший шар, що відмовив.

Підтвердьте відбиток TLS-сертифіката gateway під час першого з'єднання, опублікуйте для розробників повний очікуваний відбиток SHA-256 і плануйте ротації сертифіката. Перш ніж оголошувати політику gateway такою, що виконується, протестуйте запит до забороненої моделі, обмеження managed settings, виведення з доступу (deprovisioning) в IdP, призначення телеметрії та запуск із fail-closed для сесії, у яку увійшли через gateway. Якщо потрібна маршрутизація лише через gateway, окремо забезпечте egress провайдера.

Про загальну архітектуру gateway й обмеження зовнішніх gateway читайте [огляд gateway від Anthropic](https://code.claude.com/docs/en/gateways). Решта цієї сторінки охоплює приклади сторонніх gateway і не є специфікацією продукту Anthropic.

## Приклади сторонніх реалізацій

Решта матеріалу про LiteLLM і Portkey — це керівництво зі сторонніх реалізацій. Його віртуальні ключі, відмова моделі `403`, поведінка бюджету `429` і логування запитів/відповідей не є твердженнями про Claude apps gateway.

## 1. Навіщо потрібен шар gateway

Claude Code може викликати Anthropic чи іншого підтримуваного провайдера безпосередньо з обліковими даними й кінцевою точкою, налаштованими організацією. Без проксі-шару:

- Атрибуція за командами й проектами залежить від звітності провайдера та від того, як організація розділяє ключі
- Обмеження моделей залежать від контролів upstream-провайдера
- Примусове дотримання бюджету залежить від контролів upstream або зовнішнього політичного шару
- Немає спільної телеметрії запитів між провайдерами

Gateway розташований між налаштованими екземплярами Claude Code та їхніми upstream-провайдерами. Він видає розробникам віртуальні ключі (обмежені командою чи проектом), тримає облікові дані провайдера на стороні сервера й застосовує політики до запитів, що проходять через нього. Трафік, автентифікований підпискою, та клієнти з прямими обліковими даними провайдера лишаються поза цією площиною керування.

## 2. Gateway LiteLLM

[LiteLLM](https://github.com/BerriAI/litellm) — це open-source LLM-проксі на Python. Він підтримує Anthropic, видає віртуальні ключі, може примусово дотримуватися налаштованих бюджетів і надає метрики для зовнішніх дашбордів.

### 2.1 Встановлення

```bash
pip install 'litellm[proxy]'

# Docker is recommended for production
docker pull ghcr.io/berriai/litellm:main-latest
```

### 2.2 Конфігурація

Створіть `litellm_config.yaml` для маршрутизації до Anthropic:

```yaml
model_list:
  - model_name: claude-haiku-5-5
    litellm_params:
      model: anthropic/claude-haiku-5-5
      api_key: os.environ/ANTHROPIC_API_KEY

  - model_name: claude-sonnet-5-5
    litellm_params:
      model: anthropic/claude-sonnet-5-5
      api_key: os.environ/ANTHROPIC_API_KEY

  - model_name: claude-opus-5-5
    litellm_params:
      model: anthropic/claude-opus-5-5
      api_key: os.environ/ANTHROPIC_API_KEY

general_settings:
  master_key: os.environ/LITELLM_MASTER_KEY
  database_url: os.environ/DATABASE_URL  # PostgreSQL required for persistent keys

litellm_settings:
  drop_params: true  # Ignore unknown params silently
```

Запустіть проксі:

```bash
litellm --config litellm_config.yaml --port 4000
```

### 2.3 Підключення Claude Code

Задайте ці дві змінні середовища на кожній машині розробника (розповсюджуйте через менеджер секретів, репозиторій dotfiles чи скрипт онбордингу):

```bash
# Point Claude Code to your LiteLLM instance
# Note the /anthropic path suffix, required for Anthropic Messages API format
export ANTHROPIC_BASE_URL=http://your-litellm-host:4000/anthropic

# Developer uses a virtual key, not the real Anthropic key
export ANTHROPIC_API_KEY=sk-litellm-team-backend-abc123
```

Claude Code не потребує жодних інших змін. Він читає `ANTHROPIC_BASE_URL` і прозоро його використовує. Суфікс шляху `/anthropic` обов'язковий: LiteLLM надає формат Anthropic Messages API за адресою `/anthropic/v1/messages`, окремо від свого OpenAI-сумісного endpoint `/v1/chat/completions`.

## 3. Віртуальні ключі та бюджети команд

Створюйте віртуальні ключі через management API LiteLLM. Кожен ключ відповідає команді чи проекту й має необов'язковий місячний бюджетний ліміт.

```bash
# Backend team: Sonnet + Haiku only, $50/month budget
curl -X POST http://localhost:4000/key/generate \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "key_alias": "team-backend",
    "team_id": "team-backend",
    "max_budget": 50,
    "budget_duration": "monthly",
    "models": ["claude-haiku-5-5", "claude-sonnet-5-5"],
    "metadata": {"team": "backend", "project": "api-v2"}
  }'

# Leads: all models, $300/month
curl -X POST http://localhost:4000/key/generate \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "key_alias": "lead-full-access",
    "team_id": "leads",
    "max_budget": 300,
    "budget_duration": "monthly",
    "models": ["claude-haiku-5-5", "claude-sonnet-5-5", "claude-opus-5-5"]
  }'
```

Коли бюджет вичерпано, Claude Code отримує `429 BudgetExceededError`. Ключ автоматично скидається на початку наступного бюджетного циклу.

```bash
# Check current spend for a key
curl http://localhost:4000/key/info?key=sk-litellm-team-backend-abc123 \
  -H "Authorization: Bearer $LITELLM_MASTER_KEY"
```

### 3.1 Прогресивна політика витрат для інтерактивних користувачів

Наведений вище приклад LiteLLM демонструє термінальний ліміт. Він не демонструє прогресивних попереджень, бар'єрів схвалення чи безпечного для якості переходу на дешевшу модель. Побудуйте їх як явний політичний шар або переконайтеся, що обраний gateway реалізує кожен етап на потрібному клієнті й шляху трафіку.

| Етап порогу | Необхідна поведінка | Докази, які треба зберігати |
|---|---|---|
| **Visibility** | Показувати поточні витрати, темп витрат, модель і залишок запасу, не перериваючи роботу | Користувач, команда, модель, часова мітка, обсяг маршрутизованого трафіку |
| **Self-clearing warning** | Просити розробника підтвердити незвичний темп витрат | Поріг, підтвердження, ідентифікатор сесії чи завдання |
| **Approval gate** | Вимагати від власника бюджету схвалити подальші витрати на преміальну модель | Схвалювач, схвалена сума чи тривалість, причина, строк дії |
| **Downshift** | Переводити майбутню роботу на дешевшу схвалену модель лише для класів завдань, які пройшли той самий бар'єр якості | Попередня й нова пара модель-harness, причина маршрутизації, вплив на кеш, прийнятий результат |
| **Suspension** | Повертати чітку термінальну помилку з інструкціями щодо скидання чи ескалації | Причина відмови, час скидання, власник, шлях відновлення |

Зберігайте жорсткий термінальний бюджет для агентів без нагляду, CI, запланованих завдань і сервісів. Немає людини, яка б інтерпретувала попередження, а мовчазний перехід на дешевшу модель може змінити поведінку всередині автоматизованого воркфлоу. Для інтерактивної розробки наведені етапи можуть запобігти випадковим витратам до призупинення. Databricks повідомляє про цей прогресивний патерн зі свого розгортання та розмов з іншими компаніями; звіт неформальний і не доводить, що вищі витрати означають вищу продуктивність. Джерело: [Databricks, "Managing AI Coding Costs at Scale"](https://www.databricks.com/blog/managing-ai-coding-costs-scale), 2026-08-07.

Gateway може застосовувати ці контролі лише до трафіку, який бачить. Клієнти, автентифіковані підпискою, та прямі облікові дані провайдера лишаються поза цією політикою. Звіряйте події gateway з контролями планів для працівників і рахунками провайдера, перш ніж називати загальноорганізаційну політику витрат завершеною.

## 4. Allowlist моделей

Виклики моделей, яких немає в списку `models` ключа, повертають `403 ModelNotAllowedError` до того, як запит досягне Anthropic. Це забезпечує вашу політику схвалення моделей на мережевому рівні незалежно від того, що розробник вказав у конфігурації Claude Code.

Триярусна структура, що відповідає більшості потреб організацій:

| Ярус | Дозволені моделі | Місячний бюджет | Для кого |
|------|---------------|---------------|-----|
| Типовий для розробника | Haiku, Sonnet | $30 | Усі інженери |
| Підвищений для проекту | Haiku, Sonnet | $100 | Робота над активним спринтом |
| Лід/Архітектор | Усі моделі | $300 | Тех-ліди, архітектори |

Ці цифри є стартовою структурою, а не виміряним бенчмарком. Один опублікований звіт дає порівнянний порядок величини в масштабі: Back Market повідомив про фіксовані $200 на розробника на місяць, що скидаються щомісяця, приблизно для 245 розробників, зі шляхом ескалації замість жорсткої зупинки. Розробник, який вичерпав ліміт, може самостійно отримати одне розширення на $20 через форму, що запитує, скільки сесій було запущено, яка сесія коштувала найбільше та як витрати розподілилися між моделями. Жодна людина не схвалює це розширення; форма існує для того, щоб розробник прочитав власну консоль. Далі менеджер подає оцінку до комітету з розгляду, і проект отримує власний робочий простір OpenRouter поза індивідуальним лімітом. Звіт повідомляє, що ліміт на практиці працює, а форма розширення була добре сприйнята, але не публікує даних про завершення завдань, якість чи час рев'ю, тож він калібрує лише рядок бюджету й нічого більше. Джерело: [Nicolas Martignole](https://www.youtube.com/watch?v=pbrP--c4alk), опубліковано 2026-09-14.

Allowlist моделей — це не allowlist провайдерів. Агрегатор може надавати ту саму модель через кількох інфраструктурних провайдерів, кожен із власним контрактом і шляхом обробки. Back Market повідомив, що дозволяє лише невелику внутрішньо перевірену підмножину з приблизно 70 провайдерів, тоді доступних через OpenRouter, і серед них назвав Google Vertex, Fireworks та Amazon Bedrock. Автоматично згенерований транскрипт спотворює розмір цього короткого списку, тож точна кількість не встановлена, а доповідач не подавав це твердження як юридичну пораду. Пізніший виступ того самого доповідача описує роботу приблизно з десятьма провайдерами й додає до названого набору Microsoft Azure та Mistral; ця цифра охоплює фактично використовуваних провайдерів, що не обов'язково збігається зі схваленим списком. Перевіряйте й схвалюйте кожного провайдера окремо. Джерела: [Nicolas Martignole на 38:17](https://www.youtube.com/watch?v=DRtd8S_3E-w&t=2297s), опубліковано 2026-07-22, та [двомісячний огляд OpenRouter](https://www.youtube.com/watch?v=pbrP--c4alk), опубліковано 2026-09-14.

Той самий виступ формулює правило, яке кількість лише ілюструє: маршрутизація до десяти провайдерів означає десять політик даних для перевірки. Відповідальність не переходить до агрегатора. Звіт Back Market прямо каже, що OpenRouter не бере на себе те, що відбувається у Fireworks, Google Vertex чи Amazon Bedrock від імені клієнта, тож контракт, шлях обробки й контролі кожного провайдера лишаються справою клієнта. Один комерційний контракт з агрегатором спрощує закупівлі, а не відповідальність.

Про розділення ідентичностей для працівників і для API див. [Subscription Strategy](./subscription-strategy.uk.md#6-робочі-плани-й-production-трафік-api-розвязують-різні-проблеми).

## 5. Дашборди використання

LiteLLM надає метрики Prometheus за адресою `/metrics`. Додайте конфігурацію scrape у Prometheus:

```yaml
scrape_configs:
  - job_name: litellm
    static_configs:
      - targets: ['litellm-host:4000']
    metrics_path: /metrics
```

Ключові метрики для панелей Grafana:

```
# Total requests by team and model
litellm_requests_total{model, team_id, key_alias}

# Cost by team (USD)
litellm_spend_total{model, team_id}

# Token counts split by input/output/cache
litellm_tokens_total{token_type, model, team_id}

# Error rate by type (budget exceeded, model not allowed, upstream timeout)
litellm_failed_requests_total{model, error_type}
```

Для прогресивної політики витрат також записуйте налаштований етап порогу, підтвердження попереджень, рішення про схвалення, переходи на дешевшу модель, призупинення та результат завдання після кожного втручання. Сирі лічильники витрат і токенів не можуть показати, чи перехід на дешевшу модель збільшив кількість повторних спроб, час рев'ю чи відхилену роботу.

LiteLLM також постачає базовий UI за адресою `/ui` (вмикається змінними середовища `LITELLM_UI_USERNAME` і `LITELLM_UI_PASSWORD`) для швидких розбивок витрат без потреби в повному налаштуванні Grafana.

Звіти практиків показують, що така атрибуція може виявити, у межах трафіку, який бачить gateway. Shopify повідомляє, що атрибутує корпоративні витрати на API за командами й людьми через внутрішній проксі. Ramp повідомляє, що відстежує витрати за командами й продуктами. Back Market каже, що його телеметрія BigQuery виявила витрати на Anthropic API від клієнтів на кшталт Cursor поряд з наявною вартістю ліцензії. Ці звіти не публікують ні базових даних про витрати, ні вартості впровадження, ні вартості за прийняте завдання. Джерела: [Shopify на 22:22](https://www.youtube.com/watch?v=u-3IILWQPRM&t=1342s), опубліковано 2025-07-02; [Ramp на 24:53](https://www.youtube.com/watch?v=NMs8C2_3M0w&t=1493s), опубліковано 2026-03-09; і [Back Market на 45:09](https://www.youtube.com/watch?v=kSrEZ57thMg&t=2709s), опубліковано 2026-04-03.

## 6. Інтеграція з OpenTelemetry

LiteLLM підтримує нативний експорт OTel, що інтегрується зі стеком observability, описаним у [observability.md §10](./observability.uk.md):

```yaml
litellm_settings:
  otel_endpoint: http://otel-collector:4317
  otel_headers:
    Authorization: Bearer ${OTEL_BEARER_TOKEN}
```

Кожен запит породжує span з атрибутами, зокрема `litellm.model`, `litellm.team_id`, `litellm.key_alias`, `litellm.total_tokens` і `litellm.spend`. Вони потрапляють у ваші наявні трейси поряд зі spans рівня застосунку.

## 7. Розгортання у production

Запускайте LiteLLM за зворотним проксі з термінуванням TLS (nginx або Caddy). Мінімальне налаштування Docker Compose:

```yaml
services:
  litellm:
    image: ghcr.io/berriai/litellm:main-latest
    ports:
      - "4000:4000"
    environment:
      ANTHROPIC_API_KEY: ${ANTHROPIC_API_KEY}
      LITELLM_MASTER_KEY: ${LITELLM_MASTER_KEY}
      DATABASE_URL: postgresql://user:pass@db:5432/litellm
    volumes:
      - ./litellm_config.yaml:/app/config.yaml
    command: ["--config", "/app/config.yaml", "--port", "4000"]
    depends_on:
      - db

  db:
    image: postgres:16
    environment:
      POSTGRES_DB: litellm
      POSTGRES_USER: user
      POSTGRES_PASSWORD: pass
    volumes:
      - postgres_data:/var/lib/postgresql/data

volumes:
  postgres_data:
```

PostgreSQL потрібна для постійного керування ключами й історії використання. Без неї віртуальні ключі та стан бюджету скидаються при перезапуску контейнера.

Для високої доступності запустіть два екземпляри LiteLLM за балансувальником навантаження. Обидва використовують одну базу PostgreSQL для узгодженого стану ключів.

## 8. Portkey як керована альтернатива

[Portkey](https://portkey.ai) пропонує ті самі можливості gateway як хостинговий сервіс, без інфраструктури для керування. Безкоштовний тариф покриває малі команди (до 10K запитів на місяць).

```bash
export ANTHROPIC_BASE_URL=https://api.portkey.ai/anthropic
export ANTHROPIC_API_KEY=your-real-anthropic-key
export PORTKEY_API_KEY=your-portkey-api-key
```

Portkey також підтримує заголовки `x-portkey-virtual-key` для маршрутизації, логування та конфігурацій fallback. Компроміс: метадані ваших запитів залишають вашу інфраструктуру й потрапляють на сервери Portkey. Перегляньте їхні умови обробки даних, якщо маєте вимоги комплаєнсу.

## 9. Що gateway не покриває

Gateway контролює запити, що проходять через нього. Він не стосується:

- Використання Claude, автентифікованого підпискою, що надсилається безпосередньо до Anthropic
- API-трафіку від клієнтів, що зберігають прямі облікові дані провайдера або оминають кінцеву точку gateway
- Яких файлів Claude Code читає на машині розробника (використовуйте `permissions.deny` у `settings.json`)
- Які MCP-сервери активні локально (див. [enterprise-governance.md §3](../security/enterprise-governance.uk.md#3-процес-управління-mcp))
- Якості коду у виводі ШІ (використовуйте бар'єри рев'ю PR)
- Чи зберігають попередження, схвалення або перехід на дешевшу модель якість прийнятих завдань
- Журналів аудиту рівня сесії, що показують, які файли змінено (див. [ai-traceability.md](./ai-traceability.uk.md#журнал-аудиту-pr-pr-audit-trail))

Якщо політикою вимагається маршрутизація API лише через gateway, приберіть прямі облікові дані провайдера з машин розробників і окремо забезпечте egress провайдера. Звіряйте телеметрію gateway з планами для працівників і рахунками провайдера; один лише дашборд gateway не є повним загальноорганізаційним реєстром витрат.
