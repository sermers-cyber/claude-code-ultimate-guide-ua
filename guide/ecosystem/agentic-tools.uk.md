# Інструменти агентів: поза межами Claude Code

Claude Code — лише один інструмент у царині, що різко розширилася з 2024 року. З'явилися десятки фреймворків агентів, автономних кодерів і multi-agent систем, кожен із різними компромісами. Ця сторінка накреслює карту цієї царини, щоб ви могли вирішити, коли Claude Code є правильним вибором, а коли краще підійде щось інше.

**Що охоплює ця сторінка**: термінальні агенти для програмування, автономні кодери, multi-agent фреймворки оркестрації та інструменти оркестрації агентів. Власні multi-agent можливості Claude Code (agent teams, подієві workflow, програмне використання) задокументовано окремо, з посиланнями по тексту.

**Що вона не охоплює**: порівняння лише редакторів. IDE, ADE та продукти, що поєднують кілька інтерфейсів, розглянуто в [AI Ecosystem §6](./ai-ecosystem.uk.md#6-ide-ade-and-hybrid-coding-environments). Гібридний продукт з'являється тут лише тоді, коли його агента для програмування можна використовувати і як термінальний runtime. Інструменти multi-Claude оркестрації (Gas Town, multiclaude, десктопний застосунок Conductor) описано в [Third-Party Tools: Multi-Agent Orchestration](./third-party-tools.uk.md#multi-agent-orchestration).

Для повної картини CLI, IDE та хмарних агентів використовуйте [Agent Harness Landscape](./agent-harness-landscape.uk.md). Про цикл, контекст, інструменти, дозволи, відновлення, спостережуваність і автоматизовану оптимізацію harness читайте [Agent Harness Engineering](../core/agent-harness.uk.md). Про явні цикли зворотного зв'язку, графи workflow, правила зупинки та межі відповідальності читайте [Loop & Graph Engineering](../core/loop-graph-engineering.uk.md). [Глосарій](../core/glossary.uk.md) розрізняє runtime-harness, репозиторні harness, harness оцінювання, оркестратори та мета-harness.

## Спектр

Інструменти агентів розташовані на спектрі від інтерактивних до автономних:

```
Interactive pair programmer
  Claude Code, Codex CLI, Aider, Goose, opencode, Gemini CLI, crush
        |
  Hermes Agent (interactive + scheduled + messaging gateways)
        |
Autonomous issue fixer
  SWE-agent, Devin, claude -p in CI
        |
Multi-agent framework (build your own)
  CrewAI, LangGraph, AutoGen/MAF, MetaGPT
        |
Agent orchestrator (manage a fleet)
  Symphony (issue → run), Paperclip (goal → org chart)
```

**Інтерактивні агенти**: ви лишаєтеся в циклі, схвалюєте дії, перенаправляєте агента. Найкраще для щоденного програмування, налагодження та пошукової роботи, де вимоги змінюються.

**Автономні агенти**: ви призначаєте завдання й повертаєтеся до результату. Найкраще для чітко визначених, обмежених завдань: виправити цей баг, реалізувати цю специфікацію, переглянути цей PR. Якість опису завдання визначає якість результату більше, ніж вибір агента.

**Multi-agent фреймворки**: бібліотеки для побудови власних систем агентів. Це не інструменти програмування як такі. Ви використовуєте LangGraph, щоб побудувати агента, а не щоб писати код.

**Оптимізатори harness і мета-harness**: системи, що змінюють цільовий harness і порівнюють версії-кандидати. Вони не є ще однією категорією термінальних агентів для програмування. На цьому зовнішньому циклі працюють [ADAS](https://proceedings.iclr.cc/paper_files/paper/2025/hash/36b7acf6f6010652b3f2a433774a66fe-Abstract-Conference.html), [AFlow](https://arxiv.org/abs/2410.10762), [Meta-Harness](https://arxiv.org/abs/2603.28052) та [Agentic Harness Engineering](https://arxiv.org/abs/2604.25850). Порівнюйте їх через [дослідницький шар Landscape](./agent-harness-landscape.uk.md#harness-optimizers-and-meta-harnesses), а не ставлячи поруч із Claude Code чи Codex у таблиці функцій runtime.

## Розділ 1: Термінальні агенти для програмування

Ці інструменти роблять те, що й Claude Code: сидять у вашому терміналі, читають вашу кодову базу, пишуть код, запускають команди. Відмінності — у підтримці моделей, моделі вартості та конкретних можливостях.

### 1.1 Codex CLI (OpenAI)

Пряма відповідь OpenAI на Claude Code. Запущений у квітні 2025, написаний на Rust, з відкритим кодом під Apache 2.0.

| Атрибут | Деталі |
|-----------|---------|
| **GitHub** | [openai/codex](https://github.com/openai/codex) |
| **Зірки** | 86 200+ (травень 2026) |
| **Встановлення** | `npm install -g @openai/codex` |
| **Мова** | Rust (96%) |
| **Ліцензія** | Apache 2.0 |
| **Версія** | v0.134.0 (26 травня 2026) |
| **Релізи** | 800+ з квітня 2025 |
| **Контриб'ютори** | 400+ |

#### Що таке Codex CLI?

Термінальний ШІ-агент для написання, редагування та запуску коду, побудований на родині моделей OpenAI. Архітектура близько повторює Claude Code: ви описуєте завдання, агент читає файли, вносить правки, запускає тести та ітерує. Головна відмінність — постачальник моделей: Codex CLI працює з GPT-4o, o3, o4-mini та іншими моделями OpenAI, а не з Claude.

Підписники ChatGPT Pro і Team отримують використання Codex CLI у складі свого плану, що робить його інструментом із нульовою граничною вартістю для команд, які вже платять OpenAI.

#### Claude Code проти Codex CLI

| Аспект | Claude Code | Codex CLI |
|--------|-------------|-----------|
| **Моделі** | Лише родина Claude (Opus 5.5, Sonnet 5.5, Haiku 5.5, Fable 5.1) | GPT-4o, o3, o3-mini, o4-mini, плюс майбутні моделі OpenAI |
| **Мова** | TypeScript | Rust |
| **Ліцензія** | Відкритий код | Apache 2.0 |
| **Підписка** | Anthropic Claude Max ($20-$200/міс) | OpenAI ChatGPT Pro/Team ($20-$30/міс) |
| **Підтримка MCP** | Нативна, зростаюча екосистема | Сумісний з MCP |
| **Частота релізів** | Щотижня | Дуже висока (800+ релізів за 13 місяців) |
| **Пам'ять** | CLAUDE.md + Auto Memory | Конвенція AGENTS.md |
| **Skills/Hooks** | Повна система | Сумісний зі стандартом agentskills.io |

#### Коли обирати Codex CLI

Добрий вибір, якщо ви вже на плані ChatGPT Pro чи Team і хочете уникнути другої підписки. Також правильний вибір, якщо ви віддаєте перевагу GPT-4o чи o3 для певних завдань (міркування, аналіз довгого контексту) і хочете термінальний агент, що нативно використовує ці моделі.

Поганий вибір, якщо ваша команда вклалася в робочі процеси Claude Code, файли CLAUDE.md та специфічні для Anthropic патерни. Когнітивна ціна перемикання між двома середовищами агентів реальна.

#### Швидкий старт

```bash
npm install -g @openai/codex
export OPENAI_API_KEY=sk-...
codex
```

[Документація Codex](https://github.com/openai/codex/blob/main/README.md) від OpenAI докладно описує налаштування.

### 1.2 Hermes Agent (раніше OpenClaw)

Найпопулярніший за зірками open-source фреймворк агентів станом на травень 2026. Створений Nous Research, ШІ-лабораторією, відомою серією тонко налаштованих моделей Hermes. Називався OpenClaw до кінця 2025 року, коли був перейменований після того, як Anthropic відновила підтримку підписок.

| Атрибут | Деталі |
|-----------|---------|
| **GitHub** | [NousResearch/hermes-agent](https://github.com/NousResearch/hermes-agent) |
| **Зірки** | 170 000+ (травень 2026) |
| **Встановлення** | `pip install hermes-agent` або `curl -sSL install.hermes-agent.dev \| sh` |
| **Мова** | Python (89%), TypeScript (8%) |
| **Ліцензія** | MIT |
| **Версія** | v0.15.1 (червень 2026) |
| **Частота релізів** | Щотижня (v0.10 16 квіт → v0.15.1 черв 2026) |
| **Контриб'ютори** | 215+ |
| **Творець** | Nous Research (Teknium, @teknium1) |

#### Що таке Hermes Agent?

Самовдосконалюваний термінальний агент, що працює з понад 200 постачальниками LLM, запускається на будь-якій платформі та підключається до 22 платформ обміну повідомленнями (Telegram, Discord, Slack, WhatsApp, Signal, Teams, LINE, SimpleX та інші). Відмітна риса — його цикл навчання (GEPA): після виконання завдань Hermes аналізує, що спрацювало, виокремлює повторювані патерни та автоматично генерує skills. Бенчмарки спільноти показують, що агенти з 20+ автогенерованими skills виконують схожі завдання на 40% швидше за свіжі екземпляри на тій самій кодовій базі.

Історія OpenClaw важлива з двох причин. По-перше, шлях міграції чистий: `hermes-agent` імпортує пам'ять, skills і налаштування OpenClaw під час установки, тож вартість переходу низька. По-друге, суперечка про білінг Anthropic на початку 2026 року стосувалася саме використання OpenClaw/Hermes на підписках Claude Max без належної атрибуції програмного білінгу. Оголошення Anthropic у травні 2026 віднесло Hermes до категорії програмного використання, зміну, яку відтоді призупинено (див. [Billing: Programmatic vs Interactive](../ultimate-guide.uk.md#the-interactiveprogrammatic-billing-split-announced-then-paused)).

#### Claude Code проти Hermes Agent

| Аспект | Claude Code | Hermes Agent |
|--------|-------------|--------------|
| **Моделі** | Лише Claude | 200+ через OpenRouter, OpenAI, Anthropic, HuggingFace, локальні |
| **Самовдосконалення** | Кожна сесія починається з нуля | Skills автогенеруються з повторюваних патернів |
| **Месенджери** | Термінал + IDE | Термінал + 22 чат-платформи |
| **Планування cron** | Routines (хмара Anthropic) | Вбудований cron, працює локально |
| **Білінг** | Підписка або API | Платите безпосередньо вашому постачальнику LLM |
| **Agent SDK** | Специфічний для Anthropic | Plugin `ctx.llm` для будь-якого постачальника |
| **Skills** | Система SKILL.md | Skills Hub (agentskills.io) + автогенеровані |
| **Пам'ять** | CLAUDE.md + Auto Memory | Постійна міжсесійна пам'ять, що курується агентом |

#### Коли обирати Hermes Agent

Найсильніший аргумент — незалежність від моделі. Якщо ви хочете запускати Claude для генерації коду, GPT-4o для окремих завдань міркування та локальну модель (через Ollama) для офлайн-роботи, Hermes обробляє всі три в одному агенті. Claude Code так не може.

Самовдосконалювальний цикл справді відмінний. За 30-40 сесій на одній кодовій базі Hermes будує бібліотеку skills, специфічних для патернів вашого проєкту. Бенчмарки спільноти оцінюють складений виграш у 40% швидшого виконання завдань після накопичення 20+ skills. CLAUDE.md пишеться людиною й навмисно; skills Hermes генеруються машиною та специфічні для проєкту. Різні механізми, обидва варті того, щоб їх мати.

22 інтеграції з месенджерами корисні для команд, які хочуть взаємодіяти зі своїм агентом через Telegram чи Slack, а не термінал. Не пріоритет для більшості розробників, але критично для деяких workflow.

Поганий вибір, якщо ви вкладені в екосистему Anthropic (підписка Claude Max, Routines, Agent SDK). Anthropic не дозволяє сторонім розробникам маршрутизувати запити через облікові дані Free, Pro чи Max від імені їхніх користувачів ([Claude Code legal and compliance](https://code.claude.com/docs/en/legal-and-compliance)). Anthropic також оголосила, а потім призупинила окремий програмний кредит для використання сторонніх застосунків; поки його призупинено, таке використання спирається на ліміти вашої підписки. Враховуйте обидва чинники.

#### Швидкий старт

```bash
pip install hermes-agent

# Or one-line installer
curl -sSL install.hermes-agent.dev | sh

# Import from OpenClaw if migrating
hermes import --from openclaw

# Start (terminal-only, no WebUI, no dashboard)
hermes chat
```

Hermes не має офіційного графічного інтерфейсу. Точка входу — `hermes chat` у терміналі. На Windows потрібен WSL2; нативної підтримки Windows немає. Існує проєкт спільноти (`hermes-webui`), але Nous Research його не підтримує.

#### Відомі експлуатаційні проблеми (v0.15.x)

Кілька режимів збою повторюються в production-розгортаннях і неочевидні з документації. Нижче — відомості зі звітів спільноти та перевірених проблем у трекері проєкту.

**Агент діє до аналізу.** Типова поведінка — одразу починати писати код, не перелічуючи зачеплені файли та не пропонуючи підхід. На складних рефакторингах це призводить до часткових записів до розуміння обсягу. Додайте цей блок до `SOUL.md` (файл ідентичності, що вставляється на початку кожної сесії):

```
## Defaults
Before any development action, explicitly list:
1. Files that will be modified
2. Proposed approach
3. Identified risks
Never write code before confirming these three points.
```

`SOUL.md` містить стійку особистість і поведінку агента. `AGENTS.md` містить правила, специфічні для проєкту (шляхи, порти, команди). Змішування їх створює плутанину під час перемикання між проєктами.

**Лавина паралелізму Kanban.** Конфігурація за замовчуванням має `max_in_progress_per_profile: null` (необмежено) разом з `auto_decompose_per_tick: 3`. Пакет із 10 завдань може породити 30+ одночасних воркерів за лічені секунди. Явні ліміти в `.hermes/config.yaml`:

```yaml
kanban:
  max_in_progress_per_profile: 2
  auto_decompose_per_tick: 1
  task:
    max_runtime_seconds: 300
```

**PATH підпроцесів не успадковується.** Виконувані файли поза `/usr/bin` і `/usr/local/bin` невидимі для підпроцесів Hermes (opencode, Node під керуванням nvm, Python під керуванням pyenv, будь-який інструмент, встановлений у `$HOME`). Виправлення в `.hermes/config.yaml`:

```yaml
terminal:
  env_passthrough:
    - PATH
```

Станом на v0.15.1 це частково розв'язано для середовищ Docker (npx, npm, node розв'язуються за `/usr/local/bin`). Нативні встановлення все ще потребують ручної конфігурації вище.

**Воркери, що виходять, не закривши завдання.** Воркер, який завершив роботу й вийшов без виклику `kanban_complete` чи `kanban_block`, лишає завдання назавжди в стані «in progress». Диспетчер може перезапускати воркера в циклі (issue #28712). Додайте це правило до кожного профілю воркера:

```
Every session must end with an explicit call to kanban_complete or kanban_block.
Exiting without this call is a protocol violation and blocks downstream tasks.
```

**Пошкодження SQLite у `kanban.db`.** Швидке створення завдань, часті перезапуски gateway через SIGTERM і паралельний доступ gateway до того самого файлу можуть пошкодити базу даних. Мінімальний захист:

```bash
# Hourly backup (add to crontab)
0 * * * * cp ~/.hermes/kanban.db ~/.hermes/kanban.db.bak.$(date +%Y%m%d%H)
```

Відновлення за наявності `sqlite3`: зробіть дамп у SQL, повторно імпортуйте в новий файл, замініть. Відкритий RFC (#23717) пропонує замінити SQLite підключуваним бекендом (PostgreSQL, MySQL) для multi-agent розгортань.

**`HERMES_HOME` не передається підпроцесам.** У режимі профілю підпроцеси, запущені gateway, стартують з мінімальним середовищем і не успадковують `HERMES_HOME`. Вони мовчки відкочуються до `~/.hermes`, записуючи пам'ять і дані сесій не до того профілю. Обхідний шлях, доки не з'явиться виправлення в upstream:

```bash
export HERMES_HOME=~/.hermes/profiles/your-profile-name
hermes ...
```

**Накладні витрати токенів суттєві.** Кожен виклик LLM несе приблизно 13 900 токенів фіксованих накладних витрат ще до будь-якого вмісту завдання: визначення інструментів (~8-9K) і системний prompt (~5K). Інтеграції месенджер-gateway (Telegram, LINE, Discord) додають понад це 15-20K токенів на запит. Аналіз спільноти (issue #4379) задокументував 4 мільйони токенів, спожитих за дві години на неправильно налаштованому gateway Telegram. Явно обмежуйте контекст:

```yaml
context:
  max_tokens: 32000
```

### 1.3 Aider

Оригінальний термінальний ШІ-напарник для програмування. Запущений у 2023 Полом Готьє ще до появи Claude Code, Aider встановив багато конвенцій, які згодом перейняли інші інструменти: пряме редагування файлів, автоматичні git-коміти, багатофайлові context windows.

| Атрибут | Деталі |
|-----------|---------|
| **GitHub** | [Aider-AI/aider](https://github.com/Aider-AI/aider) |
| **Зірки** | 45 400+ (травень 2026) |
| **Встановлення** | `pip install aider-install && aider-install` |
| **Мова** | Python (80%) |
| **Ліцензія** | Apache 2.0 |
| **Творець** | Paul Gauthier (paul-gauthier) |
| **Завантаження PyPI** | 5,3M+ |

#### Що таке Aider?

Асистент для програмування на Python, що редагує файли у вашому локальному git-репозиторії та автоматично комітить з описовими повідомленнями. Ключова риса — майже універсальна підтримка моделей через LiteLLM: GPT-4o, родина Claude 5, Gemini, Ollama та десятки інших постачальників. Aider популяризував формати редагування «whole file» і «diff», що вплинули на те, як пізніші агенти обробляють зміни файлів.

Траєкторія бенчмарка SWE-Bench добре це розповідає: Aider утримував найвищий результат на SWE-Bench Verified кілька місяців у 2024-2025, перш ніж його випередили моделі з більшим контекстом і потужніші агенти. Цей рекорд закріпив його репутацію серйозного інструмента, а не просто зручної обгортки.

#### Claude Code проти Aider

| Аспект | Claude Code | Aider |
|--------|-------------|-------|
| **Підтримка моделей** | Лише Claude | GPT-4o, Claude, Gemini, Ollama, 50+ постачальників |
| **Інтеграція з git** | Нативна (читає .git, запускає git) | Глибока (автокоміти, повідомлення комітів, контекст blame) |
| **Архітектура** | Пропрієтарна Anthropic | Відкритий код, під капотом LiteLLM |
| **Редагування файлів** | На основі інструментів (Edit, Write) | Формат цілого файлу або diff, що надсилається моделі |
| **Веб-пошук** | Через MCP | Не нативний (потребує plugin) |
| **Агентний цикл** | Повний (мультиходовий, використання інструментів) | Повний (автоприйняття змін у architect mode) |
| **Частота релізів** | Щотижня | Щомісяця (останній: v0.86.0, серп 2025) |

Дата останнього релізу, серпень 2025, тут важлива: Aider лишається підтримуваним і працездатним, але частота релізів сповільнилася порівняно з Claude Code і Hermes. Це саме по собі не тривожний знак, але зіставте її з вашою потребою в нових функціях перед упровадженням.

#### Коли обирати Aider

Найкращий випадок: вам потрібна підтримка кількох моделей у зрілому, перевіреному в боях інструменті, і ви не хочете операційних накладних витрат Hermes. Aider простіший у налаштуванні за Hermes, має менший слід і багаторічну документацію спільноти.

Також добре підходить командам із сильною git-дисципліною, які хочуть, щоб кожна зміна ШІ була явно закомічена з чітким повідомленням. Поведінка автокомітів в Aider агресивніша, ніж у Claude Code (який за замовчуванням питає перед комітом).

```bash
pip install aider-install && aider-install

# With Claude
export ANTHROPIC_API_KEY=sk-ant-...
aider --model claude-sonnet-5-5

# With GPT-4o
export OPENAI_API_KEY=sk-...
aider
```

Повний перелік моделей і параметри конфігурації див. на [aider.chat](https://aider.chat).

#### Що таке opencode?

Термінальний агент для програмування, збудований навколо розділення клієнт/сервер: сам агент працює як серверний процес, а термінал, plugin для IDE чи окрема машина підключаються до нього як клієнт. Ця архітектура робить headless-роботу та сесії, що відновлюються, першокласними, а не прикрученими, оскільки відключення клієнта не зупиняє серверну сесію. opencode спочатку був проєктом SST; він перейшов до компанії Anomaly, а проєкт зберігає назву.

Друга головна риса — підтримка моделей: 75+ постачальників через єдину поверхню конфігурації, включно з локальними моделями, тож ніщо в harness не припускає саме Claude, GPT чи Gemini. Ця широта також є причиною, чому проєкт став типовою точкою відліку для «агента для програмування, що працює будь-де, на будь-чому».

#### Claude Code проти opencode

| Аспект | Claude Code | opencode |
|--------|-------------|----------|
| **Моделі** | Лише родина Claude | 75+ постачальників, включно з локальними моделями |
| **Архітектура** | Один термінальний процес | Клієнт/сервер; агент працює як сервер, термінал — один із можливих клієнтів |
| **Мова** | TypeScript | TypeScript |
| **Ліцензія** | Пропрієтарна | MIT |
| **Skills/Hooks** | Повна власна система | Розширення на основі plugin і MCP |
| **Пам'ять** | CLAUDE.md + Auto Memory | Конвенція AGENTS.md |
| **Управління** | Anthropic, один вендор | Anomaly (компанія), раніше SST |

#### Коли обирати opencode

Найсильніший аргумент — гнучкість щодо постачальників: команда, що хоче маршрутизувати між Claude, GPT, Gemini і локальною моделлю в одному harness, не перемикаючи інструменти за постачальником, отримує це тут нативно. Дизайн клієнт/сервер також окупається для тих, хто запускає агента на віддаленій машині чи всередині CI і спостерігає за ним із ноутбука.

Чесна слабка точка — глибина інтеграції з кожним постачальником. Будучи за задумом multi-provider, жодна модель не отримує першопартійного шліфування, яке Claude Code дає саме моделям Claude (поведінка кешування prompt, skills, hooks, налаштовані під формат використання інструментів одного вендора). Кількість зірок тут також не є показником стабільності: проєкт уже одного разу змінив опікуна (SST на Anomaly), і команді, що ставить на довгострокову стабільність поверхні API, варто прочитати історію міграції, перш ніж стандартизуватися на ньому.

Широта постачальників також не усуває операційних ризиків схвалення чи версій. Доповідь практиків про ШІ-рецензента коду, збудованого для заявлених 200 інженерів, описувала використання OpenRouter для швидкого прототипування через один API, а потім перехід на Vertex AI і Gemini задля кращого моніторингу, журналів, бюджетів і засобів безпеки. Після того як пізніше оновлення моделі знизило виміряну задоволеність рецензентом, команда відкотилася до попередньої моделі й спостерігала відновлення. Доповідь не повідомляє ні кількості активних користувачів, ні вартості міграції, ні значень задоволеності. Ставтеся до списків дозволених постачальників, закріплених версій моделей, телеметрії якості та відкоту як до критеріїв прийняття для multi-provider harness. Джерело: ["How We Built an AI Code Reviewer for 200 Engineers", 17:19](https://www.youtube.com/watch?v=dTye2zVfSco&t=1039s) і [21:44](https://www.youtube.com/watch?v=dTye2zVfSco&t=1304s), AI DevCon, опубліковано 2026-05-29.

#### Швидкий старт

```bash
curl -fsSL https://opencode.ai/install | bash
opencode
```

Повний список постачальників і конфігурація на [opencode.ai/docs/providers](https://opencode.ai/docs/providers/); серверна архітектура на [opencode.ai/docs/server](https://opencode.ai/docs/server/).

#### opencode Go: рівень підписки і чому він не масштабується на команду

Окрім використання з власними ключами постачальників, opencode пропонує підписку Go за $10/місяць. Поточний каталог включає Grok 4.6 і GPT 5.6 Luna поруч із DeepSeek, Qwen, GLM, Kimi та іншими моделями, тож це кураторська підписка на моделі для програмування, а не рівень лише з open-weight моделями. Використання обмежене у вартісному вираженні, а не фіксованою кількістю запитів: $12 за 5-годинне вікно, $30 на тиждень і $60 на місяць. Офіційні оцінки наразі коливаються від 110 до 45 300 запитів за 5-годинне вікно, але ці оцінки припускають специфічні для моделі профілі запитів із великими обсягами кешованого вводу й не є гарантіями кількості запитів. Джерело: [opencode.ai/docs/go](https://opencode.ai/docs/go/), перевірено 2026-08-30.

План явно одномісний: лише один учасник робочого простору може підписатися на Go. Ліміти використання також не обов'язково є жорсткою фінансовою зупинкою. Якщо підписник вмикає **Use balance**, Go після досягнення ліміту переходить на баланс OpenCode Zen робочого простору замість блокування запитів. Go може обслуговувати індивідуальну оцінку, але не є задокументованим способом забезпечення чи управління командою. Джерело: [opencode.ai/docs/go](https://opencode.ai/docs/go/), перевірено 2026-08-30. Порівняння підписок на рівні команди між постачальниками див. у [Subscription Strategy at Team Scale](../ops/subscription-strategy.uk.md).

### 1.8 DeepSeek Harness (dsh)

Офіційний runtime агента від DeepSeek. Технічно амбітний, явно експериментальний, і його не слід плутати з безпечним за замовчуванням production-sandbox.

| Атрибут | Деталі |
|-----------|---------|
| **GitHub** | [deepseek-ai/deepseek-harness](https://github.com/deepseek-ai/deepseek-harness) |
| **Інтерфейс** | Локальний веб-UI і headless CLI |
| **Ліцензія** | MIT |
| **Статус** | Developer preview; очікуються зміни, що ламають сумісність |
| **Архітектура** | Дерево plugin Cordis: моделі, інструменти, skills, сесії, sandbox, сховище, схвалення та UI — компоновані plugin |

#### Що таке DeepSeek Harness?

DeepSeek Harness, доступний як `dsh`, — це local-first runtime, що складає профіль із plugin, а не постачає одну фіксовану поверхню агента. Його офіційна архітектура документує профілі та бандли для циклу агента, адаптерів моделей, інструментів, MCP, skills, subagent, workflow, sandboxing, дозволів, сховища та UI. Це робить його цікавим еталоном для будівничих: шви видно, а не приховано за однією командою CLI.

Починайте з офіційного пакета, а не з проєкту спільноти зі схожою назвою:

```bash
npx @deepseek-ai/dsh web

# Inspect the fully composed profile before trusting it
npx @deepseek-ai/dsh --profile web --dump-config
```

Проєкт документує профілі Standard, PTC/Code Mode, Minimal та орієнтований на Creation. Журнал подій сесії може записувати повідомлення, виклики інструментів і рішення про схвалення для відтворення. Це допомагає налагодженню, але також породжує питання поводження з даними: перевірте налаштування телеметрії та експорту, перш ніж пропускати через локальний запуск пропрієтарний код чи секрети.

#### Обмеження безпеки та експлуатації

Репозиторій позначає dsh як developer preview. Сприймайте це як операційне обмеження, а не скромне формулювання. Local-first агент усе одно може читати ворожий вміст репозиторію, викликати потужний інструмент і писати до робочого простору. Використовуйте ізольовану VM чи контейнер для недовіреного коду, починайте з профілю з найменшими привілеями та робіть суттєві дії придатними до перегляду поза власним циклом міркувань моделі. Не вмикайте пресет `danger-full-access` на основній машині.

Одне зовнішнє дослідження, [arXiv:2608.16393](https://arxiv.org/abs/2608.16393), оцінило один коміт і конфігурацію DeepSeek Harness у 14 560 контрольованих тестах непрямої ін'єкції prompt. Його результати — це свідчення про ту протестовану конфігурацію, а не універсальний рейтинг безпеки. Стійкий урок простіший: сам по собі sandboxing не доводить, що недовірений вміст не може впливати на агента, що використовує інструменти. Тримайте походження, незалежну авторизацію та шлюзи перегляду поверх sandbox.

Офіційні відправні точки: [README](https://github.com/deepseek-ai/deepseek-harness), [архітектура](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/architecture.md), [підсистема sandbox](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/sandbox.md) і [пресети дозволів](https://github.com/deepseek-ai/deepseek-harness/blob/master/docs/subsystems/permission-presets.md). Знімок перевірено 2026-09-02.

#### Коли обирати DeepSeek Harness

Обирайте dsh, щоб вивчати чи розширювати plugin-first runtime, або щоб експериментувати в ізольованому середовищі з його явною моделлю композиції. Не стандартизуйтеся на ньому для production-команди лише тому, що він локальний чи з відкритим кодом. Claude Code лишається кращим вибором за замовчуванням у цьому посібнику для стабільного задокументованого workflow програмування; dsh — швидкозмінна альтернатива, яку варто оцінювати за чіткими шлюзами безпеки та підтримки.

### 1.9 Warp Agent CLI

Warp Agent — пропрієтарний агент для програмування, чий автономний CLI працює і в сторонніх терміналах, і у Warp. Це важливо для класифікації: Warp більше не лише термінальний застосунок із вбудованим асистентом. Вендор тепер подає агента як термінальний runtime зі власною інтерактивною поверхнею, multi-agent координацією та необов'язковим продовженням у хмарі.

| Атрибут | Деталі |
|-----------|---------|
| **Офіційне джерело** | [Introducing Warp Agent](https://www.warp.dev/blog/introducing-the-warp-agent-cli-coding-agent) |
| **Інтерфейси** | CLI, інтерактивний термінальний UI та веб-моніторинг для хмарних запусків |
| **Підтримка терміналів** | Автономне використання в терміналах, зокрема Ghostty, iTerm2, термінали VS Code та термінали Windows |
| **Модель виконання** | Локальна термінальна робота з необов'язковою передачею хмарним агентам Warp |
| **Стратегія моделей** | Маршрутизація, кероване вендором, плюс настроювана маршрутизація моделей |
| **Ліцензія** | Пропрієтарна |

#### Чим вирізняється?

Warp наголошує на точності терміналу. Його агент може мультиплексувати псевдотермінали та взаємодіяти з повноекранними застосунками, як-от налагоджувачі, редактори й клієнти баз даних, замість того щоб вважати кожну команду одноразовим підпроцесом. Та сама поверхня продукту може координувати кількох агентів і делегувати роботу зовнішнім агентам для програмування, включно з Claude Code і Codex, згідно зі статтею про запуск від Warp.

Передача в хмару — друга відмінність. Завдання може початися в локальному терміналі й продовжитися віддалено, а прогрес видно з хмарної поверхні Warp. Це гібридна модель виконання, а не доказ того, що кожна команда лишається локальною. Командам слід вирішити, які репозиторії, облікові дані та виводи команд можуть перетинати цю межу, перш ніж вмикати віддалені запуски.

#### Межа доказів

Наведені вище можливості походять зі статті про запуск Warp від 4 серпня 2026. Цей посібник незалежно не тестував сумісність терміналів, якість маршрутизації моделей, хмарну ізоляцію чи надійність multi-agent. Сприймайте профіль як джерельну карту продукту, а потім перевірте точну версію клієнта, шлях даних, модель дозволів і ціни на репрезентативному репозиторії перед упровадженням.

#### Коли обирати Warp Agent

Додайте його до шорт-листа, коли інтерактивні термінальні програми центральні для завдання, коли розробники хочуть того самого агента в кількох термінальних застосунках або коли передача з локального в хмарне є реальною вимогою workflow. Віддавайте перевагу термінальному агенту з відкритим кодом, коли перевірюваність чи самостійне розміщення не підлягають обговоренню. Віддавайте перевагу простішому CLI, коли віддалене продовження й термінальне мультиплексування не виправдовують ще однієї пропрієтарної поверхні керування.

### 2.1 Devin (Cognition)

Перший комерційний повністю автономний інженер-програміст. Закритий код, хмарне розміщення, корпоративне ціноутворення.

| Атрибут | Деталі |
|-----------|---------|
| **Вебсайт** | [devin.ai](https://devin.ai) |
| **Тип** | Хмарний SaaS, пропрієтарний |
| **Ціни** | Core: $20/міс (ACU з оплатою за використання), Team: $500/міс (250 ACU), Enterprise: індивідуально |
| **Запущено** | 2024 |
| **Оцінка** | $25B (залучення коштів у квітні 2026) |
| **Помітне придбання** | ШІ-нативна IDE Windsurf (липень 2025) |
| **Корпоративні клієнти** | Goldman Sachs, Microsoft, Palantir, Citi, Dell |

#### Що таке Devin?

Автономний інженер-програміст, що працює в хмарній Linux VM із власним shell, редактором коду та браузером. Devin планує підхід, пише код, запускає тести, читає повідомлення про помилки й ітерує, доки завдання не буде виконане або він не застрягне. Основний інтерфейс — Slack: ви надсилаєте повідомлення на кшталт «fix issue #342», і Devin відкриває PR, коли завершить.

Білінг іде в ACU (Agent Compute Units), де 1 ACU відповідає приблизно 15 хвилинам роботи агента. Складна функція може спожити 10-20 ACU; просте виправлення бага — 1-3.

#### Claude Code проти Devin

| Аспект | Claude Code | Devin |
|--------|-------------|-------|
| **Середовище виконання** | Ваша локальна машина | Хмарна Linux VM (у sandbox) |
| **Модель взаємодії** | Інтерактивна (ви спостерігаєте) | Асинхронна (призначили й повернулися) |
| **Стан** | У межах сесії | Зберігається протягом завдання |
| **Ціни** | Підписка ($20-$200/міс) | Оплата ACU за завдання (прибл. $0.07-$0.15/ACU) |
| **Хто веде** | Ви (парне програмування) | Агент (автономно, ви переглядаєте) |
| **Специфікація завдання** | Розмовна, ітеративна | Наперед (краща специфікація = кращий результат) |
| **Доступ до браузера** | Через MCP (Playwright) | Вбудований, нативний |
| **Інтеграція code review** | Ви переглядаєте у своїй IDE | Devin публікує PR, ви переглядаєте на GitHub |

#### Коли обирати Devin

Devin працює найкраще, коли завдання чітко визначене, обмежене й не потребує постійних суджень. Рефакторинг конкретного модуля, реалізація задокументованої кінцевої точки API, виправлення регресії з відомою першопричиною: це завдання для Devin. Проєктування нової системної архітектури, налагодження неясної проблеми в production чи написання коду, що залежить від неявного контексту у вашій кодовій базі: для цього потрібен інтерактивніший цикл.

План Team за $500/міс (250 ACU) суттєвий. За такої ціни ви платите за асинхронну цінність: розробники не блокуються в очікуванні виводу агента, агенти працюють паралельно над кількома завданнями, немає перемикання контексту. Якщо ваше вузьке місце — увага розробників, а не сира пропускна здатність, Devin вартий розрахунку. Якщо ви хочете лишатися в циклі й ітерувати інтерактивно, Claude Code за $200/міс дає більше цінності за долар.

Придбання Windsurf (липень 2025) сигналізує про рух Cognition до повного середовища розробника, а не лише фонового агента. Слідкуйте за інтегрованими workflow, що поєднують інтерактивне програмування (Windsurf IDE) і автономне виконання завдань (Devin) в одному продукті.

### 2.2 SWE-agent (Princeton)

Академічний агент, розроблений спеціально для розв'язання GitHub issues лише за описом issue. Стаття NeurIPS 2024, Princeton NLP Group і Stanford.

| Атрибут | Деталі |
|-----------|---------|
| **GitHub** | [SWE-agent/SWE-agent](https://github.com/SWE-agent/SWE-agent) |
| **Зірки** | 19 300+ (травень 2026) |
| **Стаття** | NeurIPS 2024 |
| **Ліцензія** | MIT |
| **Мова** | Python (95%) |
| **Версія** | v1.1.0 (травень 2025) |
| **Мейнтейнери** | Princeton NLP Group + Stanford |

#### Що таке SWE-agent?

Конвеєр агента, що приймає URL GitHub issue і модель, а потім намагається відтворити баг, написати виправлення та створити патч. Його архітектура використовує шар Agent-Computer Interface (ACI), що абстрагує термінал, редагування файлів і запуск тестів у послідовний набір команд незалежно від базового середовища. Цей дизайн ACI — головний академічний внесок: він показує, що продуктивність агента сильно корелює з тим, наскільки добре середовище відкриває інформацію, а не лише з сирими можливостями моделі.

Рецензована оцінка NeurIPS 2024 не тестувала Claude 3.7 чи open-weight модель у своєму основному результаті SWE-bench. На повному тестовому наборі SWE-bench SWE-agent розв'язав 12,47% issues з GPT-4 Turbo і 10,46% з Claude 3 Opus. Таблиця 1 повідомляє про середні витрати на API-інференс $1,59 і $2,59 відповідно, усереднені лише за успішно розв'язаними випадками, з лімітом $4 на запуск. Ці цифри описують конфігурацію бенчмарка з 2024 року в статті, а не сучасний рівень техніки. Джерело: [Yang et al., SWE-agent](https://proceedings.neurips.cc/paper_files/paper/2024/file/5a7c947568c1b1328ccc5230172e1e7c-Paper-Conference.pdf), PDF с. 5-6, Таблиця 1.

#### Коли обирати SWE-agent

Насамперед для академічного та дослідницького використання. Якщо ви хочете проводити систематичні оцінки того, як різні моделі працюють на реальних GitHub issues, SWE-agent — правильний інструмент, бо має інфраструктуру відтворюваності (журналювання траєкторій, harness оцінювання, YAML-конфігурація), якою production-інструменти нехтують.

Для production-пакетного розв'язання issues хмарний sandbox і краще відновлення після помилок Devin роблять його практичнішим. SWE-agent вимагає, щоб ви налаштували середовище й вручну обробляли збої.

Дослідницька цінність реальна: команди, що будують системи агентів, можуть використовувати дані траєкторій SWE-agent (згенеровані із запусків розв'язання issues) для донавчання моделей. SWE-agent-LM-32b від Nous Research (відкриті ваги, SoTA на SWE-Bench для відкритих моделей) навчено на траєкторіях, згенерованих SWE-agent.

```bash
pip install swe-agent

# Run on a GitHub issue
sweagent run \
  --agent.model.name=claude-sonnet-5-5 \
  --env.repo.github_url=https://github.com/org/repo \
  --problem_statement.github_url=https://github.com/org/repo/issues/123
```

### 2.3 Claude Code у headless-режимі

Власний автономний режим Claude Code: `claude -p "task"` виконує одну інструкцію неінтерактивно й завершується. У поєднанні з CI/CD він стає автономним агентом, що спрацьовує на події GitHub, запускається за розкладом через Routines або обробляє завдання програмно через Agent SDK.

**Білінг:** Anthropic оголосила окремий програмний кредит для `claude -p` та Agent SDK з 15 червня 2026, а потім призупинила його. Станом на перевірку 2026-09-30 це використання все ще спирається на ліміти вашої підписки. Оголошений план див. у [Billing: Programmatic vs Interactive](../ultimate-guide.uk.md#the-interactiveprogrammatic-billing-split-announced-then-paused).

```bash
# Agent SDK: programmatic with tools

```

### 2.4 OpenHands (All Hands AI)

Автономна платформа для програмування з відкритим кодом, раніше OpenDevin. Найближчий еквівалент Devin, який можна розгорнути самостійно.

| Атрибут | Деталі |
|-----------|---------|
| **GitHub** | [OpenHands/OpenHands](https://github.com/OpenHands/OpenHands) |
| **Зірки** | 79 900+ (липень 2026) |
| **Підтримка моделей** | Claude, GPT, Gemini, open-weight моделі |
| **Розгортання** | Самостійне (безкоштовно) або OpenHands Cloud/Enterprise (платно) |
| **Виконання** | Середовище в sandbox |

#### Що таке OpenHands?

Агент-планувальник будує граф залежностей до початку будь-якої роботи, а потім породжує sub-agent для його виконання: завдання без залежностей (Tier 0) виконуються паралельно, а кожне завдання Tier 1 стартує, щойно розв'язується його конкретна залежність, а не чекає завершення всього Tier 0. Потім агент-інтегратор зливає отримані файли, виправляє шляхи імпорту, з'єднує виклики API з компонентами frontend і запускає повний набір тестів, перш ніж повернути результат.

#### Коли обирати OpenHands

OpenHands — практичний вибір, коли ви хочете паралелізм за графом залежностей, як у Devin, без оплати за завдання чи закритого коду. Самостійне розміщення означає, що ви контролюєте sandbox і маршрутизацію моделей, ціною власного запуску інфраструктури.

Шар управління (guardrails, бюджети, внутрішній marketplace plugin, повний аудиторський слід) розміщено за OpenHands Cloud/Enterprise. Ядро з відкритим кодом дає граф виконання та sandbox, а не примусове застосування політик в усій організації. Якщо ваш пріоритет — детерміновані шлюзи та простежуваність у команді, закладіть бюджет на платний рівень або поєднайте OpenHands із зовнішнім шаром політик.

## Розділ 3: Multi-Agent фреймворки

Це не інструменти програмування. Це бібліотеки для побудови власних multi-agent застосунків з нуля: маркетингові конвеєри, автоматизація досліджень, обробка документів, боти підтримки клієнтів. Ви використовували б їх, якщо будуєте продукт, у якому є ШІ-агенти, а не якщо ви розробник, що хоче, аби агент писав код за вас.

Стосунок до Claude Code: Claude (модель) може бути одним із LLM, що живлять агентів, збудованих цими фреймворками. Самі фреймворки не конкурують із Claude Code більше, ніж Express.js конкурує з браузером.

### 3.1 CrewAI

Рольова multi-agent оркестрація. Домінуючий вибір для команд, що хочуть визначати агентів за посадовою функцією (Дослідник, Автор, Редактор) і дозволити їм співпрацювати над структурованими завданнями.

| Атрибут | Деталі |
|-----------|---------|
| **GitHub** | [crewAIInc/crewAI](https://github.com/crewAIInc/crewAI) |
| **Зірки** | 52 300+ (травень 2026) |
| **Мова** | Python (99%) |
| **Ліцензія** | MIT |
| **Версія** | v1.14.5 (18 травня 2026) |
| **Виконання** | Повідомлено про 2B+ виконань завдань агентами |
| **Завантаження** | 27M+ |
| **Корпоративні клієнти** | 150+ |

#### Що таке CrewAI?

Ви визначаєте агентів із роллю, ціллю та передісторією («екіпаж»). Ви визначаєте завдання й призначаєте їх агентам. CrewAI займається маршрутизацією: послідовною (A завершує, потім стартує B), паралельною (A і B працюють одночасно) або ієрархічною (агент-менеджер делегує спеціалістам). Кожен агент може використовувати інструменти, включно з MCP-серверами та веб-пошуком. Підтримується кілька постачальників LLM (Claude, GPT, Gemini, Ollama).

Він відрізняється від LangChain (старшого фреймворку, з яким його часто порівнюють), бо взагалі не залежить від LangChain. Автономна бібліотека Python.

#### Коли використовувати CrewAI

Правильний рівень абстракції для команд, що можуть описати свій workflow людськими ролями. Якщо ви можете сказати «мені потрібен дослідник, що збирає інформацію, автор, що пише чернетку, і редактор, що вдосконалює», CrewAI обробляє оркестрацію та комунікацію між агентами. Ви пишете визначення агентів, а не код оркестрації.

Уникайте його, коли ваш workflow має складне умовне розгалуження, вимагає стійкого виконання крізь збої або потребує тонкого контролю над тим, як стан передається між агентами. LangGraph краще справляється з такими випадками.

```python
from crewai import Agent, Task, Crew, Process

researcher = Agent(
    role="Technical Researcher",
    goal="Find accurate technical information",
    backstory="Expert at synthesizing documentation and research papers",
    llm="claude-sonnet-5-5"
)

writer = Agent(
    role="Technical Writer",
    goal="Write clear, accurate documentation",
    backstory="Experienced at translating technical concepts",
    llm="claude-sonnet-5-5"
)

task = Task(
    description="Research and document the new auth API endpoints",
    expected_output="Markdown documentation with examples",
    agent=writer,
    context=[research_task]  # researcher's output feeds writer
)

crew = Crew(agents=[researcher, writer], tasks=[task], process=Process.sequential)
result = crew.kickoff()
```

### 3.2 LangGraph

Графова оркестрація агентів від LangChain. Нижчого рівня, ніж CrewAI, гнучкіша, краща для складних workflow зі станом.

| Атрибут | Деталі |
|-----------|---------|
| **GitHub** | [langchain-ai/langgraph](https://github.com/langchain-ai/langgraph) |
| **Зірки** | 33 100+ (травень 2026) |
| **Мова** | Python (99%) + доступна версія JS |
| **Ліцензія** | MIT |
| **Версія** | v1.2.2 (26 травня 2026) |
| **Користувачі в production** | Klarna, Replit, Elastic |

#### Що таке LangGraph?

Фреймворк побудови агентів, що моделює workflow як орієнтовані графи з вузлами (кроки агента) і ребрами (переходи). Ключові примітиви: стан (типізований dict, що зберігається між усіма вузлами), умовні ребра (розгалуження за станом) і персистентність (checkpointing, щоб перерваний workflow відновлювався з останньої контрольної точки, а не з нуля). Human-in-the-loop — першокласний патерн: ви можете призупинити виконання на будь-якому вузлі й дочекатися рішення людини перед продовженням.

LangGraph не постачає агентів у комплекті. Ви визначаєте логіку workflow і підключаєте будь-який LLM. Фреймворк гарантує, що переходи станів передбачувані, збої відновлювані, а workflow можна налагоджувати крок за кроком.

#### Коли використовувати LangGraph

Правильний інструмент, коли ваш агент має пережити збої, розгалужуватися за умовами часу виконання або вимагати схвалення людини в конкретних точках рішення. Приклади: конвеєр code review, що ескалює до людини, коли агент виявляє зміну, важливу для безпеки; workflow обробки даних, що робить checkpoint після кожного дорогого кроку, щоб перезапуски не повторювали вже завершені етапи; багатокроковий дослідницький агент, що призупиняється для вказівок людини, коли натрапляє на неоднозначний вихідний матеріал.

Крутіша крива навчання, ніж у CrewAI. Варто того, коли складність workflow виправдовує вкладення.

```python
from langgraph.graph import StateGraph, END
from typing import TypedDict

class AgentState(TypedDict):
    messages: list
    task_complete: bool

graph = StateGraph(AgentState)
graph.add_node("agent", call_agent)
graph.add_node("tools", call_tools)
graph.add_conditional_edges("agent", should_continue, {"continue": "tools", "end": END})
graph.add_edge("tools", "agent")
graph.set_entry_point("agent")

app = graph.compile(checkpointer=MemorySaver())  # Durable execution
```

LangSmith (продукт спостережуваності LangChain) нативно інтегрується для налагодження та трасування запусків агентів.

### 3.3 AutoGen / Microsoft Agent Framework

Multi-agent фреймворк Microsoft у середині переходу від оригінальної бібліотеки AutoGen (режим підтримки з вересня 2025) до Microsoft Agent Framework (MAF), що зливає AutoGen і Semantic Kernel в один SDK.

| Атрибут | Деталі (MAF) |
|-----------|---------|
| **GitHub** | [microsoft/agent-framework](https://github.com/microsoft/agent-framework) |
| **Зірки** | 12 444 (MAF, активний, перевірено 2026-07-27; раніше було 10 800+) |
| **Застарілий GitHub** | [microsoft/autogen](https://github.com/microsoft/autogen) (60 033 зірки станом на 2026-07-27, було 58 400, режим підтримки з вер 2025) |
| **Мова** | Python + C# + TypeScript |
| **Ліцензія** | MIT |
| **Версія** | python-1.6.0 (22 травня 2026) |
| **Production-реліз** | v1.0 (квітень 2026) |

#### Що таке Microsoft Agent Framework?

MAF — це злиття AutoGen (Python, розмовна multi-agent) і Semantic Kernel (C# + Python, абстракції виклику функцій). Результат — міжрантаймовий фреймворк: агенти Python можуть координуватися з агентами .NET, усе на одному шарі обміну повідомленнями. Він реалізує протокол A2A (Agent-to-Agent), внесок Microsoft у сумісність агентів, і підтримує MCP.

Кількість зірок AutoGen (60 033 станом на 2026-07-27) відображає його історичну репутацію. AutoGen започаткував патерн «conversable agent», де агенти розмовляють між собою у структурованому циклі розмови. Цей патерн досі лишається домінантною ментальною моделлю у фреймворку, навіть коли реалізація еволюціонувала.

#### Коли використовувати MAF

Сильний вибір для команд екосистеми Microsoft: компанії з .NET + Python, розгортання Azure, корпоративні середовища, де Semantic Kernel уже усталений. Історія міжрантаймовості реальна: агент Python може викликати інструменти, реалізовані як функції .NET Semantic Kernel.

Менш переконливий для команд без наявних вкладень у .NET. Якщо ви лише на Python, CrewAI чи LangGraph мають більші спільноти й більше навчальних матеріалів.

### 3.5 MetaGPT

Оригінальний фреймворк «ШІ-софтверної компанії»: п'ять фіксованих ролей (Product Manager, Architect, Project Manager, Engineer, QA), зв'язаних у конвеєр, що перетворює однорядковий запит на PRD, діаграми та код. Історично важливий, наразі неактивний.

| Атрибут | Деталі |
|-----------|---------|
| **GitHub** | [FoundationAgents/MetaGPT](https://github.com/FoundationAgents/MetaGPT) |
| **Зірки** | 69 384 (липень 2026) |
| **Мова** | Python |
| **Ліцензія** | MIT |

| **Останній коміт** | січень 2026 |

#### Основна ідея

Теза MetaGPT вміщується в один рядок зі статті: `Code = SOP(Team)`. Закодуйте стандартну операційну процедуру софтверної компанії, призначте кожен крок ролі, і конвеєр створює артефакти, які створила б реальна команда. Кожна роль передає структурований документ наступній. Виконуваний цикл зворотного зв'язку повторює спробу до трьох разів, коли код не запускається.

Фреймворк здобув усну доповідь на ICLR 2024 і велику аудиторію. Він довів, що декомпозиція ролей плюс структуровані передачі перемагають одиночного агента в завданнях генерації з нуля.

#### Прочитайте дати перед упровадженням

Кількість зірок вводить в оману як сигнал активності. Останній позначений тегом реліз — v0.8.1 з квітня 2024, а репозиторій не отримував комітів із січня 2026. Увага команди перемістилася до MGX, хмарного комерційного продукту. Обіцяний open-source реліз v1.0 так і не вийшов.

Сприймайте MetaGPT як еталонну архітектуру, а не залежність. Його патерн структурованого артефакту між ролями вартий вивчення й трапляється майже в кожному фреймворку, що з'явився потім, включно з BMAD і Liza. Сам код відстає на два роки від останнього релізу.

#### Де він зупиняється

Довіра передбачається через дотримання процесу. Ніщо не заважає агентові проігнорувати SOP; система ставить на те, що чітко описану процедуру виконуватимуть. Обробка збоїв ґрунтується на повторах (той самий агент пробує знову), а не на структурі. Немає відновлення після аварій, немає межі ролей, що примусово діє поза prompt, і немає циклу рецензування, де другий агент може відхилити роботу першого.

### 4.4 Symphony (OpenAI)

Відповідь OpenAI на питання «що будувати поверх Codex?». Symphony стежить за дошкою Linear, створює ізольований робочий простір для кожного issue, породжує в ньому агента Codex і збирає доказ виконаної роботи перед тим, як PR потрапить у гілку.

| Атрибут | Деталі |
|-----------|---------|
| **GitHub** | [openai/symphony](https://github.com/openai/symphony) |
| **Зірки** | 25 969 (липень 2026) |
| **Мова** | Elixir (еталонна реалізація) |
| **Ліцензія** | Apache 2.0 |
| **Створено** | 26 лютого 2026 |
| **Останній коміт** | 9 червня 2026 |
| **Статус** | Інженерний прев'ю, без позначеного релізу |

#### Що він насправді робить

Слоган — «керуйте роботою, а не агентами». Symphony опитує трекер, відправляє агента на кожен issue у власний робочий простір і збирає свідчення, що робота справжня: статус CI, відгуки на PR, аналіз складності та відео-огляд. Інженер переглядає докази замість того, щоб спостерігати, як агент друкує.

Модель розповсюдження незвична: головна рекомендація репозиторію — не «встановіть наш бінарник», а «віддайте [SPEC.md](https://github.com/openai/symphony/blob/main/SPEC.md) вашому улюбленому агенту для програмування й попросіть його побудувати Symphony обраною вами мовою». Версія на Elixir — експериментальна еталонна реалізація, збудована на BEAM/OTP для супервізії та конкурентності. Специфікація і є продуктом.

Symphony припускає, що ви вже зробили [harness engineering](https://openai.com/index/harness-engineering/) для вашої кодової бази: зробили репозиторій зрозумілим для агентів через тести, документацію та інструменти. Він позиціонує себе як наступний крок після цього.

#### Прочитайте попереджувальну етикетку

README відкривається виділеним жирним попередженням, що це «low-key engineering preview for testing in trusted environments». Позначеного релізу немає, а репозиторій мовчить з 9 червня 2026. 26 265 зірок (2026-07-27) вимірюють охоплення розповсюдження OpenAI, а не готовність до production.

#### Де він зупиняється

Symphony навмисно вузький: планувальник, виконавець і зчитувач трекера. Він не рецензує і не примушує. Специфікація прямо стверджує, що вона «does not require a single approval, sandbox, or operator-confirmation policy», залишаючи позицію довіри тому, хто реалізує. Агент сам сертифікує свою роботу; немає другого агента, що може її відхилити. Еталонна реалізація працює лише з Codex.

Ця вузькість — вибір дизайну, а не недогляд. Якщо вам потрібні диспетчеризація та ізоляція робочих просторів, Symphony — чиста специфікація для копіювання. Якщо вам потрібен цикл рецензування чи шлюз злиття, ви будуєте його самі.

### 4.5 Paperclip

Організаційна схема для агентів. Paperclip моделює корпоративний апарат (ролі, бюджети, шлюзи схвалення, ланцюги делегування) і дозволяє спрямувати на нього будь-який runtime агента. Найшвидше зростаючий проєкт на всій цій сторінці.

| Атрибут | Деталі |
|-----------|---------|
| **GitHub** | [paperclipai/paperclip](https://github.com/paperclipai/paperclip) |
| **Зірки** | 74 900 (2026-07-27), 13 956 форків |
| **Мова** | TypeScript (сервер Node.js + React UI) |
| **Ліцензія** | MIT |
| **Створено** | 2 березня 2026 |
| **Останній реліз** | v2026.707.0 (7 липня 2026) |
| **Працює з** | Hermes Agent/OpenClaw, Claude Code, Codex, Cursor, Bash, HTTP |

#### Що він насправді робить

README формулює це точно: «If OpenClaw is an employee, Paperclip is the company.» Ви визначаєте ціль, наймаєте команду (CEO, CTO, інженерів, маркетологів, кожен спирається на будь-який обраний вами runtime агента), задаєте бюджети та стежите з дашборда. Він виглядає як менеджер завдань. Під ним — організаційні схеми, ліміти бюджету, правила управління та облік витрат за агентом, завданням і ціллю.

Незалежний від runtime за задумом, що підсумовує їхній власний рядок: «if it can receive a heartbeat, it's hired.» Саме це робить його цікавим поруч із Claude Code, а не у конкуренції з ним. Claude Code стає одним зі співробітників.

#### Чому важливе поширення

75K зірок і 14K форків (2026-07-27) приблизно за чотири місяці, з щотижневими релізами. Що б ви не думали про наратив «компанії без людей», поширення реальне, а проєкт підтримується. Навколо нього вже сформувалася екосистема plugin ([awesome-paperclip](https://github.com/gsxdsm/awesome-paperclip), шаблони company-wizard, адаптер Hermes від Nous Research).

#### Де він зупиняється

Довіра в Paperclip організаційна, а не поведінкова. Він керує тим, хто може діяти й скільки може витрачати, з автопаузою бюджету та журналами аудиту лише для додавання. Він не керує тим, як виконується робота всередині сесії агента. Їхня власна документація прямо каже, що це не інструмент code review. Ніщо тут не заважає агентові змінити тест, щоб зламаний код пройшов; це інший шар проблеми, який розв'язують [патерни управління spec-first](../workflows/spec-first.uk.md).

Інша й предметна область. Paperclip націлений на бізнес-операції загалом, а не конкретно на програмну інженерію. Якщо ваша мета — постачання коду, абстракція організаційної схеми може бути більшим апаратом, ніж потребує робота.

### 4.6 CLI agent orchestrator (CAO, AWS labs)

Агент-супервізор, що делегує агентам-воркерам, кожен з яких є справжнім процесом CLI у власній сесії tmux, координованим через MCP. Примітний з причини, що не стосується його функцій: це єдиний оркестратор у цій категорії з виправданим bus factor.

| Атрибут | Деталі |
|-----------|---------|
| **GitHub** | [awslabs/cli-agent-orchestrator](https://github.com/awslabs/cli-agent-orchestrator) |
| **Зірки** | 954 (2026-07-27), 184 форки, 73 відкриті issues (було 893 / 172 / 71 у липні 2026) |
| **Мова** | Python 3.10+, поширюється на PyPI як `cli-agent-orchestrator` |
| **Ліцензія** | Apache-2.0 |
| **Створено** | 29 липня 2025 |
| **Останній реліз** | v2.3.0 (12 липня 2026) |
| **Контриб'ютори** | 41, головний контриб'ютор має 20% комітів |
| **Працює з** | Claude Code, Kiro CLI, Codex CLI, Antigravity CLI, Hermes Agent, Kimi CLI, GitHub Copilot CLI, OpenCode, Cursor CLI |

#### Що він насправді робить

Один агент-супервізор запускає, надсилає повідомлення та координує кількох воркерів через три примітиви MCP: `handoff` (синхронний, чекає завершення), `assign` (асинхронний, «запустив і забув») і `send_message` (доставка в inbox між агентами). Кожен агент працює як повноцінний процес CLI в ізольованій сесії tmux, і це найважливіше рішення дизайну: оскільки він керує справжнім бінарником, а не обгортає API, нативні функції зберігаються, зокрема sub-agent Claude Code, власні агенти Kiro та автентифікація постачальників.

Звідси випливають два наслідки, які більшість оркестраторів запропонувати не може. Ви можете виконати `tmux attach` до будь-якого запущеного воркера й скеровувати його посеред завдання, а не чекати завершення sub-agent і сподіватися. І ви можете змішувати постачальників в одній сесії, закріплюючи профіль за певним CLI через frontmatter агента, тож супервізор Kiro може керувати воркерами Claude Code.

Навколо цього ядра розташовані заплановані потоки (автономні запуски у стилі cron), вбудований Web UI, сервер `cao-ops-mcp`, що дозволяє агентові породжувати й моніторити сесії CAO зі свого власного чат-циклу, постійна міжсесійна пам'ять через `memory_store` і `memory_recall`, та обмеження інструментів для кожного агента, оголошені як `role` плюс `allowedTools` у профілі, що транслюються у нативне примусове застосування кожного постачальника, де воно є.

#### Чому він узагалі тут

Ринкове дослідження липня 2026 року восьми open-source multi-agent оркестраторів, перевірене за GitHub API, а не за README проєктів, виявило сім із одним контриб'ютором, що тримає від 95% до 100% комітів. CAO був винятком: 41 контриб'ютор, головний тримає 20%.

Порівняння, яке має лишитися з вами: Mission Control ([builderz-labs/mission-control](https://github.com/builderz-labs/mission-control), MIT) має 5 862 зірки станом на 2026-07-27 (було 5 763), у 6,1 раза більше, ніж CAO, і одна людина написала 78% його комітів. Сортування цього ринку за зірками обирає майже точно не той інструмент. Позицію цього посібника щодо кількості зірок як показника поширення викладено в [Розділі 5](#the-model-lock-in-question) і в [`docs/resource-evaluations/README.md`](../../docs/resource-evaluations/README.md); CAO проти Mission Control — найчистіша ілюстрація цього в реальності.

#### Де він зупиняється

CAO володіє координацією і більше нічим. Він не постачає власного шлюзу якості й чесно це визнає: чи може агент оголосити «готово» на зламаному коді, залежить цілком від того, що запускає базовий CLI у своєму worktree. Обмеження інструментів стримують, які інструменти агент може викликати, а не те, чи правильний його вивід. Відповідайте на питання 1 [чекліста управління](../workflows/agentic-software-factories.uk.md#4-five-governance-questions-before-you-adopt-anything) самі, у власному CI, бо CAO цього за вас не зробить.

Ізоляція на рівні процесу, а не системи. tmux розділяє контексти та дає справжній доступ до PTY; це не sandbox. Агенти успадковують середовище, включно з секретами та конфігураціями. `cao-server` зміцнено саме для localhost (перевірка заголовка host проти DNS rebinding, WebSocket PTY відмовляється від не-loopback з'єднань), що вказує на призначене розгортання: ваша машина, а не спільний хост.

Станом на липень 2026 не існує опублікованого кейсу з виміряними результатами, що ставить його в те саме доказове становище, що й кожну комерційну платформу в цій категорії. Підтримка AWS Labs означає безперервність супроводу, а не доведені результати в production.

### 4.8 Liza

Liza — це multi-agent площина керування для роботи з кодом, що примусово застосовується кодом. Вона запускає CLI постачальників як воркерів, призначає кожне завдання парі виконавець/рецензент, ізолює їхні гілки в git worktrees і зберігає стан координації поза контекстом моделі.

| Атрибут | Деталі |
|-----------|---------|
| **GitHub** | [liza-mas/liza](https://github.com/liza-mas/liza) |
| **Зірки** | 363 (2026-08-28), 49 форків |
| **Ліцензія** | Apache-2.0 |
| **Мова** | Супервізори на Go, допоміжні утиліти на Python |
| **Останній реліз** | [v0.8.0](https://github.com/liza-mas/liza/releases/tag/v0.8.0), 2026-06-03 |
| **Каталог адаптерів** | Claude Code, Codex, OpenCode, Kimi, Gemini, Qwen, Mistral, Devin, Cursor; Gemini і Mistral вимкнені в закріпленому каталозі |
| **Знімок доказів** | [`a22c123`](https://github.com/liza-mas/liza/commit/a22c12381c5d884d2586a48aaaa517bca184f9cf), 2026-08-27 |

#### Що примусово застосовує код

[Модель супервізії](https://github.com/liza-mas/liza/blob/a22c12381c5d884d2586a48aaaa517bca184f9cf/specs/architecture/supervision-model.md) Liza розділяє семантичну роботу та детерміноване керування життєвим циклом. Агенти пропонують переходи завдань; супервізори на Go перевіряють володіння, стан, оренди, вердикти рев'ю та придатність до злиття. YAML-дошка (blackboard) переживає втрату контексту моделі, а покоління оренд ізолюють застарілих воркерів після відновлення. Кожен виконавець працює в ізольованому worktree, і окремий рецензент може відхилити подання, перш ніж супервізор дозволить інтеграцію.

Це робить Liza корисним прикладом поєднання двох шарів. Її шлях `liza init` встановлює ресурси репозиторного harness, як-от поведінкові контракти, skills, налаштування та guardrails. Режим MAS додає оркестратор над обраним runtime. [Каталог постачальників](https://github.com/liza-mas/liza/blob/a22c12381c5d884d2586a48aaaa517bca184f9cf/provider-catalog.yaml) підтверджує, що Claude Code, Codex та інші CLI досі володіють своїми внутрішніми циклами інструментів.

Переглянутий коміт містив 296 тестових файлів Go і пройшов завдання CI проєкту на Ubuntu та macOS. Цей огляд не запускав набір локально, бо Go був недоступний на хості огляду. CI upstream є корисним свідченням підтримки, але не встановлює якість завдань, успішність відновлення за production-навантаження чи безпеку щодо недовіреного репозиторію.

#### Де він зупиняється

Межа ізоляції Liza — git, а не операційна система. Кілька адаптерів постачальників вмикають широкі режими схвалення, зокрема `--dangerously-skip-permissions` в OpenCode і `--permission-mode dangerous` у Devin. Агенти все одно успадковують будь-яку файлову систему, середовище, облікові дані та мережевий доступ, які отримує базовий процес. Розмістіть sandbox на рівні ОС чи контейнера та облікові дані з обмеженим обсягом під Liza перед використанням без нагляду.

Проєкт також публікує незвично відвертий [реєстр архітектурних проблем](https://github.com/liza-mas/liza/blob/a22c12381c5d884d2586a48aaaa517bca184f9cf/specs/architecture/architectural-issues.md). Він фіксує залежність від одного оркестратора для семантичної інтерпретації, одного супервізора як шлюзу коректності, неповне перехресне рев'ю пар, прогалини зворотного зв'язку щодо якості специфікацій і тиск на контекст від поведінкового контракту. Ці обмеження роблять Liza придатною для ізольованого пілота на 8-12 тікетів, а не типовою production-залежністю лише на підставі кількості функцій.

Читайте Liza і як систему циклів, і як предметно-специфічний граф. Заморожена [конфігурація конвеєра](https://github.com/liza-mas/liza/blob/a22c12381c5d884d2586a48aaaa517bca184f9cf/internal/embedded/pipeline.yaml) визначає стабільний граф організації: ролі, пари ролей, словники станів, кворуми та переходи. Завдання й залежності під час виконання утворюють змінний граф роботи. Модель виконує семантичну роботу всередині вузлів; детермінований код Go перевіряє частини протоколу переходів. Liza не є загальним графовим runtime, бо її тип переходу навмисно вузький, а програми вузлів прив'язані до життєвого циклу програмування.

Межа відповідальності важливіша за мітку графа. Нелегальні переходи, застарілі заявки та невиконані кворуми відхиляються механічно. Чи достатній план або чи правильний патч, досі залежить від доказів і судження рецензента. Закріплений реєстр прямо вказує на невимірювану точність рецензента, суттєві рішення декомпозиції між парами, різноманітність постачальників, що є бажаною, а не гарантованою, і людські контрольні точки, що обмежують пропускну здатність. Оцінюйте коректність workflow і коректність завдання окремо. Протокол тестування див. в [Agent Evaluation](../roles/agent-evaluation.uk.md#evaluate-judgment-allocation-and-reviewer-independence).

Тепер існує один незалежний звіт практика. [Допис Ippon](https://blog.ippon.fr/2026/04/29/premier-rex-multi-agent-liza/) Іполіта Дюрікса описує невеликий запуск каталогу на Spring Boot, Vue.js і PostgreSQL: приблизно 30 завдань за 5 автоматизованих спринтів, 35 вердиктів рев'ю, 3 відхилення, виправлені й подані повторно, і 3-4 години людського часу. Автор також повідомляє про масове споживання токенів, потрібну людську валідацію етапів планування та відсутність тесту перехресного рев'ю між постачальниками. Це корисне операційне свідчення від реального користувача, але не production-бенчмарк: проєкт був навмисно простим, цифри самозвітні, а порівнянної базової лінії на рівні артефактів не опубліковано.

Мейнтейнер Liza також публікує окремий проєкт [bash-policy](https://github.com/liza-mas/bash-policy). Він розбирає складені shell-навантаження на командні одиниці, оцінює політику проєкту та видає рішення `allow`, `manual` або `deny`. Перевірений репозиторій не мав позначеного релізу та свідчень поширення, тож ставтеся до нього як до перевірюваного експерименту з політиками, а не зрілої залежності безпеки. Його межа все ж корисна: політика команд може обмежувати й аудитувати те, що агент просить запустити, але не забезпечує ізоляції файлової системи, облікових даних, процесів чи мережі. Поєднуйте її з нативним рушієм політик runtime і sandbox на рівні ОС.

Claude Code, Codex, Cursor, OpenCode та інші інструменти досі володіють своїми внутрішніми циклами модель-інструменти.

#### Що він насправді робить

Призначення issue, прямий чат, згадка або запланований Autopilot створює запуск у черзі сервера. Daemon на підключеному комп'ютері бере цей запуск, готує робочу директорію чи git worktree, викликає налаштований локальний CLI і передає прогрес, активність інструментів, помилки, використання токенів і фінальний результат назад до issue.

```text
issue / chat / mention / Autopilot
              |
              v
Multica server + PostgreSQL
              |
       queued run over WebSocket
              |
              v
daemon on a connected computer
              |
      worktree + local agent CLI
              |
              v
progress, logs, cost, result -> server timeline
```

Режим розгортання змінює те, де працює рівень координації, але не цей поділ виконання:

| Режим | Рівень координації | Рівень виконання |
|---|---|---|
| Multica Cloud | Multica розміщує вебзастосунок, API та базу даних | Ваш комп'ютер або хмарна машина запускає daemon, репозиторій, облікові дані та CLI агентів |
| Самостійне розміщення | Ви запускаєте вебзастосунок, API та PostgreSQL через Docker Compose або Helm | Одна чи кілька підключених машин запускають daemon і CLI агентів |

Якщо daemon офлайн, нові запуски лишаються в черзі. Запуски, що вже виконувалися, можуть зазнати збою й стати придатними до повтору; daemon повторно реєструє runtime і намагається відновитися, коли повертається. Це робить Multica чимось більшим за візуальний запускач сесій, водночас залишаючи міркування над завданням і виконання інструментів обраному CLI.

#### Межа даних і безпеки

Локальні репозиторії та облікові дані інструментів не завантажуються автоматично повністю. Сервер таки зберігає issues, коментарі, конфігурацію агентів, контекст запуску, записи виконання та результати. Значення агентів `custom_env` і конфігурація MCP зберігаються на сервері та передаються runtime, тож локальне виконання не означає, що кожен секрет чи артефакт завдання лишається на машині виконання.

[Задокументована модель безпеки](https://github.com/multica-ai/multica/blob/7a438bd5b8bf39afd54259a7eb0971390e50a8ef/apps/docs/content/docs/security-model.mdx) робить акаунт операційної системи, що запускає daemon, ефективною межею. Запуски можуть читати й записувати все, до чого цей акаунт має доступ, використовувати його облікові дані та мережу. Перевірені типові шляхи запускають Claude Code з `bypassPermissions`, а Codex з `danger-full-access`, окрім випадків, коли діє задокументоване увімкнення sandbox Codex на Windows. Використовуйте окремий акаунт ОС, контейнер чи VM з обмеженими обліковими даними Git і хмари перед виконанням без нагляду.

Стан `in_review` фіксує статус workflow всередині Multica. Він не налаштовує захист гілок і не замінює правил рев'ю та злиття хоста Git. Агенти можуть використовувати облікові дані, доступні на машині виконання, щоб пушити гілки чи відкривати pull request, тож політика репозиторію лишається точкою примусового застосування.

#### Де він зупиняється

Огляд коду охопив закріплений коміт, документацію, шляхи daemon, адаптери агентів, запити до бази даних, ліцензію та успішний upstream CI для цього коміту. Застосунок не запускали, і жодного реального запуску агента не виконували. Це встановлює архітектуру та заявлені засоби керування, але не наскрізну надійність, якість завдань, відновлення за навантаження чи захист від ворожого репозиторію.

Репозиторій описує себе як open source, але його ліцензія додає обмеження поверх Apache 2.0. Називайте його source-available, доки юридичний огляд не встановить вужчого висновку про використання. Команді, що оцінює Multica, слід провести пілот точної хмарної чи самостійно розміщеної топології з непродакшн-обліковими даними, захистом гілок, одним відновлюваним репозиторієм і відпрацьованим сценарієм відключення daemon.

### Питання прив'язки до моделі

Найпроясніше питання для вибору між Claude Code, Codex CLI, Hermes, Aider і Goose: чи має інструмент працювати рівно з одним постачальником моделей, чи з кількома?

Якщо ви віддані Claude та екосистемі Anthropic (підписка, Routines, Agent SDK, інструменти CLAUDE.md), Claude Code — однозначно правильний вибір. Інтеграція нативна, а швидкість появи функцій від Anthropic висока.

Якщо вам потрібна гнучкість моделей (локальні моделі для чутливого коду, дешевші моделі для рутинних завдань, конкретні моделі для бенчмаркінгу), Hermes Agent охоплює найширший діапазон з найбільшою автоматизацією. Aider і Goose — простіші альтернативи з меншим слідом.

Якщо ваша команда насамперед на OpenAI і вже платить за ChatGPT Pro, Codex CLI не коштує нічого додатково.

### Компроміс автономії та контролю

Вища автономія означає, що агент може виконати більше роботи без вашого нагляду, але й більше способів зійти зі шляху на неоднозначних завданнях. Правильний рівень автономії залежить від того, наскільки чітко визначені ваші завдання, а не від того, який інструмент «потужніший».

Claude Code headless (`claude -p`) і SWE-agent дають контрольовану автономію: ви задаєте завдання, агент працює, ви переглядаєте вивід. Devin дає максимальну автономію з хмарним sandbox: агент має повне Linux-середовище й може вчиняти дії, яких ви не передбачили. Більше потужності, більше рев'ю перед злиттям.

Інтерактивні агенти (термінал Claude Code, Hermes, Aider, Goose) дають контроль у реальному часі. Ви спостерігаєте, як агент думає, перенаправляєте його, коли він помиляється, і схвалюєте руйнівні дії. Для пошукової роботи, де вимоги змінюються посеред сесії, інтерактивний режим швидший за автономний, попри те що здається ручнішим.

Agentless — контрприклад до ставлення до автономії чи обсягу кандидатів як до показника якості. Його оцінка FSE 2025 використала обмежений трифазний workflow з GPT-4o на SWE-bench Lite і розв'язала 96 із 300 issues, тобто 32%, за середніх повідомлених витрат на інференс $0,70 на issue. Продуктивність виправлення вийшла на плато приблизно на 40 патчах-кандидатах. Результат отримано на одному бенчмарку з цінами API 2024 року й не враховує тестову інфраструктуру та людське рев'ю, тож це не production-прогноз. Він підтримує ідею тестувати обмежений workflow локалізації, виправлення та валідації, перш ніж додавати більше циклів агентів чи кандидатів. Джерело: [Xia et al., Demystifying LLM-Based Software Engineering Agents](https://lingming.cs.illinois.edu/publications/fse2025.pdf), DOI [10.1145/3715754](https://doi.org/10.1145/3715754), PDF с. 10-15, Таблиця 1 та Рисунок 6.
