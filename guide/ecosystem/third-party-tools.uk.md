# Інструменти спільноти Claude Code: 40+ розширень

Ця сторінка каталогізує створені спільнотою інструменти, що розширюють Claude Code, організовані за сценарієм використання. Записи перевірено за публічними репозиторіями чи реєстрами пакетів у різні дати; датовані версії, кількості та примітки про статус є знімками, а не поточним аудитом кожного інструмента. Для кожної категорії порівняння «Коли використовувати» пояснює, який інструмент підходить до якого воркфлоу, бо правильний вибір залежить від вашого стеку й обмежень, а не лише від кількості зірок.

Це не список AI-інструментів, що загалом доповнюють Claude Code. Він охоплює лише інструменти, чия основна мета полягає в розширенні самого CLI Claude Code. Ширше охоплення екосистеми AI дивіться в [AI Ecosystem](ai-ecosystem.uk.md). Рекомендації щодо серверів MCP дивіться в [MCP Servers Ecosystem](mcp-servers-ecosystem.uk.md).

Ці розширення можуть спостерігати, налаштовувати чи координувати Claude Code, але не обов'язково володіють циклом агента. Використовуйте [мапу Agent Harness](agent-harness-landscape.uk.md) для суворого порівняння runtime і ширшого каталогу з джерелами, [Agent Harness Engineering](../core/agent-harness.uk.md) для меж рівнів і [Agent Tools: Beyond Claude Code](agentic-tools.uk.md) для суміжних із runtime фреймворків і площин керування. Оцінюйте, спостерігайте й захищайте доданий інструмент через [Agent Evaluation](../roles/agent-evaluation.uk.md), [Session Observability](../ops/observability.uk.md) і [Security Hardening](../security/security-hardening.uk.md). [Глосарій](../core/glossary.uk.md) визначає розрізнення.

> **Історія верифікації**: початковий каталог перевірено в червні 2026 року; вибрані записи оновлено до жовтня 2026 року. Перевіряйте джерело кожного інструмента перед встановленням. 40+ інструментів у 18 категоріях.

## Про цю сторінку

На цій сторінці зібрано **створені спільнотою інструменти, які розширюють можливості Claude Code**. Кожен інструмент було перевірено на відповідність його публічному репозиторію або реєстру пакетів. Сюди включено лише інструменти з відкритим кодом (GitHub, npm, PyPI).

**Чим ця сторінка НЕ є**:
- Це не список ШІ-інструментів, які доповнюють Claude Code (див. [ШІ-екосистема](ai-ecosystem.uk.md))
- Це не скрипти для самостійного моніторингу (див. [Спостережуваність](../ops/observability.uk.md))
- Це не рекомендації серверів MCP (див. [Екосистема серверів MCP](mcp-servers-ecosystem.uk.md))

## Відстеження токенів та витрат

### ccusage

Найбільш зрілий інструмент відстеження витрат для Claude Code. Аналізує локальні дані сесій для створення звітів про витрати за день, місяць, сесію або 5-годинне вікно тарифікації.

| Атрибут | Деталі |
|---------|--------|
| **Джерело** | [npm: ccusage](https://www.npmjs.com/package/ccusage) / [ccusage.com](https://ccusage.com) |
| **Встановлення** | `bunx ccusage` (найшвидше) або `npx ccusage` |
| **Мова** | TypeScript (Node.js 18+) |
| **Версія** | 18.x (активно підтримується) |

**Ключові особливості**:

- `ccusage daily` / `ccusage monthly` / `ccusage session` — агреговані звіти про витрати.
- `ccusage blocks --live` — моніторинг у реальному часі відносно 5-годинних вікон тарифікації.
- Прапорець `--breakdown` для розділення витрат за моделями (Opus/Sonnet/Haiku).
- Фільтрація за датами за допомогою `--since` / `--until`.
- Вивід у форматі JSON (`--json`) для програмного доступу.
- Офлайн-режим із кешованими даними про ціни.
- Інтеграція сервера MCP (`@ccusage/mcp`).
- Віджет для macOS (`ccusage-widget`) та [розширення Raycast](https://www.raycast.com/nyatinte/ccusage).

**Обмеження**: покладається на локальний парсинг файлів JSONL; оцінки витрат можуть відрізнятися від офіційних рахунків Anthropic. Немає агрегації для команд без ручного об'єднання логів.

> **Посилання**: У головному посібнику базові команди `ccusage` описано в [ultimate-guide.md Розділ 2.4](../ultimate-guide.uk.md) (моніторинг витрат).
> Для створення власного відстеження витрат за допомогою гачків див. [Спостережуваність](../ops/observability.uk.md).

### CodeBurn

CodeBurn читає ті самі журнали сесій JSONL у `~/.claude/projects/`, що й ccusage, але відповідає на інше питання. Тоді як ccusage відповідає на "скільки я витратив?", CodeBurn відповідає на "на що я це витратив?", розбиваючи використання токенів за типом ходу й співвідносячи витрати з історією git через команду `yield`.

| Атрибут | Деталі |
|-----------|---------|
| **Джерело** | [GitHub: getagentseal/codeburn](https://github.com/getagentseal/codeburn) |
| **Встановлення** | `npm install -g codeburn` або `npx codeburn` |
| **Зірки** | 8 100+ (червень 2026; сторонні індексатори можуть показувати ~2,7K через затримку оновлення) |
| **Мова** | Node.js 22.13+ |
| **Версія** | v0.9.13 (14 червня 2026) |
| **Мультипровайдер** | Claude Code, Codex, Gemini CLI, Cursor, Cline/Roo |

**Ключові можливості**:

- `codeburn` - інтерактивний TUI-дашборд (за замовчуванням останні 7 днів)
- `codeburn today` / `codeburn month` / `codeburn overview` / `codeburn report` - підсумки за періодами
- `codeburn optimize` - сканує патерни марнотратства: цикли повторів, зайві повторні читання, покинуті сесії
- `codeburn compare` - порівняльна розбивка продуктивності моделей
- `codeburn yield` - співвідносить сесії з комітами git (які сесії випустили код, а які були покинуті чи відкочені)
- `codeburn models` - розбивка токенів і вартості за моделями
- `codeburn export` - вивід у CSV або JSON
- `codeburn menubar` - віджет у рядку меню macOS (SwiftBar)
- `codeburn plan set [claude-max|claude-pro|custom]` - відстеження плану підписки
- Сервер MCP (v0.9.12+): надає дані про використання та економію іншим агентам

**Класифікація ходів**: CodeBurn класифікує кожен хід у 13 категорій за допомогою локального детермінованого зіставлення патернів (без викликів LLM). Категорії включають Coding, Debugging, Refactoring, Testing, Exploration, Brainstorming, Planning, Feature Dev, Delegation, Git Ops і Conversation. Найдіагностичніша знахідка на практиці: ходи "Conversation" (модель відповідає без використання інструментів) часто становлять 40-56% витрат сесії. Приклади від творця: завдання з автентифікацією JWT, де 5 200 із 15 600 токенів пішли на виправлення типів, і міграція PostgreSQL, де 19 400 із 40 700 токенів пішли на налагодження зовнішніх ключів. Це ілюстративні точки даних, а не відтворювані бенчмарки.

**Обмеження**: лише для читання, тож не може перервати "втікаючу" сесію. Оцінки вартості використовують ціни LiteLLM, а не дані API виставлення рахунків Anthropic, тому цифри можуть відрізнятися на $1-2 за сесію від рахунків. Залежить від формату: зміна схеми JSONL в Anthropic зламає розбір, доки CodeBurn не оновиться. Не внесений до реєстру awesome-claude-code.

**Коли використовувати CodeBurn проти ccusage**: ccusage є правильним вибором за замовчуванням для моніторингу витрат і відстеження вікон виставлення рахунків. CodeBurn додає криміналістичний аналіз: які типи ходів формують ваші витрати, які сесії створили код, що був випущений, де цикли повторів роздувають вартість. Використовуйте обидва разом.

### ccburn

Консольний графічний інтерфейс (TUI) на Python для візуального відстеження швидкості споживання токенів (burn-rate). Відображає графіки споживання відносно тарифікаційних вікон Claude.

| Атрибут | Деталі |
|---------|--------|
| **Джерело** | [GitHub: JuanjoFuchs/ccburn](https://github.com/JuanjoFuchs/ccburn) / [Стаття в блозі](https://juanjofuchs.github.io/ai-development/2026/01/13/introducing-ccburn-visual-token-tracking.html) |
| **Встановлення** | `pip install ccburn` |
| **Мова** | Python 3.10+ (Rich + Plotext) |

**Ключові особливості**:

- Термінальні графіки, що показують споживання токенів із часом.
- Індикатори швидкості споживання (попередження про дотримання лімітів або необхідність уповільнення).
- Компактний режим відображення.
- Візуальне відстеження бюджету відносно встановлених лімітів.

**Обмеження**: екосистема тільки на Python. Менша спільнота, ніж у `ccusage`. Немає інтеграції з MCP.

**Коли обирати ccburn замість ccusage**: якщо ви віддаєте перевагу візуальним графікам швидкості споживання замість табличних звітів або якщо ваш інструментарій побудований на Python.

### Straude

Соціальний дашборд для відстеження та обміну статистикою використання Claude Code (та OpenAI Codex). Надсилайте свої щоденні витрати та споживання токенів у публічну таблицю лідерів, щоб відстежувати свою активність (streak), щотижневі витрати та глобальний рейтинг.

| Атрибут | Деталі |
|---------|--------|
| **Джерело** | [npm: straude](https://www.npmjs.com/package/straude) |
| **Сайт** | [straude.com](https://straude.com) |
| **Встановлення** | `npx straude@latest` |
| **Мова** | TypeScript (Node.js 18+) |
| **Версія** | 0.1.9 (активна розробка, створено в лютому 2026) |
| **Підтримка** | Спільнота (oscar.hong2015@gmail.com) |

**Ключові особливості**:

- `straude`: розумна синхронізація: авторизація + надсилання статистики однією командою.
- `straude push --dry-run`: попередній перегляд даних перед відправкою без реального надсилання.
- `straude push --days N`: заповнення даних за останні N днів (максимум 7).
- `straude status`: інформація про активність, щотижневі витрати, загальну кількість токенів та глобальний рейтинг.
- Підтримка відстеження як для Claude Code (`ccusage`), так і для OpenAI Codex (`@ccusage/codex`).

**Що надсилається на сервер Straude**:

За кожен день: витрати в USD, кількість токенів (вхідні, вихідні, створення кешу, читання кешу), назви використаних моделей (наприклад, `claude-sonnet-4-6`), деталізація витрат за моделями. Також надсилається SHA256-хеш вихідних даних, випадковий UUID пристрою та ім'я хоста вашої машини.

Ваш вихідний код, API-ключі та вміст розмов **не** зчитуються і **не** передаються.

**Примітки з безпеки**:

- Токен авторизації зберігається в `~/.straude/config.json` із правами доступу `0600` (лише для власника).
- Проєкт дуже молодий (створений 2026-02-18, швидка ітерація) — публічного аудиту безпеки немає.
- Ім'я хоста машини надсилається як `device_name`.
- Станом на березень 2026 року публічна політика конфіденційності відсутня.
- Використовуйте `--dry-run` для перевірки того, що саме буде надіслано, перед першим пушем.

**Коли обирати Straude замість ccusage/ccburn**:

Straude є одним із двох соціальних інструментів у цьому списку: він завантажує вашу статистику на спільну платформу. Якщо вам потрібна таблиця лідерів, відстеження активності або порівняння свого використання з іншими розробниками, підійдуть і Straude, і viberank (нижче); ccusage та ccburn лишаються суто локальними без наслідків для обміну даними.

> **Нагадування про безпеку**: Перед запуском будь-якого CLI-інструменту спільноти через `npx` перевіряйте його сторінку npm та вихідний код на наявність підозрілих речей. Для Straude скомпільований код є читабельним та відповідає заявленим цілям. Повний аналіз див. у [оцінці ресурсів](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/docs/resource-evaluations/straude-evaluation.md).

### viberank

Публічна таблиця лідерів використання AI-кодування, що читає ті самі локальні дані `ccusage`, що й Straude, але з ширшим охопленням: надходження приходять від Claude Code, Codex, Gemini CLI, Copilot, OpenCode та інших інструментів, які відстежує ccusage, а не лише від Claude Code і Codex.

| Атрибут | Деталі |
|-----------|---------|
| **Джерело** | [GitHub: sculptdotfun/viberank](https://github.com/sculptdotfun/viberank) |
| **Вебсайт** | [viberank.app](https://viberank.app) |
| **Встановлення** | `npx viberank-cli` |
| **Зірки** | 114 (2026-08-24) |
| **Ліцензія** | MIT |
| **Мова** | TypeScript |
| **Створено** | 3 липня 2025 |

**Ключові можливості**:

- Глобальні та окремі за інструментами таблиці лідерів (Claude Code, Codex, OpenCode та інші), ранжовані за виміряними витратами токенів
- Рівні витрат від Spark ($0+) до Supernova ($50K+)
- Верифіковане прив'язування профілю GitHub і бейджі для README
- Надсилання через `npx viberank-cli`, команду curl або ручне завантаження через вебінтерфейс
- Публікує агрегований розподіл витрат через безкоштовний JSON API під CC BY 4.0

**Що надсилається на сервер viberank**: лише агреговані підсумки, токени, вартість, дати та назви моделей, згідно із заявленою поведінкою CLI. На відміну від Straude, без імені хоста чи UUID пристрою.

**Коли обирати viberank замість Straude**: viberank охоплює більше інструментів, ніж Claude Code і Codex, а його набір даних опубліковано відкрито, а не залишено за інтерфейсом таблиці лідерів. Straude додає відстеження серій і подачу у стилі застосунку для тренувань; обирайте те охоплення інструментів і соціальне оформлення, що підходить.

### RTK (Rust Token Killer)

Проксі-CLI, який фільтрує вивід команд **до того**, як він потрапить у контекст Claude. 82 094 зірки (GitHub API, 2026-09-30), зростання з 73 531 зірки й 4 597 форків на 2026-07-27, 69 042 на 2026-07-07, 24 397 у квітні 2026 і 446 у лютому 2026, що продовжує ту саму круту криву зростання, яку варто звірити з повним графіком історії зірок, перш ніж цитувати у відповідальному контексті.

> **Розкриття**: автор цього посібника на ранньому етапі долучився до RTK і лишається його прихильником, не беручи нині активної участі в його коді (не є його творцем). Незалежні вимірювання цілих завдань наведені в [context-engineering-tools.md](context-engineering-tools.uk.md).

| Атрибут | Деталі |
|---------|--------|
| **Джерело** | [GitHub: rtk-ai/rtk](https://github.com/rtk-ai/rtk) |
| **Сайт** | [rtk-ai.app](https://www.rtk-ai.app/) |
| **Встановлення** | `brew install rtk` (рекомендовано в README), інсталяційний скрипт `curl -fsSL https://raw.githubusercontent.com/rtk-ai/rtk/refs/heads/master/install.sh \| sh` або `cargo install --git https://github.com/rtk-ai/rtk` (на crates.io існує інший крейт "rtk") |
| **Мова** | Rust (автономний бінарний файл) |
| **Версія** | Останній реліз v0.50.0 (2026-09-30); перелік можливостей нижче написано для v0.28.0 |

**Ключові особливості**:

- `rtk git log` (зниження на 92%), `rtk git status` (зниження на 76%), `rtk git diff` (зниження на 56%).
- `rtk vitest run`, `rtk prisma`, `rtk pnpm` (зниження на 70-90%).
- `rtk python pytest`, `rtk mypy`, `rtk go test` (підтримка багатьох мов).
- `rtk cargo test/build/clippy/nextest` (інструментарій Rust).
- `rtk aws`, `rtk psql`, `rtk docker compose`, `rtk gt` (Graphite CLI).
- `rtk wc` — компактний підрахунок слів, рядків та байтів.
- `rtk init --global` — встановлення з автоматичним патчем `settings.json` для інтеграції гачків.
- `rtk gain` / `rtk gain -p` — аналітика економії токенів (глобальна + за проєктами).
- **TOML Filter DSL**: додавання власних фільтрів виводу для будь-якої команди без написання коду на Rust, через `.rtk/filters.toml` (проєктний) або `~/.config/rtk/filters.toml` (глобальний), 33+ вбудованих фільтрів.
- `rtk rewrite` — єдине джерело істини для мапінгу команд гачків (v0.25.0+, вимагає `rtk init --global` після оновлення).
- Конфігурація `exclude_commands` для виключення конкретних команд з автоперезапису.

**Коли обирати RTK порівняно з ccusage/ccburn**:

- RTK **зменшує** споживання токенів (препроцесинг).
- ccusage/ccburn **моніторять** його (постпроцесинг).
- Використовуйте їх разом для максимальної ефективності.

**Обмеження**: не підходить для інтерактивних команд або дуже малого виводу (<100 символів).

> **Посилання**: Повна документація доступна в [ultimate-guide.md Розділ 9](../ultimate-guide.uk.md#оптимізація-виводу-команд-з-rtk).

### Примітка про сліпу пляму виставлення рахунків Рівня 4

Шлюзи рівня API (Helicone, Portkey, Langfuse, Bifrost, Compresr) перехоплюють HTTP-виклики й вимірюють використання токенів на рівні API. Це добре працює для застосунків, що викликають API Anthropic напряму. Це не працює для підписок Claude Code Max чи Pro, бо Claude Code підключається напряму до серверів Anthropic з обліковими даними підписки, а не API-ключем. Немає HTTP-шару, який міг би перехопити шлюз.

Усі чотири інструменти вище (Claude Code Usage Monitor, claude-spend, cc-statistics, claude-context-optimizer) працюють, розбираючи локальні файли сесій, які Claude Code записує на диск. Цей підхід не залежить від режиму виставлення рахунків: він однаково працює і з виставленням за API-ключем, і з підписками Max/Pro. Якщо ви на підписці Max і ваш шлюз показує нуль трафіку Claude Code, це очікувана поведінка, а не помилка налаштування.

## Стиснення контексту

Інструменти, що зменшують токени, які потрапляють у контекст LLM, через стиснення, відкладене завантаження чи інтелектуальну фільтрацію, доповнюють інструменти відстеження вище.

Tokenade поєднує локальну фільтрацію виводу, навігацію кодом, проксування MCP, дедуплікацію та інструкції стислого виводу. Покриття залежить від інтеграції з агентом; Codex CLI і Codex desktop є окремими записами в таблиці сумісності вендора.

Вендор тепер публікує [pi-infected/tokenade](https://github.com/pi-infected/tokenade), створений 2026-10-18 і тут не переглянутий |

**Порівняно з RTK:** Tokenade змінює більше, ніж вивід оболонки. Його [маніфест THOL](https://github.com/pi-infected/token-harness-optimizer-leaderboard/blob/main/competitors/tokenade/manifest.json) також змінює інструкції та налаштування контексту. RTK підтримує компактне читання файлів через свій CLI, включно з виводом лише сигнатур; його hook Bash для Claude Code не перехоплює нативні виклики Read/Grep. Не повторюйте загальне виключення стиснення файлів RTK чи нативної підтримки Windows із порівняння вендора.

**Межа бенчмарка:** [дані кампанії THOL](https://github.com/pi-infected/token-harness-optimizer-leaderboard/blob/main/docs/data/results.json), що підтримуються вендором, для Claude Code 2.1.206 повідомляють співвідношення вартості Tokenade 0.8.13 0,768 проти контролю (95% інтервал 0,647-0,900) і RTK 0.42.3 на рівні 1,052 (0,913-1,190). Кожна група має 170 успішних запусків у 17 завданнях. Це геометричні середні співвідношень по завданнях. Експеримент на користь повної конфігурації Tokenade в межах цієї кампанії; він не ізолює внесок кожного механізму й не доводить еквівалентності для RTK. Враховуйте ліцензію, налаштування, відновлення й якість при оцінці власного навантаження.

Перевіряйте hooks, що перекриваються, перш ніж поєднувати оптимізатори. Публічний інсталятор не є доказом того, що пропрієтарний рушій зберігає кожну деталь або передає лише задекларовану телеметрію.

### lean-ctx

Local-first CLI стиснення контексту та сервер MCP, написаний на Rust. Встановлюється один раз глобально й активується в кожному проєкті Claude Code без налаштування для кожного проєкту.

| Атрибут | Деталі |
|-----------|---------|
| **Джерело** | [GitHub: yvgude/lean-ctx](https://github.com/yvgude/lean-ctx) |
| **Встановлення** | `curl -fsSL https://raw.githubusercontent.com/yvgude/lean-ctx/main/skills/lean-ctx/scripts/install.sh \| bash && lean-ctx setup` |
| **Мова** | Rust |
| **Зірки** | ~1 366 |
| **Версія** | v3.6.3 |

**Як це працює**

lean-ctx реєструється як глобальний сервер MCP (`~/.claude.json`) і встановлює три hooks у `~/.claude/settings.json`, що спрацьовують на кожному виклику інструмента:

- `PreToolUse hook redirect`: перехоплює нативні виклики Read і спрямовує їх на `ctx_read` (розбір AST + кеш файлів)
- `PreToolUse hook rewrite`: спрямовує виклики Bash через `ctx_shell` (стиснення оболонки на основі патернів)
- `PostToolUse / SessionEnd hook observe`: живить міжсесійну пам'ять CCP

**4 виміри стиснення**

- **Читання файлів із розбором AST**: tree-sitter розбирає TypeScript, Python, Rust та ще 15 мов. Режим `signatures` повертає лише сигнатури типів і функцій (без тіл). Режим `map` повертає експорти та залежності. `schema.prisma` на 2364 рядки стискається приблизно до 200 токенів. Незмінені файли віддаються з кешу за ~13 токенів при повторному читанні.
- **Вивід оболонки**: понад 60 патернів стиснення, специфічних для git, cargo, npm, docker і kubectl. `git log -10 --stat` стає 10 рядками комітів плюс одним підсумком.
- **Міжсесійна пам'ять (CCP: Context Continuity Protocol)**: зберігає підсумок сесії на ~400 токенів при виході. Наступна сесія завантажує його замість холодного читання понад 50 000 токенів попереднього контексту.
- **Граф кодової бази**: граф залежностей на основі SQLite, побудований з імпортів/експортів tree-sitter у 18 мовах. `ctx_overview` використовує його для оцінки файлів за центральністю імпортів і виведення найбільш пов'язаних модулів першими.

**Виміряні бенчмарки (монорепозиторій TypeScript/T3, 2455 файлів)**

| Метрика | Значення |
|--------|-------|
| Загальна частка стиснення | 57,8% |
| Частка економії ctx_read | 86% |
| Частка економії ctx_search | 72% |
| Токенів заощаджено за один день | 1,3M |
| schema.prisma 2364L у режимі signatures | ~200 токенів (99%) |
| Повторне читання файлу (влучання в кеш) | 13 токенів |

Результати нижчі на репозиторіях із переважно Markdown, бо парсер AST знаходить менше структури для стиснення у файлах документації, ніж у вихідному коді TypeScript чи Rust.

#### RTK проти lean-ctx: взаємодоповнювальні шари

Обидва інструменти зменшують споживання токенів, але працюють у різних точках конвеєра й не конфліктують:

| Шар | Інструмент | Що стискає |
|-------|------|--------------------|
| Вивід CLI (shell hook) | RTK | Текст виводу git, cargo, npm, tsc |
| Читання файлів (перенаправлення MCP) | lean-ctx | Вміст файлів через AST + кеш |
| Міжсесійна пам'ять | lean-ctx | Підсумки сесій через CCP |

RTK стискає вивід оболонки агресивніше (економія 60-90%). Економія lean-ctx майже повністю походить від читання файлів (86% загальної економії на виміряних сесіях). Використовуйте обидва разом.

**Моніторинг**

```bash
lean-ctx gain           # dashboard: tokens saved, USD, top commands
lean-ctx gain --daily   # day-by-day breakdown
lean-ctx cep            # efficiency score /100 (compression, cache hit rate, consistency)
lean-ctx dashboard      # web UI at localhost:3333
```

Глобальна slash-команда `/lean-ctx-audit` (`~/.claude/commands/lean-ctx-audit.md`) запускає повний аудит із будь-якої сесії. Повне порівняння інструментів і посібник із налаштування дивіться в [context-engineering.md §12](../core/context-engineering.uk.md#18-інструменти-стиснення-токенів).

**Коли впроваджувати lean-ctx**

Найвища цінність у проєктах на TypeScript, Rust чи Python, де великі файли читаються повторно протягом сесії, сесії заповнюють контекст до завершення завдання або важлива міжсесійна пам'ять. Менш впливовий на репозиторіях документації, де більшість файлів у Markdown.

> **Примітка**: lean-ctx випускається часто. Запускайте `lean-ctx setup` після оновлень, щоб оновити реєстрацію hook і MCP. Для фільтрації лише виводу оболонки RTK є простішою відправною точкою.

### maki

Автономний TUI-агент на Rust (з використанням ratatui), що повністю замінює Claude Code, а не доповнює його. maki не є плагіном Claude Code чи доповненням MCP; це альтернативний агент із власним інтерфейсом і архітектурою керування контекстом.

| Атрибут | Деталі |
|-----------|---------|
| **Джерело** | [github.com/tontinton/maki](https://github.com/tontinton/maki) |
| **Мова** | Rust (TUI ratatui) |
| **Архітектура** | Автономний агент (замінює Claude Code) |
| **Провайдери LLM** | Anthropic, OpenAI, Google, Copilot, Ollama, Mistral, DeepSeek, OpenRouter |

**Інструменти ефективності контексту, вбудовані в maki**:

Інструмент `index`: скелет tree-sitter із точними діапазонами рядків. Виміряні накладні витрати на хід: +59 токенів (сам виклик index). Виміряна економія на хід: -224 токени на читаннях. Нетто: -165 токенів на хід. README maki зазначає, що вивід bash становить лише 12% загального використання токенів у типовій сесії, тож стиснення bash у стилі RTK заощаджує щонайбільше близько 6% загальної вартості. Читання файлів (65% загалом) є місцем, де більші виграші.

Інструмент `code_execution`: вбудований інтерпретатор Python (monty), що може фільтрувати, перетворювати й агрегувати дані перед тим, як вони потраплять у вікно контексту. Замість того, щоб модель читала сирий файл для підрахунку чогось, вона пише й запускає скрипт; у контекст потрапляє лише результат.

Інструмент `task`: делегування sub-agent із динамічним вибором моделі (haiku для простих підзавдань, sonnet чи opus для складних), що тримає дорогі виклики моделі пропорційними фактично потрібним міркуванням.

**Важливе розрізнення**: maki архітектурно відокремлений від Claude Code. Ви не можете використовувати maki як розширення Claude Code; вибір maki означає заміну Claude Code в сесіях, де ви його використовуєте. Команди, прив'язані до екосистеми Claude Code (hooks, skills, ієрархія CLAUDE.md, реєстр MCP), не виграють від внутрішніх інструментів maki. maki найактуальніший, якщо ви хочете єдиний інструмент, що працює з кількома провайдерами LLM, або віддаєте перевагу автономному бінарнику Rust без зовнішніх залежностей.

**Коли варто розглянути maki**:

- Ви працюєте з кількома провайдерами LLM і хочете єдиний інтерфейс
- Вам потрібне тонке керування контекстом без встановлення окремих серверів MCP
- Ви будуєте чи експериментуєте з архітектурою агентів і хочете доступ до внутрішніх механізмів

**Коли Claude Code лишається кращим вибором**:

- Ви покладаєтеся на систему hooks, skills чи path-scoping CLAUDE.md у Claude Code
- Ваша команда ділиться конфігураціями серверів MCP через `.mcp.json`
- Вам потрібні специфічні для Claude можливості (розширене мислення, Projects, системи пам'яті)

### mcp2cli

Універсальний міст CLI, що перетворює будь-який сервер MCP, специфікацію OpenAPI чи ендпоінт GraphQL на команди оболонки без впровадження схем інструментів у контекст LLM. Ключове спостереження: більшість клієнтів MCP на кожному ході вштовхують у контекст повну схему кожного зареєстрованого інструмента, потрібна вона агентові чи ні. mcp2cli замінює це відкладеним завантаженням.

| Атрибут | Деталі |
|-----------|---------|
| **Джерело** | [GitHub: knowsuchagency/mcp2cli](https://github.com/knowsuchagency/mcp2cli) |
| **Встановлення** | `uvx mcp2cli --help` (без встановлення) або `uv tool install mcp2cli` |
| **Мова** | Python |
| **Зірки** | ~1 900 |
| **Статус** | Активний (Show HN Best of March 2026) |

**Як працює відкладене завантаження**:

Замість впровадження повних схем інструментів (~44 000 токенів для сервера GitHub MCP із 43 інструментами) агент:

1. Викликає `mcp2cli --mcp <url> --list` → отримує ~16 токенів на інструмент (назва + короткий опис)
2. Викликає `mcp2cli --mcp <url> <tool-name> --help` → отримує ~120 токенів (повна схема, один інструмент)
3. Виконує інструмент із правильними аргументами

Повні схеми ніколи не потрапляють у контекст LLM, якщо їх явно не запитано.

**Бенчмарки** (незалежно відтворені Firecrawl, Scalekit, CircleCI):

- Сервер GitHub MCP (43 інструменти), просте завдання: 44 026 токенів (нативний MCP) проти 1 365 токенів (патерн gh CLI / mcp2cli), зменшення в 32 рази
- Частка збоїв на тих самих завданнях: нативний MCP 28%, патерн CLI 0% (переповнення контексту = пропущені кроки)
- 120 інструментів, 25 ходів: нативний MCP вводить ~362 000 токенів схем, перш ніж почнеться реальна робота

**Ключові можливості**:

- **Мультиджерельність**: MCP (HTTP/SSE/stdio), специфікації OpenAPI, GraphQL в одному бінарнику
- **Автентифікація**: OAuth 2.1 з PKCE для інтерактивного використання, облікові дані клієнта для конвеєрів CI/CD, кероване оновлення токенів
- **Демон + пул з'єднань**: з'єднання MCP на холодному старті займають 2-5 секунд. Демон тримає їх теплими для повторного використання з мілісекундною затримкою.
- **Формат `--toon`**: токен-ефективне кодування виводу, що скорочує токени відповідей на 40-60% проти звичайного JSON
- **Семантичні коди виходу**: `validation_error`, `auth_failure`, `tool_error`, `connection_error`, щоб shell-скрипти могли розгалужуватися без розбору тексту

```bash
# No-install test
uvx mcp2cli --mcp https://mcp.example.com/sse --list

# Execute a tool
mcp2cli --mcp https://mcp.example.com/sse search --query "test"

# Local stdio server
mcp2cli --mcp-stdio "npx @modelcontextprotocol/server-filesystem /tmp" --list

# OpenAPI spec
mcp2cli --spec ./openapi.json --base-url https://api.example.com list-pets

# Reusable config (baked alias)
mcp2cli bake create petstore --spec URL && mcp2cli @petstore --list
```

**Коли використовувати mcp2cli**:

- Ви використовуєте сервери MCP із багатьма інструментами (10+) і бачите, що контекст заповнюється схемами до початку реальної роботи
- Ви хочете налагоджувати чи тестувати сервер MCP з терміналу без розгортання повного клієнта
- Ваш конвеєр CI/CD споживає інструменти MCP програмно

**Коли не використовувати**:

- Корпоративні мультитенантні контексти, що вимагають OAuth для кожного користувача й журналів аудиту (нативні шлюзи MCP справляються краще)
- Агенти, що використовують добре відомі нативні CLI (gh, git, kubectl): модель знає їхній інтерфейс із навчальних даних, міст не потрібен
- Менше ~10 інструментів на сервер: виграш реальний, але не нагальний

> **Застереження щодо назви**: щонайменше чотири непов'язані проєкти на GitHub мають назву "mcp2cli" (Python, Go, Bun та інші). Еталонною реалізацією для цього випадку є [knowsuchagency/mcp2cli](https://github.com/knowsuchagency/mcp2cli). Перевірте автора перед встановленням.

### Entire CLI

| Атрибут | Деталі |

| **Встановлення** | `brew install --cask entireio/tap/entire`, `curl -fsSL https://entire.com/install.sh \| bash` або `irm https://entire.com/install.ps1 \| iex` у Windows |
| **Мова** | Go |
| **Компанія** | Entire, заснована Thomas Dohmke (екс-CEO GitHub), $60M seed оголошено 10 лютого 2026 |
| **Статус** | CLI 0.10.x (жовтень 2026). Хостований форж запущено 26 жовтня 2026 |

**Ключові можливості (локальний CLI, акаунт не потрібен):**

- **Фіксування сесій**: кожен коміт з роботою агента отримує контрольну точку (промпти, транскрипт, торкнуті файли), пов'язану трейлером `Entire-Checkpoint`
- **Git-нативне сховище**: один ref на контрольну точку під `refs/entire/checkpoints/` (за замовчуванням з CLI 0.10.0; старіші репозиторії використовують гілку `entire/checkpoints/v1`). До вашої гілки не додається жоден коміт

- **Міжагентне відновлення**: `entire session resume <branch>` відновлює сесії гілки у вашому агенті
- **Редагування**: сканування секретів перед кожним записом, визначені користувачем пакети правил, необов'язковий шар PII
- **Агенти**: Claude Code, Codex, Cursor, Copilot CLI, OpenCode, Antigravity, Factory AI Droid, Pi та інші через плагіни

**Лише хостований форж:** Trails з оцінюваним агентом рев'ю та шлюзи злиття (схвалення людей, знахідки, CI), розподілений хостинг Git, спільна пам'ять проєкту. Див. [Агентно-нативні Git-форжі](#агентно-нативні-git-форжі-2026).

**Юзкейси**:

| Сценарій | Чому саме Entire CLI |
|----------|----------------------|
| **Докази для аудиту** | Промпти, транскрипт і файли, пов'язані з кожним комітом, зберігаються в Git |
| **Мультиагентні воркфлоу** | Сесії можна відновлювати між агентами |
| **Відлагодження рішень ШІ** | Простежити рядок до його промпту й сесії |
| **Управління злиттям** | Шлюзи на Trails (хостований форж) |
| **Передача завдань у команді** | Відновлення гілки з її сесіями |

**Порівняння з claude-code-viewer**:

| Функція | claude-code-viewer | Entire CLI |
|---------|-------------------|-----------|
| **Призначення** | Перегляд історії (лише читання) | Фіксування сесій, пов'язане з комітами + відновлення |
| **Сховище** | Читає локальні журнали Claude Code | Контрольні точки надсилаються разом із репозиторієм |
| **Контекст** | Тільки розмова | Промпти + транскрипт + торкнуті файли |
| **Управління (Governance)**| Ні | Шлюзи злиття на хостованому форжі |
| **Мультиагентність** | Ні | Так (міжагентне відновлення) |
| **Накладні витрати** | Немає | Refs контрольних точок у репозиторії (виміряйте) |

**Коли обирати Entire замість claude-code-viewer**:
- ✅ Команді потрібно ділитися контекстом за комітами.
- ✅ Докази аудиту коду, написаного агентом.
- ✅ Мультиагентні воркфлоу.
- ❌ Потрібно просто переглянути власну історію → використовуйте `claude-code-viewer` (він легший).

**Обмеження**:
- CLI до 1.0; формат зберігання вже змінювався один раз (гілка на refs)
- Транскрипти надсилаються разом із репозиторієм: публічний репозиторій їх публікує, якщо контрольні точки не йдуть в окремий приватний репозиторій (`entire configure --local --checkpoint-remote github:<owner>/<repo>`)
- Shadow-гілки локально зберігають нередаговані знімки робочого дерева
- Для Entire на entire.com чи docs.entire.com не знайдено атестації SOC 2, ISO 27001, HIPAA чи FedRAMP (27 жовтня 2026)

**Різниця з типовими конфігураціями**:

| Потреба | Типова наявна схема | Що додає Entire |
|---------|---------------------|-----------------|
| Логування викликів інструментів | Локальний JSONL (ротація 7 днів) | Редаговані транскрипти зберігаються в Git |
| Атрибуція Людина/ШІ | Відсутня | Атрибуція за сесіями на entire.com (хостований) |
| Передача між агентами | Ручне копіювання контексту | `entire session resume` між агентами |
| Передача між розробниками | Коміти в Git / PR | Контрольні точки надсилаються разом із кодом |
| Постійність сесій | Тільки локально, тимчасово | Нативно для Git, можна ділитися |
| Управління (Governance) | Кастомні pre-commit hooks | Шлюзи злиття на Trails (хостований форж) |

**Оцінка (перед впровадженням у команді рекомендується пробний тест)**:

```bash
entire enable  # Встановлення на тимчасову гілку

# Після 2-3 звичайних сесій:
git for-each-ref refs/entire/checkpoints/ | wc -l   # Створені контрольні точки
git count-objects -vH                               # Ріст репозиторію
time git push                                       # Накладні витрати на push → тривога, якщо > 5s
ls .git/hooks/                                      # Перевірка на відсутність конфліктів із наявними hooks
```

Критерії зупинки (приклади значень, підлаштуйте під свою команду): ріст репозиторію, який ви не можете прийняти, затримка push > 5 секунд або конфлікти hooks.

### Агентно-нативні Git-форжі (2026)

Агенти кодування роблять push значно частіше за людей, і кілька вендорів тепер перебудовують хостинг Git і рев'ю коду навколо цього навантаження. Перевірено 27 жовтня 2026 за первинним джерелом кожного вендора. Усі цифри продуктивності нижче є вимірюваннями вендорів: незалежного відтворення не знайдено.

| Продукт | Що це | Сумісність із Git | Статус |
|---------|-----------|-------------------|--------|
| **[Entire](https://entire.com/blog/the-git-forge-for-agent-human-collaboration)** | Git-форж, побудований навколо агентів: Trails замінюють pull request, розподілений хостинг, спільна пам'ять проєкту | Стандартний Git; нативний хостинг або дзеркало GitHub | Запущено 26 жовтня 2026 |
| **[Cursor Origin](https://forum.cursor.com/t/origin-code-hosting/168670)** | Хостинг коду, вбудований у Cursor: репозиторії, перегляд, PR, синхронізація з GitHub | Стандартний Git; GitHub лишається джерелом істини для синхронізованих репозиторіїв | Рання бета з 17 серпня 2026, лише платні плани |
| **[Cloudflare Artifacts](https://blog.cloudflare.com/artifacts-git-for-agents-beta/)** | Версіоноване сховище, що говорить Git, створене, щоб надати кожній сесії агента власний репозиторій і форки | Git smart HTTP v1/v2, плюс REST і Workers API | Приватна бета під час запуску (16 квітня 2026); подальший статус не перевіряли |
| **[Anthropic Scion](https://www.anthropic.com/research/redesigning-source-control)** | Внутрішня система контролю версій Anthropic; Anthropic "fully migrated our monorepo from git in five months" | Відходить від протоколів git; "by no means a suitable replacement for git for general use" | Лише внутрішній, описано 13 жовтня 2026 |

**Форж Entire на практиці:**

- **Trails** оцінюють кожен push агентами рев'ю, що працюють у пісочницях (під капотом Claude Code і Codex). Знахідки мають серйозність і пропоноване виправлення. Шлюзи для кожного репозиторію блокують злиття, доки не виконано схвалення, знахідки та CI. Результати CI надходять від Buildkite чи Depot
- **Режим дзеркала** тримає GitHub джерелом істини: clone і fetch йдуть з Entire, push пересилаються на GitHub, де захист гілок і обов'язкові перевірки все одно діють. Під час збою GitHub агенти можуть продовжувати push у нативні недзеркальні гілки Entire
- **Регіони**: ЄС (Франкфурт), США (Огайо), Австралія (Сідней), Індія (Мумбаї), Великобританія (Лондон) і Сінгапур, за [сторінкою регіонів хостингу](https://entire.com/regions), чинною з 19 жовтня 2026
- **Пам'ять**: `entire-graph` будує локальну карту коду за допомогою tree-sitter, `entire-brain` пов'язує її з минулими сесіями
- **Бенчмарк вендора**: Entire повідомляє про 418 push на секунду проти 4,7 для GitHub ("up to 89x"), виміряно власним відкритим інструментом [ForgeMark](https://github.com/entireio/forgemark). Ставтеся до цього як до порівняння шляху зберігання, а не міри повного циклу рев'ю, CI і злиття
- **Ціни**: платні можливості споживають передплачені кредити ([Credit Terms](https://entire.com/credit-terms)); ціну за місце не опубліковано

**Anthropic Scion, що це показує:** Anthropic повідомляє про зростання з близько 2 500 злитих змін на день у травні 2026 до понад 30 000 на день у вересні та близько 25 мільйонів checkout коду на день для CI. Scion створює коміти, rebase і злиття на сервері ("there's nothing to push"), а Anthropic інвестувала в тестування після злиття й перед розгортанням замість глобального блокування злиття ("A proper merge queue, for example, doesn't make much sense at agent scale"). Це внутрішні цифри. Корисний урок для більшості команд полягає в тиску обсягу агентів на черги злиття та CI, а не в самому інструменті.

**Як обирати:**

| Ситуація | Розумний перший крок |
|-----------|----------------------|
| Ліміти чи збої GitHub сповільнюють ваших агентів | Дзеркалюйте один репозиторій (режим дзеркала Entire, синхронізація Origin) і тримайте GitHub джерелом істини |
| Черга рев'ю перенасичена PR від агентів | Випробуйте оцінюване агентом рев'ю на одному репозиторії, перш ніж переносити хостинг |
| Продукти, що створюють репозиторії для кожної сесії агента | Програмовне сховище Git (Cloudflare Artifacts) |
| Потрібно повністю залишити Git | Жоден із наведених продуктів цього не пропонує; Scion є внутрішнім для Anthropic |

Перед впровадженням будь-якого з них перевірте, що ви можете експортувати, крім даних Git: історію рев'ю, знахідки, шлюзи та пам'ять сесій.

> **Оцінка**: [Агентно-нативні Git-форжі](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/docs/resource-evaluations/agent-native-git-forges.md)

## Сканування безпеки

Два взаємодоповнювальні рівні: інструменти, що аудитують вашу конфігурацію Claude Code на помилки налаштування, ін'єкції hooks і ризики MCP; та сканери на основі агентів, що знаходять вразливості на рівні логіки в самому коді застосунку.

### AgentShield

Сканер безпеки, який оцінює вашу директорію `.claude/` за шкалою від 0 до 100 (оцінки A–F) на основі 102 правил у 5 категоріях. Створений на хакатоні Claude Code Hackathon (Cerebral Valley x Anthropic, лютий 2026).

| Атрибут | Деталі |
|---------|--------|
| **Джерело** | [GitHub: affaan-m/agentshield](https://github.com/affaan-m/agentshield) |
| **Встановлення** | `npx ecc-agentshield scan` (без встановлення) або `npm install -g ecc-agentshield` |
| **Мова** | TypeScript (Node.js) |
| **Ліцензія** | MIT |
| **Статус** | Рання стадія (випущено в лютому 2026 року): правила не проходили незалежний аудит |

**Ключові особливості**:

- **5 категорій сканування**: секрети (14 шаблонів: `sk-ant-`, `ghp_`, AWS, Stripe…), дозволи (директиви на кшталт `Bash(*)` та відсутність списків заборони), гачки (34 правила: ін'єкції команд через `${var}`, витік даних, приховування помилок, reverse shells), сервери MCP (23 правила: безпека ланцюжка постачання, `npx -y`, віддалений транспорт), агенти (25 правил: інструкції автозапуску, приховані директиви Unicode, рефлексія промптів).
- **Auto-fix**: `agentshield scan --fix` — замінює жорстко закодовані секрети на посилання на змінні оточення.
- **Кілька форматів виводу**: термінал (за замовчуванням), JSON (`--format json`), Markdown, автономний HTML.
- **GitHub Action**: публікує коментарі безпосередньо у файлах, виводить `score` та `grade`, підтримує поріг `fail-on-findings`.
- **Adversarial-аналіз за допомогою Opus** (`--opus --stream`): триагентний пайплайн (Атакуючий → Захисник → Аудитор) з використанням Opus 4.6 для глибокого моделювання загроз.

```bash
# Сканування конфігурації Claude Code (без встановлення)
npx ecc-agentshield scan

# Автоматичне виправлення безпечних проблем
agentshield scan --fix

# Вивід JSON для CI
agentshield scan --format json

# Триагентний аналіз за допомогою Opus (вимагає ANTHROPIC_API_KEY — стягує плату за API)
agentshield scan --opus --stream
```

**GitHub Action**:

```yaml
- name: AgentShield Security Scan
  uses: affaan-m/agentshield@v1
  with:
    path: "."
    min-severity: "medium"
    fail-on-findings: "true"
```

**Контекст `runtimeConfidence`**: результати зважуються за джерелом — `active-runtime` (повна вага) порівняно з `template-example` (0.25x ваги) та `docs-example` (0.25x ваги) — тому великий каталог шаблонів MCP не знижує оцінку так сильно, як реальні активні сервери.

**Обмеження**:
- Правила не проходили незалежного аудиту — сприймайте оцінку як корисний сигнал, а не як сертифікацію відповідності.
- Режим `--opus` здійснює виклики API Opus 4.6; плануйте бюджет відповідно перед увімкненням у CI.
- Структура API може змінюватися; фіксуйте конкретну версію в продакшені.

> **Див. також**: [Посібник із зміцнення безпеки](../security/security-hardening.uk.md) щодо ручних патернів hooks і дозволів.

### DeepSec

Сканер вразливостей на основі агентів від Vercel Labs, що знаходить помилки безпеки на рівні логіки у коді застосунку, такі, які пропускають SAST-інструменти на основі regex. Тоді як AgentShield вище аудитує вашу конфігурацію Claude Code, DeepSec аудитує сам застосунок.

| Атрибут | Деталі |
|-----------|---------|
| **Джерело** | [GitHub: vercel-labs/deepsec](https://github.com/vercel-labs/deepsec) |
| **Встановлення** | `npx deepsec init` (ініціалізує каталог `.deepsec/` у корені репозиторію) |
| **Мова** | TypeScript |
| **Ліцензія** | Apache 2.0 |
| **Статус** | Vercel Labs: експериментальний, не готовий до продакшну |

**Як це працює**: DeepSec запускає 5-кроковий конвеєр. Спершу швидке сканування regex визначає чутливі зони (потоки автентифікації, виклики криптографії, вхідні дані користувачів). Потім AI-агенти простежують потоки даних через кожен файл-кандидат і створюють знахідки. Другий прохід агента повторно валідує ці знахідки та звіряється з історією git, щоб відфільтрувати вже виправлені проблеми. Фінальний вивід є структурованим Markdown або JSON, готовим до вставки в тікети.

**Використовувані AI-моделі**: Claude Opus 4 з розширеним мисленням (за замовчуванням) і GPT-5.5 через вашу наявну підписку Anthropic або OpenAI. Для продакшн-сканувань рекомендується Vercel AI Gateway.

**Частка хибнопозитивних**: приблизно 10-20% після кроку повторної валідації.

```bash
# Initialize at repo root
npx deepsec init
cd .deepsec && pnpm install

# Run the full pipeline
pnpm deepsec scan       # fast regex pass
pnpm deepsec process    # AI agent investigation (slow, costs tokens)
pnpm deepsec triage     # P0/P1/P2 classification
pnpm deepsec revalidate # reduce false positives
pnpm deepsec export --format md-dir --out ./findings

# PR mode: scan only changed files (much cheaper)
pnpm deepsec process --diff

# Distributed mode for large monorepos (Vercel Sandboxes)
pnpm deepsec sandbox process --sandboxes 10 --concurrency 4
```

**Коли використовувати**: DeepSec знаходить крайові випадки в умовах автентифікації та тонкі проблеми потоків даних, які не виявлять інструменти на основі патернів. Він добре підходить для періодичного глибокого аудиту критичних сервісів або як шлюз `--diff` на чутливих до безпеки PR, а не як сканер для кожного коміту.

**Попередження щодо вартості**: повне сканування кодової бази на 50K рядків може коштувати $10-50 токенів Claude Opus. Великі монорепозиторії можуть сягати тисяч доларів. Для регулярного використання запускайте режим `--diff`; повні сканування лишайте для цільових аудитів.

**Конфігурація**: створіть `.deepsec/INFO.md` (50-100 рядків), що документує специфічні для проєкту патерни автентифікації та чутливі зони. Без нього агенти міркують без контексту й дають більше хибнопозитивних. Система плагінів дозволяє власні матчери regex, узгоджені з вашою архітектурою.

**Безпековий стан**: DeepSec має повний доступ до оболонки; ставтеся до нього як до агента кодування. Vercel рекомендує розгортати в мікроВМ Sandbox (Firecracker), щоб API-ключі не можна було виекфільтрувати з робочих процесів.

> **Див. також**: [анонс у блозі Vercel](https://vercel.com/blog/introducing-deepsec-find-and-fix-vulnerabilities-in-your-code-base) щодо деталей архітектури та реальних прикладів.

### SkillSpector

Сканер безпеки від NVIDIA, що перевіряє скіли перед встановленням. AgentShield аудитує вашу живу конфігурацію; DeepSec аудитує код вашого застосунку. SkillSpector закриває прогалину, яку не покриває жоден із них: статичний аналіз файлу чи репозиторію скіла до того, як він торкнеться вашої машини.

Мотивація конкретна: дослідження 2026 року (Liu et al.) на 42 447 скілах з основних маркетплейсів виявило, що 26,1% містили щонайменше одну вразливість, а 5,2% виявляли ймовірний зловмисний намір. Скіли з виконуваними скриптами мали в 2,12 раза вищу ймовірність бути вразливими.

| Атрибут | Деталі |
|-----------|---------|
| **Джерело** | [GitHub: NVIDIA/SkillSpector](https://github.com/NVIDIA/SkillSpector) |
| **Встановлення** | `uv venv .venv && source .venv/bin/activate && make install` |
| **Мова** | Python 3.12+ |
| **Ліцензія** | Apache 2.0 |
| **Статус** | Активний (підтримується NVIDIA) |

**Покриття виявлення**

64 патерни в 16 категоріях. Категорії, найрелевантніші для користувачів Claude Code:

- **Prompt injection** (5 патернів): перевизначення інструкцій, приховані директиви в коментарях, команди ексфільтрації, маніпуляція поведінкою, шкідливий вміст
- **Витік даних** (4 патерни): зовнішня передача, збір змінних оточення, перелік файлової системи, витік контексту
- **Отруєння інструментів MCP** (4 патерни): приховані інструкції в метаданих (коментарі HTML, символи нульової ширини, base64), юнікодний обман (гомогліфи, перевизначення RTL), ін'єкція в описі параметрів, невідповідність опису поведінці
- **Зловживання тригерами** (3 патерни): надто широкі ключові слова тригера, shadow-команди (скіл перевизначає вбудовану), приманювання ключовими словами
- **Ланцюжок поставок** (6 патернів): незафіксовані залежності, патерни `curl | bash`, обфусковане/закодоване виконання, живий пошук CVE через OSV.dev, покинуті пакети, typosquatting
- **Шахрайський агент** (2 патерни): самомодифікація під час виконання, несанкціоноване закріплення через cron/стартові скрипти

Патерн SC4 помітний: він у реальному часі запитує [OSV.dev](https://osv.dev), щоб перевірити оголошені залежності за повною базою бюлетенів. API-ключ не потрібен; результати кешуються в пам'яті на 1 годину. Якщо мережа недоступна, повертається до статичного списку.

**Двоетапний конвеєр**

Етап 1 є швидким статичним аналізом (regex + огляд AST для всіх файлів). Етап 2 є необов'язковою семантичною оцінкою LLM, що фільтрує хибнопозитивні й додає зрозумілі для людини пояснення. Prompt LLM включає захист від jailbreak, щоб шкідливий скіл не міг маніпулювати власним аудитом.

```bash
# Scan a local skill directory (static only)
skillspector scan ./my-skill/ --no-llm

# Scan a GitHub repository
skillspector scan https://github.com/user/my-skill

# Scan a single SKILL.md
skillspector scan ./SKILL.md

# With LLM analysis (Anthropic)
export SKILLSPECTOR_PROVIDER=anthropic
export ANTHROPIC_API_KEY=sk-ant-...
skillspector scan ./my-skill/

# JSON output for scripting
skillspector scan ./my-skill/ --no-llm --format json --output report.json

# SARIF for IDE tooling and CI
skillspector scan ./my-skill/ --format sarif --output report.sarif
```

**Оцінка ризику**: знахідки CRITICAL додають 50 балів, HIGH 25, MEDIUM 10, LOW 5. Скіли з виконуваними скриптами отримують множник 1,3. Оцінки понад 50 викликають рекомендацію "DO NOT INSTALL".

**Варіант Docker** для середовищ без доступу до мережі чи CI без Python:

```bash
docker build -t skillspector .
docker run --rm -v "$PWD:/scan" skillspector scan ./my-skill/ --no-llm
```

**Коли використовувати**: перед встановленням будь-якого скіла з незнайомого джерела, особливо тих, що мають виконувані скрипти (`scripts/`, `.sh`, `.py` поряд із SKILL.md). Запуск із `--no-llm` займає кілька секунд і ловить більшість патернів ланцюжка поставок і ексфільтрації. Вмикайте аналіз LLM для скілів, які ви розглядаєте для додавання до спільного налаштування команди.

**Заявлена точність**: ~87% після повторної валідації LLM. Лише статичний режим має вищий recall, але більше хибнопозитивних на легітимних патернах на кшталт `subprocess` в інструментах збірки.

> **Див. також**: [README NVIDIA SkillSpector](https://github.com/NVIDIA/SkillSpector) щодо повного каталогу патернів і посібника з розгортання Docker.

## Якість конфігурації

Інструменти, які оцінюють, перевіряють та підтримують якість наявних конфігурацій ШІ-агентів із часом — на відміну від їх створення з нуля.

> **Контекст**: CLAUDE.md не є статичним артефактом. У міру розвитку кодової бази інформація, яку вона надає ШІ, може застарівати: вказані шляхи зникають, знання про домен втрачають актуальність, з'являються нові патерни без документації. Описані нижче інструменти вирішують саме цю проблему підтримки.

### Caliber

CLI, який оцінює якість конфігурації вашого ШІ-агента за шкалою 0-100, генерує оптимізовані конфігурації на основі аналізу структури коду та виявляє розбіжності (drift) між кодом і вашим файлом CLAUDE.md. Працює з Claude Code, Cursor та Codex.

| Атрибут | Деталі |
|---------|--------|
| **Джерело** | [GitHub: rely-ai-org/caliber](https://github.com/rely-ai-org/caliber) |
| **Встановлення** | `npx @rely-ai/caliber score` (без встановлення) або `npm install -g @rely-ai/caliber` |
| **Мова** | TypeScript (Node.js ≥20) |
| **Ліцензія** | MIT |
| **Статус** | Рання стадія (випущено в березні 2026 року) — API можуть змінюватися |

**Ключові особливості**:

- **Локальна оцінка**: детермінована 100-бальна шкала у 6 категоріях (Наявність, Якість, Обґрунтування, Точність, Свіжість, Бонуси) — без викликів LLM та без використання API-ключів.
- **Виявлення розбіжностей (drift)**: на основі Git — виявляє випадки, коли коміти випереджають оновлення конфігурації; кеш інвалідується при зміні підпису дерева або HEAD.
- **Генерація конфігурацій**: аналіз кодової бази (мови, фреймворки, залежності) → створення CLAUDE.md + рекомендацій MCP через вашу наявну ШІ-підписку (Claude Code seat, Cursor seat або API-ключ).
- **Воркфлоу перевірки**: оцінка → пропозиція змін → перегляд diff → прийняття/відхилення → бекап у `.caliber/backups/` → `caliber undo`.
- **GitHub Action**: додає коментарі до PR з оцінкою, градацією та різницею порівняно з базовою гілкою; опціональний поріг `fail-below` блокує злиття.

```bash
# Оцінка поточної конфігурації (лише читання, без встановлення)
npx @rely-ai/caliber score

# Створення або покращення конфігурацій
npx @rely-ai/caliber init

# Виявлення розбіжностей після зміни коду
caliber refresh

# GitHub Action (відхилити PR, якщо оцінка < 75)
# uses: rely-ai-org/caliber@v1
# with: { fail-below: 75 }
```

**Категорії оцінювання**:

| Категорія | Макс | Що вимірює |
|-----------|------|------------|
| Наявність | 25 | Наявність CLAUDE.md, навичок (skills), конфігурації MCP, відповідність на різних платформах |
| Якість | 25 | Бюджет токенів, блоки коду, коефіцієнт конкретності, відсутність дублікатів |
| Обґрунтування | 20 | % директорій/файлів проєкту, згаданих у конфігурації |
| Точність | 15 | Існування вказаних шляхів на диску, кількість комітів після останнього оновлення конфігурації |
| Свіжість | 10 | Актуальність конфігурації відносно історії Git, відсутність секретів |
| Бонуси | 7 | Налаштовані гачки, наявність AGENTS.md, збережений вивчений вміст |

**Порівняння з іншими інструментами керування конфігурацією**:

| Потреба | Наявний інструмент | Що додає Caliber |
|---------|--------------------|------------------|
| Створення конфігурації з нуля | AIBlueprint | — |
| Аудит якості наявної конфігурації | Відсутній | Оцінювальна шкала + конкретні помилки |
| Виявлення розбіжностей конфігурації | Відсутній | Виявлення розбіжностей на основі Git |
| Розповсюдження стандартів в організації | Packmind | — |

**Обмеження**: інструмент на ранній стадії (березень 2026 року, ~65 зірок на момент написання; відтоді проєкт змінив назву на `ai-setup` під caliber-ai-org і досяг 1 223 зірок до 2026-07-27). Підтримка кількох інструментів (Claude Code + Cursor + Codex + Copilot) може призводити до створення універсальних, але менш специфічних для Claude Code конфігурацій. Шкала оцінювання не виводиться як окремий документ: категорії детерміновані, але їх не видно без читання вихідного коду.

**Примітка з безпеки**: команди `caliber refresh` та `caliber watch` мають доступ на запис до CLAUDE.md. Це той самий клас ризику, що й у Packmind: перевіряйте згенерований вивід перед прийняттям змін, особливо при використанні зовнішніх джерел (`caliber config`). Ставтеся до конфігураційних файлів `.caliber/` з тією самою дисципліною, що й до менеджерів секретів.

> **Посилання**: Для створення конфігурації з нуля див. [AIBlueprint](#aiblueprint). Для розповсюдження та контролю стандартів у масштабах організації див. [Packmind](#packmind). Для самостійного написання файлів CLAUDE.md див. [ultimate-guide.md Розділ 3](../ultimate-guide.uk.md#31-файли-памяті-claudemd).

### context-evaluator

Інструмент з відкритим кодом від Packmind, який оцінює якість CLAUDE.md та AGENTS.md за допомогою 17 спеціалізованих ШІ-оцінювачів. Доступний як веб-застосунок без встановлення, скомпільований бінарний файл або пакет для встановлення через Bun.

| Атрибут | Деталі |
|---------|--------|
| **Джерело** | [GitHub: PackmindHub/context-evaluator](https://github.com/PackmindHub/context-evaluator) |
| **Встановлення**| Бінарний файл з GitHub Releases або з вихідного коду через Bun |
| **Мова** | TypeScript (Bun) + React frontend |
| **Ліцензія** | Apache-2.0 |
| **Статус** | Активний (експериментальний проєкт Packmind, 2026) |

**Ключові особливості**:

- 17 оцінювачів, розділених на 13 типів помилок (наявні проблеми) та 4 типи пропозицій (прогалини на основі аналізу коду): якість вмісту, структура/форматування, повнота команд, вказівки щодо тестування, безпека, суперечливі інструкції, застарілі шляхи тощо.
- Однакове ставлення до AGENTS.md та CLAUDE.md — працює з форматами Claude Code, Cursor, GitHub Copilot та Codex.
- Аналіз структури коду: перед початком оцінювання запускається підрахунок рядків коду (CLOC) + аналіз папок + виявлення конфігураційних файлів, тому кожен промпт оцінювача містить реальні мови, фреймворки та ключові папки проєкту. Знайдені проблеми є специфічними для проєкту, а не загальними.
- **Уніфікований режим (unified mode)**: коли обсяг усіх файлів менше 100K токенів, один агент оцінює їх разом і може виявляти суперечності між файлами. Вище цього порогу агенти працюють незалежно для кожного файлу.
- **Автоматичне виправлення**: вибирайте проблеми у веб-інтерфейсі, вказуйте цільовий формат (Claude Code, Cursor, GitHub Copilot, Cursor), і ШІ згенерує файл `.patch`. Застосуйте його вручну за допомогою `git apply remediation.patch`. Жодні зміни не вносяться без вашого перегляду.
- Підтримка різних провайдерів ШІ: Claude Code (за замовчуванням), Cursor, OpenCode, GitHub Copilot, OpenAI Codex.

**Порівняння з Caliber**:

| Функція | Caliber | context-evaluator |
|---------|---------|-------------------|
| Не вимагає ШІ-провайдера | Так (детермінований) | Ні (потрібен AI CLI) |
| Оцінювальний бал (0-100) | Так | Ні |
| Виявлення відхилень Git | Так | Ні |
| Огляд вмісту на основі LLM | Ні | Так (17 оцінювачів) |
| Виявлення суперечностей між файлами| Ні | Так (unified mode) |
| Автоматичне виправлення (patch) | Ні | Так |
| Хостована веб-версія | Ні | Задокументована в upstream, але недоступна під час перевірки 2026-09-02 |

**Коли обирати context-evaluator**:
- Ви хочете отримати оцінку вмісту вашого файлу CLAUDE.md від LLM, а не просто перевірку структури.
- Ваша конфігурація може містити суперечливі інструкції, застарілі шляхи або відсутні конвенції фреймворків, які детермінована перевірка не зможе виявити.
- Вам потрібні автоматичні виправлення у вигляді файлу diff (без перезапису файлу на місці).

**Коли натомість обирати Caliber**:
- Вам потрібна оцінка без використання LLM для інтеграції в перевірки CI (поріг `fail-below`).
- Вам потрібне виявлення розбіжностей на основі Git у міру написання коду.

**Обмеження**: вимагає провайдера ШІ з доступом до CLI. Процес аналізу триває 1-3 хвилини. Немає детермінованої оцінки для CI. Немає виявлення розбіжностей Git.

> **Посилання**: Для детермінованого оцінювання конфігурацій див. [Caliber](#caliber). Для створення конфігурацій з нуля див. [AIBlueprint](#aiblueprint). Паттерни логування промптів та адаптивного режиму з цього інструменту описано в [Шаблонах проектування навичок](../core/skill-design-patterns.uk.md).

## Бутстрап контексту проєкту

Інструменти, які збирають структуровані знання про кодову базу **перед** початком сесії Claude Code — так ШІ з першого повідомлення розуміє маршрути, схему даних, залежності та важливі файли, без витрат токенів на самостійне дослідження файлової структури.

> **Контекст**: Claude Code досліджує кодову базу за допомогою викликів Glob, Grep та Read. На великих проєктах це коштує тисячі токенів ще до початку реальної роботи. Описані нижче інструменти попередньо збирають ці результати в один структурований артефакт (або набір статей), який Claude зчитує один раз на початку сесії. Це як «завантаження проєкту в оперативну пам'ять перед відкриттям сесії».

### codesight

CLI без залежностей, який аналізує кодову базу через AST та генерує структуровані карти контексту для Claude Code та інших інструментів ШІ. Заощаджує в 7-12 разів більше токенів на базовому скануванні порівняно з ручним дослідженням файлів, та до 83-131 разів при цільових запитах до бази знань (згідно з тестами розробників на 3 реальних проєктах).

| Атрибут | Деталі |
|---------|--------|
| **Джерело** | [GitHub: Houseofmvps/codesight](https://github.com/Houseofmvps/codesight) |
| **Встановлення**| `npx codesight` (без залежностей та без конфігурації) |
| **Мова** | TypeScript — використовує компілятор TS вашого проєкту, якщо він є |
| **Ліцензія** | MIT |
| **Статус** | Рання стадія (випущено у квітні 2026 року, ~386 зірок на момент написання, 1 253 станом на 2026-07-27), API можуть змінюватися |

**Основні команди**:

```bash
# Сканування поточного проєкту — створює папку .codesight/
npx codesight

# Створення бази знань у форматі вікі (.codesight/wiki/) — окремі статті на теми
npx codesight --wiki

# Генерація CLAUDE.md, .cursorrules, codex.md, AGENTS.md на основі сканування
npx codesight --init

# Показати радіус впливу (blast radius) для файлу (всі файли, на які вплине його зміна)
npx codesight --blast src/lib/db.ts

# Запуск як сервер MCP (11 інструментів) — Claude викликає його за запитом
npx codesight --mcp

# Генерація оптимізованого файлу конфігурації для конкретного ШІ-інструменту
npx codesight --profile claude-code

# Режим спостереження — пересканування при зміні файлів
npx codesight --watch

# Відкрити інтерактивний HTML-звіт у браузері
npx codesight --open
```

**Що генерується**:

| Файл | Вміст |
|------|-------|
| `.codesight/CODESIGHT.md` | Об'єднана карта контексту — один файл із повним описом проєкту |
| `.codesight/routes.md` | Кожен API-маршрут із методом, шляхом, параметрами та тим, чого він стосується (auth, db, cache, payments) |
| `.codesight/schema.md` | Кожна модель бази даних із полями, типами, первинними/зовнішніми ключами та зв'язками |
| `.codesight/graph.md` | Граф імпорту — які файли що імпортують, зміна яких файлів ламає найбільше речей |
| `.codesight/middleware.md` | Авторизація, обмеження частоти запитів, CORS, валідація, логування, обробка помилок |
| `.codesight/config.md` | Усі змінні оточення (обов'язкові та за замовчуванням), файли конфігурації, ключові залежності |
| `.codesight/wiki/` | Постійна база знань: одна стаття на тему (`auth.md`, `database.md`, `payments.md` тощо) |

**Покриття розпізнавання**:
- Маршрути (Routes): автовизначення для 25+ фреймворків (Express, Hono, Fastify, NestJS, tRPC, FastAPI та ін.).
- Схеми даних (Schema): 10 ORM (Drizzle, Prisma, TypeORM, Mongoose, SQLAlchemy, ActiveRecord, Ecto, Eloquent, Entity Framework, Sequelize).
- Компоненти: React, Vue, Svelte, Flutter, SwiftUI.
- Мови: TypeScript (повний AST), JavaScript, Python, Go, Ruby, Elixir, Java, Kotlin, Rust, PHP, Dart, Swift, C# (fallback на регулярні вирази для мов без TS).

**Інтеграція з MCP** — після налаштування Claude викликає інструмент безпосередньо без запуску `npx`:

```json
{
  "mcpServers": {
    "codesight": {
      "command": "npx",
      "args": ["codesight", "--mcp"]
    }
  }
}
```

Доступні інструменти MCP: `codesight_scan`, `codesight_get_wiki_index`, `codesight_get_wiki_article`, `codesight_get_routes`, `codesight_get_schema`, `codesight_get_blast_radius`, `codesight_get_hot_files`, `codesight_get_env`, `codesight_get_summary`, `codesight_lint_wiki`, `codesight_refresh`.

**Як вікі знижує споживання токенів**:

| Запитання | Без вікі | З вікі |
|-----------|----------|--------|
| «Як працює авторизація?» | ~12K токенів (читання 8+ файлів) | ~300 токенів (`auth.md`) |
| «Які моделі існують?» | ~5K токенів (увесь CODESIGHT.md) | ~400 токенів (`database.md`) |
| Початок нової сесії | ~5K токенів (повне завантаження) | ~200 токенів (`index.md`) |

**На якому масштабі переходити з CODESIGHT.md на вікі**: на малих та середніх проєктах (менше ~1500 файлів) завантаження `CODESIGHT.md` при старті сесії через CLAUDE.md є практичним. На великих проєктах — Next.js + tRPC монорепозиторій на 1700 файлів генерує `CODESIGHT.md` розміром 35K токенів — завантаження всього файлу стає неефективним. Використовуйте `--wiki` + сервер MCP: Claude завантажує одну статтю (~200-400 токенів) на запит замість завантаження всієї карти контексту.

**Обмеження та нюанси**:
- Бенчмарки надані авторами на основі 3 проєктів — незалежної перевірки на момент написання немає.
- Точність AST гарантується лише для TypeScript; інші мови використовують парсинг на регулярних виразах.
- Параметр `--init` створює CLAUDE.md автоматично — це може перезаписати наявний файл. Робіть бекап перед запуском у проєктах зі створеною конфігурацією.
- Інструмент на ранній стадії (квітень 2026 року): структура API може змінюватися.
- Проєкти з MongoDB коректно показують 0 моделей схем (немає SQL ORM декларацій).
- Проєкти Cloudflare Workers із прямими HTTP-обробниками (без фреймворків) показують 0 маршрутів — середовище виконання worker не входить до списку 25+ підтримуваних фреймворків.
- Проєкти Next.js App Router показують 0 маршрутів — маршрутизація на основі файлів не має явних оголошень у коді; маршрути вираховуються за шляхами до файлів, а не за патернами коду.
- Проєкти на Rust майже порожні — немає підтримки AST, пошук за регулярними виразами бачить лише імпорти модулів верхнього рівня (`src/main.rs` → `mod X`); маршрути, структури та бізнес-логіка невидимі. Не підходить для кодових баз на Rust.

## Розповсюдження інженерних стандартів

Інструменти, які вирішують проблему масштабування в організаціях: підтримання інженерних стандартів синхронізованими в десятках репозиторіїв та на різних ШІ-інструментах розробки.

> **Контекст**: У головному посібнику описано написання CLAUDE.md на рівні проєкту (Розділ 3). Описані нижче інструменти вирішують наступне завдання — дистрибуція та підтримка цих стандартів у масштабах компанії.

### Packmind

Платформа з відкритим вихідним кодом для «ContextOps» (термін розробників для опису роботи з контекстом розробки як із керованим артефактом, що має свій життєвий цикл). Фіксує стандарти один раз і розповсюджує їх як машиночитаний контекст для всіх ШІ-асистентів, які використовує команда.

| Атрибут | Деталі |
|---------|--------|
| **Джерело** | [GitHub: PackmindHub/packmind](https://github.com/PackmindHub/packmind) |
| **Встановлення**| `npx @packmind/cli init` |
| **Ліцензія** | Apache-2.0 (CLI) — хмарна версія на packmind.com (ціни не вказано) |
| **Self-hosted**| Docker / Kubernetes |
| **Мова** | TypeScript |

**Ключові особливості**:
- Єдиний плейбук (playbook) → генерує `CLAUDE.md` + слеш-команди + навички (skills) для Claude Code, `.cursor/rules/*.mdc` для Cursor, `.github/copilot-instructions.md` для Copilot, `AGENTS.md` для інших агентів.
- Сервер MCP: створення та керування стандартами безпосередньо з сесії Claude Code.
- Цикл безперервного навчання: знайдено та виправлено баг → причина зафіксована через Skill+MCP → запропоновано оновлення плейбука → людина перевіряє → оновлення розповсюджується на всі репозиторії.
- Імпорт знань з командних інструментів розробки через сервери MCP: коментарі до PR у GitHub, Slack, Jira, MR у GitLab, Confluence, Notion.

**Концептуальна модель**: Сприймайте Packmind як масштабну версію модульної структури правил `.claude/rules/`. Тоді як `.claude/rules/*.md` підтримує порядок в одному проєкті, Packmind забезпечує узгодженість у 40 репозиторіях — і синхронізується з усіма ШІ-інструментами, а не лише з Claude Code.

**Примітка з безпеки**: Централізація розповсюдження CLAUDE.md означає, що компрометація репозиторію Packmind може одночасно надіслати шкідливі інструкції в сесії розробки всіх інженерів. Ставтеся до конфігурацій Packmind як до чутливих артефактів, застосовуйте правила доступу, як до менеджера секретів, та уважно перевіряйте пропоновані оновлення плейбуків перед злиттям.

## Утиліти гачків (Hooks)

Інструменти, які розширюють систему гачків Claude Code додатковою логікою, умовним виконанням або автоматизацією. Самостійні приклади гачків наведено у відповідному розділі головного посібника.

### gitdiff-watcher

Корисна утиліта для гачка `Stop`, яка перевіряє якість коду перед тим, як Claude поверне контроль користувачу. Запускає команди (збирання, тести, лінтинг) лише тоді, коли змінилися відповідні файли, що робить правила якості в CLAUDE.md детермінованими.

| Атрибут | Деталі |
|---------|--------|
| **Джерело** | [GitHub: fcamblor/gitdiff-watcher](https://github.com/fcamblor/gitdiff-watcher) |
| **Встановлення**| `npx @fcamblor/gitdiff-watcher@0.1.0` (без глобального встановлення) |
| **Мова** | Node.js |
| **Версія** | 0.1.0 — у процесі розробки, API можуть змінюватися |
| **Автор** | Флоріан Камблор (Florian Camblor) |

**Проблема, яку це вирішує**: Правила CLAUDE.md на кшталт «тести мають проходити перед завершенням роботи» не є детермінованими. У міру зростання контексту ці правила конкурують за увагу моделі з нещодавніми виводами інструментів і можуть ігноруватися — тому Claude іноді повертає контроль із непрацюючим кодом, навіть якщо правила були чіткими. Гачок `Stop` виконується поза контекстом LLM, тому його неможливо обійти.

**Як це працює**:
1. Приймає маску файлів (`--on`) та одну або кілька команд для запуску (`--exec`).
2. При кожній події `Stop` вираховує SHA-256 хеші всіх файлів, що відповідають масці та фігурують у `git diff` (індексовані + неіндексовані).
3. Порівнює їх із попереднім станом, збереженим у `.claude/gitdiff-watcher.state.local.json`.
4. Якщо змін у файлах немає: завершується з кодом 0 (команди не запускаються).
5. Якщо зміни виявлено: запускає всі команди `--exec`.
6. Якщо будь-яка команда завершується з помилкою (код не 0): Claude отримує stderr та робить нову спробу виправлення — стан файлів НЕ оновлюється, тому перевірка запуститься знову при наступному `Stop`.
7. При успішному виконанні всіх перевірок: оновлює знімок стану.

**Приклад конфігурації** (`.claude/settings.json`):

```json
{
  "hooks": {
    "Stop": [
      {
        "hooks": [
          {
            "type": "command",
            "command": "npx @fcamblor/gitdiff-watcher@0.1.0 --on 'src/**/*.{ts,tsx}' --exec 'npm run build'",
            "timeout": 300,
            "statusMessage": "Checking TypeScript build..."
          },
          {
            "type": "command",
            "command": "npx @fcamblor/gitdiff-watcher@0.1.0 --on 'src/**/*.{ts,tsx}' --exec 'npm test -- --passWithNoTests'",
            "timeout": 300,
            "statusMessage": "Checking tests..."
          }
        ]
      }
    ]
  }
}
```

Кілька гачків виконуються паралельно (Claude Code запускає окремого субагента для кожного запису гачка).

**Ключові особливості**:
- **Умовність**: запускається лише при зміні відповідних файлів — без зайвих витрат часу на непов'язані редагування.
- **Безпека повторних спроб**: невдалі запуски зберігають старий знімок стану, тому перевірка повториться при наступній спробі.
- **Послідовність/паралельність**: кілька команд `--exec` в одному записі гачка виконуються послідовно; використовуйте окремі записи для паралельного виконання.
- **Мовчазність при відсутності змін**: виходить із кодом 0 без виводу, якщо зміни не зачіпають вказані файли.

**Обмеження**:
- Версія v0.1.0 явно вказана як «work in progress», параметри CLI та формат файлу стану можуть змінюватися.
- Використовує `git diff` для виявлення файлів — файли, які не відстежуються в Git, невидимі для утиліти.
- Нескінченні цикли: неправильно налаштована перевірка, яка завжди завершується помилкою, змусить Claude повторювати спроби нескінченно; додайте `--exec-timeout` та переконайтеся, що команди мають коректні коди виходу.
- Кожна невдала перевірка гачка `Stop` запускає новий хід Claude, що споживає токени; поблизу ліміту в 200K токенів це може швидко вичерпати бюджет контексту.

**Коли використовувати gitdiff-watcher замість нативного гачка Stop**:
Таку саму перевірку якості можна написати самостійно на bash у ~20 рядків. Використовуйте `gitdiff-watcher`, якщо вам потрібна готова умовна логіка перевірки змін та збереження стану без написання власного коду, або коли потрібні паралельні перевірки в багатомовних проєктах (наприклад, збирання TypeScript + тести на Kotlin одночасно).

## Рендеринг у терміналі (mods)

Claude Code 2.1.287 додав [mods](../ultimate-guide.uk.md#claude-mods-v21287): плагіни, чиї обробники працюють усередині Claude Code й можуть перемальовувати те, що він показує. Mod рендерингу зберігає власний термінальний інтерфейс Claude Code й змінює вигляд відповідей. У цьому відмінність від [альтернативних інтерфейсів](#альтернативні-інтерфейси) нижче, які замінюють інтерфейс. Вимкнення плагіна mod у `/plugin` повертає стандартний рендерер.

### prismantis

Mod Claude Code, що перемальовує відповіді в терміналі: кольорові таблиці, код із підсвічуванням синтаксису, діаграми mermaid і графіки, текстові фігури та кнопки копіювання на кожному блоці. Він також перемальовує рядки інструментів (редагування стають картками diff), вивід slash-команд і ваші власні prompt. Автор цього посібника користується ним і рекомендує його.

| Атрибут | Деталі |
|-----------|---------|
| **Джерело** | [NahumLitvin/prismantis на GitHub](https://github.com/NahumLitvin/prismantis) і допис мейнтейнера про запуск [prismantis: real charts, tables and code in Claude Code's terminal](https://www.catchkill9.dev/posts/prismantis.html) |
| **Версія** | 0.38.2 (30 жовтня 2026), 64 релізи GitHub з 2 жовтня 2026 |
| **Потребує** | Claude Code 2.1.287 або новішої |
| **Ліцензія** | MIT |
| **Сигнали** | 266 зірок і 24 учасники на 31 жовтня 2026; включений до Awesome Claude Code ([issue-сповіщення #209](https://github.com/NahumLitvin/prismantis/issues/209), 18 жовтня 2026) |
| **Протестовано на** | Термінал macOS вручну, за README; CI запускає тести на macOS, Linux і Windows. Застосунок Desktop, VS Code і мобільні поки не перевірялися вручну |

**Встановлення** (усередині Claude Code):

```text
/plugin marketplace add NahumLitvin/prismantis
/plugin install prismantis@prismantis
```

Потім `/prismantis setup` проведе вас через тему та стилі з намальованими прев'ю, `/prismantis demo` покаже основні можливості, а `/prismantis theme <name>` перемикає між 17 темами (16 палітр плюс `mono`).

**Оновлення** (з оболонки), потім запустіть `/reload` у кожній відкритій сесії, бо сесія зберігає версію, яку завантажила:

```bash
claude plugin marketplace update prismantis && claude plugin update prismantis@prismantis
```

**Налаштування** через рядки prismantis у `/config` або під `pluginConfigs` у `~/.claude/settings.json`, потім `/reload`. Налаштування проєкту не читаються для параметрів плагіна, тож значення застосовується до кожного проєкту.

#### Копіювання виводу в Slack, GitHub чи документ

| Блок | Кнопка | Що потрапляє в буфер обміну |
|-------|--------|-----------------------------|
| Таблиця | `⧉ md` | Оригінальний Markdown |
| Таблиця | `⧉ art` | Текстова таблиця в рамці, що добре вставляється в Slack |
| Таблиця | `⧉ html` | Форматована таблиця плюс копія з табуляцією. Локальний термінал macOS або графічна сесія Linux із запущеним CopyQ |
| Таблиця, діаграма, фігура | `▣ png` | PNG намальованого арту, у локальному терміналі macOS чи Windows |
| Діаграма, фігура | `⧉ source` / `⧉ art` | Джерело mermaid чи фігури або намальований текст |
| Код, список, цитата | `[ ⧉ copy ]` | Код без огорож, список як Markdown, цитата без маркерів `> ` |
| Відповідь із кількома блоками | `⧉ copy reply` | Вся відповідь так, як її написав Claude |

Без миші `/prismantis copy` копіює останню відповідь, а `/prismantis copy code` її останній блок коду. Використовуйте команди в терміналах, що копіюють при виділенні (README називає Warp), де клацання кнопки може захопити слово "copy".

Виділення списку мишею раніше копіювало намальовані гліфи `•` і `◦`, які Slack показує як текст, а не як список. З 0.38.0 `listMarker: dash` малює `-` на кожному рівні, тож виділений список вставляється як список Markdown. Нумеровані списки зберігають свої номери.

```json
{
  "pluginConfigs": {
    "prismantis@prismantis": {
      "options": { "listMarker": "dash" }
    }
  }
}
```

#### Скільки коштує `diagramHints` і коли його вимикати

Claude рідко пише діаграму, якщо не знає, що термінал може її намалювати. Із увімкненим `diagramHints` (за замовчуванням) prismantis додає примітку, яку читає лише модель, до кожного prompt, який ви вводите, і до кожного prompt, який надсилає інший плагін. Примітка каже, які елементи рендеряться, просить команди в огороджених блоках і пояснює, коли фігура працює краще за діаграму mermaid. README оцінює це приблизно в 630 токенів на prompt і близько 710 з увімкненим `latex`, порахованих токенізатором Claude. Це цифри мейнтейнера; цей посібник їх не вимірював. Примітку пропускають для першого prompt безголового запуску `claude -p` і для фонових сповіщень.

Примітка змінює те, що пише Claude, а не лише вартість. Вимкніть її через `"diagramHints": false` і `/reload`, коли:

- Ви складаєте текст для вставки деінде (повідомлення Slack, опис PR, лист). Блоки mermaid і фігури надходять туди як джерело, а `⧉ art` чи `▣ png` допомагають лише для одного блоку за раз.
- Накладні витрати на prompt важать для вас більше за картинки, наприклад, у довгих сесіях, де ви стежите за використанням контексту.

Рендеринг лишається увімкненим і без підказок: таблиці, код і будь-яка діаграма, яку Claude все ж напише, малюються як і раніше. Оскільки параметри плагіна читаються лише з користувацьких налаштувань, перемикач застосовується до кожного проєкту, доки ви не ввімкнете його знову.

#### Безпека

Mod є кодом без пісочниці, що працює в процесі Claude Code (див. примітку щодо безпеки в [розділі про mods головного посібника](../ultimate-guide.uk.md#claude-mods-v21287)). README стверджує, що prismantis не робить мережевих викликів і запускає програму лише для допоміжної програми буфера обміну `⧉ html` і `▣ png` при клацанні та для рендерера LaTeX, коли ввімкнено `latex`. Щоб перевірити, що декларує версія, перед встановленням:

```bash
git clone https://github.com/NahumLitvin/prismantis
claude plugin validate ./prismantis
```

На коміті `dc51f35` (v0.38.2) валідація пройшла. Рядок `calls:` перелічив `$.process.run` через допоміжну програму буфера обміну та верстальник LaTeX, рядок `hooks:` включав `tool.call` і `prompt.submit`, а `env writes:` був порожнім. Текстовий пошук у поставленому коді `hooks/` за `fetch`, `http`, `https`, `net` і `WebSocket` нічого не знайшов. Це статична перевірка однієї версії, а не аудит коду.

#### Чуйність мейнтейнера

30 жовтня 2026 о 06:10 UTC автор цього посібника відкрив [issue #319, копіювання маркерів списку для вставки в Slack](https://github.com/NahumLitvin/prismantis/issues/319). Мейнтейнер опублікував [реліз v0.38.0 з параметром `listMarker`](https://github.com/NahumLitvin/prismantis/releases/tag/v0.38.0) о 08:53 UTC, потім відповів і закрив issue о 09:05 UTC. Одна датована точка даних, а не зобов'язання щодо підтримки.

**Коли використовувати**: ви читаєте таблиці, diff і діаграми у відповідях Claude й хочете, щоб вони були намальовані, а не показані як джерело Markdown, або часто копіюєте вивід Claude у Slack, GitHub чи документ. **Пропустіть**, для безголового `claude -p`, де нічого не малюється, або на машинах, де адміністратори дозволяють лише керовані mods (`allowManagedModsOnly`).

Оцінка: [оцінка prismantis](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/docs/resource-evaluations/prismantis-terminal-rendering-mod.md).

### Conductor

Десктопний застосунок для macOS для координації кількох запущених екземплярів Claude Code (та Codex) паралельно за допомогою git worktrees, з вбудованим переглядом diff, процесом PR та автоматизацією GitHub.

| Атрибут | Деталі |
|---------|--------|
| **Джерело** | [conductor.build](https://conductor.build) |
| **Документація**| [Документація Conductor](https://www.conductor.build/docs) |
| **Встановлення**| Завантаження з [conductor.build](https://conductor.build) |
| **Платформа** | Клієнт macOS; локальні робочі простори або хмарні пісочниці Linux |
| **Агенти** | Claude Code, Codex, Cursor, OpenCode |
| **Автор** | Melty Labs |

**Воркфлоу**: створіть робочий простір для фічі чи виправлення, запустіть агента, перегляньте його зміни, надішліть зворотний зв'язок на рівні рядків, потім створіть чи перегляньте PR. Робочий простір тримає разом свою гілку, файли, термінал і розмову. [Переглядач diff](https://www.conductor.build/docs/reference/diff-viewer) підтримує перегляд файлів і комітів; [Checks](https://www.conductor.build/docs/reference/checks) об'єднує стан PR, CI, коментарі й завдання там, де вони доступні. Checks можуть блокувати чи не рекомендувати злиття залежно від воркфлоу; їхня наявність не доводить, що обов'язковий тест було запущено.

**Локально й у хмарі**: локальні робочі простори використовують Git worktrees на Mac. [Хмарні робочі простори](https://www.conductor.build/docs/cloud) працюють у пісочницях Linux із налаштованими залежностями та змінними оточення й можуть продовжувати роботу при закритому ноутбуці, доки робочий простір не засне. Організації можуть ділитися хмарними робочими просторами та чатами. Це розширює виконання за межі десктопу; це не додає клієнта для Windows чи Linux.

**Межа дозволів**: [Git worktree](https://www.conductor.build/docs/concepts/git-worktrees) відокремлює робочі файли, ділячи історію та посилання Git. Локальні агенти працюють із дозволами акаунта користувача. Хмарне виконання використовує пісочниці Vercel, але користувачі можуть явно дозволити хмарним агентам діяти на їхній локальній машині. Перегляньте це налаштування, перш ніж вважати хмарний робочий простір ізольованим від Mac. Дивіться [безпеку та дозволи](https://www.conductor.build/docs/reference/security-and-permissions).

**Коли тестувати**: ви користуєтеся Mac і хочете мати виконання агента, зворотний зв'язок щодо diff і перевірки PR в одному робочому просторі, зокрема з хмарним варіантом. Це пропрієтарний продукт; доступ провайдера агента й доступність хмари мають власні вимоги. Це задокументовані можливості, а не виміряний приріст продуктивності.

### Agent orchestrator (AO)

Десктопний застосунок і CLI з відкритим кодом, що координують наявних агентів кодування, worktrees проєктів і стан доставки PR. Його демон спостерігає за подіями CI та рев'ю й може надсилати зворотний зв'язок пов'язаній сесії агента.

| Атрибут | Деталі |
|-----------|---------|
| **Джерело** | [OrchestratorInc/agent-orchestrator](https://github.com/OrchestratorInc/agent-orchestrator), раніше згадувався як AgentWrapper і ComposioHQ |
| **Встановлення** | Використовуйте [офіційні десктопні релізи](https://github.com/OrchestratorInc/agent-orchestrator/releases); у жовтневому пробному запуску використовувався вбудований демон через його CLI |
| **Ліцензія** | Apache-2.0 у корені репозиторію |
| **Платформа** | Десктопні збірки для Windows, macOS і Linux; тут перевірено лише роботу CLI/демона на macOS |
| **Пробний запуск** | 27 жовтня 2026: AO v0.14.6, Codex CLI 0.159.2, один синтетичний репозиторій і PR |

**Перевірено в пробному запуску**: AO створив worktree Codex, відстежив PR і фінальний коміт та автоматично переслав невдалу перевірку GitHub до Codex. Агент виправив локально відтворену помилку. AO також прийняв інлайновий коментар рев'ю з його файлом і рядком, але доставку до Codex не спостерігали понад п'ять хвилин після прийняття, зокрема після завершення схвалення. Для завершення виправлення за рев'ю знадобилося ручне пробудження; п'ять локальних тестів потім пройшли.

**Віддалений CI лишався заблокованим**: GitHub не запустив завдання через виставлення рахунків акаунта чи ліміт витрат. Сповіщення AO містило помилку отримання логу, а не цей діагноз. Локальні тести, що проходять, не встановлюють успіху віддаленого CI. Приватні записи пробного запуску є доказами оцінювача, а не публічно відтворюваними артефактами CI.

**Перевірте типові налаштування перед впровадженням**: протестоване [відображення дозволів Codex](https://github.com/OrchestratorInc/agent-orchestrator/blob/v0.14.6/backend/pkg/agentruntime/command.go#L198) змушує `default` AO обходити схвалення та пісочницю. Пробний запуск вибрав `accept-edits` і окремо налаштував Codex із `workspace-write` і схваленнями `on-request`. [Документація телеметрії](https://github.com/OrchestratorInc/agent-orchestrator/blob/v0.14.6/docs/telemetry.md) релізу також описує дані, пов'язані з акаунтом, і налаштування конфіденційності для вимкнення віддаленого збору; раніше наведений опис повністю анонімної телеметрії не зберігається.

**Коли оцінювати AO**: тестуйте його для консолідованого нагляду за PR/CI/рев'ю. Вимагайте справжнього віддаленого тесту "червоне-зелене" та доставки рев'ю після схвалення, перш ніж покладатися на цикл без нагляду. Цей пробний запуск не порівнював швидкість, вартість, графічну зручність чи надійність із Codex Desktop, Conductor, Orca чи Escouade. Він також не підтверджує історичне твердження "retry CI twice, then escalate".

Повна оцінка та межі доказів: [`Agent Orchestrator with Codex`](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/docs/resource-evaluations/agent-orchestrator-composio.md).

## Маршрутизація моделей

Ці інструменти вибирають, яку модель і який effort отримує завдання кодування, замість того, щоб лишати одне типове значення на всю сесію. [Економіка AI](../ops/ai-unit-economics.uk.md#маршрутизація-за-складністю) пояснює три рівні маршрутизації та чому економію треба вимірювати на ваших власних завданнях.

### Agent Router

Дозволи, бюджет, ризик і відсутні докази хоста прибирають кандидатів до обчислення будь-якої оцінки, а ті самі входи відтворюються в те саме рішення (квитанцію рішення). Кожна схвалена фаза працює як окремий процес хоста в пісочниці ОС, із записами, обмеженими worktree Git; він не перемикає модель розмови, у якій ви перебуваєте.

> **Статус**: публічний з 2026-10-28 як експериментальний кандидат у вихідному коді (тег `v0.0.1`, без пакетованого релізу). Статус README від 2026-10-27 каже, що офлайн-маршрутизація працює, а автоматичне щоденне використання Claude Code чи Codex ще не кваліфіковане.
>
> **Розкриття**: Agent Router написаний автором цього посібника.

| Атрибут | Деталі |

| **Ліцензія** | Apache-2.0 |
| **Встановлення** | Збірка з вихідного коду з Rust 1.85+: `cargo build --locked -p agent-router-cli`; посібник зі встановлення також охоплює закріплене встановлення Cargo Git і локально згенеровану формулу Homebrew. Немає пакета crates.io, публічного tap чи підписаного релізного ресурсу |

### abtop

TUI-інтерфейс на Rust, який показує всі активні сесії Claude Code та Codex CLI на одному екрані — як htop, але для флоту ШІ-агентів.

| Атрибут | Деталі |
|---------|--------|
| **Джерело** | [GitHub: graykode/abtop](https://github.com/graykode/abtop) |
| **Встановлення**| `curl --proto '=https' --tlsv1.2 -LsSf https://github.com/graykode/abtop/releases/latest/download/abtop-installer.sh \| sh` або `cargo install abtop` |
| **Мова** | Rust (ratatui) |
| **Ліцензія** | MIT |
| **Платформа** | macOS, Linux (WSL для Windows) |

**Ключові особливості**:
- Автоматичне виявлення сесій Claude Code та Codex CLI на основі стану локальних процесів — без API-ключів та авторизації.
- Графічні індикатори для кожної сесії: споживання токенів, % заповнення вікна контексту, квота ліміту запитів.
- Виявлення залишених (orphan) портів із можливістю швидкого закриття однією клавішею (`X`).
- Відображення дерева субагентів (лише для Claude Code).
- Інтеграція з tmux: натисніть `Enter`, щоб перейти безпосередньо до панелі відповідної сесії.
- Прапорець `--once` для виводу статичного знімку стану (для CI).
- Прапорець `--setup` для встановлення гачка збору лімітів частоти запитів.
- 10 вбудованих тем, включаючи 4 адаптовані для людей із розладами сприйняття кольору (`high-contrast`, `protanopia`, `deuteranopia`, `tritanopia`).

**Використання**:

```bash
abtop                    # Запуск TUI (вимагає термінал 120x40, масштабується до 80x24)

abtop --theme dracula    # Запустити з конкретною темою
```

**Рекомендована схема роботи з tmux**:

```bash
tmux new -s work
# pane 0: abtop
# pane 1: claude (project A)
# pane 2: claude (project B)
# Натисніть Enter в abtop для переходу до панелі активного агента
```

**Підтримувані функції за агентами**:

| Функція | Claude Code | Codex CLI |
|---------|:-----------:|:---------:|
| Відстеження токенів | ✅ | ✅ |

| Ліміти запитів (Rate limit) | ✅ | ✅ |
| Дерево субагентів | ✅ | ❌ |

### YYLO

Інструмент командного рядка для оркестрації агентів кодування, що володіє шаром доставки: типізовані межі завдання, валідації та злиття навколо worktrees Git на кожне завдання. YYLO (команди `yylo` і `yy`) делегує внутрішній цикл агента наявним CLI агентів кодування, як-от Pi і Codex CLI, і керує життєвим циклом навколо них.

| Атрибут | Деталі |
|-----------|---------|
| **Джерело** | [GitHub: yylo-dev/yylo](https://github.com/yylo-dev/yylo) |
| **Встановлення** | `npm install --global '@yylo/cli@latest'` |
| **Мова** | Python (CLI, що розповсюджується через npm) |
| **Ліцензія** | MIT |
| **Команди** | `yylo` і `yy` (еквівалентні); `ypl` це `yy pi --live` |

**Ключові можливості**:

- `task start` фіксує SHA захищеної цілі, створює окрему гілку/worktree на завдання й завершує налаштовану гідратацію залежностей, перш ніж повідомити `WORKING`
- `task preflight` лише для читання й виявляє дефекти замикання до дорогих шлюзів; `task finish` вимагає чистого закоміченого кінчика й ставить завдання в чергу; воно не зливає
- `merge land` компонує рівно одне незмінне джерело завдання в приватному від'єднаному кандидаті й приземляє його із захистом Git expected-old ref; ціль, що зрушила, змушує до перекомпонування й повторних перевірок
- Merge не запускає моделей, не вибирає рев'юерів і не планує набори тестів: тести й семантичні рев'ю лишаються явними перевірками проєкту поза кроком злиття
- Машинний вивід із квитанціями (`--format json|ndjson --raw`) для команд завдань, злиття та інтеграції, зі збереженими доказами

**Використання**:

```bash
npm install --global '@yylo/cli@latest'
yy init --task "Document the onboarding path" --subagent pi
yy task start TASK_ID       # freeze target SHA, create the task worktree
yy task preflight TASK_ID   # read-only closure checks before finishing
yy merge status             # observe the queue
```

**Обмеження**: рання стадія впровадження, 60 зірок і приблизно 900 завантажень npm на місяць станом на вересень 2026. Merge компонує й приземляє роботу; він її не переглядає, а під runtime агентів немає пісочниці рівня ОС. Лише англомовна документація.

> **Коли використовувати**: коли кілька агентів кодування працюють паралельно над одним репозиторієм і ви хочете типізовану межу "завдання → worktree → шлюз злиття", яку оркестратори, орієнтовані на диспетчеризацію, залишають оператору. Специфікація Symphony стверджує "if you want a review loop or a merge gate, you build that yourself"; YYLO є готовим шаром шлюзу злиття, тоді як сам цикл рев'ю лишається за перевірками вашого проєкту.

### Concord

Сервер MCP, що надає агентам кодування в одному репозиторії спільний стан роботи: хто присутній, яке завдання й файли заявив кожен агент, попередження про перекриття перед тим, як хтось редагує, prompt і відповіді між агентами в різних harness, а також передачі з доказами рев'ю. Concord не запускає агентів і не створює worktrees; він працює поруч із тим, що їх запускає (термінал, виконавець worktrees, десктопний застосунок).

| Атрибут | Деталі |
|-----------|---------|
| **Джерело** | [GitHub: Get-Concord-AI/concord-mcp](https://github.com/Get-Concord-AI/concord-mcp) |
| **Встановлення** | `npm install -g @concord-ai/concord-mcp`, потім `concord setup` у репозиторії |
| **Мова** | TypeScript (Node.js 22.12+) |
| **Ліцензія** | MIT |
| **Клієнти** | Claude Code, Codex, Cursor, Gemini CLI, Grok Build, Goose, Google Antigravity; будь-який клієнт MCP може використовувати інструменти |

**Ключові можливості**:

- `concord setup` реєструє сервер для Claude Code, Cursor, Gemini, Grok і Codex та записує інструкції інструментів у `CLAUDE.md`, `AGENTS.md` і `.cursor/rules/`, зливаючись із наявною конфігурацією; його безпечно запускати повторно
- П'ять інструментів MCP: `start_work` заявляє завдання та очікувані файли чи модулі й повертає перекриття з активними заявками інших агентів; `inspect_work` показує, хто присутній, активну роботу й застарілі заявки; `update_work` записує контекст або надсилає prompt чи відповідь іншому агентові; `transfer_work` призначає, передає й перепризначає; `finish_work` записує докази й позначає роботу готовою до рев'ю чи завершеною
- Пов'язані worktrees Git розв'язуються до основного checkout, тож кожен worktree репозиторію ділить один робочий простір Concord: сесії, запущені виконавцем worktrees, бачать заявки одна одної до того, як їхні гілки зустрінуться
- Зміни володіння версіонуються: якщо два агенти діють на одній версії завдання, успішним є лише перший перехід, а кожна зміна зберігається в історії лише для додавання
- Стан є базою даних SQLite у каталозі `.concord/` репозиторію, що ігнорує себе через власний `.gitignore`; `HANDOFF.md` і `REVIEW_PACKET.md` експортуються для людей
- Необов'язковий hook Claude Code `PreToolUse` (`concord setup --claude-hooks`), що попереджає, коли редагування торкається файлу, заявленого іншим активним завданням, і блокує його, коли завдання власної сесії задано в `CONCORD_TASK`

**Використання**:

```bash
npm install -g @concord-ai/concord-mcp
cd your-repo && concord setup   # register the MCP server and agent instructions, then restart agent sessions
concord status                  # roster, active work, overlaps, stale claims, review-ready tasks
concord dashboard               # read-only live TUI of agents, tasks and alerts
concord adapters status         # which installed agents can receive live prompts, and how
```

**Обмеження**: молодий проєкт: v0.14.2, 562 зірки й близько 3 400 завантажень npm за 30 днів до 2026-10-18. Координація кооперативна: агенти мають викликати інструменти (setup встановлює інструкції з цим проханням), і поза необов'язковим hook Claude Code ніщо не заважає агентові редагувати заявлений файл. Доставка живих prompt залежить від harness-одержувача; сесії Goose поки не можуть отримувати prompt, а prompt недосяжному агентові завершується невдачею, а не перенаправляється. Стан локальний для одного checkout і його worktrees, якщо ви не входите в необов'язковий режим Concord Cloud. Телеметрія ввімкнена за замовчуванням: назви операцій, результати й часові показники, без коду, шляхів файлів, повідомлень чи вмісту завдань; сервер зберігає IP запиту й виведену країну без автоматичного терміну дії. Вимкніть її через `CONCORD_TELEMETRY_DISABLED=1` (або `DO_NOT_TRACK=1`). Перший інтерактивний `concord setup` також пропонує глобальний режим (за замовчуванням так), що реєструє Concord на рівні користувача й додає короткий розділ до користувацьких файлів інструкцій, як-от `~/.claude/CLAUDE.md`; `concord setup --no-global` видаляє рівно те, що додав.

> **Коли використовувати**: коли два чи більше агентів, часто в різних harness (скажімо, Claude Code і Codex), одночасно працюють в одному репозиторії й ви хочете, щоб вони поділили роботу до редагування, а не виявляли колізію під час злиття. Виконавці worktrees, як-от multiclaude чи claude-squad, тримають файли кожного агента окремо; Concord додає спільний погляд на те, хто що робить у цих worktrees. Він доповнює їх і не замінює.

## Зовнішні фреймворки оркестрації

> **Архітектурна різниця**: Інструменти, описані вище (Gas Town, multiclaude), запускають кілька екземплярів Claude Code поруч. Зовнішні фреймворки оркестрації йдуть далі — вони замінюють або доповнюють внутрішній рівень оркестрації Claude Code власним середовищем виконання, додаючи координацію роїв (swarms), збереження пам'яті та спеціалізовані пули агентів. ### Ruflo (раніше claude-flow)

**GitHub**: [github.com/ruvnet/ruflo](https://github.com/ruvnet/ruflo) (66,3K зірок станом на 2026-07-27, зростання з 18,9K+ у березні 2026)
**npm**: `ruflo` (раніше `claude-flow`) | **Ліцензія**: MIT

Найбільш поширений зовнішній фреймворк оркестрації для Claude Code. Перетворює його на мультиагентну платформу з ієрархічними роями (queen + workers), 98 спеціалізованими агентами (кодери, тестери, рев'юери, архітектори, аудитори безпеки) та збереженням стану в SQLite (AgentDB).

| Сервер MCP зареєстровано | Ні | Так (`memory_store`, `swarm_init`, `agent_spawn` тощо) |
| Найкраще для | Спроби одного плагіна без зобов'язань | Використання в продакшні |

# CLI path (full install — inspect source first)
npx ruflo@latest init wizard
# Do NOT use the curl|bash variant: it pulls from the old repo name (claude-flow) and bypasses package manager security

**Основні функції**:
- Маршрутизатор на основі Q-Learning, який направляє завдання відповідному агенту на основі минулих успішних патернів.
- 30+ вбудованих скілів, 27 hooks, що нативно інтегруються з Claude Code.
- Сервер MCP з 314 інструментами (лише шлях CLI).
- Збереження сесій в SQLite зі спільним використанням пам'яті між різними агентами (AgentDB).
- **Федерація агентів**: кросмашинна співпраця за принципом zero-trust через mTLS та ідентичність ed25519, зі стриманням PII перед виходом назовні та поведінковою оцінкою довіри до кожного учасника. На відміну від LangGraph чи CrewAI (за замовчуванням один екземпляр), агенти Ruflo можуть координуватися між машинами й організаціями без передавання сирих даних. Керується через 9 інструментів MCP і 10 команд CLI.
- 33 нативні плагіни в маркетплейсі Claude Code (рій, пам'ять RAG, безпека, браузерне тестування, IoT та інше)
- Необов'язковий вебінтерфейс на [flo.ruv.io](https://flo.ruv.io/) і планувальник цілей GOAP на [goal.ruv.io](https://goal.ruv.io/)
- Неінтерактивний режим для CI/CD.

> **Примітка щодо тверджень**: проєкт публікує метрики продуктивності (оцінки SWE-Bench, множники швидкості, 22M+ завантажень екосистеми) без повністю незалежної методології. Існує gist бенчмарка SOTA, що порівнює з LangGraph, AutoGen і CrewAI, але незалежне відтворення не підтверджено. Вважайте всі цифри неперевіреними.

> **Примітка щодо зрілості**: перейменовано з claude-flow на початку 2026 року. Пакет npm тепер `ruflo` (підтверджено). Перегляньте вихідний код перед розгортанням у продакшні.

**Коли використовувати**: коли нативних інструментів Task та subagents Claude Code недостатньо, зазвичай для складних багатоетапних конвеєрів, що вимагають збереженого стану між багатьма сесіями, або для команд, яким потрібна координація агентів між машинами через федерацію.

### Athena Flow

**GitHub**: [github.com/lespaceman/athena-flow](https://github.com/lespaceman/athena-flow) | **Ліцензія**: MIT (заявлено)
**Статус**: Спостереження, опубліковано в березні 2026 року, аудит не проводився

Інший архітектурний підхід: замість розширення агентного рівня Claude Code, Athena Flow працює на **рівні гачків**. Він перехоплює події гачків через Unix Domain Socket (NDJSON), спрямовує їх через постійне середовище виконання Node.js та надає TUI для моніторингу та контролю воркфлоу в реальному часі.

```
Claude Code → hook-forwarder → Unix Domain Socket → Athena Flow runtime → TUI
```

Перший реалізований воркфлоу: автономний генератор E2E тестів (готовий вихідний код для Playwright CI). У планах: візуальна регресія, тестування API, підтримка Codex.

**Наразі не рекомендується до використання**: очікується аудит вихідного коду, проєкт занадто новий для оцінки стабільності. Поверніться до аналізу через 4-6 тижнів.

**Юзкейси**: повторювані воркфлоу з великим обсягом даних — опрацювання документів, оцінка кандидатів, класифікація листів, аналіз контрактів. Не підходить для творчих задач із відкритим фіналом, де нативні агенти Claude Code працюють краще.

**Статус**: Спостереження, 8 місяців існування, стандарт MTHDS ще не валідовано у великому масштабі. Стежте за динамікою до Q3 2026.

## Граф знань

### Graphify

Інструмент CLI, що відображає кодову базу (разом із будь-якою сумішшю документів, PDF, зображень і відео) у граф знань, до якого можна робити запити. Замість того, щоб просити Claude Code перечитувати файли щосесії для розуміння структури, ви будуєте граф один раз і запитуєте його. Виграш: значно менше токенів на орієнтацію та виявлені зв'язки, які пропускають grep і ручний перегляд.

**GitHub**: [github.com/safishamsi/graphify](https://github.com/safishamsi/graphify)
**PyPI**: `graphifyy` (зверніть увагу на подвійне y: пакет з одним y є іншим, непов'язаним проєктом)
**Ліцензія**: MIT | **Мова**: Python 3.10+

| Атрибут | Деталі |
|-----------|---------|
| **Встановлення** | `uv tool install graphifyy` (рекомендовано) або `pipx install graphifyy` |
| **Платформи** | Claude Code, Cursor, Copilot CLI, Aider, Codex, Gemini CLI, OpenCode та ще 8+ |
| **Перевірено** | Травень 2026 (v0.8.9) |

**Результати кожного запуску:**

| Файл | Вміст |
|------|---------|
| `graphify-out/graph.html` | Інтерактивна візуалізація з вузлами, на які можна клацати, і фільтрацією |
| `graphify-out/GRAPH_REPORT.md` | Ключові концепції, несподівані зв'язки, пропоновані запитання |
| `graphify-out/graph.json` | Структуровані дані графа, що використовуються повторно в кожному запиті |

**Під капотом: файли кешу в `graphify-out/`:**

Окрім 3 публічних файлів, Graphify тримає шар кешу, що забезпечує інкрементальні перебудови. Ці приховані файли з'являються після першого запуску:

| Файл | Роль |
|------|------|
| `.graphify_ast.json` | Сирий AST від tree-sitter, весь код, без виклику API, часто 15-20 МБ |
| `.graphify_detect.json` | Вивід `collect_files()`: повний маніфест файлів |
| `.graphify_chunk_XX.json` | Партії файлів, надісланих до AI API для семантичного вилучення |
| `.chunk_manifest_XX.json` | Які файли належать кожному фрагменту, використовується `--update` для ізоляції змін |
| `.graphify_semantic.json` | Семантичні вкладення після дедуплікації сутностей |
| `.graphify_uncached.txt` | Файли, ще не кешовані в останньому запуску |
| `cache/` | Хеші вмісту кожного файлу для виявлення змін |

При `--update`: Graphify порівнює поточні хеші вмісту з кешем, визначає, які файли змінилися, повторно обробляє лише їхні фрагменти через AI API, а потім відновлює `graph.json` із незмінених фрагментів плюс нових. Файли, що не змінилися, коштують нуль токенів API.

**Ініціалізація в проєкті:**

```bash
# 1. Build the graph from project root
graphify .

# 2. Register with Claude Code — installs the /graphify skill
graphify install --platform claude

# 3. Commit the output so teammates start with a pre-built map
git add graphify-out/ && git commit -m "chore: add graphify knowledge graph"
# Or exclude it entirely: echo "graphify-out/" >> .gitignore

# 4. Subsequent runs: --update uses semantic caching by content hash
#    Only changed files get re-processed — saves API cost on large repos
graphify . --update
```

**Запити до графа:**

```bash
graphify query "what connects auth to the database?"
graphify path "UserService" "DatabasePool"
```

Після реєстрації в Claude Code встановлений скіл дозволяє Claude читати `graph.json` напряму замість обходу файлів, тож запити відбуваються всередині розмови без повторного читання вихідного коду.

**Ключові аналітичні можливості:**

- **God nodes**: високопов'язані архітектурні вузли, компоненти, від яких залежить усе інше
- **Несподівані зв'язки**: міжмодульні зв'язки, ранжовані за оцінкою несподіваності
- **Вилучення обґрунтування дизайну**: витягує ЧОМУ з вбудованих коментарів і docstring, а не лише ЩО
- **Позначення впевненості**: кожен зв'язок позначено `EXTRACTED` (явний імпорт/виклик), `INFERRED` (виведено з контексту) або `AMBIGUOUS` (позначено для перегляду)

**Підтримка файлів**: 31 мова програмування, Markdown, RST, YAML, HTML, PDF. Відео й аудіо: `pip install graphifyy[video]` (локальний faster-whisper, без зовнішнього виклику API). Документи Office: `pip install graphifyy[office]`.

**Режим сервера MCP:**

```bash
# Exposes: query, shortest_path, god_nodes, neighbor_traversal tools
graphify mcp
```

Для великих кодових баз (graph.json понад ~5 МБ) режим MCP значно ефективніший. Без нього Claude спершу завантажує `GRAPH_REPORT.md` для орієнтації, а потім за потреби підтягує цільові розділи `graph.json`. Із запущеним MCP Claude напряму викликає `god_nodes`, `query "auth flow"` чи `shortest_path` і отримує лише релевантний підграф, без повного завантаження графа в контекст. `graph.json` на 22 МБ, завантажений повністю, коштує набагато більше токенів, ніж 4-5 цільових викликів інструментів MCP, що повертають ту саму відповідь.

**Як Claude використовує встановлений скіл:**

Після `graphify install --platform claude` скіл вводить правило: якщо `graphify-out/` існує в поточному проєкті, ставтеся до архітектурних питань як до запитів до графа, а не читання файлів. Порядок розв'язання на практиці:

1. Claude спершу читає `GRAPH_REPORT.md`, компактний (зазвичай 150-200 КБ), дає орієнтацію щодо god nodes і несподіваних зв'язків
2. Для конкретних запитів Claude звертається до цільових розділів `graph.json`
3. Із запущеним сервером MCP: Claude напряму викликає інструменти `query`, `shortest_path`, `god_nodes` чи `neighbor_traversal`, набагато дешевше в масштабі

Без Graphify: Claude перечитує вихідні файли щосесії для розуміння структури, витрачаючи токени на орієнтацію. З Graphify: ця вартість сплачується один раз під час збірки, а потім амортизується на всі сесії.

**Додаткові експорти**: вікі в стилі Wikipedia з вікілінками між спільнотами, сховище Obsidian із розкладками Canvas, HTML зі згортним деревом D3, діаграми потоку викликів Mermaid з інтерактивним масштабуванням/панорамуванням, надсилання до Neo4j.

**Конфіденційність**: файли коду обробляються локально через tree-sitter, без викликів API для аналізу коду. Документи й PDF надсилаються до вашого налаштованого API моделі AI. Для повністю локального виведення: `pip install graphifyy[ollama]`.

**Командний воркфлоу**: коміт `graphify-out/` у git дає кожному колезі спільну карту при clone. Graphify постачає драйвер злиття git, що запобігає маркерам конфліктів у `graph.json`, і необов'язкові hooks git для автоматичних перебудов при коміті.

**Конвеєр:** `detect() → extract() → build_graph() → cluster() → analyze() → report() → export()`: кожен етап ізольований, без спільного стану. Додавання мови потребує реєстрації екстрактора в `extract.py` плюс залежностей tree-sitter.

**Обмеження:**

- Назва пакета `graphifyy` (подвійне y) є головною причиною тертя: `pip install graphify` встановлює непов'язаний інструмент без жодної помилки
- Вилучення з документів/PDF робить виклики AI API; вартість росте з обсягом документації, а не розміром коду
- v0.8.x швидко розвивається; деякі прапорці CLI змінюються між мінорними версіями, перевіряйте changelog перед оновленням

**Коли використовувати**: великі чи незнайомі кодові бази, де Claude Code палить токени на перечитування файлів лише для розуміння структури. Побудуйте граф один раз, потім запитуйте його. Висока цінність для онбордингу в застарілий код, навігації монорепозиторієм і архітектурного рев'ю перед PR.

## Спостережуваність скілів

### Skillsight

Єдиний інструмент з відкритим кодом для аналітики використання скілів на рівні команди. Приймає телеметрію OTEL Claude Code й показує, які скіли справді викликаються (ким, як часто, у яких сесіях), а не які скіли, на вашу думку, використовуються.

| Атрибут | Деталі |
|-----------|---------|
| **Джерело** | [GitHub: PackmindHub/skillsight](https://github.com/PackmindHub/skillsight) |
| **Автор** | Cédric Teyton (Packmind) |
| **Ліцензія** | Apache 2.0 |
| **Версія** | 0.2.1 (активний, 101 коміт) |
| **Стек** | Bun + Hono + PostgreSQL + React 18 (self-hosted Docker) |
| **Прийом даних** | Надсилання OTLP HTTP від Claude Code або Loki pull із Grafana Cloud |

**Що відстежує:** виклики скілів за користувачем і сесією, каталог плагінів (синхронізований із маркетплейсів Git), сегментацію за когортами, журнал аудиту, потік подій у реальному часі.

**Два режими прийому даних:**

*Пряме надсилання OTLP*: Claude Code надсилає телеметрію прямо до Skillsight. Менша затримка, простіше налаштування:

```json
// ~/.claude/settings.json
{
  "env": {
    "OTEL_LOGS_EXPORTER": "otlp",
    "OTEL_EXPORTER_OTLP_LOGS_ENDPOINT": "http://your-skillsight:4200/api/v0/telemetry/v1/logs",
    "OTEL_EXPORTER_OTLP_LOGS_HEADERS": "Authorization=Bearer <your-ingestion-token>",
    "OTEL_EXPORTER_OTLP_PROTOCOL": "http/json",
    "OTEL_LOG_TOOL_DETAILS": "1",
    "OTEL_LOGS_EXPORT_INTERVAL": "5000"
  }
}
```

*Loki pull*: Skillsight опитує кінцеву точку Grafana Cloud Loki за налаштованим розкладом. Корисно, якщо ви вже агрегуєте журнали там.

Токен прийому створюється в інтерфейсі Skillsight (`/tokens`) і має окремий тип JWT, відмінний від токенів сесій: він може лише записувати телеметрію, а не мати доступ до адмін-інтерфейсу.

**Налаштування (пряме надсилання):**

1. `docker compose up -d`: запускає Skillsight на порту 4200 + Postgres
2. Увійдіть на `http://localhost:4200` із початковими обліковими даними адміністратора
3. Перейдіть на сторінку Onboarding: вона генерує повний фрагмент settings.json із попередньо створеним токеном прийому
4. Скопіюйте фрагмент у `~/.claude/settings.json` або `.claude/settings.json` вашого проєкту
5. Запустіть сесію Claude Code: події з'являються в дашборді протягом 5 секунд

**Застереження щодо розгортання (прочитайте перед виходом у продакшн):**

- **Ніколи не розгортайте без перевизначення `JWT_SECRET` і `ADMIN_PASSWORD_INITIAL`**: типові значення в поставці є буквальними публічними рядками (`change-me-in-production...` і `admin`). Попередження під час запуску не видається. Будь-який екземпляр, досяжний з інтернету з цими типовими значеннями, тривіально компрометується.
- **Задайте `PUBLIC_BASE_URL`** у вашому `.env`: ця змінна керує і політикою CORS, і кінцевою точкою, показаною у фрагменті Onboarding. Без неї CORS є вільним (повертає origin запиту), а фрагмент показує `https://your-domain.com`.
- **Запускайте міграції Drizzle вручну при оновленнях**: контейнер не запускає `drizzle-kit migrate` автоматично при старті (станом на v0.2.1). Якщо оновлюєтеся з 0.1.x, запустіть міграції перед стартом нового контейнера, інакше застосунок упаде на застарілій схемі.

Це відомі проблеми, що активно розробляються. Виправлення прості; стежте за вирішенням у репозиторії.

**Обмеження:**

- Лише self-hosted: пропозиції SaaS немає
- Керування джерелами маркетплейсу лише через API (поки без UI, у документації немає прикладів curl)
- Невідповідність назви образу в README (`skills-obs` проти фактичного `skillsight`): дотримуйтесь `docker-compose.yml`, а не фрагмента curl у README
- v0.2.x: молодий проєкт, деякі шорсткості в документації; проте CLAUDE.md справді корисний для контриб'юторів

**Коли використовувати:** ви хочете знати, які скіли ваша команда справді викликає на практиці, а які ви лише розгорнули. Корисно для ROI бібліотеки скілів, вимірювання ефективності онбордингу та виявлення мертвих скілів.

> **Пов'язане:** [Packmind ContextOps Platform](#розповсюдження-інженерних-стандартів): інструмент того самого автора для *розповсюдження* стандартів серед AI-агентів. Skillsight показує, які скіли використовуються; Packmind допомагає створювати й синхронізувати їх.
> **Оцінка:** [2026-05-18-skillsight-packmind.md](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/docs/resource-evaluations/2026-05-18-skillsight-packmind.md)

## Екосистема плагінів

Система плагінів Claude Code підтримує розширення від спільноти. Документацію див. тут:
- **[Розділ 8 головного посібника](../ultimate-guide.uk.md)** - Система плагінів, команди, встановлення.
- **[claude-plugins.dev](https://claude-plugins.dev)** - Індексовано 11,989 плагінів та 63,065 навичок.
- **[claudemarketplaces.com](https://claudemarketplaces.com)** - Автоматичне сканування GitHub на наявність плагінів.
- **[agentskills.io](https://agentskills.io)** - Відкритий стандарт для навичок агентів (підтримка 26+ платформ).

**Важливі набори навичок (skill packs)**:
- **[Superpowers](https://github.com/obra/superpowers)**: повний набір методологій розробки програмного забезпечення (262K зірок, 23.4K форків станом на 2026-07-27, зростання з 95K+ зірок / 7.5K форків раніше; MIT). 7 контекстно-залежних скілів, що охоплюють повну дугу розробки: виявлення специфікації через сократівський брейнсторм, детальне планування реалізації (завдання на 2-5 хв з точними шляхами файлів), розробка на основі subagents із двоетапним рев'ю (відповідність специфікації, потім якість коду), обов'язкове дотримання TDD (код, написаний до тесту, видаляється), код-рев'ю, керування git worktree і завершення життєвого циклу гілки (рішення merge/PR/discard). Скіли спрацьовують автоматично залежно від контексту: ручний виклик не потрібен. Встановлення: `/plugin install superpowers@claude-plugins-official`. Автор Jesse Vincent (Prime Radiant), MIT. Також підтримує Cursor, Codex, OpenCode і Gemini CLI.
- **[gstack](https://github.com/garrytan/gstack)**: еволюційний набір воркфлоу, що охоплює виявлення попиту (`/office-hours`), продуктове та інженерне рев'ю, код-рев'ю, `/qa`, реліз (`/ship`) і `/retro`. `/landing-report` робить чергу релізу видимою. Дивіться [Cognitive Mode Switching](../workflows/gstack-workflow.uk.md) щодо вибраного шляху, а не повного переліку скілів. Набір документує контролі; він не встановлює результату Lean чи виміряного приросту доставки. Автор Garry Tan. Про AI-агентів, що імітують ролі керівників, а не переглядають продуктові рішення, дивіться [AI Executive Agents](ai-executive-agents.uk.md).
- **[Скіли Matt Pocock](https://github.com/mattpocock/skills)**: окремо обмежені, компонувані інженерні скіли. `/triage` обробляє вхідну роботу, `/to-spec` зберігає рішення, коли робота охоплює кілька сесій, `/to-tickets` створює незалежно тестовані вертикальні зрізи, а `/tdd`, `/code-review` і `/retro` замикають цикл навчання. Автор явно радить пропускати `/to-spec`, коли робота вміщується в одну сесію. Ставтеся до цього як до можливих контролів Lean і вимірюйте їхній вплив на WIP, очікування та прийняті результати, перш ніж називати воркфлоу Lean.
- **[Ponytail](https://github.com/DietrichGebert/ponytail)**: режим "лінивого сеньйора" для AI-агентів. Перед написанням коду агент зупиняється на першому щаблі, що тримається: чи це взагалі має існувати? → stdlib? → нативна можливість платформи? → встановлена залежність? → один рядок? → лише тоді мінімум, що працює. Його README (прочитано 2026-09-30) повідомляє про приблизно 54% менше коду в середньому (до 94% на одному завданні), на 22% менше токенів і приблизно на 20% нижчу вартість на 12 завданнях фіч з Haiku 4.5 (n=4) та стверджує, що раніша цифра 80-94% була стелею на завдання, а не середнім. Сторонній запуск Stet виміряв +20%, потім -2% вартості навантаження за два повторення, із більшою кількістю програшів у тестах, ніж виграшів (див. [незалежні бенчмарки](context-engineering-tools.uk.md#незалежні-бенчмарки)). Три рівні інтенсивності: `lite` (пропонує лінивіший шлях, дає користувачеві вибрати), `full` (примушує драбину, за замовчуванням), `ultra` (екстреміст YAGNI, ставить під сумнів вимогу у тій самій відповіді). Свідомі скорочення позначаються коментарем `ponytail:` із зазначенням стелі та шляху оновлення; `/ponytail-debt` збирає їх у реєстр, щоб "пізніше" лишалося видимим. Чотири команди: `/ponytail [lite|full|ultra|off]`, `/ponytail-review` (рев'ю надмірного інжинірингу поточного diff), `/ponytail-audit` (сканування всього репозиторію), `/ponytail-debt` (реєстр скорочень). Встановлення: `/plugin install ponytail@ponytail`. MIT. Підтримує 13 агентів: Claude Code, Codex, GitHub Copilot CLI, Gemini CLI, Antigravity CLI, OpenCode, pi, OpenClaw, Cursor, Windsurf, Cline, Kiro і VS Code з розширенням Codex.
- **[fable-mode](https://github.com/mrtooher/fable-mode)**: скіл дисципліни виконання для складних завдань, структурований як 4-крокова петля: (1) записати пронумеровану карту етапів з очікуваними результатами перед тим, як щось чіпати, (2) делегувати незалежні етапи паралельним subagents там, де runtime це дозволяє, (3) верифікувати кожен етап перевіркою, яка справді може не пройти (тести, diff, прочитані джерела, а не самооцінка), (4) самокритика як скептичного рев'юера перед доставкою. Названо на честь моделі Claude Fable, але працює на будь-якій моделі; чесно визнає, що формує процедуру, а не стелю можливостей. Три варіанти: `fable-mode` (вбудований на поточній моделі), `fable-sonnet` (закріплює subagent Sonnet), `fable-haiku` (закріплює subagent Haiku для чутливої до вартості роботи). Містить 4 розібрані приклади з різних доменів (помилка null-шляху API, хибно приписане дослідницьке твердження, SQL null, мовчки відкинуті з AVG, багатосесійний рефакторинг без критеріїв завершення), кожен показує, де саме перевірка, що може не пройти, ловить те, що пропускає одноразова спроба. Два операційні правила, вартих уваги: виводьте накопичені попередження при порозі 3, а не по одному; прив'язуйте заміни sed до меж слів, щоб не псувати складні слова. Встановлення: скопіюйте каталог скіла туди, звідки ваше середовище Claude завантажує скіли (запису в реєстрі плагінів ще немає). Без ліцензії. 802 зірки, 86 форків станом на 2026-07-27 (було 477 зірок, 54 форки через 5 днів після запуску в червні 2026).
