# Командна база знань для Claude Code + Cowork

**Час читання**: 18 хвилин
**Рівень підготовки**: Місяць 1+ (тімлід, що розгортає обидва інструменти)

> **Охоплення**: Цей розділ описує, як налаштувати спільну корпоративну базу знань (KB), яку можуть читати і Claude Code (CLI для розробників), і Claude Cowork (десктопний застосунок для не-розробників, research preview). Це перше інфраструктурне питання, з яким стикається більшість команд, що розгортають обидва інструменти. Якщо ви використовуєте лише Claude Code на одній кодовій базі, патерн «репозиторій як KB» із [§9.25 Harness Engineering](../ultimate-guide.uk.md#925-harness-engineering-at-agent-throughput) уже покриває ваші потреби. Цей розділ — для командного випадку: спільні документи, живі системи та повторно використовувані робочі процеси для розробників і працівників знань.

## Пастка «Один інструмент для трьох потреб»

Команда розгортає Claude Code для інженерів і Cowork для PM, операційників і підтримки. Хтось ставить очевидне запитання: «Де нам зберігати корпоративні знання, щоб обидва інструменти могли ними користуватися?» Інстинкт — обрати єдину відповідь. Вікі. Робочий простір Notion. Векторна база даних. Одне місце, один конектор, готово.

Цей інстинкт і є пасткою. Він породжує пів року міграційної роботи, наполовину проіндексований простір Confluence і агента, який усе одно пропускає половину відповідей.

Причина в тому, що «корпоративні знання» — це не одна річ. Коли дивишся, до чого команди насправді хочуть надати агенту доступ, з'являються три різні форми, і кожна має різне найкраще сховище та механізм доступу. Спроба впихнути всі три в один інструмент означає, що щонайменше дві з них пасуватимуть погано.

Три форми:

| Природа знань | Як змінюються? | Найкращий інструмент |
|-------------------------|--------------|---------------|
| **Статичні документи** (runbook-и, ADR, стандарти кодування, онбординг, політики) | Через редагування файлів, з комітами | Версіонований Markdown-репозиторій (Obsidian опційно поверх) |
| **Живі системи** (тікети Jira, сторінки Confluence, записи CRM, внутрішні API) | Безперервно, іншими людьми та процесами | Конектор MCP / plugin до джерела істини |
| **Повторно використовувані командні робочі процеси** (slash-команди, skills, агенти, промпти) | Через командну ітерацію самого робочого процесу | Plugin, що розповсюджується через маркетплейс |

Помилка — вважати всі три «документами, які треба десь зберегти». Статичні документи потребують контролю версій і прямого читання файлів. Живі системи потребують з'єднання з місцем, де дані вже живуть, а не копії, що застаріває в мить синхронізації. Робочі процеси — це взагалі не документи; це поведінка, а поведінку пакують і розповсюджують інакше, ніж вміст.

Щойно ви класифікуєте кожен фрагмент знань за його природою, вибір інструмента стає механічним. Решта цього розділу проходить по кожному рівню з конкретними кроками налаштування, а потім охоплює патерн plugin для робочих процесів, застереження щодо управління чутливими даними та таблицю рішень про те, що будувати першим.

### Чому Claude Projects не підходить

Перед трьома рівнями — один антипатерн, який варто назвати першим, бо команди тягнуться до нього раніше за будь-який із трьох. Claude Projects (вебфункція, де ви завантажуєте файли й чатитеся з ними) виглядає як очевидна спільна KB. Але для команди, що працює з Code і Cowork, це не так.

| Обмеження | Наслідок для командної KB |
|------------|---------------------------|
| Лише веб | Ні Claude Code, ні Cowork не можуть програмно прочитати Project |
| Лише завантаження | Немає живої синхронізації; перезавантажувати треба після кожної зміни |
| Практичний ліміт ~20 файлів | Не масштабується далі жменьки документів |
| Немає доступу до файлової системи | Агент не може навігувати, grep-ити чи перехресно посилатися |

Projects підходять окремій людині, що досліджує фіксований набір PDF у вебзастосунку. Як спільна командна інфраструктура, з якої мають читати два агентні інструменти, вони — глухий кут. Використовуйте їх для разового аналізу, а не як хребет KB.

## Рівень 1: Версіонований markdown-vault (статичні документи)

Більша частина того, що команда називає «базою знань», — це статична документація. Runbook-и, записи архітектурних рішень, стандарти кодування, посібники з онбордингу, документ «як ми деплоїмо», постмортеми інцидентів. Вони змінюються через свідомі редагування, і ви хочете, щоб кожна зміна проходила рев'ю й була оборотною. Цей опис і є визначенням git-репозиторію.

### Чому Markdown-репозиторій, а не вікі

Ключове спостереження: і Claude Code, і Cowork читають локальні файли напряму. Claude Code клонує репозиторій і має повний доступ до файлової системи (читання, grep, перехресні посилання між тисячами файлів). Cowork отримує доступ до тієї самої локальної теки на машині користувача. Обидва інструменти вказують на одне джерело. Немає окремої «ШІ-копії», яку треба синхронізувати, бо агент читає саме джерело.

Вікі (Confluence, хмарний Notion, внутрішній портал) ховає вміст за API чи веб-інтерфейсом. Щоб агент міг це читати, ви додаєте конектор — і тепер ви підтримуєте конектор та турбуєтеся про його свіжість і ліміти запитів. Версіонований Markdown-репозиторій пропускає весь цей шар для статичного вмісту. Агент читає файл. Git відповідає за історію. Pull request-и відповідають за рев'ю.

| Властивість | Markdown-репозиторій | Хмарна вікі |
|----------|---------------|-------------|
| Доступ агента | Пряме читання файлів (без конектора) | Потрібен конектор MCP/API |
| Історія версій | Нативна (git) | Залежить від інструмента, часто слабка |
| Процес рев'ю | Pull request-и | Ручний або відсутній |
| Офлайн / локально | Так | Ні |
| Diff і blame | Нативні | Обмежені |
| Вартість міграції пізніше | Низька (простий текст) | Висока (біль експорту) |

### Налаштування

Створіть окремий репозиторій для спільних знань, відокремлений від будь-якої кодової бази. Клонуйте його у стабільний спільний шлях на кожній машині. Угода, яку вже використовує цей посібник, — директорія `~/Shared/`:

```bash
# На машині кожного члена команди
git clone git@github.com:yourcompany/knowledge-base.git ~/Shared/knowledge-base
```

Дайте йому структуру, що відображає те, як думає команда, а не як виглядає оргсхема:

```
~/Shared/knowledge-base/
├── CLAUDE.md                  # Кореневий індекс (зміст)
├── engineering/
│   ├── deploy-runbook.md
│   ├── incident-response.md
│   └── adr/                   # Записи архітектурних рішень
│       ├── 001-postgres-over-mongo.md
│       └── 002-event-sourcing.md
├── product/
│   ├── roadmap-process.md
│   └── spec-template.md
├── ops/
│   ├── oncall-rotation.md
│   └── vendor-contacts.md
└── policies/
    ├── security-baseline.md
    └── data-handling.md
```

### Кореневий CLAUDE.md як індекс

Найкорисніший файл — кореневий `CLAUDE.md`. Він слугує змістом, що повідомляє агенту, що існує і де це знайти. Claude Code читає `CLAUDE.md` автоматично, коли директорія в зоні видимості. Cowork читає його, коли отримує доступ до теки. Хороший кореневий індекс не містить знань; він вказує на них, щоб агент завантажував лише те, що потрібно для поточного завдання (прогресивне розкриття через файлову систему).

```markdown
# Company Knowledge Base

This repo holds shared static documentation for engineering, product, and ops.
Read the file relevant to your task. Do not guess; if it is not written here,
it is not a company convention.

## Engineering
- Deploy procedure: engineering/deploy-runbook.md
- Incident response: engineering/incident-response.md
- Architecture decisions: engineering/adr/ (one file per decision)

## Product
- How we run roadmap: product/roadmap-process.md
- Spec format: product/spec-template.md

## Ops
- On-call rotation and escalation: ops/oncall-rotation.md
- Vendor and account contacts: ops/vendor-contacts.md

## Policies (read before any external-facing or data work)
- Security baseline: policies/security-baseline.md
- Data handling rules: policies/data-handling.md
```

Це патерн `~/Shared/CLAUDE.md`, згаданий в інших місцях посібника, розгорнутий у робочу структуру. Той самий файл обслуговує обидва інструменти, бо обидва читають файлову систему.

### Obsidian як опційний людський шар

Репозиторій — джерело істини та машинозчитуваний інтерфейс. Люди все одно хочуть зручного способу переглядати й редагувати. Obsidian чисто лягає поверх, бо vault Obsidian — це просто тека з Markdown-файлами. Спрямуйте Obsidian на `~/Shared/knowledge-base/` — і ви отримаєте зворотні посилання, графовий вигляд і швидкий редактор, тоді як git під капотом зберігає історію версій, а агент читає сирі `.md`-файли.

Нічого з Obsidian не є обов'язковим. Це переглядач і редактор для тих, кому він подобається. Агент ніколи не бачить Obsidian; він бачить Markdown. Якщо половина вашої команди воліє VS Code чи простий текстовий редактор, це працює ідентично. Не перевантажуйте специфічний для Obsidian синтаксис (вікіпосилання на кшталт `[[note]]`, callout-и), якщо хочете, щоб файли чисто читалися як стандартний Markdown для агента, бо глибоко вкладені плагіни Obsidian дають синтаксис, який агентові доводиться обходити під час розбору.

### Коли достатньо прямого читання файлів

Для статичних документів пряме читання файлів — і найпростіший, і найточніший підхід, до певної межі. Агент відкриває файл і читає точний вміст без шару пошуку між ними. Немає кроку ембедингу, що може пропустити релевантний уривок, немає чанкінгу, що розрізає процедуру на два видобуті фрагменти. Точка, де це перестає масштабуватися, розглянута на Рівні 3. Для типової командної KB з десятків чи кількох сотень документів Рівень 1 сам по собі — правильна відповідь, і слід опиратися спокусі додавати інфраструктуру пошуку, поки вона справді не потрібна.

## Рівень 2: Конектори MCP для живих систем

Статичні документи — легка половина. Важча половина — знання, що живуть у системах, які інші люди оновлюють цілий день: беклог Jira, простір Confluence, CRM, внутрішнє API метрик. Скопіювати це в Markdown-репозиторій не можна, бо воно застаріває миттєво після копіювання. Дошка спринту змінюється щогодини. Запис клієнта змінюється, коли до нього торкається підтримка. Правильний підхід — підключити агента до системи-першоджерела, щоб він читав актуальний стан на вимогу.

Механізм — MCP (Model Context Protocol). Сервер MCP виставляє живу систему як набір інструментів, які агент може викликати. Claude Code додає сервери MCP через свою конфігурацію. Cowork постачається з нативними конекторами та plugin-ами для поширених систем. Принцип той самий в обох: агент опитує живе джерело, а не синхронізовану копію.

### Atlassian (Jira + Confluence)

Atlassian — найпоширеніший випадок, бо багато команд використовують Jira і Confluence разом. Хороша новина: одне з'єднання покриває обидва.

Для Cowork є нативний plugin Jira. PM без технічного бекграунду може встановити його й попросити Cowork прочитати тікети, підсумувати спринт чи скласти статус-апдейт зі стану живої дошки — і все це без звернення до терміналу.

Для Claude Code використовуйте Atlassian Remote MCP server, що покриває і Jira, і Confluence через одне автентифіковане з'єднання:

```bash
# Додати Atlassian Remote MCP server до Claude Code
claude mcp add --transport http atlassian https://mcp.atlassian.com/v1/sse
```

Перший виклик запускає потік OAuth у браузері. Після авторизації Claude Code може читати задачі Jira та сторінки Confluence з дозволами автентифікованого користувача.

Важливий наслідок: **якщо ваші статичні документи вже живуть у Confluence, вам, можливо, узагалі не треба їх мігрувати.** Те саме з'єднання Atlassian MCP, що читає тікети, читає й сторінки Confluence. Це дає агенту живий доступ до наявної KB без жодної міграції. Компроміс відносно Рівня 1 реальний (немає git-історії, немає рев'ю через pull request, залежність від конектора), тож рішення залежить від того, чи цінуєте ви ці властивості репозиторію достатньо, щоб перенести вміст. Для документів, які вже добре підтримуються в Confluence і часто змінюються через вебінтерфейс вікі, залишити їх на місці й підключитися через MCP — шлях меншого зусилля.

### Notion

Notion пропонує офіційний віддалений сервер MCP на `mcp.notion.com`, а також plugin Claude Code, що пакує специфічні для Notion skills.

```bash
# Додати офіційний Notion MCP server
claude mcp add --transport http notion https://mcp.notion.com/mcp
```

Після OAuth-рукостискання агент може шукати в робочому просторі, читати сторінки й бази даних і (з правами на запис) створювати чи оновлювати вміст. Якщо ваша команда веде KB у Notion, це пряма відповідність випадку Atlassian: підключайтеся до живого робочого простору замість експорту. Шар plugin додає curated skills (наприклад, структурований робочий процес «створити сторінку проєкту зі специфікації»), щоб команда не описувала щоразу ті самі операції Notion на кожній сесії.

### GitBook

Якщо ваша опублікована документація працює на GitBook, ви отримуєте доступ MCP без налаштування, крім знання URL. Кожен опублікований сайт GitBook виставляє нативну кінцеву точку MCP за адресою `/~gitbook/mcp`.

```bash
# Спрямувати Claude Code на нативну кінцеву точку MCP сайту GitBook
claude mcp add --transport http docs https://docs.yourcompany.com/~gitbook/mcp
```

Це дає агенту живий пошук по поточній опублікованій документації, що завжди відображає те, що реально бачать читачі. Для команд, чия зовнішня чи внутрішня документація вже живе на GitBook, це найменш затратне з'єднання з живою документацією, бо нічого не треба хостити і нічого синхронізувати.

### Вибір між Рівнем 1 та Рівнем 2 для документації

Обидва рівні можуть містити «документацію», і вибір між ними не завжди очевидний. Вирішальне питання — як змінюються документи і яке рев'ю ви хочете навколо них.

| Сигнал | Схиляйтеся до Рівня 1 (Markdown-репозиторій) | Схиляйтеся до Рівня 2 (MCP до вікі) |
|--------|------------------------------|----------------------------|
| Документи змінюються через свідомі, перевірені редагування | ✅ | |
| Документи постійно змінюються через вебінтерфейс багатьма людьми | | ✅ |
| Ви хочете рев'ю через pull request на кожну зміну | ✅ | |
| Вміст уже живе в Confluence/Notion/GitBook і підтримується | | ✅ |
| Ви хочете git-історію, diff і blame | ✅ | |
| Ви хочете нуль міграції | | ✅ |
| Той самий агент має читати тікети/записи з цієї системи | | ✅ (один конектор покриває обидва) |

Багато команд зрештою мають обидва: інженерні стандарти та ADR — у Markdown-vault (Рівень 1), продуктова вікі й тікети — через Atlassian чи Notion MCP (Рівень 2). Це правильно. Ці два рівні не конкуренти; вони обслуговують вміст із різними патернами змін.

## Рівень 3: RAG у масштабі

Рівні 1 і 2 покривають майже кожну команду. Рівень 3 існує для однієї конкретної ситуації: у вас стільки документів, що агент не може читати їх напряму, а пошук через конектор надто грубий. У цей момент ви додаєте шар пошуку (RAG, retrieval-augmented generation), що індексує корпус і повертає найрелевантніші фрагменти для кожного запиту.

### Поріг: коли додавати RAG

Не додавайте RAG за замовчуванням. Це інфраструктура, а інфраструктура має вартість підтримки. Картина бенчмарків 2026 року узгоджена щодо цього компромісу:

- **Пряме читання файлів точніше.** Агент читає справжній документ, тож нічого не втрачається через чанкінг чи неузгодженість ембедингів.
- **RAG швидший у масштабі.** Він уникає завантаження великих корпусів у контекст, повертаючи лише релевантні фрагменти.

Практична точка перетину лежить приблизно на **100–1000 документів**, залежно від розміру документів і того, наскільки кожен запит має охоплювати. Нижче цього діапазону читайте файли напряму (Рівень 1) або підключайтеся до джерела (Рівень 2); агент здатен навігувати кількома сотнями файлів, і ви зберігаєте точність прямого читання. Вище цього діапазону корпус більше не вкладається в модель прямого читання, і шар RAG, виставлений агенту як сервер MCP, починає окупати налаштування.

| Розмір корпусу | Рекомендований підхід |
|-------------|----------------------|
| < ~100 документів | Пряме читання файлів (Рівень 1) або живий конектор (Рівень 2) |
| ~100 до ~1000 документів | Справа судження; почніть із прямого читання, додайте RAG, якщо якість пошуку падає |
| > ~1000 документів | Шар RAG як сервер MCP (Рівень 3) |

Сигнал, що ви перетнули поріг, конкретний: агент починає пропускати релевантні документи, які, як ви знаєте, існують, бо не може утримати чи просканувати достатньо корпусу на завдання. Коли це трапляється повторно, додавайте пошук. Не раніше.

### Onyx (self-hosted, open source)

[Onyx](https://github.com/onyx-dot-app/onyx) (раніше Danswer) — це open-source корпоративна платформа RAG, яку ви запускаєте самі. Вона постачається як Docker, включає 50+ конекторів (Slack, Google Drive, Confluence, GitHub, Notion та інші), виконує гібридний пошук (за ключовими словами плюс векторний) і сумісна з Anthropic на боці генерації.

```bash
# Onyx запускається через Docker Compose (self-hosted)
git clone https://github.com/onyx-dot-app/onyx.git
cd onyx/deployment/docker_compose
docker compose -f docker-compose.dev.yml up -d
```

Onyx — сильний вибір, коли дані мають лишатися на вашій власній інфраструктурі, а ви хочете єдиний індекс над багатьма джерелами. Одне застереження, щоб правильно налаштувати очікування: Onyx — це насамперед власна чат-платформа. Вона не інтегрована нативно в Claude Code чи Cowork так, як конектори Рівня 2. Щоб користуватися нею з Claude Code, ви підключаєтеся через поверхню API Onyx (виставлену як сервер MCP перед нею). Це більше інтеграційної роботи, ніж у керованих варіантів нижче, і ви берете на себе експлуатацію стека. Винагорода — повний контроль і резиденція даних on-premise, що саме потрібно деяким командам (див. розділ про управління).

### LlamaCloud (керований)

[LlamaCloud](https://cloud.llamaindex.ai/) — це керований сервіс RAG з офіційним сервером MCP, що означає: Claude Code може опитувати його напряму без запуску власного стека пошуку.

```bash
# Підключити Claude Code до керованого RAG LlamaCloud через його сервер MCP
claude mcp add --transport http llamacloud https://mcp.llamaindex.ai/sse
```

Ви завантажуєте та індексуєте свій корпус у LlamaCloud, а агент опитує індекс через інструменти MCP. LlamaCloud поєднується з LlamaParse для документів, що чинять опір наївному вилученню: складні PDF із таблицями, багатоколонковою версткою, відскановані форми. Якщо ваша KB рясніє такими джерелами (фінансові звіти, контракти, технічні специфікації), LlamaParse — та частина, що робить різницю, бо саме чистий парсинг визначає, чи поверне пошук придатні фрагменти.

### Ragie (найшвидше кероване налаштування)

[Ragie](https://www.ragie.ai/) — керований сервіс RAG, позиціонований навколо швидкого підняття робочого індексу. Коли мета — «підняти пошук над нашими документами сьогодні вдень, а не в цьому спринті», Ragie — керований варіант із найменшим налаштуванням. Ви вказуєте джерела, він індексує, а ви опитуєте його з агента. Компроміс проти LlamaCloud — ширина парсингу та контроль налаштування; компроміс проти Onyx — він керований (немає резиденції on-premise). Обирайте його, коли швидкість до робочого індексу важливіша за тонкий контроль.

### Порівняння варіантів Рівня 3

| Варіант | Хостинг | Зусилля на налаштування | Нативний MCP для Code | Найкраще, коли |
|--------|---------|--------------|---------------------|-----------|
| **Onyx** | Self-hosted (Docker) | Високі | Ні (через його API) | Дані мають лишатися on-prem; багато джерел, один індекс |
| **LlamaCloud** | Керований | Середні | Так | Складні PDF (LlamaParse); потрібне кероване, але з налаштуванням |
| **Ragie** | Керований | Низькі | Так | Найшвидший шлях до робочого індексу |

## Патерн plugin: розповсюдження командних робочих процесів

Третя форма знань із таблиці на початку — це взагалі не документи. Це повторно використовувана поведінка: slash-команди, skills, агенти й промпти, що кодують, як працює ваша команда. Команда `/deploy-checklist`, skill `incident-summary`, агент для code review, налаштований на ваші стандарти. Це не вміст для зберігання; це поведінка для розповсюдження, а механізм розповсюдження — plugin.

### Тримайте вміст у vault, поведінку — у plugin

Чітке розділення, що діє на всіх трьох рівнях: **вміст живе у vault (Рівень 1) або в системі-джерелі (Рівень 2/3); поведінка живе в plugin.** Plugin не вбудовує базу знань. Він посилається на неї. Skill, що підсумовує інциденти, читає документи про інциденти з `~/Shared/knowledge-base/engineering/`; skill — це поведінка, документи — вміст. Це дає змогу оновлювати кожне у власному циклі. Ви переглядаєте runbook без повторного релізу plugin і покращуєте робочий процес, не чіпаючи документи.

### Що пакує plugin

Plugin Claude Code об'єднує в одну встановлювану одиницю:

- **Slash-команди** (`commands/`): іменовані робочі процеси, які викликає команда, як-от `/release` чи `/oncall-handoff`
- **Skills** (`skills/`): структуровані можливості, що агент завантажує за потреби
- **Агенти** (`agents/`): спеціалізовані субагенти з власними інструкціями та інструментами
- **Конфігурації MCP**: визначення конекторів Рівня 2/3, тож встановлення plugin також налаштовує доступ до живих систем

Саме останній пункт робить plugin правильним домом для всього шару доступу до KB. Новий член команди встановлює один plugin і отримує команди команди, skills команди та MCP-з'єднання команди з Jira, Notion чи індексом RAG, усе налаштоване. Йому не треба вручну редагувати конфігурацію MCP чи копіювати файли команд.

### Розповсюдження через marketplace.json

Plugin-и розповсюджуються через маркетплейс — git-репозиторій з маніфестом `marketplace.json`, що перелічує доступні plugin-и. Команда публікує свій plugin у внутрішньому (або публічному) репозиторії маркетплейсу, і члени встановлюють звідти:

```bash
# Додати маркетплейс команди, потім встановити plugin KB
claude plugin marketplace add yourcompany/claude-plugins
claude plugin install knowledge-base
```

Мінімальний запис `marketplace.json`:

```json
{
  "name": "yourcompany-plugins",
  "plugins": [
    {
      "name": "knowledge-base",
      "description": "Team KB access: commands, skills, and live-system MCP connectors",
      "source": "./plugins/knowledge-base"
    }
  ]
}
```

Коли ви покращуєте команду чи додаєте skill, ви пушите в репозиторій маркетплейсу, і команда оновлюється однією командою. Знання про робочі процеси лишаються версіонованими й переглянутими, так само як статичні документи, і поширюються на всіх без ручного копіювання файлів. Саме цю модель використовує власна [екосистема plugin-ів](https://github.com/FlorianBruniaux/claude-code-plugins) цього посібника: шаблони створюються один раз, розповсюджуються як встановлювані plugin-и.

## Застереження щодо управління та чутливості

Наведена вище архітектура оптимізована для доступу. Перш ніж підключати до неї чутливий корпус, чесно зважте сторону управління (governance), бо два агентні інструменти тут різного рівня зрілості.

### Поточні прогалини Cowork

Станом на середину 2026 року Cowork — це research preview, і його корпоративне управління має прогалини, що важливі для регульованих чи чутливих даних. Особливо дві:

- **Аудит-логи**: корпоративні аудит-сліди рівня enterprise з можливістю запитів про те, до чого агент мав доступ і що робив, ще не повні. Якщо ваша політика відповідності вимагає повного запису кожного прочитаного документа та кожної виконаної дії, Cowork цього поки не дає.
- **DLP (запобігання витоку даних)**: інтеграція з корпоративними інструментами DLP обмежена. Засоби, що запобігають виходу чутливих даних за схвалені межі, не такі зрілі, як у усталеному корпоративному софті.

Практичний висновок: Cowork доречний для внутрішніх, але не секретних знань (процесні документи, продуктовий контекст, загальні операції), доки ці прогалини не закриються. Це ще не той інструмент, який варто спрямовувати на ваш найчутливіший корпус, якщо ви працюєте за суворих вимог аудиту чи DLP. Claude Code з його усталенішою системою дозволів і hooks дає більше точок контролю, але все одно слід перевіряти відповідність вашим конкретним вимогам, а не припускати покриття.

### Коли дані мають лишатися on-premise

Якщо дані настільки чутливі, що не можуть залишати вашу інфраструктуру взагалі, відповідь — не «підключити хмарний сервіс RAG». Це утримати все всередині межі, яку ви контролюєте. Відповідний патерн, у research preview станом на травень 2026 року, — корпоративні self-hosted пісочниці з приватними тунелями MCP: агент працює в пісочниці на вашій інфраструктурі, а його з'єднання з внутрішньою KB іде через приватний тунель MCP, що ніколи не виставляє дані назовні. Self-hosted варіант Рівня 3 (Onyx) вписується в цю модель на боці пошуку, бо індекс і документи лишаються на вашому обладнанні.

Це більше налаштування, ніж будь-який керований шлях. Суть у тому, що така опція існує, тож «наші дані надто чутливі для хмари» — це питання конфігурації, а не причина взагалі відмовитися від агентної KB. Підбирайте розгортання під чутливість даних, а не нав'язуйте один підхід для всіх.

### Задокументована опорна точка

Власна документація Anthropic показує патерн живої KB через MCP у дії. Приклад кінцевої точки `https://kb.internal.example.com/mcp`, описаної як «Internal knowledge base and documentation search», є канонічною формою: внутрішня KB, виставлена як сервер MCP, що агент опитує на вимогу. Це Рівень 2 (або Рівень 3 за ним) для self-hosted KB, і саме цей патерн захищає наведений вище підхід із self-hosted пісочницею.

## З чого почати

Помилка на початку цього розділу полягала в тому, щоб тягнутися до одного інструмента. Виправлення — класифікувати кожен фрагмент знань за його природою, а потім застосувати відповідний рівень. Ось шлях рішення, від найпоширенішої відправної точки назовні.

### Таблиця рішень

| Якщо ваша ситуація... | Почніть із | Чому |
|-------------------------|------------|-----|
| Статичні командні документи, десятки або кілька сотень файлів | **Рівень 1**: Markdown-vault у `~/Shared/`, кореневий індекс `CLAUDE.md` | Обидва інструменти читають його напряму, повна історія, без конектора |
| Документи вже добре підтримуються в Confluence/Notion/GitBook | **Рівень 2**: конектор MCP до цієї системи | Нуль міграції; один конектор також покриває тікети/записи |
| Потрібні живі тікети, стан спринту, записи CRM | **Рівень 2**: Atlassian / Notion / MCP джерела | Живе джерело істини, ніколи не застаріла копія |
| Понад ~1000 документів і агент щось пропускає | **Рівень 3**: RAG як MCP (LlamaCloud/Ragie керовані, Onyx self-hosted) | Пошук масштабується за межі ліміту прямого читання |
| Повторно використовувані командні команди, skills, агенти для спільного використання | **Plugin** через `marketplace.json` | Поведінка розповсюджується однією встановлюваною одиницею, разом із конфігураціями |
| Чутливі дані, що не можуть залишати вашу інфраструктуру | **Self-hosted** (Onyx + приватний тунель MCP / корпоративна пісочниця) | Резиденція on-premise, агент залишається всередині вашої межі |

### Рекомендована послідовність для нової команди

1. **Спершу підніміть Рівень 1.** Створіть спільний Markdown-репозиторій, напишіть кореневий індекс `CLAUDE.md`, клонуйте його в `~/Shared/` на кожній машині. Лише це покриває більшість потреб і Code, і Cowork, і це дешево підтримувати. Опирайтеся спокусі додавати інфраструктуру пошуку, доки не маєте доказів, що вона потрібна.

2. **Підключіть одну-дві живі системи, що найважливіші.** Зазвичай Jira (Atlassian MCP) для інженерії та продукту, плюс та вікі, що містить ваші наявні документи, якщо ви вирішили їх не мігрувати. Додавайте конектори Рівня 2 по одному, а не всі разом.

3. **Запакуйте ваші повторювані робочі процеси як plugin**, щойно помітите, що команда щоразу на сесії описує ті самі операції. Опублікуйте його у внутрішньому маркетплейсі, щоб встановлення було однією командою. Тримайте вміст у vault, а поведінку — у plugin.

4. **Додавайте шар RAG лише тоді, коли корпус перерос пряме читання.** Сигнал — агент повторно пропускає документи, які, як ви знаєте, існують. Доки цього немає, Рівень 3 — це витрати без користі.

5. **Звіряйте управління з фактичною чутливістю ваших даних** перед тим, як спрямовувати будь-який інструмент на чутливий корпус, з особливою обережністю щодо поточних прогалин Cowork в аудиті та DLP. Для даних, що не можуть залишати вашу інфраструктуру, одразу йдіть у self-hosted, а не доопрацьовуйте це пізніше.

Команди, що досягають успіху, сприймають це як три окремі проблеми з трьома окремими інструментами, з'єднаними через MCP і plugin-и, а не як одне рішення про сховище, яке треба ідеально вгадати наперед. Почніть із Markdown-vault, підключіть живі системи, до яких ви справді звертаєтеся, і додавайте масштаб і пакування, коли виникне потреба.
