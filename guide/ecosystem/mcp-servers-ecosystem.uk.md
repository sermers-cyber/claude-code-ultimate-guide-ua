# Екосистема MCP-серверів

**Останнє оновлення**: Травень 2026 • **Наступний перегляд**: Червень 2026

Цей посібник охоплює перевірені сервери MCP від спільноти, окрім офіційних серверів від Anthropic. Усі перелічені сервери було оцінено на предмет готовності до використання у виробничому середовищі (production readiness), активності обслуговування та безпеки.

> **Не впевнені, що використовувати: MCP-сервер чи CLI-інструмент?** Дивіться [Посібник із вибору: MCP проти CLI](./mcp-vs-cli.md) для детального розбору компромісів, матриці рішень та рекомендацій для конкретних ситуацій.

## Офіційні сервери проти серверів спільноти (Official vs Community)

| Тип | Приклади | Характеристики | Коли використовувати |
|------|----------|-----------------|----------------------|
| **Офіційні** | filesystem, memory, brave-search, github | Підтримуються Anthropic, гарантована стабільність | Вибір за замовчуванням, базовий функціонал |
| **Спільноти** | Playwright, Semgrep, Kubernetes | Підтримуються організаціями/особами, можуть бути готові до продакшену | Спеціалізовані потреби, інтеграція в екосистему |

**Kлючова відмінність**: Офіційні сервери мають підтримку SLA від Anthropic, сервери спільноти потребують індивідуальної оцінки.

## Фреймворк оцінки (Evaluation Framework)

Усі сервери спільноти оцінюються за такими критеріями:

| Критерій | Поріг | Обґрунтування |
|-----------|-----------|---------------|
| **GitHub Stars** | ≥50 | Мінімальна перевірка спільнотою |
| **Останній реліз** | <3 місяців | Активне обслуговування |
| **Документація** | README + приклади + конфігурація | Зменшує труднощі впровадження |
| **Тести/CI** | ✅ Автоматизовано | Гарантує стабільність |
| **Сценарій використання** | Не покривається офіційними серверами | Уникає дублювання |
| **Ліцензія** | Потрібен відкритий код (OSS) | Стійкість та можливість аудиту |

**Компоненти оцінки якості (Quality Score)**:
- Обслуговування (10 балів): частота релізів, час реагування на проблеми (issues)
- Документація (10 балів): повнота README, приклади, вирішення проблем (troubleshooting)
- Тести (10 балів): покриття тестами, автоматизація CI/CD
- Продуктивність (10 балів): час відповіді, ефективність використання ресурсів
- Впровадження (10 балів): використання спільнотою, розгортання в продакшені

**Загальна оцінка**: `/50` → Нормалізовано до `/10` для фінального рейтингу.

## Контроль версій (Офіційні сервери)

Ці фундаментальні MCP-сервери забезпечують автоматизацію контролю версій для всіх робочих процесів розробки. **Офіційні сервери Anthropic** із гарантованою стабільністю.

### Git MCP (Anthropic)

**Офіційний сервер Anthropic** для взаємодії з репозиторіями Git через Model Context Protocol. Надає програмний доступ до операцій Git зі структурованим виводом та безпекою на різних платформах.

**Репозиторій**: [modelcontextprotocol/servers/git](https://github.com/modelcontextprotocol/servers/tree/main/src/git)
**Ліцензія**: MIT
**Статус**: Рання розробка (API може змінюватися)
**Зірки**: 77,908+ (батьківський репозиторій)

**Сценарії використання**:
- **Автоматизовані процеси комітів**: ШІ генерує повідомлення комітів, додає зміни до індексу, робить коміти
- **Аналіз логів**: фільтрація комітів за датою, автором, гілкою зі структурованим виводом
- **Управління гілками**: створення гілок для фіч, checkout, фільтрація за SHA
- **Економія токенів при диффах**: контроль кількості рядків контексту для сфокусованого перегляду коду
- **Автоматизація кількох репозиторіїв**: керування кількома репозиторіями у монорепозиторіях

#### Основні можливості

| Інструмент | Опис | Параметри |
|------|-------------|------------|
| `git_status` | Стан робочого дерева (staged, unstaged, untracked) | - |
| `git_log` | Історія комітів із розширеною фільтрацією | `max_count`, `skip`, `start_timestamp`, `end_timestamp`, `author` |
| `git_diff` | Різниця (diff) між комітами/гілками | `target`, `source`, `context_lines` |
| `git_diff_unstaged` | Неіндексовані зміни | `context_lines` |
| `git_diff_staged` | Індексовані зміни | `context_lines` |
| `git_commit` | Створення коміту | `message` |
| `git_add` | Додавання файлів/шаблонів до індексу | `files` |
| `git_reset` | Видалення файлів з індексу | `files` |
| `git_branch` | Список/фільтрація гілок | `contains`, `not_contains` |
| `git_create_branch` | Створення нової гілки | `name` |
| `git_checkout` | Перемикання гілок/комітів | `ref` |
| `git_show` | Деталі коміту | `revision` |

**Розширена фільтрація** (`git_log`):
- **Дати ISO 8601**: `2024-01-15T14:30:25`
- **Відносні дати**: `2 weeks ago`, `yesterday`, `last month`
- **Абсолютні дати**: `2024-01-15`, `Jan 15 2024`
- **Фільтр авторів**: `--author="John Doe"`

#### Налаштування

**Встановлення (3 методи)**:

```bash
# Метод 1: UV (рекомендовано) - в один рядок
uvx mcp-server-git --repository /path/to/repo

# Метод 2: pip + модуль Python
pip install mcp-server-git
python -m mcp_server_git

# Метод 3: Docker (в пісочниці)
docker run -v /path/to/repo:/repo ghcr.io/modelcontextprotocol/mcp-server-git
```

**Конфігурація Claude Code** (`~/.claude.json`):

```json
{
  "mcpServers": {
    "git": {
      "command": "uvx",
      "args": ["mcp-server-git", "--repository", "/Users/you/projects/myrepo"]
    }
  }
}
```

**Підтримка кількох репозиторіїв**:

```json
{
  "mcpServers": {
    "git-main": {
      "command": "uvx",
      "args": ["mcp-server-git", "--repository", "/path/to/main-repo"]
    },
    "git-docs": {
      "command": "uvx",
      "args": ["mcp-server-git", "--repository", "/path/to/docs-repo"]
    }
  }
}
```

#### Матриця рішень: Git MCP проти GitHub MCP проти Bash Tool

**Коли який інструмент використовувати**:

| Операція | Git MCP | GitHub MCP | Bash Tool | Обґрунтування |
|-----------|---------|------------|-----------|---------------|
| **Локальні коміти** | ✅ Найкраще | ❌ | ⚠️ Нормально | Структурований вивід, безпека на різних ОС |
| **Управління гілками** | ✅ Найкраще | ❌ | ⚠️ Нормально | Фільтрація `git_branch`, включення/виключення SHA |
| **Аналіз diff/log** | ✅ Найкраще | ❌ | ⚠️ Нормально | Контроль `context_lines`, економія токенів |
| **Індексація файлів** | ✅ Найкраще | ❌ | ⚠️ Нормально | Відповідність шаблонам (`git_add`), безпечніше |
| **Створення PR** | ❌ | ✅ Найкраще | ⚠️ gh CLI | API GitHub, теги, виконавці, рецензенти |
| **Керування Issues** | ❌ | ✅ Найкраще | ⚠️ gh CLI | Специфічні операції GitHub |
| **Перевірка CI/CD** | ❌ | ✅ Найкраще | ⚠️ gh CLI | Інтеграція з GitHub Actions |
| **Інтерактивний rebase** | ❌ | ❌ | ✅ Найкраще | Git MCP не підтримує прапорець `-i` |
| **Відновлення через reflog** | ❌ | ❌ | ✅ Найкраще | Складні операції Git |
| **Налагодження через git bisect** | ❌ | ❌ | ✅ Найкраще | Складні робочі процеси налагодження |
| **Багатоінструментальні пайплайни** | ✅ | ✅ | ❌ | MCP-сервери поєднуються з іншими інструментами MCP |

**Дерево рішень**:

```
Це операція, специфічна для GitHub (PR, Issues, Actions)?
├─ ТАК → Використовуйте GitHub MCP
└─ НІ → Це базова операція Git (commit, branch, diff, log)?
    ├─ ТАК → Використовуйте Git MCP (структурований, безпечний, економний для токенів)
    └─ НІ → Це розширена функція Git (rebase -i, reflog, bisect)?
        ├─ ТАК → Використовуйте інструмент Bash (гнучкість)
        └─ НІ → За замовчуванням використовуйте Git MCP (безпечніший, структурований)
```

**Приклади робочих процесів**:

| Робочий процес | Ланцюжок інструментів | Обґрунтування |
|----------|-----------|---------------|
| **Розробка фічі** | Git MCP (`git_create_branch` + `git_commit`) → GitHub MCP (PR) | Атомарний, структурований, повний життєвий цикл |
| **Аналіз історії комітів** | Git MCP (`git_log` з параметром `start_timestamp: "2 weeks ago"`) | Економна фільтрація токенів, відносні дати |
| **Підготовка до рев'ю коду** | Git MCP (`git_diff` з параметром `context_lines: 3`) | Сфокусований контекст, зменшення витрат токенів |
| **Очищення комітів (rebase)** | Bash tool (`git rebase -i HEAD~5`) | Інтерактивний режим відсутній у Git MCP |
| **Відновлення втрачених комітів** | Bash tool (`git reflog`) | Reflog не доступний через Git MCP |
| **Пошук багів за допомогою bisect** | Bash tool (`git bisect start/good/bad`) | Процес bisect відсутній у Git MCP |
| **Автоматизований реліз** | Git MCP (коміт + тег) → GitHub MCP (створення релізу) | Повна автоматизація, структурована робота |

## Перевірені сервери спільноти (Validated Community Servers)

### Автоматизація браузера (Browser Automation)

#### Playwright MCP (Microsoft)

**Офіційний сервер Microsoft** для автоматизації браузера, оптимізований для LLM. Використовує дерева доступності (accessibility trees) замість скріншотів, що значно зменшує витрати токенів.

**Сценарій використання**: ШІ-агенти перевіряють свою роботу в браузерах (E2E-тестування, перевірка багів).

**Основні можливості**:

| Функція | Деталі |
|------------|---------|
| Автоматизація браузера | Навігація, кліки, заповнення форм, наведення курсору (Playwright API) |
| Вилучення контенту | Структуровані дані через дерева доступності |
| Скріншоти | Повні сторінки + скріншоти конкретних елементів |
| Виконання JavaScript | Запуск коду в контексті сторінки |
| Управління сесіями | Збереження стану браузера |
| Підтримувані браузери | Chromium, Firefox, WebKit |

**Налаштування**:

```bash
# Встановлення
npm install @microsoft/playwright-mcp
# або
npx @microsoft/playwright-mcp
```

**Конфігурація Claude Code** (`~/.claude.json`):

```json
{
  "mcpServers": {
    "playwright": {
      "command": "npx",
      "args": ["--yes", "@microsoft/playwright-mcp"]
    }
  }
}
```

**Приклад використання**:

```
Користувач: "Перейди на example.com, увійди з поштою test@example.com, потім зроби скріншот"

Claude: [Використовує playwright_navigate → playwright_type → playwright_click → playwright_screenshot]

Результат: Скріншот + дерево доступності в контексті
```

**Оцінка якості**: **8.8/10** ⭐⭐⭐⭐⭐

| Вимір | Оцінка | Примітки |
|-----------|-------|-------|
| Обслуговування | 9/10 | Релізи кожні два тижні, активна команда Microsoft |
| Документація | 9/10 | Повний README, приклади, відео Playwright Live |
| Тести | 10/10 | Великий набір тестів, автоматизований CI/CD |
| Продуктивність | 8/10 | Швидкі знімки (~200ms), ефективне використання пам'яті |
| Впровадження | 8/10 | 2890+ використань (за даними відстеження Smithery.ai) |

**Обмеження та обхідні шляхи**:

| Обмеження | Обхідний шлях |

| Один сеанс браузера | Використовуйте ID сесії для збереження стану |

#### Sentry MCP

**Офіційний сервер Sentry** для моніторингу помилок та спостережуваності. Замикає цикл діагностики: спрацьовує сповіщення Sentry → Claude читає помилку + стек-трейс → діагностує першопричину → пропонує або пише виправлення.

**Репозиторій**: [getsentry/sentry-mcp](https://github.com/getsentry/sentry-mcp)
**Ліцензія**: MIT
**Підтримка**: Sentry (офіційно)

**Сценарій використання**: у продакшені спрацьовує алерт Sentry. Інженер запитує Claude: "У чому причина SEN-4521?". Claude вивчає весь стек-трейс, відстежує регресію в коді та створює патч — безпосередньо в IDE. Контур спостережуваності замикається всередині Claude Code.

**Основні інструменти**:

| Інструмент | Опис |
|------|-------------|
| `list_issues` | Отримання невирішених помилок із синтаксисом запитів Sentry (`is:unresolved level:error`) |
| `get_issue` | Повні деталі помилки — стек-трейс, постраждалі користувачі, час першої/останньої появи |
| `get_event` | Конкретна подія за ID, корисно для часово-обмежених розслідувань |
| `search_events` | Повнотекстовий пошук за сирими подіями з фільтрами полів |
| `list_projects` | Список проектів у вашій організації Sentry |

**Налаштування**:

```bash
# Через npx (рекомендовано — звірте ім'я пакета з офіційною документацією)
npx -y @sentry/mcp-server

# Додавання в один рядок для Claude Code
claude mcp add sentry -- npx -y @sentry/mcp-server
```

**Конфігурація Claude Code** (`~/.claude/settings.json`):

```json
{
  "mcpServers": {
    "sentry": {
      "command": "npx",
      "args": ["-y", "@sentry/mcp-server"],
      "env": {
        "SENTRY_AUTH_TOKEN": "your_auth_token",
        "SENTRY_ORG": "your-org-slug"
      }
    }
  }
}
```

> Токен авторизації: [sentry.io/settings/account/api/auth-tokens/](https://sentry.io/settings/account/api/auth-tokens/) — необхідні права: `project:read`, `event:read`, `org:read`

**Приклад використання**:

```
Користувач: "Що викликає SEN-4521? Вона з'явилася після вчорашнього деплою."

  [get_issue: issue_id="4521"]

Результат: NullPointerException в UserController.getProfile() на рядку 142.
  З'явилася у коміті a3f8c2 (вчора о 14:32 UTC) — видалено перевірку null
  під час рефакторингу профілю. Рішення: відновити Optional.ofNullable на рядку 142.
  Створюю PR.
```

**Синтаксис запитів** (критично для ефективного використання — найчастіша причина помилок виклику):

```
is:unresolved                         # лише невирішені помилки
is:unresolved level:error             # лише помилки (без warnings, info)
is:unresolved has:user                # помилки з ідентифікованими користувачами
is:unresolved times_seen:>100         # високочастотні помилки
project:api-service is:unresolved     # обмеження до одного проекту
assigned:me is:unresolved             # помилки, призначені на вас
!has:assignee is:unresolved           # помилки без відповідального
```

### Пошук та аналіз коду (Code Search & Analysis)

#### Grepai MCP

**Сервер спільноти** для семантичного пошуку коду та аналізу графа викликів за допомогою локальних ембеддингів Ollama. Шукає код за наміром (intent), наприклад, "платіжний шлюз", "логіка авторизації", замість точного збігу тексту, а також відстежує зв'язки викликів функцій.

**Репозиторій**: [yoanbernabeu/grepai](https://github.com/yoanbernabeu/grepai)
**Ліцензія**: MIT
**Статус**: Активна розробка
**Конфіденційність**: Повністю локально (Ollama + nomic-embed-text), дані не залишають ваш пристрій

**Сценарій використання**: розробнику потрібно розібратися в незнайомій кодовій базі → grepai знаходить релевантний код за текстовим описом природною мовою та будує зв'язки функцій без повного зчитування файлів.

**Основні можливості**:

| Функція | Деталі |
|------------|---------|
| `grepai_search` | Семантичний пошук за запитом природною мовою (наприклад, "error handling middleware") |
| `grepai_trace_callers` | Пошук усіх функцій, які викликають вказаний символ |
| `grepai_trace_callees` | Пошук усіх функцій, які викликаються вказаним символом |
| `grepai_trace_graph` | Повний граф викликів (callers + callees) із налаштовуваною глибиною |
| `grepai_index_status` | Перевірка стану: проіндексовані файли, чанки, конфігурація |

**Ефективність використання токенів**:

| Процес | Токени | Вердикт |
|----------|--------|---------|
| Пошук через Grep + читання файлів (brute force) | ~15K | Багато шуму, нерелевантний контекст |
| Пошук grepai + трасування | ~4K | Сфокусовані, лише релевантні результати |
| Лише пошук grepai (без деталізації) | ~2-3K | Швидке ознайомлення |

**Налаштування**:

```bash
# Встановлення grepai
curl -sSL https://raw.githubusercontent.com/yoanbernabeu/grepai/main/install.sh | sh

# Встановлення Ollama + модель ембеддингів
brew install ollama
ollama pull nomic-embed-text

# Ініціалізація у вашому проекті
cd /path/to/project
grepai init  # Оберіть: ollama, nomic-embed-text, gob

# Індексація кодової бази
grepai index

# Опціонально: моніторинг змін (авто-індексація)
grepai watch
```

**Конфігурація Claude Code**:

```bash
claude mcp add grepai -- grepai mcp
```

**`.mcp.json` (у межах проекту)**:

```json
{
  "mcpServers": {
    "grepai": {
      "command": "grepai",
      "args": ["mcp"]
    }
  }
}
```

**Приклад використання**:

```

  - src/auth/middleware.ts:12-45 (0.89)
  - src/routes/login.ts:8-32 (0.85)
  - src/utils/jwt.ts:1-28 (0.78)

Користувач: "Що викликає функцію validateToken?"

  - refreshHandler → validateToken
  - wsAuthGuard → validateToken
```

| Вимір | Оцінка | Примітки |

| Обслуговування | 8/10 | Активна розробка, швидка реакція автора |

**Обмеження та обхідні шляхи**:

### Оркестрація (Orchestration)

#### MCP-Compose

**Інструмент спільноти** для керування кількома MCP-серверами у стилі Docker Compose. Декларативна конфігурація YAML, підтримка кількох видів транспорту (STDIO/HTTP/SSE).

**Сценарій використання**: розробнику потрібно запустити 5+ MCP-серверів; конфігурація у стилі Docker Compose спрощує керування їхнім життєвим циклом.

**Основні можливості**:

| Функція | Деталі |
|------------|---------|
| Конфігурація YAML | Визначення серверів у стилі Docker Compose |
| Мультитранспортність | Підтримка STDIO, HTTP, SSE, TCP |
| Середовища виконання | Docker, Podman, локальні процеси |
| Управління мережею | Автоматичне створення мереж Docker |
| Моніторинг стану | Пули з'єднань, керування сесіями |
| Проксі-сервер HTTP | Єдина уніфікована кінцева точка HTTP |
| Гаряче перезавантаження | Оновлення конфігурації без перезапуску |

**Налаштування**:

```bash
git clone https://github.com/phildougherty/mcp-compose
cd mcp-compose
cargo build --release
```

**Конфігурація** (`mcp-compose.yaml`):

```yaml
version: "1.0"
mcpServers:
  filesystem:
    command: npx
    args:
      - "@modelcontextprotocol/server-filesystem"
      - "/tmp"
    transport: stdio

  memory:
    command: npx
    args:
      - "@modelcontextprotocol/server-memory"
    transport: stdio
    env:
      DEBUG: "true"

  postgres:
    image: postgres:15
    transport: tcp
    port: 5432
    env:
      POSTGRES_PASSWORD: secret

proxy:
  port: 3000
  listen: "127.0.0.1"
```

**Генерація конфігурації Claude Desktop**:

```bash
./mcp-compose create-config --type claude --output ~/.claude.json
```

**Запуск серверів**:

```bash
./mcp-compose up
# Єдиний уніфікований проксі HTTP на http://localhost:3000
```

**Оцінка якості**: **7.4/10** ⭐⭐⭐⭐

**Обмеження**:

| Обмеження | Обхідний шлях |
|------------|-----------|
| Потребує компіляції Cargo | Використовуйте готові бінарні файли (якщо доступні) |
| Складність вивчення YAML | Використовуйте шаблони для типових конфігурацій |
| Складність налагодження | Використовуйте логи `mcp-compose logs` для пошуку проблем |

**Ресурси**:

### Контрольний список безпеки (Security Checklist)

- [ ] **Ключі API** зберігаються у файлі `.env`, а не у файлах конфігурації
- [ ] **RBAC/дозволи** перевірено (особливо для Kubernetes, Semgrep)
- [ ] **Ліміти запитів** узгоджено (складність Linear GraphQL, Vercel API)
- [ ] **Резервні механізми** для випадків недоступності API реалізовано
- [ ] **Моніторинг та логування** активовано для всіх MCP-серверів

**Мінімум (Essentials)**:

- [ ] **Сервери спільноти**: Огляд трендових серверів на GitHub (≥50 зірок, реліз <3 місяців тому)
- [ ] **Зміни в екосистемі**: Моніторинг блогу Anthropic на предмет оновлень протоколу
- [ ] **Стан серверів**: Переоцінка наявних серверів (релізи, проблеми, обслуговування)
- [ ] **Безпека**: Перевірка на виявлені вразливості (GitHub Security Advisories)
- [ ] **Застаріле**: Виявлення архівних репозиторіїв або проектів без підтримки
- [ ] **Оновлення посібника**: Додавання нових перевірених серверів, видалення застарілих

### Шаблон оцінки

Для кожного потенційного сервера:

1. **Базова перевірка**:
   - Чи має GitHub stars ≥50?
   - Чи був останній реліз <3 місяців тому?
   - Чи повна документація (README + приклади + налаштування)?
   - Чи присутні тести/CI?

2. **Оцінка якості** (див. [Фреймворк оцінки](#evaluation-framework)):
   - Обслуговування: `/10`
   - Документація: `/10`
   - Тести: `/10`
   - Продуктивність: `/10`
   - Впровадження: `/10`
   - **Разом**: `/50` → Нормалізовано до `/10`

3. **Аналіз сценарію використання**:
   - Яку проблему вирішує?
   - Чи покривається він вже офіційними серверами?
   - Які є альтернативи?

4. **Рішення**:
   - **Інтегрувати** (оцінка ≥8): додавання розділу до посібника
   - **Спостерігати** (оцінка 6-7): додавання до [Списку спостереження](../../docs/resource-evaluations/watch-list.md), повторна оцінка наступного місяця
   - **Відхилити** (оцінка <6): документування причин у розділі [Виключені сервери](#excluded-servers)

### Процес інтеграції

При додаванні нового сервера:

1. Створіть розділ у відповідній категорії (Browser Automation, DevOps тощо)
2. Вкажіть:
   - Опис сценарію використання
   - Таблицю ключових можливостей
   - Інструкції з налаштування
   - Приклади конфігурації
   - Оцінку якості
   - Обмеження та обхідні шляхи
   - Порівняння альтернатив
   - Ресурси (GitHub, документація, інструкції)
3. Оновіть [Базовий стек розробника](#quick-start-stack), якщо інструмент є критично важливим
4. Оновіть [Контрольний список безпеки](#security-checklist), если это важно для безопасности

## Документування MCP для Claude: Паттерн довідкового файлу (Reference File Pattern)

Коли ви інтегруєте MCP-сервер у навичку (skill), Claude доводиться самостійно розбиратися з синтаксисом запитів, обов'язковими комбінаціями параметрів та особливостями поведінки. Для простих MCP це працює. Але для складних систем виробничого рівня (інструменти спостережуваності, API управління проектами, лог-агрегатори) цей підхід швидко ламається. Claude робить припущення щодо формату параметрів, отримує незрозумілу помилку, пробує інші варіанти і марнує ваш бюджет токенів на зайві спроби.

Рішення від інженерної команди Packmind (відкрите під ліцензією Apache 2.0): додайте файл `references/<mcp-name>.md` поруч із файлом навички, і зробіть так, щоб першим кроком навичка зчитувала цей файл перед будь-яким викликом MCP.

### Що містить довідковий файл

Три типи контенту, які Claude не може надійно вивести самостійно:

**1. Семантика параметрів, яка відрізняється від назви інструменту**

Наприклад, інструмент "пошуку" Datadog, який використовує синтаксис запитів Datadog (а не регулярні вирази). Або інструмент Sentry, який вимагає параметр `organization_slug` (ідентифікатор з URL, а не відображувану назву компанії). Це не баги в MCP, це просто неочевидні деталі реалізації.

**2. Відомі паттерни помилок та причини їх виникнення**

Наприклад: "Якщо ви використовуєте псевдоніми `SELECT` у секції `GROUP BY` з DDSQL, ви отримаєте незрозумілу помилку. Замість цього повторіть повний вираз". Це перетворює 10-хвилинне розслідування на миттєве виправлення.

**3. Працюючі приклади запитів для 80% випадків**

Приклади копіювання та вставки, які охоплюють найчастіші запити. Claude може адаптувати їх, а не будувати з нуля.

### Структура файлів

```
.claude/skills/my-mcp-skill/
├── SKILL.md                    # Головний файл навички
└── references/
    └── <mcp-name>.md           # Довідковий файл MCP (цей паттерн)
```

Сценарій `SKILL.md` зчитує довідковий файл на першому ж кроці:

```markdown
## Крок 1: Зчитування довідкового файлу MCP

Перш ніж робити будь-що інше, прочитайте `references/<mcp-name>.md`.
Він містить синтаксис запитів та відомі особливості роботи цього MCP.
Не пропускайте цей крок.
```

### Чому це працює

Довідковий файл — це не документація для людей. Це структуроване впровадження контексту. Кожна деталь у ньому зменшує ймовірність некоректного виклику MCP з боку Claude. За умови правильного налаштування це усува циклу повторних спроб через синтаксичні помилки і робить навичку достатньо надійною для запуску за розкладом без постійного нагляду.

Цей паттерн підходить для будь-якого MCP з нетривіальною поведінкою: Datadog, Sentry, PagerDuty, Linear, Jira, Mixpanel, Posthog. Якщо MCP має власну мову запитів, особливості пагінації або обов'язкові параметри з неінтуїтивними назвами, створення довідкового файлу окупається з першого ж запуску.

### Готовий шаблон для використання

Повний шаблон навички, що демонструє цей паттерн (на прикладі Sentry), доступний за адресою:

`examples/skills/mcp-integration-reference/` у цьому репозиторії

Шаблон містить:
- `SKILL.md` із 5-кроковою структурою (читання довідки, збір контексту, отримання даних, аналіз, звіт)
- `references/sentry-mcp.md` із повною документацією параметрів, підводними каменями, прикладами запитів та списком виключення шуму
- Інструкції з адаптації під будь-який інший сервер MCP

> Створено на основі довідкового файлу Datadog MCP з [офіційного репозиторію Packmind](https://github.com/packmind/packmind) (Apache 2.0, Cédric Teyton). Повний опис авторства дивіться у [Credits](../core/credits.md).
