# Agentic software factories: карта орієнтації

Ця сторінка відповідає на одне питання: ви хочете використовувати Claude Code як щось ближче до фабрики ПЗ, ніж до однієї сесії, тож з чого почати і що обрати. Вона не повторює детальний матеріал, який уже є в шести інших файлах цього посібника. Вона вказує на нього по порядку й додає дві речі, яких бракувало: чесне дерево рішень для закритих комерційних платформ і контрольний список управління, що містить питання, якого не ставить про себе жодна сторінка вендора.

**Час читання**: ~15 хв
**Передумови**: базове знайомство із субагентами та інструментом Task
**Пов'язане**: [Agent Teams](./agent-teams.uk.md), [Dynamic Workflows](./dynamic-workflows.uk.md), [Plan-Validate-Execute Pipeline](./plan-pipeline.uk.md), [Spec-First Development](./spec-first.uk.md), [Loop & Graph Engineering](../core/loop-graph-engineering.uk.md), [Agent Tools: Beyond Claude Code](../ecosystem/agentic-tools.uk.md)

## Прочитайте карту, перш ніж додавати площину керування

Фабрика ПЗ поєднує кілька шарів. Модель міркує; runtime harness володіє циклом кодування; repository harness надає інструкції та детерміновані бар'єри постачання; оркестратор розподіляє роботу між сесіями чи робочими просторами. Фабрика чи площина керування може координувати середовища виконання, не стаючи самим середовищем виконання.

Починайте з [Agent Harness Map](../ecosystem/agent-harness-landscape.uk.md), коли питання в тому, який продукт володіє циклом кодування, а які записи каталогу лише суміжні. Читайте [Agent Harness Engineering](../core/agent-harness.uk.md) про межі шарів, [Loop & Graph Engineering](../core/loop-graph-engineering.uk.md) про потік керування та контракти судження, [Agent Tools: Beyond Claude Code](../ecosystem/agentic-tools.uk.md) про фреймворки й продукти оркестрації, [Agent Evaluation](../roles/agent-evaluation.uk.md) про протокол тестування, [Session Observability](../ops/observability.uk.md) про слід доказів і [Security Hardening](../security/security-hardening.uk.md) перед тим, як дозволити роботу без нагляду. Терміни визначено в [глосарії](../core/glossary.uk.md).

### Фабрика ПЗ — це операційна модель

Купівля платформи не створює фабрики ПЗ. Операційна модель визначає, хто пише намір, яке середовище виконання діє, де зберігається стан, які перевірки можуть блокувати прогрес, хто обробляє винятки та хто може випускати незворотну зміну. Продукт може запакувати ці функції, але розподіл відповідальності залишається вашим.

| Відповідальність | Власник за замовчуванням | Потрібні докази |
|---|---|---|
| намір, обсяг і толерантність до ризику | відповідальна людина | версіонована специфікація та названий власник |
| обмежене виконання | runtime harness або граф workflow | траса, політика інструментів, бюджет і причина зупинки |
| механічна верифікація | repository harness або рушій політик | команда, вивід, статус виходу та ревізія артефакту |
| неоднозначний виняток або реліз із високим впливом | названа людина або попередньо уповноважена політика | вердикт, посилання на докази та запис про виняток |
| майбутнє вдосконалення процесу | версіонований цикл вдосконалення | кандидат-diff та оцінювання на відкладеній вибірці |
| чи принесла випущена зміна задуману цінність | особа, що написала намір, зазвичай продукт | сигнал результату чи впровадження, названий до початку роботи, зчитаний після релізу |

Павань Белагатті (Pavan Belagatti) підсумовує цей розподіл так: ["агенти виконують роботу, люди забезпечують бар'єри"](https://www.youtube.com/watch?v=0nM1ygBm8tA&t=97s). Його довший розбір фабрики ПЗ показує [бар'єр людського рев'ю](https://www.youtube.com/watch?v=pE1S1egMrAI&t=908s) плюс [автоматичний відкат і зворотний зв'язок](https://www.youtube.com/watch?v=pE1S1egMrAI&t=764s) у workflow на базі Port. Відео доводять, що продемонстрований workflow можна налаштувати. Вони не вимірюють надійність, сукупну вартість, час рев'юерів, поведінку за ворожих вхідних даних чи порівняльну продуктивність.

Звіт OpenAI [Harness Engineering](https://openai.com/index/harness-engineering/) використовує споріднену фразу «Люди керують. Агенти виконують» і документує один внутрішній експеримент з нуля. Його самозвітні оцінки пропускної здатності та часу корисні як свідчення реалізації, але не як нейтральний бенчмарк. В обох описах людина виходить із повторюваного виконання, залишаючись відповідальною за управління.

### Обмеження зміщується вгору за течією, до того, що варто будувати

Більшість дизайнів фабрик ПЗ, включно з кожним рівнем у розділі 1, оптимізують інженерний час: швидша реалізація, більше паралельних агентів, щільніші цикли верифікації. Швидше виробництво коду може перемістити обмеження на продуктові рішення, рев'ю, реліз чи впровадження. Знайдіть реальну точку очікування для одного класу запитів, перш ніж збільшувати потужність генерації. Фабрика, що вимірюється лише обсягом коду, не може показати, чи отримують користувачі корисний результат швидше.

Опис OpenAI власного конвеєра вказує в той самий бік (див. [розділ 6](#6-the-half-of-the-factory-that-runs-after-the-merge) щодо джерела та його меж). Венкат Венкатараман (Venkat Venkataramani) відносить судження, пріоритезацію та смак до першого етапу, де людина визначає результат, і стверджує, що інженери OpenAI дедалі більше стають схожими на продакт-менеджерів, ніж на традиційних системних інженерів. Та сама стаття повідомляє, що фахівці предметної галузі вбудовані в інженерні команди ChatGPT Work, бо в деяких доменах розробники вже не можуть самостійно передати потрібний смак у harness, наприклад, як виглядає добра презентація чи бізнес-звіт. Це самоопис однієї компанії, а не виміряний результат, але він локалізує роботу, що лишається людською, в намірі й судженні, а не у виконанні.

Два наслідки для будь-кого, хто будує фабрику:

- **Поверніть автора наміру до верифікації.** Перше питання розділу 4 запитує, чи бар'єр детермінований. Поруч існує друга прогалина: тести можуть проходити, не покриваючи того, про що просив тікет. Агент рев'ю лише для читання може порівняти критерії прийняття тікета з фактично написаними тестами й повідомити людині, яка їх написала, про критерії, які жоден тест не перевіряє. Результатом є список прогалин для судження цієї людини, а не схвалення. [Spec-first development](./spec-first.uk.md) розглядає, як писати критерії прийняття, які агент може перевірити.
- **Вимірюйте другу половину.** Фабрика, що звітує про пропускну здатність і частку невдалих змін, але не про впровадження чи час до цінності, повторює на продуктовому боці пастку, яку розділ 5 описує на боці коду. Продуктові метрики з [Team Metrics](../ops/team-metrics.uk.md#product-metrics-the-often-missing-layer) є відсутньою половиною дашборда фабрики, а останній рядок таблиці вище дає їм власника.
- **Завершіть одну повну одиницю, перш ніж додавати лінії.** Для змін у legacy визначте наявну поведінку, виконайте характеризаційні перевірки до модифікації, доставте один придатний зріз через обов'язковий шлях рев'ю й релізу та протестуйте відкат або видалення старого шляху. Карта репозиторію з коректними посиланнями на джерела допомагає обрати одиницю; вона не доводить поведінки під час виконання. Карта ризиків може спрямовувати людське рев'ю, але її мітки потребують власника та спостережених тестів, перш ніж надавати агентові більше автономії. [Methodologies](../core/methodologies.uk.md#lean-software-engineering-as-a-delivery-lens) порівнює вибори планування й тестування, а [цикл контрзаходів repository harness](../core/agent-harness.uk.md#lean-countermeasure-loop-for-a-repository-harness) тестує засоби контролю в точці виконання роботи.

## 1. Спектр: шість рівнів, шість вартостей

Кожен варіант нижче розв'язує реальну проблему, якої не розв'язує попередній рівень. Жоден не безкоштовний, і вартість рідко зводиться лише до грошей.

**Рівень 0: одна сесія Claude Code.** Не розв'язує нічого понад те, що вміщують один розробник, одне вікно контексту й одна розмова. Коштує стільки, скільки вже коштує ваша підписка. Переходьте вище, коли завдання природно розпадається на незалежні шматки, які інакше змусили б вас вручну перемикати контекст всередині однієї сесії.

**Рівень 1: `/batch`.** Нативна команда, додана у v2.1.63, що розподіляє велику повторювану зміну (міграцію, масовий прохід з анотацією типів, заміну залежності) між 5–30 паралельними агентами, кожен у власному git worktree, кожен відкриває власний pull request. Розв'язує випадок «та сама правка, багато файлів, спільне судження не потрібне». Коштує приблизно N разів вартість токенів одного агента, що виконує одну одиницю роботи, сплачується наперед, без накладних витрат на координацію, бо координувати нічого: одиниці незалежні за побудовою. Повний опис за адресою [guide/ultimate-guide.md:9642](../ultimate-guide.uk.md#the-batch-command). Переходьте вище, коли одиниці насправді не незалежні, коли їм потрібно бачити виводи одна одної або коли завдання не повторюване, а дослідницьке.

**Рівень 2: Agent Teams (нативно, експериментально).** Кілька екземплярів Claude Code, що координуються через git і спільну поштову скриньку, із головним агентом, який синтезує результати від учасників. Розв'язує координацію з переважним читанням: багатокутне рев'ю коду, паралельне тестування гіпотез під час налагодження, аналіз архітектури з кількох перспектив одночасно. Коштує 3x чи більше токенів порівняно з одним агентом і реальне когнітивне навантаження на розуміння, коли це допомагає, а коли лише спалює бюджет за той самий результат. Існує шість задокументованих продакшен-кейсів (Fountain, CRED, внутрішній проєкт компілятора C від Anthropic Research, застосунок для пошуку роботи Пола Рейнера, паралельне тестування гіпотез та один великий рефакторинг), усі докладно описані з джерелами в [guide/workflows/agent-teams.md](./agent-teams.uk.md), розділ 4. Дерево рішень у [guide/workflows/agent-teams.md](./agent-teams.uk.md), розділ 7, уже відокремлює Agent Teams від звичайної роботи з кількома екземплярами та двома екземплярами; прочитайте його, перш ніж читати щось інше на цій сторінці. Переходьте вище, коли робота перестає бути «кілька агентів дивляться на одне й те саме» і стає «кілька агентів будують різні частини визначеного конвеєра».

**Рівень 3: Dynamic Workflows (`ultracode`).** Конвеєр, оркестрований на JavaScript, доданий у v2.1.154, побудований із невеликого набору примітивів (`agent`, `parallel`, `pipeline`, `phase`), що дає детермінований потік керування, валідовані за схемою виводи між етапами та автоматичне відновлення після переривання. Сам скрипт оркестратора нічого не коштує під час виконання; кожен долар іде на виклики `agent()`, які він робить. Це найближче до скриптованої фабрики в нативному наборі інструментів: реальний приклад dev-flow (від issue до змерженого PR) задокументований наскрізно в [guide/workflows/dynamic-workflows.md](./dynamic-workflows.uk.md), розділ 7. Переходьте вище, коли потрібен довготривалий стан між багатьма запусками, керований ADR цикл навчання або формальний поділ plan-validate-execute з незалежними рев'юерами, чого самі лише сирі примітиви не дають.

**Рівень 4: Plan-Validate-Execute Pipeline.** Три команди (`/plan-start`, `/plan-validate`, `/plan-execute`), побудовані на тих самих примітивах, що додають динамічний пул дослідницьких агентів, двошаровий пул незалежної валідації та цикл навчання ADR, який зменшує, як часто людині доводиться переривати наступний запуск. Повністю задокументовано в [guide/workflows/plan-pipeline.md](./plan-pipeline.uk.md), включно з реальним профілем вартості (зазвичай від $2 до $10 за функцію Tier 2, що знижується зі зростанням покриття ADR). Це практична стеля того, що нативний набір інструментів Claude Code пропонує сьогодні для чогось, що нагадує фабрику ПЗ. Переходьте вище, лише якщо вам потрібно щось зовсім поза екосистемою Anthropic: федерація агентів між машинами, інший провайдер моделей, змішаний у конвеєр, або керований вендором шар управління, який ви не хочете будувати самостійно.

**Рівень 5: сторонні фреймворки оркестрації.** Інструменти, що стоять над Claude Code чи поряд із ним і керують кількома екземплярами чи агентами на рівні, якого нативний набір не досягає: Ruflo (ієрархічні рої, федерація між машинами), Gas Town і multiclaude (менеджери робочих просторів для кількох Claude), Entire CLI (управління насамперед, послідовні передачі, аудиторські сліди комплаєнсу), CAO (AWS Labs, делегування supervisor-worker через MCP з кожним агентом у власній сесії tmux, і єдиний проєкт цієї категорії, що пережив перевірку bus-factor, див. [agentic-tools.md §4.6](../ecosystem/agentic-tools.uk.md#46-cli-agent-orchestrator-cao-aws-labs)). Повне порівняння в [guide/ecosystem/third-party-tools.md](../ecosystem/third-party-tools.uk.md) у розділах Multi-Agent Orchestration та External Orchestration Frameworks, а також у [guide/ecosystem/agentic-tools.md](../ecosystem/agentic-tools.uk.md) для інструментів, що замінюють Claude Code, а не оркеструють його. Вартість зростає одразу трьома шляхами: витрати токенів, інфраструктура для запуску й підтримки оркестратора та час на вивчення режимів відмов другої системи поверх власних режимів Claude Code. Переходьте вище (радше вбік) до рівня 6, лише якщо ви також хочете, щоб хтось інший володів усім життєвим циклом від специфікації до розгортання, а не лише шаром координації.

**Рівень 6: закриті фабрики ПЗ повного циклу.** Комерційні платформи (Maleus, Factory.ai, Blitzy і Devin, коли використовується так), що виконують увесь цикл за керованим інтерфейсом: приймання специфікації, ізольована паралельна збірка, валідація, розгортання. Задокументовано як ринкову категорію в [guide/workflows/spec-first.md:959-999](./spec-first.uk.md#full-cycle-ai-software-factories). Саме тут важливий розділ 2 нижче, бо чесну вартість цього рівня не публікує жоден вендор.

## 2. Відсутнє дерево рішень: коли закрита фабрика ПЗ справді перемагає

У цьому посібнику вже є два дерева рішень для суміжних виборів: робота з кількома екземплярами проти одного екземпляра в [guide/ultimate-guide.md:20320](../ultimate-guide.uk.md#decision-matrix) (розгалужується за кількістю розробників і бюджетом) та Agent Teams проти кількох екземплярів проти двох екземплярів у [guide/workflows/agent-teams.md](./agent-teams.uk.md), розділ 7 (розгалужується за формою завдання). Еквівалента для вибору між закритою фабрикою ПЗ і нативним стеком (Agent Teams, `/batch`, dynamic-workflows), що вже покриває більшу частину тієї самої території за вартість підписки Claude, не існувало. Ось одне, побудоване на тому, що справді можна було перевірити, а не на заявах вендорів.

```
Чи потрібен вам весь цикл від специфікації до розгортання під одним вендором?
├─ Ні, вам просто потрібне швидше паралельне виконання визначених завдань
│  └─ Використовуйте рівні 1-4 (нативний стек). Зупиніться тут.
│
├─ Так, але ваша команда вміє писати специфікації та рев'ювати PR
│  ├─ Розмір команди < 10, немає виділеного інженера платформи
│  │  └─ Нативний стек (рівні 2-4) майже завжди виграє за вартістю й контролем.
│  │     Закрита фабрика додає стосунки з вендором, другу модель
│  │     білінгу та ризик прив'язки заради проблеми, яку ви вже можете розв'язати.
│  │
│  ├─ Розмір команди 10-50, бюджет чітко виділено на інструменти
│  │  ├─ Є регуляторна чи аудиторська вимога (SOC2, HIPAA, простежуваність)?
│  │  │  └─ Розгляньте Entire CLI (походження сесій, пов'язане з комітами,
│  │  │     бар'єри злиття на його хостингу forge, сумісний з Claude Code)
│  │  │     перед повною закритою фабрикою.
│  │  │     Див. guide/ops/ai-traceability.md, розділ 5.1.
│  │  └─ Немає драйвера комплаєнсу, просто хочете рухатися швидше
│  │     └─ Запустіть пілот однієї закритої фабрики на одному обмеженому проєкті.
│  │        Не мігруйте основну кодову базу в першому пілоті.
│  │
│  └─ Розмір команди 50+, або нерозробники-стейкхолдери мають випускати продукт
│     └─ Закрита фабрика (Maleus для наміру природною мовою, Factory.ai
│        для архітектури Missions, Blitzy для дуже великих кодових баз)
│        стає виправданою. Виконайте контрольний список управління з розділу 4
│        нижче, перш ніж щось підписувати, бо вендор не виконає його
│        за вас.
│
└─ Так, і ви хочете самохостинг та повністю зберегти код усередині компанії
   └─ OpenHands — найближчий open-source еквівалент паралелізму Devin
      на графі залежностей, ціною власного запуску
      інфраструктури. Див. guide/ecosystem/agentic-tools.md,
      розділ 2.4.
```

Скажімо прямо те, що зазвичай замовчують: для малої команди — майже ніколи. Сприймайте це як редакційне судження цього посібника, а не виміряний поріг, бо ніхто не опублікував порівняльного дослідження вартості, що розв'язало б питання. Міркування за ним, однак, можна перевірити: Agent Teams має шість задокументованих продакшен-кейсів із джерелами ([`agent-teams.md`](./agent-teams.uk.md), розділ 4), тоді як закриті платформи мають раунди фінансування й демо, але жодного незалежно верифікованого розгортання з метриками. Agent Teams плюс `/batch` плюс dynamic-workflows уже покривають переважну більшість того, що продає закрита фабрика ПЗ, за ціну підписки Claude, а не другого контракту з вендором. Прогалина, що лишається, здебільшого не в можливостях. Вона в пакуванні управління: аудиторські сліди, бар'єри схвалення та кероване інтерфейсне середовище для людей, які не читатимуть git diff. Якщо вам потрібне саме це пакування, купуйте його. Якщо ви купуєте закриту фабрику, бо паралельне виконання агентів звучить так, ніби потребує виділеної платформи, — вона не потрібна, ще ні, не за такого розміру команди.

Прогалина у свідченнях діє і в зворотний бік, і це має насторожувати будь-кого незалежно від розміру команди. Будьте точні щодо того, в чому прогалина, бо закритим платформам не бракує названих клієнтів. Cognition публікує Mercedes-Benz (200 000 рядків COBOL, оцінка у вісім місяців скорочена до восьми днів) та Itaú (70% вразливостей безпеки розв'язано автоматично). Blitzy публікує модернізацію мейнфрейму Fortune 100 (33 мільйони рядків за 3,5 дня), QAD і Builders FirstSource (3x швидкість). Factory публікує агреговані цифри (550 000 заощаджених людино-годин, доставка в 31 раз швидша). Це реальні компанії, які погодилися бути названими, і відкидати їх як порожнечу було б нечесно.

Проблема на один рівень глибше. Кожна з цих цифр повідомлена вендором, а не клієнтом і не незалежною третьою стороною. Огляд у липні 2026 року для цього посібника не зміг знайти жодного випадку в категорії, де клієнт опублікував власні виміряні результати або де нейтральна сторона верифікувала результати вендора. Назване лого — це схвалення, а не вимір, який можна перевірити. Mercedes дозволив Cognition опублікувати «від восьми місяців до восьми днів» і не опублікував власних цифр. У цій відмінності вся суть: шість кейсів Agent Teams у [`agent-teams.md`](./agent-teams.uk.md), розділ 4, мають джерелом практиків, які їх запускали, тоді як кейси закритих платформ мають джерелом сторінку продажів. Єдині сторонні сигнали, що з'явилися під час огляду, свідчать проти платформ, а не за них: задокументований звіт про три команди, які відмовилися від Devin упродовж першого кварталу, та польові звіти, що оцінюють частку дефектів у коді, згенерованому агентами, приблизно в 1,5–2 рази вищою, ніж у коді, написаному людьми. Незалежного порівняльного дослідження вартості закритої фабрики й нативного стеку не існує взагалі, і саме ця цифра розв'язала б судження «майже ніколи» вище, і саме її ніхто не опублікував. Ставтеся до кожної заяви з маркетингових матеріалів закритої фабрики так, як розділ 5 нижче ставиться до README: перевірте, що це підключено, перш ніж повірити.

## 4. П'ять питань управління перед впровадженням будь-чого

[guide/workflows/spec-first.md:970-975](./spec-first.uk.md#full-cycle-ai-software-factories) уже перелічує чотири питання, які варто поставити перед впровадженням будь-якої платформи повного циклу, закритої чи відкритої. Тут їх повторено, бо вони так само стосуються нативного конвеєра dynamic-workflow, який ви будуєте самі, як і платформи вендора, плюс п'яте, додане за прямими свідченнями.

1. **Детермінований бар'єр чи самооцінка LLM?** Чи окремий не-LLM процес (лінтер, перевірка типів, набір тестів, валідація контрактів) блокує злиття, чи агент, що написав код, сам вирішує, чи він правильний?
2. **Чи є механізм «зупинити лінію»?** Після N невдалих спроб виправлення конвеєр зупиняється й ескалює до людини, чи продовжує повторювати спроби, спалюючи токени?
3. **Чи простежуване кожне рішення?** Чи можете ви постфактум відновити, який агент і яка версія моделі зробили конкретну зміну і чи схвалила її людина?
4. **Чи лишається специфікація авторитетною після першої генерації?** Чи код відходить від специфікації, коли застосунок розвивається за межі першої версії, без надійного механізму синхронізації?
5. **Чи справді функція верифікації, що її рекламує README, підключена до шляху коду, який виконується?** Це не гіпотетична проблема. Аудит на рівні вихідного коду однієї самоописаної «фабрики ПЗ» (див. розділ 5 нижче) знайшов 986-рядковий модуль змагальної верифікації, справді сильний дизайн, що відповів би на питання 1 вище краще за більшість альтернатив у цьому посібнику, імпортований лише через `import type`. Імпорти лише типів стираються під час компіляції. Модуль ніколи не створювався в єдиній виробничій точці входу; шлях коду, що мав би його викликати, мовчки вважав перевірку невдалою. Функція існувала, була протестована і не виконувалася. Перевірка того, що файл існує чи навіть імпортується, нічого не доводить про те, чи він виконується. Просіть конкретну точку входу під час виконання, що викликає код верифікації, а не існування модуля в репозиторії.

## 5. Пастка необмеженої швидкості

Оцінка на рівні вихідного коду Fusion, самоописаного «фабрики ПЗ, що працює під багатоагентним оркестратором», повністю задокументована в [docs/resource-evaluations/fusion-multi-agent-orchestrator.md](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/docs/resource-evaluations/fusion-multi-agent-orchestrator.md). Вона коротка й заслуговує на пряме читання. Підсумок тут навмисно вузький: що вона демонструє про швидкість без архітектури, а не огляд самого інструмента.

Репозиторію менше чотирьох місяців (перший коміт 2026-03-25, оцінено 2026-07-15), він містить 727 279 рядків коду без тестів, написаних майже повністю однією людиною, що працювала з агентами: 94% із 11 333 комітів у main походять від однієї ідентичності контриб'ютора плюс її бот-акаунтів, а другий людський контриб'ютор має 3,3%. Один файл, `executor.ts`, налічує 19 328 рядків. Два бекенди сховища (SQLite і Postgres) підтримуються у повній паралелі, кожне сховище реалізовано двічі, при цьому дорожня карта досі називає міграцію «запланованою», тоді як рев'ю переходу датоване днем раніше за оцінку. Модуль поведінкової верифікації, описаний у питанні 5 вище, дизайн-патерн, достатньо сильний, щоб розв'язати проблему декоративного CI, яку цей посібник уже позначає в [guide/workflows/spec-first.md:979-988](./spec-first.uk.md#the-decorative-ci-trap-question-1-in-practice), було збудовано, протестовано й ніколи не підключено до продакшену.

Той останній пункт виявився більшим за помилку одного проєкту. Огляд ринку цієї категорії в липні 2026 року, проведений після оцінки Fusion та перехресно перевірений через GitHub API, а не за README проєктів, не зміг знайти жодного підтримуваного open-source оркестратора, який бере код, написаний агентом, генерує проти нього змагальний план атаки, виконує цей план у sandbox і притримує вердикт «готово», доки атаки не зазнають невдачі. Натомість в усіх досліджених інструментах є коди виходу, pre-push hooks, захисти від конфліктів та LLM-рев'юери, що оцінюють інші LLM, і останнє цитована вище стаття Refute-or-Promote емпірично спростовує. Навіть референсна реалізація цієї статті ([abhinavagarwal07/refute-or-promote](https://github.com/abhinavagarwal07/refute-or-promote)) є грою оркестрації (playbook), а не запускним harness, має одну зірку, а її останній коміт зроблено через три дні після першого.

Висновок незручний. Подвійний checkout у Fusion, схоже, є найближчим до індустріалізованої відповіді, яку хтось написав, і він не виконується. Найсильніший механізм на ринку з агрегованою оцінкою в десятки мільярдів лежить у 986 рядках мертвого коду з ліцензією MIT, доступних будь-кому, хто захоче його скопіювати. Змагальна верифікація — не розв'язана проблема, до якої цей посібник запізнився; це відкрита діра, і питання 5 розділу 4 існує через неї.

Усе це не твердження, що агентна швидкість погана. Це вимір того, що відбувається, коли швидкість випереджає архітектуру: 727 000 рядків, випущених за шістнадцять тижнів однією людиною, — це реальна здатність, а не міф. Що ця здатність дає без другого рев'юера, bus factor вищого за один чи свідомої зупинки, щоб злити два бекенди сховища в один, — це документація, що описує поведінку, якої немає, і кодова база, розплутування якої коштуватиме більше, ніж її написання. Масштабуйте власне використання рівнів 3–6 вище з урахуванням цього компромісу. Питання ніколи не в тому, чи можуть агенти виробляти стільки коду. Питання в тому, чи зможе хтось, включно з автором prompt, пояснити через рік, що саме все це робить.

Та сама пастка проявляється й зсередини, а не лише в перевіреній кодовій базі. Власний опис Anthropic масштабування своєї служби вибору тестів для CI ([Agentic coding is straining CI](https://claude.com/blog/agentic-coding-is-straining-ci-heres-how-we-scaled-test-impact-analysis-at-anthropic), вересень 2026; див. [повну оцінку](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/docs/resource-evaluations/2026-09-14-anthropic-ci-test-impact-analysis.md)) описує інфраструктуру верифікації, а не код, що ламається під обсягом, який створюють агенти: більша машина виграла 70 днів, шардування ще 29, щоденні перезапуски менше доби, після чого переписування замінило єдиного записувача-синглтона на stateless, горизонтально масштабований дизайн. Anthropic прямо каже, що окремі техніки масштабування — не те, що слід винести з цієї історії. Висновок той самий, що його Fusion демонструє зовні: швидкість, яка випереджає власний шар верифікації, чи то змагальне тестування, чи конвеєр CI, що вирішує, що тестувати, породжує систему, якій ніхто не може довіряти в питанні, що саме зламалося.

OpenAI повідомляє про ту саму стіну з окремої кодової бази та набору інструментів: приблизно 10-кратне зростання навантаження на деякі системи доставки приблизно за шість місяців, названі в контролі версій, CI/CD та релізі в продакшен, із заявленим очікуванням нової проблеми масштабування інфраструктури щомісяця ([оцінка](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/docs/resource-evaluations/2026-09-15-openai-agentic-software-factory.md), і розділ 6 нижче). Жодний опис не публікує частоту дефектів, частоту пропусків чи частку невдалих змін поряд із цими цифрами пропускної здатності. Дві передові лабораторії, що сходяться на одному вузькому місці, заслуговують на вагу; дві передові лабораторії, які вимірюють лише чисельник, заслуговують на обережність.

## 6. Половина фабрики, що працює після злиття

Кожен рівень у розділі 1 зупиняється в тому самому місці: злитий pull request. Це не випадковість цієї сторінки, а місце, де справді закінчуються нативний набір інструментів і кожен порівнюваний вище оркестратор. Фабрика, що зупиняється на злитті, — це лінія виробництва коду, а не фабрика, бо в ній ніщо не володіє частиною, де ПЗ зустрічається з користувачами.

Перший датований операторський опис іншої половини походить від OpenAI, його навів Гергелі Орос (Gergely Orosz) у [Inside OpenAI's agentic software factory](https://newsletter.pragmaticengineer.com/p/openai-software-factory) (вересень 2026, платний доступ після розділу 3; опис конвеєра є у безкоштовному прев'ю). Повна оцінка з таблицею перевірки фактів: [docs/resource-evaluations/2026-09-15-openai-agentic-software-factory.md](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/docs/resource-evaluations/2026-09-15-openai-agentic-software-factory.md). Читайте подальше як опис працюючої системи однієї компанії журналістові, а не як перевірену референсну архітектуру. Кожна цифра в ньому самозвітна від OpenAI, а стаття ніде не публікує ні частоти дефектів, ні частки невдалих змін, ні кількості відкатів.

### 6.1 Чотири післязлиттєві етапи і хто тримає кожен бар'єр

| Етап | Що робить агент | Де розташований бар'єр | Не опубліковано |
|---|---|---|---|
| Рев'ю за рівнем ризику | Кілька агентів рев'юють паралельно, кожен налаштований на одну сферу (дані, інфраструктура, хмара, безпека). Зміну класифікують за ризиком | Високий ризик: більше рев'ю агентів плюс обов'язкова людина після завершення агентів. Низький ризик: область кодової бази може обрати агента, що автоматично схвалює | Чи мають автоматично схвалені PR низького ризику такий самий профіль дефектів, як рев'ювані людьми |
| Розгортання для кожної зміни | Один агент на зміну, якому доручено супроводжувати її, доки вона повністю не розгорнеться. Для feature flag він знаходить прапор, з'ясовує, що робить зміна, вирішує, які сигнали означають успіх чи невдачу, і будує власний дашборд | Людина схвалює зміну для продакшену, перш ніж агент її візьме | Що стається з дашбордами згодом і хто узгоджує їх зі спільним стеком спостережуваності |
| Perf Factory | Агенти просіюють сповіщення й дашборди, дедуплікують сигнали, виділяють реальні регресії затримки, шукають їхню першопричину та пропонують виправлення, що повертаються в конвеєр на етапі кодування | Запропоноване виправлення знову проходить звичайний шлях рев'ю й розгортання | Частка хибнопозитивних у визначенні регресій |
| Sevbot (інциденти) | Збирає контекст про виявлений інцидент, визначає можливі пом'якшення, відповідає на запитання інженерів у каналі Slack | Агент ніколи не виконує пом'якшення. Інженер каже йому, яке застосувати | Чи є щось, що замикає цикл від інциденту до постійного виправлення |

Заявлена довгострокова мета — автономний SRE на кожну зміну та автономне пом'якшення рутинних збоїв, щоб нікого не будили поза робочим часом. Стаття прямо каже, що жодного з них сьогодні немає і що чергування on-call досі існує.

### 6.2 Три речі, які варто взяти, і чого коштує кожна

**Класифікація ризику як маршрутизація рев'ю, а не як мітка.** Цікаво не те, що зміни отримують оцінку ризику, а те, що оцінка обирає шлях: більше рев'юерів, обов'язкова людина або ніхто. Це те саме питання 1 із розділу 4, застосоване на рівні маршрутизації, а не бар'єра, і це єдиний механізм в описі, що робить людину-рев'юера дефіцитним ресурсом, який витрачається свідомо, а не вузьким місцем, що застосовується рівномірно. Ціна в тому, що ваш класифікатор ризику стає засобом безпеки. Помилково класифікуйте зміну як низькоризикову в області, що погодилася на автоматичне схвалення, і вона потрапить у продакшен, не прочитана жодною людиною.

**Спостережуваність на кожну зміну замість спостережуваності на кожен сервіс.** Повідомлений зсув — від інженерів, що будують дашборди на сервіс, до агентів, що будують їх на розгорнуту зміну, з прив'язкою до сигналів, які ця конкретна зміна має зрушити. Це той самий інстинкт, що й ефемерний стек спостережуваності на worktree у ранішому [описі harness engineering від OpenAI](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/docs/resource-evaluations/2026-02-11-openai-harness-engineering.md), винесений у продакшен. Ціна — розростання, і опис її не розглядає. Дашборди на кожну зміну та дашборди сервісів сталого стану відповідають на різні запитання й не замінюють один одного, тож якщо ніщо не прибирає першу категорію і не переносить її висновки в другу, організація не зможе відповісти, який дашборд відкрити під час інциденту. Запитайте політику зберігання, перш ніж копіювати патерн.

**Агент інцидентів, що пропонує і ніколи не виконує.** Обмеження Sevbot — це помітний вибір дизайну, а не його можливості. Він тримає контекст, готує пом'якшення і відповідає на запитання в каналі, а вирішує людина. Це розподіл creator-verifier із [agent-harness.md §8](../core/agent-harness.uk.md#8-creator-verifier-pattern), застосований у найгірший момент для помилки, і саме обмеження робить патерн придатним для впровадження під час збою, а не під час демо.

### 6.3 Цикл, який ніхто не замикає

В описі є рівно один автоматизований цикл зворотного зв'язку в розробку: Perf Factory, що бере регресію затримки, знайдену в продакшені, і пропонує виправлення, яке повертається на етапі кодування. Цей цикл реальний і є архітектурним доказом, що конвеєр уміє повертати продакшен у код.

Нічого подібного немає для інцидентів. Sevbot пом'якшує; він не усуває, і жоден описаний етап не бере інцидент і не створює довготривале виправлення, що запобігає повторенню. Стандартна післяінцидентна дисципліна, де кожен інцидент винен першопричину та запланову зміну, у цьому конвеєрі не має ні агента, ні названого власника.

Не поспішайте з висновком, що це недогляд. Післяінцидентний аналіз — це робота з найвищим судженням у всій операційній моделі: саме там одночасно сходяться причинне міркування, організаційний контекст і рішення про те, що не виправляти. Автоматизований цикл, що бере збій і пропонує постійну архітектурну зміну, — єдине місце, де хибна відповідь накопичується найшвидше. Те, що OpenAI автоматизувала цикл затримки, а не цикл інцидентів, принаймні так само виправдане як свідома межа, як і викривальне як прогалина. Справедливо сказати вужче, але все ж корисно: це єдиний етап, де фабрика повертає роботу людям лише з контекстом, і кожен, хто копіює конвеєр, успадковує цю діру свідомо чи ні.

### 6.4 Що це змінює щодо рівнів у розділі 1

Нічого — на рівнях, які посідає більшість читачів. Рівні 1–4 залишаються правильною відповіддю для малої команди, і жоден із чотирьох етапів вище недосяжний із нативного налаштування Claude Code без самостійної побудови інтеграції розгортання та спостережуваності.

Що опис справді змінює — це форма стелі. Обмеження в OpenAI — не можливості моделі й не оркестрація; воно в тому, що кожна система доставки нижче за генерацію коду поглинає навантаження, на яке її не будували, про що повідомлено як про приблизно 10x на деяких системах приблизно за шість місяців. Це та сама стіна, на яку Anthropic натрапила у власному CI, задокументована в розділі 5, з абсолютно окремої кодової бази й набору інструментів. Дві конкурентні передові лабораторії, що незалежно повідомляють, що саме їхня інфраструктура верифікації й доставки, а не агенти, стала обмежувальним чинником, — найбільш переносиме в обох описах.

Читайте це поряд із тим, чого не публікує жоден опис. Обидва докладно вимірюють пропускну здатність, і жоден не публікує частоти дефектів, частоти пропусків чи частки невдалих змін. Пастка розділу 5 — не гіпотеза, що стосується менших команд із меншою ретельністю. Вона видна у звітності двох організацій, найкраще розташованих, щоб виміряти шлях виходу з неї.

## 7. До злиття: два цикли, які Claude Code уже постачає

Розділ 6 охоплює етапи, яких нативне налаштування досягти не може. Той самий опис OpenAI також розповідає про два цикли перед злиттям, що мають нативний аналог у Claude Code, що робить їх найдешевшою частиною конвеєра для копіювання. Джерело та його межі ті самі, що й у розділі 6: система однієї компанії, описана журналістові, без показників якості.

### 7.1 Одна довготривала мета замість багатьох сесій під наглядом

OpenAI відносить частину свого внутрішнього сплеску впровадження на рахунок налаштування `/goal` у Codex, де агент продовжує працювати, доки не буде досягнуто заявленого результату. Ендрю Амбросіно (Andrew Ambrosino), керівник десктопного Codex, описує вплив на те, як люди працюють: «Здається, те, що Codex добре справляється з довшими завданнями, змушує людей робити менше речей паралельно. Це тому, що довготривалий агент часто породжує інших агентів для інших завдань, зменшуючи площу поверхні, якою ви, як людина, маєте керувати». Це спостереження однієї команди, а не вимір. Стрибок внутрішнього використання з квітня на травень (з 60% до 90%), який він частково пояснює кращою обробкою довготривалих завдань, самозвітний і без методу підрахунку.

Це твердження все ж варто сприймати серйозно, бо воно суперечить поширеній пораді: відкривати більше паралельних сесій, щоб працювати швидше. Кожна паралельна сесія — це контекст, який людина має тримати, перевіряти й зливати. Єдина мета, що делегує субагентам, переносить це розгалуження всередину harness, де головний агент володіє синтезом. Рівень 2 і рівень 3 у розділі 1 уже описують таку форму; мета — це те, що тримає її в русі без prompt на кожен крок.

Claude Code постачає той самий примітив. [Офіційна документація `/goal`](https://code.claude.com/docs/en/goal) описує механіку:

- `/goal <condition>` одразу починає хід і продовжує запускати нові. Після кожного ходу невелика швидка модель (за замовчуванням Haiku на Claude API) повертає один із трьох вердиктів: ще не досягнуто, досягнуто або неможливо. Мета очищується при «досягнуто», при «неможливо» або при помилці, яку потрібно виправити.
- Перевірку завершення виконує окрема модель, а не та, що виконує роботу. Це розподіл creator-verifier із [agent-harness.md §8](../core/agent-harness.uk.md#8-creator-verifier-pattern), застосований на рівні циклу.
- Мета не змінює режим дозволів. Запуски без нагляду потребують auto mode; у Manual mode Claude все одно запитує перед викликами інструментів, які ваші налаштування не дозволяють.
- Вона працює неінтерактивно: `claude -p "/goal <condition>"` виконує цикл до завершення за один виклик.
- Якщо Claude кілька ходів поспіль відповідає оцінювачеві, не використовуючи жодного інструмента, цикл зупиняється й повертає керування, а мета лишається встановленою.

Обмеження, під яке слід проєктувати: оцінювач судить про умову за тим, що з'являється в розмові. Він сам не виконує команд і не читає файлів. Умову на кшталт «функція працює» може задовольнити впевнений підсумок. Умова на кшталт «`npm test` завершується з 0, а `git status` не показує змін поза `src/auth`» змушує вивести доказ у транскрипт, де його може прочитати оцінювач. Це питання 1 із розділу 4, детермінований бар'єр чи самооцінка LLM, застосоване до однієї сесії. Щоб обмежити вартість, порада самої документації — додати застереження про ходи чи час до самої умови, наприклад `or stop after 20 turns`.

### 7.2 Агент, що няньчить pull request, доки той не позеленіє

У конвеєрі OpenAI агент-кодер відкриває pull request і потім залишається на ньому: виправляє збої CI, відповідає на коментарі рев'ю й оновлює PR, доки перевірки не пройдуть. Людина не та, що передає агентові червоні збірки.

Нативний аналог — [Auto-fix pull requests](https://code.claude.com/docs/en/claude-code-on-the-web#auto-fix-pull-requests), що запускається з терміналу командою `/autofix-pr` у гілці PR. За офіційною документацією, вона породжує хмарну сесію, що підписується на активність GitHub для цього PR. На збій перевірки чи новий коментар рев'ю Claude надсилає виправлення, коли впевнений, питає вас, коли коментар неоднозначний чи архітектурно значущий, і журналює дублікати без дій.

Чотири обмеження вирішують, чи підходить це вашому репозиторію:

| Обмеження | Наслідок |
|---|---|
| Потребує Claude GitHub App у репозиторії | Недоступно на forge, до якого застосунок не дістається |
| GitHub не надсилає webhook, коли базова гілка зсувається і створює конфлікт | Конфлікти досі потребують людського prompt («rebase») |
| Claude відповідає в тредах рев'ю під вашим акаунтом GitHub, позначаючись як Claude Code | Рев'юери бачать ваше ім'я на відповідях, написаних агентом |
| Ці відповіді можуть запускати автоматизацію, керовану коментарями (Atlantis, Terraform Cloud, workflows `issue_comment`) | Документація радить вимикати auto-fix, де коментар у PR може розгорнути інфраструктуру |

Останній рядок найважливіший для фабрики. Агент, що може публікувати коментарі в репозиторії, де коментарі є командами, має права на розгортання через чорний хід. Перевірте workflows репозиторію, що запускаються коментарями, перш ніж вмикати це, так само як питання розділу 4 перевіряють платформу перед впровадженням.

Чого нативний цикл не включає — це частини етапу рев'ю OpenAI, що вирішує, скільки рев'ю отримує зміна. `/autofix-pr` реагує на все, що створюють рев'юери та CI. Класифікація ризику, що спрямовує зміну до більшої кількості агентів, обов'язкової людини чи автоматичного схвалення (розділ 6.1), лишається тим, що ви будуєте самі. Цикл прибирає роботу з передавання; він не замінює рішення про те, кому треба дивитися.
