# Multi-Provider code review: недубльоване автоматизоване рев'ю PR

> **Межа доказів**: це патерн дизайну, заснований на конфігурації проєкту, а не перевірений наскрізний контракт розгортання. Перевіряйте в своєму репозиторії фактичне виконання провайдерів, дозволи, обробку виводу та політику гілок. Пороги серйозності, доменні імена та відсічки за кількістю файлів — ілюстративні відправні точки; консультативний (advisory) робочий процес і симуляція контролю мають окремі обмеження, описані нижче.

Рев'юери, що перекриваються, можуть дублювати знахідки й збільшувати роботу з тріажу. Порівняйте одного рев'юера з додатковою роллю на зарезервованих завданнях, включно з хибнопозитивними результатами та шкідливими виправленнями. Після цього порівняння запишіть кожну збережену роль та її повноваження.

Ця сторінка розділяє семантичне рев'ю, виконувані перевірки та міжфайлове розслідування. Claude Code Action, CodeRabbit і Greptile можуть робити внесок у ці ролі, але назва провайдера не встановлює детермінованої поведінки чи права блокувати злиття. Призначайте обов'язкові перевірки через політику репозиторію. [GitHub Actions Workflows](./github-actions.uk.md) і [шаблони](../../examples/github-actions/) дають приклади реалізації з обмеженнями, описаними нижче. [Loop & Graph Engineering](../core/loop-graph-engineering.uk.md#5-розподіляйте-судження-явно) пояснює повноваження приймання та незалежність рев'юерів.

## Коли ще один рев'юер заслуговує на місце

Інший інструмент може виявити сліпу зону, але додаткове покриття слід вимірювати. Пошук по репозиторію може допомогти дослідити викликачів поза diff. Виконувані lint-правила та тести дають повторювані перевірки заданих властивостей; вони все одно можуть пропускати випадки поза своєю моделлю, обсягом чи реалізацією. ШІ-рев'юер, що видає PASS/FAIL, не стає тим самим детермінованим. Зокрема, не припускайте, що кастомні перевірки CodeRabbit мають такі самі гарантії, як компілятор чи протестоване lint-правило.

Нашарування інструментів, що перекриваються, може збільшити кількість дубльованих знахідок без достатньої кількості додаткових підтверджених дефектів, щоб виправдати вартість. Перш ніж розширювати парк, виміряйте унікальні підтверджені знахідки, хибні тривоги та зусилля на арбітраж.

## Розподіл ролей

| Провайдер | Робота | Чи може блокувати злиття? | Чому ця робота пасує цьому інструменту |
|----------|-----|---------------------|------------------------------|
| **Claude Code Action** | Глибоке семантичне рев'ю: логічні помилки, безпека (IDOR, автентифікація, ін'єкції), порушення архітектури, цілісність даних | Лише через верифіковане виконання та явну політику приймання репозиторію | Може перевіряти контекст репозиторію, наданий робочим процесом |
| **CodeRabbit** (або еквівалент) | Підсумки PR і налаштовані перевірки рев'ю | Лише через явну політику обов'язкових перевірок із верифікованим виконанням і обробкою виводу | Оцініть фактичний механізм і поведінку при помилках кожної перевірки; бінарний вивід — не гарантія надійності |
| **Виконувані lint-правила та тести** | Задані обмеження синтаксису, типів і поведінки | Так, де це вимагає політика репозиторію | Повторювані в межах своїх входів і середовища; покриття та якість тестів обмежують виявлення |
| **Greptile** (або еквівалент) | Міжфайлові інваріанти: ланцюги залежностей, «чи кожен викликач X дотримується правила Y», патерни, що повторюються у віддалених файлах | Лише через верифіковане виконання та явну політику приймання репозиторію | Може досліджувати проіндексованих викликачів поза diff; перевіряйте покриття й свіжість індексу |
| **GitLab Code Review Flow** | Агентне рев'ю merge request усередині GitLab: попереднє сканування збирає пов'язані файли, потім рев'ю публікує рядкові коментарі; наступні рев'ю повторно використовують власні попередні треди | Його схвалення не зараховується до обов'язкових схвалень. З бета-налаштуванням «GitLab Duo can approve and request changes» (GitLab 19.5, за feature flag, типово вимкненим) його запит змін блокує merge request, як і запит користувача | Нативний для merge request; запускається як завдання CI/CD на раннері з тегом `gitlab--duo`; читає `mr-review-instructions.yaml`, але не `AGENTS.md` чи `SKILL.md`; етап рев'ю не може отримати контекст поза попереднім скануванням, обмеженим приблизно 1 MiB |

Факти про GitLab Code Review Flow походять із [документації GitLab](https://docs.gitlab.com/user/duo_agent_platform/flows/foundational_flows/code_review/), прочитаної 8 листопада 2026 року: загальнодоступний у GitLab 18.8, доступний на безкоштовному рівні на GitLab.com із GitLab Credits у 18.10 та пропонується на GitLab.com, Self-Managed і Dedicated. Цей посібник його не запускав.

Підлаштовуйте стовпець «робота» під ваш стек, а не принцип. Якщо ваш інструмент детермінованих перевірок — щось інше (власне lint-правило, окреме завдання CI, Semgrep), роль усе одно належить цьому стовпцю, а не дублюється в промпті LLM-рев'юера.

### Відокремлюйте виявлення від доказів верифікації

У [Using LLMs to Secure Source Code, на 12:19](https://www.youtube.com/watch?v=imFedndyXYQ&t=739s) Юджин Ян (Eugene Yan) описує верифікатор, який не отримує трасу міркувань агента-виявлення й намагається спростувати кандидатів у вразливості. ## Правило недублювання

Запишіть межу в кожен конфігураційний файл, а не лише на вікі-сторінку, яку ніхто не читає під час налаштування рев'ю. Конкретно:

- `.github/prompts/code-review.md` (Claude): однорядковий заголовок, що зазначає: він постачає докази семантичного рев'ю до політики приймання, а не стильові дрібниці, які вже ловить лінтер.
- `.coderabbit.yaml` (або еквівалент): коментар угорі, що вказує: він не повинен дублювати LLM-рев'юера чи інструмент RAG. Див. [шаблон у цьому репозиторії](../../examples/github-actions/.coderabbit.yaml).
- `.greptile/rules.md` (або еквівалент): та сама примітка про недублювання, з явним зазначенням, які інваріанти живуть тут, бо вимагають міжфайлового пошуку, а не тому, що їх було найлегше записати. Див. [шаблон](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/examples/github-actions/.greptile/rules.md).

Призначте власника кожного правила й відрізняйте навмисний захист у глибину від дубльованих коментарів. SQL-ін'єкція може потребувати і виконуваного аналізу, і контекстного рев'ю. Обмеження за тенантом може потребувати пошуку по репозиторію та тестів у викликачах. Дедуплікуйте повідомлену знахідку після незалежних перевірок; не прибирайте корисний контроль лише тому, що інший інструмент розглядає той самий ризик.

## Блокування злиття: гейт CI

Автоматичний коментар не встановлює права на злиття. Обов'язкова перевірка або обов'язкове схвальне рев'ю мають бути частиною ефективної політики репозиторію. Розбір кількості серйозності — один із входів перевірки; це не достатній контракт приймання.

**Межа шаблону:** [`claude-code-review.yml`](../../examples/github-actions/claude-code-review.yml) — консультативний. Його колишній гейт-парсер серйозності вибирав непов'язане останнє рев'ю, інтерпретував відсутній заголовок як нуль і пропускався після збою виробника; цей гейт видалено. Не використовуйте успішне консультативне завдання як вердикт приймання. Локальна вправа нижче — окрема симуляція контролера, а не заміна адаптера квитанцій GitHub. Фактичне виконання провайдера в робочому процесі та налаштована доступність інструментів усе одно потребують кваліфікації в цільовому репозиторії.

Гейт приймання потребує:

1. Версіонованої схеми виводу, прив'язаної до очікуваного провайдера, репозиторію, запуску, поточної ревізії та охопленого обсягу. Відсутні, некоректні, застарілі, часткові чи невдалі докази не повинні ставати чистим результатом. Перевіряйте ці випадки явно.
2. Калібрування серйозності на основі наслідків, включно з доступом до даних і зовнішніми ефектами. Внутрішній адмін-інструмент усе одно може бути критичним. Записуйте власника, дозволені відкладення та вимоги до відновлення.
3. Ефективних обов'язкових перевірок, очікуваних видавців перевірок, схвальних ідентичностей і правил обходу. Верифікуйте політику, а не лише файл робочого процесу. Див. [захищені гілки GitHub](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches).

Записуйте базу, merge base, протестовану інтеграційну ревізію та точні ревізії PR, що поєднуються. Нова база чи merge group робить попередній результат інтеграції недійсним. [Черги злиття](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/configuring-pull-request-merges/managing-a-merge-queue) потребують перевірок, що виконуються на групі, а не лише на окремому PR. Дві низькоризикові зміни можуть взаємодіяти з високим впливом.

Глибоке людське рев'ю може бути вибірковим за документованою політикою, з чутливими шляхами, закріпленими за власником. Перш ніж покладатися на відновлюваність, відпрацюйте виявлення, стримування та відновлення після неправильно прийнятої зміни. Поновлення процесу рев'ю не відновлює дані застосунку й не компенсує зовнішніх ефектів.

### Відпрацюйте споживача та шлях відновлення

Запустіть [локальну вправу з контролем](../../examples/workflows/review-control-demo.py) з кореня репозиторію командою `python3 examples/workflows/review-control-demo.py`. Вона перевіряє дозволений результат, явну відмову, `not approved`, відсутні чи застарілі докази, невідомого виробника, змінену ревізію, довговічний бюджет і втрату відповіді. Сервіс ефектів симульований; це не інтеграційний тест із живим GitHub.

Розглядайте ємність верифікації як умову допуску, використовуючи [аркуш](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/examples/workflows/review-admission.md). Відкладене завдання потребує відповідального власника та шляху назад у рев'ю. Досьє рішення тримає видимими поточну ревізію, докази, розбіжності та невирішені питання.

## Масштабування на великі PR: батчинг

Один прохід рев'ю по PR на 150 файлів або перевищує тайм-аут, або розмазує увагу моделі так тонко, що знахідки стають поверховими. [Шаблон батчованого робочого процесу](../../examples/github-actions/claude-code-review-batched.yml) у цьому репозиторії розв'язує це: завдання `check-size` рахує змінені файли, а понад порогом (75 у наведеному прикладі, підлаштуйте під розподіл розмірів ваших PR) матричне завдання ділить diff за доменом (міграції, бекенд-сервіси, маршрути API, фронтенд, тести) і запускає кожен зріз як незалежне паралельне рев'ю. Фінальне завдання синтезу зводить знахідки за доменами в одну дедубльовану таблицю серйозності.

Це зберігає той самий файл промпту (`code-review.md`) як джерело істини для критеріїв рев'ю, змінюється лише обсяг у кожному матричному завданні — через `append_system_prompt`, що обмежує кожен батч glob-ами файлів свого домену. Немає дубльованої логіки рев'ю для підтримки між шляхами малих і великих PR.

## Скорочення зайвих рев'ю: Delta-Review

Повторне рев'ю всього diff на кожен пуш у довгоживучий PR спалює токени на повторну перевірку коду, який Claude уже схвалив на попередньому пуші. Крок delta-review порівнює SHA, вбудований у попереднє рев'ю (опублікуйте його як HTML-коментар `<!-- reviewed-sha: abc123 -->` у тілі рев'ю), із SHA поточного пушу й обмежує нове рев'ю лише файлами, зміненими відтоді.

Цей репозиторій не постачає готового шаблону delta-review, бо правильна реалізація залежить від того, як конкретний проєкт уже відстежує стан рев'ю (коментар-маркер, мітка, окремий запуск перевірки з ключем за SHA коміту). Механіка однакова незалежно від цього: прочитати останній маркер, виконати `git diff <last-sha>..HEAD --name-only` і передати цей список файлів у промпт так само, як батчований робочий процес обмежує матричне завдання за доменом.

Маркер — лише локатор, а не автентифікований доказ. Перевіряйте його видавця та запуск і робіть недійсним уражене рев'ю, коли відрізняються вимоги, залежності, база, конфігурація провайдера чи поєднані зміни. Включайте зачеплених викликачів і споживачів, навіть якщо їхні файли не змінювалися. Незмінний список імен файлів не встановлює незмінного ризику.

## Крос-інструментальна дедуплікація

Зберігайте незалежні спостереження, перш ніж об'єднувати знахідки. Опціональне завдання синтезу читає попередні рев'ю після їх створення; це відрізняється від обумовлення рев'юера іншим рев'ю до його початкового вердикту. Якщо застосовується останнє, декларуйте це як експериментальний вплив (treatment) і не називайте отримані спостереження незалежними.

Зберігайте розбіжності та докази за унікальними знахідками. Враховуйте виправлення, що вводять регресії, разом із хибнопозитивними, врятованими дефектами та зусиллями на тріаж. Інший провайдер заслуговує на місце лише тоді, коли порівняння з базовою лінією підтримує його граничну цінність у межах задекларованого бюджету.

## Відоме тертя: розходження правил між конфігураціями

Немає єдиного генератора, що проштовхує одне джерело істини в усі три конфігурації провайдерів. Канонічні конвенції живуть у будь-яких внутрішніх документах, які проєкт уже підтримує, а кожна конфігурація провайдера — це ручна, стисла транскрипція відповідної підмножини, навмисно коротка, бо рев'ю-інструмент не повинен завантажувати й розбирати всю внутрішню вікі на кожному PR.

Практична ціна: список виключень файлів (lock-файли, згенерований код, міграції) зрештою дублюється в `paths-ignore` робочого процесу, `path_filters` CodeRabbit та `ignorePatterns` Greptile. Ніщо не ловить розходження автоматично, коли один список оновлюється, а два інші — ні. Періодично аудитуйте три конфігурації одна проти одної та проти канонічних документів; сприймайте невідповідність як сигнал, що потребує підтримки саме налаштування рев'ю, а не лише код, який воно рев'юює.

## Інтерактивні помічники проти CI

Шаблони робочих процесів націлені на CI; локальна симуляція та аркуш допуску слугують різним цілям. Окремий, доповнювальний шар — жменька локальних skills Claude Code, які розробник запускає вручну під час активної роботи: швидка перевірка статусу CI/рев'ю/прев'ю поточного PR, збір усього, що опубліковано з моменту останнього пушу всіма ботами та людьми-рев'юерами, і періодичний ретроспективний аудит за останні N PR, щоб помітити знахідки, які боти постійно підсвічують, а жоден файл правил їх ще не покриває. Це інструменти зручності розробника, а не частина пайплайна CI, і вартує будувати їх як проєктні локальні skills, коли архітектура на боці CI вище стабілізується, а не раніше.

### Локальні поверхні рев'ю для змін, написаних агентом

Другий локальний шар допомагає рев'юеру прочитати те, що написав агент, до або під час рев'ю. Шість інструментів нижче прочитано з їхнього вихідного коду чи README 8 листопада 2026 року, не запускалися; SHA та обмеження див. в [оцінці](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/docs/resource-evaluations/agent-review-surfaces.md).

| Інструмент | Звідки береться пояснення | Прив'язка | Зворотний зв'язок агенту | Forge |
|---|---|---|---|---|
| [diffo](https://github.com/DiffoHQ/diffo) | Агент публікує впорядковані шари та коментарі через свій CLI | Ідентифікатор hunk з хешу вмісту, потім рядок, файл, вся зміна | `diffo poll` повертає треди типів Change або Question | GitHub через `gh` |
| [glassbox](https://github.com/brianwestphal/glassbox) | Агент записує нотатки (обґрунтування, доказ, ризик) через `glassbox note add`, що зберігаються як SARIF у репозиторії | Рядок, повторно прив'язаний зіставленням збереженого фрагмента | Файл рев'ю, який читає агент | У його вихідному коді не знайдено |
| [hunk](https://github.com/modem-dev/hunk) | Агент коментує в живій термінальній сесії або JSON-sidecar | Старі та нові діапазони рядків, зіставлені з поточним hunk | Агент читає нотатки людини й відповідає | Читає diff GitHub |
| [drift](https://github.com/tothalex/drift) | Немає: показує лише обговорення forge | `position` GitLab з `diff_refs`; застарілі треди зберігаються | Надсилає вибраний діапазон та інструкцію до панелі агента | GitHub (`gh`) і GitLab (`glab`) |
| [ai-pr-review](https://github.com/houshuang/ai-pr-review) | Модель пише огляд постфактум за diff | Діапазони та цитати `path:line`, звірені з diff і деревом | Немає | GitHub через `gh` |
| [guidedreview](https://github.com/nshntarora/guidedreview) | LLM групує hunks в одиниці рев'ю з коротким коментарем | Коментарі на реальних рядках diff | Копіює промпт, побудований із нотаток | GitHub (розширення); локальний CLI |

Що показує таблиця, без вимірювання за нею:

- Жоден із п'яти, прочитаних у коді, не розміщує пояснення агента в стовпці поряд із diff; glassbox і hunk вставляють його під прив'язаним рядком, а README guidedreview про це не каже. Кастомний вигляд pull request із diff, коментарем агента та стовпцем рев'юера, описаний у [Resisting Cognitive Surrender](../roles/learning-with-ai.uk.md#ревю-машинного-виводу-є-третім-режимом), — особиста збірка.
- Лише diffo типізує зворотний зв'язок рев'юера, тож агент може відрізнити запитання від запитаної зміни.
- На прочитаних версіях лише drift, як виявлено, читав і писав обговорення merge request GitLab. Стороннє розширення hunk для merge request GitLab з'явилося пізніше й не читалося.

> **Безпека**: на прочитаній версії ai-pr-review верифікував свої поради рев'ю, запускаючи Codex у тимчасовому worktree із правом запису та мережею на коді pull request без запиту схвалення, тож недовірений код міг виконуватися на машині рев'юера. Не запускайте його на недовірених pull request. diffo типово надсилає анонімну телеметрію.

[Три місця, де пояснюється зміна агента](../diagrams/06-development-workflows.uk.md#три-місця-де-пояснюється-зміна-агента) малює, як ці поверхні розташовані між агентом і ботами CI.

## Чекліст налаштування

1. Скопіюйте `claude-code-review.yml` + `prompts/code-review.md` (базове налаштування див. у [GitHub Actions Workflows](./github-actions.uk.md))
2. Заповніть контекст стека в промпті та таблицю калібрування серйозності, узгоджену з реальним профілем ризику вашого продукту, а не загальним списком OWASP
3. Реалізуйте й кваліфікуйте окремий адаптер квитанцій та перевірку приймання; відпрацюйте застарілі/відсутні/некоректні/невдалі результати, перш ніж налаштовувати політику обов'язкових перевірок
4. Якщо ваші PR регулярно перевищують ~50–75 файлів, додайте `claude-code-review-batched.yml` і налаштуйте доменні glob-и
5. Призначте повторювані інваріанти виконуваним lint-правилам чи тестам; оцінюйте перевірки ШІ-рев'ю окремо та документуйте, які результати можуть блокувати
6. Порівняйте міжфайлового рев'юера з базовою лінією на зарезервованих випадках; додавайте його, лише якщо його підтверджений внесок виправдовує помилки, тріаж і вартість
7. Заплануйте періодичний прохід, що порівнює всі конфігурації провайдерів між собою на предмет розходження правил
