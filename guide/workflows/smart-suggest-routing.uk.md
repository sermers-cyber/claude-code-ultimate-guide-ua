# Smart-Suggest routing: підказки skill через Regex + BM25

Hooks `UserPromptSubmit` можуть додавати дорадчий контекст до того, як модель обробить prompt. Regex підходить для фіксованих правил примусового виконання. Okapi BM25 підходить для варіацій природної мови, підкріплених перевіреним корпусом skill.

Готова до запуску реалізація в `examples/hooks/bm25-routing/` підтримує Claude Code і Codex. Рекомендоване розгортання для Codex — один глобальний hook, що визначає і проєктні, і користувацькі skill із робочої директорії кожного prompt.

## Оберіть правильний рушій

| Ситуація | Regex | BM25 |
|---|---:|---:|
| Фіксована команда або фраза політики | Сильний | Слабкий |
| Примусове виконання перед дією | Сильний | Недоречний |
| Двомовні варіації природної мови | Крихкий | Сильний із корпусом |
| Новий skill із менш ніж вісьмома позитивами | Можливе ручне правило | Лише нативне зіставлення |
| Широкий намір із контрастними прикладами | Великий набір правил | Сильний після оцінювання |

Regex і BM25 можна підключити до `UserPromptSubmit`, але вони розв'язують різні задачі. Regex-нагадування може вимагати перевірки changelog. Підказка BM25 може визначити ймовірний skill для рев'ю чи пошуку в репозиторії. Жоден із них не повинен автоматично схвалювати чи автоматично запускати деструктивну дію.

Розібраний приклад показує межу лексичного збігу. `workspace-cleanup` пройшов свій поріг завдяки двом поширеним французьким словам, "en" і "plu" (основа "plus"), жодне з яких токенізатор не вважає стоп-словом. Його найближчий негатив набрав 6,59 проти 6,91, тож вето не спрацювало. Виправлення — ближчий контрастний негатив у корпусі цього skill, а не нижчий глобальний поріг.

У термінах патернів маршрутизатор є детермінованим [Content-Based Router](../core/ai-design-patterns.uk.md#content-based-router), розміщеним перед власним вибором skill моделі.

## Архітектура Codex

Codex поєднує відповідні hooks із глобальної та проєктної конфігурації. Тому встановлення того самого обробника BM25 на обох рівнях може вставляти дубльований контекст. Використовуйте один глобальний обробник на налаштованій робочій станції:

```text
prompt + cwd
    |
    v
~/.codex/hooks/skill-router/bm25-suggest.js
    |
    +-- <cwd>/.agents/skills up to <git-root>/.agents/skills
    +-- ~/.agents/skills
    +-- ~/.codex/skills
    +-- /etc/codex/skills when readable
    +-- SKILL_ROUTER_EXTRA_ROOTS
    +-- external corpus overlays
    |
    v
user-owned cache keyed by repo, relative cwd, and resolved roots
    |
    v
one bounded additionalContext, or silent output
```

Найближчий проєктний skill затіняє skill із кореня проєкту чи глобальний skill з тим самим frontmatter `name`. Це важливо в монорепозиторіях, де вкладений каталог `.agents/skills` може навмисно перевизначати ширше визначення.

Skill без відкаліброваного корпусу позначаються `native-only`. Codex усе одно може вибрати їх за описом, або користувач може викликати їх явно через `$skill-name`.

## Архітектура Claude Code

Той самий runtime можна встановити в режимі проєкту через `SKILL_ROUTER_HOST=claude`. Виявлення та калібрування лишаються тими самими. Змінюється лише синтаксис явної підказки: з `$skill-name` у Codex на `/skill-name` у Claude Code.

Зберігайте проєктні regex-hooks, як-от `smart-suggest.sh`, коли вони кодують окремі правила примусового виконання. Не дублюйте сам обробник BM25 у активних шарах конфігурації Codex.

## Формат корпусу

Суміжний корпус розміщується в `<skill>/evals/scenarios.json`:

```json
{
  "skill": "debug-db",
  "positive": [
    "my Prisma client reports connection refused",
    "connexion à la base de données impossible",
    "the database pool is exhausted"
  ],
  "negative": [
    "optimize this slow SQL query",
    "add an index to the users table",
    "export a database backup"
  ]
}
```

Значення `skill` має збігатися з назвою активного `SKILL.md` і відповідати `^[a-z0-9][a-z0-9:_-]{0,127}$`. Для калібрування потрібно щонайменше вісім позитивних і два негативні prompt. На практиці використовуйте 12 або більше різноманітних позитивів і щонайменше п'ять близьких негативів.

Негативи мають мати спільну лексику з позитивами. Непов'язані негативи роблять завдання штучно легким і задають небезпечний поріг. Runtime також оцінює контрастні негативні приклади й накладає вето на кандидата, якщо його найсильніший негативний збіг не слабший за позитивний.

Використовуйте зовнішній overlay, коли каталог skill має суворий файловий контракт. `SKILL_ROUTER_OVERLAY_ROOTS` вказує на один чи кілька каталогів із JSON-файлами корпусу. Overlay ігнорується, доки його `skill` не вказує на активний skill.

## Виявлення та межі безпеки

Маршрутизатор розбирає лише `name` і `description` з перших 64 KiB кожного `SKILL.md`. Він відхиляє некоректні назви та файли сценаріїв, що вказують на неактивні чи невідповідні skill.

Символічні посилання skill розв'язуються до справжнього шляху. Ціль приймається лише тоді, коли залишається всередині виявленого або явно авторизованого кореня skill. Видана підказка містить саме цей розв'язаний шлях до `SKILL.md`, що дає моделі перевірювану ціль.

Пріоритет детермінований:

1. найближчий предок `cwd` з `.agents/skills`;
2. `.agents/skills` у корені репозиторію;
3. `~/.agents/skills`;
4. `~/.codex/skills`;
5. `/etc/codex/skills`;
6. явні додаткові корені.

## Індекс і калібрування

Оцінювач використовує Okapi BM25 з `K1 = 1.2` і `B = 0.3`. Він не реалізує BM25+, бо дельта-члена немає. Форма IDF:

```text
IDF(t) = log(1 + (N - n + 0.5) / (n + 0.5))
```

Позитивні та контрастні негативні документи ділять один простір термінів IDF. Оцінки позитивів і негативів кожного skill — це максимум за відповідними прикладами цього skill. Максимум запобігає надаванню переваги skill лише тому, що його корпус має більше prompt.

Калібрування за схемою leave-one-out обирає поріг, що максимізує F-beta за beta у квадраті, рівного чотирьом. Статус використовує звичайний F1:

| Статус | Значення | Поведінка runtime |
|---|---|---|
| `ok` | F1 калібрування щонайменше 0,60 і перехресне оцінювання skill пройдено | Придатний для BM25 |
| `conflict` | Поріг існує, але F1 нижче 0,60 | Ніколи не пропонується |
| `excluded` | Менше восьми позитивів або двох негативів | Ніколи не пропонується |
| `native-only` | Активний skill не має прийнятого корпусу | Лише нативне зіставлення |

Початковий маршрутизатор відфільтровував лише `excluded`, через що skill зі статусом `conflict` могли спрацьовувати. Поточний runtime вимагає саме `status: ok`, скінченний поріг, придатність за перехресним оцінюванням skill, активний розв'язаний skill і відсутність сильнішого контрастного негативного збігу. Об'єднана придатна множина має досягти глобального F1 0,70. Проєктні корпуси нижчої якості лишаються `native-only`; overlay, що пройшов незалежний holdout, лишається захищеним, поки проєктну множину скорочують.

## Поведінка кешу

Кожна розв'язана область отримує окремий ключ кешу на основі кореня репозиторію, відносного `cwd`, розв'язаних коренів skill і версії алгоритму. Це не дає двом вкладеним робочим просторам монорепозиторію ділити несумісний індекс.

Відбиток збірки містить нормалізовані шляхи, розмір, час зміни, хеш вмісту SHA-256 і версію алгоритму для кожного активного `SKILL.md` і корпусу. Гарячий шлях prompt перевіряє stat-відбиток за відомими шляхами джерел і спостереження, що виявляє звичайні додавання, редагування та видалення без повторного читання сотень файлів. Кожні 60 секунд відокремлена глибока перевірка перераховує хеші вмісту. Це також ловить незвичну правку незмінного розміру, чий час зміни відновили вручну.

Один збирач тримає блокування `O_EXCL` з TTL 30 секунд. Файли кешу записуються у тимчасові файли й атомарно перейменовуються. Під час перебудови поточний prompt використовує останній чинний індекс. Без чинного індексу hook тихо завершується й планує збірку у фоні.

Під час prompt у поточному репозиторії жоден файл не записується. Глобальний інсталятор задає каталог даних, що належить користувачу. Необов'язкові журнали містять лише метадані маршрутизації, ніколи сирий текст prompt.

## Контракт виводу

Адаптер Codex видає:

```json
{
  "hookSpecificOutput": {
    "hookEventName": "UserPromptSubmit",
    "additionalContext": "Skill routing candidates:\n- $agentic-project-finder (/absolute/path/SKILL.md)\nUse only if the intent matches."
  }
}
```

Адаптер Claude використовує `/agentic-project-finder`. Маршрутизатор видає щонайбільше три кандидати та 500 символів. Він не показує відсоток упевненості, бо `score / sum(top scores)` не є відкаліброваною ймовірністю. Звичайні підказки не мають `systemMessage`.

Звичайне заперечення лишається придатним для маршрутизації. Наприклад, `analyse ce dépôt sans modifier les fichiers` усе одно може обрати skill для рев'ю. Явні відмови, як-от `ne suggère aucune skill`, зупиняють маршрутизацію. Наявна згадка активного `$skill` для Codex або команда `/skill` для Claude також зупиняє маршрутизатор, щоб уникнути зайвої поради.

## Встановлення

Попередній перегляд глобального встановлення для Codex:

```bash
cd examples/hooks/bm25-routing
node install.js --host codex --scope user --dry-run
```

Попередній перегляд перелічує джерело, призначення, контрольну суму та зміни hook без запису. Застосовуйте лише після перегляду:

```bash
node install.js --host codex --scope user --apply
```

Інсталятор зберігає наявні обробники, додає один обробник `UserPromptSubmit` і створює резервну копію з часовою позначкою. Повторне ідентичне встановлення нічого не змінює.

Після встановлення відкрийте `/hooks` у Codex. Некеровані hooks потребують явного перегляду та довіри. Саме копіювання файлу не робить новий обробник активним.

Для автономного проєктного встановлення на машині без глобального обробника:

```bash
node install.js \
  --host codex \
  --scope project \
  --project-root /absolute/path/to/repo \
  --dry-run
```

Згенерований проєктний hook усе одно записує кеші в користувацький каталог. Не активуйте разом проєктний і глобальний обробники BM25 для Codex.

## Оцінювання

Навчальні приклади не повинні слугувати доказом прийняття. Тримайте окремий набір prompt з очікуваними та забороненими skill:

```json
{
  "prompt": "find repositories implementing shared agent memory",
  "expected": ["agentic-project-finder"],
  "forbidden": ["critique-plan"]
}
```

Запустіть суворий оцінювач:

```bash
SKILL_ROUTER_CWD=/absolute/path/to/repo \
node routing/eval.js \
  --acceptance test/acceptance-prompts.json \
  --strict
```

Вбудований шлюз вимагає точності щонайменше 0,80, F1 щонайменше 0,70 та нуля заборонених влучань. Розширюйте покриття по одному перевіреному skill. Не генеруйте виробничі сценарії автоматично з описів.

## Режими збою для тестування

- відсутній, обрізаний чи недійсний кеш тихо повертає порожній результат;
- проєктні та глобальні дублікати назв розв'язуються на проєктний шлях;
- назви skill зі статусами `conflict`, `excluded` та неактивні ніколи не з'являються;
- додавання, редагування чи видалення корпусу інвалідує лише відповідну область;
- дві одночасні перебудови дають одного записувача;
- необов'язкові журнали не містять тексту prompt;
- 30 або більше позитивних, негативних і явних викликів prompt проходять перед розгортанням;
- затримка теплого hook лишається нижче 75 мс на p95 на цільовій машині.

Використовуйте `routing/benchmark.js --iterations 1000 --cwd <repo>` для шлюзу затримки теплого шляху. Він вимірює завантаження кешу, stat-перевірки інвалідації, токенізацію, оцінювання, фільтрацію та побудову виводу в одному процесі, не враховуючи одноразового запуску Node.

Повні тести, що запускаються, використовують вбудований тестовий раннер Node:

```bash
node --test examples/hooks/bm25-routing/test/*.test.js
```
