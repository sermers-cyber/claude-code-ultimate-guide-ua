# Обмін повідомленнями між сесіями

Обмін повідомленнями між сесіями дозволяє одній сесії Claude Code доставити коротке текстове повідомлення іншій, незалежно запущеній сесії Claude Code, без копіювання вручну між терміналами. Усю функцію забезпечують два інструменти: `ListAgents` виявляє, які сесії досяжні, а `SendMessage` доставляє текст одній із них за іменем. Жоден із цих інструментів ви не викликаєте самі; Claude вирішує, коли їх використати, сам або за вашим проханням.

**Офіційна документація**: [code.claude.com/docs/en/cross-session-messaging](https://code.claude.com/docs/en/cross-session-messaging)

> **Див. також**: [Tools Reference](../core/tools-reference.uk.md#міжсесійні-повідомлення-listagents--sendmessage) — запис у таблиці інструментів, [Agent Teams](./agent-teams.uk.md) — споріднений, але відмінний механізм поштових скриньок учасників команди, [Security Hardening: Cross-Session Messaging](../security/security-hardening.uk.md#cross-session-messaging-threat-model) — модель загроз каналу, [Native Sandboxing: Cross-session inbox sockets](../security/sandbox-native.uk.md#inbox-сокети-між-сесіями) — ізоляція процесів Bash і винятки для Unix-сокетів, а також [Agent Harness: Creator-Verifier](../core/agent-harness.uk.md#8-патерн-створювачверифікатор) — контролі доказів і незалежності рецензента.

## 1. Яку проблему це розв'язує і чим не є

Формулювання Anthropic: «коли зміна в одній сесії ламає те, на чому будує інша, Claude може попередити ту сесію, перш ніж ви помітите. Коли одна сесія розв'язує питання, яке блокує іншу, Claude може передати відповідь». Повідомлення визначено вузько: це шматок тексту, який один Claude пише іншому, ніколи не історія розмови й ніколи не файли. Перенесення цілої розмови чи її контексту — це інша функція, [відновлення сесії](../ultimate-guide.uk.md#916-session-teleportation).

Claude Code має окрему функцію для кожного способу запускати чи досягати кількох сесій, і обмін повідомленнями між сесіями є правильним вибором лише в одному з них:

| Ви хочете... | Використайте натомість |
|---|---|
| Продовжити одну розмову в іншому терміналі або поділитися її контекстом із новою сесією | [Відновити сесію](../ultimate-guide.uk.md#916-session-teleportation) |
| Скоординовану команду сесій, яку Claude сам створює й контролює | [Agent Teams](./agent-teams.uk.md) |
| Спостерігати й керувати багатьма сесіями з одного місця | Agent view (фонові сесії) |
| Керувати сесією самостійно з телефону чи іншого пристрою | [Remote Control](../ultimate-guide.uk.md#922-remote-control-mobile-access) |
| Передавати зовнішні події (результати CI, повідомлення чатів) у сесію | [Channels](./monitor-event-delegation.uk.md#плагінні-монітори-та-channels) |
| **Обмінюватися повідомленнями між незалежними сесіями, які ви запускаєте й ведете самі** | **Обмін повідомленнями між сесіями** |

Останній рядок — випадок, який охоплює решта цієї сторінки: сесії без відносин породження між собою, кожна відкрита у власному терміналі, кожна зі своїм вікном контексту, дозволами й робочим каталогом.

## 2. Виявлення: `ListAgents`

Виконайте `/list-agents` (псевдонім `/peers`) у будь-якій сесії, щоб побачити, що доступно Claude. Перший рядок — власне ім'я сесії (те, за яким до неї звертаються інші); рядки нижче перелічують кожного досяжного агента, згруповані за типом:

- **Subagents**: агенти, що працюють усередині поточної сесії.
- **Teammates**: учасники [команди агентів](./agent-teams.uk.md) цієї сесії. До v2.1.239 вони не з'являлися в переліку, хоча `SendMessage` уже міг досягати їх за іменем.
- **Your other local sessions**: сесії Claude Code, що працюють на тій самій машині, зокрема фонові. Сесія з'являється лише після того, як прив'яже сокет inbox (див. §5); бездіяльний робочий процес, який супервізор фонових сесій тримає напоготові, з'являється лише після того, як ви надішлете йому роботу.
- **Your cloud sessions**: ваші сесії Claude Code on the web, що показуються, поки поточна сесія підключена до Remote Control. Мають позначку `cloud`.
- **Your Remote Control sessions on other machines**: показуються за тієї самої умови, з позначкою `Remote Control`. Сесія, у якої розірвалося з'єднання Remote Control, показується як `offline`.

Поточна сесія ніколи не є рядком у власному переліку. Якщо Claude адресує повідомлення власному імені, Claude Code відхиляє його й повідомляє про це Claude, замість поведінки до v2.1.239, коли повідомлялося «no agent named …».

Сесія відгукується на ім'я, задане через `/rename` або `--name`, або на автоматично згенероване. Коли перейменування чи нова сесія збігаються з уже зайнятим іменем, Claude Code залишає ім'я за сесією, що вже його має, а новій призначає варіант. Тож дві сесії можуть цілком легітимно ділити ім'я (старіша версія Claude Code або збіг автогенерованих імен); `/list-agents` показує робочий каталог кожної локальної сесії, щоб ви могли їх розрізнити, а коли кілька живих сесій мають одне ім'я, Claude питає вас, яку саме ви маєте на увазі, перш ніж надсилати.

Claude Code читає списки хмарних сесій і сесій Remote Control від найновіших і зупиняється після обмеженої кількості сторінок. Сесія, що опинилася за цим вікном, не перелічується й недоступна для повідомлення за іменем; Claude Code повідомляє про це, і Claude бачить ту саму примітку, коли намагається.

## 3. Доставка: `SendMessage`

Формулювання повідомлення можна залишити на Claude:

```text
Ask the session running in my other terminal whether the migration finished
```

```text
Explain what we just did to the session working on the payments API
```

Або назвати ціль самостійно через `@`-згадку, той самий механізм, що й для [явного звернення до subagent](../core/tools-reference.uk.md#agent). Введіть `@` і перші літери імені сесії та оберіть її з підказки (потрібна v2.1.232+):

```text
Let @api-worker know the schema migration finished
```

Самотній `@` не показує рядків сесій; введіть ще принаймні одну літеру, щоб з'явилися підказки. Хмарна сесія або сесія Remote Control з'являється в підказці лише після того, як Claude вже перелічив чи надсилав повідомлення вашим сесіям за межами поточної машини.

### Що бачить сесія-одержувач

Починаючи з v2.1.247, повідомлення з'являється в розмові одержувача як приглушений однорядковий попередній перегляд під ім'ям сесії відправника. Натисніть `Ctrl+O`, щоб прочитати повний текст у переглядачі транскрипту; сесія, запущена з `--verbose`, показує його повністю одразу. Попередній перегляд лишається в розмові:

```text
Schema migration finished: the new column is tenant_id, and rebasing on main is safe now.
```

Claude читає повне повідомлення незалежно від того, чи розгорнули ви попередній перегляд. Сесія-одержувач отримує ім'я відправника й, за винятком односторонньої міжмашинної ситуації (§4), адресу для відповіді; вона ніколи не отримує історію розмови чи файли відправника. Після доставки повідомлення враховується у використанні так само, як промпт, який ви ввели.

### Час

Claude-одержувач читає повідомлення між викликами інструментів під час активного ходу, тож запущений інструмент ніколи не переривається. Коли одержувач бездіяльний, Claude Code одразу починає новий хід із цим повідомленням.

### Коли надсилання відхиляється одразу

Claude Code відмовляється надсилати, ще до того, як повідомлення залишить відправника, у чотирьох випадках:

1. Повідомлення перевищує ліміт розміру (§7).
2. Швидкий потік повідомлень до сесії на тій самій машині вже досяг того, що приймає inbox цієї сесії.
3. Ціль відповіді на цій машині не проходить перевірку безпеки: шлях сокета є символічним посиланням або підключена кінцева точка не є очікуваним процесом. Див. [Refusing to send a cross-session message](https://code.claude.com/docs/en/errors#refusing-to-send-a-cross-session-message).
4. Claude адресує повідомлення власному імені сесії-відправника.

## 4. Доставка на тій самій машині та між машинами

Чи торкнеться повідомлення інфраструктури Anthropic, цілком залежить від того, де працює сесія-ціль:

| Де працює інша сесія | Як подорожує повідомлення |
|---|---|
| На цій машині | Через Unix domain socket окремої сесії (macOS/Linux/WSL2) або іменований канал (нативний Windows). Ніколи через сервери Anthropic. |
| На іншій з ваших машин | Через сервери Anthropic, надходить через з'єднання Remote Control тієї машини. |
| У Claude Code on the web | Через сервери Anthropic, прямо до хмарної сесії. |

Доставка на тій самій машині цілком локальна: кожна сесія реєструє себе у файлах на диску, а `ListAgents`/`SendMessage` читають ці файли. Дві сесії можуть досягти одна одної лише тоді, коли бачать ті самі файли реєстрації, тому контейнер і його хост не можуть обмінюватися повідомленнями (окремі файлові системи), і так само не можуть сесія WSL2 та нативна сесія Windows на одному комп'ютері (різні домашні каталоги, різні типи сокетів).

Для початку розмови із сесією на іншій з ваших машин потрібна v2.1.225 або новіша, і ціль уже має бути в переліку. До v2.1.225 сесія могла лише відповісти на повідомлення, що надійшло, але не відкрити розмову.

Поки сесія-відправник підключена до Remote Control, повідомлення на іншу з ваших машин показується там під ім'ям Remote Control відправника, і одержувач може відповісти на це ім'я. Якщо відправник не підключений до Remote Control, коли надсилає за межі поточної машини, повідомлення все одно проходить, але не має адреси для відповіді: Claude-одержувач бачить його, але не може відповісти, і відправнику про це повідомляють.

Щоб вимагати вашого явного схвалення перед тим, як будь-яке повідомлення взагалі покине машину, задайте `isolatePeerMachines: true` (§6).

## 5. Сокет inbox сесії

Актуально, коли очікувана сесія відсутня в переліку, коли hook чи скрипт має надіслати повідомлення в сесію, або коли команда в пісочниці не може досягти сокета.

Claude Code прив'язує сокет inbox для кожної сесії з увімкненим обміном повідомленнями: Unix domain socket на macOS/Linux/WSL2, іменований канал у нативному Windows. Його шлях показано в рядку `Peer address` команди `/status` (з префіксом `uds:`) і експортується до hooks та команд Bash як `CLAUDE_CODE_MESSAGING_SOCKET`. Поруч експортується `CLAUDE_CODE_MESSAGING_TOKEN` для окремої сесії; скрипт, що надсилає в сокет власної сесії, може відправити `{"type":"auth","token":"<token>"}` першим рядком з'єднання. Нативний Windows вимагає цього рядка; macOS/Linux/WSL2 приймають з'єднання з ним або без нього.

Сокет обмежений користувачем операційної системи на macOS/Linux; у Windows кожне з'єднання має автентифікуватися ключем, який може прочитати лише цей користувач. Так чи інакше, сесія, запущена одним користувачем ОС, не може досягти сесії, запущеної іншим, навіть на тій самій машині, навіть в одному сервері tmux.

Сесії `claude -p` прив'язують inbox так само, як інтерактивні. Сесії, запущені в [bare mode](../ultimate-guide.uk.md#headless-mode), не прив'язують сокет і ніколи не з'являються в списку агентів.

`ListAgents` і `SendMessage` виконуються в самому Claude Code, поза пісочницею Bash. Тому звичайна доставка між сесіями не потребує винятку для Unix-сокетів. Виняток важливий лише тоді, коли команда Bash у пісочниці підключається безпосередньо до `CLAUDE_CODE_MESSAGING_SOCKET`. На macOS [`sandbox.network.allowUnixSockets`](../core/settings-reference.uk.md#sandboxnetworkallowunixsockets) може обмежити виняток за шляхом сокета. На Linux і WSL2 allowlist сокетів за шляхом недоступний; [`sandbox.network.allowAllUnixSockets: true`](../core/settings-reference.uk.md#sandboxnetworkallowallunixsockets) знімає фільтр Unix-сокетів для кожного сокета, якого може досягти команда. Надавайте перевагу вбудованому інструменту `SendMessage` і не розширюйте доступ до Unix-сокетів лише для того, щоб увімкнути звичайний обмін повідомленнями між сесіями. [Native Sandboxing: Cross-session inbox sockets](../security/sandbox-native.uk.md#inbox-сокети-між-сесіями) розглядає компроміс для кожної платформи.

## 6. Модель безпеки

Дизайн Anthropic утримує в напрузі три властивості: сесії вільно координуються, але жодна не може керувати іншою, і дозволи ніколи не подорожують разом із повідомленням.

### Чого не може вхідне повідомлення

Коли сесія A надсилає повідомлення сесії B, Claude Code явно повідомляє Claude в B, що текст надійшов від іншої сесії, а не від користувача, і відповідно його обмежує:

- **Воно нічого не може схвалити.** Повідомлення від рівноправної сесії ніколи не вважається вашою згодою; воно не може відповісти на запит дозволу, що очікує, від вашого імені.
- **Воно не може змінити конфігурацію.** Claude-одержувачеві наказано ніколи не змінювати налаштування дозволів, `CLAUDE.md` чи будь-яку іншу конфігурацію лише тому, що про це попросила інша сесія.
- **Команди не виконуються.** Команда, вбудована в текст повідомлення, наприклад `/compact`, надходить як звичайний текст. Claude Code ніколи її не виконує.
- **Запити дозволів усе одно спрацьовують.** Якщо для дії за повідомленням потрібен дозвіл, якого сесія-одержувач не має, користувач бачить той самий запит, що й для будь-якого іншого прохання.

Claude також отримує інструкцію з боку відправника ніколи не просити іншу сесію про дію, яку його власна сесія вже заборонила, заблокувала або заблокувала б за власними правилами дозволів; така робота повертається користувачеві.

### Керування тим, що надходить: `crossSessionInbound`

Кожна сесія вирішує, що робити з вхідними повідомленнями від інших сесій, через налаштування `crossSessionInbound`:

| Значення | Поведінка |
|---|---|
| `accept` | Claude Code доставляє кожне повідомлення Claude. |
| `hold` | Claude Code тримає повідомлення без доставки. Наступний застосовний `accept` їх вивільняє; явний `hold` не створює діалогу схвалення для кожного повідомлення і не спливає через `dialogExpiry`. |
| `refuse` | Claude Code відкидає кожне повідомлення без доставки. |

Редагується через `/config` → **Messages from your other sessions** (v2.1.232+; приховано, коли ключ уже задано в managed settings або через `--settings`). Коли жодне значення не застосовується з жодної області налаштувань, Claude Code вирішує для кожного повідомлення за класом режиму дозволів обох сесій: сесії, що оминають запити дозволів, утворюють один клас, усі інші сесії (зокрема режим планування там, де доступний bypass, а також `auto`/`acceptEdits`/`dontAsk`, які вважаються такими, що запитують) утворюють інший. Одержувач, що запитує, за замовчуванням доставляє й утримує лише повідомлення від відправника, що оминає запити; одержувач, що оминає запити, за замовчуванням утримує й доставляє лише від іншого відправника, що оминає запити.

Таке утримання за замовчуванням відкриває діалог для кожного повідомлення. **Approve** доставляє це повідомлення; **Deny** або закриття відкидає його. Діалоги без відповіді зазвичай спливають через `dialogExpiry` (за замовчуванням 5 хвилин). Така поведінка діалогу належить до типової поведінки режиму дозволів, а не до явного налаштування `crossSessionInbound: "hold"`.

Claude Code утримує щонайбільше 100 повідомлень, окремо від черги доставки, відкидаючи найстаріші понад цей ліміт.

### Додаткове посилення обмежень

`isolatePeerMachines: true` вимагає вашого явного схвалення перед будь-яким `SendMessage`, що досягає сесії за межами поточної машини, навіть у режимі `bypassPermissions`. Він ніколи не запитує для надсилань на тій самій машині. Значення `true`, задане будь-де (зокрема в закомічений файл проекту), застосовується; не існує способу перевизначити його назад на `false` зі слабшої області.

Щоб повністю вимкнути напрям: `crossSessionInbound: "refuse"` зупиняє отримання, а правило deny дозволів із назвами `SendMessage` і `ListAgents` (голі назви інструментів, без специфікатора) зупиняє надсилання й перелік. Заборона `SendMessage` також прибирає повідомлення до subagent і учасників команд агентів, бо вони ділять цей інструмент. Загальноорганізаційне блокування в managed settings поєднує обидва:

```json
{
  "permissions": {
    "deny": ["SendMessage", "ListAgents"]
  },
  "crossSessionInbound": "refuse"
}
```

За такої конфігурації сесія все ще прив'язує свій сокет inbox, але відкидає все, що на нього надходить. Ні `/status`, ні `/list-agents` іншої сесії не розкривають, що сесію заблоковано таким чином; підтверджуйте це читанням застосовних налаштувань, а не спостереженням за поведінкою.

### Перевірки підміни кінцевої точки

Перед доставкою до цілі на тій самій машині `SendMessage` перевіряє, що кінцева точка є тим, за що себе видає, і відмовляє замість надсилати, коли це не так: ціль відповіді у вигляді символічного посилання, кінцева точка, що з'єднується, але не є очікуваним процесом, або кінцева точка, ідентичність якої неможливо прочитати, — усе це призводить до відмови замість мовчазного надсилання не туди. Див. [Refusing to send a cross-session message](https://code.claude.com/docs/en/errors#refusing-to-send-a-cross-session-message).

### Де вписується нативна пісочниця

Доставлене повідомлення від іншої сесії може впливати на те, що Claude-одержувач спробує далі. Чотири межі покривають різні режими збою; жодна не замінює інші:

| Межа | Що вона контролює | Чого вона не гарантує |
|---|---|---|
| `crossSessionInbound`, `isolatePeerMachines` і дозволи інструментів | Які повідомлення надходять, чи залишають вони машину без схвалення та які інструменти може викликати одержувач | Що доставлене твердження правильне чи актуальне |
| [Нативна пісочниця](../security/sandbox-native.uk.md#inbox-сокети-між-сесіями) | Вплив команд Bash та їхніх дочірніх процесів на файлову систему й мережу | Безпека вбудованих викликів `Read`, `Edit` чи `Write`; правильність повідомлення; незалежність сесій |
| Один worktree на кожного паралельного автора змін | Розділення робочих файлів та індексів під час паралельних змін | Ізоляція хоста, облікових даних, мережі чи процесів |
| [Harness і CI-бар'єри](../core/agent-harness.uk.md#8-патерн-створювачверифікатор) | Відтворювані перевірки поточного коміту та незалежне рев'ю за вимогами | Ізоляція на рівні ОС чи політика дозволів |

Нативна пісочниця обмежує частину радіуса ураження, якщо одержувач діє за шкідливим чи хибним повідомленням. Вона не запобігає корельованому дрейфу і не перетворює дві сесії, що діляться одним checkout, на ізольованих виконавців.

### Безпека координації: корельований дрейф і хибний консенсус

Наведені вище контролі відповідають на запитання, хто може надсилати, куди йде повідомлення і яку владу воно несе. Вони не гарантують, що повідомлення правильне, актуальне чи в межах наміру користувача. Повідомлення від іншої сесії може бути безпечним для доставки й водночас поширювати хибну передумову.

Більше комунікації не обов'язково дає більше помилок. Своєчасне повідомлення може виявити конфлікт ще до того, як будь-яка сесія відредагує відповідний код. Ризик зростає, коли одержувачі повторно використовують висновок колеги без перевірки, бо тоді помилка однієї сесії стає спільним контекстом, і незалежні сесії починають помилятися в одному напрямку.

| Збій координації | Приклад | Контроль |
|---|---|---|
| **Поширення хибної передумови** | Одна сесія повідомляє, що міграцію завершено, після перегляду застарілого стану; інша сесія сприймає це повідомлення як факт про репозиторій. | Надсилайте твердження разом із гілкою чи worktree, SHA коміту, виконаними командами, відповідним виводом і рештою невизначеності. Одержувач повторно перевіряє стан, від якого залежить. |
| **Застаріла передача** | Повідомлення було правдивим на одному коміті, але перед тим, як одержувач діяв, з'явилася інша зміна. | Прив'яжіть передачу до SHA коміту й порівняйте його з поточним `HEAD` одержувача перед редагуванням чи схваленням. |
| **Хибний консенсус** | Рецензент отримує міркування автора, успадковує його рамку й підтверджує ту саму помилку. | Дайте незалежному верифікатору початкові вимоги, артефакт і докази, без обґрунтування автора. Додайте інші інструменти, докази часу виконання або іншу модель/провайдера, коли ризик виправдовує вартість. |
| **Гонка за спільне робоче дерево** | Дві сесії домовляються про володіння файлами в чаті, але все одно одночасно читають і пишуть той самий checkout. | Використовуйте один worktree на кожну паралельну сесію й явно фіксуйте володіння. `SendMessage` не блокує файли, не серіалізує запис і не заважає одній сесії зробити недійсним читання іншої. |
| **Зелений, але хибний результат** | Обидві сесії задовольняють тести, пропускаючи невисловлену продуктову вимогу чи властивість безпеки. | Запускайте детерміновані бар'єри на поточному SHA, а потім перевіряйте кожну вимогу за доказами. Залиште людський чи політичний бар'єр для неоднозначних, незворотних чи вагомих рішень. |
| **Відмивання повноважень** | Колега просить про дію, яку його власний користувач не дозволяв, але яка потрапляє в наявні дозволи інструментів одержувача. | Одержувач звіряє запит зі своїми інструкціями користувача й межами. Для чутливих сесій використовуйте `hold` або `refuse`; наявність дозволу не є авторизацією завдання. |

Сприймайте кожне повідомлення від іншої сесії як твердження з походженням, а не як доказ. Компактна передача може використовувати такий контракт:

```text
Target: @api-worker
Scope: review only; do not edit
Repository state: branch feature/tenant-migration, commit 4f2c1ab
Claim: the tenant_id migration is complete
Evidence: migration test and schema validation passed at that commit
Uncertainty: rollback was not tested
Requested action: verify compatibility against your current HEAD
```

Скористайтеся [моделлю загроз Security Hardening](../security/security-hardening.uk.md#cross-session-messaging-threat-model) для контролів відправника, транспорту, політики вхідних повідомлень і меж виконання. [Посібник Agent Harness](../core/agent-harness.uk.md#8-патерн-створювачверифікатор) охоплює незалежність верифікатора й пакети доказів. [Посібник Agent Evaluation](../roles/agent-evaluation.uk.md#оцінюйте-розподіл-прийняття-рішень-і-незалежність-рецензента) пояснює, як вимірювати хибні прийняття, хибні відхилення, врятовані збої та розбіжності, замість того щоб припускати, що другий агент незалежний.

## 7. Обмеження

Це властивості самого каналу, незалежні від платформи чи провайдера (їх окремо розглядає §8):

- **Лише простий текст.** Структуровані протокольні повідомлення команди агентів лишаються всередині команди; повідомлення між сесіями несуть лише текст.
- **Ліміт розміру на тій самій машині близько 1 048 576 символів.** Понад це `SendMessage` відхиляє надсилання, перш ніж воно залишить відправника; до одержувача нічого не доходить. Покладіть великий вміст у файл і надішліть натомість його шлях, стисніть зміст або розділіть на кілька повідомлень.
- **Швидкі потоки до однієї сесії відхиляються на боці відправника.** Коли потік до сесії на тій самій машині досягає того, що приймає inbox цієї сесії, подальші надсилання відхиляються в сесії-відправнику, якій кажуть об'єднати решту в одне повідомлення або зачекати. До v2.1.236 потік, що перевищував цей ліміт, повідомлявся як надісланий, тоді як сесія-одержувач мовчки його відкидала.
- **Цикли повідомлень обмежуються на боці одержувача.** Claude Code обмежує частоту повторюваних повідомлень за відправником, відкидає однакові повтори, що надходять у короткому вікні, і ставить у чергу щонайбільше 50 прийнятих повідомлень для читання Claude, що саме по собі зупиняє цикл повідомлень між двома сесіями.

## 9. Отримати сповіщення, коли інша сесія стає бездіяльною (v2.1.236+)

Замість опитування попросіть Claude підписатися на одне сповіщення від сесії на тій самій машині:

```text
Tell me when the migration session finishes what it's working on
```

Claude підписується через вхід `notify_when_idle` інструмента `SendMessage`, або прикріплений до повідомлення, яке він уже надсилає, або окремо (що нічого не коштує в сесії, за якою стежать, і спрацьовує негайно, якщо ця сесія вже бездіяльна). Сповіщення одноразове, і жодна сесія не опитує іншу; якщо воно не надходить протягом 12 годин, підписка скасовується, і Claude про це повідомляють, щоб він перестав чекати. Підписатися може лише основна розмова, і лише на сесії поточної машини; subagent, учасник команди чи сесія за межами поточної машини, що спробує, отримає відмову одразу, разом із повідомленням.

## 11. Практичні патерни

**Передати знахідку.** Сесія, яка виявляє зламну зміну чи ухвалює рішення, просить Claude підсумувати це для сесії, що працює над відповідною ділянкою, замість того щоб людина пояснювала це там знову.

**Координувати паралельні worktree.** Сесії, що працюють з одним репозиторієм у окремих [worktree](../ultimate-guide.uk.md#912-git-best-practices--workflows), дізнаються, що потрапило в сусідній worktree, без того щоб людина це передавала.

**Не координуйте спільне робоче дерево через чат.** Повідомлення про володіння файлами — це не блокування. Помістіть кожного паралельного автора змін у власний worktree, а потім інтегруйте через коміти, diff і звичайні бар'єри репозиторію.

**Розподіл праці за ролями.** Одна сесія для міграцій бази даних, одна для бекенду, одна для фронтенду, одна для документації, кожна в окремому терміналі. Коли міграція завершується, ця сесія пише сесії бекенду, щоб вона могла продовжити без опитування; коли сесія документації розв'язує питання, що блокувало фронтенд, відповідь іде тим самим шляхом.

**Продовження між пристроями.** Довга збірка, що працює в терміналі настільного комп'ютера, надсилає підсумок сесії документації, до якої є доступ із телефону через Remote Control, коли збірка завершується.

Жоден із цих випадків не потребує `TeamCreate`. Скористайтеся [Agent Teams](./agent-teams.uk.md) натомість, коли хочете, щоб головна сесія сама створювала й контролювала учасників зі структурованим розподілом завдань; користуйтеся обміном повідомленнями між сесіями, коли сесії вже існують незалежно, а ви лише прибираєте людину з передачі.

Про патерн координації, що стоїть за цим вибором, див. [Mediator в AI Design Patterns](../core/ai-design-patterns.uk.md#mediator): обмін повідомленнями між рівноправними сесіями є немедіаційною альтернативою координувальній сесії.
