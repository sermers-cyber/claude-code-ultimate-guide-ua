# Конвеєр підготовки виступів (Talk Preparation Pipeline): від ідеї до слайдів з ШІ

> **Confidence**: Рівень 2 — Валідовано на реальних виступах на конференціях (DevWithAI Lyon, 2026).

Перетворіть неопрацьовану статтю, транскрипт або нотатки на повноцінну доповідь для конференції — включаючи готовий до використання в Kimi промпт для створення слайдів за допомогою ШІ. Шість етапів, два режими та одна обов'язкова точка перевірки людиною (human-in-the-loop checkpoint).

## TL;DR

```
Source Material (article / transcript / notes)
        │
        ▼
[Stage 1] EXTRACT ─────────────── {slug}-summary.md
        │
        ├──────────────────────────────────────┐
        │                                      │
        ▼ (--rex only)                         ▼
[Stage 2] RESEARCH               [Stage 3] CONCEPTS
  git-archaeology.md              concepts.md
  changelog-analysis.md           concepts-enriched.md
  timeline.md                         │
        │                             │
        └──────────────┬──────────────┘
                       │
                       ▼
              [Stage 4] POSITION
                angles.md
                titre.md
                descriptions.md
                feedback-draft.md
                       │
                  [CHECKPOINT]
             User selects angle + title
                       │
                       ▼
              [Stage 5] SCRIPT
                pitch.md
                slides.md
                kimi-prompt.md ──► Copy-paste into Kimi.com
                       │
                       ▼
              [Stage 6] REVISION
               revision-sheets.md
```

Два режими: **REX** (доповідь із практичним досвідом — історія git, метрики) та **Concept** (на основі ідей/тез — пропускає Етап 2).

## Коли використовувати

Цей конвеєр підходить, якщо вам потрібно підготувати виступ і у вас є:

- **Практичний досвід (REX), яким ви хочете поділитися**: ви створили щось, запустили це в роботу, отримали реальні метрики — і хочете перетворити це на структуровану доповідь для конференції.
- **Концепція для розробки**: у вас є стаття, нотатки або ідеї, які ви хочете перетворити на структуровану презентацію.

Відповідні формати:
- Доповіді на конференціях (20-45 хв)
- Презентації на мітапах (15-30 хв)
- Внутрішні технічні доповіді
- Вступи до воркшопів

Не підходить для: оновлення слайдів для регулярних зустрічей, коротких бліц-доповідей (lightning talks) тривалістю до 10 хвилин або випадків, коли у вас немає жодного вихідного матеріалу для роботи.

## Передумови

**Обов'язково**:
- Встановлений Claude Code із налаштованими навичками (див. [examples/skills/talk-pipeline/](../../examples/skills/talk-pipeline/))
- Вихідний матеріал: файл статті `.mdx`, транскрипт `.md`, нотатки або їх суміш
- Метадані виступу: slug (ідентифікатор), назва події, дата, тривалість, опис аудиторії

**Тільки для режиму REX**:
- Доступ до репозиторію git, який ви хочете проаналізувати
- Опціонально: шлях до `CHANGELOG.md`, якщо він відрізняється від кореня репозиторію

**Для генерації слайдів у Kimi (вихідні дані Етапу 5)**:
- Безкоштовний акаунт на [kimi.com](https://kimi.com) (API не потрібен — лише скопіювати та вставити)

**Опціонально, але рекомендовано**:
- Папка `talks/` у корені вашого проєкту для вихідних файлів
- 1-2 колеги, яким можна надіслати чернетку для відгуків (Stage 4)

## Покроковий опис етапів

### Етап 1: Extract (Вилучення)

**Що робить**: читає вихідний матеріал та створює структурований підсумок — наративну арку, ключові метрики, основні теми та прогалини.

| | |
|--|--|
| **Вхідні дані** | Вихідний файл + метадані (slug, подія, дата, тривалість, аудиторія, режим) |
| **Вихідні дані** | `{slug}-summary.md` |
| **Інструменти** | Read, Write, AskUserQuestion |
| **Режим** | REX + Concept |

**Ключові правила**:
- Автоматично визначає тип джерела (REX чи Concept) на основі сигналів (дати, метрики, «я запустив» проти «я думаю»).
- Витягує кожну вимірювану метрику з її джерелом — жодних вигаданих чисел.
- Чітко вказує прогалини в матеріалі замість того, щоб приховувати їх.

**Запуск**:
```
/talk-stage1-extract
```

Або через оркестратор:
```
/talk-pipeline --stage=extract --slug=my-talk --event="Conf 2026" --date=2026-06-15 --duration=30 --audience="senior devs"
```

**Перевірка перед переходом до наступного етапу**:
- Наративна арка є зв'язною (а не загальною на кшталт «ця доповідь про ШІ...»).
- Усі метрики мають чітко вказане джерело.
- Перераховано прогалини (навіть якщо це «немає суттєвих прогалин»).
- Автовизначення типу (REX / Concept / Hybrid) виконано правильно.

---

### Етап 2: Research (Дослідження — тільки для режиму REX)

**Що робить**: «археологія» Git — вилучає метрики швидкості розробки, зіставляє з CHANGELOG, будує фактичну хронологію, підтверджену комiтами в git (а не припущеннями).

| | |
|--|--|
| **Вхідні дані** | `{slug}-summary.md` + шлях до репозиторію |
| **Вихідні дані** | `git-archaeology.md`, `changelog-analysis.md`, `timeline.md` |
| **Інструменти** | Bash (тільки для команд git на читання), Read, Write |
| **Режим** | Тільки REX — **автоматично пропускається в режимі Concept** |

**Ключові правила**:
- Тільки команди git для читання — ніколи не змінює репозиторій.
- Дати, які не знайдено в git, позначаються як «неперевірені» (unverified) — ніколи не оцінюються приблизно.
- Суперечності між джерелами фіксуються, а не замовчуються.

**Команди Git, які використовуються** (лише для читання):
```bash
git log --pretty=format:"%Y-%m" | sort | uniq -c   # velocity by month
git shortlog -sn --no-merges                         # contributors
git tag --sort=version:refname                       # releases
git log --merges --oneline | wc -l                   # PRs merged
```

**Перевірка перед переходом до наступного етапу**:
- Хронологія охоплює весь період з опису (summary).
- Немає приблизних дат — усі дати перевірені.
- Піки швидкості розробки (velocity peaks) мають контекстні примітки.

---

### Етап 3: Concepts (Концепції)

**Що робить**: будує пронумерований каталог усіх концепцій у матеріалі з відповідними оцінками. Кожна концепція отримує оцінку потенціалу доповіді (HIGH / MEDIUM / LOW).

| | |
|--|--|
| **Вхідні дані** | `{slug}-summary.md` + `{slug}-timeline.md` (опціонально) |
| **Вихідні дані** | `{slug}-concepts.md`, `{slug}-concepts-enriched.md` (якщо є доступ до репозиторію) |
| **Інструменти** | Read, Write |
| **Режим** | REX + Concept |

**Критерії оцінювання**:
- **HIGH (Високий)**: можна продемонструвати, суперечить інтуїції, має підтверджені цифри, можна застосувати на практиці за 30 секунд.
- **MEDIUM (Середній)**: корисно, але очікувано, бракує доказів або цифр.
- **LOW (Низький)**: занадто абстрактно, заїжджена тема, важко проілюструвати на слайді.

**Дисципліна оцінювання**: максимум 30% оцінок HIGH — сенс саме в ретельному відборі.

**Перевірка перед переходом до наступного етапу**:
- Виявлено понад 15 концепцій (понад 20 для REX з доступом до репозиторію).
- Оцінки відкалібровані (не всі HIGH і не всі LOW).
- Кожна концепція має конкретний опис в 1-2 реченнях.

---

### Етап 4: Position (Позиціонування) + CHECKPOINT (Точка перевірки)

**Що робить**: генерує стратегічні кути подачі (angles), варіанти назв, описи та чернетку повідомлення для відгуків колег. Потім **зупиняється та очікує** на ваш вибір кута подачі та назви.

| | |
|--|--|
| **Вхідні дані** | `{slug}-summary.md` + `{slug}-concepts.md` + обмеження події |
| **Вихідні дані** | `angles.md`, `titre.md`, `descriptions.md`, `feedback-draft.md` |
| **Інструменти** | Read, Write, AskUserQuestion |
| **Режим** | REX + Concept |

**Що генерується**:
- **3-4 кути подачі (angles)**: кожен із сильними та слабкими сторонами, відповідністю аудиторії та оцінкою (score /5).
- **Рекомендація**: один чіткий варіант із детально структурованим обґрунтуванням.
- **3-5 варіантів назв** для кожного кута подачі.
- **Короткий опис** (анотація ~100 слів) + **довгий опис** (заявка на доповідь / CFP ~250 слів).
- **Чернетка для відгуків**: готове повідомлення для надсилання колегам з метою перевірки ідеї (у 3 форматах: Slack DM, email, LinkedIn post).

**Відображення CHECKPOINT** (обов'язкове перед Етапом 5):

```
---
CHECKPOINT : Choix angle + titre

J'ai généré 4 fichiers :
- talks/{YYYY}-{slug}-angles.md    → {n} angles analysés
- talks/{YYYY}-{slug}-titre.md     → {n} options de titre
- talks/{YYYY}-{slug}-descriptions.md
- talks/{YYYY}-{slug}-feedback-draft.md

Avant de lancer le script (Stage 5), j'ai besoin de ton choix :

1. Quel angle tu retiens ? (recommandé : Angle {X} — {nom})
2. Quel titre tu préfères ? (recommandé : "{titre}")

Tu peux aussi modifier, mixer, ou proposer quelque chose d'autre.
---
```

**Етап 5 не може розпочатися без чіткого підтвердження користувача.**

**Перевірка перед підтвердженням**:
- Ви прочитали чернетку для відгуків і, за бажанням, надіслали її колезі.
- Обраний кут подачі дозволяє утримувати увагу аудиторії протягом усього часу без повторень.
- Назва є конкретною (без зайвого жаргону та клікбейту).

---

### Етап 5: Script (Сценарій)

**Що робить**: створює повний текст доповіді в 5 актах із нотатками спікера (speaker notes), специфікацією слайдів та промптом для Kimi.

| | |
|--|--|
| **Вхідні дані** | summary + concepts + timeline (опціонально) + **затверджений кут подачі та назва** |
| **Вихідні дані** | `{slug}-pitch.md`, `{slug}-slides.md`, `{slug}-kimi-prompt.md` |
| **Інструменти** | Read, Write |
| **Режим** | REX + Concept |

**Три результати роботи**:

1. **`pitch.md`**: повний наратив у 5 актах із нотатками спікера, хронометражем та ключовими моментами. Те, що ви говорите, а не те, що читаєте зі слайдів.

2. **`slides.md`**: специфікація слайдів — назва, опис візуалу, ключовий текст (не більше 30 слів), нотатки спікера, тривалість, номер акту. Готово для передачі дизайнеру або в Kimi.

3. **`kimi-prompt.md`**: готовий промпт для [kimi.com](https://kimi.com) — містить дизайн-систему, палітру кольорів, специфікації шрифтів, повний контент слайдів та місця для скріншотів. Готовий до копіювання.

**Правило «один слайд — одна ідея»**: якщо для опису слайда потрібен сполучник «та», розділіть його.

**Перевірка перед переходом до наступного етапу**:
- Перевірка хронометражу: загальний час ≤ тривалість доповіді + 10% буфера.
- Нотатки спікера звучать природно (прочитайте їх вголос для тесту).
- У промпті для Kimi не залишилося незаповнених місць на кшталт `{PLACEHOLDER}`.

---

### Етап 6: Revision (Доопрацювання)

**Що робить**: створює шпаргалки для повторення під час та після виступу — швидку навігацію по актах, зведену таблицю концепцій, шпаргалку Q&A та глосарій.

| | |
|--|--|
| **Вхідні дані** | `pitch.md` + `slides.md` + `concepts.md` |
| **Вихідні дані** | `{slug}-revision-sheets.md` |
| **Інструменти** | Read, Write |
| **Режим** | REX + Concept |

**Вміст шпаргалок для повторення**:
- **Навігація** з якірними посиланнями на кожен акт.
- **Аналіз кожного акту**: ключові концепції + метрики + анекдоти + ймовірні запитання й відповіді.
- **Зведена таблиця**: концепція → визначення в 1-2 реченнях → посилання для обміну.
- **Шпаргалка Q&A**: 6-10 ймовірних запитань із короткими відповідями (не більше 20 секунд на промову).
- **Блок метрик**: усі цифри зібрані в одному місці.
- **Зовнішні ресурси**: посилання, які згадуються в доповіді.
- **Глосарій**: технічні терміни, максимум 10 слів на кожен.

**Мета**: хтось ставить запитання → ви миттєво знаходите потрібний розділ → ділитеся URL-адресою за 5 секунд.

## Передача в Kimi (The Kimi Handoff)

Етап 5 створює `{slug}-kimi-prompt.md` — готовий промпт для [kimi.com](https://kimi.com).

**Що з ним робити**:
1. Відкрийте створений файл.
2. Переконайтеся, що не залишилося незаповнених полів `{PLACEHOLDER}` (виконайте пошук по файлу).
3. Перейдіть на [kimi.com](https://kimi.com) — потрібен безкоштовний акаунт, API не потрібен.
4. Почніть новий діалог.
5. Скопіюйте та вставте весь текст промпту.
6. Kimi згенерує презентацію (у форматі PowerPoint або PDF).

**Ітерація з Kimi**:
- Після першої генерації перевірте слайди на відповідність специфікації `slides.md`.
- Додавайте уточнюючі запити для коригування окремих деталей: «Slide 7: make the number larger, remove the bullet list».
- Для скріншотів: після експорту презентації вручну вставте зображення замість заповнювачів `SCREENSHOT AREA`.

**Дизайн-система**, закладена в шаблон:
- Темна тема (фон #0a0a0a)
- Помаранчевий акцент (#f97316) для ключових цифр та закликів до дії (CTA)
- Шрифти Inter / SF Pro
- Не більше 30 слів на слайд, цифри як головні герої
- Контрастність за стандартом WCAG AA (безпечно для проекторів)

**Чому саме Kimi?** На момент написання цього посібника Kimi створює якісніші презентації для конференцій за детальними промптами, ніж більшість альтернатив. Шаблон налаштований під Kimi, але дизайн-система та структура слайдів працюватимуть з будь-яким іншим ШІ-інструментом для створення презентацій.

## Точки перевірки за участю людини (Human-in-the-Loop Checkpoints)

Конвеєр містить дві обов'язкові перевірки людиною:

### Перевірка 1: Збір метаданих на Етапі 1

Якщо метадані виступу (slug, подія, дата, тривалість, аудиторія, режим) не надані заздалегідь, Етап 1 використовує `AskUserQuestion`, щоб зібрати їх перед початком. Це дозволяє уникнути генерації непотрібного підсумку.

### Перевірка 2: Етап 4 — Вибір кута подачі та назви (обов'язково)

Це найважливіший перехідний етап у конвеєрі. Етап 5 не може розпочатися без чіткого вибору людини.

**Чому це важливо**: кут подачі та назва визначають усе, що буде створено далі — структуру з 5 актів, вибір концепцій, тон промпту для Kimi. Автоматичний вибір на цьому етапі призвів би до створення шаблонної, нецікавої доповіді. Це єдине рішення, яке має належати саме вам.

**Що робити на цій точці перевірки**:
1. Прочитайте файл `angles.md` — не пропускайте цей крок, рекомендований варіант може не підійти вашому контексту.
2. За бажанням надішліть `feedback-draft.md` колезі, якому довіряєте (це займає 10 хвилин, але економить 2 години виправлень).
3. Дайте відповідь із вашим вибором (це може бути рекомендація, її модифікація або щось зовсім інше).

## Адаптація конвеєра

### Бліц-доповідь (Lightning talk, 10-15 хв)

- Залиште Етапи 1, 3, 4, 5 — пропустіть Етап 2 навіть у режимі REX.
- На Етапі 3: обмежтеся 8-10 концепціями (безжально відфільтруйте лише до рівня HIGH).
- На Етапі 4: згенеруйте максимум 2 кути подачі.
- На Етапі 5: орієнтуйтеся на ~8-10 слайдів, приблизно по 2 хвилини на слайд.
- Пропустіть Етап 6 (не потрібен для короткого формату).

### 45-хвилинна доповідь

- Повний конвеєр, усі етапи.
- На Етапі 3: націлюйтеся на 25-35 концепцій (цього достатньо, щоб наповнити 5 солідних актів).
- На Етапі 5: 20-25 слайдів, у середньому по 3 хвилини на слайд.
- Етап 6 стає критично важливим (сесія Q&A триває 10-15 хвилин).

### Воркшоп (90+ хв)

- Запустіть конвеєр до Етапу 4.
- На Етапі 5: замінить `slides.md` специфікацією активностей (вправи, таймінг, робота в групах).
- Розділ промпту для Kimi стає необов'язковим (менш актуальним для матеріалів воркшопу).

### Немає доступу до репозиторію git (REX без коду)

- Використовуйте режим `--rex`, якщо у вас є метрики з інших джерел (аналітика, дашборди, звіти про інциденти).
- На Етапі 2: замініть команди git ручним збором даних із цих джерел.
- Будьте суворішими до джерел — «неперевірені» метрики не повинні потрапити в доповідь.

## Поширені помилки

### Метрики без джерел

Етап 1 вилучає метрики, але не перевіряє їх. Етап 2 здійснює перевірку. Якщо ви працюєте в режимі Concept, будь-яка метрика, яку ви згадуєте в доповіді, має бути чітко підтверджена джерелом у підсумку (summary) — або видалена. Слухачі часто запитують: «Звідки ця цифра?», і відповідь «Я знайшов це в інтернеті» не підходить.

### Перевантажені слайди

Промпт для Kimi вимагає не більше 30 слів на слайд, але файл `pitch.md`, який ви пишете на Етапі 5, може поступово наповнюватися списками. Завжди перевіряйте правило «один слайд — одна ідея»: якщо для опису слайда потрібен сполучник «та», розділіть його.

### Пропуск точки перевірки (CHECKPOINT)

Запуск Етапу 5 без затвердженого кута подачі та назви призведе до створення технічно правильного сценарію для зовсім іншої доповіді. Рекомендація на Етапі 4 — це чудова відправна точка, але не остаточне рішення; ваше розуміння аудиторії має вирішальне значення.

### Занадто пізнє надсилання чернетки для відгуків

Чернетка для відгуків створюється на Етапі 4, ще до написання тексту доповіді. Це зроблено навмисно: відгуки колег на етапі вибору кута подачі та назви є корисними. Відгуки на вже готовий текст найчастіше приносять лише розчарування та необхідність переробляти великий обсяг роботи.

### Шаблонні нотатки спікера

Нотатки спікера в `pitch.md` повинні звучати як живе мовлення. Якщо ви помітили, що пишете фрази на кшталт «на цьому слайді ми обговорюємо...», перепишіть їх так, як ви реально сказали б це аудиторії в залі. Промпт для Kimi копіює ці нотатки, тому вони мають бути розмовними.

## Продемонстровані патерни проєктування

Цей конвеєр цікавий з точки зору використання Claude Code, оскільки він демонструє кілька передових патернів в одній цілісній системі.

### Ланцюжок навичок (Skill chaining) із файловим станом

Кожен етап записує файли, які зчитує наступний етап. Стан зберігається між викликами навичок через файлову систему — жодного зв'язування в оперативній пам'яті. Ви можете запустити Етап 3 через тиждень після Етапу 2 без втрати контексту.

```
Stage 1 → writes {slug}-summary.md
Stage 2 → reads {slug}-summary.md → writes 3 new files
Stage 3 → reads summary + timeline → writes 2 new files
...
```

### Обмеження дозволів інструментів (Tool permission scoping)

Етап 2 — єдиний, якому потрібен інструмент Bash (для команд git). Усі інші етапи використовують лише Read + Write. Це зроблено навмисно: мінімальний набір дозволів для кожного етапу зменшує ймовірність помилок.

```yaml
# Stage 2 only
allowed-tools:
  - Write
  - Read
  - Bash
```

### Людські шлюзи валідації (Human-in-the-loop gates)

Етап 4 використовує `AskUserQuestion` для відображення CHECKPOINT — не просто для зручності, а як структурну вимогу. Навичка не перейде до Етапу 5 без чіткої відповіді людини. Це класичний патерн «Claude пропонує, людина вирішує».

### Передача роботи від ШІ до ШІ (AI-to-AI handoff)

Етап 5 генерує промпт для іншої ШІ-системи (Kimi). Claude не створює слайди безпосередньо — він створює специфікацію, яку виконує інший ШІ. Цей патерн дозволяє поєднувати сильні сторони: Claude — для побудови структурованого наративу, Kimi — для візуального оформлення презентації.

```
Claude (Stage 5) → kimi-prompt.md → Kimi.com → slides.pptx
```

### Два режими виконання з умовним пропуском етапів

Прапорець `--rex` / `--concept` визначає, які саме етапи запускаються. Етап 2 автоматично пропускається в режимі Concept. Оркестратор (`/talk-pipeline`) керує маршрутизацією, тоді як навички окремих етапів залишаються незалежними від режиму.
