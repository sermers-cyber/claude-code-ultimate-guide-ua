# Пайплайн Plan-Validate-Execute

> **Confidence**: Tier 2, перевірено в реальних проєктах (production) командами, які масштабують AI-first продукти. Розширює вбудований режим `/plan` (Plan Mode) структурованою оркестрацією агентів та накопиченням інституційної пам'яті.

Повний цикл розробки всього у 3 команди: планування з динамічною командою дослідників, валідація незалежними спеціалізованими рев'юерами, виконання паралельними агентами. Кожен запуск покращує наступні завдяки навчальному циклу ADR, що послідовно зменшує потребу у втручанні людини.

**Час читання**: ~25 хв
**Необхідні знання**: Суб-агенти, Task tool, worktrees, базові концепти ADR
**Пов'язані теми**: [Plan-Driven Development](./plan-driven.uk.md), [Agent Teams](./agent-teams.uk.md), [Spec-First](./spec-first.uk.md)

## TL;DR

```
/plan-start    → 5-phase planning: PRD analysis + dynamic research team + ADRs
/plan-validate → 2-layer review: structural checks + trigger-based specialist agents
/plan-execute  → worktree + TDD + parallel execution + PR + merge + cleanup
```

**Чим цей підхід відрізняється від стандартного режиму `/plan`**:
- Дослідження виконується спеціалізованими агентами паралельно, а не одним агентом послідовно
- Валідація відокремлена від планування (усувається упередженість підтвердження — confirmation bias)
- Кожне важливе рішення генерує документ ADR, який автоматично вирішує аналогічні питання в майбутньому
- Виконання створює окремих агентів для кожного завдання в ізольованому git worktree, робить комміти під кожне завдання, створює та зливає (merge) PR

**Запускайте `/clear` між кожною командою**, щоб скинути контекст і уникнути накладних витрат на стискання лімітів (/compact).

## Philosophy

### Non-Prescriptive AI-First

Кажіть Claude **що** зробити, але ніколи — **як** це реалізувати. Тільки-но ви починаєте диктувати деталі реалізації, ви використовуєте свої знання як стелю, замість того щоб використовувати знання Claude як фундамент.

Хороший стартовий промпт для нового проєкту:
```
How should I use you most effectively to build this platform?
```

Дозвольте Claude запропонувати архітектурні рішення. Ваша робота полягає у валідації рішень, а не в їх диктуванні.

### No Bandaids, No Workarounds

Жорстке правило для кожного агента в пайплайні:

> Ми створюємо передове програмне забезпечення (state-of-the-art). Завжди обирайте найкращу у своєму класі архітектуру, найнадійніші патерни та індустріальні стандарти.

Час і зусилля на розробку не мають значення при прийнятті архітектурних рішень. Ніколи не враховуйте складність реалізації під час оцінки варіантів. Правильне рішення — це завжди найкращее рішення.

**Чек-лист контролю** (застосовуйте перед реалізацією):
- [ ] Чи використовую я прапорець зворотної сумісності, костиль (shim) або застарілий режим (legacy mode)?
- [ ] Чи робили б ми це саме так у новому проєкті, слідуючи поточній офіційній документації?
- [ ] Чи переношу я старі патерни замість того, щоб вивчати нові?
- [ ] Чи латаю я окремий компонент, коли проблема лежить на рівні всієї системи?

Якщо хоча б на одне питання відповідь "так": зупиніться та виправте це на належному рівні.

### Why Independent Validation?

Валідатори, які не писали сам план, не прив'язані до його початкових припущень. Дослідження показують, що рев'ю кількома агентами в режимі конструктивної опозиції (adversarial framing) виявляє значно більше проблем, ніж самоперевірка. Середній план генерує близько 18 зауважень під час перевірки незалежною командою. Близько 95% із них автоматично вирішуються на основі існуючих ADR та базових принципів.

## The Three Commands

### `/plan-start`: 5-phase planning

**Phase 1: PRD & Design Analysis** *(інтерактивно, без залучення суб-агентів)*

Прочитайте PRD та виділіть проблеми у 3 категорії перед запуском будь-яких агентів:
- Відсутні вимоги (нечіткі критерії приймання, неописані крайні випадки)
- Двозначні вимоги (кілька можливих інтерпретацій)
- Питання відповідності стандартам (безпека, приватність даних, API-контракти)

Представте варіанти з їхніми плюсами та мінусами, запишіть рішення. Пропустіть цей крок для завдань без PRD (рефакторинг, інфраструктура, виправлення багів).

Якщо завдання передбачає зміни UI, додайте аналіз дизайну: інвентаризація екранів, каталог станів інтерфейсу (порожній/завантаження/заповнений/помилка), специфікації взаємодії, патерни анімації, доступність (ARIA), оновлення дизайн-токенів.

**Phase 2: Technical Analysis** *(1-2 Explore агенти + інтерактив)*

Спочатку перевірте існуючі ADR та PATTERNS.md. Якщо 3 або більше підтверджених ADR відповідають потрібному рішенню → воно приймається автоматично без запиту користувача. В іншому випадку:
- Запустіть Explore агентів для цільового дослідження кодової бази
- Представте архітектурні рішення з варіантами та рекомендаціями
- Створіть документи ADR для важливих рішень (див. [ADR Learning Loop](#adr-learning-loop))
- Оновіть PATTERNS.md

**Phase 3: Scope Assessment** *(автоматично + затвердження користувачем)*

Застосуйте правила тригерів до пулу агентів (див. [Dynamic Agent Pool](#dynamic-agent-pool)). Представте запропоновану команду з обґрунтуванням для кожного агента. Користувач може додати або видалити агентів перед початком дослідження.

| Tier | Agent Count | Label |
|------|-------------|-------|
| 0 | 0 | Solo (вбудоване дослідження) |
| 1 | 1-3 | Focused |
| 2 | 4-6 | Standard |
| 3 | 7-9 | Comprehensive |
| 4 | 10+ | Full Spectrum |

**Phase 4: Research & Plan Creation** *(динамічна команда)*

- Tier 0: вбудоване дослідження, без запуску додаткових агентів
- Tier 1+: паралельний запуск схвалених агентів у фоні, координатор відстежує їх, зчитуючи шлях до вихідних даних, який повідомляє кожен агент
- `planning-coordinator` (модель Opus) синтезує всі звіти у фінальний план
- Збережіть (commit) файл плану, ADR та створені артефакти

Вихідні файли: `docs/plans/plan-{name}.md` + `docs/adr/ADR-XXXX.md` + `docs/plans/metrics/{name}.json`

**Автоматичний перехід**: якщо немає невирішених двозначностей → автоматичний запуск `/plan-validate`.

### `/plan-validate`: 2-layer validation

**Layer 1: Structural** *(вбудована швидка перевірка)*

Механічні перевірки, які не потребують запуску агентів:
- Формат плану та його повнота (наявність усіх обов'язкових розділів)
- Послідовність завдань та ланцюжок залежностей (відсутність циклічних залежностей)
- Перевірка існування файлів (файли, вказані для зміни, дійсно існують)
- Узгодженість з ADR (план відповідає створеним ADR)
- Відповідність правилам CLAUDE.md

**Layer 2: Specialist Review** *(запуск за тригерами, 0-8 агентів)*

| Agent | Trigger | Model |
|-------|---------|-------|
| `security-reviewer` | Auth, payments, PII, RBAC, нові API | Opus |
| `db-migration-reviewer` | Нові таблиці, стовпці, індекси, міграції | Opus |
| `performance-reviewer` | Нові резолвери, запити, роути, нові залежності | Sonnet |
| `design-system-reviewer` | Нові UI-компоненти, візуальний стиль | Sonnet |
| `ux-reviewer` | Нові сторінки, форми, інтерактивні елементи | Sonnet |
| `cross-platform-reviewer` | Web + mobile, або спільні пакети | Sonnet |
| `native-app-reviewer` | Мобільні екрани, нативні UI-пакети | Sonnet |
| `integration-reviewer` | Нові сервіси, бібліотеки, конфігурація OTEL | Opus |

Для тривіальних планів агенти автоматично не вибираються. Функціонал платежів може активувати 4 або більше агентів.

**Auto-Fix Phase (Автоматичне виправлення)**

Кожна знайдена проблема має бути вирішена, пропускати не можна. Сортування помилок:
1. Проблеми, які збігаються з існуючими рішеннями в ADR → автоматичне вирішення
2. Проблеми, які збігаються з підтвердженими записами в PATTERNS.md → автоматичне вирішення
3. Проблеми, які можна вирішити на основі базових принципів → автоматичне вирішення
4. Залишкові проблеми → рішення людини → створення нового правила → автовирішення наступного разу

**Автоматичний перехід**: після вирішення всіх проблем → автоматичний запуск `/plan-execute`.

### `/plan-execute`: Execution to merged PR

Одна єдина команда виконує всі етапи:

1. **Створення worktree**: ізольована гілка на основі поточного стану
2. **Створення TDD-заготовок**: написання тестів, що не проходять, для завдань, позначених як TDD
3. **Паралельне виконання на основі рівнів**: виявлення незалежних завдань, запуск агентів під кожне завдання, створення окремих коммітів під кожну задачу
4. **Виявлення відхилень (drift)**: попередження, якщо реалізація починає відходити від плану
5. **Контроль якості (Quality gate)**: паралельний запуск тестів + інтеграційні smoke-тести (GraphQL-запити, сканування логів контейнерів, запуск визначених планом smoke-команд)
6. **Оновлення документації перед PR**: узгодження з PRD + архівування плану (всередині worktree)
7. **Створення та злиття PR**: squash-merge, чистий та інформативний опис комміту
8. **Метрики після злиття**: запис даних виконання у файл метрик
9. **Очищення worktree**: видалення тимчасової гілки та каталогів worktree

Якщо контроль якості не пройдено: до 3 автоматичних спроб виправлення спеціалізованими debug-агентами. Якщо помилка залишається → сповіщення користувача.

## Dynamic Agent Pool

Агенти **не** прописуються жорстко в CLAUDE.md. Вони створюються динамічно під час виклику: опис, критерії запуску та вибір моделі вбудовуються у фазу планування, де они запускаються. Це дозволяє тримати CLAUDE.md лаконічним, надаючи кожному агенту повний контекст для його ролі.

### Research Pool (`/plan-start`)

| Agent | Trigger | Model |
|-------|---------|-------|
| `code-explorer` | Завжди | Sonnet |
| `arch-researcher` | Багатошарові зміни (2+ шарів) | Sonnet |
| `database-analyst` | Будь-які зміни схеми БД | Sonnet |
| `security-analyst` | Auth, payments, PII, RBAC | Opus |
| `test-analyzer` | Нетривіальний функціонал | Sonnet |
| `cross-platform-specialist` | Потрібен паритет із мобільною версією | Sonnet |
| `native-app-specialist` | Завдання зачіпає mobile/UI | Sonnet |
| `design-system-researcher` | Зміни UI в рамках завдання | Sonnet |
| `dependency-researcher` | Додавання нових пакетів | Sonnet |
| `devops-specialist` | Docker, env vars, CI/CD | Sonnet |
| `integration-researcher` | Нові сервіси, бібліотеки, OTEL | Opus |
| `planning-coordinator` | Завжди (коли обрано 2+ агентів) | Opus |

**Ключові архітектурні рішення**:
- Модель Opus використовується лише для критично важливих ролей (security, integration, coordination)
- Sonnet використовується для стандартних досліджень (висока якість, низька вартість)
- Агент `planning-coordinator` створюється лише тоді, коли обрано 2 або більше агентів: він займається синтезом результатів, а не первинними дослідженнями

### Validation Pool (`/plan-validate`)

Див. таблицю Layer 2 вище. Це інші агенти, які не перетинаються з пулом дослідження, адже валідатори не мають упередженості, спричиненої процесом створення плану.

## ADR Learning Loop

Кожне важливе архітектурне рішення генерує документ ADR. З часом ADR накопичуються в інституційну пам'ять проєкту, що зменшує кількість відволікань розробника.

### What Triggers an ADR

**Завжди створюйте ADR для:**
- Вибору між кількома робочими UI-патернами (overlay чи сторінка, drawer чи modal)
- Нових патернів анімації чи переходів, які відсутні в поточних стандартах
- Рішень щодо розбіжності поведінки платформ (веб проти мобільного додатка)
- Стратегій завантаження даних, які впроваджують нові підходи
- Стратегії авторизації, підходу до схеми БД, меж сервісів
- Вибору нових залежностей, що впливають на архітектуру

**НЕ потрібно створювати ADR для:**
- Рішень, які явно випливають із затверджених стандартів чи існуючих правил
- Незначних деталей розмітки в межах узгоджених шаблонів
- Стандартних елементів каталогу станів інтерфейсу (типові стани пустих екранів, завантаження чи помилок)

### Maturity Levels

```
1 ADR  → Watching   — відстежується, але ще не є обов'язковим стандартом
2 ADRs → Emerging   — пропонується як рекомендований варіант за замовчуванням з історичним контекстом
3+ ADRs → Confirmed — автоматично вирішується при плануванні (без залучення розробника)
          → Кандидат на перенесення в CLAUDE.md як жорстке правило
```

### The Loop

```
/plan-start Phase 2     →  ADR created
                                ↓
                        PATTERNS.md updated
                                ↓
/adr-review (periodic)  →  Detect patterns across ADRs
                                ↓
                        Propose CLAUDE.md promotions
                                ↓
Future /plan-start      ←  Confirmed rules auto-resolve decisions
```

Запускайте `/adr-review` кожні 10-15 планів, щоб пакетно аналізувати накопичені патерни та пропонувати доповнення до CLAUDE.md.

**Ефект накопичення**: на проєкті з 20 планами близько 80% архітектурних рішень приймаються та затверджуються автоматично. Участь людини фокусується лише на принципово нових викликах.

## CLAUDE.md Discipline

### Hard Limit: 120 Lines

Кожен рядок у CLAUDE.md витрачає токени контексту на кожен ваш запит. Файл CLAUDE.md обсягом 300 рядків — це важкий баласт, який зчитується перед кожним промптом. Встановіть та суворо контролюйте ліміт у 120 рядків.

**Що заслуговує на місце в CLAUDE.md:**
- Базові засади (жорсткі правила, що перекривають особисті вподобання агента)
- Підтверджені патерни з ADR (3+ використання)
- Специфічні для проєкту правила, які агенти не можуть вивести безпосередньо з коду
- Посилання на додаткові підфайли

**Чого НЕ повинно бути в CLAUDE.md:**
- Повного опису дизайн-систем, конфігурацій середовища, архітектурних схем
- Правил, які застосовуються менш ніж до 10% завдань
- Пояснень та обґрунтувань рішень (для цього пишіть ADR)

### Pointer Strategy

Замість завантаження всього контексту безпосередньо в CLAUDE.md, використовуйте систему посилань:

```markdown
## Context Files (load only when relevant)
- @docs/DESIGN_SYSTEM.md    — when UI changes are in scope
- @docs/ARCHITECTURE.md     — when service boundaries are touched
- @docs/ENV_CONFIG.md       — when Docker or env vars are modified
- @docs/ADR_PATTERNS.md     — during planning phases
```

Агенти підвантажують лише ті файли, які необхідні для їхнього конкретного завдання. Бекенд-завдання ніколи не буде зчитувати дизайн-систему. Контекст залишається чистим.

### Regular Trimming

Перевіряйте та очищуйте CLAUDE.md кожні 10-15 планів паралельно з виконанням `/adr-review`. Переносьте підтверджені патерни, видаляйте правила, які вже стали очевидними через загальний стиль коду, прибирайте те, на що давно ніхто не посилається.

## Context Management

### `/clear` Between Steps

Запускайте `/clear` між кроками `/plan-start`, `/plan-validate` та `/plan-execute`. Кожна команда є повністю самодостатньою: файл плану на диску є готовим артефактом передачі стану, тримати його в оперативній пам'яті контексту немає потреби.

Без регулярного виклику `/clear`: контекст накопичується на всіх фазах розробки, стискання (/compact) починає спрацьовувати занадто рано, агенти отримують купу зайвої інформації з минулих кроків, а витрати на токени значно зростають.

### Why This Works

Кожна команда зчитує свої вхідні дані безпосередньо з диска (файли планів, ADR, кодова база). Немає жодного стану, який мав би жити у вікні контексту між різними кроками. Дисципліна регулярного очищення між кроками дозволяє пайплайну масштабуватися на великі проєкти без загрози впертися в ліміти контексту посеред виконання.

---

## When to Use

### ✅ Використовуйте цей пайплайн, коли:

- Фіча зачіпає велику кількість файлів та кілька шарів архітектури (API + БД + UI)
- Вносяться зміни, чутливі до безпеки (auth, payments, PII)
- Плануються складні міграції БД
- Інтегруються нові зовнішні сервіси
- Будь-які завдання, де помилка планування коштуватиме дорого
- Командна робота, де важлива історія та прозорість рішень

### ❌ Не використовуйте, коли:

- Потрібно виправити друкарську помилку чи провести простий локальний рефакторинг (використовуйте стандартний режим `/plan`)
- Проводиться швидке прототипування, де фінальні вимоги ще невідомі
- Потрібно зробити гаряче виправлення (hotfix) під великим тиском часу (використовуйте dual-instance planning)
- Зміни зачіпають не більше 2 файлів і не вимагають жодних архітектурних рішень

### ⚡ Скорочений шлях Tier 0

Для невеликих, але важливих змін пайплайн все одно запускається, але система автоматично визначить рівень складності як Tier 0 та пропустить створення додаткових фонових агентів: дослідження відбудеться прямо в чаті, валідація обмежиться Layer 1, а виконання буде зроблено одним основним агентом. Команди ті самі, але накладні витрати набагато менші.

## Cost Profile

| Phase | Cost Driver | Approximate Range |
|-------|-------------|-------------------|
| `/plan-start` Tier 0 | Inline research only | $0.10-0.30 |
| `/plan-start` Tier 1-2 | 2-6 Sonnet agents | $0.50-2.00 |
| `/plan-start` Tier 3 | 7+ agents + Opus coordinator | $2.00-8.00 |
| `/plan-validate` | 0-8 agents | $0.20-3.00 |
| `/plan-execute` | Per-task agents + quality gate | $0.50-5.00 |
| **Typical feature (Tier 2)** | Full pipeline | **$2-10** |

Вартість розробки суттєво знижується в міру зростання бази ADR: потрібно менше агентів, виникає менше проблем при валідації, а саме виконання проходить швидше.

Використовуйте `/plan-metrics` періодично для аналізу трендів витрат та калібрування майбутніх оцінок.
