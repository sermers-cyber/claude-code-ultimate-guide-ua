# Вибір вашого підходу до впровадження

**Дисклеймер**: Claude Code — дуже молодий інструмент (~1 рік). Ніхто ще не має остаточних відповідей — включаючи цей посібник. Це стартові точки на основі спостережуваних паттернів, а не доведені найкращі практики. Активно адаптуйте їх під свій контекст.

---

## Чого ми ще не знаємо

Перед тим як зануритися в тему, зазначимо, що насправді залишається невідомим:

- **Оптимальний розмір CLAUDE.md** — деякі команди успішно працюють із 10 рядками правил, інші — зі 100. Чіткого переможця немає.
- **Шаблони командного впровадження** — чи перевершує стандартизація «зверху вниз» органічне впровадження «знизу вгору», поки не доведено.
- **Пороги керування контекстом** — показники в 70%/90% є евристиками, а не науково доведеними цифрами.
- **ROI розширених функцій** — сервери MCP, гачки, агенти — поки неясно, коли саме витрати на їх налаштування окупаються.

Якщо хтось каже вам, що повністю розібрався в цьому, він або випереджає індустрію, або занадто самовпевнений.

## Що ми знаємо (емпіричні дані)

Деякі патерни вималювалися з досліджень практиків та командних ретроспектив:

| Знахідка | Дані | Наслідок |
|----------|------|----------|
| **Масштаб має вирішальне значення** | 1-3 файли: ~85% успіху, 8+ файлів: ~40% | Починайте з малого, розширюйте поступово |
| **«Золота середина» CLAUDE.md** | Оптимально 4-8KB, >16K погіршує узгодженість | Лаконічність краща за всеосяжність |
| **Ліміти сесій** | 15-25 ходів до початку відхилення від обмежень | Скидайте сесію для нових завдань |
| **ROI генерації скриптів** | Заявлено про 70-90% економії часу | Найкращий перший юзкейс |
| **Дослідження перед імплементацією** | +20-30% до якості рішень | Спочатку запитуйте альтернативні варіанти |

**Джерело**: інженерний блог MetalBear, дослідження практиків на arXiv, інженерні гілки Reddit (2024-2025).

## Стартові точки (не приписи)

| Ваш контекст | Один з підходів для спроби |
|--------------|----------------------------|
| Обмежений час на налаштування | **Готовий (Turnkey)** — мінімальна конфігурація, ітерація при появі труднощів |
| Індивідуальний розробник | **Автономний (Autonomous)** — спочатку вивчіть концепції, налаштовуйте за потреби |
| Мала команда (4-10) | **Гібридний (Hybrid)** — спільні основи + простір для особистих уподобань |
| Велика команда (10+) | **Готовий + документація** — узгодженість важливіша на масштабі |

Це лише гіпотези. Ваші результати можуть відрізнятися.

## Готовий старт (Turnkey Quickstart)

### Крок 1: Створіть мінімальну конфігурацію

```bash
mkdir -p .claude
```

Створіть `.claude/CLAUDE.md`:

```markdown
# Project: [your-project-name]

## Stack
- Runtime: [Node 20 / Python 3.11 / etc.]
- Framework: [Next.js / FastAPI / etc.]

## Commands
- Test: `npm test` or `pytest`
- Lint: `npm run lint` or `ruff check`

## Convention
- [One rule you care most about, e.g., "TypeScript strict mode required"]
```

### Крок 2: Перевірте налаштування

```bash
claude
```

Потім запитайте:
```
What's this project's test command?
```

**Успіх**: Повертає налаштовану вами команду.
**Помилка**: CLAUDE.md не завантажився — перевірте, чи шлях є `.claude/CLAUDE.md` або `./CLAUDE.md`

### Крок 3: Перше реальне завдання

```bash
claude "Review the README and suggest improvements"
```

Claude має автоматично врахувати ваш стек та правила.

**Готово.** Додавайте більше конфігурацій лише тоді, коли виникають реальні труднощі.

## Автономний шлях навчання (Autonomous Learning Path)

Якщо ви віддаєте перевагу розумінню інструменту перед його налаштуванням, ось послідовний підхід. Оцінок часу немає — швидкість залежить від вашого досвіду роботи з інструментами ШІ.

### Фаза 1: Ментальна модель

**Мета**: Зрозуміти, як працює Claude Code, перед додаванням конфігурацій.

1. Прочитайте [Розділ 5: Ментальна модель](./ultimate-guide.md) (рядок 1675)
2. Основна концепція: Claude працює в циклі — промпт → план → виконання → перевірка.
3. **Спробуйте**: Виконайте кілька реальних завдань без конфігурацій. Зверніть увагу, де виникають труднощі.

### Фаза 2: Керування контекстом

**Мета**: Зрозуміти головне обмеження інструменту.

1. Прочитайте [Керування контекстом](./ultimate-guide.md) (рядок 944)
2. Загальна ідея (точні пороги залежать від юзкейсу):
   - Низьке споживання: працюйте вільно
   - Середнє споживання: будьте більш вибірковими
   - Високе споживання: розгляньте `/compact`
   - Поблизу ліміту: `/clear` для скидання
3. **Спробуйте**: Періодично перевіряйте `/status`. Спостерігайте, як розвиваються ваші патерни використання.

### Фаза 3: Файли пам'яті

**Мета**: Надати Claude контекст проєкту.

1. Прочитайте [Файли пам'яті](./ultimate-guide.md) (рядок 2218)
2. Пріоритетність: проєктний `.claude/CLAUDE.md` > глобальний `~/.claude/CLAUDE.md`.
3. **Спробуйте**: Створіть мінімальний CLAUDE.md, перевірте, чи Claude зчитує його.

### Фаза 4: Розширення (при появі труднощів)

Додавайте складність лише тоді, коли стикаєтеся з реальними проблемами:

| Труднощі | Можливе рішення | Посилання |
|----------|-----------------|-----------|
| Часто повторюється те саме завдання | Створіть агента | [Шаблон агента](./ultimate-guide.md) рядок 2793 |
| Питання безпеки | Налаштуйте гачок (hook) | [Шаблони гачків](./ultimate-guide.md) рядок 4172 |
| Потрібен доступ до зовнішніх інструментів | Використовуйте MCP | [Конфігурація MCP](./ultimate-guide.md) рядок 4771 |
| ШІ повторює ту саму помилку | Додайте конкретне правило | Почніть з одного рядка, а не з десяти |

Чи варті ці рішення часу на налаштування — залежить виключно від вашого контексту.

## Базові перевірки (Sanity Checks)

Це сигнали того, що все працює, а не жорсткі віхи.

### Базове налаштування працює

```bash
claude --version          # Повертає версію
claude /status            # Показує інформацію про контекст
claude /mcp               # Виводить список серверів MCP (може бути порожнім)
```

Якщо це не працює: проблема зі встановленням — запустіть `claude doctor`.

### Конфігурація зчитується

**Тест**: Запитайте Claude: "What's the test command for this project?"

Якщо він повертає вашу налаштовану команду, CLAUDE.md завантажено успішно. Якщо ні — перевірте шлях до файлу.

### Ви керуєте контекстом

**Сигнал**: Ви помічаєте, коли контекст стає завеликим, і вживаєте заходів.

Це розвивається природно з використанням. Якщо ви ніколи не думаєте про контекст, ви або не використовуєте Claude інтенсивно, або ігноруєте сигнали, які можуть бути важливими.

### Розширення корисні (або не потрібні)

**Сигнал**: Ви або створили щось (агента, гачок, команду), що допомагає, або вам це не знадобилося.

Обидва варіанти прийнятні. Розширення необов'язкові — не додавайте їх просто заради їх наявності.

## Типові помилки

Ці патерни здаються проблемними на основі спостережень, хоча індивідуальний досвід може відрізнятися.

| Патерн | Що відбувається | Альтернатива |
|--------|-----------------|--------------|
| **Величезна скопійована конфігурація** | Правила ігноруються, неясно, що важливо | Почніть з малого, додавайте при появі труднощів |
| **Надмірне проєктування налаштувань** | Час витрачається на конфігурацію замість написання коду | Використовуйте шаблони як стартові точки |
| **Відсутність спільних правил** | Розробники розходяться в підходах, плутанина при онбордингу | Задокументуйте кілька найважливіших правил |
| **Увімкнення всього й одразу** | Зайва складність без чіткої вигоди | Вмикайте функції лише тоді, коли вони потрібні |

Це не універсальні істини — деякі команди успішно працюють із великими конфігураціями або повним набором функцій.

## Врахування розміру команди

Це стартові точки, а не непорушні правила. Динаміка команди важливіша за кількість людей.

### Solo / Мала команда (2-3 розробники)

**Типова структура**:
```
./CLAUDE.md                    # Базові правила проєкту, комітяться в репозиторій
~/.claude/CLAUDE.md            # Особисті уподобання
```

**Що може працювати**:
- Короткий проєктний CLAUDE.md зі стеком та основними командами.
- Особисті налаштування для моделей, прапорців.
- Розширення лише в тому випадку, якщо ви часто повторюєте однакові завдання.

**За чим стежити**: Надмірне проєктування. Якщо ви витрачаєте більше часу на конфігурацію, ніж на код, зробіть крок назад.

### Середня команда (4-10 розробників)

**Типова структура**:
```
./CLAUDE.md                    # Командні правила (комітяться)
./.claude/settings.json        # Спільні гачки (комітяться)
~/.claude/CLAUDE.md            # Індивідуальні уподобання (не комітяться)
```

**Що може працювати**:
- Спільні правила, яких команда дійсно дотримується.
- Гачки безпеки, якщо вони актуальні для вашого контексту.
- Простір для особистих уподобань.

**Один зі способів розділення конфігурацій**:

| Спільне (репозиторій) | Особисте (~/.claude) |
|-----------------------|----------------------|
| Команди тестування/лінту | Уподобання щодо моделей |
| Конвенції проєкту | Кастомні агенти |
| Формат комітів | Прапорці за замовчуванням |

**Продакшен-команди**: Впроваджуйте [Правила безпеки в продакшені](production-safety.uk.md) для захисту портів/БД/інфраструктури через гачки та правила заборони дозволів.

**За чим стежити**: Правила, які існують лише на папері, але не виконуються.

### Велика команда (10+ розробників)

**Типова структура**:
```
./CLAUDE.md                    # Документовано, комітиться
./.claude/settings.json        # Стандартні гачки, комітиться
./.claude/agents/              # Спільні агенти, комітиться
~/.claude/CLAUDE.md            # Особисті додатки
```

**Що може працювати**:
- Задокументовані правила з обґрунтуванням.
- Стандартизовані гачки для всієї команди.
- Онбординг, що охоплює базові речі, такі як `/status`.
- **Продакшен-команди**: Забезпечуйте [Правила безпеки в продакшені](production-safety.uk.md) через гачки та правила заборони дозволів.

**За чим стежити**: Розбіжність конфігурацій (config drift). Без координації налаштування з часом розходяться. Чи має це значення — залежить від вашої команди.

> **Новий підхід**: Деякі організації досліджують «корпоративні ШІ-маркетплейси» для об'єднання ШІ-навичок, агентів та правил на рівні компанії, а не окремих команд (Hugo/Writizzy 2026[^hugo2026]). Документованих продакшен-впроваджень поки небагато, але концепція вирішує питання управління на масштабі.

### Впровадження в масштабах підприємства (Enterprise Rollout) (50+ розробників або регульовані середовища)

На такому масштабі індивідуальних налаштувань команд недостатньо. Вам потрібен спільний базовий рівень конфігурації, який застосовується послідовно в усіх проєктах.

**Поетапний підхід до впровадження:**

**Фаза 1 — Фундамент (Тиждень 1–2)**: Встановлення базового рівня управління.
- Створення спільного репозиторію конфігурацій організації (шаблони `.claude/` за рівнями).
- Публікація Хартії використання ШІ (див. [шаблон хартії](../../examples/scripts/ai-usage-charter-template.md)).
- Створення реєстру MCP з поточними використовуваними серверами (навіть якщо там лише 3 записи).
- Встановлення глобальних гачків безпеки на машини всіх розробників через скрипт онбордингу.

**Фаза 2 — Впровадження (Тиждень 3–6)**: Запуск конфігурацій проєктів.
- Класифікація наявних проєктів за рівнями (Starter / Standard / Strict / Regulated).
- Бутстрап кожного проєкту з відповідною конфігурацією рівня через скрипт налаштування.
- Додавання онбордингу Claude Code до загального чек-листа адаптації інженерів.
- Проведення першого аудиту управління для визначення базового стану.

**Фаза 3 — Оптимізація (Місяць 2–3)**: Вдосконалення на основі зворотного зв'язку.
- Аналіз частоти хибнопозитивних спрацьовувань гачків — налаштування правил, які блокують легітимну роботу.
- Ідентифікація запитів на MCP та їх опрацювання через процес реєстру.
- Додавання перевірок управління в CI/CD для запобігання розбіжностям конфігурацій.
- Проведення першого щоквартального перегляду реєстру MCP.

**Типові помилки впровадження на цьому масштабі:**

| Помилка | Наслідок | Виправлення |
|---------|----------|-------------|
| Впровадження рівня Strict скрізь у перший день | Спротив розробників, пошук обхідних шляхів | Почніть зі Standard, переносьте критичні проєкти на Strict поступово |
| Відсутність центрального репозиторію конфігурацій | Кожна команда розходиться в підходах за кілька тижнів | Платформна команда володіє спільними шаблонами |
| Перевірки управління, які повністю блокують роботу | Розробники вимикають гачки | Використовуйте гачки в режимі попередження (warn-only), усувайте першопричину |
| Відсутність онбордингу → хартія ігнорується | Політика існує лише на папері | 30-хвилинна сесія онбордингу для кожної команди |

**Для формальних програм відповідності** (SOC2, ISO27001, HIPAA) додаткові вимоги щодо аудиторських журналів, класифікації даних та циклів перегляду описано в [Корпоративному управлінні ШІ](../security/enterprise-governance.uk.md).

## Типові ситуації

### «Я оцінюю Claude Code для своєї команди»

**Підхід до швидкого тестування**:
1. Встановіть: `npm i -g @anthropic-ai/claude-code`
2. Запустіть у наявному проєкті: `claude`
3. Спробуйте реальне завдання: `claude "Analyze this codebase architecture"`
4. Перевірте `/status`, щоб зрозуміти споживання токенів.

**Запитання, на які потрібно відповісти**:
- Чи розуміє Claude ваш стек без додаткових налаштувань?
- Чи покращує результати мінімальний CLAUDE.md?
- Чи може ваша команда освоїти базові принципи керування контекстом?

Уникайте розширених функцій (MCP, гачки, агенти) під час первинної оцінки.

### «Моя команда не може узгодити конфігурацію»

**Один із варіантів розподілу обов'язків**:

| Рівень | Типовий власник | Типовий вміст |
|--------|-----------------|---------------|
| CLAUDE.md проєкту | Рішення команди | Стек, команди, основні правила |
| Гачки проєкту | Розробники, орієнтовані на безпеку | Захисні бар'єри (guardrails) за потреби |
| Особистий ~/.claude | Індивідуальний розробник | Уподобання, особисті агенти |

Спосіб вирішення конфліктів залежить від культури вашої команди. Деякі команди голосують, деякі делегують рішення тімлідам, інші дозволяють індивідуальні відмінності.

### «Claude продовжує робити ту саму помилку»

**Звабливо**: Додати багато правил, щоб запобігти цьому.

**Часто краще**: Додати одне конкретне правило, перевірити, чи воно працює, та ітерувати.

```markdown
## [Specific issue]
When doing [X], avoid [specific mistake].
Instead: [correct approach]
```

Якщо правило не допомагає, можливо воно занадто розмите. Зробіть його конкретнішим або подумайте, чи правила є правильним інструментом у цьому випадку.

### «Я успадкував величезний CLAUDE.md»

**Один з підходів**:
1. Попросіть Claude підсумувати те, що написано в CLAUDE.md.
2. Порівняйте це з тим, що команда робить насправді.
3. Видаліть правила, які не виконуються або на які немає посилань.
4. Залиште те, що дійсно корисне.

**Евристика**: Якщо ви не можете пояснити, чому правило існує, розгляньте можливість його видалення.

### «Коли мені слід додавати більше складності?»

Універсальної відповіді немає. Деякі сигнали, які можуть свідчити про таку потребу:

| Сигнал | Можлива відповідь |
|--------|-------------------|
| Часто повторюється один і той самий промпт | Створіть команду |
| Питання безпеки | Додайте гачок (hook) |
| Потрібен доступ до зовнішніх інструментів | Використовуйте MCP |
| Однакові запитання від команди | Створіть документацію |

Але також: можливо, вам не потрібна додаткова складність. Прості налаштування чудово працюють для багатьох команд.

## Швидкий довідник

### Корисні команди

| Команда | Призначення |
|---------|-------------|
| `/status` | Перевірити споживання контексту |
| `/compact`| Стиснути контекст, коли він завеликий |
| `/clear` | Повністю скинути контекст |
| `/plan` | Увійти в режим планування |
| `/model` | Перемикання між моделями |

Як часто ви використовуєте ці команди — залежить від вашого воркфлоу.

### Вартість моделей (відносна)

| Модель | Вартість | Типові юзкейси |
|--------|----------|----------------|
| Haiku | $ | Прості завдання, швидкі відповіді |
| Sonnet | $$ | Загальна розробка |
| Opus | $$$ | Складний аналіз, архітектура |

Більшість розробників починають із Sonnet. Коригуйте вибір на основі свого досвіду.
