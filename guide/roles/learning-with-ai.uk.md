## Проблема за 60 секунд

> ШІ може зробити вас у 3 рази продуктивнішим АБО повністю непридатним для працевлаштування через 3 роки.
> У чому різниця? У тому, ЯК саме ви його використовуєте.

Забудьте на хвилинку про статистику. Ось проста метафора:

**ШІ — це ваш GPS.**

- Чудово підходить для того, щоб швидко дістатися потрібного місця
- Стає небезпечним, якщо ви повністю втрачаєте здатність орієнтуватися без нього
- Дійсно корисний тоді, коли ви розумієте саму карту ТА використовуєте GPS для допомоги

Розробник, який лише копіює та вставляє результати роботи ШІ, схожий на водія, який не вміє читати дорожню карту. Все гаразд, поки GPS працює — або поки хтось не попросить пояснити обраний маршрут.

### Прогалина в навичках

```
Традиційне навчання: Проблема → Боротьба → Розуміння → Рішення
Навчання з ШІ (неправильно): Проблема → ШІ → Рішення → ??? (немає розуміння)
Навчання з ШІ (правильно): Проблема → Спроба → Поради ШІ → Розуміння → Рішення
```

Етап боротьби та пошуку рішень не є необов'язковим. Саме на ньому відбувається навчання.

### Пастка «Вайб-кодингу» (Vibe Coding Trap)

Термін, введений [Андрієм Карпати](https://x.com/karpathy/status/1886192184808149383) (лютий 2025 року, слово року 2025 за версією Collins): написання коду шляхом «повного підкорення вайбу» без розуміння згенерованого коду.

> **Пов'язано**: Для командних та open-source контекстів див. [AI Traceability](../ops/ai-traceability.uk.md) щодо політик розкриття інформації (LLVM, Ghostty, Fedora) та інструментів атрибуції.

**Симптоми:**
- Вибір «Accept All» без ретельного читання різниці в коді (diffs)
- Копіювання помилок без розуміння першопричини
- Налагодження шляхом прохання ШІ внести випадкові зміни, поки все якось «не запрацює»

**Застереження Карпати**: «Не так уже й погано для дрібних пет-проектів на вихідних» — але смертельно небезпечно для продакшн-коду, який вам доведеться самостійно підтримувати роками.

**Протиотрута**: Протокол UVAL (§5) змушує зрозуміти код перед його прийняттям.

> **Пов'язано**: Для стратегій управління контекстом, які запобігають хаосу вайб-кодингу, див. [Anti-Pattern: Context Overload](#anti-pattern-context-overload) в основному посібнику (§9.8).

**У масштабах всієї команди** вайб-кодинг накопичується в те, що деякі практики називають *боргом розуміння* (comprehension debt — новий термін, 2025-2026 рр.): зростаючий розрив між тим, скільки коду існує в системі, і тим, скільки з нього людина реально розуміє. На відміну від технічного боргу, який проявляється через повільну збірку чи заплутані залежності, борг розуміння породжує хибну впевненість — швидкість виглядає чудово, тести зелені, а розплата приходить у найгірший момент, зазвичай під час серйозного інциденту чи аудиту.

## Реальність продуктивності з ШІ

Перш ніж оптимізувати свій підхід до навчання, зрозумійте, що насправді показують дослідження продуктивності — результати набагато тонші, ніж стверджує маркетинг.

### Крива продуктивності (Це не пряма лінія)

Більшість розробників проходять через три різні фази:

| Фаза | Термін | Продуктивність | Що насправді відбувається |
|------|--------|----------------|---------------------------|
| **Ефект Вау!** | 0-2 тижні | ~0% приросту | Захоплення маскує криву навчання; час, витрачений на промптинг, нівелює зекономлений час |
| **Цільові досягнення** | 2-8 тижнів | +20-50% | ШІ прискорює виконання конкретних завдань, які ви навчилися ефективно делегувати |
| **Стабільне плато** | 3-6 місяців | +20-30% | Стабільні результати, але лише для розробників, які вже мають міцні фундаментальні знання |

**Критичний нюанс**: Ці вигоди є умовними. Дослідження показують, що досвідчені розробники (5+ років досвіду) бачать більші та триваліші результати. Джуніор-розробники часто відчувають початковий сплеск, за яким слідує регресія — тому що швидкість без розуміння створює технічний борг. Рандомізоване контрольоване дослідження (RCT) 2026 року ([Shen & Tamkin, Anthropic Fellows](https://arxiv.org/abs/2601.20245)) зафіксувало **17%-ве зниження рівня засвоєння навичок**, коли розробники вивчали нову бібліотеку за допомогою ШІ (n=52, p=0.01) — без суттєвої економії часу. Лише ~20% користувачів ШІ (патерн чистого делегування) закінчили завдання швидше, але ціною того, що не навчилися майже нічого.

**Специфічний фактор стресу від ШІ**: Недетерміновані результати (однакові промпти → різні виходи) створюють когнітивну тривогу, відмінну від традиційного налагодження. Ця мінливість може викликати «втому від ШІ» (AI fatigue) — ментальне виснаження від непередбачуваної поведінки інструменту, яке накопичується під час тривалих сесій. Спосіб пом'якшення: обмежуйте сесії за часом (максимум 30 хвилин), обмежуйте кількість повторних спроб генерації (максимум 3 до того, як перейти до ручного написання коду) та вчасно розпізнавайте, коли непередбачуваність інструменту сигналізує про необхідність скидання контексту (`/clear`) або переходу до ручного вирішення.

### Де ШІ допомагає (А де шкодить)

| Завдання з високою ефективністю | Завдання з низькою/від'ємною ефективністю |
|---------------------------------|-------------------------------------------|
| Генерація шаблонного коду (boilerplate) | Архітектурні рішення |
| Скелет тестування (test scaffolding) | Специфічна доменна бізнес-логіка |
| Рефакторинг відомих патернів | Глибоке налагодження (deep debugging) |
| Чернетки документації | Тонка оптимізація продуктивності |
| Онбординг у нову кодову базу | Код, критичний для безпеки |
| CRUD операції | Розробка нових нестандартних алгоритмів |

Загальний патерн: **ШІ чудово справляється з чітко визначеними, повторюваними завданнями**. Він зазнає труднощів з неоднозначними проблемами, які вимагають глибокого розуміння контексту чи творчого судження.

### Чому одні команди отримують результати (А інші ні)

**Успішні команди:**
- Встановлюють чіткі правила використання ШІ (коли використовувати, а коли ні)
- Підтримують високі стандарти коду (згенерований ШІ код рецензується так само суворо, як і написаний людиною)
- Створюють спільні бібліотеки промптів для типових завдань
- Об'єднують розробників-початківців із досвідченими менторами під час роботи з ШІ

**Команди, що стагнують:**
- Не мають стандартів якості для згенерованого ШІ коду
- Джуніори безконтрольно використовують ШІ без нагляду
- Вимірюють лише швидкість випуску фіч, ігноруючи рівень розуміння коду розробниками
- Пропускають етап рев'ю коду, бо «його ж написав ШІ»

Різниця полягає не в самому інструменті — а в організаційній дисципліні навколо нього.

**Пляшкове горло рецензування перевернулося.** Коли код було дорого створювати, старші інженери могли рецензувати його швидше, ніж молодші його писали — рев'ю було воротами якості. ШІ перевертає це: джуніор тепер може генерувати код швидше, ніж сеньйор здатний його критично перевірити. Обмежувальний фактор швидкості, який раніше робив рев'ю змістовним, зник. Те, що раніше було воротами якості, тепер перетворилося на проблему пропускної здатності. Команди, які не враховують це, закінчують сліпим схваленням (rubber-stamping) ШІ-коду в промислових масштабах.

> **Для техлідів**: Якщо ви відповідаєте за структурування цього процесу — онбординг, політики, вимірювання зростання — перейдіть безпосередньо до розділу [§13 Для техлідів та інженерних менеджерів](#для-техлідів-та-інженерних-менеджерів).

**Щодо страху втрати підтримки коду**: Побоювання, що згенерований ШІ код створює непідтримувані кодові бази, не підтверджується емпірично — розробники, які згодом працюють із цим кодом, не показують суттєвої різниці в часі розвитку чи якості коду (Borg et al., 2025, n=151). Справжніми ризиками є атрофія навичок розробників та надмірне делегування завдань ШІ, а не внутрішнє погіршення якості коду для наступного розробника. ([arXiv:2507.00788](https://arxiv.org/abs/2507.00788))

### Наслідки для навчання

Ці дослідження формують основу решти цього посібника:

1. **Правило 70/30** (§5) не є випадковим — воно чітко откаліброване під зони, де ШІ допомагає чи заважає навчанню
2. **Три патерни** нижче відображають ці результати продуктивності
3. **Подолання залежності** (§7) орієнтоване саме на вирішення пастки для початківців

## Три патерни поведінки

Кожен розробник, який використовує ШІ, відноситься до одного з трьох патернів:

| Патерн | Ознаки | Головний ризик | Цей посібник |
|--------|--------|----------------|--------------|
| **Залежний (Dependent)** | Копіює без розуміння, не може відлагодити ШІ-код, тривожність без ШІ | Непридатність до працевлаштування | [§7](#подолання-залежності-патерн-залежний) |
| **Уникаючий (Avoidant)** | Відмовляється від ШІ «з принципів», працює повільніше за колег, не сприймає інструменти | Залишиться позаду ринку | [§8](#освоєння-інструментів-ші-патерн-уникаючий) |
| **Доповнений (Augmented)** | Використовує ШІ критично, розуміє кожну лінійку, знає межі ШІ | Процвітає та зростає | [§9](#оптимізація-вашого-процесу-патерн-доповнений) |

**Траєкторія продуктивності за патернами** (на основі [досліджень з §3](#реальність-продуктивності-з-ші)):

| Патерн | 0-2 тижні | 2-8 тижнів | 6+ місяців |
|--------|-----------|------------|------------|
| Залежний | +50% (ілюзорно) | +20% | -10% (накопичення боргу) |
| Уникаючий | -30% | -20% | 0% (без використання важеля ШІ) |
| Доповнений | +10% | +30-50% | +20-30% (стабільно) |

### Патерн 1: Залежний (Dependent)

**Як ви сюди потрапили**: Почали використовувати ШІ з першого дня навчання, не побудували базові навички, тиск термінів змусив обирати швидкі шляхи (шорткати).

**Пастка**: Ви випускаєте код, який не можете самостійно пояснити. Коли він ламається, ви безпорадні. На технічних співбесідах ви застигаєте від розгубленості.

**Що бачать інтерв'юери на співбесідах:**
- Нездатність написати базові алгоритми на дошці
- Труднощі з відповіддю на запитання «чому ви обрали саме цей підхід?»
- Постійні прохання «підглянути в довідник» щодо фундаментальних концепцій мови

### Патерн 2: Уникаючий (Avoidant)

**Як ви сюди потрапили**: Мислення перфекціоніста чи пуриста, страх «шахрайства», навчання у часи до появи ШІ, недовіра до нових технологій.

**Пастка**: Ви працюєте повільніше за своїх колег. Ви витрачаєте години на рутинні проблеми, які ШІ вирішує за секунди. Ви не вчитеся краще від того, що більше страждаєте над кодом — ви просто стаєте повільнішими та менш ефективними.

**Що бачать команди:**
- Винахід велосипеда без жодної потреби
- Повільне виконання рутинних завдань
- Опір сучасному інструментарію розробки

### Патерн 3: Доповнений (Augmented)

**Як ви сюди потрапили**: Спершу побудували міцний фундамент АБО свідомо виправили звички з Патернів 1 та 2; ставитеся до ШІ як до інструменту, а не милиці; перевіряєте абсолютно все.

**Перевага**: Ви рухаєтеся швидко І водночас розумієте кожну деталь. Ви використовуєте ШІ для масштабування своїх можливостей, а не для заміни власного мислення.

**Що бачать наймаючі менеджери:**
- Швидке виконання завдань із чітким та логічним поясненням кожної деталі коду
- Здатність працювати як з ШІ, так і повністю без нього
- Доречне використання правильних інструментів під конкретні завдання

## Протокол UVAL

Систематичний підхід до використання ШІ, який дозволяє зберігати та розвивати власну майстерність.

### Огляд

| Крок | Дія | Чому це важливо |
|------|-----|-----------------|
| **U** (Understand First) | Зрозумій спочатку | Дозволяє ставити кращі запитання та одразу помічати помилки моделі |
| **V** (Verify) | Перевір | Гарантує, що ви насправді розібралися, а не просто скопіювали |
| **A** (Apply) | Застосуй | Перетворює пасивне знання на активну навичку через модифікацію коду |
| **L** (Learn) | Вивчи | Допомагає зафіксувати отримані інсайти для довгострокової пам'яті |

---

### U — Understand First (Правило 15 хвилин)

**Це не просто «подумайте 15 хвилин»** — це чіткий структурований протокол:

#### Крок 1: Сформулюйте проблему (2 хвилини)

Опишіть проблему ОДНИМ реченням. Якщо ви не можете цього зробити, ви ще не до кінця розумієте її суть.

```
❌ "Код чомусь не працює"
✅ "Форма входу не показує помилки валідації, коли поле email залишається порожнім"
```

#### Крок 2: Накидайте можливі підходи (5 хвилин)

Запишіть щонайменше 3 можливі шляхи вирішення, навіть якщо ви не впевнені, чи спрацюють вони:

```
1. Додати валідацію на клієнтській стороні за допомогою JavaScript
2. Використати стандартний атрибут `required` в HTML5
3. Додати валідацію на серверній стороні та повертати помилки клієнту
```

Це змушує ваш мозок почати працювати та генерувати рішення до того, як ви запитаєте ШІ.

#### Крок 2.5: Розпізнайте сигнали втоми (30 секунд)

Перед тим як рухатися далі, зупиніться та оцініть свій когнітивний стан:

- **Тривалість сесії**: Працюєте вже понад 30 хвилин поспіль? → Зробіть 5-хвилинну перерву, подумайте про команду `/clear`, щоб скинути контекст.
- **Кількість спроб**: Спробували один і той самий промпт 3+ рази, отримуючи нестабільні результати? → Перейдіть до ручної реалізації.
- **Рівень роздратування**: Відчуваєте тривогу через непередбачувані відповіді ШІ? → Це «втома від ШІ» (стрес від недетермінованості), це нормально — це особливість мінливості інструменту, а не ваша провина.

Цей проміжний чек-поінт запобігає виснаженню від тривалих сесій із дедалі меншою віддачею.

#### Крок 3: Визначте прогалини в знаннях (3 хвилини)

Що саме ви зараз НЕ знаєте?

```
- Я знаю, що мені потрібна валідація, але не знаю, як саме красиво виводити помилки під полями в React.
- Я ніколи раніше не працював з бібліотекою Zod, хоча часто чув про неї.
```

#### Крок 4: І ТІЛЬКИ ТОДІ запитуйте ШІ (5 хвилин)

Тепер ваше запитання до ШІ буде в 10 разів якіснішим та точнішим:

```
❌ "Як мені зробити валідацію поля?"
✅ "Я розробляю форму входу на React. Я хочу:
   1. Валідувати формат email на стороні клієнта.
   2. Показувати помилки безпосередньо під відповідним полем вводу.
   3. Використовувати бібліотеку Zod для опису схеми валідації.

   Я пробував використовувати стандартний HTML-атрибут `required`, але мені потрібні кастомні стилізовані повідомлення про помилки.
   Який підхід вважається найбільш ідіоматичним для React?"
```

Кращі запитання → Якісніші відповіді → Швидше навчання.

#### Налаштування в Claude Code

Додайте до вашого файлу `CLAUDE.md`:

```markdown
## Learning Mode
Before generating code for me, ask:
1. What approaches have I already considered?
2. What specifically am I stuck on?
3. What do I expect the solution to look like?

If I skip these, remind me to think first.
```

### V — Verify (Поясніть це назад)

**Правило**: Якщо ви не можете детально пояснити цей код своєму колезі, значить, ви його ще не засвоїли.

#### Протокол «Гумової качечки» (The Rubber Duck Protocol)

Після того як ШІ згенерував код:

1. Прочитайте кожен рядок коду вголос
2. Поясніть своїми словами, що робить кожна частина
3. Поясніть, ЧОМУ це зроблено саме так (а не просто «що воно робить»)
4. Чітко визначте фрагменти, які вам не до кінця зрозумілі
5. Запитайте ШІ конкретно про ці незрозумілі фрагменти

#### Приклад

ШІ згенерував для вас:
```typescript
const schema = z.object({
  email: z.string().email(),
  password: z.string().min(8)
}).refine(data => data.password !== data.email, {
  message: "Password cannot be email",
  path: ["password"]
});
```

Ваше пояснення:
- Рядок 1: Створює об'єкт схеми валідації Zod.
- Рядки 2-3: Валідує формат email та перевіряє, щоб пароль мав щонайменше 8 символів.
- Рядки 4-6: Додає кастомну валідацію... **зачекайте, а що насправді робить метод `refine`?**

→ Тепер запитайте ШІ конкретно про роботу методу `refine`, замість того щоб просто сліпо скопіювати весь блок коду.

#### Налаштування в Claude Code

Створіть кастомну команду `/explain-back`:

```markdown
# Explain Back

After I accept generated code, help me verify understanding.

## Instructions

1. Show the code I just accepted
2. Ask me to explain what each major section does
3. Correct any misunderstandings
4. If I can't explain it, break it down further

## Example Prompt

"You just accepted this code. Can you explain:
1. What problem does it solve?
2. Why was this approach chosen?
3. What would break if we removed line X?"
```

Див. посилання на [/learn:quiz command](../examples/commands/learn/quiz.md) для більш детальної та комплексної версії.

### A — Apply (Модифікуйте, а не копіюйте)

**Правило**: Ніколи не копіюйте код ШІ в проект у чистому вигляді. Завжди вносьте власні зміни.

#### Чому це працює

Модифікація змушує ваш мозок активно включатися в роботу. Навіть мінімальні зміни вимагають розуміння структури коду:

| Дія | Когнітивне навантаження | Рівень навчання |
|-----|-------------------------|-----------------|
| Сліпий копіпаст | Нульове | Нульове |
| Перейменування змінних | Низьке | Невеликий |
| Додавання граничного випадку | Середнє | Хороший |
| Рефакторинг структури | Високе | Відмінний |

#### Мінімально життєздатні модифікації (Minimum Viable Modifications)

Завжди робіть хоча б ОДНУ з цих дій:

1. **Перейменуйте** — Змініть назви змінних чи функцій, щоб вони ідеально відповідали угодам (naming conventions) вашого проекту.
2. **Переструктуруйте** — Винесіть допоміжну функцію в окремий хелпер, змініть метод ітерації (наприклад, з `forEach` на `map`).
3. **Розширте** — Додайте обробку ще одного граничного випадку, додаткову валідацію або обробку помилок.
4. **Спростіть** — Видаліть зайві фічі чи перевірки, які не потрібні для вашого конкретного завдання.

#### Приклад

ШІ дає вам такий код:
```javascript
function calculateTotal(items) {
  return items.reduce((sum, item) => sum + item.price * item.quantity, 0);
}
```

Ви трансформуєте його:
```javascript
// Додано: явна перевірка типів та обробка граничного випадку з пустим кошиком
function calculateCartTotal(cartItems) {
  if (!Array.isArray(cartItems) || cartItems.length === 0) {
    return 0;
  }
  return cartItems.reduce((total, item) => {
    const itemPrice = Number(item.price) || 0;
    const itemQty = Number(item.quantity) || 0;
    return total + itemPrice * itemQty;
  }, 0);
}
```

Тепер ви взаємодіяли з кодом, додали власні думки, зробили його надійнішим та реально чогось навчилися.

### L — Learn (Зафіксуйте інсайт)

**Це не щоденник роздумів** — їх ніхто не веде довго. Замість цього: автоматична та швидка фіксація.

#### Правило одного інсайту (The One-Thing Rule)

Наприкінці кожної сесії кодування зафіксуйте РІВНО ОДНУ річ, яку ви сьогодні вивчили. Не десять. Одну.

```markdown
## 2026-01-17
**Вивчено**: Метод `refine()` у бібліотеці Zod для крос-польової валідації.
**Контекст**: Для форми входу потрібна була перевірка, щоб пароль не збігався з email.
**На майбутнє**: Використовувати `refine()`, коли умови валідації залежать від кількох полів одночасно.
```

#### Налаштування в Claude Code

Створіть хук завершення сесії:

```bash
# .claude/hooks/bash/learning-capture.sh
# Запитує один вивчений інсайт при завершенні роботи з Claude Code
```

Див. скрипт [examples/hooks/bash/learning-capture.sh](../examples/hooks/bash/learning-capture.sh) для детального налаштування.

Хук автоматично запитає: *«Яку ОДНУ важливу річ ви дізналися під час цієї сесії?»* та автоматично занесе її до логу.

## Claude Code для навчання (а не просто для генерації)

Claude Code має специфічні вбудовані функції, які допомагають у навчанні. Ось як їх налаштувати.

### Почніть звідси: /powerup

Перш ніж налаштовувати щось інше, запустіть у терміналі команду `/powerup`. Це вбудована інтерактивна команда, яка проведе вас через основні можливості Claude Code за допомогою коротких, практичних анімованих уроків. Кожен урок короткий, наочний та орієнтований на те, щоб показати можливості на практиці. Почніть саме з цього, якщо ніколи не проходили структурований онбординг по інструменту.

### Налаштування CLAUDE.md для режиму навчання (Learning Mode)

```markdown
- My level: [beginner/intermediate] on these topics

- Always explain WHY, not just WHAT

- Highlight concepts I should understand deeper
- Point out common mistakes beginners make

## Challenges
- Suggest exercises to reinforce concepts after implementing
- Point out edge cases I should consider
- Ask me to predict output before showing it

## When I Ask for Help
1. First ask what I've already tried
2. Guide me toward the answer before giving it
3. Explain the underlying concept, not just the fix
```

### Тижневий розподіл 70/30 (The 70/30 Weekly Split)

Дотримуйтеся балансу між навчанням та безпосереднім випуском коду:

| Діяльність | Частка часу | Використання ШІ | Чому саме так |
|------------|-------------|-----------------|---------------|
| **Глибоке навчання** (нові концепції) | 70% часу | 30% допомоги ШІ | Самостійна розумова боротьба будує глибокі нейронні зв'язки |
| **Практика/Проекти** (рутина, знайомі навички) | 30% часу | 70% допомоги ШІ | Дозволяє масштабувати та застосовувати те, що ви вже добре вмієте |

> **Наукове обґрунтування**: Цей баланс повністю відповідає [дослідженням продуктивності з ШІ (§3)](#реальність-продуктивності-з-ші), які показують, що ШІ приносить максимальну користь на чітко визначених рутинних завданнях, тоді як навчання нових концепцій вимагає самостійних розумових зусиль, які ШІ не здатний скоротити без втрати якості знань розробника.

#### Приклад тижневої структури розробника:

```
Понеділок:  Вивчення нового React-патерну (мінімум ШІ, глибокий аналіз)
Вівторок:   Вивчення нового React-патерну (мінімум ШІ, самостійні спроби)
Середа:     Застосування патерну в реальному проекті (активне використання ШІ)
Четвер:     Вивчення підходу до тестування (мінімум ШІ)
П'ятниця:   Написання тестів та деплой фічі (активна допомога ШІ)
```

Головне правило: Не використовуйте ШІ інтенсивно, коли вивчаєте НОВІ для себе речі. Використовуйте його на повну силу, коли застосовуєте концепції, які ви вже добре розумієте.

## Подолання залежності (Патерн: Залежний)

**Для розробників Патерну 1 (Залежний)**: Ви занадто довго використовували ШІ як милицю. Ось детальний план, як перебудувати свій фундамент знань.

### Тиждень 1: Період «холодної індички» (Cold Turkey)

**Мета**: Довести собі, що ви здатні писати код повністю самостійно без ШІ.

| Дні | Практична вправа | Тривалість |
|-----|------------------|------------|
| 1-2 | Напишіть невелику фічу ПОВНІСТЮ БЕЗ ШІ | 2 години |
| 3-4 | Відлагодьте помилку, користуючись виключно документацією мови | 1 година |
| 5 | Вголос детально поясніть код, який раніше для вас згенерував ШІ | 30 хвилин |

**Приготуйтеся до того, що робота здаватиметься дуже повільною та виснажливою.** Це нормально. Саме так відбувається реальне навчання вашого мозку.

### Тиждень 2: Контрольоване повернення інструменту

**Мета**: Використовувати ШІ суто як розумного викладача, а не генератора коду.

| Дні | Практична вправа | Роль ШІ |
|-----|------------------|---------|
| 1-2 | Просіть ШІ пояснити концепцію, після чого пишіть код самі | Тьютор (Tutor) |
| 3-4 | Пишіть код спочатку самі, а потім просіть ШІ зробити код-рев'ю | Рецензент (Reviewer) |
| 5 | Порівняйте своє рішення з рішенням ШІ, проаналізуйте різницю | Компаратор (Comparator) |

### Тиждень 3-4: Збалансоване використання

**Мета**: Закріпити критичні звички роботи з ШІ.

Застосовуйте протокол UVAL (§4) до кожної вашої взаємодії:

1. **Understand** (Зрозумій) — 15 хвилин аналізу проблеми до запиту.
2. **Verify** (Перевір) — Поясніть кожну лінійку коду гумовій качечці.
3. **Apply** (Застосуй) — Обов'язково модифікуйте та покращуйте згенерований код.
4. **Learn** (Вивчи) — Записуйте рівно один інсайт після кожної сесії.

### Червоні прапорці того, що ви знову сповзаєте в залежність

| Сигнал тривоги | Негайні дії для виправлення |
|----------------|-----------------------------|
| Копіювання коду без його попереднього прочитання | Зупиніться. Повільно прочитайте кожен рядок до копіювання. |
| Нездатність пояснити власноруч замерджений код | Викличте команду `/explain-back`. |
| Тривога та розгубленість, якщо ШІ тимчасово недоступний | Практикуйте кодування по 30 хвилин щодня без ШІ. |
| Повний провал на базових питаннях співбесід | Тимчасово відключіть ШІ та пишіть прості алгоритми вручну. |

## Освоєння інструментов ШІ (Патерн: Уникаючий)

**Для розробників Патерну 2 (Уникаючий)**: Ви свідомо уникали ШІ. Ось чому це сповільнює вашу кар'єру та як це змінити без шкоди для ваших знань.

### Чому уникання інструментів є реальною проблемою

Сучасний ринок праці кардинально змінився:

- Сучасні команди очікують від розробників високої продуктивності за допомогою ШІ
- Ручне написання абсолютно всього шаблонного коду робить вас неконкурентоспроможними
- Демонстративна відмова від сучасних інструментів часто сприймається менеджерами як професійна негнучкість

Ви не читерите, коли використовуєте ШІ для рутинних справ. Ви просто неефективно витрачаєте свій час (та гроші компанії), коли відмовляєтеся від нього.

### Тиждень 1: Безпечне та комфортне знайомство

**Мета**: Використовувати ШІ для завдань, які не викликають внутрішнього відчуття «шахрайства».

| Завдання | Чому це абсолютно безпечно для навчання | Спробуйте такий промпт |
|----------|-----------------------------------------|------------------------|
| Генерація бойлерплейту | Ніхто не стає розумнішим від написання імпортів та базових класів | «Generate React component boilerplate» |
| Пояснення чужого коду | Раніше ви б шукали це в Google або Stack Overflow | `/explain this codebase` |
| Написання документації | Опис коду словами не є вашою основною технічною навичкою | «Document this function» |
| Генерація тест-кейсів | Тести лише перевірять і закріплять ВАШЕ розуміння роботи коду | «Generate test cases for this function» |

### Тиждень 2: Розширення зон використання

**Мета**: Використовувати ШІ для вирішення завдань, над якими ви раніше довго «застрягали».

| Завдання | Як ви робили це раніше | Сучасний підхід з ШІ |
|----------|------------------------|-----------------------|
| Налагодження помилок | Годинами читали форуми Stack Overflow | «Explain this error and likely causes» |
| Знайомство з новою лібою | Читали сотні сторінок сухої документації | «Show me the key patterns for X» |
| Рефакторинг коду | Довгий та небезпечний ручний перепис | «Refactor for readability, explain changes» |

### Тиждень 3-4: Інтеграція в щоденний процес

**Мета**: ШІ стає звичною та органічною частиною вашого повсякденного робочого процесу.

Застосовуйте протокол UVAL, щоб гарантувати, що ви продовжуєте рости як спеціаліст, а не просто автоматизуєте рутину.

### Зсув ментальної парадигми (Mindset Shift)

**Застаріле мислення**: *«Якщо я користуюся ШІ, значить, я несправжній програміст».*

**Сучасне мислення**: *«ШІ миттєво бере на себе всю нудну рутину та написання шаблонного коду, щоб я міг повністю сфокусуватися на проектуванні архітектури, системному дизайні та вирішенні складних бізнес-проблем».*

Найкращі інженери світу завжди використовують найкращі доступні інструменти. ШІ — це просто надпотужний інструмент у ваших руках.

## Оптимізація вашого процесу (Патерн: Доповнений)

**Для розробників Патерну 3 (Доповнений)**: Ви вже чудово та свідомо використовуєте ШІ. Ось як вам вийти на рівень справжнього майстра (Staff/Principal).

### Просунуті техніки застосування UVAL

#### Прогностичний промптинг (Predictive Prompting)

Перед тим як дозволити ШІ згенерувати код, спробуйте самостійно передбачити оптимальний підхід:

```
Моє припущення: Для цього завдання найкраще підійде метод reduce() з акумулятором.
[Запуск промпту]
Порівняйте згенерований ШІ код зі своїм припущенням — детально проаналізуйте відмінності.
```

#### Навчання через викладання (Teaching Mode)

Використовуйте ШІ як розумного критика, навчаючи його:

```
Я детально поясню тобі, як працюють хуки в React. Твоє завдання — вказати на мої логічні помилки та заповнити прогалини.

Отже, useState зберігає стан, який не втрачається між рендерами...
```

ШІ тут виступає як кваліфікована «гумова качечка», здатна миттєво знаходити помилки у ваших міркуваннях.

#### Компаративний аналіз підходів (Comparative Analysis)

Завжди просіть ШІ надати кілька кардинально різних варіантів вирішення завдання:

```
Show me 3 ways to implement this:
1. Using class components
2. Using hooks
3. Using a state management library

Explain trade-offs of each.
```

Це чудово розвиває ваше архітектурне мислення та розуміння проектування систем.

## Кейс-стаді: Принципи гібридного навчання

Які підходи є найбільш ефективними для навчання разом з ШІ? Академічні дослідження та успішні практики сходяться до однієї спільної моделі.

### На основі академічних досліджень (2023-2025)

Дослідження ефективності навчання за допомогою ШІ демонструють найкращі результати при поєднанні трьох компонентів:

| Компонент системи | Призначення | Що відбувається без нього |
|-------------------|-------------|---------------------------|
| **Людський контроль** | Мотивація, критичний зворотний зв'язок, підзвітність | Учні втрачають фокус, навчання хаотизується |
| **Допомога ШІ** | Миттєві відповіді, нескінченне терпіння, практичне тренування | Повільніша ітерація, менше практики |
| **Прогресивна автономія** | Поступове зменшення контролю в міру зростання навичок | Учні так і не стають повністю самостійними |

Головний висновок вчених: **ШІ ідеальний для рутинної практики та швидких відповідей**, тоді як **людина незамінна для мотивації, виставлення планки якості та критичного оцінювання**.

### Реальний приклад: Французька освітня платформа Méthode Aristote

Французька освітня платформа для середніх та старших класів застосовує ці принципи в масштабах всієї країни:

**Їхня робоча модель**:
- Персональний людський тьютор = відповідальність + критичний розбір помилок
- Практичні вправи на базі ШІ = структурована практика з перевіреним експертами контентом
- Один і той самий тьютор протягом тривалого часу = стабільний зв'язок та розуміння реального прогресу учня

**Корисні принципи для розробників:**

| Принцип Aristote | Еквівалент для розробника |
|-------------------|---------------------------|
| Персональний тьютор | Ментор/Tech Lead + регулярні сесії код-рев'ю |
| Верифікований контент | ШІ + сувора перевірка лінтерами, тестами та колегами |
| Рівнева система розвитку | Створення проектів з поступовим зростанням складності |
| Стабільні робочі стосунки | Постійний та чесний фідбек від однієї команди розробників |

**Їхня філософія**: *«Exigence, bienveillance, équité»* (Вимогливість, доброзичливість, справедливість)

Застосовано до розробки коду:
- **Вимогливість**: Ніколи не приймайте код, роботу якого ви не можете детально пояснити.
- **Доброзичливість**: ШІ — це просто інструмент розробки, користуйтеся ним без жодного почуття провини.
- **Справедливість**: Кожен розвивається у власному темпі — ніколи не порівнюйте свій початок із чужою серединою кар'єри.

→ [methode-aristote.fr](https://www.methode-aristote.fr/)

### Створення власної системи підтримки

Навіть якщо у вас немає персонального ментора, ви можете самостійно побудувати таку структуру:

| Ваша потреба | Практичне вирішення |
|--------------|---------------------|
| Підзвітність та контроль | Щотижневі зустрічі з колегою або ментором для обговорення прогресу |
| Критичний фідбек | Суворі код-рев'ю, активна практика парного програмування |
| Структурована практика | Свідоме виконання вправ (deliberate practice), а не лише виконання робочих тікетів |
| Відстеження прогресу | Ведення журналу навчання, регулярна самостійна оцінка навичок |

Поєднання **людської підзвітності та практики з ШІ** дає значно вищі результати, ніж використання будь-якого з цих підходів окремо. Це повністю підтверджує [дослідження успішних команд розробників](#чому-одні-команди-отримують-результати-а-інші-ні): критично важливими є чіткі правила, суворі стандарти рев'ю та розвинена система менторства.

## Де ви перебуваєте на кривій впровадження агентів?

> **Цільова аудиторія**: Розробники, які вже активно використовують Claude Code та прагнуть об'єктивно оцінити рівень своєї майстерності — не для початківців (їм краще скористатися 30-денним планом нижче).

Перш ніж обрати подальший шлях розвитку, визначте свою поточну позицію. Ніколя Мартіньоль (Nicolas Martignole, головний інженер у Back Market) у березні 2026 року запропонував шкалу зрілості з 6 рівнів, яка чудово відображає реальну роботу з Claude Code. Рівні 3-5 — це зона, якій присвячено більшу частину матеріалів цього посібника.

| Рівень | Профіль | Основний сигнал |
|--------|---------|-----------------|
| **0** | Взагалі не використовує ШІ-інструменти розробки | Максимум використовує звичайні чат-боти в браузері, нічого не інтегровано в термінал чи IDE |
| **1** | Інструменти автодоповнення коду | Cursor, Copilot, Windsurf — але виключно на рівні розумного inline-автокомпліту |
| **2** | Зовнішні LLM, ручний копіпаст | Запити в ChatGPT або Claude у вікні браузера, самостійне копіювання коду в редактор |
| **3** | Базовий користувач Claude Code | Робота в режимі Plan, прості точкові промпти, ретельний ручний перегляд кожної зміни |
| **4** | Делегатор цілих етапів | Повна передача ШІ цілих етапів розробки (дослідження, проектування, написання коду, тести) — власноруч пише менше 10% коду |
| **5** | Контекст-инженер (Context Engineer) | Свідоме проектування файлів `CLAUDE.md`, тонке налаштування суб-агентів, MCP-серверів та кастомних хуків |
| **6** | Оркестратор систем (Orchestrator) | Проектування та координація складних графів агентів, циклів зворотного зв'язку та розподілених ШІ-систем |

**Питання для швидкої самодіагностики:**
- Чи можете ви спокійно залишити Claude Code працювати над складною фічею в окремій гілці на 20+ хвилин, не контролюючи його щомиті? → Рівень 4+
- Чи пишете ви файл `CLAUDE.md` до початку роботи над проектом, а не після її завершення? → Рівень 5
- Чи створили ви власного кастомного агента або складний хук за останній місяць? → Рівень 5-6
- Чи є вашим основним продуктом проектування промптів та архітектури систем, а не написання рядків коду? → Рівень 6

Якщо ваші відповіді відповідають Рівню 3 або нижче: 30-денний план розвитку нижче — ваш ідеальний наступний крок. Якщо ви вже на Рівнях 4-6: сміливо переходьте до розділів [Context Engineering](../core/context-engineering.uk.md), [Agent Patterns](../../examples/agents/) або [MCP Ecosystem](../ecosystem/mcp-servers-ecosystem.uk.md).

## 30-денний план розвитку

Конкретний практичний шлях переходу від будь-якого рівня до статусу високоефективного Доповненого розробника (Augmented Developer).

### Тиждень 1: Фундамент

**Основний фокус**: Побудова (або відновлення) ключових навичок кодування без значного залучення ШІ.

| День | Практична активність | Частка використання ШІ |
|------|----------------------|-----------------------|
| 1-2 | Створення простої фічі ПОВНІСТЮ БЕЗ ШІ | 0% |
| 3 | Рев'ю: Детальне пояснення свого коду вголос якійсь речі | 0% |
| 4-5 | Рефакторинг коду за допомогою ШІ як критика (не генератора) | 20% |
| 6 | Налагодження та пошук багів без допомоги ШІ | 0% |
| 7 | Заслужений відпочинок та осмислення результатів | — |

**Критерій успіху**: Ви можете чітко та впевнено пояснити кожен рядок коду, який написали за тиждень.

### Тиждень 2: Свідоме розуміння

**Основний фокус**: Використання ШІ з обов'язковим та жорстким розумінням результатів.

| День | Практична активність | Частка використання ШІ |
|------|----------------------|-----------------------|
| 1-2 | Генерація коду за допомогою ШІ з детальним поясненням КОЖНОГО рядка | 40% |
| 3 | Ви пишете код самостійно, ШІ вказує на помилки, ви їх самі виправляєте | 30% |
| 4-5 | ШІ докладно роз'яснює вам нову концепцію, ви реалізуєте її руками | 40% |
| 6 | Проведення міні-іспиту для себе за всіма темами тижня | 10% |
| 7 | Відпочинок та рефлексія | — |

**Критерій успіху**: Ви можете впевнено, свідомо та безпомилково вносити зміни у згенерований ШІ код.

### Тиждень 3: Критичний аналіз

**Основний фокус**: Свідомий аналіз пропозицій ШІ, пошук їхніх помилок та вивчення обмежень інструменту.

| День | Практична активність | Частка використання ШІ |
|------|----------------------|-----------------------|
| 1-2 | Запит кількох різних підходів у ШІ, самостійний вибір найкращого | 60% |
| 3 | Свідомий пошук прихованих багів та неточностей у згенерованому ШІ коді | 50% |
| 4-5 | Реалізація складної комплексної фічі з активною допомогою ШІ | 60% |
| 6 | Детальне пояснення архітектури всієї фічі гумовій качечці | 10% |
| 7 | Відпочинок | — |

**Критерій успіху**: Ви чітко помічаєте та виправляєте помилки, яких припускається ШІ під час роботи.

### Тиждень 4: Рівень «Доповнений» (Augmented)

**Основний фокус**: Максимальна швидкість розробки за умови стовідсоткового розуміння кожної деталі коду.

| День | Практична активність | Частка використання ШІ |
|------|----------------------|-----------------------|
| 1-5 | Робота над реальним проектом із жорстким дотриманням протоколу UVAL | 70% |
| 6 | Фінальне рев'ю: Чого конкретно ви навчилися за цей тиждень? | 10% |
| 7 | Планування нових цілей навчання на наступний місяць | — |

**Критерій успіху**: Ви розробляєте завдання в рази швидше, чудово розуміючи кожну деталь створеної системи.

## Для техлідів та інженерних менеджерів

> **Цільова аудиторія**: Інженерні менеджери, техліди, старші розробники (seniors), відповідальні за менторство та розвиток початківців.
>
> **Проблема**: Решта матеріалу посібника орієнтована на індивідуального розробника. Цей розділ створений для тих, хто безпосередньо відповідає за створення умов, у яких формуються (або руйнуються) корисні інженерні звички команди.

Протокол UVAL чудово вирішує індивідуальну проблему розробника. Проте на рівні компанії завдання звучить інакше: як спроектувати умови, за яких початківці *самі хотіли б* думати перед написанням промптів, де якість коду ніколи не приноситься в жертву швидкості, а згенерований ШІ технічний борг не накопичується непомітно в масштабах всієї команди?

### Імператив правильного онбордингу

Надання доступу до ШІ без попереднього навчання дає вкрай низькі результати. Дослідження Create Future 2025 року показало, що джуніор-розробники без спеціальної підготовки отримували лише 14-42% економії часу на завданнях. Після проходження навіть короткого інструктажу цей показник злітав до 35-65%. Інструмент сам по собі не вчить ним користуватися.

**Структурований онбординг набагато кращий за простий підхід «ось твоя ліцензія, працюй»:**

| Тиждень | Основний фокус | Чого слід уникати |
|---------|----------------|-------------------|
| **1** | Знайомство з кодовою базою без ШІ — оцінка базових навичок | Надання повного доступу до Copilot/Cursor з першого ж дня |
| **2** | Перші прості фічі пишуться руками, ШІ виступає виключно як рецензент | Використання ШІ як генератора коду до того, як видно реальний рівень новачка |
| **3** | Знайомство з протоколом UVAL + спільні сесії парного програмування | Повністю автономне використання ШІ початківцем без контролю |
| **4+** | Повноцінна робота з ШІ за умови щотижневої перевірки рівня розуміння коду | Використання суто швидкості випуску фіч (velocity) як єдиної метрики успіху |

Перший тиждень роботи без ШІ — це не покарання для новачка. Це калібрування. Вам необхідно чітко побачити реальний рівень знань розробника до того, як ШІ почне маскувати всі його професійні прогалини. Джуніор, який відчуває труднощі на першому тижні, потребує зовсім іншого менторства, ніж той, хто впевнено пише код руками — і ви ніколи не зможете їх розрізнити, якщо вони обидва почнуть використовувати ШІ з першої хвилини онбордингу.

### Вимірювання того, що насправді має значення

Швидкість розробки (velocity) — це оманливий запізнілий показник. Він абсолютно нічого не говорить про розрив у навичках, який тихо утворюється під капотом команди.

**Метрики, що відображають реальне професійне зростання розробника:**

| Метрика | Як саме її виміряти на практиці | Червоний прапорець |
|---------|--------------------------------|---------------------|
| Здатність детально пояснити свій код на рев'ю | Запитайте: «Проведи мене крок за кроком через свій підхід» | «Ну, так мені запропонував написати ШІ...» |
| Самостійне налагодження багів | Виміряйте час, який розробник витрачає на вирішення блокерів | Повна нездатність зробити крок без підказок ШІ |
| Прогнозування результатів коду | Запитайте: «Що саме зробить цей рядок коду?» перед запуском | Нездатність відповісти без безпосереднього тестування |
| Пропозиція альтернативних рішень | Під час обговорення дизайну чи архітектури системи | Сліпе погодження з першим виданим варіантом ШІ |
| Виявлення помилок у коді ШІ | Оцінка якості коментарів до PR колег та ШІ | Повна відсутність критичного аналізу видачі моделі |

**Питання для щотижневого аудиту зростання** (5 хвилин на ретроспективі, у будь-якому форматі):

> «Яку саме річ ти цього тижня зрозумів максимально глибоко на концептуальному рівні — а не просто випустив у продакшн?»

Якщо розробник не може дати чіткої відповіді два тижні поспіль — це серйозний сигнал для вас, що потрібно сповільнити темп.

### Масштабовані моделі менторства

Класична модель наставництва 1:1 (один досвідчений сеньйор на одного джуніора) фізично не здатна масштабуватися в командах, де більше 5-10 осіб. Ці три підходи чудово вирішують цю проблему:

**1. Ротаційне парне кодування (сесії по 2 години)**
Два джуніор-розробники працюють над завданням разом за допомогою ШІ. Головне жорстке обмеження: жоден з них не має права прийняти код від ШІ, якщо не може детально пояснити його логіку своєму партнеру. Будь-які суперечки щодо архітектурного *«чому»* ескалюються на старшого інженера. Витрати: 2 години на тиждень на кожного джуніора, мінімум залучення дорогого часу сеньйорів.

**2. Архітектурний «гарячий стілець» (15 хвилин на тиждень)**
Будь-який розробник-початківець може забронювати короткий 15-хвилинний слот із сеньйором, щоб детально пояснити логіку прийнятого ним архітектурного рішення. Старший інженер дає рівно один ключовий фідбек. Без перегляду самого коду — аналізується виключно логіка вибору рішення (*«why»*). Це чудово масштабується на будь-яку кількість початківців і змушує їх активно розвивати архітектурне мислення, замість сліпого копіювання рішень.

**3. Спільна розробка та підтримка файлу CLAUDE.md**
Джуніори самостійно пропонують нові доповнення та правила до командного файлу `CLAUDE.md`. Будь-які пропозиції мають базуватися на реальних помилках чи успішних практиках, з якими вони зіткнулися в роботі цього тижня. Старші інженери переглядають пропозиції та затверджують їх із поясненням причин. Це стимулює постійну рефлексію розробників та допомагає будувати єдині стандарти використання ШІ в команді.

### Керуючі метрики на рівні всієї команди

Розділ «Вимірювання того, що насправді має значення» описує індивідуальні сигнали росту розробника. Цей розділ присвячений показникам, на які ви повинні дивитися щотижня та щомісяця, щоб ефективно керувати всією командою розробки, а не просто оцінювати окремих людей.

Ми виділяємо два рівні метрик, кожен з яких має своє чітке призначення.

**Рівень 1 — Здоров'я постачання коду (на основі стандартів DORA)**

| Метрика | Що саме вона вам показує |
|---------|-------------------------|
| Deployment Frequency (Частота деплоїв) | Чи випускаємо ми код стабільно та рівномірно, чи великими небезпечними порціями? |
| Cycle Time (Час циклу від комміту до деплою) | На якому саме етапі робота найчастіше зупиняється або буксує? |
| Bug Escape Rate (Рівень пропущених багів) | Яка саме частка багів проходить через наші фільтри та потрапляє до кінцевих користувачів? |

Ці метрики є класичними промисловими стандартами. Відстежуйте їх незалежно від того, використовуєте ви ШІ чи ні. Проте в епоху ШІ їх самих стає критично недостатньо.

**Рівень 2 — Якість впровадження ШІ**

| Метрика | Як саме її правильно виміряти на практиці |
|---------|------------------------------------------|
| % PR з підтримкою ШІ, перевірених із повним розумінням коду | Випадкова вибіркова перевірка: попросіть автора детально пояснити логіку конкретного блоку в 1 з 5 PR джуніорів |
| Час перевірки PR (з ШІ проти написаних вручну) | Час від статусу «готовий до рев'ю» до мерджу, детально сегментований за походженням коду |
| Рівень успішного проходження перевірки розуміння коду | Відстежуйте, як часто на запитання «проведи мене через цей код» ви отримуєте чітку відповідь проти спроб уникнути конкретики |

Ці три показники чітко дадуть вам зрозуміти: чи використовує ваша команда ШІ для того, щоб рухатися швидше з глибоким розумінням коду, чи просто сліпо схвалює результати видачі моделей та тоннами відвантажує у ваш проект технічний борг розуміння.

**Пастка швидкості (The Velocity Trap)**

Команди, які активно використовують ШІ, часто надзвичайно швидко досягають найвищих показників за шкалою DORA (high performer). Частота деплоїв стрімко зростає, час циклу скорочується. Зовні це виглядає як фантастичний успіх розробки. Проте це ілюзія, якщо показники Рівня 2 паралельно стрімко деградують. Швидкість не є показником збереження навичок та якості знань, коли більшу частину коду пише ШІ. Команда може дедалі швидше закривати спринти, але при цьому з кожним місяцем все менше розуміти пристрій власної кодової бази. Обов'язково аналізуйте обидва рівні метрик разом, а не кожен окремо.

**Щотижневий ранковий ритуал по понеділках (3 цифри, 5 хвилин)**

1. Частота деплоїв за цей тиждень порівняно з минулим.
2. Кількість відкритих PR, які висять без дій понад 24 години.
3. Кількість багів, що просочилися до кінцевих користувачів цього тижня.

Якщо будь-який із цих трьох показників демонструє негативний тренд два тижні поспіль — це серйозний привід для детального внутрішнього розслідування, а не привід негайно ламати чинні процеси розробки. Важливі довгострокові патерни поведінки системи, а не окремі випадкові коливання точок на графіку.

Для отримання повної системи з дашбордами та налаштуваннями лімітів тривоги зверніться до посібника `ops/team-metrics.md`.

### Правила використання ШІ на рівні всієї команди (CLAUDE.md для команд)

Індивідуальні правила у файлі `CLAUDE.md` (§6) орієнтовані на одного розробника. Правила використання ШІ на рівні всієї команди мають бути прописані в кореневому файлі `CLAUDE.md` вашого спільного репозиторію. Зробіть їх короткими та лаконічними, щоб розробники реально їх читали та дотримувалися:

```markdown
## Team AI Usage Policy

### Required before using AI on a feature
- Write the function signature yourself
- Write at least one test case before asking AI to implement

### Required after AI generates code
- All AI-generated code undergoes the same code review as human code
- Reviewer asks: "Can you explain this section?" for junior PRs — not optional

### Prohibited patterns
- Accepting AI changes without reading the diff
- AI-generated code in security-critical paths without explicit senior sign-off
- Using "AI wrote it" as explanation for any architectural decision in a PR
```

Почніть із мінімального набору правил. Додавайте нові обмеження лише тоді, коли бачите стійкий негативний патерн поведінки в команді. Величезний шестисторінковий регламент, який ніхто ніколи не читає, набагато гірший за три прості правила, які реально змінюють культуру розробки.

|-------------------|-------------------------|-----------------------------|

### Особливості роботи в регульованих галузях (Regulatory Exposure)

Для команд, які випускають програмне забезпечення для сфер охорони здоров'я, фінансів або державних систем, накопичення боргу розуміння коду є не просто ризиком для якості продукту — це прямий та серйозний юридичний ризик порушення вимог комплаєнсу.

**Закон ЄС про ШІ (EU AI Act)** класифікує медичні системи на базі ШІ як системи з високим рівнем ризику. Жорсткі вимоги щодо обов'язкового значущого людського нагляду (meaningful human oversight) діють для моделей загального призначення з 2 серпня 2025 року та стають повністю обов'язковими з 2 серпня 2026 року (для медичного обладнання — з серпня 2027 року). Порушення вимог цього законодавства тягне за собою колосальні штрафи — аж до 6% від глобального річного обороту компанії. Вимога закону щодо «значущого людського нагляду» за результатами роботи ШІ накладає на компанію пряме юридичне зобов'язання реально розуміти логіку роботи всього коду, який ви постачаєте на ринок — просте виправдання *«так написала модель»* юридично не відповідає стандартам безпеки.

**Проект керівництва FDA від січня 2025 року** щодо програмного забезпечення медичних пристроїв з підтримкою ШІ вимагає обов'язкового ведення специфікації матеріалів ШІ (AI Bill of Materials, AIBOMs), детального документування походження даних (data lineage) та наявності планів постмаркетингового моніторингу. Оновлене керівництво з кібербезпеки від червня 2025 року додає жорсткі вимоги до прозорості сторонніх компонентів. Команда, яка не здатна детально пояснити поведінку та логіку роботи згенерованого ШІ коду під час подання документів до FDA, гарантовано не зможе пройти сертифікацію відповідності цим стандартам.

**Практичний висновок для техлідів**: Якщо ваша команда розробляє продукт у суворо регульованій сфері, вимога «поясни мені логіку роботи цього коду» на етапі рев'ю є не просто корисною педагогічною вправою для початківців — це пряма та обов'язкова юридична вимога до документування продукту. Рецензенти, які сліпо схвалюють згенерований ШІ код, створюють величезні юридичні зобов'язання та фінансові ризики для всієї компанії, а не лише технічні проблеми в коді. Обов'язково зафіксуйте це правило в командній політиці використання ШІ.

## Чек-лист «червоних прапорців»

Основні тривожні сигнали того, що ви починаєте втрачати кваліфікацію та впадати в повну залежність від ШІ, а також кроки для термінового виправлення ситуації:

| Червоний прапорець | Що насправді відбувається | Негайні практичні дії для виправлення |
|--------------------|---------------------------|---------------------------------------|
| Ви взагалі не можете почати роботу над завданням без ШІ | Ви повністю передоручили ШІ найважливіший етап декомпозиції проблем | Щодня виділяйте 30 хвилин на проектування та кодування повністю без ШІ |
| Ви абсолютно не розумієте логіку згенерованого ШІ коду | Ви просто копіюєте чужі рішення, зупинивши власний професійний розвиток | Жорстко викликайте команду `/explain-back` на абсолютно КОЖНОМУ блоці коду |
| Ви не здатні самостійно відлагодити помилки в коді ШІ | Ви ніколи на практиці не вчилися мистецтву системного дебагінгу коду | Навмисно зламайте локально свій код та спробуйте знайти помилку суто по логах вручну |
| Ви відчуваєте тривогу та безпорадність, якщо ШІ відключено | У вас сформувалася сильна емоційна та професійна залежність від інструменту | Нагадуйте собі, що ШІ — це лише інструмент, а не ваш мозок. Практикуйте роботу без нього |
| Ви постійно «завалюєте» технічні співбесіди на простих базах | Ваші фундаментальні знання сильно атрофувалися за час використання ШІ | Свідомо тренуйтеся вирішувати класичні алгоритмічні завдання на дошці без ШІ |
| Ви завжди запитуєте ШІ «як», але ніколи не питаєте «чому» | Ви використовуєте інструмент виключно на поверхневому рівні | Змушуйте себе завжди ставити запитання: «Чому саме цей підхід тут є оптимальним?» |
| Абсолютно всі ваші рішення виглядають шаблонно та однаково | ШІ має свої фіксовані паттерни, і ви сліпо переймаєте їх, обмежуючи кругозір | Самостійно вивчайте та розбирайте різноманітні архітектурні реалізації в опенсорсі |
| Завдання здається простим, але ви не можете детально його розібрати | **Ефект розриву сприйняття** — користувачі ШІ оцінюють завдання як простіші, показуючи на 17% гірші результати ([Shen & Tamkin 2026](https://arxiv.org/abs/2601.20245)) | Після успішного виконання кожного завдання детально розберіть та поясніть його логіку без підглядань у код |
| Ви проводите довгі сесії кодування без жодних перерв | **Втома від сесії** — однакові промпти дають різні результати, накопичуючи внутрішню тривогу | Встановіть жорсткі ліміти: 30 хвилин роботи, максимум 3 спроби генерації, після чого перехід на ручний код |

### Щотижневий самоаудит

Кожну п'ятницю ввечері чесно запитуйте себе:

1. Яку саме важливу річ я дізнався та глибоко зрозумів цього тижня, чого не знав раніше?
2. Чи зміг би я виконати всю свою роботу цього тижня, якби в мене взагалі не було доступу до ШІ?
3. Чи розумію я кожну лінійку коду, яку за останні 5 днів відправив у головну гілку проекту?
4. Чи став я працювати швидше, ніж минулого місяця? Чи став я при цьому розумнішим та досвідченішим як інженер?

Якщо ви стали працювати швидше, але не стали при цьому розумнішими — ви впевнено будуєте небезпечну професійну залежність.

### Досвід ІТ-спільноти

Звіти практиків про реальне використання інструментів дають відмінне емпіричне підтвердження теоретичних моделей. Croce (2026)[^croce2026] детально документує колосальне зростання швидкості вирішення локальних алгоритмічних завдань (90 секунд у Claude Code проти в середньому 60 хвилин у людини на завданнях Advent of Code), проте виділяє серйозні компроміси в командній роботі під час індивідуального проходження челенджів: різке зниження залученості команди, менше живих творчих дискусій та помітне збіднення спектру обговорюваних підходів до проектування.

**Важливе застереження**: Ці висновки базуються на індивідуальних звітах (N=1) в умовах проходження змагань із конкурентного програмування (Advent of Code), а не на великих рецензованих дослідженнях чи репрезентативних робочих процесах реального продакшн-девелопменту. Помічене зниження рівня колаборації може бути особливістю суто індивідуальних змагань, а не загальним правилом командних воркфлоу розробки.

[^croce2026]: Steve Croce, ["What I Learned Challenging Claude to a Coding Competition"](https://www.anaconda.com/blog/challenging-claude-code-coding-competition), Anaconda Blog, 16 січня 2026 року. Погляд Field CTO компанії Anaconda на результати 12-денного змагання людини та Claude Code на задачах Advent of Code. Зафіксовані метрики: Claude в середньому 90 секунд на завдання, людина — 60 хвилин, жодного ручного налагодження до 6-го дня змагань. Примітка: дослідження за участю одного розробника на алгоритмічних пазлах, а не на реальному продакшн-девелопменті.

## Швидка довідкова картка

### Суть протоколу UVAL

```
U — UNDERSTAND FIRST (Зрозумій спочатку)
    Сформулюй проблему → Опиши варіанти → Знайди прогалини → Тільки тоді пиши ШІ

V — VERIFY (Перевір)
    Повільно прочитай кожен рядок → Поясни логіку вголос качечці → Запитай ШІ про темні плями

A — APPLY (Застосуй)
    Ніколи не копіюй сліпо → Перейменуй / Переструктуруй / Розшир / Спрости код під себе

L — LEARN (Вивчи)
    Визнач рівно один головний інсайт сесії → Запиши його в лог → Періодично повторюй
```

### Золоте правило 70/30

```
Вивчення нового:  70% розумових зусиль та боротьби, 30% допомоги ШІ
Застосування знань: 30% розумових зусиль, 70% активного масштабування через ШІ
```

### Щоденний мінімум свідомого інженера

```
☐ 15 хвилин: Напишіть щось корисне повністю вручну без жодної допомоги ШІ
☐ 5 хвилин: Вголос детально розберіть та поясніть логіку роботи одного блоку коду
☐ 1 хвилина: Чесно зафіксуйте у свій лог рівно один вивчений сьогодні інсайт
```

### Корисні команди Claude Code для навчання

```
/explain              — Детально розібрати та пояснити логіку існуючого коду
/learn:quiz           — Влаштувати собі міні-іспит для перевірки розуміння коду
/learn:teach <topic>  — Покроково та з прикладами вивчити абсолютно нову тему
/learn:alternatives   — Порівняти кілька різних підходів із глибоким розбором компромісів
```
