## 1. Локальне vs Спільне: Розподіл управління

Найбільша помилка в корпоративному управлінні ШІ — застосування однакових правил до всього. Локальне використання розробником та спільна робота над репозиторієм мають фундаментально різні профілі ризику.

### 1.1 Матриця ризиків

| Вимір | Локальне використання | Спільне використання |
|-----------|-------------|--------------|
| **Витік даних** | Власні файли розробника | Дані клієнтів, спільні кодові бази, секрети |
| **Зона впливу** | Одна машина | Весь репозиторій, CI/CD, продакшн |
| **Підзвітність** | Індивідуальна | Команда / організація |
| **Відтворюваність** | Сесія завершується, історія зникає | Потрібен повний аудиторський слід |
| **Область комплаєнсу** | Зазвичай відсутня | SOC2, ISO27001, HIPAA (якщо застосовно) |
| **Дрейф конфігурацій** | Особисті вподобання розробника | Узгодженість у команді є критично важливою |

### 1.2 Що ви можете і чого не можете контролювати

**Ви МОЖЕТЕ контролювати** (через доданий до репозиторію конфіг):
- Які MCP-сервери є схваленими (`settings.json` у репозиторії)
- Які інструменти може використовувати Claude (`permissions.deny`)
- Що написано у файлі CLAUDE.md щодо конвенцій проєкту
- Скрипти хуків, які запускаються до/після використання інструментів (pre/post tool use)
- Шлюзи CI/CD, які перевіряють згенерований ШІ код

**Ви НЕ МОЖЕТЕ безпосередньо контролювати**:
- Які особисті файли `~/.claude/settings.json` мають розробники
- Які моделі вони використовують з особистими API-ключами
- Що вони роблять в особистих проєктах поза вашими репозиторіями
- Вміст пам'яті / сесій між робочими сеансами

**Практичний висновок**: Фокусуйте управління на тому, що додається до ваших репозиторіїв та розгортається у спільних середовищах. Особистий робочий процес розробника є його власною відповідальністю.

### 1.3 Фреймворк прийняття рішень: Коли впроваджувати управління

Не все потребує жорсткого контролю. Застосовуйте засоби управління пропорційно ризикам.

```
Що саме ви регулюєте?
│
├─ Особистий робочий процес (локальний, тимчасовий код)
│   └─ Мінімальний контроль: рекомендації в CLAUDE.md + базові хуки
│
├─ Кодова база команди (спільний репозиторій, не продакшн)
│   └─ Стандартний контроль: спільний settings.json + реєстр MCP + PR-шлюзи
│
├─ Продакшн-система (орієнтована на клієнтів, реальні дані)
│   └─ Суворий контроль: повна конфігурація рівнів + процес схвалення + аудиторський лог
│
└─ Регульоване середовище (HIPAA, SOC2, PCI, фінанси)
    └─ Регульований контроль: все вищезазначене + комплаєнс-аудит
```

## 2. Хартія використання ШІ

Хартія використання відповідає на фундаментальне запитання: "Що нам дозволено робити з Claude Code в нашій компанії?". Без неї кожна команда розробки буде відповідати на це запитання по-своєму, створюючи неконтрольовані та неузгоджені ризики.

Це спрощена версія хартії. Повну версію хартії з юридичними аспектами див. у [Whitepaper #11: Enterprise AI Governance](../../whitepapers/en/11-enterprise-ai-governance.qmd) (коли стане доступним).

### 2.1 Лаконічний шаблон хартії

Скопіюйте цей шаблон у файл `docs/ai-usage-charter.md` вашої організації та адаптуйте під власні потреби:

```markdown
# Хартія використання інструментів кодування на базі ШІ

**Застосовується до**: Claude Code (та будь-яких асистентів кодування на базі ШІ)
**Дата набрання чинності**: [ДАТА]
**Власник політики**: Engineering Lead / CTO
**Періодичність перегляду**: Щоквартально

---

## Схвалені інструменти

| Інструмент | Область застосування | Класифікація даних |
|------|-------|---------------------|
| Claude Code (Pro/Team/Enterprise) | Усі види розробки | До CONFIDENTIAL включно |
| Claude Code (особисті акаунти) | Тільки особиста розробка | Лише PUBLIC/INTERNAL |
| [Інші схвалені інструменти] | [Область] | [Класифікація] |

---

## Правила класифікації даних

| Класифікація | Приклади | Дозволено з Claude Code? |
|----------------|----------|--------------------------|
| **PUBLIC** | Відкритий код (Open Source), публічна документація | Так, без обмежень |
| **INTERNAL** | Внутрішні інструменти, нечутливий код | Так, зі стандартною конфігурацією |
| **CONFIDENTIAL** | Внутрішні комерційні таємниці, регульована інтелектуальна власність (IP) | Так, лише на тарифі Enterprise |
| **RESTRICTED** | Персональні дані клієнтів (PII), дані платіжних карток (PCI), медичні дані (PHI), облікові дані | Ні — ніколи в контексті ШІ без офіційного дозволу юридичного відділу або відділу комплаєнсу |

**Суворе правило**: Дані класу RESTRICTED ніколи не повинні потрапляти у вікно контексту ШІ. Ні в промптах, ні у файлах, які читає Claude, ні як приклади. Налаштуйте `permissions.deny`, щоб заблокувати доступ до файлів із обмеженим доступом.

---

## Схвалені сценарії використання

- Дописування коду, рев'ю, рефакторинг
- Генерація тестів
- Створення чернеток документації
- Налаштування та аналіз першопричин помилок (Debugging)
- Аналіз архітектури (тільки внутрішніх систем)
- Написання CLI-скриптів та автоматизація

---

## Заборонені сценарії використання

- Обробка даних платіжних карток (область дії PCI)
- Генерація коду, який працює з необробленими медичними даними (PHI) без перевірки безпеки
- Автономний деплой у продакшн без затвердження людиною
- Використання особистих ШІ-акаунтів для роботи з даними CONFIDENTIAL або вище
- Передача реальних даних клієнтів у промптах як прикладів
```

## 3. Процес управління MCP

Індивідуальна перевірка MCP (5-хвилинний аудит) описана в [security-hardening.uk.md §1.1](./security-hardening.uk.md#11-mcp-vetting-workflow). Цей розділ присвячений організаційному процесу: як нові сервери MCP отримують схвалення, розгортаються та контролюються у вашій команді.

### 3.1 Робочий процес схвалення (Approval Workflow)

```
Розробник хоче додати новий MCP-сервер
        │
        ▼
[1] Подання запиту на MCP
    - Назва, URL-адреса джерела, версія
    - Запропонований сценарій використання
    - Обсяг даних (до чого сервер матиме доступ?)
        │
        ▼
[2] Рев'ю безпеки (Tech Lead + опціонально команда безпеки)
    - 5-хвилинний аудит MCP (див. security-hardening.uk.md)
    - Перевірка: зірок >50, свіжі коміти, немає небезпечних прапорців
    - Перевірка: відсутність CVE (пошук в NVD + GitHub Security Advisories)
    - Класифікація ризику: LOW / MEDIUM / HIGH
        │
     ┌──┴──┐
   LOW   MED/HIGH
     │      │
     ▼      ▼
Схвалити   Розширене рев'ю
           (2 тижні тестування в пісочниці)
           + погодження від команди безпеки
        │
        ▼
[3] Додавання до Реєстру схвалених інструментів
    - Фіксація точної версії
    - Документування схваленої області доступу
    - Встановлення дати закінчення дозволу (6 місяців)
        │
        ▼
[4] Розгортання через спільний settings.json
    - Збереження у репозиторії
    - Заборона локальних перевизначень для схвалених MCP
        │
        ▼
[5] Моніторинг та періодичний повторний огляд
    - Перевірка безпеки кожні 30 днів
    - Повторне затвердження оновлень (patch: авто, minor+: вручну)
    - Щоквартальний повний аудит реєстру
```

### 3.2 Формат реєстру MCP

Підтримуйте реєстр схвалених MCP у файлі `.claude/mcp-registry.yaml` у репозиторії спільної конфігурації вашої команди:

```yaml
# .claude/mcp-registry.yaml
# Схвалені сервери MCP для [Назва Організації]
# Остання зміна: 2026-03-10
# Хто перевірив: [Ім'я, посада]

metadata:
  review_cycle: quarterly
  next_review: "2026-06-10"
  owner: "platform-team@company.com"

approved:
  - name: context7
    version: "1.2.3"
    source: "https://github.com/context7/mcp-server"
    approved_by: "john.doe@company.com"
    approved_date: "2026-01-15"
    expires: "2026-07-15"
    data_scope: PUBLIC
    risk: LOW
    rationale: "Пошук документації лише для читання. Без виведення даних у мережу."
    config:
      command: npx
      args: ["-y", "@context7/mcp-server@1.2.3"]

  - name: sequential-thinking
    version: "0.6.2"
    source: "https://github.com/modelcontextprotocol/servers"
    approved_by: "jane.smith@company.com"
    approved_date: "2026-01-15"
    expires: "2026-07-15"
    data_scope: INTERNAL
    risk: LOW
    rationale: "Лише локальні міркування. Немає доступу до мережі."
    config:
      command: npx
      args: ["-y", "@modelcontextprotocol/server-sequential-thinking@0.6.2"]

  - name: internal-db-readonly
    version: "2.1.0"
    source: "internal"
    approved_by: "security@company.com"
    approved_date: "2026-02-01"
    expires: "2026-05-01"  # Коротший термін для підвищеного ризику
    data_scope: CONFIDENTIAL
    risk: MEDIUM
    rationale: "Доступ до репліки бази даних тільки для читання. Таблиці PII вилучені з білого списку."
    restrictions:
      - "Лише облікові дані з правами Read-only"
      - "Немає доступу до таблиць користувачів, платежів або аудит-логів"
    config:
      command: npx
      args: ["-y", "@company/db-mcp@2.1.0"]

pending_review:
  - name: github-mcp
    requested_by: "dev@company.com"
    requested_date: "2026-03-05"
    use_case: "Автоматизація Pull Requests"
    status: under_review

denied:
  - name: browser-automation-mcp
    denied_date: "2026-02-10"
    reason: "Повний доступ до браузера без обмеження області видимості. Ризик занадто високий."
```

### 3.3 Примусове застосування реєстру через хуки

Використовуйте хук управління, щоб переконатися, що використовуються лише схвалені сервери MCP. Наведений нижче скрипт є мінімальною інтегрованою версією, яку ви можете додати до файлу `.claude/hooks/governance-check.sh`. Більш детальну реалізацію з додатковими перевірками (блокування чорних списків, виявлення небезпечних білих списків) див. у [`examples/hooks/bash/governance-enforcement-hook.sh`](../../examples/hooks/bash/governance-enforcement-hook.sh).

```bash
#!/bin/bash
# .claude/hooks/governance-check.sh
# Подія: SessionStart
# Перевіряє конфігурацію активних MCP на відповідність затвердженому реєстру

REGISTRY=".claude/mcp-registry.yaml"
SETTINGS="${HOME}/.claude.json"

if [[ ! -f "$REGISTRY" ]]; then
  exit 0  # Немає реєстру = немає примусового контролю (добровільна участь)
fi

# Перевірка на несанкціоновані MCP (потребує наявності yq та jq)
if command -v jq &>/dev/null && command -v yq &>/dev/null; then
  ACTIVE=$(jq -r '.mcpServers | keys[]' "$SETTINGS" 2>/dev/null)
  APPROVED=$(yq e '.approved[].name' "$REGISTRY" 2>/dev/null)

  for mcp in $ACTIVE; do
    if ! echo "$APPROVED" | grep -q "^${mcp}$"; then
      echo "ПОПЕРЕДЖЕННЯ УПРАВЛІННЯ: MCP-сервер '${mcp}' відсутній у схваленому реєстрі."
      echo "Подайте запит на сторінці: https://your-internal-wiki/mcp-requests"
      echo "Сесію продовжено — будь ласка, усуньте невідповідність протягом 48 годин."
    fi
  done
fi

exit 0
```

> [!NOTE]
> Цей хук лише попереджає, але не блокує запуск. Блокування на початку сесії створює занадто багато незручностей для розробників. Замість цього використовуйте регулярний аудит відповідності (див. §5.3).

## 4. Рівні обмежень (Guardrail Tiers)

Попередньо налаштовані рівні обмежень для чотирьох типових сценаріїв. Скопіюйте відповідний рівень у `.claude/settings.json` та `CLAUDE.md` вашого проєкту.

### Рівень 1: Стартовий (Starter)

```markdown
## Стан безпеки: STRICT (СУВОРИЙ)

Ви працюєте в середовищі із підвищеними вимогами до безпеки. Дотримуйтесь цих правил без жодних винятків.

### Заблоковані файли (Locked Files)
Ці файли та каталоги не можуть бути змінені без явного схвалення в поточному діалозі:
- docker-compose.yml, Dockerfile, .github/workflows/**, terraform/**, kubernetes/**

3. Зачекайте на явне схвалення користувача перед запуском будь-якої команди встановлення (`install`).

Перед читанням будь-якого файлу, розташованого за межами кореня проєкту:
1. Чітко поясніть шлях до файлу та обґрунтуйте необхідність його аналізу.
```

## 5. Впровадження політик у масштабі

Наявність політики не означає її автоматичне виконання. Цей розділ описує те, як зробити так, щоб корпоративні правила реально працювали у команді з 10–100 розробників.

### 5.1 Централізована дистрибуція конфігурацій

**Головний принцип**: Конфігурація управління та обмежень зберігається в репозиторії проєкту, а не локально на комп'ютерах розробників.

```
your-org-config/                 ← окремий репозиторій "платформної конфігурації"
├── .claude/
│   ├── settings.json            ← спільні налаштування (залежно від рівня)
│   ├── mcp-registry.yaml        ← реєстр схвалених MCP
│   ├── hooks/
│   │   ├── governance-check.sh  ← перевірка реєстру MCP
│   │   ├── session-logger.sh    ← ведення аудит-логу
│   │   └── velocity-governor.sh ← обмеження швидкості запитів
│   └── agents/
│       └── security-reviewer.md ← спільний агент для рев'ю безпеки
├── templates/
│   ├── CLAUDE.md.starter        ← шаблони CLAUDE.md для кожного рівня
│   ├── CLAUDE.md.standard
│   ├── CLAUDE.md.strict
│   └── CLAUDE.md.regulated
└── scripts/
    └── setup-project.sh         ← скрипт розгортання потрібного рівня в новий проєкт
```

**Ініціалізація нового проєкту**:

```bash
#!/bin/bash
# scripts/setup-project.sh
# Використання: ./setup-project.sh [starter|standard|strict|regulated]

TIER=${1:-standard}
CONFIG_REPO="https://github.com/your-org/claude-code-config"

echo "Налаштування управління Claude Code: рівень $TIER"

# Створення директорії .claude
mkdir -p .claude/hooks

# Копіювання конфігурації рівня
curl -s "$CONFIG_REPO/raw/main/templates/.claude/settings.${TIER}.json" \
  -o .claude/settings.json

# Копіювання шаблону CLAUDE.md
curl -s "$CONFIG_REPO/raw/main/templates/CLAUDE.md.${TIER}" \
  -o CLAUDE.md

# Копіювання хуків управління
curl -s "$CONFIG_REPO/raw/main/hooks/governance-check.sh" \
  -o .claude/hooks/governance-check.sh
chmod +x .claude/hooks/governance-check.sh

echo "Готово. Закомітьте директорію .claude/ та файл CLAUDE.md у ваш репозиторій."
```

### 5.3 Автоматизований аудит відповідності

Скрипт періодичної автоматизованої перевірки конфігурації на наявність змін ("дрейфу"):

```bash
#!/bin/bash
# scripts/claude-governance-audit.sh
# Запускається щотижня через CI/CD або cron

PASS=0
FAIL=0
WARN=0

check() {
  local name="$1"
  local result="$2"
  local severity="${3:-FAIL}"

  if [[ "$result" == "OK" ]]; then
    echo "  PASS: $name"
    ((PASS++))
  else
    echo "  $severity: $name — $result"
    [[ "$severity" == "FAIL" ]] && ((FAIL++)) || ((WARN++))
  fi
}

echo "=== Аудит управління Claude Code ==="
echo ""

# Перевірка: наявність та фіксація settings.json
echo "1. Конфігурація репозиторію"
[[ -f ".claude/settings.json" ]] \
  && check "settings.json присутній" "OK" \
  || check "settings.json присутній" "Відсутній — корпоративне управління не діє" "FAIL"

git ls-files --error-unmatch .claude/settings.json &>/dev/null \
  && check "settings.json додано в git" "OK" \
  || check "settings.json додано в git" "Не відстежується в git — налаштування не застосуються до команди" "WARN"

# Перевірка: правила блокування секретів
echo ""
echo "2. Захист секретів"
if [[ -f ".claude/settings.json" ]]; then
  jq -e '.permissions.deny[]? | select(test("env|pem|key"))' \
    .claude/settings.json &>/dev/null \
    && check "Правила захисту .env" "OK" \
    || check "Правила захисту .env" "Відсутні обмеження для .env або файлів ключів" "FAIL"
fi

# Перевірка: встановлення та виконання хуків
echo ""
echo "3. Стек хуків"
for hook in ".claude/hooks/governance-check.sh"; do
  if [[ -f "$hook" ]]; then
    [[ -x "$hook" ]] \
      && check "$hook має права на виконання" "OK" \
      || check "$hook має права на виконання" "Немає прав на виконання — запустіть chmod +x $hook" "FAIL"
  else
    check "$hook присутній" "Відсутній" "WARN"
  fi
done

# Перевірка: наявність реєстру MCP
echo ""
echo "4. Управління MCP"
[[ -f ".claude/mcp-registry.yaml" ]] \
  && check "Реєстр MCP присутній" "OK" \
  || check "Реєстр MCP присутній" "Немає реєстру — використання MCP не контролюється" "WARN"

# Перевірка: наявність та відстеження CLAUDE.md
echo ""
echo "5. Документація"
[[ -f "CLAUDE.md" ]] || [[ -f ".claude/CLAUDE.md" ]] \
  && check "CLAUDE.md присутній" "OK" \
  || check "CLAUDE.md присутній" "Відсутній — немає контексту проєкту для ШІ" "WARN"

echo ""
echo "=== Підсумки аудиту ==="
echo "  Успішно (Passed):  $PASS"
echo "  Помилок (Failed):   $FAIL (вимагає виправлення)"
echo "  Попереджень (Warn): $WARN (бажано виправити)"
echo ""

[[ $FAIL -gt 0 ]] && exit 1 || exit 0
```

**Підхід: опис обмежень за ролями у файлі CLAUDE.md**

```markdown
<!-- Доповнення до CLAUDE.md — вказівки з урахуванням ролей -->
## Розробники та ролі (Developer Context)

Цей проєкт містить правила для розробників рівнів [JUNIOR|SENIOR|LEAD].

### Якщо ви JUNIOR (< 1 року в компанії):
- Завжди погоджуйте архітектурні рішення з техлідом перед початком імплементації.
- Не змінюйте схеми баз даних, файли міграцій або логіку автентифікації без парної роботи із Senior-розробником.
- Кожен ваш PR повинен проходити ручну перевірку коду, згенерованого ШІ, з боку Senior.
- Завжди використовуйте режим `/plan` перед написанням будь-якого коду обсягом понад 50 рядків.

### Якщо ви SENIOR (1+ років у компанії):
- Застосовується стандартний процес рев'ю.
- Дозволено змінювати більшість файлів, проте критична логіка (auth/payments/crypto) все ще потребує погодження техліда.
- Атрибуція ШІ в Pull Requests є обов'язковою.

### Якщо ви LEAD/PRINCIPAL:
- Повний доступ, обмеження на основі власного досвіду та здорового глузду.
- Відповідальність за встановлення та підтримання рівнів обмежень для проєктів своєї команди.
- Обов'язок проводити щоквартальний перегляд реєстру MCP.
```

**Підхід: окремі файли settings.json для різних середовищ**

У CI/CD перевіряйте шлях до активного `settings.json` на початку пайплайну для застосування правильного рівня обмежень. Claude Code зчитує `.claude/settings.json` із кореня проєкту — зафіксуйте там вашу конфігурацію суворого рівня (Strict), щоб CI-система завжди використовувала її незалежно від локальних файлів розробників.

```bash
# На етапі ініціалізації CI перевірте правильність доданого settings.json
if ! grep -q '"Bash(curl \*)"' .claude/settings.json; then
  echo "ПОМИЛКА: Для CI потрібна конфігурація рівня Regulated (команда curl має бути заборонена)"
  exit 1
fi
```

### 5.5 Фільтри та шлюзи в CI/CD (CI/CD Gates)

Блокуйте невідповідне використання ШІ до того, як код потрапить у продакшн:

```yaml
# .github/workflows/ai-governance.yml
name: AI Governance Check

on: [pull_request]

jobs:
  governance:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Check governance config present
        run: |
          if [[ ! -f ".claude/settings.json" ]]; then
            echo "::error::Missing .claude/settings.json — governance config required"
            exit 1
          fi

      - name: Check no credential access permissions
        run: |
          if jq -e '.permissions.allow[]? | select(test("env|pem|key|secret"))' \
            .claude/settings.json 2>/dev/null; then
            echo "::error::Dangerous permissions.allow detected — credentials may be exposed"
            exit 1
          fi

      - name: Run governance audit
        run: |
          chmod +x scripts/claude-governance-audit.sh
          ./scripts/claude-governance-audit.sh

      - name: Check AI attribution in PR description
        if: ${{ env.REQUIRE_AI_ATTRIBUTION == 'true' }}
        uses: actions/github-script@v7
        with:
          script: |
            const body = context.payload.pull_request.body || '';
            const hasAttribution = body.includes('AI') ||
                                   body.includes('Claude') ||
                                   body.includes('AI-generated');
            if (!hasAttribution) {
              core.warning('No AI attribution section found. Please disclose AI usage.');
            }
```

## 6. Аудит, відповідність та структура управління

### 6.1 Що насправді запитують аудитори SOC2 та ISO27001

Під час перевірки використання інструментів штучного інтелекту аудитори зазвичай вимагають підтвердження наявності таких контролів:

| Питання аудитора | Що вони хочуть бачити | Реалізація в Claude Code |
|-----------------|----------------------|---------------------------|
| "Чи маєте ви затверджену політику використання ШІ?" | Письмову хартію, підписану або погоджену розробниками | `docs/ai-usage-charter.md` + чек-лист онбордингу |
| "Як ви контролюєте передачу даних стороннім ШІ-вендорам?" | Схему класифікації даних + технічні обмеження | Правила `permissions.deny` для файлів із конфіденційними даними |
| "Як ви перевіряєте сторонні компоненти ШІ?" | Процес схвалення + актуальний реєстр компонентів | Реєстр схвалених MCP-серверів + покроковий процес погодження |
| "Чи ведеться у вас аудиторський лог дій ШІ?" | Журнал запущених інструментів та прочитаних файлів | Лог-файли сесій JSONL + скрипт `compliance-audit-logger.sh` |
| "Як ви проводите рев'ю коду, створеного ШІ?" | Процес перевірки коду з обов'язковим декларуванням ШІ | Шаблони Pull Request + правила атрибуції коду |
| "Які ваші дії у випадку інциденту безпеки з ШІ?" | Регламент реагування на інциденти (Incident Response) | Стандартний процес реагування компанії з додаванням ШІ-специфіки |

**Для SOC2**: Відповідні критерії довірчих послуг (Trust Services Criteria) — це CC6.1 (контроль логічного доступу), CC6.3 (видалення доступу), CC7.1 (моніторинг) та CC9.2 (управління ризиками постачальників). Ваше управління Claude Code має чітко відповідати цим пунктам.

**Для ISO27001**: Відповідні контроли Додатка А включають А.8.3 (обмеження доступу до інформації), А.8.24 (використання криптографії), А.8.25 (безпечний життєвий цикл розробки) та А.5.23 (інформаційна безпека під час використання хмарних сервісів).

### 6.2 Налаштування аудиторського сліду (Audit Trail)

Сесії Claude Code автоматично записуються до каталогу `~/.claude/projects/<project>/*.jsonl`. Головне завдання для комплаєнсу — зробити ці логи:
1. Доступними для аналізу (вони не повинні зникати після звільнення розробника).
2. Захищеними від несанкціонованих змін (редагування заднім числом).
3. Зручними для швидкого пошуку та аналізу.

**Мінімальний лог аудиту (без використання стороннього ПЗ)**:

```bash
#!/bin/bash
# .claude/hooks/compliance-audit-logger.sh
# Подія: PostToolUse (для всіх інструментів)
# Додає структуровані записи про дії в загальний лог

LOG_DIR="${COMPLIANCE_LOG_DIR:-/var/log/claude-audit}"
LOG_FILE="$LOG_DIR/$(date +%Y-%m-%d).jsonl"

mkdir -p "$LOG_DIR"

INPUT=$(cat)
TOOL=$(echo "$INPUT" | jq -r '.tool.name // "unknown"')
USER=$(whoami)
PROJECT=$(basename "$PWD")
TIMESTAMP=$(date -u +"%Y-%m-%dT%H:%M:%SZ")

echo "{\"timestamp\":\"$TIMESTAMP\",\"user\":\"$USER\",\"project\":\"$PROJECT\",\"tool\":\"$TOOL\"}" \
  >> "$LOG_FILE"
```

**Відправка логів до незмінюваного сховища** (наполегливо рекомендовано для регульованих середовищ):

```bash
# Щоденно: синхронізація логів сесій у захищений s3-бакет
aws s3 sync ~/.claude/projects/ \
  s3://your-audit-bucket/claude-sessions/$(whoami)/ \
  --storage-class GLACIER_INSTANT_RETRIEVAL \
  --exclude "*.tmp"
```

**Для побудови повного аудиторського сліду** з можливістю створення контрольних шлюзів розгляньте використання Entire CLI — він фіксує повний контекст сесій (промпти, міркування, виклики інструментів, diff-зміни) із криптографічним зв'язуванням із git-комітами. Для вибору цього або альтернативних рішень зверніться до розділу [AI Traceability §5.1](../ops/ai-traceability.uk.md#51-entire-cli).

### 6.3 Комітет з управління ШІ (AI Governance Committee)

Для організацій, які керують ризиками ШІ в масштабі, створення легковагового Комітету з управління ШІ забезпечує саме ту структуру підзвітності, яку очікують побачити аудитори. Це інструмент координації та допомоги розробникам, а не бюрократична перешкода.

**Мінімальна структура комітету** (ефективна для команд від 10 до 100 розробників):

| Роль у комітеті | Хто займає | Сфера відповідальності |
|------|--------|----------------|
| **Governance Lead** | Engineering Manager або Lead | Оновлення політик, щоквартальний перегляд конфігурацій, ескалація питань |
| **Security Rep** | SecEng або DevSecOps | Аналіз ризиків MCP, реагування на інциденти безпеки |
| **Dev Rep** | Ротація Senior-розробників (термін 3 місяці) | Отримання фідбеку від команди, збереження балансу між безпекою та зручністю |
| **Compliance Rep** | Представник юридичного/комплаєнс-відділу | Адаптація хартії, відповідність регуляторним стандартам |

**Періодичність зустрічей**: Щоквартально (30 хвилин). Порядок денний зустрічі:
1. Рев'ю реєстру MCP — чи потрібно щось додати, видалити або змінити?
2. Розгляд інцидентів — чи були пов'язані з ШІ події безпеки з моменту минулої зустрічі?
3. Оновлення політики — які зміни чи уточнення слід внести в Хартію використання ШІ?
4. Оцінка метрик — результати автоматизованих аудитів, стан комплаєнсу.

Детальні інструкції щодо RACI-матриць, побудови та взаємодії Комітету з управління ШІ див. у спеціалізованому матеріалі Whitepaper #11: Enterprise AI Governance.

### 6.4 Моніторинг відповідності (Compliance Monitoring)

Рівень моніторингу та спостереження детально описано у посібнику [observability.uk.md](../ops/observability.uk.md). Для цілей перевірки відповідності стандартам безпеки найбільш корисними є такі пошукові запити:

```bash
# До яких файлів звертався Claude за останні 30 днів?
# macOS: date -v-30d; Linux: date -d '30 days ago'
if [[ "$OSTYPE" == "darwin"* ]]; then
  SINCE=$(date -v-30d +%Y-%m-%d)
else
  SINCE=$(date -d '30 days ago' +%Y-%m-%d)
fi

find ~/.claude/projects/ -name "*.jsonl" -newer "$SINCE" | \
  xargs jq -r 'select(.type == "assistant") |
    .message.content[]? |
    select(.type == "tool_use" and .name == "Read") |
    .input.file_path' 2>/dev/null | sort -u

# Чи були спроби доступу до конфіденційних файлів/шаблонів?
# (Запустіть запит вище та перенаправте через grep)
grep -E '\.(env|pem|key)$|secrets/|credentials'

# CLI-команди Bash, які виконував Claude протягом цього тижня
if [[ "$OSTYPE" == "darwin"* ]]; then
  SINCE_WEEK=$(date -v-7d +%Y-%m-%d)
else
  SINCE_WEEK=$(date -d '7 days ago' +%Y-%m-%d)
fi

find ~/.claude/projects/ -name "*.jsonl" -newer "$SINCE_WEEK" | \
  xargs jq -r 'select(.type == "assistant") |
    .message.content[]? |
    select(.type == "tool_use" and .name == "Bash") |
    .input.command' 2>/dev/null | sort
```

## Швидкий довідник (Quick Reference)

### Вибір рівня обмежень

| Ваша ситуація | Рекомендований рівень | Час на запуск |
|----------------|------|------------|
| Pet-проєкт, особисте використання | Starter | 10 хв |
| Мала команда, внутрішній проєкт | Starter | 10 хв |
| Команда 5–20 осіб, будь-який продакшн-код | Standard | 45 хв |
| Команда 20+ осіб, робота з даними клієнтів | Strict | 2 год |
| Регульована індустрія (HIPAA/SOC2/PCI) | Regulated | Пів дня |

### Рівні зрілості управління ШІ (AI Governance Maturity Levels)

| Рівень зрілості | Що у вас уже впроваджено | Чого вам бракує |
|----------|---------------|----------------|
| **Ad hoc (Хаотичний)** | Кожен розробник налаштовує інструмент самостійно | Узгодженості, загальної підзвітності |
| **Basic (Базовий)** | Спільний CLAUDE.md + загальний settings.json | Управління MCP, аудиторського сліду |
| **Managed (Керований)** | + реєстр схвалених MCP + робочі хуки безпеки | Регулярної комплаєнс-звітності |
| **Compliant (Відповідний)** | + логування сесій + підписана Хартія + регулярний перегляд | Нічого критичного |
| **Audited (Аудійований)** | + зовнішня валідація політик + повна простежуваність | — |

### Типові помилки та способи їх усунення

| Помилка | Спосіб усунення |
|---------|-----|
| Налаштування безпеки збережені лише в `~/.claude` (локально) | Перенесіть конфігурацію в директорію `.claude/` у вашому репозиторії |
| Особисті `permissions.allow` обходять `deny` команди | Впровадьте щоквартальний аудит особистих конфігурацій розробників |
| Відсутність реєстру MCP → кожен ставить свої плагіни | Створіть файл реєстру, навіть якщо у ньому буде лише 3 записи |
| Файл CLAUDE.md занадто великий → Claude ігнорує правила | Тримайте розмір файлу в межах 8 КБ, фокусуйтеся лише на головному |
| Аудитори просять лог дій ШІ → нічого не зберігається | Налаштуйте щоденну синхронізацію логів сесій JSONL у захищений S3-бакет |
