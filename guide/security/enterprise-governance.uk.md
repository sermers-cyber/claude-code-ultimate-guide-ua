## 1. Локальне vs Спільне: Розподіл управління

Керуйте залежно від доступу до даних, облікових даних, дій і середовища виконання. Локальна копія репозиторію може містити облікові дані продакшну чи дані клієнтів; спільний репозиторій може містити лише публічні приклади. Саме розташування не визначає рівня ризику.

### 1.1 Матриця ризиків

| Вимір | Локальне використання | Спільне використання |
|-----------|-------------|--------------|
| **Витік даних** | Будь-які дані, доступні сесії | Будь-які дані, доступні сесії |
| **Зона впливу** | Залежить від облікових даних, файлової системи, мережі та інструментів | Залежить від облікових даних, файлової системи, мережі та інструментів |
| **Підзвітність** | Іменований оператор і чинна політика організації | Іменовані власники та чинна політика організації |
| **Відтворюваність** | Збережені сесії можуть існувати; перевірте строки зберігання та доступ | Налаштуйте й перевірте потрібний аудиторський слід |
| **Область комплаєнсу** | Визначається даними та зобов'язаннями щодо обробки | Визначається даними та зобов'язаннями щодо обробки |
| **Дрейф конфігурацій** | Перевіряйте активні особисті, проєктні та керовані джерела | Перевіряйте активні джерела та розгорнуту політику |

### 1.2 Що ви можете і чого не можете контролювати

**Конфігурація репозиторію розповсюджує базовий рівень**: діліться інструкціями проєкту, підтримуваними налаштуваннями, хуками та визначеннями MCP проєкту в `.mcp.json`. Залишайте перевірки CI як незалежні шлюзи. Файл у репозиторії не є блокуванням політики на рівні всієї організації.

**Керовані засоби контролю примусово застосовують відповідну політику всередині Claude Code**: розгортайте підтримувані керовані налаштування та керовані обмеження MCP для охоплених акаунтів чи хостів. Перевіряйте, яка політика активна, за допомогою `/status` і перевіряйте заблоковані дії на практиці. Деякі значення, як-от модель за замовчуванням, залишаються лише значеннями за замовчуванням; використовуйте задокументований ключ обмеження, коли вибір потрібно обмежити. [Кероване розгортання](https://code.claude.com/docs/en/managed-settings#what-a-developer-can-change).

**Поза цією межею**: некеровані пристрої, інші API-клієнти та локальні адміністратори можуть потребувати окремих засобів контролю ідентичності, кінцевих точок, мережі та облікових даних. Не стверджуйте, що керуєте цими поверхнями, спираючись на закомічений файл.

### 1.3 Фреймворк прийняття рішень: Коли впроваджувати управління

Нижче наведено запропонований організаційний фреймворк, а не рівні продукту. Застосовуйте засоби контролю залежно від даних і дій; перевіряйте фактичну політику в кожному середовищі.

```
Що саме ви регулюєте?
│
├─ Особистий робочий процес (локальний, тимчасовий код)
│   └─ Мінімальний контроль: рекомендації в CLAUDE.md + базові хуки
│
├─ Кодова база команди (спільний репозиторій, не продакшн)
│   └─ Стандартний контроль: спільна конфігурація + керована політика, де потрібно + PR-шлюзи
│
├─ Продакшн-система (орієнтована на клієнтів, реальні дані)
│   └─ Суворий контроль: повна конфігурація рівнів + процес схвалення + аудиторський лог
│
└─ Регульоване середовище (HIPAA, SOC2, PCI, фінанси)
    └─ Регульований контроль: все вищезазначене + комплаєнс-аудит
```

## 2. Хартія використання ШІ

Хартія використання відповідає на фундаментальне запитання: "Що нам дозволено робити з Claude Code в нашій компанії?". Без неї кожна команда розробки буде відповідати на це запитання по-своєму, створюючи неконтрольовані та неузгоджені ризики.

Це приклад політики, який слід адаптувати разом із власниками, відповідальними за ваші дані, договори та системи. Він не встановлює права за тарифним планом і не є юридичною вимогою комплаєнсу.

### 2.1 Лаконічний шаблон хартії

Скопіюйте цей шаблон у файл `docs/ai-usage-charter.md` вашої організації та адаптуйте. Вибір класифікацій, періодичність перегляду та погодження нижче є прикладами організаційних рішень:

```markdown
# Хартія використання інструментів кодування на базі ШІ

**Застосовується до**: Claude Code (та будь-яких асистентів кодування на базі ШІ)
**Дата набрання чинності**: [ДАТА]
**Власник політики**: Engineering Lead / CTO
**Періодичність перегляду**: Щоквартально

---

## Схвалені інструменти

| Інструмент | Область застосування | Класифікація даних |
|------|-------|---------------------|
| Схвалений організацією акаунт Claude Code і маршрут обробки | Схвалена розробка | Лише схвалені класифікації |
| Особисті акаунти | Лише особиста публічна робота | Лише PUBLIC |
| [Інші схвалені інструменти] | [Область] | [Класифікація] |

---

## Правила класифікації даних

| Класифікація | Приклади | Дозволено з Claude Code? |
|----------------|----------|--------------------------|
| **PUBLIC** | Відкритий код (Open Source), публічна документація | Так, з урахуванням дозволів на дії |
| **INTERNAL** | Внутрішні інструменти, нечутливий код | Лише через схвалений маршрут обробки |
| **CONFIDENTIAL** | Внутрішні комерційні таємниці, нерегульована інтелектуальна власність (IP) | Лише коли договори, зберігання та засоби контролю схвалені |
| **RESTRICTED** | Персональні дані клієнтів (PII), дані платіжних карток (PCI), медичні дані (PHI), облікові дані | Заборонено за цією прикладовою хартією |

**Суворе правило**: Дані класу RESTRICTED ніколи не повинні потрапляти у вікно контексту ШІ. Ні в промптах, ні у файлах, які читає Claude, ні як приклади. Приберіть дані з обмеженим доступом із середовища виконання та застосуйте перевірені засоби контролю інструментів, файлової системи, мережі й облікових даних. Самого тексту інструкцій недостатньо.

## Схвалені сценарії використання

- Дописування коду, рев'ю, рефакторинг
- Генерація тестів
- Створення чернеток документації
- Налаштування та аналіз першопричин помилок (Debugging)
- Аналіз архітектури (тільки внутрішніх систем)
- Написання CLI-скриптів та автоматизація

---

## Заборонені сценарії використання

- Обробка даних платіжних карток (область дії PCI)
- Генерація коду, який працює з необробленими медичними даними (PHI) без перевірки безпеки
- Автономний деплой у продакшн без затвердження людиною
- Використання особистих ШІ-акаунтів для роботи з даними CONFIDENTIAL або вище
- Передача реальних даних клієнтів у промптах як прикладів
```

### 2.2 Зв'язок між класифікацією даних та налаштуваннями Claude Code

Ці правила дозволів є стартовим прикладом для вбудованих інструментів, а не повною ізоляцією даних. Shell-програми та сервери MCP можуть отримувати доступ до даних іншими шляхами. Використовуйте засоби контролю ОС і вузько обмежені облікові дані, а потім перевіряйте непрямі читання та вихідний мережевий трафік. [Межі дозволів](https://code.claude.com/docs/en/permissions#how-permissions-interact-with-sandboxing).

```json
{
  "permissions": {
    "deny": [
      "Read(./**/*.pem)",
      "Read(./**/*.key)",
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./secrets/**)",
      "Read(**/credentials*)",
      "Bash(cat .env*)",
      "Bash(printenv*)",
      "Bash(env)"
    ]
  }
}
```

```markdown
<!-- Доповнення до CLAUDE.md — правила обробки даних -->
## Обробка даних (Data Handling)

**НІКОЛИ** не читайте, не посилайтеся і не включайте у вивід:
- Файли, що відповідають шаблонам: .env, *.pem, *.key, credentials.*, secrets/
- Поля персональних даних клієнтів (PII) (поля з назвами: email, phone, ssn, dob, card_*)
- Облікові дані або API-ключі (навіть масковані/заретушовані приклади)

Якщо під час читання файлу ви натрапите на конфіденційні дані обмеженого доступу, негайно зупиніться та повідомте користувача.
Не продовжуйте роботу, доки не отримаєте явну вказівку пропустити цей контент.
```


### 2.3 Поширення налаштувань у команді

Написати хартію замало: розробники мають реально працювати з потрібною конфігурацією. Використовуйте взаємодоповнювальні механізми, кожен зі своєю областю дії:

**Спільний settings.json у репозиторії команди**

Зберігайте (commit) підтримувані налаштування проєкту в `.claude/settings.json`. Перевіряйте область дії кожного ключа та вимоги до довіри до робочої області; саме клонування репозиторію не активує всі можливі налаштування. [Область дії налаштувань проєкту](https://code.claude.com/docs/en/settings#a-committed-key-doesnt-reach-teammates).

```json
{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Read(./**/*.key)",
      "Bash(curl *)",
      "Bash(wget *)"
    ]
  },
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "\"$CLAUDE_PROJECT_DIR\"/.claude/hooks/dangerous-actions-blocker.sh"
          }
        ]
      }
    ]
  }
}
```

Локальні налаштування можуть змінювати звичайні типові значення проєкту без редагування відстежуваних файлів. Правила deny/ask для дозволів поєднуються з різних джерел, а не підпорядковуються звичайному пріоритету скалярних значень. Для обов'язкових обмежень використовуйте керовану політику та перевіряйте результат. Приклад припускає, що згаданий виконуваний хук існує й протестований; його патерни Bash не блокують усіх мережевих маршрутів. [Пріоритет налаштувань](https://code.claude.com/docs/en/settings#settings-precedence), [конфігурація хуків](https://code.claude.com/docs/en/hooks#hook-locations).

**Спільний CLAUDE.md для правил поведінки**

Використовуйте `CLAUDE.md` проєкту для поширення стандартів кодування та пояснення політики поводження з даними. Це настанова для моделі, а не примусові обмеження інструментів. Шаблон хартії див. у §2.2.

**Адміністративні засоби контролю Anthropic Team та Enterprise**

Розгортайте керовані засоби контролю, доступні вашій організації та клієнту. Адміністрування API Console, налаштування організації claude.ai та політика хоста є різними поверхнями; перевірте, яка з них досягає сесії. Організаційні обмеження потребують підтримуваних ключів політики, доставки до потрібного акаунта чи хоста та перевірки під час виконання. [Механізми розгортання](https://code.claude.com/docs/en/managed-settings).

Спільна конфігурація репозиторію залишається корисною для типових значень проєкту. Вона доповнює керовану політику та засоби контролю середовища виконання.

## 3. Процес управління MCP

Індивідуальна перевірка MCP (5-хвилинний аудит) описана в [security-hardening.uk.md §1.1](./security-hardening.uk.md#11-воркфлоу-перевірки-веттингу-mcp). Цей розділ присвячений організаційному процесу: як нові сервери MCP отримують схвалення, розгортаються та контролюються у вашій команді.

### 3.1 Робочий процес схвалення (Approval Workflow)

Це приклад організаційного процесу. Назва сервера, рейтинг популярності чи відсутність відомих вразливостей не є достатнім доказом безпеки.

```
Розробник запитує MCP
        |
        v
[1] Зафіксуйте джерело, точну версію, сценарій використання, потік даних, облікові дані
        |
        v
[2] Перегляньте код/походження, залежності, повідомлення про вразливості, дозволи,
    описи інструментів, доступ до мережі та репрезентативну поведінку
        |
        +-- Доказів недостатньо --> Відкласти або відхилити
        |
        v
[3] Схваліть обмежений обсяг і переглянуту версію
    Зафіксуйте власника, докази рішення та тригери повторного перегляду
        |
        v
[4] Розповсюдьте визначення проєкту через .mcp.json
    Розгорніть керовану політику MCP там, де обмеження мають примусово діяти
    Перевірте активну політику та заблоковані дії
        |
        v
[5] Відстежуйте повідомлення про вразливості та поведінку; повторно переглядайте зміни
    Оновіть схвалення до розгортання зміненої версії чи обсягу
```

### 3.3 Примусове застосування реєстру через хуки

Для примусових обмежень використовуйте керовану конфігурацію MCP. Зразок нижче є лише діагностичним попередженням для верхньорівневої мапи `mcpServers` у `~/.claude.json`; він не бачить інших областей дії, записів проєкту, plugins, конекторів і визначень у командному рядку. Він не може перевірити остаточний набір активних серверів. Перегляньте й протестуйте будь-який хук перед використанням; окремий [приклад хука управління](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/examples/hooks/bash/governance-enforcement-hook.sh) також потребує перевірки для вашого розгортання.

```bash
#!/bin/bash
# .claude/hooks/governance-check.sh
# Подія: SessionStart
# Попереджає про одну збережену мапу MCP; не складає опису активних серверів

REGISTRY=".claude/mcp-registry.yaml"
SETTINGS="${HOME}/.claude.json"

if [[ ! -f "$REGISTRY" ]]; then
  exit 0  # Немає реєстру = немає примусового контролю (добровільна участь)
fi

# Перевірка на несанкціоновані MCP (потребує наявності yq та jq)
if command -v jq &>/dev/null && command -v yq &>/dev/null; then
  ACTIVE=$(jq -r '.mcpServers | keys[]' "$SETTINGS" 2>/dev/null)
  APPROVED=$(yq e '.approved[].name' "$REGISTRY" 2>/dev/null)

  for mcp in $ACTIVE; do
    if ! echo "$APPROVED" | grep -q "^${mcp}$"; then
      echo "ПОПЕРЕДЖЕННЯ УПРАВЛІННЯ: MCP-сервер '${mcp}' відсутній у схваленому реєстрі."
      echo "Подайте запит на сторінці: https://your-internal-wiki/mcp-requests"
      echo "Сесію продовжено — будь ласка, усуньте невідповідність протягом 48 годин."
    fi
  done
fi

exit 0
```

> [!NOTE]
> Цей приклад завжди продовжує сесію, зокрема й тоді, коли бракує його залежностей. Він не є шлюзом примусового застосування чи схвалення. Використовуйте розгорнуті керовані засоби контролю MCP та перевіряйте їхнє покриття для поверхонь клієнта, що використовуються.

### 3.4 Нове: ізоляція інструментів MCP на рівні runtime

Окрім процесів схвалення, виникає підхід, що ізолює доступ кожного інструмента MCP до ОС під час виконання через WebAssembly. Інструменти на кшталт [Wassette](https://github.com/microsoft/wassette) запускають сервери MCP як компоненти Wasm із забороною за замовчуванням доступу до файлової системи та мережі, що оголошується в YAML. Станом на середину 2026 року жоден із цих інструментів не готовий до продакшну, але їх варто відстежувати, якщо ваша модель ризиків враховує сторонні сервери MCP з непередбачуваним обсягом привілеїв. Повний огляд: [sandbox-isolation.md §7b](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/guide/security/sandbox-isolation.md#7b-webassembly-based-mcp-tool-sandboxing-experimental).

### 3.5 Спостерігайте: Executor, патерн реєстру як продукт

Робочий процес §3.1-§3.3 вище (подати, переглянути, зареєструвати, примусово застосувати хуком) є ручною відповіддю на питання, яке дедалі більша категорія інструментів намагається автоматизувати: єдиний каталог схвалених інтеграцій, спільний для кожного агента, що до нього підключається, замість окремого реєстру для кожної команди чи інструмента.

[Executor](https://github.com/UsefulSoftwareCo/executor) (MIT, `1.4.0-beta.0`) є найвиразнішим нинішнім прикладом. Він оголошує інтеграцію один раз (специфікація OpenAPI, endpoint GraphQL, наявний сервер MCP), загортає її в підключення, що ідентифікується як `(scope, integration, name)`, тож одна інтеграція може містити кілька автентифікованих акаунтів, і обмежує кожен інструмент тими самими трьома станами, які цей розділ уже називає: allow, require approval, block. Відображення на формат реєстру з §3.2 майже один до одного: інтеграція відповідає полям `source` і `config` запису реєстру, підключення відповідає іменованому автентифікованому екземпляру цього запису, а стани політики відповідають полю `risk` реєстру, узагальненому на кожен інструмент, а не на кожен сервер. Далі, ніж ручна версія тут, він іде в самих облікових даних: підключення ніколи не зберігає сирий секрет, лише посилання (`op://`, `keychain://`, `env://`, `vault://`), яке провайдер розв'язує під час виклику за проксі, тож секрет не може потрапити в схему інструмента чи відповідь MCP навіть випадково. Формат реєстру з §3.2 не має для цього відповідного поля; поводження з обліковими даними в цьому патерні й далі залежить від менеджера секретів, що стоїть під `.claude/settings.json`.

Компроміс реальний, і його слід зважувати щодо власної зрілості реєстру, а не щодо маркетингу Executor. Проєкт однієї людини (93% комітів від одного учасника, виміряно 2026-07-29) на версії до 1.0 має інший профіль ризику, ніж YAML-файл, яким володіє ваша команда й який можна прочитати від початку до кінця за десять хвилин. Сприймайте Executor як те, до чого зрештою зводиться ручний реєстр, коли йому потрібні спільний доступ для кількох агентів і непряме звернення до облікових даних, а не як готову заміну робочому процесу вище. Повна оцінка, зокрема розрив між баченням і поставленим кодом та деталі щодо bus factor: [`docs/resource-evaluations/executor-integration-governance-layer.md`](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/docs/resource-evaluations/executor-integration-governance-layer.md).

## 5. Впровадження політик у масштабі

Наявність політики не означає її автоматичне виконання. Цей розділ описує те, як зробити так, щоб корпоративні правила реально працювали у команді з 10–100 розробників.

### 5.1 Централізована дистрибуція конфігурацій

**Головний принцип**: Конфігурація управління та обмежень зберігається в репозиторії проєкту, а не локально на комп'ютерах розробників.

```

├── .claude/
│   ├── settings.json            ← спільні налаштування (залежно від рівня)
│   ├── mcp-registry.yaml        ← реєстр схвалених MCP
│   ├── hooks/
│   │   ├── governance-check.sh  ← перевірка реєстру MCP
│   │   ├── session-logger.sh    ← ведення аудит-логу
│   │   └── velocity-governor.sh ← обмеження швидкості запитів
│   └── agents/
│       └── security-reviewer.md ← спільний агент для рев'ю безпеки
├── templates/
│   ├── CLAUDE.md.starter        ← шаблони CLAUDE.md для кожного рівня
│   ├── CLAUDE.md.standard
│   ├── CLAUDE.md.strict
│   └── CLAUDE.md.regulated
└── scripts/
    └── setup-project.sh         ← скрипт розгортання потрібного рівня в новий проєкт
```

### 5.3 Автоматизований аудит відповідності

Скрипт періодичної автоматизованої перевірки конфігурації на наявність змін ("дрейфу"):

```bash
#!/bin/bash
# scripts/claude-governance-audit.sh
# Запускається щотижня через CI/CD або cron

PASS=0
FAIL=0
WARN=0

check() {
  local name="$1"
  local result="$2"
  local severity="${3:-FAIL}"

  if [[ "$result" == "OK" ]]; then
    echo "  PASS: $name"
    ((PASS++))
  else
    echo "  $severity: $name — $result"
    [[ "$severity" == "FAIL" ]] && ((FAIL++)) || ((WARN++))
  fi
}

echo "=== Аудит управління Claude Code ==="
echo ""

# Перевірка: наявність та фіксація settings.json
echo "1. Конфігурація репозиторію"
[[ -f ".claude/settings.json" ]] \
  && check "settings.json присутній" "OK" \
  || check "settings.json присутній" "Відсутній — корпоративне управління не діє" "FAIL"

git ls-files --error-unmatch .claude/settings.json &>/dev/null \
  && check "settings.json додано в git" "OK" \
  || check "settings.json додано в git" "Не відстежується в git — налаштування не застосуються до команди" "WARN"

# Перевірка: правила блокування секретів
echo ""
echo "2. Захист секретів"
if [[ -f ".claude/settings.json" ]]; then
  jq -e '.permissions.deny[]? | select(test("env|pem|key"))' \
    .claude/settings.json &>/dev/null \
    && check "Правила захисту .env" "OK" \
    || check "Правила захисту .env" "Відсутні обмеження для .env або файлів ключів" "FAIL"
fi

# Перевірка: встановлення та виконання хуків
echo ""
echo "3. Стек хуків"
for hook in ".claude/hooks/governance-check.sh"; do
  if [[ -f "$hook" ]]; then
    [[ -x "$hook" ]] \
      && check "$hook має права на виконання" "OK" \
      || check "$hook має права на виконання" "Немає прав на виконання — запустіть chmod +x $hook" "FAIL"
  else
    check "$hook присутній" "Відсутній" "WARN"
  fi
done

# Перевірка: наявність реєстру MCP
echo ""
echo "4. Управління MCP"
[[ -f ".claude/mcp-registry.yaml" ]] \
  && check "Реєстр MCP присутній" "OK" \
  || check "Реєстр MCP присутній" "Немає реєстру — використання MCP не контролюється" "WARN"

# Перевірка: наявність та відстеження CLAUDE.md
echo ""
echo "5. Документація"
[[ -f "CLAUDE.md" ]] || [[ -f ".claude/CLAUDE.md" ]] \
  && check "CLAUDE.md присутній" "OK" \
  || check "CLAUDE.md присутній" "Відсутній — немає контексту проєкту для ШІ" "WARN"

echo ""
echo "=== Підсумки аудиту ==="
echo "  Успішно (Passed):  $PASS"
echo "  Помилок (Failed):   $FAIL (вимагає виправлення)"
echo "  Попереджень (Warn): $WARN (бажано виправити)"
echo ""

[[ $FAIL -gt 0 ]] && exit 1 || exit 0
```

## 6. Аудит, відповідність та структура управління

### 6.1 Що насправді запитують аудитори SOC2 та ISO27001

Під час перевірки використання інструментів штучного інтелекту аудитори зазвичай вимагають підтвердження наявності таких контролів:

| Питання аудитора | Що вони хочуть бачити | Реалізація в Claude Code |
|-----------------|----------------------|---------------------------|
| "Чи маєте ви затверджену політику використання ШІ?" | Письмову хартію, підписану або погоджену розробниками | `docs/ai-usage-charter.md` + чек-лист онбордингу |
| "Як ви контролюєте передачу даних стороннім ШІ-вендорам?" | Схему класифікації даних + технічні обмеження | Правила `permissions.deny` для файлів із конфіденційними даними |
| "Як ви перевіряєте сторонні компоненти ШІ?" | Процес схвалення + актуальний реєстр компонентів | Реєстр схвалених MCP-серверів + покроковий процес погодження |
| "Чи ведеться у вас аудиторський лог дій ШІ?" | Журнал запущених інструментів та прочитаних файлів | Лог-файли сесій JSONL + скрипт `compliance-audit-logger.sh` |
| "Як ви проводите рев'ю коду, створеного ШІ?" | Процес перевірки коду з обов'язковим декларуванням ШІ | Шаблони Pull Request + правила атрибуції коду |
| "Які ваші дії у випадку інциденту безпеки з ШІ?" | Регламент реагування на інциденти (Incident Response) | Стандартний процес реагування компанії з додаванням ШІ-специфіки |

**Для SOC2**: Відповідні критерії довірчих послуг (Trust Services Criteria) — це CC6.1 (контроль логічного доступу), CC6.3 (видалення доступу), CC7.1 (моніторинг) та CC9.2 (управління ризиками постачальників). Ваше управління Claude Code має чітко відповідати цим пунктам.

**Для ISO27001**: Відповідні контроли Додатка А включають А.8.3 (обмеження доступу до інформації), А.8.24 (використання криптографії), А.8.25 (безпечний життєвий цикл розробки) та А.5.23 (інформаційна безпека під час використання хмарних сервісів).

### 6.2 Налаштування аудиторського сліду (Audit Trail)

Сесії Claude Code автоматично записуються до каталогу `~/.claude/projects/<project>/*.jsonl`. Головне завдання для комплаєнсу — зробити ці логи:
1. Доступними для аналізу (вони не повинні зникати після звільнення розробника).
2. Захищеними від несанкціонованих змін (редагування заднім числом).
3. Зручними для швидкого пошуку та аналізу.

**Мінімальний лог аудиту (без використання стороннього ПЗ)**:

```bash
#!/bin/bash
# .claude/hooks/compliance-audit-logger.sh
# Подія: PostToolUse (для всіх інструментів)
# Додає структуровані записи про дії в загальний лог

LOG_DIR="${COMPLIANCE_LOG_DIR:-/var/log/claude-audit}"
LOG_FILE="$LOG_DIR/$(date +%Y-%m-%d).jsonl"

mkdir -p "$LOG_DIR"

INPUT=$(cat)
TOOL=$(echo "$INPUT" | jq -r '.tool.name // "unknown"')
USER=$(whoami)
PROJECT=$(basename "$PWD")
TIMESTAMP=$(date -u +"%Y-%m-%dT%H:%M:%SZ")

echo "{\"timestamp\":\"$TIMESTAMP\",\"user\":\"$USER\",\"project\":\"$PROJECT\",\"tool\":\"$TOOL\"}" \
  >> "$LOG_FILE"
```

**Відправка логів до незмінюваного сховища** (наполегливо рекомендовано для регульованих середовищ):

```bash
# Щоденно: синхронізація логів сесій у захищений s3-бакет
aws s3 sync ~/.claude/projects/ \
  s3://your-audit-bucket/claude-sessions/$(whoami)/ \
  --storage-class GLACIER_INSTANT_RETRIEVAL \
  --exclude "*.tmp"
```

**Для побудови повного аудиторського сліду** з можливістю створення контрольних шлюзів розгляньте використання Entire CLI — він фіксує повний контекст сесій (промпти, міркування, виклики інструментів, diff-зміни) із криптографічним зв'язуванням із git-комітами. Для вибору цього або альтернативних рішень зверніться до розділу [AI Traceability §5.1](../ops/ai-traceability.uk.md#51-entire-cli).

### 6.3 Комітет з управління ШІ (AI Governance Committee)

Для організацій, які керують ризиками ШІ в масштабі, створення легковагового Комітету з управління ШІ забезпечує саме ту структуру підзвітності, яку очікують побачити аудитори. Це інструмент координації та допомоги розробникам, а не бюрократична перешкода.

**Мінімальна структура комітету** (ефективна для команд від 10 до 100 розробників):

| Роль у комітеті | Хто займає | Сфера відповідальності |
|------|--------|----------------|
| **Governance Lead** | Engineering Manager або Lead | Оновлення політик, щоквартальний перегляд конфігурацій, ескалація питань |
| **Security Rep** | SecEng або DevSecOps | Аналіз ризиків MCP, реагування на інциденти безпеки |
| **Dev Rep** | Ротація Senior-розробників (термін 3 місяці) | Отримання фідбеку від команди, збереження балансу між безпекою та зручністю |
| **Compliance Rep** | Представник юридичного/комплаєнс-відділу | Адаптація хартії, відповідність регуляторним стандартам |

**Періодичність зустрічей**: Щоквартально (30 хвилин). Порядок денний зустрічі:
1. Рев'ю реєстру MCP — чи потрібно щось додати, видалити або змінити?
2. Розгляд інцидентів — чи були пов'язані з ШІ події безпеки з моменту минулої зустрічі?
3. Оновлення політики — які зміни чи уточнення слід внести в Хартію використання ШІ?
4. Оцінка метрик — результати автоматизованих аудитів, стан комплаєнсу.

Детальні інструкції щодо RACI-матриць, побудови та взаємодії Комітету з управління ШІ див. у спеціалізованому матеріалі Whitepaper #11: Enterprise AI Governance.

### 6.4 Моніторинг відповідності (Compliance Monitoring)

Рівень моніторингу та спостереження детально описано у посібнику [observability.uk.md](../ops/observability.uk.md). Для цілей перевірки відповідності стандартам безпеки найбільш корисними є такі пошукові запити:

```bash
# До яких файлів звертався Claude за останні 30 днів?
# macOS: date -v-30d; Linux: date -d '30 days ago'
if [[ "$OSTYPE" == "darwin"* ]]; then
  SINCE=$(date -v-30d +%Y-%m-%d)
else
  SINCE=$(date -d '30 days ago' +%Y-%m-%d)
fi

find ~/.claude/projects/ -name "*.jsonl" -newer "$SINCE" | \
  xargs jq -r 'select(.type == "assistant") |
    .message.content[]? |
    select(.type == "tool_use" and .name == "Read") |
    .input.file_path' 2>/dev/null | sort -u

# Чи були спроби доступу до конфіденційних файлів/шаблонів?
# (Запустіть запит вище та перенаправте через grep)
grep -E '\.(env|pem|key)$|secrets/|credentials'

# CLI-команди Bash, які виконував Claude протягом цього тижня
if [[ "$OSTYPE" == "darwin"* ]]; then
  SINCE_WEEK=$(date -v-7d +%Y-%m-%d)
else
  SINCE_WEEK=$(date -d '7 days ago' +%Y-%m-%d)
fi

find ~/.claude/projects/ -name "*.jsonl" -newer "$SINCE_WEEK" | \
  xargs jq -r 'select(.type == "assistant") |
    .message.content[]? |
    select(.type == "tool_use" and .name == "Bash") |
    .input.command' 2>/dev/null | sort
```

## Швидкий довідник (Quick Reference)

### Вибір рівня обмежень

| Ваша ситуація | Рекомендований рівень | Час на запуск |
|----------------|------|------------|
| Pet-проєкт, особисте використання | Starter | 10 хв |
| Мала команда, внутрішній проєкт | Starter | 10 хв |
| Команда 5–20 осіб, будь-який продакшн-код | Standard | 45 хв |
| Команда 20+ осіб, робота з даними клієнтів | Strict | 2 год |
| Регульована індустрія (HIPAA/SOC2/PCI) | Regulated | Пів дня |

### Рівні зрілості управління ШІ (AI Governance Maturity Levels)

| Рівень зрілості | Що у вас уже впроваджено | Чого вам бракує |
|----------|---------------|----------------|
| **Ad hoc (Хаотичний)** | Кожен розробник налаштовує інструмент самостійно | Узгодженості, загальної підзвітності |
| **Basic (Базовий)** | Спільний CLAUDE.md + загальний settings.json | Управління MCP, аудиторського сліду |
| **Managed (Керований)** | + реєстр схвалених MCP + робочі хуки безпеки | Регулярної комплаєнс-звітності |
| **Compliant (Відповідний)** | + логування сесій + підписана Хартія + регулярний перегляд | Нічого критичного |
| **Audited (Аудійований)** | + зовнішня валідація політик + повна простежуваність | — |

### Типові помилки та способи їх усунення

| Помилка | Спосіб усунення |
|---------|-----|
| Налаштування безпеки збережені лише в `~/.claude` (локально) | Перенесіть конфігурацію в директорію `.claude/` у вашому репозиторії |
| Особисті `permissions.allow` обходять `deny` команди | Впровадьте щоквартальний аудит особистих конфігурацій розробників |
| Відсутність реєстру MCP → кожен ставить свої плагіни | Створіть файл реєстру, навіть якщо у ньому буде лише 3 записи |
| Файл CLAUDE.md занадто великий → Claude ігнорує правила | Тримайте розмір файлу в межах 8 КБ, фокусуйтеся лише на головному |
| Аудитори просять лог дій ШІ → нічого не зберігається | Налаштуйте щоденну синхронізацію логів сесій JSONL у захищений S3-бакет |
