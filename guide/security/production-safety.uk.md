# Правила безпеки в продакшені

> **Цільова аудиторія**: Команди, що розгортають Claude Code у продакшн-середовищах.
> **Для індивідуального навчання**: Замість цього див. розділ [Початок роботи](#getting-started).

---

## TL;DR (30 секунд)

**6 обов'язкових до виконання правил для продакшн-команд**:

1. ✅ **Стабільність портів**: Ніколи не змінюйте порти бекенду/фронтенду
2. ✅ **Безпека баз даних**: Завжди робіть бекап перед деструктивними операціями
3. ✅ **Повнота функціоналу**: Ніколи не випускайте наполовину реалізовані фічі
4. ✅ **Блокування інфраструктури**: Зміни у Docker або конфігураціях оточення вимагають дозволу
5. ✅ **Безпека залежностей**: Жодних нових залежностей без узгодження
6. ✅ **Дотримання патернів**: Відповідність існуючим конвенціям кодової бази

---

## Коли використовувати ці правила

| Тип проекту | Використовувати ці правила? | Чому |
|--------------|------------------|-----|
| Навчання / Туторіали | ❌ Ні | Занадто суворо для досліджень та експериментів |
| Соло-прототипи | ❌ Ні | Накладні витрати не виправдовують себе |
| Малі команди (2-3 розробники), staging-оточення | ⚠️ Частково | Тільки правила 1, 3 та 6 |
| Продакшн-додатки, команди з багатьма розробниками | ✅ Так | Усі 6 правил |
| Регульовані галузі (HIPAA, SOC2) | ✅ Так + додати правила комплаєнсу | Критично важлива безпека |

## Правило 1: Стабільність портів

### Проблема

Зміна портів ламає:
- Локальні середовища розробки
- Конфігурації Docker Compose
- Налаштування розгорнутих сервісів
- Робочі середовища інших членів команди

**Реальний інцидент**: Під час рефакторингу порт бекенду було змінено з 3000 на 8080. Усі розробники втратили день на переналаштування локальних середовищ. Деплой на staging тихо провалився, оскільки проксі nginx все ще вказував на порт 3000.

### Правило

**Ніколи не змінюйте порти бекенду чи фронтенду без прямого дозволу команди.**

### Реалізація

**Варіант А: Заборона дозволів (deny) у settings.json**

```json
{
  "permissions": {
    "deny": [
      "Edit(docker-compose.yml:*ports*)",
      "Edit(package.json:*PORT*)",
      "Edit(.env.example:*PORT*)",
      "Edit(vite.config.ts:*port*)"
    ]
  }
}
```

**Варіант Б: Хук PreToolUse**

```bash
# .claude/hooks/PreToolUse.sh
if [[ "$TOOL" == "Edit" ]]; then
    FILE=$(echo "$INPUT" | jq -r '.tool.input.file_path')
    CONTENT=$(echo "$INPUT" | jq -r '.tool.input.new_string')

    if [[ "$FILE" =~ (docker-compose|vite.config|package.json) ]] && \
       [[ "$CONTENT" =~ (port|PORT):[[:space:]]*[0-9] ]]; then
        echo "⚠️ BLOCKED: Port modification detected in $FILE"
        echo "Ports must remain stable across team. Request permission first."
        exit 2
    fi
fi
```

**Варіант В: Обмеження в CLAUDE.md**

```markdown
## Налаштування портів (Port Configuration)

**КРИТИЧНО**: Порти заблоковані для координації команди.

Поточні порти:
- Frontend (Vite): 5173
- Backend (Express): 3000
- Database: 5432

Для зміни портів:
1. Створіть документ RFC у `/docs/rfcs/`
2. Отримайте схвалення команди (3+ ревьюера)
3. Оновіть усі середовища одночасно
4. Повідомте команду за 48 годин до змін
```

### Граничні випадки (Edge Cases)

| Сценарій | Поведінка |
|----------|----------|
| Додавання НОВОГО сервісу | OK (не ламає існуючі) |
| Зміна порту тестового оточення | OK (ізольовано від розробки/продакшену) |
| Конфлікт портів на машині | Попросіть користувача вирішити локально (.env.local) |

## Правило 2: Безпека баз даних

### Проблема

Випадкові видалення у продакшені призводять до незворотної втрати даних.

**Реальні інциденти**:
- `DELETE FROM users WHERE id = 123` ➔ забули вказати `WHERE` ➔ видалено всіх користувачів
- `DROP TABLE sessions` під час очищення ➔ видалено таблицю у продакшені
- Відкат міграції (rollback) ➔ втрата даних через відсутність резервної копії

### Правило

**Завжди створюйте резервну копію (бекап) перед виконанням деструктивних операцій.**

Деструктивні операції:
- `DELETE FROM` (без `LIMIT 1`)
- `DROP TABLE`
- `TRUNCATE`
- `ALTER TABLE ... DROP COLUMN`
- Міграції бази даних, які не підтримують безпечний відкат (rollback)

### Реалізація

**Варіант А: Хук PreToolUse із примусовим створенням бекапу**

```bash
# .claude/hooks/PreToolUse.sh
#!/bin/bash
INPUT=$(cat)
TOOL=$(echo "$INPUT" | jq -r '.tool.name')

if [[ "$TOOL" == "Bash" ]]; then
    COMMAND=$(echo "$INPUT" | jq -r '.tool.input.command')

    # Виявлення деструктивних операцій з базою даних
    if [[ "$COMMAND" =~ (DROP TABLE|DELETE FROM|TRUNCATE|ALTER.*DROP) ]]; then
        echo "🚨 BLOCKED: Destructive database operation detected"
        echo ""
        echo "Required steps:"
        echo "1. Create backup: pg_dump -U user dbname > backup_\$(date +%Y%m%d_%H%M%S).sql"
        echo "2. Verify backup size is reasonable"
        echo "3. Re-run after backup confirmation"
        exit 2
    fi
fi

exit 0
```

**Варіант Б: Безпечна обгортка для міграцій**

```bash
# scripts/safe-migrate.sh
#!/bin/bash
set -e

echo "🔍 Pre-migration checks..."

# 1. Перевірка середовища
if [[ "$NODE_ENV" == "production" ]]; then
    echo "❌ BLOCKED: Use migration service for production"
    exit 1
fi

# 2. Створення бекапу
BACKUP_FILE="backups/pre-migration-$(date +%Y%m%d_%H%M%S).sql"
mkdir -p backups
pg_dump $DATABASE_URL > "$BACKUP_FILE"
echo "✅ Backup created: $BACKUP_FILE"

# 3. Запуск міграції
echo "🚀 Running migration..."
npm run prisma:migrate:dev

# 4. Валідація
echo "🔍 Verifying database state..."
npm run prisma:validate

echo "✅ Migration complete. Backup: $BACKUP_FILE"
```

**Варіант В: Протокол у CLAUDE.md**

```markdown
## Операції з базою даних

### Протокол деструктивних операцій

**НІКОЛИ не запускайте їх без бекапу**:
- DELETE, DROP, TRUNCATE, ALTER...DROP

**Обов'язкові кроки**:
1. Анонсуйте дію в Slack-каналі #dev-ops
2. Створіть бекап: `./scripts/backup-db.sh`
3. Перевірте бекап: `ls -lh backups/` (має бути > 0 байт)
4. Спочатку виконайте на staging
5. Зачекайте 24 години на виявлення можливих проблем
6. Виконайте на продакшені в присутності чергового інженера

**Аварійний відкат (Emergency rollback)**:
```bash
psql $DATABASE_URL < backups/[latest].sql
```
```

### Безпека баз даних в MCP

Якщо використовуються MCP-сервери баз даних (Postgres, MySQL тощо):

```json
{
  "mcpServers": {
    "database": {
      "command": "npx",
      "args": ["@modelcontextprotocol/server-postgres"],
      "env": {
        "POSTGRES_URL": "postgres://readonly:***@dev-db.example.com:5432/appdb"

    }
  }

```

**Критично важливо**: Використовуйте користувачів баз даних із правами тільки для читання (read-only) для MCP. Див. [Посібник із конфіденційності даних](./data-privacy.uk.md#risk-2-mcp-database-access).

## Правило 3: Повнота функціоналу

### Проблема

Коли контекст стає замалим, Claude Code іноді схильний "халтурити" або спрощувати реалізацію фіч:
- Видаляє існуючий функціонал замість виправлення багів
- Залишає коментарі `TODO` для критично важливої логіки
- Не обробляє стани помилок
- Використовує заглушки (mock-реалізації) в продакшн-коді

**Реальні інциденти**:
- Валідація платежів "виправлена" шляхом повного видалення валідації
- Обробка помилок "додана" через рядок `throw new Error("Not implemented")`
- Реалізація фічі "завершена" коментарем `// TODO: Add actual logic here`

### Правило

**Ніколи не випускайте наполовину реалізовані фічі. Якщо ви почали роботу, доведіть її до повністю робочого стану.**

### Реалізація

**Варіант А: Обмеження в CLAUDE.md**

```markdown
## Стандарти реалізації фіч

### ОБОВ'ЯЗКОВО ДО ВИКОНАННЯ

1. **Жодних TODO для базової функціональності**
   - TODO дозволені ТІЛЬКИ для майбутніх покращень
   - Основні фічі мають бути повністю завершеними та працездатними

2. **Жодних заглушок (mock-реалізацій)**
   - Жодних `throw new Error("Not implemented")`
   - Жодних фейкових генераторів даних у продакшн-коді

3. **Повна обробка помилок**
   - Кожен асинхронний виклик має бути обгорнутий у try/catch
   - Усі вхідні дані користувача проходять валідацію
   - Кожен виклик API містить таймаути та логіку повторних спроб (retry)

4. **Даунгрейд = Повне видалення фічі**
   - Якщо ви не можете виправити фічу належним чином, видаліть її
   - Задокументуйте причину в повідомленні коміту
   - Створіть тікет для повноцінної реалізації згодом

### Валідація

Перед прийняттям змін перевірте:
- [ ] Відсутність `TODO` у змінених файлах (крім майбутніх покращень)
- [ ] Відсутність `throw new Error("Not implemented")`
- [ ] Відсутність закоментованого коду без пояснень
- [ ] Наявність обробки помилок у всіх нових функціях
```

**Варіант Б: Git-хук перед комітом**

```bash
# .git/hooks/pre-commit
#!/bin/bash

# Перевірка проіндексованих файлів на наявність "халтурних" патернів
STAGED=$(git diff --cached --name-only --diff-filter=ACM)

for FILE in $STAGED; do
    if [[ "$FILE" =~ \.(ts|tsx|js|jsx|py)$ ]]; then
        # Не перевіряємо тести
        if ! [[ "$FILE" =~ test|spec ]]; then
            if git diff --cached "$FILE" | grep -E "^\+.*TODO.*implement|^\+.*Not implemented"; then
                echo "❌ COMMIT BLOCKED: TODO/Not implemented in $FILE"
                echo "   Complete the feature or remove it entirely."
                exit 1
            fi
        fi

        # Перевірка тимчасових заглушок
        if git diff --cached "$FILE" | grep -E "^\+.*(MOCK_DATA|fakeData|placeholder)"; then
            echo "⚠️ WARNING: Mock data detected in $FILE"
            echo "   Ensure this is intentional for staging/dev only."
        fi
    fi
done

exit 0
```

**Варіант В: Команда оцінки результату**

```bash

# - Коректність (10/10)
# - Повнота (10/10)  ← Виявляє недоробки
# - Безпека (10/10)
```

## Правило 4: Блокування інфраструктури

### Проблема

Claude може змінити конфігурації інфраструктури, не розуміючи їхнього впливу на продакшн:
- Зміна томів (volumes) у Docker Compose ➔ втрата даних
- Зміна шаблону `.env.example` ➔ збій онбордингу нових розробників
- Оновлення Terraform ➔ неочікувані зміни хмарних ресурсів
- Зміна маніфестів Kubernetes ➔ простої сервісів (downtime)

### Правило

**Модифікація інфраструктури вимагає явного дозволу команди.**

Файли, які потрібно захистити:
- `docker-compose.yml`, `Dockerfile`
- `.env.example` (шаблони, але НЕ особистий .env.local)
- каталоги `kubernetes/`, `k8s/`, `terraform/`, `helm/`
- Налаштування CI/CD (`.github/workflows/`, `.gitlab-ci.yml`)
- Схеми баз даних (вимагають ретельного огляду міграцій)

### Реалізація

**Варіант А: Заборона дозволів (deny)**

```json
{
  "permissions": {
    "deny": [
      "Edit(docker-compose.yml)",
      "Edit(Dockerfile)",
      "Edit(.env.example)",
      "Edit(terraform/**)",
      "Edit(kubernetes/**)",
      "Edit(.github/workflows/**)",
      "Edit(prisma/schema.prisma)"
    ]
  }
}
```

**Варіант Б: Правило в CLAUDE.md**

```markdown
## Зміни в інфраструктурі

Вам **ЗАБОРОНЕНО** змінювати ці файли без явного дозволу користувача:

- `docker-compose.yml`, `Dockerfile`
- `.env.example` (шаблон конфігурацій для нових розробників)
- `terraform/`, `kubernetes/` (інфраструктура як код)
- `.github/workflows/` (пайплайни CI/CD)
- `prisma/schema.prisma` (схема бази даних)

**Якщо необхідні зміни в інфраструктурі**:
1. Запитайте користувача: "Це потребує зміни інфраструктури. Мені створити RFC?"
2. Створіть документ RFC у `docs/rfcs/YYYYMMDD-<назва>.md`
3. НЕ змінюйте файли до затвердження RFC
```

**Примітка**: Особисті файли `.env.local` змінювати можна (вони знаходяться у списку .gitignore).

## Правило 5: Безпека залежностей

### Проблема

Додавання залежностей без узгодження з командою:
- Збільшує розмір збірки (погіршує продуктивність)
- Приносить нові вразливості в безпеці
- Створює проблеми із сумісністю ліцензій ПЗ
- Збільшує витрати на подальшу підтримку

**Реальні інциденти**:
- Додано бібліотеку `moment.js` (200KB), хоча в проекті вже використовувалася легка `date-fns`
- Встановлено `lodash`, хоча проект стандартизований під `ramda`
- Додано бібліотеку з ліцензією GPL ➔ порушення ліцензійних вимог у комерційному коді

### Правило

**Жодних нових залежностей без явного схвалення команди.**

### Реалізація

**Варіант А: Заборона використання менеджерів пакетів**

```json
{
  "permissions": {
    "deny": [
      "Bash(npm install *)",
      "Bash(npm i *)",
      "Bash(pnpm add *)",
      "Bash(yarn add *)",
      "Bash(pip install *)",
      "Bash(poetry add *)"
    ],
    "allow": [
      "Bash(npm install)",
      "Bash(pnpm install)",
      "Bash(pip install -r requirements.txt)"
    ]
  }
}
```

**Варіант Б: Протокол у CLAUDE.md**

```markdown
## Керування залежностями

### Правило незмінного стеку (Immutable Stack Rule)

**Вам ЗАБОРОНЕНО додавати нові залежності** (`npm install <package>`).

**Якщо нова залежність дійсно необхідна**:
1. Перевірте, чи можна вирішити задачу існуючими засобами:
   - Робота з датами? Використовуйте існуючу `date-fns`
   - Запити HTTP? Використовуйте існуючий `axios`
   - Керування станом? Використовуйте існуючий `zustand`
2. Якщо альтернативи немає, ЗАПИТАЙТЕ:
   - "Мені потрібен пакет [назва] для [причина]. Існуючі альтернативи: [X, Y]. Можна його додати?"
3. Очікуйте явного схвалення
4. Користувач виконає `npm install <package>` вручну

**Дозволено без запиту**:
- `npm install` (встановлення вже існуючих залежностей із package.json)
- Dev-залежності для тестування (прапорець `-D` після схвалення)
```

**Варіант В: Хук PreToolUse**

```bash
# .claude/hooks/PreToolUse.sh
if [[ "$TOOL" == "Bash" ]]; then
    COMMAND=$(echo "$INPUT" | jq -r '.tool.input.command')

    # Блокування встановлення нових залежностей
    if [[ "$COMMAND" =~ (npm|pnpm|yarn)[[:space:]]+(install|add|i)[[:space:]]+[a-zA-Z] ]]; then
        echo "🚨 BLOCKED: New dependency installation"
        echo ""
        echo "Dependencies must be approved by team lead."
        echo "Create PR with RFC explaining:"
        echo "1. Why this dependency is needed"
        echo "2. Alternatives considered"
        echo "3. Bundle size impact"
        echo "4. License compatibility"
        exit 2
    fi

    # Дозволити: npm install (без аргументів), npm install -g, pnpm install
    if [[ "$COMMAND" =~ ^(npm|pnpm|yarn)[[:space:]]+install$ ]]; then
        exit 0
    fi
fi
```

## Правило 6: Дотримання патернів

### Проблема

Claude може впровадити нові підходи чи патерни, невідповідні поточному стилю коду:
- Використовує React-компоненти на класах, хоча проект побудований на функціональних компонентах
- Імпортує `lodash`, коли в проекті затверджено використання `ramda`
- Створює REST-ендпоінти, коли стандартом проекту є GraphQL
- Використовує `fetch()`, коли кодова база стандартизована під `axios`

### Правило

**Суворо дотримуйтеся існуючих конвенцій кодової бази. Перевіряйте стиль перед реалізацією.**

### Реалізація

**Варіант А: Конвенції в CLAUDE.md**

```markdown
## Стиль та конвенції коду

### Технологічний стек (ВІДХИЛЕННЯ ЗАБОРОНЕНІ)

**Frontend**:
- React 18 з **функціональними компонентами та хуками** (ЖОДНИХ компонентів на класах)
- Стан: Zustand (НЕ Redux, НЕ Context)
- HTTP: axios (НЕ fetch)
- Стилізація: Tailwind CSS (НЕ styled-components, НЕ emotion)
- Форми: React Hook Form + Zod

**Backend**:
- Node.js + Express
- База даних: Prisma ORM (НЕ сирий SQL, НЕ TypeORM)

## Правило 7: Парадокс верифікації

### Проблема

Коли ШІ успішно виконує роботу в 99% випадків, традиційна перевірка людиною стає менш уважною та вразливою.

**Формулювання парадоксу**: Зі збільшенням надійності ШІ якість перевірки людиною падає.

- **Втома пильності**: Рідкісні помилки (1%) легко пропускаються розробниками, які підсвідомо довіряють результатам ШІ
- **Звикання до безпомилковості**: Ручний контроль послаблюється, оскільки розробники перестають чекати помилок
- **Хибна впевненість**: "Це працювало попередні 50 разів" створює сліпу зону для 51-ї помилки
- **Когнітивне навантаження**: Люди не пристосовані для ефективного та тривалого виявлення помилок із ймовірністю 1 до 100

**Реальні інциденти**:
- Валідація платежів була пропущена ШІ після 200 успішних транзакцій ➔ виникло шахрайство на 201-й транзакції
- Перевірка безпеки була пропущена розробником, бо "ШІ завжди робить авторизацію правильно" ➔ витік облікових даних
- Тести проходили у 99% випадків ➔ продакшн-баг виник саме у тому 1% кейсів, який не покрили тестами

**Джерело**: [Інженерна команда Alan (Charles Gorintin, Maxime Le Bras), лютий 2026 р.](https://www.linkedin.com/pulse/le-principe-de-la-tour-eiffel-et-ralph-wiggum-maxime-le-bras-psmxe/)

### Правило

**Будуйте автоматизовані системи перевірки замість того, щоб покладатися виключно на пильність людини.**

Коли надійність ШІ перевищує ~95%, перенесіть фокус із ручного огляду на автоматичні інструменти захисту (guardrails).

### Антипатерни проти кращих підходів

| Антипатерн | Кращий підхід |
|--------------|-----------------|
| Ручний перегляд кожного рядка виводу ШІ | Автоматичні тестові сюїти + точковий аудит |
| Довіра, тому що "минулого разу це спрацювало" | Контракти верифікації (тести, типи, лінтери) |
| Людина як єдиний детектор помилок | Захисні бар'єри з принципом швидкої відмови (fail-fast в CI/CD) |
| Стратегія випадкової перевірки для частих операцій | Повна автоматизована валідація змін |
| Втома рев'юера = зниження стандартів з часом | Стабільні автоматизовані планки якості |

### Реалізація

**Варіант А: Стек автоматизованої перевірки (Guardrail Stack)**

      - name: Unit tests
        run: npm run test            # Перевіряє поведінкові контракти коду

**Варіант Б: Контракти верифікації в CLAUDE.md**

```markdown
## Протокол верифікації (Verification Protocol)

### НІКОЛИ не покладайтеся виключно на ручний огляд розробником

**Обов'язкова автоматизована перевірка**:
1. **Типізація**: команда `npm run typecheck` має завершуватися з 0 помилок
2. **Тести**: покриття коду тестами `npm run test` має бути ≥ 80% для нових змін
3. **Лінтер**: запуск `npm run lint` має проходити без жодного попередження (zero warnings)
4. **Безпека**: `npm audit` не повинна показувати вразливостей високого чи критичного рівнів
5. **Продуктивність**: показник Lighthouse для змінених сторінок має бути ≥ 90

**Ручний огляд розробника потрібен для**:
- Архітектурних рішень
- Оцінки UX/дизайну
- Валідації бізнес-логіки
- Нестандартних граничних випадків, які важко автоматизувати

**Ручний огляд розробника НЕ потрібен для**:
- Синтаксичних помилок (використовуйте лінтери)
- Помилок типізації (використовуйте TypeScript)
- Падіння продуктивності (використовуйте автоматичні бенчмарки)
- Питань безпеки залежностей (використовуйте автоматичні сканери)
```

# 1. Типізація

### Граничні випадки (Edge Cases)

| Сценарій | Поведінка |
|----------|----------|
| ШІ пише бездоганний код у 99.9% випадків | ВСЕ ОДНО запускайте автоматизацію (парадокс діє навіть при 99.9%) |
| Брак часу, "потрібно терміново релізити" | Автоматизація не підлягає обговоренню (швидкість ≠ ігнорування безпеки) |
| Дрібні зміни (виправлення описки) | Запускайте автоматизацію (описки також можуть зламати продакшн) |
| Терміновий хотфікс (Emergency hotfix) | Автоматизація ОБОВ'ЯЗКОВА (стрес = вища ймовірність помилки людини) |

### Чому це важливо

**Стара модель (до епохи ШІ)**:
- Якість коду = експертиза людини + ретельний огляд
- Помилки відловлюються досвідченими розробниками під час читання коду
- Якість рев'ю залишається відносно стабільною

**Нова модель (з асистентами ШІ)**:
- ШІ створює високоякісний код у 95%+ випадків
- Люди розслабляються ("ШІ зазвичай робить все правильно")
- 5% помилок непомітно проходять через стомлене ручне рев'ю

**Рішення**: Автоматизуйте нудну перевірку (синтаксис, типи, тести), збережіть фокус уваги людини на творчому та стратегічному аналізі.

### Інтеграція з іншими правилами

- **Правило 3 (Повнота функціоналу)**: Автоматичні тести гарантують, що фіча завершена
- **Правило 2 (Безпека баз даних)**: Тести міграцій виявляють деструктивні операції
- **Правило 6 (Дотримання патернів)**: Лінтери автоматично контролюють конвенції стилю

Дзеркальним відображенням цього парадоксу на боці агента є патерн "Розрив верифікації" (Verification Gap), описаний у [робочому процесі TDD](../workflows/tdd-with-claude.uk.md#the-verification-gap).

## Усунення несправностей (Troubleshooting)

### "Ці правила занадто обмежують роботу"

**Рішення**: Адаптуйте правила під розмір вашої команди та стадію проекту.

| Розмір команди | Рекомендовані правила |
|-----------|-------------------|
| 1-2 розробники | Тільки правила 1, 3, 6 |
| 3-10 розробників | Правила 1, 3, 5, 6 |
| 10+ розробників або продакшн | Усі 6 правил |

### "Claude постійно блокується безпекою"

**Рішення**: Безпекові правила працюють! Ваші варіанти дій:

1. **Надайте тимчасовий дозвіл**:
   ```markdown
   # В CLAUDE.md
   ## Тимчасовий дозвіл (діє до 2026-01-25)
   Для цієї конкретної фічі дозволено зміни в інфраструктурі.
   Причина: Налаштування нового мікросервісу.
   ```

2. **Створіть виключення у дозволах**:
   ```json
   {
     "permissions": {
       "allow": ["Edit(docker-compose.dev.yml)"],
       "deny": ["Edit(docker-compose.prod.yml)"]
     }
   }
   ```

3. **Перевірте доцільність правила**:
   - Соло-розробник блокує сам себе? ➔ Видаліть зайве обмеження
   - Команді потрібно більше гнучкості? ➔ Використовуйте режим "ask" замість жорсткого "deny"

### "Як поширити ці правила на всю команду?"

**Рішення**: Зберігайте їх у репозиторії проекту, а не у своїх локальних налаштуваннях.

```bash
# Спільні правила для всієї команди
/project/.claude/settings.json        # Комітиться у репозиторій
/project/CLAUDE.md                    # Комітиться у репозиторій

# Особисті налаштування розробника
/project/.claude/settings.local.json  # Знаходиться у .gitignore
/project/.claude/CLAUDE.md            # Знаходиться у .gitignore
```

Командні налаштування мають вищий пріоритет, але розробники можуть локально встановлювати ще суворіші правила для себе.

## Правило 6: Безпека автономних циклів (Autonomous Loop Safety)

### Проблема

Автономні цикли агентів — коли сесія Claude працює без нагляду протягом кількох годин, обробляючи чергу завдань або моніторячи систему, — мають неприємний режим збою, який важко відлагоджувати: процес *виглядає* запущеним, але насправді тихо завис. Жодних помилок. Жодних вихідних кодів помилки. Просто нічого не відбувається, поки ваш бюджет API продовжує витрачатися.

Це трапляється, коли:
- Claude входить у нескінченний логічний цикл міркувань без умови виходу
- Виклик інструменту зависає в очікуванні ресурсу, який раптово зник
- Сесія потрапляє в граничний випадок, який не видає результатів, але й не викликає збою

### Правило

**Для будь-якої автономної сесії, що має працювати довше кількох хвилин, обов'язково впроваджуйте механізм серцебиття (heartbeat). Якщо серцебиття припиняється, завершуйте весь процесовий пул (process group), а не лише батьківський процес.**

**Чому саме процесовий пул, а не тільки батько**: Claude Code породжує дочірні процеси (команди оболонки, виклики інструментів). Завершення лише батьківського процесу залишає "процеси-сироти", які продовжують споживати ресурси та виконувати дії без будь-якого контролю.

### Реалізація

**Запис серцебиття (Heartbeat writer)** — запускається всередині автономного циклу як хук PostToolUse:

```bash
#!/bin/bash
# .claude/hooks/autonomous-heartbeat.sh
# Хук PostToolUse: записує часову позначку після кожного виклику інструменту

HEARTBEAT_FILE="${CLAUDE_HEARTBEAT_FILE:-/tmp/claude-heartbeat-$$}"
date +%s > "$HEARTBEAT_FILE"
```

**Сторожовий таймер аварійного вимкнення (Dead-man watchdog)** — запускається як окремий процес паралельно з Claude:

```bash
#!/bin/bash
# scripts/watchdog.sh
# Використання: ./scripts/watchdog.sh <timeout_seconds> <pid>

TIMEOUT="${1:-30}"
TARGET_PID="${2:-}"
HEARTBEAT_FILE="${CLAUDE_HEARTBEAT_FILE:-/tmp/claude-heartbeat-$TARGET_PID}"

if [[ -z "$TARGET_PID" ]]; then
  echo "Usage: watchdog.sh <timeout_seconds> <pid>" >&2
  exit 1
fi

while true; do
  sleep 5

  if ! kill -0 "$TARGET_PID" 2>/dev/null; then
    echo "Watchdog: process $TARGET_PID has exited cleanly"
    exit 0
  fi

  if [[ -f "$HEARTBEAT_FILE" ]]; then
    LAST_BEAT=$(cat "$HEARTBEAT_FILE")
    NOW=$(date +%s)
    AGE=$(( NOW - LAST_BEAT ))

    if [[ "$AGE" -gt "$TIMEOUT" ]]; then
      echo "Watchdog: no heartbeat for ${AGE}s (limit: ${TIMEOUT}s) — killing process group"
      kill -TERM -"$TARGET_PID" 2>/dev/null || kill -TERM "$TARGET_PID"
      sleep 2
      kill -KILL -"$TARGET_PID" 2>/dev/null || true
      rm -f "$HEARTBEAT_FILE"
      exit 1
    fi
  fi
done
```

**Скрипт запуску (Launch script)**, який зв'язує їх разом:

```bash
#!/bin/bash
export CLAUDE_HEARTBEAT_FILE="/tmp/claude-heartbeat-$$"

claude --print "Process the task queue in tasks.json" &
CLAUDE_PID=$!

./scripts/watchdog.sh 30 "$CLAUDE_PID" &
WATCHDOG_PID=$!

wait "$CLAUDE_PID"
EXIT_CODE=$?

kill "$WATCHDOG_PID" 2>/dev/null
rm -f "$CLAUDE_HEARTBEAT_FILE"
exit "$EXIT_CODE"
```

### Налаштування таймауту

| Тип задачі | Рекомендований таймаут |
|-----------|-------------------|
| Прості операції з файлами | 15–30 с |
| Веб-запити, виклики API | 60 с |
| Компіляція коду, запуск тестів | 120 с |
| Тривалі дослідницькі завдання | 300 с |

Починайте з таймауту 30 секунд і збільшуйте його лише тоді, коли помічаєте обґрунтовані паузи у роботі, триваліші за встановлене значення.

### Коли це НЕ потрібно використовувати

- Інтерактивні сесії (коли ви самі стежите за екраном) — сторожовий таймер тут не потрібен
- Завдання, що тривають менше 5 хвилин — накладні витрати на налаштування не виправдані
- Пайплайни, де помилки очікуються та обробляються логікою повторних спроб (retry logic)

> **Подяка**: Патерн аварійного вимкнення "dead-man switch" на основі серцебиття для автономних агентів взято з посібника [Everything Claude Code Security Guide](https://github.com/affaan-m/everything-claude-code) від Affaan Mustafa. Ідея розділення сторожового таймера та завершення всього процесового пулу (process group) належить автору проекту.
