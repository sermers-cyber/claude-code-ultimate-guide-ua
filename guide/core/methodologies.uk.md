Цей документ є коротким довідником з 15 структурованих методологій розробки, які з'явилися для роботи з ШІ у 2025-2026 роках. Для отримання практичних інструкцій та воркфлоу див. [workflows/](../workflows/).

## Методологія не означає володіння harness

Методології визначають, як робота планується, перевіряється і вдосконалюється. Вони не визначають, чи володіє продукт циклом агента. Тримайте чотири шари окремо: модель генерує токени, runtime harness виконує цикл, repository harness дає специфічний для проєкту зворотний зв'язок, а оркестратор координує кілька запусків.

Використовуйте [Agent Harness Engineering](./agent-harness.uk.md) для цієї моделі та [Agent Harness Map](../ecosystem/agent-harness-landscape.uk.md), щоб порівнювати строгі runtime harness, не плутаючи їх із ширшим каталогом фреймворків і площин керування. [Agent Tools: Beyond Claude Code](../ecosystem/agentic-tools.uk.md) описує ці суміжні інструменти. Для виробничого методу поєднуйте workflow з [Agent Evaluation](../roles/agent-evaluation.uk.md), [Session Observability](../ops/observability.uk.md) та [Security Hardening](../security/security-hardening.uk.md). Спільні терміни зібрано в [глосарії](./glossary.uk.md).

## Карта методологій

Де кожна методологія знаходиться на двох осях: **Спочатку Специфікація проти Спочатку Код** (Y) та **Легкий/Solo проти Керований** (X). Друга вісь описує налаштування workflow і вартість координації. Вона не класифікує Toyota Production System чи Lean-менеджмент; про обмежене застосування потоку та jidoka до поставки за допомогою ШІ див. [допуск за ємністю рев'ю](./loop-graph-engineering.uk.md#обмежуйте-допуск-ємністю-верифікації).

```
                      СПОЧАТКУ СПЕЦИФІКАЦІЯ / ПЛАНУВАННЯ
                                  ▲
    ── легка · специф. ──         │         ── керована · специф. ──
                                  │
    [Doc-Driven]  [SDD]           │    [BDD]  [ATDD]   [Req-Driven]
    [GSD]  [Plan-First]           │ [CDD] [ADR-Driven]  [DDD]  [BMAD full]
                                  │
    LIGHTWEIGHT ──────────────────┼────────────────────────────────► GOVERNED
                                  │
    ── легкий · код ──            │         ── керований · код ──
                                  │
    [Context Eng.]   [TDD]        │       [Multi-Agent]
    [Prompt Eng.]  [Iterative]    │       [Eval-Driven]       [FDD]
    [Ralph Loop]                  │           [JiTTesting]
                                  │
                             КОД / ЕМЕРДЖЕНТ
```

**Як це читати:**

- **Вгорі ліворуч** (легкі підходи зі специфікацією): `SDD`, `Doc-Driven`, `Plan-First`. Природна точка входу для соло-розробників та малих команд, які хочуть відійти від підходу "спочатку код".
- **Вгорі праворуч** (керовані підходи зі специфікацією): повний шлях планування `BMAD`, `Req-Driven`, `ATDD`, `DDD`. Координація та простежуваність можуть виправдати більше артефактів; BMAD також підтримує пряму розробку для невеликої зміни.
- **Внизу ліворуч** (легкі підходи через код): природна територія Claude Code. `TDD` + `Ralph Loop` + `Iterative` = ядро соло-роботи.
- **Внизу праворуч** (код-орієнтовані підходи у масштабі): `Multi-Agent`, `Eval-Driven`, `JiTTesting` (Meta, 100M+ рядків коду). Нові патерни для команд з великим обсягом роботи.
- **На осях**: `Plan-First`, `CDD`, `ADR-Driven`, `GSD`, гібридні підходи, що адаптуються до будь-якого контексту.

## Lean-інженерія програмного забезпечення як оптика поставки

Lean не займає один квадрант цієї карти. [Адаптація для програмного забезпечення](https://res.infoq.com/articles/poppendieck-implementing-lean/en/resources/poppendieck_ch02.pdf) від Мері та Тома Поппендіків закликає команди вбудовувати якість у роботу й оптимізувати весь потік від потреби клієнта до розгорнутого програмного забезпечення, що її задовольняє. Метод може давати кращу специфікацію чи швидший код, тоді як запит чекає на рішення, рев'ю, реліз або впровадження.

| Питання Lean | Методи, що вже є на цій сторінці | Що перевірити в реальному workflow |
|---|---|---|
| Чи варта ця робота виконання? | SDD, BDD, BMAD | Назвіть проблему користувача й умову приймання, перш ніж розширювати специфікацію. Відхиліть або звузьте роботу, яку не можна пов'язати з потребою. |
| Де робота очікує? | BMAD, GSD, SDD, Multi-Agent | Простежте один запит через верифікацію та реліз. Встановіть явну політику обмеження незавершеної роботи (WIP) на вузькому етапі замість генерації нових чернеток. |
| Чи вбудована якість у роботу? | TDD, ATDD, BDD, Eval-Driven | Запускайте перевірки рано й зупиняйте зачеплену роботу, коли тест, оцінювання чи перевірка доказів не проходять. Одне лише фінальне рев'ю є пізнім бар'єром. |
| Чи може план змінюватися разом із доказами? | SDD, OpenSpec, BMAD | Де можливо, залишайте рішення оборотними. Оновлюйте специфікацію чи план, коли нове знання змінює вимогу; не зберігайте застарілий артефакт заради формальної відповідності процесу. |
| Чи покращився процес? | Ретроспективи, ADR, цикли верифікації | Перетворіть повторювану помилку на конкретну перевірку чи правило на попередньому етапі, а потім простежте, чи зменшилися повторюваність і зусилля на виправлення. |
| Чи справді одна одиниця роботи завершена? | SDD, ATDD, TDD, поступова міграція | Для застарілого коду опишіть наявну поведінку перед змінами, доведіть одну придатну до використання одиницю через верифікацію та реліз і перевірте, чи можна вивести старий шлях з обігу. Посилання на джерело чи успішна збірка самі по собі не підтверджують поведінкову відповідність. |
| Скільки коштує сам метод? | BMAD, SDD, Multi-Agent, процеси рев'ю | Рахуйте очікування, хибні блокування, повторні перевірки, втручання людини та підтримку нарівні з прийнятими змінами. Залишайте бар'єр, лише якщо він запобігає збою або дає докази, варті своєї затримки. |

[Kanban Guide](https://kanbanguides.org/the-kanban-guide/) робить потік операційним: визначте, коли елемент починається й завершується, як контролюється незавершена робота та як змінюється workflow. Його чотири мінімальні метрики потоку: WIP, пропускна здатність (throughput), вік робочого елемента та час циклу. Обирайте межі, що охоплюють чергу, яку потрібно діагностувати. Цим метрикам усе одно потрібен окремий результат для користувача; завершений pull request не доводить, що проблему клієнта розв'язано. [Картування розробки продукту від Lean Enterprise Institute](https://www.lean.org/the-lean-post/articles/why-value-stream-mapping-is-essential-to-product-and-process-development/) є корисним джерелом для картування рішень і передач між функціями.

Застосуйте той самий тест до самої методології. Специфікація, що запобігає одній хибній реалізації, може виправдати час на підготовку й рев'ю; обов'язкова специфікація для невеликого оборотного виправлення може лише додати чергу. Порівнюйте той самий клас запитів до і після зміни методу, враховуючи доопрацювання та час до прийнятого результату. [Цикл контрзаходів repository harness](./agent-harness.uk.md#цикл-lean-контрзаходів-для-repository-harness) показує, як перевірити контроль, перш ніж робити його постійним правилом.

Workflow залежить і від репозиторію, до якого він потрапляє. [Модель Agent Readiness від Factory](https://docs.factory.com/agent-readiness/overview) перевіряє, чи інструкції, збірки, тести та операційні сигнали роблять роботу агента придатною до верифікації. Це доповнює специфікації SDD чи BMAD та перевірки TDD; але не замінює питання Lean про те, чи завершена зміна дійшла до користувача. Виправте повторювану помилку репозиторію, перш ніж збільшувати паралелізм агентів, а потім порівняйте той самий тип завдань і чергу далі за потоком. Див. [приклад workflow агента](./loop-graph-engineering.uk.md#обмежуйте-допуск-ємністю-верифікації).

Два репозиторії відкривають вужчі механізми. [RaiSE](https://github.com/humansys/raise) описує постійний стан workflow та детерміновані перевірки на межах фаз. [Andon](https://github.com/PrimeFoldTools/andon) фіксує повторювані дефекти агента та запропоновані контрзаходи. Їхні репозиторії роблять проєктні рішення придатними до огляду; жоден не надає незалежних доказів покращення результатів для клієнтів. Приклад картування запиту з ШІ та межі доказів див. у [Lean and AI reading path](https://cc.bruniaux.com/lean-ai/) та [розділі про командні метрики](../ops/team-metrics.uk.md).

### Skill packs: корисні засоби контролю, а не результат Lean

Ці пакети документують повторювані кроки. Їхня відповідність Lean є інтерпретацією, яку слід перевіряти в реальному потоці поставки, а не твердженням чи вимірюванням самих проєктів.

| Пакет | Механізм, який можна перевірити | Питання Lean і обмеження |
|---|---|---|
| [gstack](https://github.com/garrytan/gstack) | `/office-hours` ставить під сумнів попит; `/review` та `/qa` перевіряють роботу; `/landing-report` показує чергу на реліз; `/retro` аналізує завершену роботу. | Чи скорочує повний шлях час до прийнятого результату для користувача, чи додає черги планування та верифікації? Його `/ship` також виконує дії Git і PR, тому використовуйте його лише на передбаченій межі релізу. |
| [Skills Метта Покока](https://github.com/mattpocock/skills) | `/triage` класифікує вхідні запити; [`/to-spec`](https://github.com/mattpocock/skills/blob/main/docs/engineering/to-spec.md) зарезервовано для роботи, що охоплює кілька сесій; [`/to-tickets`](https://github.com/mattpocock/skills/blob/main/docs/engineering/to-tickets.md) створює тонкі вертикальні зрізи, придатні до тестування; `/tdd` та `/retro` підтримують якість і навчання. | Чи може команда відхилити, звузити й завершити один цінний зріз, перш ніж починати наступні? Skills описують засоби контролю, а не виміряний ліміт WIP чи результат для клієнта. |

[Пакет Superpowers](https://github.com/obra/superpowers) є ще одним наявним у посібнику прикладом бар'єрів планування, TDD та рев'ю. Більше бар'єрів може допомогти, коли вони запобігають повторюваним збоям, але може й збільшити очікування. Залишайте найменший набір, що відповідає виявленому вузькому місцю, і вимірюйте WIP, час циклу, доопрацювання та результат для користувача на одному й тому самому типі запитів.

## 15 методологій

Організовані у 6-рівневу піраміду від стратегічної оркестрації до технік оптимізації.

### Рівень 1: Стратегічна оркестрація

| Назва | Що це | Найкраще для | Сумісність з Claude |
|------|------|----------|------------|
| **BMAD** | Робочі процеси мислення та розробки, розмірені під зміну | Від дрібних виправлень до складних ініціатив | ⭐⭐ Корисно, коли його артефакти виправдовують свою вартість |
| **GSD** | 6-фазний робочий процес з чистим контекстом для кожного завдання | Соло-розробники, Claude Code CLI | ⭐⭐ Схоже на патерни в гайді |

**BMAD (Breakthrough Method for Agile AI-Driven Development)** пропонує skills для мислення та робочі процеси розробки, з додатковими артефактами планування для більших або невизначених завдань. Його [актуальна документація](https://docs.bmad-method.org/) стверджує, що зрозуміле невелике виправлення можна одразу передати в `bmad-build`; більша зміна може починатися з `bmad-spec` або повнішого шляху планування. Агенти на основі ролей є необов'язковою частиною цієї системи, а не доказом того, що кожна зміна потребує кількох агентів.

- **Ключова концепція**: розмірюйте шлях планування та рев'ю під зміну й переносьте далі рішення, потрібні наступним крокам.
- **Коли використовувати**: використовуйте пряму розробку для добре зрозумілої невеликої зміни; додавайте планування, коли вартість рішення чи координації це виправдовує.
- **Коли уникати**: не запускайте повний ланцюжок артефактів для зрозумілого оборотного виправлення лише тому, що фреймворк його надає. Переглядайте артефакти, коли вимоги змінюються.
- **Встановлення та запуск**: див. [spec-first.md § With BMAD-METHOD](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/guide/workflows/spec-first.md#with-bmad-method-multi-role-planning) щодо інсталятора та вибору між прямою розробкою й більш структурованим плануванням.
- **Канонічний репозиторій**: [bmad-code-org/BMAD-METHOD](https://github.com/bmad-code-org/BMAD-METHOD). Нижче наведений порт спільноти (BMAD-AT-CLAUDE) є форком, специфічним для Claude Code, а не вихідним проєктом.

**GSD (Get Shit Done)** вирішує проблему "гниття контексту" (context rot) через систематичний 6-фазний процес (Initialize → Discuss → Plan → Execute → Verify → Complete) з новими сесіями по 200 тис. токенів на кожне завдання. Основні концепції (оркестрація багатьох агентів, управління чистим контекстом) суттєво перетинаються з існуючими патернами, такими як Ralph Loop, Gas Town та BMAD. Див. [оцінку ресурсів](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/docs/resource-evaluations/gsd-evaluation.md) для детального порівняння.

> **Нове**: [Ralph Inferno](https://github.com/sandstream/ralph-inferno) реалізує автономні робочі процеси з багатьма ролями (Analyst→PM→UX→Architect→Business) з виконанням у віртуальних машинах (VM) та циклом самокорекції E2E. Експериментальний підхід, але цікавий для "вайб-кодування у великих масштабах" (vibe coding at scale).

### Фундаментальна дисципліна: Спочатку План (Plan-First Workflow)

> **"Коли план хороший — код хороший."**
> Борис Черний, творець Claude Code

**Це систематична дисципліна, а не просто функція (команда `/plan`).**

> **Контекстна інженерія (Context Engineering)**: Thoughtworks визначає цей ширший підхід як "Контекстна інженерія" у своєму Technology Radar (листопад 2025 року)[^thoughtworks2025], це систематичне проектування інформації, що надається великим мовним моделям під час виведення. Три основні техніки: налаштування контексту (мінімальні системні промпти, few-shot приклади), управління контекстом для довгострокових завдань (резюмування, зовнішня пам'ять, архітектури субагентів) та динамічне отримання інформації (JIT-завантаження контексту). Пов'язані патерни в Claude Code: `AGENTS.md`, `MCP Context7`, `Plan Mode`.

[^thoughtworks2025]: Thoughtworks Technology Radar Vol 33, Nov 2025. [PDF](https://www.thoughtworks.com/content/dam/thoughtworks/documents/radar/2025/11/tr_technology_radar_vol_33_en.pdf). Див. також: [Блог-пост про макротренди](https://www.thoughtworks.com/insights/blog/technology-strategy/macro-trends-tech-industry-november-2025).

**Ментальна модель**:

Планування не є опціональним для складних завдань. Це різниця між:
- ❌ 8 ітераціями "спробував → виправив → ще раз виправив → знову переробив"
- ✅ 1 ітерацією "спланував → перевірив → чисто виконав"

**Коли планувати спочатку**:

| Складність завдання | Планувати спочатку? | Чому |
|----------------|-------------|-----|
| Змінено >3 файлів | ✅ Так | Залежності між файлами потребують архітектурного планування |
| Змінено >50 рядків | ✅ Так | Достатньо складності для виникнення помилок |
| Архітектурні зміни | ✅ Так | Необхідний аналіз наслідків та впливу змін |
| Незнайома кодова база | ✅ Так | Потрібне попереднє дослідження перед дією |
| Очевидна помилка / опечатка | ❌ Ні | Витрати на планування > час виконання завдання |
| Зміна в один рядок | ❌ Ні | Просто зробіть це |

**Як працює Plan-First**:

1. **Фаза дослідження** (Режим планування через `Shift+Tab` або команду `/plan`):
   - Claude читає файли, вивчає архітектуру
   - Редагування заборонено → це змушує думати перед дією
   - Пропонує підхід з описом переваг та компромісів

2. **Фаза валідації** (ви перевіряєте):
   - План викриває припущення та потенційні прогалини
   - Значно легше скоригувати напрямок зараз, ніж після того, як буде написано 100 рядків коду
   - План стає своєрідним "контрактом" для виконання

3. **Фаза виконання** (перехід у Normal Mode за допомогою `Shift+Tab`):
   - Перетворення плану на код стає механічним перекладом
   - Менше несподіванок, чистіша реалізація
   - Швидше виконання в цілому, попри "повільніший" старт

**Воркфлоу Бориса Черного**:

> "Я запускаю багато сесій, починаю в режимі планування (plan mode), а потім переходжу до виконання (execution), коли план виглядає правильно. Головне покращення тут — це верифікація: надання Claude способу самостійно протестувати та підтвердити свої результати."

**Переваги над підходом "просто почати кодувати"**:

- **Менше ітерацій виправлень**: План виявляє проблеми ще до того, як вони стануть кодом
- **Краща архітектура**: Змушує спочатку подумати про структуру коду
- **Чіткіша комунікація**: План створює спільне розуміння завдання між вами та Claude
- **Зниження вартості**: Одна чиста ітерація коштує дешевше, ніж багато хаотичних спроб (навіть якщо етап планування споживає токени)

**Інтеграція з CLAUDE.md**:

Задокументуйте тригери вашої команди для обов'язкового планування:
```markdown
## Planning Policy
- ALWAYS plan first: API changes, database migrations, new features
- OPTIONAL planning: Bug fixes <10 lines, test additions
- NEVER skip: Changes affecting >2 modules
```

**Див. також**: [Документація режиму планування (Plan Mode)](#23-plan-mode) для отримання детальної інформації про команду `/plan`.

> **Просунутий патерн**: Для ітеративного підходу на основі анотацій до розробки під керівництвом плану див. [Спеціальні плани у форматі Markdown (Патерн Бориса Тане)](../workflows/plan-driven.uk.md#просунуте-власні-markdown-плани-патерн-boris-tane).

### Рівень 2: Специфікація та Архітектура

| Назва | Що це | Найкраще для | Сумісність з Claude |
|------|------|----------|------------|
| **SDD** | Специфікації перед кодом | API, контракти | ⭐⭐⭐ Базовий патерн |
| **Doc-Driven** | Документація як джерело істини | Узгодження між командами | ⭐⭐⭐ Нативно для CLAUDE.md |
| **Req-Driven** | Багатий контекст артефактів (20+ документів) | Складні вимоги | ⭐⭐ Важке налаштування |
| **DDD** | Доменна мова спочатку | Бізнес-логіка | ⭐⭐ Етап проектування |

**SDD (Spec-Driven Development)**: Зробіть задуману поведінку явною до реалізації та переглядайте специфікацію, коли докази змінюють вимогу. Файл інструкцій проєкту, як-от `CLAUDE.md`, містить стабільні конвенції; він автоматично не є специфікацією функції. [Документація SDD від Spec Kit](https://github.com/github/spec-kit/blob/main/docs/how-to/sdd.md) охоплює як нові, так і наявні проєкти.

**Doc-Driven Development**: Жива документація, що версіонується в git, стає єдиним джерелом істини. Зміни в специфікаціях запускають безпосереднє впровадження у коді.

**Requirements-Driven Development (Розробка на основі вимог)**: Використовує `CLAUDE.md` як всеохоплюючий посібник з реалізації з понад 20 структурованими артефактами.

**DDD (Domain-Driven Design / Проектування на основі домену)**: Узгоджує програмне забезпечення з мовою бізнесу через:
- Єдину мову (Ubiquitous Language): Спільний словник термінів у коді
- Обмежені контексти (Bounded Contexts): Ізольовані межі різних бізнес-доменів
- Дистиляцію домену (Domain Distillation): Розподіл на основні (Core), допоміжні (Support) та загальні (Generic) домени

### Рівень 3: Поведінка та Прийняття

| Назва | Що це | Найкраще для | Сумісність з Claude |
|------|------|----------|------------|
| **BDD** | Сценарії "Дано-Коли-Тоді" (Given-When-Then) | Співпраця з бізнес-замовниками | ⭐⭐⭐ Тести та специфікації |
| **ATDD** | Спочатку критерії прийняття | Комплаєнс, регульовані сфери | ⭐⭐ Багато процесів |
| **CDD** | API-контракти як інтерфейс | Мікросервіси | ⭐⭐⭐ Нативно для OpenAPI |

**BDD (Behavior-Driven Development / Розробка на основі поведінки)**: Більше ніж просто тестування, це процес спільної роботи.
1. Відкриття (Discovery): Спільне залучення розробників та бізнес-експертів
2. Формулювання (Formulation): Опис прикладів через сценарії Given-When-Then
3. Automation (Автоматизація): Перетворення сценаріїв на виконувані тести (Gherkin/Cucumber)

```gherkin
Feature: Order Management
  Scenario: Cannot buy without stock
    Given product with 0 stock
    When customer attempts purchase
    Then system refuses with error message
```

**ATDD (Acceptance Test-Driven Development / Розробка на основі приймальних тестів)**: Критерії прийняття визначаються ПЕРЕД написанням коду спільно всією командою ("Тріада" або "Three Amigos": представник бізнесу, розробник, тестувальник).

В агентній розробці ATDD є особливо ефективним, оскільки агентам потрібні однозначні умови успіху. Цей процес ідеально лягає на завдання для агентів:

1. **Визначення критеріїв прийняття** у форматі Gherkin (зручному для людей, придатному для автоматичного виконання)
2. **Агент пише тести, що падають**, на основі сценаріїв (а не конкретної реалізації)
3. **Агент розробляє код**, поки всі тести не стануть успішними

```gherkin
Feature: Password Reset
  Scenario: User resets via email
    Given a registered user with email "user@example.com"
    When they request a password reset
    Then they receive a reset email within 60 seconds
    And the reset link expires after 24 hours
```

Цей сценарій Gherkin є контрактом між наміром та реалізацією. Агент не може неправильно витлумачити обсяг роботи (scope), оскільки поняття "готово" (done) чітко визначене ще до написання першого рядка коду.

> **Застосування до агентів**: Передайте Gherkin-файл до Claude Code перед початком розробки. Дайте вказівку: "Напиши тести, що падають, для цього файлу функцій, а потім реалізуй код, поки вони не пройдуть." Роль автора сценарію (людина або агент) фіксує чіткі межі завдань перед виконанням.

**CDD (Contract-Driven Development / Розробка на основі контрактів)**: API-контракти (специфікації OpenAPI) як виконуваний інтерфейс взаємодії між командами. Патерни: "Контракт як тест" (Contract as Test), "Контракт як заглушка" (Contract as Stub).

**JiTTesting (Just-in-Time Testing / Тестування в останній момент)**: Тести, які генеруються "на льоту" під час створення pull request (PR), розроблені для навмисного виявлення збоїв (failing by design) і видаляються після мержу. Відсутні витрати на підтримку, немає роздування тестової бази.

Методології TDD/BDD/ATDD виходять із припущення, що розробник повністю контролює темп написання коду. Агентна розробка ламає це припущення: автономний агент здатний генерувати по 200+ рядків коду на годину, з чим класичний процес написання тестів людиною просто не встигає конкурувати. JiT-тести є індустріальною відповіддю на цей дисбаланс.

Механізм роботи: під час створення PR велика мовна модель аналізує намір у diff-файлі змін, генерує мутанти коду (навмисно пошкоджені варіанти), створює тести, які виявляють ці мутації, запускає комбіновані правила та LLM-оцінювачі для фільтрації хибнопозитивних спрацьовувань, і виводить інженеру лише реальні регресійні помилки. Ці тести ніколи не потрапляють у фінальну кодову базу.

Компанія Meta розгорнула цю практику у великих масштабах (понад 100 млн рядків коду): зафіксовано 4-кратне покращення виявлення регресій порівняно з традиційними тестами стабілізації коду, на 70% знизилося навантаження на інженерів під час код-рев'ю, вдалося запобігти 4 серйозним збоям у продакшені з 41 проаналізованого кандидата.

Наразі відкритих (open-source) реалізацій цього підходу немає. Ви можете спробувати наблизитися до цього сьогодні: перед мержем PR, згенерованого агентом, дайте Claude промпт: "Згенеруй тести, які б виявили регресії, внесені саме цим diff-файлом. Я запущу їх локально і видалю після закриття PR." Такий тимчасовий формат фокусує створення тестів саме на тому, що реально змінилося, замість загального покриття.

> **Джерело**: [Just-in-Time Catching Test Generation at Meta](https://arxiv.org/abs/2601.22832) (Harman, 2026).

### Рівень 4: Поставка функцій

| Назва | Що це | Найкраще для | Сумісність з Claude |
|------|------|----------|------------|
| **FDD** | Поставка по одній функції (Feature-by-feature) | Команди з паралельною розробкою функцій | ⭐⭐ Структура |
| **Context Eng.** | Контекст як першокласний об'єкт архітектури | Довгі сесії розробки | ⭐⭐⭐ Фундаментально |

**FDD (Feature-Driven Development / Розробка на основі функцій)**: П'ять основних процесів:
1. Розробка загальної моделі (Develop Overall Model)
2. Створення списку функцій (Build Features List)
3. Планування за функціями (Plan by Feature)
4. Проектування за функціями (Design by Feature)
5. Реалізація за функціями (Build by Feature)

Суворий таймінг: максимум 2 тижні на кожну функцію.

**Контекстна інженерія (Context Engineering)**: Ставтеся до контексту як до елемента проектування:
- Поступове розкриття (Progressive Disclosure): Дозвольте агенту відкривати кодову базу крок за кроком
- Управління пам'яттю (Memory Management): Чітке розділення між діалоговою та довгостроковою пам'яттю
- Динамічне оновлення (Dynamic Refresh): Перезапис та уточнення списку TODO перед наданням фінальної відповіді

### Рівень 5: Реалізація

| Назва | Що це | Найкраще для | Сумісність з Claude |
|------|------|----------|------------|
| **TDD** | Red-Green-Refactor | Надійний та якісний код | ⭐⭐⭐ Ядро воркфлоу |
| **Eval-Driven** | Евалі для виходів LLM | Продукти на базі ШІ | ⭐⭐⭐ Робота з агентами |
| **Multi-Agent** | Оркестрація субагентів | Складні комплексні завдання | ⭐⭐⭐ Інструмент Task |

**TDD (Test-Driven Development / Розробка через тестування)**: Класичний цикл:
1. **Red**: Написати тест, що падає
2. **Green**: Написати мінімальний код для проходження тесту
3. **Refactor**: Провести рефакторинг та очищення коду, зберігаючи тести зеленими

При роботі з Claude будьте конкретними: "Напиши ТЕСТИ, ЩО ПАДАЮТЬ, яких наразі ще немає у проекті."

> **Цикли верифікації (Verification Loops)**: Формалізований патерн для автономних ітерацій (ширший за класичний TDD):
>
> **Головний принцип**: Надання Claude інструментів для самостійної перевірки власних результатів.
>
> ```
> Генерація коду ➔ Інструмент верифікації ➔ Петля зворотного зв'язку ➔ Вдосконалення
> ```
>
> **Чому це працює** (Борис Черний): *"Агент, який здатний самостійно 'бачити' та аналізувати свої дії, дає значно кращі результати."*
>
> **Механізми верифікації за сферами використання**:
>
> | Сфера | Інструмент верифікації | Що саме "бачить" Claude |
> |--------|-------------------|-------------------|
> | **Frontend** | Попередній перегляд у браузері (live reload) | Візуальний рендеринг, макет, інтерактивність |
> | **Backend** | Тести (unit / integration) | Статус проходження, повідомлення про помилки |
> | **Типи** | Компілятор TypeScript | Помилки типізації, несумісність інтерфейсів |
> | **Стиль коду** | Лінтери (ESLint, Prettier) | Порушення стилю, помилки форматування |
> | **Продуктивність** | Профайлери, бенчмарки | Час виконання, використання пам'яті |
> | **Доступність** | axe-core, зчитувачі екрана | Порушення WCAG, проблеми навігації |
> | **Безпека** | Статичні аналізатори (Semgrep) | Потенційні вразливості, небезпечні патерни |
> | **UX** | Користувацькі тести, записи сесій | Проблеми зручності використання, незрозумілі зони |
>
> **TDD як класичний приклад**:
> 1. Claude пише тести для нової функції
> 2. Claude ітеративно дописує код, поки всі тести не будуть пройдені успішно
> 3. Процес триває до виконання чітких критеріїв завершення
>
> **Офіційна рекомендація**: *"Спрямуйте Claude продовжувати роботу, поки всі тести не будуть пройдені успішно. Зазвичай для цього потрібно кілька ітерацій."* ([Anthropic Best Practices](https://www.anthropic.com/engineering/claude-code-best-practices))
>
> **Варіанти реалізації**:
> - **Хуки (Hooks)**: Хук `PostToolUse` автоматично запускає верифікацію після кожної зміни файлу
> - **Розширення браузера**: Claude у Chrome безпосередньо аналізує рендеринг сторінки
> - **Спостерігачі за тестами (Test watchers)**: Режим спостереження у Jest/Vitest забезпечує миттєвий зворотний зв'язок
> - **Ворота CI/CD**: Робочі процеси GitHub Actions запускають повний набір перевірок
> - **Верифікація кількома Claude**: Один Claude пише код, інший — перевіряє та тестує його
>
> **Антипатерн**: Сліпа ітерація без отримання зворотного зв'язку. Без наявності механізму верифікації Claude не здатний прийти до правильного рішення: він просто вгадує.

Щодо запобігання помилкам реалізації на цьому етапі див. [Розрив верифікації (The Verification Gap)](../workflows/tdd-with-claude.uk.md#розрив-верифікації-the-verification-gap) у воркфлоу розробки через тестування.

**Eval-Driven Development (Розробка на основі евалів)**: Аналог TDD для великих мовних моделей. Тестування поведінки агентів через спеціальні оцінки (evals):
- На основі коду: перевірка рівності `output == golden_answer`
- На основі LLM: інший незалежний інстанс Claude оцінює якість
- Оцінка людиною: найбільш точний, але тривалий процес

> **Набір для оцінювання (Eval Harness)**: Інфраструктура, яка запускає оцінки наскрізно, надає інструкції та інструменти, виконує завдання паралельно, записує кроки роботи, оцінює результати та агрегує статистику.
>
> Детальніше у гайді від Anthropic: [Demystifying Evals for AI Agents](https://www.anthropic.com/engineering/demystifying-evals-for-ai-agents)

**Orchestration субагентів (Multi-Agent Orchestration)**: Перехід від одного універсального асистента до оркестрованої команди фахівців:
```
Meta-Agent (Orchestrator)
├── Analyst (вимоги та аналіз)
├── Architect (проектування та архітектура)
├── Developer (написання коду)
└── Reviewer (валідація та рев'ю)
```

### ADR-Driven Development (Розробка під керівництвом рішень щодо архітектури)

**Патерн**: Напишіть ADR простою англійською мовою ➔ Передайте спеціалізованому скілу `implement-adr` ➔ Отримайте нативне виконання.

Записи архітектурних рішень (Architecture Decision Records — ADR) у поєднанні зі скілами Claude Code формують робочий процес, де стратегічні архітектурні рішення безпосередньо керують написанням коду.

**Етапи робочого процесу**:
1. **Задокументуйте рішення** у форматі ADR (контекст, рішення, наслідки)
2. **Створіть скіл реалізації** (загальний або спеціалізований `implement-adr`)
3. **Передайте ADR як промпт** для скілу із чіткими критеріями прийняття
4. **Claude виконує розробку**, суворо дотримуючись архітектурних настанов з ADR

**Приклад шаблону ADR**:
```
# ADR-001: Database Migration Strategy

## Context
Legacy MySQL schema needs migration to PostgreSQL for better JSON support.

## Decision
Use incremental dual-write pattern with feature flags.

## Consequences
- Positive: Zero-downtime migration
- Negative: Temporary code complexity during transition
```

**Сценарій реалізації**:
```bash
# 1. Запишіть ADR (простою англійською мовою)
vim docs/adr/001-database-migration.md

# 2. Передайте файл скілу реалізації
/implement-adr docs/adr/001-database-migration.md

# 3. Claude виконує розробку на основі вимог ADR:
# ➔ Створює міграційні скрипти
# ➔ Оновлює конфігурацію ORM
# ➔ Додає фіча-флаги (feature flags)
# ➔ Впроваджує логіку подвійного запису (dual-write)
```

**Переваги**:
- ✅ **Керування через документацію**: Архітектура та реальний код завжди залишаються синхронізованими
- ✅ **Нативне виконання**: Немає потреби у використанні складних зовнішніх фреймворків
- ✅ **Просте відстеження рішень**: Чіткий та зрозумілий зв'язок між архітектурною ідеєю та кодом
- ✅ **Спільне розуміння в команді**: ADR однаково ефективно комунікують наміри як людям, так і ШІ

**Джерело**: [Ембеддед-воркфлоу розробки від Гура Саннікова](https://www.linkedin.com/posts/gursannikov_claudecode-embeddedengineering-aiagents-activity-7423851983331328001-DrFb)

### Рівень 6: Оптимізація

| Назва | Що це | Найкраще для | Сумісність з Claude |
|------|------|----------|------------|
| **Iterative Loops** | Автономне вдосконалення коду | Оптимізація алгоритмів | ⭐⭐⭐ Ядро системи |
| **Fresh Context** | Скидання контексту, збереження стану у файлах | Довгі автономні сесії | ⭐⭐⭐ Для досвідчених користувачів |
| **Prompt Eng.** | Фундаментальні техніки роботи | Будь-які завдання | ⭐⭐⭐ Необхідна база |

**Ітеративні цикли вдосконалення (Iterative Refinement Loops)**: Автономна збіжність результату:
1. Виконати промпт
2. Observe result (Проаналізувати отриманий результат)
3. Якщо результат ≠ "DONE" ➔ уточнити промпт та повторити знову

**Prompt Engineering (Інженерія промптів)**: Основа для будь-якої взаємодії з Claude:
- Zero-Shot Chain of Thought: Інструкція "Думай крок за кроком" (Think step by step)
- Few-Shot Learning: Надання 2-3 прикладів очікуваного патерну
- Структуровані промпти: Використання тегів XML для чіткої організації запиту
- Важливість позиціонування: У довгих документах розміщуйте ключове питання наприкінці запиту

**Патерн свіжого контексту (Fresh Context Pattern / Ralph Loop)**: Вирішує проблему "гниття контексту" шляхом запуску абсолютно свіжих інстансів агента для кожного підзавдання. Стан розробки фіксується у git та спеціальних файлах прогресу, а не накопичується в історії чату. Ідеально підходить для тривалих автономних завдань (наприклад, міграції великих модулів або нічні запуски). Опис впровадження наведено в розділі [Ultimate Guide - Fresh Context Pattern](#fresh-context-pattern-ralph-loop).

## Довідник інструментів SDD

Три ключові інструменти, які з'явилися для формалізації та спрощення процесу Spec-Driven Development:

| Інструмент | Сфера використання | Офіційна документація | Інтеграція з Claude |
|------|----------|---------------|-------------------|
| **Spec Kit** | Нові та наявні проєкти, структуровані специфікації | [Документація SDD від Spec Kit](https://github.com/github/spec-kit/blob/main/docs/how-to/sdd.md) | `/speckit.constitution`, `/speckit.specify`, `/speckit.plan` |
| **OpenSpec** | Доопрацювання існуючих проектів (Brownfield), внесення змін | [github.com/Fission-AI/OpenSpec](https://github.com/Fission-AI/OpenSpec) | `/openspec:proposal`, `/openspec:apply`, `/openspec:archive` |
| **Specmatic** | Тестування API-контрактів | [specmatic.io](https://specmatic.io) | Доступний спеціалізований MCP-агент |
| **Spec-to-Code Factory** | Greenfield, інструментальний контроль | [github.com/SylvainChabaud/spec-to-code-factory](https://github.com/SylvainChabaud/spec-to-code-factory) | Референтна мультиагентна реалізація (BREAK➔MODEL➔ACT➔DEBRIEF) |

### Spec Kit (нові та наявні проєкти)

5-фазний процес розробки:
1. Конституція (Constitution): `/speckit.constitution` ➔ встановлення обмежень
2. Специфікація (Specify): `/speckit.specify` ➔ збір вимог
3. План (Plan): `/speckit.plan` ➔ проектування архітектури
4. Завдання (Tasks): `/speckit.tasks` ➔ декомпозиція на підзавдання
5. Реалізація (Implement): `/speckit.implement` ➔ написання коду

### OpenSpec (Для існуючих проектів / Brownfield)

Двопапкова архітектура:
```
openspec/
├── specs/      ← Поточне джерело істини (стабільне)
└── changes/    ← Пропозиції змін (тимчасове)
```

Воркфлоу: Створення пропозиції (Proposal) ➔ Рев'ю (Review) ➔ Застосування (Apply) ➔ Архівування (Archive)

### Specmatic (Контракти API)

- **Контракт як тест (Contract as Test)**: Автоматично генерує тисячі тестів безпосередньо зі специфікації OpenAPI
- **Контракт як заглушка (Contract as Stub)**: Створює mock-сервер для паралельної розробки різними командами
- **Зворотна сумісність**: Виявляє зміни, що ламають сумісність (breaking changes)

## Написання ефективних специфікацій

> На основі детального аналізу понад 2500 конфігураційних файлів агентів розробки.
> Джерело: [Адді Османі (Addy Osmani)](https://addyosmani.com/blog/good-spec/)

### Шість обов'язкових компонентів

| Компонент | Що слід включити | Конкретний приклад |
|-----------|-----------------|---------|
| **Команди** | Готові до запуску команди з прапорцями | `npm test -- --coverage` |
| **Тестування** | Обраний фреймворк, очікуване покриття, шляхи | `vitest, 80%, tests/` |
| **Структура проекту** | Явний опис структури папок коду | `src/`, `lib/`, `tests/` |
| **Стиль коду** | Один наочний приклад замість абзаців опису | Показати реальну функцію у потрібному стилі |
| **Git-процес** | Назви гілок, формат комітів, вимоги до PR | `feat/name`, conventional commits |
| **Межі доступу** | Рівні дозволів на дії для ШІ | Див. таблицю дозволів нижче |

### Рівні дозволів (Permission Tiers)

| Рівень | Символ | Сфера застосування |
|------|--------|---------|
| Робити завжди | ✅ | Безпечні операції, що не потребують підтвердження (lint, format) |
| Запитати спочатку | ⚠️ | Дії з високим рівнем впливу (видалення файлів, публікація) |
| Ніколи не робити | 🚫 | Суворі заборони (коміт паролів/ключів, force push в main) |

### Прокляття інструкцій (Curse of Instructions)

> ⚠️ Той самий аналіз показав: **чим більше інструкцій надається, тим гірше дотримується кожна з них**.
>
> Рішення: Передавайте Claude лише ті частини специфікації, які є релевантними для поточного завдання, а не весь великий документ цілком.

### Монолітні специфікації проти модульних

| Розмір проекту | Рекомендований підхід |
|--------------|----------|
| Малий (<10 файлів) | Один файл специфікації |
| Середній (10-50 файлів) | Специфікація, розбита на секції; передача частинами під кожне завдання |
| Великий (50+ файлів) | Маршрутизація субагентів за окремими доменами розробки |

## Патерни комбінування

Це стартові комбінації, а не виміряний приріст продуктивності. Додавайте метод, коли він розв'язує реальне рішення, дефект чи передачу. Перевіряйте отриману чергу та вартість підтримки.

| Ситуація | Стартова комбінація | Що перевірити |
|-----------|----------------------|----------------|
| Індивідуальна зміна з ризикованою поведінкою | Коротка специфікація завдання + TDD | Прийнята поведінка та зусилля на виправлення |
| Команда з повторюваними непорозуміннями щодо вимог | Spec Kit + BDD + TDD | Менше спірних прикладів без непомірного беклогу специфікацій |
| Сервіси з явними API-контрактами | CDD + Specmatic | Збої контрактів, виявлені до інтеграції |
| Наявний продукт зі змінною поведінкою | OpenSpec + BDD | Поточні специфікації відповідають поведінці в продакшені після кожної зміни |
| Складна робота на межах сервісів | BMAD + Specmatic | Одне джерело планування, корисні перевірки контрактів та прийнятне очікування рев'ю |
| LLM-продукт із повторюваними збоями виводу | Eval-Driven; додавайте Multi-Agent лише для окремої ролі | Якість оцінювання та результат для користувача після релізу |

-----------|-------------------|-------|
| Solo MVP | SDD + TDD | Мінімальні накладні витрати, максимальний фокус на якості коду |
| Команда 5-10 осіб, Greenfield | Spec Kit + TDD + BDD | Баланс між управлінням, якістю розробки та комунікацією |
| Мікросервісна архітектура | CDD + Specmatic | Розробка від API-контракту, паралельна робота різних команд |
| Наявний SaaS-продукт (100+ фіч) | OpenSpec + BDD | Чітке відстеження змін, запобігання розходженню документації з кодом |
| Складні системи / Сфери з комплаєнсом | BMAD + Spec Kit + Specmatic | Максимальний рівень контролю, контрактів та відповідності вимогам |
| ШІ-орієнтовані продукти (AI-native) | Eval-Driven + Multi-Agent | Системи з можливістю самовдосконалення |
