## 1. Що таке інженерія контексту

### Визначення

Андрій Карпати ввів цей термін: **"Інженерія контексту — це мистецтво заповнення вікна контексту правильною інформацією у правильний час."**

Це речення містить три не очевидні вимоги:

- **Заповнення (Filling)**: вікно контексту має наповнюватися свідомо, а не випадково. Напівпорожнє вікно марнує потужність моделі; хаотично заповнене — марнує ваші токени та погіршує якість результату.
- **Правильна інформація (Right information)**: не вся інформація однаково цінна. Архітектурні рішення важливіші за вподобання щодо лінтера. Негативні обмеження ("ніколи не повертай клієнту сирі помилки SQL") дієвіші за загальні цілі ("пиши чистий код").
- **Правильний час (Right time)**: правила для бекенд-коду не мають цінності, коли ви редагуєте фронтенд-компонент. Завантаження всього і завжди — це лінивий підхід, який погіршує дотримання інструкцій.

### Промпт-інженерія проти Інженерії контексту

Ці терміни часто плутають. Але різниця суттєва:

| Вимір | Промпт-інженерія | Інженерія контексту |
|-----------|-------------------|---------------------|
| **Область** | Один запит | Вся сесія або система |
| **Тривалість** | Одна взаємодія | Зберігається між взаємодіями |
| **Зусилля** | Створення запиту щоразу | Початкове проектування системи |
| **Масштаб** | Індивідуальний | Командний або організаційний |
| **Результат** | Рядок промпту | Система конфігурації |

**Промпт-інженерія** — це створення правильного запитання для одного завдання. **Інженерія контексту** — це система, яка гарантує, що Claude має правильні фонові знання *перед* початком будь-якого завдання. Ви можете мати чудові промпти поверх поганої інженерії контексту і все одно отримувати посередні результати — оскільки моделі бракуватиме структурного розуміння вашого проекту, його конвенцій та обмежень.

Практична аналогія: промпт-інженерія — це написання хорошого листа підряднику. Інженерія контексту — це процес онбордингу, гайдлайни щодо стилю коду, архітектурна документація та командні норми, які гарантують, що підрядник розуміє проект ще до того, як прочитає хоча б один лист.

### Інженерія контексту проти Оптимізації контексту

Обидва терміни зустрічаються в літературі та іноді використовуються як синоніми. Але вони різняться.

| Вимір | Інженерія контексту | Оптимізація контексту |
|-----------|--------------------|--------------------|
| **Основне питання** | Яка інформація має бути в контексті? | Який мінімальний набір високосигнальних токенів максимізує результат? |
| **Ціль** | Повнота та правильність | Ефективність та щільність сигналу |
| **Метод** | Визначення того, що моделі необхідно знати | Видалення всього, що їй знати не потрібно |
| **Режим відмови** | Відсутність критичної інформації | Перебір — занадто багато нерелевантного контенту |
| **Результат** | Контекстна система | Обрізаний, високоточний промпт або конфіг |

Корисна ментальна модель: інженерія контексту відповідає на питання "що включити", оптимізація контексту — "що відсікти".

На практиці ви робите і те, і інше. Інженерний етап будує повну картину: архітектурні рішення, конвенції, обмеження. Етап оптимізації очищує її: видаляє дублювання, стискає розлогі правила, архівує застарілі записи, обмежує релевантність підсистем за шляхами. Методи скорочення в Розділі 8 — це і є етап оптимізації.

**Синтез проти міркування**

Ще одна важлива відмінність, яку варто виділити окремо:

- **Синтез контексту (Context synthesis)** є збережним (stateful) та ітеративним. Він накопичує знання між сесіями, оновлюється при зміні конвенцій та відображає історію проекту. `CLAUDE.md` — це синтез контексту.
- **Міркування (Reasoning)** є ефемерним та одноразовим. Кожен крок виведення використовує контекст для створення результату, а потім відкидає проміжний стан. Ланцюжок думок (chain-of-thought) Claude — це міркування.

Поширеною помилкою є ставлення до артефактів міркування (проміжних думок, трасувань відладки, виводів помилок) як до матеріалу для синтезу контексту. Це засмічує контекст ефемерним станом та прискорює його "гниття". Відокремлюйте те, що має зберігатися (синтез), від того, що має бути відкинуто (шум міркувань).

### Чому це важливо

LLM — це комп'ютери з вікном контексту. Якість виводу обмежена якістю вводу. Це не просто абстрактне твердження, воно має жорстке технічне підґрунтя:

1. Модель не має постійної пам'яті між сесіями (без використання спеціальних інструментів). Кожна сесія починається з нуля, якщо контекст не надано навмисно.
2. Модель не може вгадати незаписані конвенції. Якщо ви хочете використовувати інтерфейси TypeScript замість аліасів `type`, про це має бути сказано. Якщо ви хочете, щоб помилки логувалися перед генерацією винятку, це має бути вказано.
3. Моделі чутливі до розміщення та формулювання інструкцій. Інструкція, похована на 400-му рядку 500-рядкового `CLAUDE.md`, має набагато менше шансів бути виконаною, ніж та, що знаходиться в перших 50 рядках.

Команди, які інвестують в інженерію контексту, стабільно повідомляють про меншу кількість ітерацій правок, краще дотримання конвенцій та більш передбачувані результати. Інвестиції робляться наперед (створення системи), але дивіденди накопичуються під час кожної взаємодії.

Корисне діагностичне переосмислення: **більшість збоїв у роботі ШІ — це збої контексту, а не збої моделі.** Коли Claude генерує загальну відповідь, ігнорує конвенцію або створює код, який не відповідає вашому стеку, модель майже ніколи не є зламаною — просто контекст, який вона отримала, був неповним, суперечливим або не містив правильної інформації у правильний час. Це переосмислення зміщує фокус усунення проблем з "ШІ погано з цим справляється" на "чого саме бракує в контексті?".

### Три шари

Інженерія контексту в Claude Code працює на трьох окремих рівнях:

| Шар | Механізм | Область дії | Коли завантажується |
|-------|-----------|-------|-------------|
| **Глобальний конфіг** | `~/.claude/CLAUDE.md` | Усі проекти | Завжди |
| **Проектний конфіг** | `./CLAUDE.md` + модулі за шляхами | Поточний проект | На сесію |
| **Сесійний** | Інструкції в чаті, `/add`, прапорці | Лише поточна сесія | Під час виконання |

Кожен шар має свої компроміси. Глобальний конфіг працює завжди, але не може містити специфічних для проекту деталей. Сесійні інструкції гнучкі, але ефемерні. Проектний конфіг є основною робочою конячкою: структурований, версіонований, доступний для аудиту.

Хороша інженерія контексту означає розміщення кожної частини інформації на потрібному рівні — без намагання втиснути все в один файл і без залишення критичних знань на рівні сесії, де вони випаруються після закінчення розмови.

### Статичний проти Динамічного Контексту

Описана вище трирівнева система є *статичним контекстом* — конфігураційними файлами, які збираються перед початком сесії та залишаються стабільними протягом усього часу. Claude Code є переважно системою статичного контексту, саме тому структура `CLAUDE.md` та обмеження релевантності за шляхами (path-scoping) мають таке велике значення.

У міру того, як ви рухаєтеся до агентних воркфлоу, з'являється друга категорія: *динамічний контекст*, який збирається безпосередньо під час виведення в міру роботи агента.

| Тип | Як збирається | Приклади в Claude Code |
|------|--------------|-------------------------|
| **Статичний** | Перед сесією, з файлів | `CLAUDE.md`, модулі за шляхами, скіли |
| **Динамічний** | Під час виконання, через інструменти | Виводи інструментів, читання файлів, вебресурси, дані MCP |

На практиці кожна сесія Claude Code використовує обидва типи. Статичний контекст (ваша конфігурація) задає поведінкові межі; динамічний контекст (файли, які Claude читає, результати роботи інструментів) надає конкретну інформацію для кожного завдання. Інженерія контексту охоплює обидва види, але типи помилок різняться: проблеми статичного контексту проявляються як системні порушення конвенцій; проблеми динамічного контексту проявляються як дії Claude на основі застарілої або неповної інформації всередині завдання.

Для команд, які розробляють автоматизовані конвеєри та агентів, інженерна публікація Anthropic за вересень 2025 року ["Effective context engineering for AI agents"](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents) детально розкриває динамічний аспект.

### Чому гниття контексту є структурним, а не випадковим

Моделі-трансформери аналізують усі токени попарно. Це означає, що кількість зв'язків уваги у вікні контексту зростає як $n^2$, а не як $n$. Подвоєння довжини контексту вчетверо збільшує кількість зв'язків, які модель має зважувати. При 200K токенів це означає мільярди попарних обчислень, через що увага моделі неминуче розсіюється.

Це не баг, який майбутні моделі повністю усунуть. Це наслідок самої архітектури. Гниття контексту (context rot) — поступове погіршення дотримання інструкцій у міру зростання обсягу контексту — є структурно неминучим. Звідси висновок: ви не можете вирішити проблему гниття контексту, просто покладаючись на великі вікна контексту. Ви вирішуєте її, підтримуючи контекст лаконічним і завантажуючи інформацію точно вчасно (just in time).

**Вчасне вилучення проти попереднього завантаження**

Існує дві стратегії надання Claude потрібної інформації:

| Стратегія | Механізм | Коли використовувати |
|----------|-----------|-------------|
| **Попереднє завантаження (RAG)** | Пошук та додавання всього потенційно релевантного контексту перед виведенням | Відомі, стабільні вимоги до контексту |
| **Вчасне вилучення (Just-in-Time)** | Отримання контексту на вимогу, точно і лише тоді, коли він потрібен | Динамічний контекст під конкретне завдання |

Попереднє завантаження — це знайомий патерн RAG: створення пошукового індексу, вилучення релевантних фрагментів та завантаження їх у промпт наперед. Це працює, коли ви заздалегідь знаєте, які саме дані знадобляться моделі.

Вчасне вилучення складніше в реалізації, але набагато ефективніше в масштабі: модель вилучає інформацію динамічно за запитом завдання, використовуючи виклики інструментів, сервери MCP або читання файлів. У контексті залишається лише інформація, необхідна для поточного кроку.

Поведінка Claude Code відображає цей патерн: `CLAUDE.md` завантажується наперед (попереднє завантаження, актуальне завжди), тоді як вміст файлів та результати роботи інструментів вилучаються під час роботи через `read_file`, `glob`, `grep` та виклики MCP. Інструменти glob та grep є шаром вчасного вилучення (JIT). Вони поміщають вміст конкретних файлів у контекст лише тоді, коли завдання безпосередньо стосується цих файлів.

**Інструмент пам'яті (Memory tool, бета)**

Починаючи з Claude Sonnet 4.5, Anthropic випустила інструмент пам'яті (Memory tool) у публічній беті. Він дозволяє Claude зберігати та вилучати факти між сесіями без ручного керування `CLAUDE.md`. Інструмент підтримує структуроване сховище знань, до якого Claude звертається, коли потрібен релевантний контекст.

Це відрізняється від `CLAUDE.md`: `CLAUDE.md` є статичною конфігурацією (завжди завантаженою), тоді як Memory tool є динамічним вилученням (запити на вимогу). Для команд, які розробляють агентів, інструмент пам'яті зменшує потребу вручну вносити знання у конфігураційні файли.

**Ланцюжок міркувань у тривалих завданнях**

Промптінг із ланцюжком міркувань (Chain-of-thought, CoT) покращує логічні висновки моделі на ізольованих завданнях. Проте інженерні дані Anthropic показують, що це може зашкодити продуктивності в тривалих агентних сценаріях. Механізм наступний: CoT генерує додаткові токени, які збільшують довжину контексту, що прискорює гниття контексту для наступних кроків. На завданнях, які охоплюють понад 20 викликів інструментів, цей ефект стає критично відчутним.

Практичне правило: використовуйте CoT для складних ізольованих логічних кроків, а не як універсальну стратегію для агентних робочих процесів. У довгих сесіях віддавайте перевагу стислому проміжному виводу перед розлогими трасуваннями міркувань.

## 2. Бюджет контексту

### Математика токенів

Конкретний базовий рівень для проекту середнього розміру:

| Джерело | Типовий діапазон токенів |
|--------|---------------------|
| Глобальний `CLAUDE.md` | 1,000 – 3,000 токенів |
| Проектний `CLAUDE.md` (root) | 2,000 – 8,000 токенів |
| Обмежені за шляхом модулі (всі активні) | 1,000 – 5,000 токенів |
| Імпортовані скіли / команди | 500 – 3,000 токенів |
| **Всього завжди активного контексту** | **~5,000 – 20,000 токенів** |

Claude Sonnet 4.6 має вікно контексту 200K токенів. Це означає, що навіть великий постійний конфігураційний бюджет (20K токенів) займає лише близько 10% вікна, залишаючи 180K токенів для безпосередньої роботи: файлів коду, історії розмови та виводів інструментів.

Практичне правило: **завжди активний контекст повинен залишатися нижче 5% від вікна контексту.** Вихід за ці межі витісняє реальний вміст завдання, який має більшу цінність на один токен, ніж статичні інструкції.

### Стеля у 150 інструкцій

Емпіричні спостереження команд, що використовують великі файли `CLAUDE.md`: після перевищення приблизно 150 окремих правил моделі починають вибірково ігнорувати деякі з них. Це не жорстка межа — вона залежить від складності правил, їхнього перекриття та позиціонування — але це надійний сигнал, що більше правил не означає кращого дотримання.

Механізмом є дифузія уваги: коли промпт містить сотні потенційних обмежень, увага моделі розділяється між ними. Правила з високою значущістю (нещодавні, жорстко сформульовані, розміщені на початку) витісняють правила з нижчою значущістю.

Виробничі дані HumanLayer показують, що команди зі структурованим контекстом (менше правил, вища специфічність, ієрархічна організація) отримують на 15-25% краще дотримання інструкцій порівняно з командами, які використовують довгі неструктуровані списки правил.

Висновок: **якість правил перемагає кількість.** Двадцять конкретних, дієвих правил перевершують 200 загальних декларативних побажань.

### Погіршення дотримання за розміром файлу

```
Рядки в CLAUDE.md     Рівень дотримання (оцінка)
─────────────────     ──────────────────────────
1 – 100               ~95%
100 – 200             ~88%
200 – 400             ~75%
400 – 600             ~60%
600+                  ~45% і падає
```

Ці показники є оціночними орієнтирами, а не гарантією. Обмеження релевантності за шляхами (path-scoping) та модульна архітектура дозволяють підтримувати високий рівень дотримання правил навіть при великій загальній кількості інструкцій, гарантуючи, що в контексті в кожен момент часу знаходяться лише релевантні правила.

### Ознаки перевантаження контексту

Коли завжди активний контекст стає надто великим або надто шумним, з'являються передбачувані проблеми:

- **Замовчування правил (Rule silencing)**: Claude стабільно слідує 80% конвенцій, але повністю ігнорує окремі правила, які повинні застосовуватися.
- **Суперечлива поведінка**: Claude застосовує правило в одних файлах, але ігнорує в інших, або застосовує суперечливі правила залежно від формулювання.
- **Повільні перші відповіді**: Модель витрачає більше часу на обробку великого контексту перед початком генерації виводу (це помітно за тривалішою затримкою навіть на простих завданнях).
- **Загальні відповіді**: Замість застосування специфічних паттернів проекту Claude повертається до загальних best practices — ознака того, що контекст проекту витісняється.

При появі таких ознак діагноз однозначний: проведіть аудит контексту (див. Розділ 7), а не пишіть додаткові інструкції.

### Обмеження за шляхом та ефективність бюджету

Обмеження релевантності за шляхом (Path-scoping) — це найефективніша поодинока техніка для скорочення постійного контексту. Замість завантаження всіх правил для всіх частин кодової бази ви завантажуєте лише ті, що стосуються файлів у поточному фокусі.

Типовий проект без обмеження за шляхами:

```
Завжди активний: кореневий CLAUDE.md з правилами бекенду + фронтенду + БД + API = 8,000 токенів
```

Той самий проект з обмеженням за шляхами:

```
Завжди активний: кореневий CLAUDE.md зі спільними правилами = 2,000 токенів
Активний в src/api/: модуль api = +1,500 токенів
Активний в src/components/: модуль frontend = +1,200 токенів
Активний в prisma/: модуль database = +800 токенів
```

Результат: зменшення завжди активного контексту на 40-50% без жодної втрати якості покриття інструкціями. Кожна підсистема отримує свій повний набір правил, але тільки тоді, коли робота йде безпосередньо в ній.

## 3. Ієрархія конфігурацій

### Трирівневий стек

```
┌──────────────────────────────────────────────┐
│  Глобальний (~/.claude/CLAUDE.md)            │
│  Ідентичність, тон, універсальні інструменти,│
│  міжпроектні конвенції                       │
├──────────────────────────────────────────────┤
│  Проектний (./CLAUDE.md + модулі шляхів)     │
│  Архітектурні рішення, стек, правила         │
│  команди, процедури деплою                   │
├──────────────────────────────────────────────┤
│  Сесійний (інструкції в чаті, прапорці)      │
│  Спеціальні перевизначення, обмеження        │
│  експерименту, параметри одного завдання     │
└──────────────────────────────────────────────┘
```

Нижчі рівні перевизначають вищі. Сесійна інструкція може змінити проектне правило; проектне правило може змінити глобальний дефолт. Це надає вам гнучкі шляхи обходу без необхідності вносити незворотні зміни у спільну конфігурацію.

### Глобальна конфігурація

**Розташування**: `~/.claude/CLAUDE.md`

**Що має бути тут**:
- Налаштування ідентичності та стилю спілкування
- Універсальні вподобання щодо інструментів (наприклад, RTK, CLI-утиліти)
- Загальні конвенції написання коду (формат комітів, стиль PR)
- Безпекові обмеження, які діють скрізь
- Дефолтні налаштування тону та форматів виводу

**Чого тут бути НЕ повинно**:
- Архітектурні рішення під конкретний проект
- Правила під конкретний стек (React-хуки, Prisma-паттерни)
- Специфіка розгортання або середовища виконання
- Усе, що змінюється від проекту до проекту

**Цільовий розмір**: Тримайте глобальний конфіг у межах 200 рядків. Це ваші постійні накладні витрати для кожної сесії в будь-якому проекті. Його роздування однаково шкодить усім вашим проектам.

```markdown
# Приклад: Мінімальний ефективний глобальний CLAUDE.md

## Communication
- Respond in the same language the user writes in
- Prefer direct answers over preamble
- No em dashes in written output

## Git
- Commit messages: imperative mood, <72 chars subject line
- Never commit without being asked

## Code Style
- Prefer explicit error handling over silent failure
- Add TODO comments only when referencing a tracked issue
```

### Проектна конфігурація

**Розташування**: `./CLAUDE.md` (корінь проекту)

**Що має бути тут**:
- Стек технологій та версії, що використовуються
- Архітектурні рішення та їх обґрунтування
- Командні конвенції, специфічні для цієї кодової бази
- Шаблони організації файлів
- Вимоги до тестування та цільове покриття
- Правила безпеки для конкретного проекту
- Оголошення імпорту модулів за шляхами (path-scope)

**Шаблон структури**:

```markdown
# Project: MyAwesomeApp

## Stack
- Language: TypeScript 5.3
- Framework: Next.js 14 (App Router)
- Database: PostgreSQL 16 via Prisma
- Testing: Vitest + React Testing Library

## Architecture
- Server Components by default; use "use client" only when interactivity requires it
- API routes in /app/api; no business logic in route handlers
- Business logic in /lib/services; each service is a plain function module

## Conventions
- File naming: kebab-case for files, PascalCase for React components
- Error handling: wrap service calls in Result<T, E> pattern (see lib/result.ts)
- Never expose raw database IDs in API responses; use UUIDs

## Path-Scoped Modules
@src/api/CLAUDE-api.md
@src/components/CLAUDE-components.md
@prisma/CLAUDE-db.md
```

**Проблема Золотоволоски: висота**

У виробничих файлах `CLAUDE.md` стабільно виникають два типи помилок:

**Занадто розмиті правила**: "Пиши чистий код", "Дотримуйся найкращих практик безпеки", "Роби функції маленькими". Ці інструкції проходять крізь модель, не змінюючи її поведінку. Модель вже має власне розуміння "чистого коду" з етапу переднавчання і за замовчуванням використовує його, що може абсолютно не збігатися з потребами вашого проекту. Побажання і загальні заклики ігноруються.

**Занадто деталізовані правила**: "Використовуй відступи у 2 пробіли", "Додавай порожній рядок після блоків імпорту", "Починай приватні методи з підкреслення". Це правила лінтера, а не когнітивні рішення. Вони мають бути в `.eslintrc`, `.editorconfig` або `prettier.config.js` і забезпечуватися детермінованими інструментами, а не ймовірнісною моделлю. Їхнє внесення до `CLAUDE.md` марнує бюджет контексту та працює ненадійно.

**Ефективна висота**: Фіксуйте рішення, які модель без цієї інструкції прийняла б інакше. Перевірочне запитання звучить так: "Чи міг би Claude без контексту проекту зробити тут щось по-іншому?". Якщо так, правило має бути в `CLAUDE.md`. Якщо воно загальне чи декларативне — видаліть його. Якщо воно забезпечується лінтером — видаліть його.

| Висота | Приклад | Вердикт |
|----------|---------|---------|
| **Занадто розмите** | "Write clean code" | Видалити — модель ігнорує, поведінка не змінюється |
| **Занадто розмите** | "Follow best practices for security" | Видалити — замініть конкретними обмеженнями |
| **Ефективне** | "Never expose raw database IDs in API responses; use UUIDs" | Залишити — конкретно, модель за дефолтом зробила б інакше |
| **Ефективне** | "Use the Result<T, E> pattern for service functions, not try/catch" | Залишити — конкретно, перевизначає поширений дефолт |
| **Занадто детальне** | "Use 2-space indentation" | Видалити — доручіть це Prettier |
| **Занадто детальне** | "Add JSDoc comments to every function" | Видалити — перенесіть у лінтер |

Архітектурні вибори, стандарти якості та чіткі правила типу "чого не робити і чому" — це і є ефективна висота. Загальні побажання та механічні дрібниці є просто шумом.

### Сесійна конфігурація

**Механізм**: Інструкції в чаті, `/add-dir` або прапорці системного промпту для поточної сесії.

**Що має бути тут**:
- Обмеження під конкретне завдання ("Для цього рефакторингу не змінюй публічний API")
- Параметри експерименту ("Використовуй новий формат помилок, який я тестую в цьому файлі")
- Обмеження відладки ("Логуй кожен виклик інструменту для цієї сесії")
- Тимчасові перевизначення проектних конвенцій

Сесійні інструкції не зберігаються. Вони випаровуються після завершення сесії. Будь-яка інструкція, яку ви змушені повторювати з сесії в сесію, має бути перенесена в конфіг проекту, а не залишатися на рівні сесії.

### Дерево рішень: Куди спрямувати це правило?

```
Чи актуальне це правило для КОЖНОГО проекту, над яким я працюю?
├── Так → Глобальний CLAUDE.md (~/.claude/CLAUDE.md)
└── Ні ↓

Чи стосується це правило лише окремих файлів або підсистем?
├── Так → Модуль з обмеженням за шляхом (наприклад, src/api/CLAUDE-api.md)
└── Ні ↓

Чи актуальне це правило для всього проекту в цілому?
├── Так → Проектний CLAUDE.md (у корені)
└── Ні ↓

Чи стосується це правило лише поточної сесії або поточного завдання?
├── Так → Інструкція в сесії (inline)
└── Ні → Переосмисліть: чи дійсно це правило, чи просто одноразове вподобання?
```

### Ланцюжок імпорту та семантика перевизначення

Потік імпорту рухається так: `глобальний → корінь проекту → модулі за шляхами → сесія`.

У разі конфліктів:
- Більш специфічне перевизначає менш специфічне (модуль за шляхом виграє у кореня, корінь виграє у глобального)
- Оголошене пізніше перевизначає оголошене раніше на тому самому рівні
- Сесійні інструкції перевизначають будь-яку збережену конфігурацію

**Практичний приклад**: Ваш глобальний конфіг каже "use two-space indentation". Проектний каже "use four-space indentation for Python". А сесія вимагає "match the existing file style". Сесійна інструкція виграє для цієї сесії, з дефолтом у 4 пробіли для Python-файлів та 2 пробіли для всіх інших.

Документуйте перевизначення явно. Недокументоване перевизначення, яке прямо суперечить батьківському правилу, створює плутанину під час аудитів.

## 4. Модульна архітектура

### Проблема з монолітною конфігурацією

600-рядковий `CLAUDE.md` без чіткої структури — найпоширеніша причина невдач у промислових проектах. Симптоми:

1. Змішуються правила з абсолютно різних доменів — конвенція React-компонента лежить поруч із правилом міграції БД
2. Claude читає всі 600 рядків, але через особливості розподілу уваги правила на 5-й сторінці важать набагато менше, ніж на 1-й
3. Нові члени команди не можуть швидко зорієнтуватися в правилах
4. Оновлення потребують вичитки всього файлу, щоб уникнути конфліктів перед внесенням змін
5. Дотримання інструкцій (adherence) прогресуюче погіршується в міру зростання файлу

Вихід є архітектурним: розділити моноліт на фокусні модулі та використовувати обмеження релевантності за шляхами (path-scoping), щоб завантажувати кожен модуль лише тоді, коли він дійсно потрібен.

### Патерн обмеження за шляхом (Path-Scoping)

**Механізм**: Claude Code підтримує імпорт вигляд `@path/to/file.md` у файлі `CLAUDE.md`. Коли імпорт із обмеженням за шляхом є активним, правила з цього модуля додаються до контексту *тільки тоді*, коли файли за вказаним шляхом знаходяться у фокусі поточного завдання.

**Структура файлів**:

```
project/
├── CLAUDE.md                       # Кореневий конфіг, спільні правила + @imports
├── src/
│   ├── api/
│   │   └── CLAUDE-api.md           # Правила конкретно для API
│   ├── components/
│   │   └── CLAUDE-components.md    # UI/React правила
│   └── lib/
│       └── CLAUDE-lib.md           # Правила загальних бібліотек/утиліт
├── prisma/
│   └── CLAUDE-db.md                # Правила бази даних та міграцій
└── tests/
    └── CLAUDE-tests.md             # Конвенції тестування
```

**Кореневий `CLAUDE.md` з імпортами**:

```markdown
# Project Config

## Shared Rules
[...shared rules here...]

## Subsystem Modules
@src/api/CLAUDE-api.md
@src/components/CLAUDE-components.md
@src/lib/CLAUDE-lib.md
@prisma/CLAUDE-db.md
@tests/CLAUDE-tests.md
```

**Приклад модуля за шляхом** (`src/api/CLAUDE-api.md`):

```markdown
# API Rules

- Route handlers in /app/api only; no business logic inline
- All endpoints must validate input with Zod before processing
- Error responses use the standard format: { error: string, code: string }
- Never log request bodies that may contain PII; log IDs only
- Rate limiting headers must be present on all public endpoints
- Authentication: verify JWT in middleware, not in individual handlers
```

Ці 6 правил будуть у контексті лише тоді, коли робота йде безпосередньо в директорії `src/api/`. Вони не споживають бюджет токенів, коли ви створюєте компоненти в `src/components/`.

### Скіли проти Правил

Ця відмінність часто ігнорується, хоча вона критично важлива:

| Вимір | Правила (Rules) | Скіли (Skills) |
|-----------|-------|--------|
| **Суть** | Обмеження, стандарти, конвенції | Можливості, процедури, воркфлоу |
| **Коли активні** | Завжди діють у фокусі | Викликаються виключно на вимогу |
| **Приклад** | "Never use `any` in TypeScript" | "How to add a new API endpoint" |
| **Розташування** | `CLAUDE.md` | `.claude/skills/` |
| **Вартість токенів** | Завжди активні (overhead) | Завантажуються тільки при виклику |

**Правила (Rules)** визначають, чого Claude має або не має робити за замовчуванням. Вони окреслюють межі прийнятного виводу коду.

**Скіли (Skills)** описують, як виконувати складні багатоетапні завдання, що вимагають специфічних для проекту знань. Вони завантажуються лише тоді, коли Claude має виконати конкретний тип завдання, а не висять у пам'яті постійно.

*Практичний приклад*: Правило каже: "API-ендпоінти повинні мати валідацію Zod". Скіл каже: "Ось покроковий шаблон для створення нового API-ендпоінту в цьому проекті, включаючи схему Zod, обгортку обробки помилок, перевірку авторизації та структуру тестів".

Внесення процедури створення ендпоінту до правил означало б завантаження 40 рядків процедурних інструкцій у кожну сесію, навіть коли ви просто фіксуєте баг у верстці. Перенесення цього в скіл дозволяє завантажувати ці рядки лише при створенні ендпоінту.

**Правило**: `Never expose raw database IDs in API responses.`
**Скіл**: `How to generate and use UUID-based public identifiers for entities.`

**Спільнотні бібліотеки скілів**

Готові набори скілів значно зменшують початкові витрати на створення модульного контексту:

- `anthropics/claude-code-skills` (офіційна): шаблони скілів від команди розробників Anthropic, які покривають загальні робочі процеси розробки.
- `ibelick/ui-skills`: скіли для роботи з UI-компонентами та дизайн-системами у фронтенд-проектах.

Їх можна клонувати, досліджувати та адаптувати під конвенції вашого проекту замість написання з нуля. Ставтеся до них як до вихідних точок — форкайте та змінюйте під ваш стек та命名 конвенції, а не копіюйте сліпо.

### Прогресивне розкриття

Принцип простий: не завантажуйте все наперед. Завантажуйте інформацію по мірі виникнення потреби.

**Ядро конфігурації (завжди активне)**:
- Архітектурні рішення та їхні причини
- Стандарти кодування та правила іменування
- Обмеження безпеки
- Вподобання щодо інструментів

**Контекстні модулі (завантажуються під завдання)**:
- Процедури розгортання (завантажуються при деплої)
- Шаблони API (завантажуються при роботі з API-шаром)
- Шаблони тестів (завантажуються при написанні тестів)
- Схеми бази даних та міграції (завантажуються при зміні схеми)

**Шаблон реалізації з використанням скілів**:

```
.claude/
├── skills/
│   ├── deploy-production.md      # Завантажується при запиті: "deploy this"
│   ├── add-api-endpoint.md       # Завантажується при запиті: "add endpoint for X"
│   ├── write-migration.md        # Завантажується при запиті: "add DB column"
│   └── create-component.md      # Завантажується при запиті: "create component for X"
```

Кожен файл скіла містить покрокову інструкцію з конкретними паттернами проекту. Claude підтягує його, коли розпізнає тип завдання, а не завантажує заздалегідь.

**Кількість інструментів MCP та бюджет контексту**

Сервери MCP інтегрують описи інструментів безпосередньо в системний промпт. Кожен сервер додає свої JSON-схеми інструментів, які з'їдають бюджет контексту ще до початку будь-якого діалогу. Інженерні гайдлайни Anthropic рекомендують:

- Не більше 10 активних серверів MCP на проект
- Не більше 80 інструментів сумарно серед усіх активних серверів

При виході за ці ліміти накладні витрати на описи інструментів починають відчутно зменшувати кількість токенів, доступних для коду та історії завдань. При 80+ інструментах ви спалюєте від 15 до 20 тисяч токенів лише на схеми інструментів — бюджет, який міг би піти на код, історію діалогу чи вміст файлів.

Принцип прогресивного розкриття актуальний для MCP серверів так само, як і для правил. Завантажуйте сервери MCP контекстно під конкретні задачі замість активації всього списку для кожного проекту:

```json
{
  "mcpServers": {
    "database": { },
    "github": { }
  }
}
```

Уникайте практики додавання кожного доступного MCP сервера в налаштування проекту "про всяк випадок". Кожен незадіяний, але завантажений сервер — це чистий збиток токенів. Якщо сервер використовується менш ніж у 20% сесій проекту, йому не місце в дефолтному конфігу.

### Антипаттерн: монолітний CLAUDE.md

**Як це виглядає**:

```markdown
# CLAUDE.md (600 lines)

## Rules
1. Use TypeScript
2. No any types
3. Run tests before committing
4. API endpoints need auth
5. Use Prisma for DB queries
6. React components in PascalCase
7. Deploy with ./scripts/deploy.sh
8. Check OWASP Top 10 before shipping
[...492 more rules...]
```

**Чому це не працює**:

- Правила 1-20 отримують ~95% ваги уваги; правила після 500-го — лише ~30%
- Фронтенд-розробник змушений завантажувати правила бекенду та БД, які йому зараз не потрібні, і навпаки
- Відсутність логічного групування змушує вичитувати весь файл для пошуку потрібного правила
- Додавання нового правила вимагає перевірки всього гігантського файлу на конфлікти
- Рівень дотримання правил моделлю невпинно знижується в міру зростання файлу

**Як це виправити**:

1. Виділіть правила за доменами в окремі модулі за шляхами (path-scoped)
2. Залиште в кореневому `CLAUDE.md` лише спільні правила та декларації імпорту
3. Перенесіть процедурні покрокові знання у скіли
4. Зменшіть розмір кореневого `CLAUDE.md` після очищення до менш ніж 150 рядків

### Файлы структурных метаданных (Structural Metadata Files)

Правила та структура проекту — це два абсолютно різні типи контексту. Їхнє змішування створює файли, які занадто великі для постійного завантаження, але водночас занадто важливі, щоб їх ігнорувати.

**Контекст правил (Rules context)** відповідає на питання: *як я маю працювати в цьому проекті?* Він живе в `CLAUDE.md` та модулях за шляхами. Він є відносно стабільним та майже завжди актуальним.

**Структурний контекст (Structural context)** відповідає на питання: *яка форма цього проекту?* Скільки маршрутів API існує, які домени мають свої компоненти, де лежать вкладені `CLAUDE.md`, скільки моделей Prisma описано. Ця інформація потрібна виключно для завдань реалізації (implementation) — створення нового файлу, додавання роуту, навігації по новому домену — і абсолютно не потрібна для сесій відладки, написання документації або код-рев'ю.

Постійне завантаження структурного контексту марнує токени. Але його повна відсутність змушує Claude блукати файловою системою вручну на початку кожного завдання, витрачаючи ваші кроки (turns) та створюючи зайвий шум.

Рішення: невеликий автоматично згенерований YAML-файл (~1K токенів), який фіксує структурну форму кодової бази та реєструється в `CLAUDE.md` як вказівник (pointer), а не імпортується автоматично.

**Що туди включати** — лише п'ять розділів і нічого більше:

| Розділ | Вміст | Приклад |
|---------|----------|---------|
| `layers` | Архітектурні шари з кореневими шляхами та кількістю файлів | `routers: { root: "src/api", count: 33 }` |
| `component_domains` | Домени фіч із шляхами та кількістю компонентів | `{ name: "chat", count: 66 }` |
| `nested_contexts` | Усі вкладені `CLAUDE.md` / `AI_INSTRUCTIONS.md` у `src/` з кількістю рядків та фокусом | `{ path: "src/server/CLAUDE.md", lines: 45 }` |
| `stats` | Агрегована статистика: всього файлів, кількість тестів, моделей схеми | `total_ts_files: 543` |
| `key_paths` | Канонічні шляхи, в яких Claude часто помиляється | `prisma_schema: "src/server/db/prisma/schema.prisma"` |

Тримайте цей файл у межах 1K токенів. Будь-яка вища деталізація вже належить до самих вихідних файлів коду.

**Патерн реєстрації вказівників (Pointer Registration)**

Не завантажуйте цей файл автоматично через директиву `@machine-readable/code-map.yaml` у `CLAUDE.md`. Замість цього зареєструйте його в таблиці посилань, яка пояснює Claude, що містить цей файл і коли до нього слід звертатися:

```markdown
## Context Indexes (load on demand)

| File | Contents | When to load |
|------|----------|--------------|
| machine-readable/code-map.yaml | Architecture layers (counts + roots), component domains, nested context files, project stats | Before any implementation task: new file, new route, new component |
| machine-readable/ai-config.yaml | Full AI tooling config: rules, skills, commands, agents, hooks | When auditing or modifying AI configuration |
| PROJECT_INDEX.md | Detailed architecture narrative, ADRs, domain glossary | Deep architectural work only |
```

Цей патерн масштабується: Claude зчитує таблицю на початку сесії, розуміє, які довідкові файли існують і навіщо вони потрібні, і підвантажує їх лише тоді, коли поточне завдання цього вимагає. Сесія відладки взагалі не торкнеться карти коду (`code-map.yaml`). Завдання з реалізації завантажить її за один виклик інструменту.

**Що означає "автоматично згенерований" на практиці**

Скрипт генерації має робити лише три речі: викликати `readdirSync` на коренях шарів для підрахунку файлів, обійти дерево `src` для визначення сумарної кількості `.ts`/`.tsx` файлів та знайти через glob вкладені `CLAUDE.md` для наповнення `nested_contexts`. Ніякого AST-парсингу, запитів до БД чи мережевих викликів. Весь скрипт має виконуватися менш ніж за секунду. Додайте його до вашої задачі `pnpm ai:sync` (або її аналога).

Критичне обмеження проектування: **ніколи не додавайте в цей файл контент, який редагується вручну.** Як тільки ви це зробите, файл почне застарівати та дрейфувати. Автоматично згенеровані файли не можуть брехати про поточний стан кодової бази; файли з ручним контентом — будуть і роблять це постійно.

**Практичний приклад** (EdTech платформа Méthode Aristote, ~1,300 файлів вихідного коду):

```yaml
version: "1.0.0"
architecture: "Client → tRPC → Router → Service → Repository → Prisma"

layers:
  routers:
    root: "src/server/api/routers"
    description: "Tier 1 — Zod validation, delegate to service"
    count: 33
  services:
    root: "src/server/api/services"
    description: "Tier 2 — business logic, enforcePermission()"
    count: 61
  repositories:
    root: "src/server/api/repositories"
    description: "Tier 3 — CRUD Prisma only"
    count: 38

stats:
  total_ts_files: 543
  total_tsx_files: 798
  prisma_models: 48
  unit_tests: 268
```

Завдяки реєстрації цього файлу як вказівника Claude відповідає на питання "скільки роутерів tRPC існує?" за один запит замість того, щоб вручну сканувати директорію `src/server/api/routers/`. Для завдання типу "додати роутер оплати" модель миттєво дізнається правильний корінь, поточну кількість та архітектурне обмеження — ще до того, як прочитає хоча б один вихідний файл коду.

Готовий до використання шаблон доступний у файлі [`examples/context-engineering/code-map-template.yaml`](../examples/context-engineering/code-map-template.yaml).

## 5. Командна збірка

### Проблема N × M × P

У масштабах команди інженерія контексту стикається з комбінаторним викликом:

- **N розробників**: різні ролі, інструменти, вподобання у стилі спілкування
- **M проектів**: різні стеки технологій, конвенції, цілі розгортання
- **P конфігурацій**: кожен розробник × кожен проект потребує своєї конфігурації

Підтримувати вручну $N \times M$ окремих файлів `CLAUDE.md` неможливо. Коли змінюється спільна командна конвенція, вам доведеться оновити $N \times M$ файлів. При створенні нового проекту все доводиться будувати з нуля. При зміні ролі розробника його конфігурацію доводиться переписувати.

Рішення полягає у **профільному складанні (profile-based assembly)**: єдина спільна кодова база модулів конфігурації та індивідуальні профілі, які декларативно вказують, які саме модулі включити та які персональні вподобання накласти зверху.

Рівняння $N \times M \times P$ перетворюється на: $N$ профілів $\times 1$ спільна база модулів — що є абсолютно керованим.

### Структура профілю YAML

Кожен член команди має свій файл профілю YAML, який декларативно визначає його конфігурацію:

```yaml
# profiles/alice.yaml

profile:
  name: "Alice"
  role: "frontend"
  tools:
    - typescript
    - react
    - tailwind
  conventions:
    - atomic-design
    - accessibility-first
  communication:
    language: "en"
    verbosity: "concise"

modules:
  include:
    - shared/core-rules.md
    - shared/git-conventions.md
    - shared/security-baseline.md
    - frontend/react-patterns.md
    - frontend/tailwind-conventions.md
    - frontend/testing-rtl.md
    - frontend/accessibility-checklist.md
  exclude:
    - backend/database-rules.md
    - backend/api-design.md
    - devops/deployment-procedures.md

overrides:
  - "Prefer named exports over default exports"
  - "Use Radix UI primitives before writing custom components"
```

### Скрипт збірки

Скрипт збірки зчитує файл профілю розробника та конкатенує вказані в ньому модулі у фінальний `CLAUDE.md`:

```bash
#!/usr/bin/env bash
# scripts/assemble-context.sh

set -euo pipefail

PROFILE="${1:-}"
CHECK_MODE="${2:-}"

if [[ -z "$PROFILE" ]]; then
  echo "Usage: ./assemble-context.sh <profile-name> [--check]"
  exit 1
fi

PROFILE_FILE=".claude/profiles/${PROFILE}.yaml"
OUTPUT_FILE="CLAUDE.md"
MODULES_DIR=".claude/modules"

if [[ ! -f "$PROFILE_FILE" ]]; then
  echo "Profile not found: $PROFILE_FILE"
  exit 1
fi

# Parse profile with yq or python
MODULES=$(python3 -c "
import yaml
with open('$PROFILE_FILE') as f:
    profile = yaml.safe_load(f)
for m in profile['modules']['include']:
    print(m)
")

# Assemble output
ASSEMBLED=$(mktemp)

echo "# Claude Code Configuration" > "$ASSEMBLED"
echo "# Generated from profile: $PROFILE" >> "$ASSEMBLED"
echo "# Generated at: $(date -u +%Y-%m-%dT%H:%M:%SZ)" >> "$ASSEMBLED"
echo "" >> "$ASSEMBLED"

while IFS= read -r module; do
  MODULE_PATH="${MODULES_DIR}/${module}"
  if [[ -f "$MODULE_PATH" ]]; then
    echo "## From: ${module}" >> "$ASSEMBLED"
    cat "$MODULE_PATH" >> "$ASSEMBLED"
    echo "" >> "$ASSEMBLED"
  else
    echo "WARNING: module not found: $MODULE_PATH" >&2
  fi
done <<< "$MODULES"

# Append personal overrides
python3 -c "
import yaml
with open('$PROFILE_FILE') as f:
    profile = yaml.safe_load(f)
overrides = profile.get('overrides', [])
if overrides:
    print('## Personal Overrides')
    for o in overrides:
        print(f'- {o}')
" >> "$ASSEMBLED"

if [[ "$CHECK_MODE" == "--check" ]]; then
  if diff -q "$OUTPUT_FILE" "$ASSEMBLED" > /dev/null 2>&1; then
    echo "OK: CLAUDE.md matches profile $PROFILE"
    rm "$ASSEMBLED"
    exit 0
  else
    echo "DRIFT: CLAUDE.md does not match profile $PROFILE"
    diff "$OUTPUT_FILE" "$ASSEMBLED"
    rm "$ASSEMBLED"
    exit 1
  fi
fi

mv "$ASSEMBLED" "$OUTPUT_FILE"
echo "Assembled CLAUDE.md from profile: $PROFILE"
```

**Використання**:

```bash
# Згенерувати CLAUDE.md з вашого профілю
./scripts/assemble-context.sh alice

# Перевірити наявність дрейфу (використовується в CI)
./scripts/assemble-context.sh alice --check
```

### Виявлення дрейфу в CI (CI Drift Detection)

Члени команди регенерують свій `CLAUDE.md` із власних профілів, але базові модулі в репозиторії постійно розвиваються. Без автоматичного контролю розробник може працювати із застарілим конфігом — таким, що не містить нещодавно доданих правил безпеки чи оновлених конвенцій.

Спеціальна задача в GitHub Actions дозволяє автоматично виявляти такий дрейф:

```yaml
# .github/workflows/context-drift.yml

name: Context Drift Detection

on:
  schedule:
    - cron: '0 9 * * 1'   # Щопонеділка о 9:00 UTC
  push:
    paths:
      - '.claude/modules/**'

jobs:
  check-drift:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Install dependencies
        run: pip install pyyaml

      - name: Check all profiles for drift
        run: |
          DRIFT=0
          for profile_file in .claude/profiles/*.yaml; do
            profile=$(basename "$profile_file" .yaml)
            echo "Checking profile: $profile"
            if ! ./scripts/assemble-context.sh "$profile" --check; then
              echo "DRIFT detected in profile: $profile"
              DRIFT=1
            fi
          done
          exit $DRIFT

      - name: Notify on drift
        if: failure()
        uses: actions/github-script@v7
        with:
          script: |
            github.rest.issues.create({
              owner: context.repo.owner,
              repo: context.repo.repo,
              title: 'Context drift detected — CLAUDE.md needs regeneration',
              body: 'One or more team profiles are out of sync with the current module library. Run `./scripts/assemble-context.sh <profile>` to regenerate.',
              labels: ['context-engineering']
            })
```

### Онбординг за допомогою профілів

Для нових членів команди ланцюжок онбордингу стає неймовірно простим:

```bash
# 1. Скопіюйте шаблонний профіль під вашу роль
cp .claude/profiles/template-frontend.yaml .claude/profiles/yourname.yaml

# 2. Налаштуйте файл профілю під власні вподобання

# 3. Згенеруйте ваш індивідуальний CLAUDE.md

# 4. Перевірте згенерований файл

# 5. Додайте ваш профіль в Git (генерований CLAUDE.md має бути в .gitignore)
git add .claude/profiles/yourname.yaml
git commit -m "chore: add context profile for yourname"
```

Обов'язково додайте `CLAUDE.md` до файлу `.gitignore` у корені проекту. Джерелом правди є виключно файл профілю YAML, а не кінцевий згенерований файл.

## 6. Життєвий цикл контексту

### Борг інструкцій (Instruction Debt)

Правила мають властивість накопичуватися. Але їх рідко видаляють. Це створює борг інструкцій: поступове накопичення застарілих, непотрібних чи суперечливих правил — кожне з яких продовжує з'їдати ваш дорогоцінний бюджет контексту.

Ознаки наявності боргу інструкцій:

- Правило посилається на бібліотеку, використання якої припинено півроку тому
- Два правила говорять протилежні речі про один і той самий патерн кодування
- Правило описує крайовий випадок (edge case), який був актуальний лише під час конкретної міграції
- Одне й те саме обмеження прописано тричі в різних розділах конфігу
- Розробники змушені коментувати або ігнорувати конкретні правила, оскільки вони конфліктують із поточною практикою розробки

Борг інструкцій має накопичувальну вартість: кожне конфліктне чи неактуальне правило витісняє дійсно корисне, а поведінка моделей при наявності конфліктів стає непередбачуваною.

**Квартальний ритм аудиту**: Плануйте систематичний аудит контексту щокварталу (або після завершення великих віх проекту). Промпт для аудиту:

```
Review every rule in CLAUDE.md for:
1. Relevance: Does this still apply to the current stack and patterns?
2. Specificity: Is this actionable, or is it too vague to enforce?
3. Conflicts: Does this contradict another rule?
4. Coverage: Is this already covered by a more general rule?

For each rule, classify as: KEEP | UPDATE | ARCHIVE | DELETE
```

Запускайте це як окрему сесію з Claude, подаючи на вхід поточний `CLAUDE.md` та вимагаючи структурованого звіту.

### Цикл оновлення (The Update Loop)

Найпоширеніша помилка після отримання невдалого коду від Claude — просто виправити код руками та піти далі. Це втрачена можливість навчання системи.

**Поганий цикл**:
```
Claude генерує некоректний патерн
→ Розробник виправляє його вручну
→ Наступна сесія: Claude знову генерує той самий некоректний патерн
→ Розробник знову виправляє його вручну
→ Повторення до нескінченності
```

**Хороший цикл**:
```
Claude генерує некоректний патерн
→ Розробник аналізує причину (правило відсутнє? надто розмите? конфліктує з іншим?)
→ Розробник оновлює CLAUDE.md, додаючи виправлене або нове правило
→ Наступна сесія: Claude одразу генерує правильний код
→ Правило назавжди залишається в конфігу та страхує інших
```

Цикл оновлення — це спосіб, за допомогою якого ваша система конфігурації вчиться на реальному досвіді. Кожен невдалий вивід моделі — це сигнал про те, що у вашій інженерії контексту щось не так або чогось бракує. Ставтеся до цього як до баг-репорту проти `CLAUDE.md`, а не як до випадкової одноразової помилки.

**Практичний формат оновлення правил**:

Коли ви додаєте нове правило для виправлення помилки, записуйте причину (Rationale) прямо в тексті правила:

```markdown
- Use the `Result<T, E>` type for service functions, not try/catch
  (Rationale: try/catch at service level hides error types from callers;
   Result forces explicit error handling at the call site)
```

Таке обґрунтування вирішує дві задачі: допомагає майбутнім аудиторам зрозуміти, чому це правило взагалі існує, і надає Claude набагато кращий контекст для правильного застосування правила.

### Підживлення знань після спринтів (Knowledge Feeding)

Наприкінці кожного спринту або релізу виділіть кілька хвилин на сесію підживлення знань:

1. **Нові стандарти**: "У цьому спринті ми стандартизували підхід Х для вирішення задач типу Y. Додай це в CLAUDE.md."
2. **Виявлені антипатерни**: "Ми спробували підхід Х, і це призвело до проблем Y. Додай правило, щоб уникати цього."
3. **Архітектурні рішення**: "Ми вирішили використовувати Х замість Y, оскільки Z. Задокументуй це, щоб Claude більше не пропонував Y."
4. **Застарілі паттерни**: "Ми відмовляємося від Х. Додай правило використовувати Y та маркувати використання Х як deprecated."

Це дозволяє підтримувати конфігурацію в актуальному стані без необхідності проводити масштабні капітальні перегляди конфігу.

### Конвеєр ACE (Assemble → Check → Execute)

Для команд, які запускають Claude Code в автоматизованих або напівавтоматизованих сценаріях, конвеєр ACE пропонує чітку модель виконання:

```
Assemble (Збірка) → Check (Перевірка) → Execute (Виконання)
```

**Assemble (Збірка)**: Генерація файлу `CLAUDE.md` під конкретного розробника та завдання на основі його профілю та спільних модулів проекту.

**Check (Перевірка)**: Запуск швидкої перевірки — набору з 3-5 контрольних промптів (Canary Checks), які підтверджують ключові моделі поведінки перед виконанням основного завдання. Якщо перевірка провалена, виправте конфіг перед запуском.

**Execute (Виконання)**: Безпосередній запуск Claude Code з валідованим контекстом для виконання основного завдання.

```bash
#!/usr/bin/env bash
# ace.sh — Assemble, Check, Execute

PROFILE="${1:-}"
TASK="${2:-}"

if [[ -z "$PROFILE" || -z "$TASK" ]]; then
  echo "Usage: ./ace.sh <profile> <task-description>"
  exit 1
fi

echo "=== ASSEMBLE ==="
./scripts/assemble-context.sh "$PROFILE"

echo "=== CHECK ==="
./scripts/run-canaries.sh
CANARY_EXIT=$?

if [[ $CANARY_EXIT -ne 0 ]]; then
  echo "Canary checks failed. Fix context issues before executing."
  exit 1
fi

echo "=== EXECUTE ==="
claude "$TASK"
```

### Ретроспектива сесії (Session Retrospective)

Наприкінці кожної сесії роботи з Claude Code, перед самим закриттям чату, запитайте модель:

```
Looking at what we built or changed in this session:
1. What patterns did we use that aren't in CLAUDE.md?
2. What did I have to correct that could become a rule?
3. What decisions did we make that should be documented?

Generate 3-5 candidate rules for CLAUDE.md based on this session.
```

Це займає всього 2-3 хвилини, але дає вам чіткі, готові до використання правила. Ви переглядаєте їх та обираєте ті, що дійсно варто додати. З часом саме завдяки цьому ваша система конфігурації накопичуватиме справжні знання про проект, а не просто загальні правила.

### Ланцюжок контекстів (Context Chaining)

Ланцюжок контекстів — це патерн, коли вихідні дані одного вікна контексту стають структурованими вхідними даними для наступного. Кожна сесія будується поверх попередньої, передаючи вперед лаконічний структурований звіт замість того, щоб просто викидати накопичений стан.

Це відрізняється від підходу "Сесія під задачу" (Session-per-Concern, в описах свіжого контексту), який розділяє задачі в ізольовані сесії. Ланцюжок контекстів дозволяє знанням накопичуватися: висновки кожної сесії збагачують стартовий контекст наступної.

**Структура паттерну**:

```
Сесія 1:
  Вхід: Опис завдання + CLAUDE.md
  Робота: Дослідження, аналіз, початкова реалізація
  Вихід: summary.md (прийняті рішення, відкриті питання, валідовані паттерни)

Сесія 2:
  Вхід: Опис завдання + CLAUDE.md + summary.md з Сесії 1
  Робота: Реалізація коду на основі результатів Сесії 1
  Вихід: оновлений summary.md + написані файли коду

Сесія 3:
  Вхід: Опис завдання + CLAUDE.md + оновлений summary.md
  Робота: Огляд, полірування, інтеграція коду
  Вихід: фінальні артефакти + lessons.md для внесення в CLAUDE.md
```

Критичне правило дисципліни: звіт, що передається вперед, має бути ретельно очищеним та структурованим, а не просто сирим логом діалогу. Сирі логи миттєво повертають проблему гниття контексту. Хороший звіт — це від 200 до 500 токенів чистої суті: які рішення прийняті, які підходи підтверджено, які тупикові шляхи відкинуто.

**Коли використовувати**:
- Складні багатоденні завдання, де починати кожну сесію з нуля було б занадто дорого за токенами та часом
- Завдання-дослідження, де результати перших сесій накладають жорсткі рамки на наступні етапи
- Ітеративні дизайнерські завдання, де накопичене розуміння має критичне значення

**Коли НЕ використовувати**:
- Завдання з чистими атомарними межами (одна сесія, один результат, наступного разу чистий старт)
- Сценарії, коли початкові припущення першої сесії виявилися помилковими і вам потрібен свіжий, неупереджений погляд

Ланцюжок контекстів розширює контекст свідомо. Це протилежність циклу Ральфа (Ralph Loop), який повністю відкидає стан. Використовуйте ланцюжок, коли накопичене розуміння є цінним активом; використовуйте цикл Ральфа, коли накопичений стан стає тягарем та джерелом помилок.

## 7. Вимірювання якості

### Питання для самооцінки

Періодично (щонайменше раз на квартал) перевіряйте свій `CLAUDE.md` за цими запитаннями:

**Актуальність (Relevance)**:
- Чи відповідає це правило поточним версіям бібліотек, стеку та практикам команди?
- Чи не було це правило написане для проблеми, якої в коді більше не існує?
- Чи зрозуміє новий розробник, чому це правило взагалі тут присутнє?

**Специфічність (Specificity)**:
- Чи достатньо конкретне це правило, щоб Claude розумів, коли саме його треба застосувати?
- Чи містить правило хоча б один реальний приклад відповідності та приклад порушення?
- Чи можуть двоє розробників зрозуміти це правило по-різному?

**Конфліктність (Conflicts)**:
- Чи не суперечить це правило іншому правилу в тому самому файлі?
- Чи не суперечить це правило інструкціям у вкладених модулях за шляхами?
- Чи не суперечить воно глобальним конвенціям без явного оголошення перевизначення?

**Покриття (Coverage)**:
- Чи не є це правило просто окремим випадком іншого, більш загального правила, яке вже описане?
- Чи не дублює воно архітектурні рішення, які вже зафіксовані в інших секціях?

Правило, яке провалює більше ніж одну з цих перевірок, є першим кандидатом на оновлення або видалення.

### Canary Checks (Перевірочні промпти)

Canary Checks — це прості, швидкі тестові промпти, які перевіряють, чи слідує Claude ключовим конвенціям проекту. Запускайте їх перед та після внесення змін у `CLAUDE.md` для запобігання регресіям поведінки.

**Структура**: 3-5 промптів, які досить прості для миттєвої генерації, але водночас достатньо специфічні, щоб одразу виявити ігнорування правил.

**Приклад набору canaries для React/TypeScript проекту**:

```bash
# scripts/run-canaries.sh

PASS=0
FAIL=0

check() {
  local name="$1"
  local prompt="$2"
  local expected_pattern="$3"

  result=$(claude "$prompt" --output-format text 2>/dev/null)

  if echo "$result" | grep -qE "$expected_pattern"; then
    echo "PASS: $name"
    PASS=$((PASS + 1))
  else
    echo "FAIL: $name"
    echo "  Expected pattern: $expected_pattern"
    echo "  Got: $(echo "$result" | head -5)"
    FAIL=$((FAIL + 1))
  fi
}

check "TypeScript interfaces" \
  "Generate a React component that accepts a name and age prop" \
  "interface.*Props"

check "Named exports" \
  "Create a utility function that formats a date" \
  "^export (function|const)"

check "No any type" \
  "Write a function that processes user data" \
  "^((?!: any).)*$"

check "Error result type" \
  "Write a service function that fetches user data from an API" \
  "Result<"

echo ""
echo "Canaries: $PASS passed, $FAIL failed"
[[ $FAIL -eq 0 ]]
```

**Коли запускати перевірочні промпти**:
- Перед злиттям (merge) будь-яких змін у `CLAUDE.md`
- Після додавання нового модуля за шляхом
- Коли хтось із команди повідомляє про дивну чи нестабільну поведінку Claude
- Як регулярний крок у процесі виявлення дрейфу конфігів у CI

### Відстеження дотримання (Adherence Tracking)

Простий, але надзвичайно ефективний метод: для кожного ключового правила в `CLAUDE.md` відстежуйте, як часто Claude порушує його на кожні 10 послідовних взаємодій, де це правило мало застосовуватися.

| Правило | Кількість порушень / 10 | Стан |
|------|----------------|--------|
| TypeScript interfaces for props | 1/10 | Здоровий |
| Result type for service functions | 0/10 | Здоровий |
| No raw database IDs in API responses | 3/10 | Потребує перегляду |
| Structured logging with request context | 5/10 | Занадто розмите |
| OWASP Top 10 check before shipping | 8/10 | Недієве в такому формулюванні |

Правила з рівнем порушень понад 20% є неефективними з однієї з трьох причин:
1. Занадто розмито описані
2. Конфліктують з іншими правилами
3. Знаходяться занадто низько в кінці файлу, отримуючи замало уваги моделі

**Виправлення для "занадто розмитих"**: Додайте один чіткий приклад відповідності (compliance) та один антиприклад порушення коду.

**Виправлення для "конфліктних"**: Знайдіть конфлікт, визначте, яке з правил є пріоритетним, видаліть або оновіть слабше правило та додайте чітке зауваження.

**Виправлення для "занижених у файлі"**: Перенесіть правило у верхню третину файлу або на більш помітне місце в його розділі.

### Оцінка боргу контексту (Context Debt Score)

Універсальна метрика здоров'я вашої системи інженерії контексту:

$$\text{Context Debt Score} = \left(\frac{\text{total\_rules}}{150}\right) \times \left(\frac{\text{conflicts\_found}}{\text{total\_rules}}\right) \times 100$$

Де:
- `total_rules` = кількість окремих дієвих правил у всіх завантажених конфігах
- `150` = умовна стеля ефективної уваги моделі
- `conflicts_found` = кількість правил, які прямо чи опосередковано суперечать іншим

| Рівень оцінки | Стан | Необхідна дія |
|-------------|--------|--------|
| **< 30** | Здоровий | Стандартний квартальний аудит |
| **30 – 60** | Деградація | Очищення та дедуплікація; усунення конфліктів |
| **60 – 80** | Слабкий | Необхідна серйозна реструктуризація |
| **> 80** | Критичний | Почніть з нуля, залишивши лише топ-30 правил |

**Розрахунок оцінки**:

```bash
# Підрахунок правил (приблизний: рядки, що починаються з "- ")
TOTAL_RULES=$(grep -c "^- " CLAUDE.md 2>/dev/null || echo 0)

# Підрахунок конфліктів потребує ручного огляду або LLM-сесії
# Запустіть: claude "Scan CLAUDE.md and count rules that contradict each other. Return the count."

echo "Total rules: $TOTAL_RULES"
echo "Run conflict audit manually or with Claude"
```

### Виявлення дрейфу контексту (Context Drift Detection)

Існуючі метрики дотримання (canaries, ручні підрахунки) потребують регулярної інтерпретації людиною: ви дізнаєтеся про порушення правила лише тоді, коли самі його помітите. Системне автоматичне виявлення дрейфу — це комплементарний шар, який ловить зміни в поведінці моделі автоматично, ще до того, як вони стануть реальними помилками в коді.

Ці підходи прийшли з моніторингу ML-моделей (ML observability). Вони більше актуальні для автоматизованих CI-конвеєрів розробки, ніж для повсякденної інтерактивної роботи, але самі концепти корисні скрізь.

**Метод косинусної відстані (Cosine distance method)**

Найбільш готовий до впровадження інженерний підхід. Ми отримуємо ембеддінги виводів моделі (відповідей на фіксовані тестові промпти) та вимірюємо їх косинусну відстань від еталонного "золотого" ембеддінгу.

1. Створіть 5-10 фіксованих тестових промптів, які перевіряють конвенції (аналогічно до canaries).
2. На стабільному етапі ("golden baseline") збережіть вихідні відповіді моделі та розрахуйте їх ембеддінги.
3. При кожному наступному запуску генеруйте відповіді на ті самі промпти та вимірюйте косинусну відстань від еталону.
4. Сигналізуйте про проблему, якщо середня відстань перевищує поріг (зазвичай 0.15-0.20 для речення або невеликого блоку тексту).

Що це ловить: поступовий дрейф стилю, стирання дрібних конвенцій, зміни структури виводу — все це задовго до того, як відсоток грубих порушень почне зростати.

**Частка зміщених ознак (Share of drifted features)**

Більш глибокий метод порівняно з простою косинусною відстанню. Замість єдиного агрегованого показника відстані ви відстежуєте, які саме виміри ембеддінгу змістилися вище встановленого порогу. Це дозволяє точно зрозуміти, яка саме характеристика виводу змінилася (довжина, формальність, стиль коду), а не просто зафіксувати факт змін.

Для реалізації потрібна модель ембеддінгів та база даних моніторингу. Починайте з косинусної відстані; додавайте аналіз ознак лише тоді, коли виникне потреба детально діагностувати причини дрейфу.

**Максимальна середня розбіжність (Maximum Mean Discrepancy, MMD)**

Ядерний метод порівняння двох розподілів виводів моделі. MMD дає математичну відповідь на запитання: "Чи є виводи моделі за цей тиждень статистично відмінними від еталонного періоду?". Метод чудово працює з високорозмірними ембеддінгами та не потребує попереднього визначення ознак для моніторингу.

MMD потребує складнішого налаштування, ніж косинусна відстань, але генерує значно менше хибних тривог при природно високій варіативності відповідей моделі. Релевантно для команд із великим обсягом генерацій (сотні запусків Claude на день).

**Пороги статистичної відстані**

Незалежно від обраного методу, пороги чутливості мають значення:

| Метрика відстані | Поріг для тривоги | Примітка |
|----------------|-----------------|------|
| **Cosine distance** | > 0.15 | Працює для більшості ембеддінгів речень |
| **Euclidean distance** | Залежить від розмірності | Потребує попередньої нормалізації ембеддінгів |
| **Manhattan distance** | Залежить від розмірності | Більш стійка до викидів (outliers), ніж евклідова |

Ці пороги є лише стартовою точкою. Калібруйте їх під природну дисперсію вашого проекту: якщо ваші завдання творчі та гнучкі, встановлюйте більш лояльні пороги.

**Коли використовувати виявлення дрейфу**:
- Автоматизовані конвеєри розробки, де немає постійного контролю кожної відповіді людиною
- Після оновлень `CLAUDE.md`, щоб переконатися, що загальна поведінка залишилася стабільною
- При оновленні версій моделей Claude (поведінка моделей може помітно дрейфувати від версії до версії)
- Автоматичний регресійний аналіз після будь-яких змін конфігурацій контексту

Для повсякденної розробки з регулярним оглядом людиною цілком достатньо canary-тестів та відстеження рівня дотримання правил розробниками вручну.

### Корисні метрики для відстеження з часом

| Метрика | Як виміряти | Цільовий рівень |
|--------|---------------|--------|
| **Обсяг завжди активного контексту** | `wc -w CLAUDE.md ~/.claude/CLAUDE.md` | < 5,000 слів |
| **Кількість діючих правил** | `grep -c "^- " CLAUDE.md` | < 150 правил |
| **Вік конфігураційного файлу** | `git log --follow -p CLAUDE.md | head -20` | Великий перегляд кожні 6 місяців |
| **Рівень порушень ключових правил** | Ручні періодичні перевірки | < 20% порушень |
| **Відсоток проходження canaries** | `./scripts/run-canaries.sh` | 100% (усі пройдено) |

## 8. Методи скорочення контексту

### Обмеження за шляхом: найдієвіший метод

Обмеження релевантності за шляхом (Path-scoping) дозволяє скоротити постійний контекст на 40-50% без жодної втрати глибини правил. Це найважливіша структурна зміна для проектів, де розмір конфігу перевищує ~200 рядків.

Кроки впровадження:

1. Визначте природні кордони доменів у вашому коді (API, фронтенд, БД, тести, інфраструктура)
2. Для кожного домену створіть файл `CLAUDE-{domain}.md` у відповідній директорії
3. Перенесіть туди специфічні правила з кореневого `CLAUDE.md`
4. Замініть перенесений контент у кореневому `CLAUDE.md` директивами `@path/to/CLAUDE-domain.md`
5. Перевірте працездатність та дотримання інструкцій через canary-тести

Ціль після рефакторингу: кореневий `CLAUDE.md` розміром менше 150 рядків (тільки загальні правила та імпорти).

### Негативні обмеження (Negative Constraints)

Емпірично доведено: негативні обмеження ("ніколи не роби Х") працюють на 15-25% ефективніше, ніж позитивні інструкції ("роби Y") для запобігання використанню поганих паттернів. Це звучить контрінтуїтивно, адже здається, що позитивна інструкція є чіткішою. Але на практиці моделі потрібно активно боротися зі своєю природною схильністю використовувати типові дефолти; чітке найменування забороненого паттерну із префіксом "ніколи" діє набагато сильніше.

| Патерн правила | Формулювання | Рівень дотримання |
|---------|-------------|-----------|
| **Позитивне (слабше)** | "Use structured logging for all backend services" | ~75% |
| **Негативне (сильніше)** | "Never use console.log in backend services; use the structured logger (pino)" | ~90% |

**Техніка**: Для кожного правила, де некоректний патерн є типовою поведінкою моделі за замовчуванням (використання console.log, try/catch без обгортки, дефолтні експорти, типи any), переформулюйте правило як негативне обмеження, прямо вказавши, чого саме слід уникати.

### Стиснення правил (Rule Compression)

Довгі розлогі правила з поясненнями з'їдають токени та розсіюють увагу моделі. Стискайте правила до їхньої сухої суті:

**До стиснення** (розлого, 38 слів):
```markdown
- When creating React components, always make sure to use TypeScript interfaces
  for props, and define them before the component declaration, not inline, to
  improve readability and enable reuse.
```

**Після стиснення** (стисло, 9 слів):
```markdown
- React props: TypeScript interface, declared before component, never inline.
```

Стиснута версія демонструє вищий рівень дотримання — короткі чіткі тези отримують більше когнітивної уваги моделі на одне правило. Зберігайте розлогі пояснення виключно у форматі приміток (comments або blockquotes), коли вони дійсно критичні для розуміння.

**Правило стиснення**: Якщо правило займає більше одного рядка, запитайте себе — це саме обмеження чи вже пояснення його причин? Переносьте пояснення в коментарі (з символом `#` або блоком `>`). Саме правило тримайте в межах одного рядка.

### Видалення дублікатів (Deduplication)

Одне й те саме обмеження, записане різними словами в різних місцях, не підсилює його виконання — воно лише роздуває контекст та розсіює увагу моделі. Знаходьте та безжально видаляйте семантичні дублікати.

**Основні джерела дублювання**:
- Спільне правило в загальній секції та його трохи інша копія у вкладеному модулі за шляхом
- Нове правило, додане для виправлення багу, без видалення старого більш загального правила, яке воно фактично замінює
- Правила, скопійовані з конфігів різних розробників при їх злитті

**Процес дедуплікації**:

```
Scan CLAUDE.md for semantic duplicates. Two rules are duplicates if they
constrain the same behavior, even if worded differently. List all duplicate
pairs and recommend which version to keep based on specificity and clarity.
```

Запустіть цей промпт у сесії з Claude проти вашого `CLAUDE.md`. Оцініть рекомендації та об'єднайте правила.

### Патерн архівування (The Archive Pattern)

Коли ви видаляєте правило, ви втрачаєте інституційну пам'ять команди про те, чому воно взагалі з'явилося. Ця пам'ять є надзвичайно цінною — через півроку хтось може знову спробувати принести в проект той самий поганий патерн, з яким боролося це правило.

Замість повного видалення застарілих правил використовуйте патерн архівування:

```
.claude/
├── CLAUDE.md              # Активні правила (актуальний контекст)
└── CLAUDE-archive.md      # Архів застарілих правил із примітками про причини
```

**Формат архівного запису**:

```markdown
## Archived Rules

### [Retired 2026-01] Use MongoDB for session storage
Replaced by: Use PostgreSQL with the sessions table for session storage.
Reason: Standardized on single database; MongoDB was only used for sessions and added operational complexity.
```

Архів не завантажується моделлю — це довідковий документ виключно для людей. Він надійно оберігає команду від повторення старих помилок та суперечок.

### Правило 80/20 для правил

У більшості реальних проектних конфігурацій лише 20% правил визначають 80% критичних рішень Claude. Інші 80% правил покривають рідкісні крайові випадки, дрібні стилістичні вподобання та ситуації, які виникають раз на місяць.

Визначення вашого топу 20%:

1. Випишіть усі правила з вашого `CLAUDE.md`
2. Для кожного правила оцініть: "Як часто це правило реально змінює код Claude в процесі щоденної роботи?"
3. Правила щоденної дії: залишайте, шліфуйте, ставте на самий початок файлу
4. Правила щотижневої дії: залишайте, розміщуйте в середині файлу
5. Правила щомісячної дії: розгляньте можливість перенесення в скіли, які завантажуються виключно на вимогу
6. Правила рідкісної дії: безжально переносьте в архів

Мета полягає не в тому, щоб взагалі відмовитися від покриття цих випадків — а в тому, щоб правила першочергової важливості не розчинялися в купі другорядних інструкцій.

**Позиціонування має значення**: Розміщуйте ваш топ-20% правил у першій третині файлу `CLAUDE.md`. Увага моделі розподіляється нерівномірно по довгому документу — перші рядки отримують максимальну увагу.

### Підсумок: методи скорочення за впливом

| Метод | Скорочення контексту | Складність впровадження | Вплив на дотримання (Adherence) |
|-----------|------------------|--------|-----------------|
| **Path-scoping** | 40-50% | Середня | +15-25% |
| **Negative constraints** | 0% (переформулювання) | Низька | +15-25% на правило |
| **Rule compression** | 20-30% | Низька | +5-10% |
| **Deduplication** | 10-20% | Низька | +5-15% |
| **Archive pattern** | 10-30% | Низька | +5-10% |
| **80/20 prioritization** | 0% (зміна порядку) | Низька | +10-20% |

Найбільш ефективна послідовність дій для проекту з високим боргом контексту:
1. Застосуйте Path-scoping (найбільший архітектурний виграш)
2. Проведіть дедуплікацію (видаліть зайвий шум)
3. Стисніть правила (зробіть решту правил чіткими та короткими)
4. Заархівуйте застаріле (очистіть конфіг безпечно)
5. Змініть порядок правил (підніміть найважливіші на самий початок)

## 9. Оцінка зрілості

Розвиток інженерії контексту в команді проходить кілька послідовних етапів. Більшість команд зупиняється на Рівні 2 — не тому, що вищі рівні занадто складні, а тому, що проблеми Рівня 2 часто є невидимими. Якість коду здається нормальною, тому стимул рухатися далі просто не виникає. Ця оцінка робить розрив видимим.

### Шість рівнів зрілості

| Рівень | Назва | Що реально існує | Головна проблема (Режим відмови) |
|-------|------|-------------|--------------|
| **0** | **Без конфігу** | LLM взагалі без `CLAUDE.md` | Загальні відповіді, нульове розуміння проекту |
| **1** | **Плоский конфіг** | Один файл `CLAUDE.md`, без структури | Правила накопичуються хаотично, дотримання падає після ~100 рядків |
| **2** | **Структурований** | Розділи, відокремлення глобальних правил | Добре для одного розробника, ламається в команді |
| **3** | **Модульний** | Модулі за шляхами (path-scoped), скіли | Правила підтримуються, але немає перевірки дотримання |
| **4** | **Вимірюваний** | Canary-тести, відстеження порушень | Система працює, але з часом непомітно дрейфує |
| **5** | **Інженерний** | Профілі, CI-контроль за дрейфом, конвеєр ACE, квартальний аудит | — |

### Самооцінка зрілості

Дайте відповідь на запитання. Зупиніться на першому запитанні, де ваша відповідь "Ні" — це і є ваш поточний рівень зрілості інженерії контексту.

**Рівень 0 → 1**: Чи є у вашому проекті файл `CLAUDE.md`?

**Рівень 1 → 2**: Чи розділена ваша конфігурація на загальні правила (в `~/.claude/CLAUDE.md`) та специфічні для проекту правила (в корені проекту `./CLAUDE.md`)? Чи є у файлі чітко структуровані розділи?

**Рівень 2 → 3**: Чи винесені правила конкретних підсистем в окремі вкладені модулі за шляхами (path-scoped) замість кореневого `CLAUDE.md`? Чи кореневий `CLAUDE.md` займає менше 150 рядків?

**Рівень 3 → 4**: Чи є у вас регулярні canary-тести для перевірки виконання правил? Чи ведеться хоча б спрощене відстеження рівня порушень правил? Чи проводиться аудит контексту після завершення великих етапів проекту?

**Рівень 4 → 5**: Чи збирають розробники свій `CLAUDE.md` декларативно з профілів замість ручного редагування? Чи налаштована CI-перевірка на наявність дрейфу конфігів від базових модулів? Чи проводяться ретроспективи наприкінці сесій для повернення знань у конфігурацію?

### Що робити на кожному рівні зрілості

| Поточний рівень | Наступна дія |
|------------|-------------|
| **0** | Створіть мінімальний `CLAUDE.md` з 5-10 ключовими правилами (див. Розділ 3). |
| **1** | Розділіть глобальний та проектний конфіги. Перенесіть спільні налаштування в `~/.claude/CLAUDE.md`. |
| **2** | Виділіть 2-3 підсистеми з найвищою активністю розробки. Створіть для них модулі за шляхами. |
| **3** | Напишіть 3-5 перевірочних промптів (canary prompts) для правил, які найчастіше ігноруються. |
| **4** | Впровадьте систему профілів розробників. Додайте контроль дрейфу в CI. Почніть робити ретроспективи. |
| **5** | Підтримуйте ритм квартальних аудитів. Система побудована — тепер важливе точне калібрування. |

Більшість команд переходять з Рівня 0 на Рівень 2 за один день. Рух із Рівня 3 на Рівень 4 вимагає вироблення звички вимірювання, а не просто написання додаткових конфігів. Головна проблема на високих рівнях зрілості — це не знання, а дисципліна ставлення до конфігурації як до живої системи, що постійно розвивається, а не як до одноразово налаштованого шаблону.

## 10. Робочий процес аудиту токенів

Теорія інженерії контексту перетворюється на реальні дивіденди лише тоді, коли ви почнете вимірювати ваші реальні накладні витрати токенів. Більшість розробників з подивом виявляють, що вони завантажують від 40 до 60 тисяч токенів постійного контексту ще до того, як відправлять перше повідомлення в сесії — файли конфігурацій, правила, виводи хуків, файли пам'яті та системний промпт Claude Code сумуються та створюють гігантський баласт. Цей розділ пропонує простий, відтворюваний процес аудиту, який займає менше 5 хвилин і дає чіткий план оптимізації.

### Що входить до постійного контексту (Fixed Context)

Кожна сесія роботи починається з базового набору токенів, які Claude завантажує перед обробкою першого повідомлення користувача:

| Компонент | Коли завантажується | Типовий обсяг |
|-----------|-------------|--------------|
| `~/.claude/CLAUDE.md` + `@imports` | Завжди | 5-15K токенів |
| Проектний `CLAUDE.md` | Завжди | 2-8K токенів |
| `.claude/rules/*.md` (автозавантаження) | Завжди | 5-40K токенів |
| `MEMORY.md` (пам'ять проекту) | Завжди | 1-3K токенів |
| Системний промпт Claude Code | Завжди | ~7,500 токенів |
| Вивід хуків (Hooks) | На кожен виклик інструменту | 0.1-2K токенів × частота викликів |
| `.claude/commands/*.md` | Лише при виклику | 0 за замовчуванням |
| `.claude/agents/*.md` | Лише при виклику | 0 за замовчуванням |

Важлива відмінність: Директорія `.claude/rules/` завантажує *всі* `.md` файли на початку сесії незалежно від їх релевантності завданням. Команди та агенти завантажуються ледаче (lazy-loading) — вони не коштують нічого, поки ви їх прямо не викличете. Файли правил у папці rules є найчастішим джерелом невидимого роздуття контексту.

### Крок 1 — Вимірювання компонентів

Запустіть ці команди в корені вашого проекту для детального аналізу компонентів за символами:

```bash
# Проектний CLAUDE.md
echo "=== PROJECT CLAUDE.md ===" && wc -c CLAUDE.md

# Файли правил, відсортовані за розміром (ваша найбільша зона економії)
echo "=== RULES FILES ===" && find .claude/rules -name "*.md" 2>/dev/null \
  | xargs wc -c 2>/dev/null | sort -rn | head -20

# Глобальні файли конфігурації
echo "=== GLOBAL ~/.claude ===" && ls -la ~/.claude/*.md 2>/dev/null \
  | awk '{print $5, $9}' | sort -rn
```

### Крок 2 — Розрахунок бюджету токенів

Кількість токенів $\approx$ кількість символів $\div 4$ (груба, але дуже надійна оцінка для суміші англійського тексту, коду та української прози).

```bash
# Розрахунок сумарного бюджету постійного контексту
GLOBAL=$(cat ~/.claude/CLAUDE.md ~/.claude/*.md 2>/dev/null | wc -c)
PROJECT=$(wc -c < CLAUDE.md 2>/dev/null || echo 0)
RULES=$(find .claude/rules -name "*.md" 2>/dev/null | xargs cat | wc -c)
MEMORY=$(find ~/.claude/projects -name "MEMORY.md" -path "*$(pwd | tr '/' '-')*" \
  2>/dev/null | xargs cat 2>/dev/null | wc -c || echo 0)
TOTAL=$(( GLOBAL + PROJECT + RULES + MEMORY + 30000 ))

echo "Global ~/.claude   : ~$(( GLOBAL / 4 )) tokens"
echo "Project CLAUDE.md  : ~$(( PROJECT / 4 )) tokens"
echo "Rules (auto-loaded): ~$(( RULES / 4 )) tokens"
echo "MEMORY.md          : ~$(( MEMORY / 4 )) tokens"
echo "System prompt      : ~7,500 tokens (estimate)"
echo "---"
echo "TOTAL              : ~$(( TOTAL / 4 )) tokens"
```

Для розуміння масштабу: вікно Claude становить 200K токенів. Постійне навантаження у 60K токенів означає, що 30% вікна з'їдено ще до початку будь-якої корисної роботи. Якщо реальне кодування додає ще 20-40K токенів, у вас залишається менше половини вікна для генерації вихідного коду.

### Крок 3 — Класифікація правил за частотою використання

Файли правил у папці `.claude/rules/` — це місце, де ховаються найбільші резерви економії токенів. Для кожного файлу в цій папці дайте відповідь на запитання: як часто він реально потрібен у типовій робочій сесії?

| Клас релевантності | Визначення | Необхідна дія |
|-------|------------|--------|
| **Завжди критичні (ALWAYS)** | Стосуються абсолютно кожної задачі (конвенції коду, формати виводу, правила безпеки) | Залишити в автозавантаженні |
| **Іноді потрібні (SOMETIMES)** | Релевантні у 20-40% сесій (методології відладки, правила керування задачами) | Залишити, якщо файли малі; перенести на запит, якщо великі |
| **Рідко потрібні (RARELY)** | Релевантні менш ніж у 10% сесій (робота з макетами Figma, сумісність з Windows, специфіка дизайн-системи) | Прибрати з автозавантаження |
| **Непотрібні (NEVER)** | Застарілі правила, покриті лінтером або іншими правилами проекту | Видалити або перенести в архів |

Запустіть цю класифікацію як промпт для Claude:

```
Read every file in .claude/rules/. For each file, classify it as:
- ALWAYS: applies to most tasks in a typical session
- SOMETIMES: applies in 20-40% of sessions
- RARELY: applies in under 10% of sessions

Output a table: | File | Size (chars) | Class | Reasoning |
Sort by size descending within each class.
Calculate: total chars that could be removed from auto-load if RARELY files
are excluded.
```

### Крок 4 — Аудит накладних витрат хуків (Hook Overhead)

Хуки, які запускаються на події `PreToolUse` або `PostToolUse`, виконуються при кожному виклику інструменту. Кожен такий запуск додає свій стандартний вивід (stdout) безпосередньо у вікно контексту. Хук, який видає всього 500 символів тексту при кожному виклику, за сесію зі 150 викликами інструментів додасть у ваш контекст 75K символів (~19K токенів) абсолютно безглуздого баласту.

Для перевірки ваших хуків запустіть:

```bash
# Список усіх хуків та типів подій
cat ~/.claude/settings.json | python3 -c "
import json, sys
data = json.load(sys.stdin)
hooks = data.get('hooks', {})
for event, hook_list in hooks.items():
    for h in hook_list:
        cmd = h.get('command', h.get('hooks', [{}])[0].get('command', '?'))
        print(f'{event}: {cmd[:80]}')
"
```

Для кожного хука `PreToolUse` або `PostToolUse` оцініть обсяг виводу, запустивши його команду вручну. Потім помножте цей обсяг на середню кількість викликів інструментів за сесію (запустіть команду `/cost` наприкінці типової сесії, щоб дізнатися точну кількість викликів).

**Шкідливі паттерни хуків, які слід негайно усунути:**
- Хуки, які через `cat` виводять цілі файли або багаторядкові звіти на кожен виклик інструменту
- Хуки, які безумовно запускають важкі команди на кшталт `git status` або `git log`
- Забуті інструкції `echo`, які використовувалися для налагодження та не були видалені

### Крок 5 — Створення плану дій

Типова економія токенів, яку можна отримати без використання складних RAG-систем чи кастомної інфраструктури:

| Дія | Складність | Ризики | Типова економія токенів |
|--------|--------|------|----------------|
| Прибрати автозавантаження для рідко використовуваних правил | 30 хв | Низькі | 5-20K токенів |
| Розділити великі файли правил на ядро + деталі | 1-2 год | Низькі | 3-8K токенів |
| Скоротити вивід хуків лише до критично необхідних полів | 1 год | Низькі | 2-10K токенів |
| Стиснути розлогі правила до сухої суті (див. Розділ 8) | 1-2 год | Низькі | 2-5K токенів |
| Очистити застарілі записи у файлі `MEMORY.md` | 30 хв | Низькі | 1-2K токенів |

Реальний перший прохід за цим планом зазвичай дозволяє скоротити постійний контекст на 30-50% без жодної необхідності розробляти складні інфраструктурні рішення.

### Питання про RAG (The RAG Question)

Ви можете зустріти поради повністю перенести всі файли правил у векторну базу даних та вилучати їх динамічно через механізм RAG. Це дійсно крута та виправдана оптимізація в масштабах величезних ентерпрайз-проектів — вона перетворює фіксований оверхед контексту на гнучкий точковий пошук під кожен запит та забезпечує ідеальне ліниве завантаження.

Але перш ніж інвестувати час у побудову такої інфраструктури, оцініть математику абсолютно чесно:

- Скільки токенів ви реально заощадите? (Виміряйте це точно за допомогою Кроків 1-3)
- Яка вартість реалізації? Налаштування `pgvector` або `Chroma` з кастомним MCP сервером — це повноцінний проект на 1-2 тижні роботи для команди розробників
- На якому етапі настане точка окупності? Якщо ваш постійний контекст після простого очищення вже впав нижче 20K токенів, побудова RAG принесе купу складності при майже нульовому реальному виграші

Для більшості індивідуальних розробників та невеликих команд класифікація та ледаче завантаження правил (просте відключення прапорця автозавантаження для рідкісних файлів) дає 80% результату RAG при всього 2% інвестицій часу та сил. RAG виправдовує свою складність лише тоді, коли кількість файлів правил у вас перевищує 50 і вам дійсно необхідна складна автоматична система розуміння інтенту розробника для підвантаження інструкцій.

### Шаблон промпту для аудиту

Цей промпт при запуску всередині проекту генерує детальний звіт про аудит. Замініть змінні шляхів за необхідності:

```
# Token Audit — [PROJECT NAME]

Audit this Claude Code project configuration for token overhead.
Be systematic and exhaustive, not superficial.

**Step 1 — Inventory**
List every file that is loaded at session start:
- ~/.claude/CLAUDE.md and all @imported files (with line counts)
- ./CLAUDE.md (line count)
- .claude/rules/*.md (all files, sorted by size)
- Project MEMORY.md (line count)

For each file, note: lines, approximate tokens (chars ÷ 4), and one-sentence
description of what it contains.

**Step 2 — Budget calculation**
Calculate: total fixed-context tokens before any user task.
Show the breakdown by component. Express as % of Claude's 200K window.

**Step 3 — Signal/noise classification**
For every rules file, classify as ALWAYS / SOMETIMES / RARELY based on how
often it would apply in a typical session on this project.
Flag any file over 5K chars that is classified SOMETIMES or RARELY.

**Step 4 — Hook audit**
Read .claude/settings.json (and ~/.claude/settings.json).
For each hook: event type, command, estimated stdout per invocation, and
whether it fires on every tool call or only at session boundaries.
Flag hooks that inject more than 200 chars per PreToolUse or PostToolUse call.

**Step 5 — Action plan**
Produce a prioritized table:
| Action | Estimated token savings | Effort | Risk |
Sort by: savings descending, then effort ascending.
Include only actions achievable without external infrastructure (no RAG, no
vector databases, no custom MCP servers).

**Step 6 — RAG verdict**
Based on the remaining savings after Step 5, calculate whether RAG would be
worth it: estimate residual savings, estimate setup cost in hours, and state
clearly whether the infrastructure investment is justified.
```
