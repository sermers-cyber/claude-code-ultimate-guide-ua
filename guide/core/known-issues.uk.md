# Відомі проблеми та критичні помилки

Цей документ відстежує підтверджені критичні проблеми, що впливають на користувачів Claude Code, на основі звітів спільноти та офіційних повідомлень.

> **Останнє оновлення**: 23 квітня 2026 року
> **Джерело**: [GitHub Issues](https://github.com/anthropics/claude-code/issues) + [Офіційні повідомлення Anthropic](https://www.anthropic.com/engineering)

---

## 🚨 Активні критичні проблеми

### 0. Баги кешу промптів — Тихе роздуття витрат (Березень 2026 - дотепер)

**Критичність**: 🔴 **ВИСОКА - ВПЛИВ НА ВИТРАТИ**
**Статус**: ⚠️ ЧАСТКОВО ВИПРАВЛЕНО (Баг 3 та Баг 2 все ще активні станом на v2.1.88)
**Проблема**: [#40524](https://github.com/anthropics/claude-code/issues/40524)
**Вперше повідомлено**: Березень 2026 року
**Вразливі версії**: v2.1.69+ (Баги 2 і 3), v2.1.36+ автономний бінарний файл (Баг 1)

#### Опис проблеми

Три незалежні баги порушують префіксне кешування промптів від Anthropic, призводячи до нарахування плати за створення кешу (`cache_creation`, повна вартість токенів) замість читання (`cache_read`, знижена вартість). Виміряний вплив на витрати залежить від шаблону використання:

- **Тільки Баг 3 (заголовок атрибуції)**: 2-5-кратне роздуття вартості системного промпту (~12K токенів) при кожному старті сесії та при кожному виклику субагента.
- **Активний Баг 2 (відновлення + 10+ скілів)**: перебудова 87-118K токенів при кожному відновленні сесії; у сесіях з 3-4 відновленнями зафіксовано **коефіцієнт читання кешу (cache read ratio) на рівні 4.3-34.6%** (порівняно з 95-99% у нормальних сесіях), що означає **10-20-кратну вартість кожного ходу** у найгірших випадках.
- **Комбінований ефект**: підтверджено покращення коефіцієнта попадання в кеш з 48% до 99.98% після застосування обхідних шляхів (вимірювання спільноти, CC#40524).

> **Підстава**: Підтверджено за допомогою зворотного проектування спільноти (CC#40524), аналізу вихідного коду витоку sourcemap npm та незалежного аналізу файлів JSONL сесій (ArkNill, квітень 2026). Anthropic випустила часткове виправлення у v2.1.88 (байти схеми інструментів). Баги 2 і 3 залишаються невиправленими.

#### Баг 2 — Повна перебудова кешу при --resume / --continue (v2.1.69+) — ВИСОКИЙ ВПЛИВ

**Першопричина**: Записувач сесій у форматі JSONL видаляє записи прикріплень `deferred_tools_delta` перед збереженням на диск. При відновленні сесії через `--resume` ці записи відсутні — тому рівень відкладених інструментів (deferred tools) не має історії попередніх оголошень і повторно оголошує всі інструменти з нуля. Це зміщує позицію кожного повідомлення у відновленому діалозі, повністю ламаючи префікс кешу на рівні повідомлень.

**Конкретні докази** (з аналізу JSONL-файлів сесій спільнотою, сесії з 14 скілами):

| Entry | cache_read | cache_creation | Event |
|-------|-----------|----------------|-------|
| 102 | 84,164 | 174 | Звичайний хід |
| 103 | 0 | 87,176 | **Відновлення — повна перебудова** |
| 105 | 87,176 | 561 | Відновлено |
| 166 | 115,989 | 221 | Звичайний хід |
| 167 | 0 | 118,523 | **Відновлення — повна перебудова** |

Кожне відновлення = 87-118K токенів перебудовуються як `cache_creation` замість `cache_read`. 3-4 відновлення за сесію = 300-400K марно витрачених токенів. Вплив масштабується відповідно до кількості скілів/відкладених інструментів: користувачі з 10+ скілами (поширено при роботі з фреймворками) бачать нульовий коефіцієнт читання кешу (0% cache ratio) при кожному відновленні.

**Тимчасове рішення**: Уникайте використання `--resume` та `--continue`, доки не вийде офіційне виправлення. Починайте нові сесії. Варіант даунгрейду: `npm install -g @anthropic-ai/claude-code@2.1.68` (остання версія перед цією регресією). Anthropic відстежує це внутрішньо (у вихідній телеметрії позначається як `inc-4747`).

**Технічне виправлення**: Збереження записів `deferred_tools_delta` та `mcp_instructions_delta` при записі сесії в JSONL, щоб процес відновлення міг коректно обчислити різницю (delta) замість повторного оголошення всього списку.

#### Баг 3 — Заголовок атрибуції (вплив від низького до середнього, v2.1.69+)

**Першопричина**: Claude Code додає платіжний заголовок (billing header) як **перший блок** системного промпту при кожному API-запиті. Цей заголовок містить 3-символьний хеш, згенерований з вашого першого повідомлення користувача, що робить його унікальним для кожної сесії, субагента та бічного запиту. Оскільки кеш Anthropic базується на префіксах, цей унікальний перший блок викликає "холодний промах" (cold miss) для системного промпту обсягом ~12K токенів під час кожного старту сесії та виклику субагента.

**Нюанс** (за інформацією jmarianski, першого аналітика, який здійснив RE): промах кешу системного промпту на початку сесії має "незначний вплив" на практиці, оскільки системний промпт є малим порівняно з загальним контекстом сесії. Баг з відновленням (Баг 2) має набагато більшу вимірювану вартість для активних користувачів.

**Емпіричне вимірювання**: Покращення коефіцієнта попадання в кеш з 48% до 99.98% із застосуванням тимчасового рішення — але це відображає комбінований ефект разом з іншими факторами кешування; ізольований вплив Багу 3 може бути меншим.

**Тимчасове рішення** (застосувати негайно, низький ризик):
```json
// ~/.claude/settings.json
{
  "env": {
    "CLAUDE_CODE_ATTRIBUTION_HEADER": "false"
  }
}
```
Дозволені значення: `"false"`, `"0"`, `"no"`, `"off"`. Перезапуск не потрібен.

#### Баг 1 — Заміна сигнального рядка (автономний бінарний файл v2.1.36+, граничний випадок)

**Першопричина**: Власний HTTP-стек Bun замінює плейсхолдер `cch=00000` у тілі запиту після серіалізації. Якщо цей точний рядок з'являється у вмісті вашого повідомлення (наприклад, у файлі `CLAUDE.md`, де обговорюється цей баг), він може бути замінений у неправильному місці.

**Тимчасове рішення**: Не вставляйте рядок `cch=00000` буквально в `CLAUDE.md` або конфігураційні файли. Примітка: це стосується лише автономного бінарного файлу, а не встановлень через npm/npx.

#### Інструмент для аудиту

Запустіть команду `/check-cache-bugs` (інструкція з встановлення знаходиться в директорії [examples/commands](../../examples/commands/check-cache-bugs.md)), щоб перевірити ваше середовище на наявність усіх трьох багів приблизно за 20 секунд.

> **Найкраща практика**: запускайте цю команду на самому початку нової сесії або як разовий виклик через `claude -p "$(cat .claude/commands/check-cache-bugs.md)"`, щоб уникнути забруднення контексту поточної сесії рядками `cch=` (що може спровокувати Баг 1).

#### Моніторинг здоров'я кешу

Щоб перевірити, чи ваші сесії є "здоровими", скористайтеся офіційною змінною середовища `ANTHROPIC_BASE_URL` для маршрутизації через прозорий локальний проксі-сервер та логуйте значення `cache_creation_input_tokens` / `cache_read_input_tokens` з відповідей API:

```json
// ~/.claude/settings.json
{
  "env": {
    "ANTHROPIC_BASE_URL": "http://localhost:8080"
  }
}
```

Запустіть наскрізний проксі-сервер на порту 8080, який читає, але не змінює запити й відповіді, розбираючи об'єкт `usage` з кожної відповіді. **Здорові сесії** показують коефіцієнт читання кешу > 80%; **уражені сесії** показують < 40%.

Альтернативно, перевіряйте файли сесій у форматі JSONL безпосередньо в `~/.claude/projects/` — шукайте поля `cache_creation_input_tokens` та `cache_read_input_tokens` для кожного ходу.

Інструменти спільноти для моніторингу:
- [`cc-diag`](https://github.com/nicobailey/cc-diag) — аналіз трафіку Claude Code на базі mitmproxy
- [`claude-code-router`](https://github.com/pathintegral-institute/claude-code-router) — прозорий проксі з логуванням

Патч від спільноти (застосовує виправлення як для Багу 1, так і для Багу 2):
- [`cc-cache-fix`](https://github.com/Rangizingo/cc-cache-fix) — розроблений спільнотою патч + набір інструментів тестування

#### Офіційна реакція

Часткове виправлення випущено у v2.1.88 (байти схеми інструментів). Підтверджено, що Баги 2 та 3 все ще активні.

**Відстеження**: [Issue #40524](https://github.com/anthropics/claude-code/issues/40524) (відкрита з березня 2026 року)

**Пов'язані проблеми**: [#40652](https://github.com/anthropics/claude-code/issues/40652) (cch= billing hash) · [#41663](https://github.com/anthropics/claude-code/issues/41663) (cache token consumption) · [#41607](https://github.com/anthropics/claude-code/issues/41607) (duplicate compaction subagents) · [#41767](https://github.com/anthropics/claude-code/issues/41767) (auto-compact loops v2.1.89) · [#41750](https://github.com/anthropics/claude-code/issues/41750) (context management fires every turn)

### 1. Автоматичне створення GitHub Issues не в тому репозиторії (Грудень 2025 - дотепер)

**Критичність**: 🔴 **КРИТИЧНА - РИЗИК БЕЗПЕКИ ТА ПРИВАТНОСТІ**
**Статус**: ⚠️ АКТИВНО (станом на 28 січня 2026 року)
**Проблема**: [#13797](https://github.com/anthropics/claude-code/issues/13797)
**Вперше повідомлено**: 12 грудня 2025 року
**Вразливі версії**: v2.0.65+

#### Опис проблеми

Claude Code **систематично створює публічні GitHub-іш'ю в репозиторії `anthropics/claude-code`** замість власного приватного репозиторію користувача, навіть під час роботи всередині локальної директорії git-репозиторію.

#### Наслідки

**ВИСОКИЙ - РИЗИК ПРИВАТНОСТІ/БЕЗПЕКИ**: Зафіксовано щонайменше **17+ підтверджених випадків**, коли користувачі випадково розкривали конфіденційну інформацію в публічному репозиторії:

- Схеми баз даних
- Облікові дані API (credentials) та деталі конфігурації
- Архітектура інфраструктури
- Приватні дорожні карти проектів (roadmaps)
- Налаштування безпеки

#### Симптоми

- Створення іш'ю з неочікуваним прапорцем `--repo anthropics/claude-code`
- Деталі приватних проектів з'являються в публічних іш'ю репозиторію `anthropics/claude-code`
- Відсутність запиту на підтвердження перед створенням іш'ю в публічному репозиторії
- Проблема виникає, коли ви просите Claude "створити іш'ю" (create an issue), перебуваючи в локальному git-репозиторії

#### Приклади випадкового створення

Нещодавні підтверджені випадки (січень 2026):
- [#20792](https://github.com/anthropics/claude-code/issues/20792): "Deleted - created in wrong repo"
- [#16483](https://github.com/anthropics/claude-code/issues/16483), [#16476](https://github.com/anthropics/claude-code/issues/16476): "Claude OPENS ISSUES ON THE WRONG REPO"
- [#17899](https://github.com/anthropics/claude-code/issues/17899): "Claude Code suddenly decided to create issue in claude code repo"
- [#16464](https://github.com/anthropics/claude-code/issues/16464): "[Mistaken Post] Please delete"

Повний список: [Пошук за запитом "wrong repo" АБО "delete this"](https://github.com/anthropics/claude-code/issues?q=is%3Aissue+%22wrong+repo%22+OR+%22delete+this%22)

#### Першопричина (Гіпотеза)

Claude Code може плутати:
- **Легітимний зворотний зв'язок (feedback)** щодо самого Claude Code → `anthropics/claude-code` (правильно)
- **Проблеми власного проекту користувача** → Поточний локальний репозиторій (має бути за замовчуванням)

Здається, інструмент жорстко закодував або має надлишковий пріоритет для `anthropics/claude-code` як цілі за замовчуванням.

#### Тимчасові рішення

**🛡️ ПЕРЕД створенням будь-яких GitHub-іш'ю через Claude Code:**

1. **Завжди перевіряйте поточний репозиторій**:
   ```bash
   # Перевірити поточний віддалений репозиторій (remote)
   git remote -v
   ```

2. **Явно вказуйте репозиторій**:
   ```bash
   gh issue create --repo YOUR_USERNAME/YOUR_REPO --title "..." --body "..."
   ```

3. **Перевіряйте команду** перед виконанням:
   - Шукайте прапорець `--repo anthropics/claude-code`
   - Якщо він присутній і є неправильним, скасуйте команду та вкажіть правильний репозиторій

4. **Використовуйте ручне підтвердження** для всіх команд `gh` у налаштуваннях Claude settings

5. **Ніколи не додавайте чутливу інформацію** у промпти для створення іш'ю, поки цей баг не буде виправлено

#### Якщо ви постраждали

Якщо ви випадково створили іш'ю з витоком конфіденційних даних:

1. **Негайно зверніться до підтримки GitHub Support** з проханням повністю видалити іш'ю (а не просто закрити)
2. **Анулюйте та оновіть (rotate) будь-які оприлюднені облікові дані** (ключі API, паролі, токени)
3. **Повідомте Anthropic** на [електронну адресу безпеки](mailto:security@anthropic.com), якщо витік є критичним з точки зору безпеки
4. **Перевірте можливі витоки даних**: Слідкуйте за використанням інформації, яка потрапила у відкритий доступ

#### Офіційна реакція

Станом на 28 січня 2026 року: **проблема залишається відкритою**, жодного офіційного виправлення не анонсовано.

**Відстеження**: [Issue #13797](https://github.com/anthropics/claude-code/issues/13797) (відкрита з 12 грудня 2025 року)

### 2. Надмірне споживання токенів (Січень 2026 - дотепер)

**Критичність**: 🟠 **ВИСОКА - ВПЛИВ НА ВИТРАТИ**
**Статус**: ⚠️ ПОВІДОМЛЕНО (Anthropic досліджує проблему)
**Проблема**: [#16856](https://github.com/anthropics/claude-code/issues/16856)
**Вперше повідомлено**: 8 січня 2026 року
**Вразливі версії**: v2.1.1+ (зареєстровано), може впливати і на попередні версії

#### Опис проблеми

Багато користувачів повідомляють про **в 4 рази швидше споживання токенів** порівняно з попередніми версіями, що призводить до:
- Набагато швидшого досягнення лімітів запитів (rate limits)
- Значно більшого споживання токенів для одинакових робочих процесів
- Несподіваного зростання витрат

#### Симптоми

Зі звіту в Issue #16856:
> "Починаючи з сьогоднішнього ранку після оновлення до CC 2.1.1 — використання просто смішне. Я працюю над тими ж проектами місяцями, ті самі завдання, той самий час. Але сьогодні я вичерпав 5-годинні ліміти приблизно в 4+ рази швидше!"

Поширені повідомлення:
- Тижневі ліміти вичерпуються за 1-2 дні (замість звичайних 5-7 днів)
- Сесії досягають 90% заповнення контексту після всього 2-3 повідомлень
- Збільшення споживання токенів у 4-20 разів для ідентичних операцій

#### Контекст

**Закінчення святкового бонусі лімітів**: З 25 по 31 грудня 2025 року Anthropic подвоїла ліміти використання як новорічний подарунок. Коли 1 січня 2026 року ліміти повернулися до норми, користувачі відчули суб'єктивне враження "зменшення лімітів".

Проте **повідомлення про проблему продовжували надходити і після цього періоду**, що вказує на наявність реальної внутрішньої проблеми.

#### Реакція Anthropic

З матеріалу видання [The Register](https://www.theregister.com/2026/01/05/claude_devs_usage_limits/) (5 січня 2026 року):
> "Представники Anthropic заявили, що компанія 'серйозно ставиться до всіх подібних звітів, але не виявила жодних збоїв чи багів, пов'язаних із використанням токенів', і зазначили, що виключили ймовірність помилок у своєму стеку виведення (inference stack)."

**Статус**: **Офіційно не підтверджено як баг** з боку Anthropic станом на 28 січня 2026 року.

#### Тимчасові рішення

Доки Anthropic розслідує цю проблему, скористайтеся такими порадами:

1. **Активно моніторьте використання токенів**:
   ```
   /context
   ```
   Регулярно перевіряйте обсяг використаних токенів відносно максимального ліміту.

2. **Використовуйте коротші сесії**:
   - Перезапускайте сесії, коли заповнення контексту наближається до 50-60%.
   - Розбивайте складні завдання на кілька окремих сесій.

3. **Вимкніть автоматичну компактизацію** (це може допомогти):
   ```bash
   claude config set autoCompaction false
   ```

4. **Зменшіть кількість інструментів MCP**, якщо вони не потрібні:
   - Перевірте файл `~/.claude.json` (поле `"mcpServers"`)
   - Вимкніть невикористовувані сервери

5. **Використовуйте субагентів** для ізольованих завдань:
   - Субагенти мають власні окремі вікна контексту
   - Використовуйте інструмент Task для складних операцій

6. **Відстежуйте свої шаблони використання**:
   - Порівнюйте споживання токенів до та після оновлення версії
   - Документуйте нетипові сплески

#### Поради щодо дослідження

Якщо ви стикаєтеся з надмірним споживанням токенів:

1. Запишіть вашу **версію Claude Code**: `claude --version`
2. **Порівняйте версії**: Протестуйте роботу на попередній стабільній версії, якщо є можливість
3. **Документуйте закономірності**: Які саме операції викликають високе споживання?
4. **Повідомляйте про баг з даними**: Додавайте інформацію про версію, тип операції та точну кількість токенів у звітах про помилки.

## ✅ Вирішені історичні проблеми

### Інцидент "Потрійної упряжі": Effort, токени міркування, багатослівність (Березень-Квітень 2026)

**Критичність**: 🔴 **ВИСОКА**
**Статус**: ✅ **ВИРІШЕНО** (всі три проблеми усунено до 20 квітня 2026 року)
**Хронологія**: 4 березня – 20 квітня 2026 року

#### Опис проблеми

Три незалежні зміни в системі зв'язування (harness) та системних промптах погіршували якість виведення Claude Code протягом шеститижневого періоду. Жодна з них не була регресією на рівні самої моделі; всі проблеми виникли на рівні шару зв'язування Claude Code. Використання Anthropic API напряму (без обгортки Claude Code) цією проблемою уражене не було.

#### Інцидент 1: Зміна значення Effort за замовчуванням з High на Medium (4 березня, скасовано 7 квітня)

**Тригер**: Тривала затримка (latency) у режимі високого міркування (high effort) викликала відчуття "зависання" інтерфейсу у деяких сесіях.
**Зміна**: Anthropic змінила рівень міркування (reasoning effort) за замовчуванням з `high` на `medium` для моделей Sonnet 4.6 та Opus 4.6.
**Наслідки**: Користувачі, які не налаштовували параметр `/effort high` вручну, без попередження отримували міркування середньої якості. Індикатор всередині продукту продовжував показувати значення "high", приховуючи цю регресію понад місяць.
**Уражені моделі**: Sonnet 4.6, Opus 4.6.
**Вирішення**: Скасовано 7 квітня. Нові значення за замовчуванням: `xhigh` для Opus 4.7, `high` для всіх інших моделей. Також було додано кращий інтерфейс (анімації міркування, чіткіший UX команди `/effort`).

#### Інцидент 2: Очищення токенів міркування (Thinking Tokens) після простою сесії (26 березня, виправлено 10 квітня)

**Тригер**: Anthropic впровадила очищення токенів міркування один раз, якщо сесія була неактивною понад годину (для зменшення затримки та вартості кешу при відновленні).
**Баг**: Дефект у коді спричинив очищення токенів міркування на кожному наступному кроці для решти сесії, а не лише один раз під час відновлення.
**Наслідки**: Сесії ставали повторюваними, "забуваючи" контекст, а Claude прогресивно втрачав нитку розмови у відновленій бесіді.
**Уражені моделі**: Sonnet 4.6, Opus 4.6.
**Вирішення**: Баг виправлено 10 квітня 2026 року (v2.1.101). Першопричина за словами Бориса Черного (Boris Cherny, команда CC): великі неактивні сесії спричиняли повні промахи кешу (900K+ токенів), викликаючи суттєві стрибки вартості токенів для користувачів тарифу Pro при відновленні сесії.

#### Інцидент 3: Інструкція промпту щодо скорочення багатослівності (16 квітня, скасовано 20 квітня)

**Тригер**: Anthropic додала до системного промпту інструкцію щодо зменшення багатослівності (verbosity) відповідей.
**Наслідки**: У поєднанні з іншими змінами промптів, які були активні на той момент, якість кодування помітно впала.
**Уражені моделі**: Sonnet 4.6, Opus 4.6, Opus 4.7.
**Вирішення**: Скасовано 20 квітня. Проблема тривала лише чотири дні і була вирішена найшвидше з усіх трьох інцидентів.

#### Вплив на спільноту

- Масові скарги на погіршення якості на платформах Reddit, HN, X/Twitter (березень–квітень 2026 року)

### Деградація якості моделі (Серпень-Вересень 2025)

**Критичність**: 🔴 **КРИТИЧНА**
**Статус**: ✅ **ВИРІШЕНО** (середина вересня 2025 року)
**Хронологія**: 25 серпня - початок вересня 2025 року

#### Опис проблеми

Користувачі повідомляли, що Claude Code створює:
- Гірші результати, ніж попередні версії
- Несподівані синтаксичні помилки
- Раптові вставки сторонніх символів (тайський/китайський текст у англомовних відповідях)
- Провали на базових завданнях
- Неправильні правки коду

#### Першопричина

Anthropic виявила **три інфраструктурні баги** (а не деградацію самої моделі):

1. **Неправильна маршрутизація трафіку**: ~30% запитів Claude Code спрямовувалися на неправильний тип сервера → погіршення відповідей
2. **Пошкодження виводу (Output Corruption)**: Помилка конфігурації при розгортанні 25 серпня викликала збої генерації токенів
3. **Помилка компіляції XLA:TPU**: Оптимізація продуктивності спровокувала латентний баг компилятора, що вплинув на вибір токенів

- Настрій користувачів на Reddit різко погіршився

## 🔄 Щоденні коливання якості роботи LLM (LLM Day-to-Day Performance Variance)

**Тип**: Очікувана поведінка (не баг)
**Критичність**: 🟡 **НИЗЬКА - ДЛЯ ОЗНАЙОМЛЕННЯ**
**Статус**: Притаманно роботі великих мовних моделей, не залежить від конкретної версії

### Що це таке

Якість виведення Claude може помітно відрізнятися від сесії до сесії, навіть за використання ідентичних промптів та чистого вікна контексту. Це відрізняється від деградації контекстного вікна (яка відбувається в межах однієї сесії у міру її заповнення). У даному випадку йдеться про різницю між абсолютно новими сесіями.

Користувачі іноді повідомляють про коротші відповіді, більш консервативні пропозиції або несподівані відмови на завдання, які чудово виконувалися напередодні. Це може створювати враження погіршення версії моделі, але це не так.

### Першопричини

**Ймовірнісне виведення (Probabilistic inference)**: Температура вище 0 означає, що кожен запуск виведення є недетермінованим. Два запуски одного промпту призведуть до генерації різних послідовностей токенів. Це фундаментальний принцип роботи мовних моделей.

**Варіативність маршрутизації MoE (Mixture of Experts)**: Claude використовує архітектуру суміші експертів (Mixture of Experts). При кожному прямому проході (forward pass) механізм маршрутизації вибирає, які ваги експертів активувати. Різні запуски активують різні комбінації, створюючи дещо відмінні результати навіть для семантично ідентичних вхідних даних.

**Варіативність інфраструктури**: У продакшені запити потрапляють на різні сервери з різними рівнями навантаження, поколіннями обладнання та тепловим станом (thermal states). Ці фактори впливають на обчислювальну точність арифметики з рухомою комою під час виведення, що призводить до ледь помітних, але реальних розбіжностей у відповідях.

**Чутливість до контексту**: Навіть після виклику `/clear` накопичуються крихітні відмінності між сесіями. Системний промпт, список інструментів та ініціалізація сесії — все це дещо коригує перші виведення моделі.

### Помітні ознаки

| Ознака | Що ви бачите | Що це означає |
|--------|-------------|---------------|
| Довжина відповіді | Коротша, менш детальна відповідь, ніж зазвичай | Маршрутизація обрала більш консервативний шлях експертів |
| Відмови (Refusals) | Граничні випадки, які зазвичай працюють, відхиляються | Інше калібрування параметрів безпеки під час цього запуску |
| Стиль коду | Більш розлогий або більш мінімалістичний код | Суміш активованих експертів спрацювала інакше |
| Креативність | Більш консервативні, менш оригінальні рішення | Це не втрата можливостей моделі, а результат вибірки токенів |
| Багатослівність | Більше застережень та дисклеймерів, ніж зазвичай | Нормальна варіативність ймовірностей токенів |

### Чим це НЕ є

- **Не є погіршенням версії моделі**: Anthropic випускає нові версії моделей навмисно та офіційно документує зміни. Щоденна варіативність відбувається в межах однієї й тієї ж версії моделі.
- **Не є багом, про який слід повідомляти**: Така поведінка є очікуваною та описана в літературі про великі мовні моделі. Вона є невід'ємною частиною ймовірнісного виведення.
- **Не є постійною проблемою**: Наступна сесія, найімовірніше, поводитиметься інакше. "Невдалий" запуск не свідчить про довгострокові зміни якості.
- **Не є деградацією вікна контексту**: Це явище всередині сесії, спричинене накопиченням токенів. Коливання якості — це розбіжності між різними чистими запусками.

> Винятком став інцидент серпня-вересня 2025 року ([див. розділ "Вирішені історичні проблеми"](#деградація-якості-моделі-серпень-вересень-2025)), коли Anthropic підтвердила реальні інфраструктурні баги, які спричинили системне погіршення роботи. Справжнє системне погіршення є рідкісним явищем і детально розслідується компанією. Звичайні коливання від сесії до сесії — це зовсім інше.

### Стратегії мінімізації впливу

**Обмежуйте промпт (Constrain the prompt)**: Більш специфічні промпти звужують простір можливих відповідей і роблять варіативність менш помітною. Запит "Напиши функцію, яка робить X, Y, Z, повертає тип T і обробляє граничний випадок E" дає значно стабільніші результати, ніж "напиши мені щось для обробки X."

**Очищуйте контекст перед важливою роботою**: Запускайте `/clear` перед виконанням критично важливих завдань. Накопичений шум від попередніх пошукових кроків може викривити подальші відповіді навіть в межах однієї сесії.

**Переформулюйте та спробуйте знову**: Якщо результат виглядає гіршим за ваші очікування, спробуйте подати той самий запит під іншим кутом. Друге формулювання часто спрямовує обчислення через інші шляхи експертів MoE та дає кращий результат.

**Порівнюйте з перевіреним промптом**: Якщо у вас є промпт із попередньої сесії, який дав чудовий результат, використовуйте його як еталон. Якщо сьогодні цей самий промпт стабільно видає значно гірші результати, це є приводом для детальнішого аналізу (і, можливо, відкриття іш'ю на GitHub, якщо це вдається відтворити).

**Калібруйте очікування відповідно до типу завдання**: Детерміновані завдання (регулярні вирази, прості перетворення, чітко визначені алгоритми) демонструють значно меншу варіативність, ніж творчі чи аналітичні завдання. Використовуйте Claude Code для перших з високим рівнем надійності; для других — заздалегідь плануйте етапи перевірки результатів у вашому процесі розробки.
