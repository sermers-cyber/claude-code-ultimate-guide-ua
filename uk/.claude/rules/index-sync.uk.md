# Синхронізація індексу

Коли в `guide/` з'являється сторінка, розділ, іменоване поняття чи іменований інструмент, машиночитний індекс має дізнатися про це в тому самому проході. Індекс живить MCP-сервер і палітру Cmd+K на лендінгу, тому вміст, який ніхто не проіндексував, ніхто й не знайде.

## Що оновлювати

| Файл | Коли | Як |
|------|------|-----|
| `machine-readable/reference.yaml` | Завжди | Ключ `deep_dive`, що вказує на `path#anchor`. Віддавай перевагу якорям перед `path:LINE`, який «пливе» щоразу, коли вище вставляють рядки. |
| `mcp-server/content/reference.yaml` | Завжди | Ручна копія. Скрипта ресинхронізації немає, і раніше вони розходилися. |
| `llms-full.txt` | Лише структура рівня посібника | Нова область верхнього рівня, а не кожен розділ. |
| `llms.txt`, `machine-readable/llms.txt` | Зміни у списку покриття | Тримай їх побайтово ідентичними. |

## Перевірка

```bash
python3 scripts/check-index-coverage.py --check   # кожен файл посібника досяжний
python3 scripts/validate-reference-yaml.py --ci   # якорі розв'язуються, шляхи існують
```

Обидві перевірки виконуються в CI (`.github/workflows/index-integrity.yml`). Бар'єр покриття стоїть на нулі, тож новий непроіндексований файл ламає збірку.

Ключ `deep_dive`, який додано, перейменовано або видалено, також потребує `pnpm build:search` у репозиторії лендінгу, інакше палітра пошуку й далі видаватиме старий запис.

## Примусове виконання

Hook `Stop` `.claude/hooks/index-sync-reminder.sh` повідомляє наприкінці ходу, якщо `guide/` змінився, а жоден індексний файл — ні. Він попереджає, але ніколи не блокує: хід може цілком законно завершитися посеред редагування, а hook, який це забороняє, зрештою вимикають.
