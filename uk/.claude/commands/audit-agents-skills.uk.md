# Аудит якості агентів/skills/команд

Комплексний аудит якості агентів, skills і команд Claude Code. Оцінює кожен файл за зваженими критеріями з виставленням оцінки готовності до продакшену.

## Аргументи

- `[path]` - Директорія для аудиту (за замовчуванням: `.claude/` поточного проєкту)
- `--fix` - Згенерувати пропозиції виправлень для критеріїв, що не пройшли
- `--verbose` - Показати подробиці за всіма критеріями (не лише за тими, що не пройшли)

## Використання

```bash
/audit-agents-skills              # Audit current project
/audit-agents-skills --fix        # Audit + fix suggestions
/audit-agents-skills ~/other-repo # Audit another project
/audit-agents-skills --verbose    # Full details for all criteria
```

## Фаза 1: Виявлення

**Мета**: знайти й класифікувати всіх агентів, skills і команди

### Кроки

1. **Просканувати директорії**:
   ```
   .claude/agents/
   .claude/skills/
   .claude/commands/
   examples/agents/      (if exists)
   examples/skills/      (if exists)
   examples/commands/    (if exists)
   ```

2. **Класифікувати файли**:
   - **Агент**: файл у директорії `agents/` з YAML frontmatter, що містить поле `tools:`
   - **Skill**: файл у директорії `skills/` АБО з іменем `SKILL.md`, АБО з frontmatter, що містить поле `allowed-tools:`
   - **Команда**: файл у директорії `commands/` з frontmatter, що містить `name:` і `description:`

3. **Показати підсумок**:
   ```
   Found: X agents, Y skills, Z commands
   ```

## Фаза 2: Аудит окремих файлів

Кожен тип файлу оцінюється за **зваженими критеріями**. Максимальні бали:
- **Агенти**: 32 бали
- **Skills**: 32 бали
- **Команди**: 20 балів

### Агенти (макс. 32 бали)

#### Ідентичність (вага: 3x) - 12 балів

| Критерій | Бали | Виявлення |
|-----------|--------|-----------|
| Зрозуміле поле `name` | 3 | У frontmatter YAML є поле `name:`, яке є описовим (не загальне на кшталт "agent1") |
| `description` із тригерами | 3 | Опис містить ключові слова "when", "use" або "trigger", що вказують на контекст активації |
| Указано `model` | 3 | У frontmatter є поле `model:` (sonnet/haiku/opus) |
| `tools` належним чином обмежено | 3 | Список інструментів не містить Bash без обґрунтування або містить пояснення для ризикових інструментів |

**Обґрунтування**: Ідентичність визначає **знаходимість** і **активацію**. Якщо користувачі не можуть знайти чи викликати агента, подальша якість не має значення.

#### Якість промпту (вага: 2x) - 8 балів

| Критерій | Бали | Виявлення |
|-----------|--------|-----------|
| Визначено роль | 2 | Містить твердження "You are" або "Your role", що визначає персону агента |
| Указано формат виводу | 2 | Має розділ "Output", "Format" або "Deliverables", що визначає очікувану структуру |
| Визначено обсяг/межі | 2 | Має розділ, що визначає обсяг, тригери або коли НЕ використовувати агента |
| Заходи проти галюцинацій | 2 | Містить ключові слова: "verify", "cite", "source", "evidence" або застереження проти галюцинацій |

**Обґрунтування**: Якість промпту визначає **надійність** і **точність** відповідей агента.

#### Валідація (вага: 1x) - 4 бали

| Критерій | Бали | Виявлення |
|-----------|--------|-----------|
| 3+ приклади використання | 1 | Має розділ "Examples", "Usage" або "Scenarios" щонайменше з 3 різними прикладами |
| Задокументовано крайні випадки | 1 | Згадує сценарії "edge case", "error", "failure" або "limitation" |
| Задокументовано інтеграцію | 1 | Посилається на інших агентів, skills чи інструменти, з якими працює |
| Описано обробку помилок | 1 | Згадує "fallback", "recovery", "error handling" або режими відмов |

**Обґрунтування**: Валідація забезпечує **стійкість** завдяки всебічним тестовим сценаріям.

#### Дизайн (вага: 2x) - 8 балів

| Критерій | Бали | Виявлення |
|-----------|--------|-----------|
| Єдина відповідальність | 2 | Розмір файлу <5000 токенів І опис сфокусований (не "general purpose" і не кілька дієслів) |
| Без дублювання | 2 | Опис суттєво не перетинається з іншими агентами (перевірка подібності ключових слів >50%) |
| Компонованість (посилання на skills) | 2 | Посилається на skills чи інших агентів, яких може викликати, демонструючи модульність |
| Розумний бюджет токенів | 2 | Розмір файлу <8000 токенів (уникає роздування контексту) |

**Обґрунтування**: Патерни дизайну визначають **підтримуваність** і **масштабованість** архітектури агентів.

### Skills (макс. 32 бали)

#### Структура (вага: 3x) - 12 балів

| Критерій | Бали | Виявлення |
|-----------|--------|-----------|
| Валідний SKILL.md або frontmatter | 3 | Файл із назвою `SKILL.md` АБО має YAML frontmatter з полем `name:` |
| Валідне `name` | 3 | Назва в нижньому регістрі, 1-64 символи, відповідає шаблону `[a-z0-9-]+` (без пробілів/спецсимволів) |
| Непорожнє `description` | 3 | Поле опису існує й має >20 символів |
| Указано `allowed-tools` | 3 | У frontmatter є поле `allowed-tools:` зі списком дозволів на інструменти |

**Обґрунтування**: Відповідність структурі забезпечує **сумісність зі специфікацією** середовища виконання Claude Code.

#### Вміст (вага: 2x) - 8 балів

| Критерій | Бали | Виявлення |
|-----------|--------|-----------|

| Указано формат виводу | 2 | Має розділ, що визначає формат результату (Markdown, JSON, структура звіту) |
| Наведено приклади | 2 | Має розділ "Examples", "Usage" або "Scenarios" з конкретними випадками |
| Включено чек-листи | 2 | Містить синтаксис чекбоксів Markdown `- [ ]` або `- [x]` для дієвих пунктів |

**Обґрунтування**: Багатство вмісту визначає **зручність використання** та **криву навчання**.

#### Технічні аспекти (вага: 1x) - 4 бали

| Критерій | Бали | Виявлення |
|-----------|--------|-----------|
| Скрипти мають обробку помилок | 1 | Якщо є вбудовані скрипти, містять шаблони `set -e`, `trap` або `|| exit` |

| Без секретів | 1 | Жодних ключових слів: "password", "secret", "token", "api_key", "credentials" у відкритому вигляді |
| Задокументовано залежності | 1 | Якщо потрібні зовнішні інструменти, є розділ "Requirements", "Dependencies" або "Prerequisites" |

**Обґрунтування**: Технічна гігієна запобігає **проблемам переносимості** та **ризикам безпеки**.

#### Дизайн (вага: 2x) - 8 балів

| Критерій | Бали | Виявлення |
|-----------|--------|-----------|

**Обґрунтування**: Дизайн визначає **знаходимість** і **підтримуваність** між проєктами.

## Фаза 3: Оцінювання

### Оцінка окремого файлу

```
Score = (Points Obtained / Max Points) × 100
```

**Приклад**: агент набирає 26/32 бали → оцінка 81%

### Присвоєння оцінки

| Оцінка | Діапазон | Статус |
|-------|-------------|--------|
| A | 90-100% | Готово до продакшену ✅ |
| B | 80-89% | Добре (поріг продакшену) ⚠️ |
| C | 70-79% | Потребує покращення 🔧 |
| D | 60-69% | Значні прогалини ⚠️ |
| F | <60% | Критичні проблеми ❌ |

**Поріг продакшену**: 80% (оцінка B або вище)

### Загальна оцінка проєкту

Зважене середнє за типами файлів:
```
Overall = (Σ Agent Scores × Agent Count + Σ Skill Scores × Skill Count + Σ Command Scores × Command Count) / Total Files
```

## Галузевий контекст

**Джерело**: LangChain Agent Report 2026 (перевірено)

**Ключова статистика**:
- 29.5% організацій розгортають агентів без систематичного оцінювання
- 18% називають "баги агентів" головною проблемою

**Порівняння**: ручні чек-листи (як-от Agent Validation Checklist посібника на рядку 4921) всебічні, але схильні до помилок. Автоматизоване оцінювання зменшує людські помилки та дає кількісні метрики для відстеження покращень у часі.

### Виявлення перетину

Порівняй описи за подібністю Жаккара:
```python
def jaccard_similarity(desc1, desc2):
    words1 = set(desc1.lower().split())
    words2 = set(desc2.lower().split())
    intersection = words1 & words2
    union = words1 | words2
    return len(intersection) / len(union) if union else 0

# Flag if similarity > 0.5 (50% keyword overlap)
```
