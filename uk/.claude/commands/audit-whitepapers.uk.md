# Аудит Whitepapers і карток-резюме

Комплексний аудит актуальності та якості всіх whitepapers (FR + EN) і карток-резюме (FR + EN). Оцінює кожен документ відносно поточної версії посібника, перевіряє паритет FR/EN і валідує узгодженість метаданих.

## Аргументи

- `--fix` - Згенерувати пропозиції оновлень і патчі frontmatter (файли не змінює)
- `--verbose` - Показати всі критерії, включно з пройденими, а не лише збої
- `--cards-only` - Аудит лише карток-резюме (пропустити основні whitepapers)
- `--wp-only` - Аудит лише основних whitepapers (пропустити картки-резюме)

## Використання

```bash
/audit-whitepapers                  # Full audit, failures only
/audit-whitepapers --fix            # Audit + prioritized update suggestions
/audit-whitepapers --verbose        # Full details for all criteria
/audit-whitepapers --cards-only     # Recap cards only
/audit-whitepapers --wp-only        # Whitepapers only
```

## Фаза 1: Виявлення

**Мета**: знайти й інвентаризувати всі документи, придатні до аудиту.

### Кроки

1. **Прочитати поточну версію посібника**: прочитай файл `VERSION` у корені проєкту. Це цільова версія, з якою мають бути синхронізовані всі документи.

2. **Просканувати директорії** на файли `.qmd`:
   ```
   whitepapers/fr/         (main whitepapers FR)
   whitepapers/en/         (main whitepapers EN)
   whitepapers/recap-cards/fr/    (recap cards FR)
   whitepapers/recap-cards/en/    (recap cards EN)
   ```

3. **Класифікувати кожен файл**:
   - **Основний whitepaper**: файли, що відповідають `[0-9][0-9]-*.qmd` у `whitepapers/fr/` або `whitepapers/en/`
   - **Шпаргалка**: файли, що відповідають `*cheatsheet*.qmd` (відстежуються окремо, не оцінюються)
   - **Кастомний whitepaper**: файли, що відповідають `*-whitepaper.qmd` або `*-cheatsheet.qmd` від зовнішніх партнерів (strangebee, purchasely, devwithai) -- виключаються з оцінювання, перелічуються окремо
   - **Картка-резюме**: усі файли `.qmd` у `recap-cards/fr/` або `recap-cards/en/`
   - **Збірка/include**: `fiches-recap-serie.qmd`, файли в підкаталозі `fiches/` -- виключаються (це складені документи)

4. **Розібрати YAML frontmatter** кожного включеного файлу (читай між першим `---` і другим `---`). Витягни:
   - `title`, `subtitle`, `author`, `date`
   - `version` (версія посібника, що відстежується в основних WP і картках-резюме)
   - `wp-version` (власний semver whitepaper, лише основні WP)
   - `guide-version` (явне поле версії посібника, що використовується в картках-резюме)
   - `card-number`, `category`, `difficulty` (лише картки-резюме)
   - `series` (лише основні WP)

5. **Показати підсумок виявлення**:
   ```
   Guide version: {VERSION}
   Found: {N} main whitepapers ({FR}/{EN} FR/EN), {N} recap cards ({FR}/{EN} FR/EN)
   Excluded: {N} custom files (strangebee, purchasely, devwithai), {N} bundle files
   ```

## Фаза 2: Аналіз розриву версій (40 балів на файл)

**Мета**: оцінити, наскільки актуальний кожен документ відносно посібника.

### Логіка порівняння semver

Розбери рядки версій як `MAJOR.MINOR.PATCH`. Метрика застарілості — `minor_gap = current_minor - file_minor` (за того самого MAJOR). Якщо MAJOR відрізняється, вважай це критичним.

Для **основних whitepapers** поле версії посібника — `version`.
Для **карток-резюме** поле версії посібника — `guide-version` (якщо його немає, використовуй `version`).

### Таблиця оцінювання

| Критерій | Бали | Виявлення |
|-----------|--------|-----------|
| Версія посібника актуальна (відстає на 0-1 minor) | 15 | `minor_gap` <= 1 |
| Версія посібника недавня (відстає на 2-3 minor) | 10 | `minor_gap` 2-3 (часткові бали, замінює 15) |
| Версія посібника стара (відстає на 4-10 minor) | 5 | `minor_gap` 4-10 (часткові бали) |
| Поле wp-version присутнє й є валідним semver | 5 | Поле існує І відповідає `\d+\.\d+\.\d+` (лише WP) |
| wp-version узгоджене з парою FR/EN | 10 | Те саме значення `wp-version` у парному файлі (лише WP) |
| guide-version узгоджене з парою FR/EN | 10 | Те саме `guide-version` (або `version`) у парному файлі (картки) |

**Мітки актуальності**:
- Відстає на 0-1 minor: Fresh (свіжий)
- Відстає на 2-3 minor: Stale (застарілий)
- Відстає на 4-10 minor: Very Stale (дуже застарілий)
- Відстає на 11+ minor: Critical (критичний)

Примітка: 15, 10, 5 балів за версію посібника взаємовиключні (нараховуй лише найвищий застосовний рівень).

### Кроки

1. Для кожного основного whitepaper витягни поле `date`. Якщо дата не у форматі `YYYY-MM-DD`, розбери її (напр., "2026-02-12" або "March 2026").
2. Виконай `git log --since="{date}" --oneline -- guide/ultimate-guide.md guide/roles/ guide/core/`, щоб порахувати коміти, що зачепили вміст посібника від дати whitepaper.
3. Оціни:

| Критерій | Бали | Виявлення |
|-----------|--------|-----------|
| Немає комітів посібника від дати wp | 10 | `git log` повертає 0 комітів |
| Мало комітів від дати wp (1-5) | 7 | 1-5 комітів (частково) |
| Помірно комітів (6-15) | 4 | 6-15 комітів (частково) |
| Багато комітів (>15) | 0 | Понад 15 комітів |
| Для цього WP визначено відповідність | 5 | Номер WP є у вищенаведеній таблиці відповідності |
| Git-історія доступна | 5 | Команда `git log` виконується без помилки |

**Картки-резюме**: пропусти детальний git-аналіз. Нарахуй фіксований бал застарілості за `minor_gap`:
- Відстає на 0-1: 20 балів
- Відстає на 2-3: 15 балів
- Відстає на 4-10: 8 балів
- Відстає на 11+: 0 балів

## Фаза 4: Перевірка паритету FR/EN (20 балів на файл)

**Мета**: кожен документ має мати повну, узгоджену за версією пару іншою мовою.

### Стратегія зіставлення пар

**Основні whitepapers**: зіставляй за двоцифровим числовим префіксом (напр., `00`, `03`, `10`). Імена файлів FR та EN відрізняються, але префікс однаковий.

**Картки-резюме**: зіставляй за ідентичним іменем файлу (обидві мовні директорії використовують однакові імена файлів).

### Таблиця оцінювання

| Критерій | Бали | Виявлення |
|-----------|--------|-----------|
| Парний файл іншою мовою існує | 10 | Знайдено файл зі збіжним префіксом (WP) або ідентичним іменем (картки) |
| wp-version збігається в парі | 5 | Те саме значення `wp-version` (лише WP) |
| Версія посібника збігається в парі | 5 | Те саме значення `version`/`guide-version` |

Оцінюй обидва файли FR і EN пари однаково за паритетом (якщо пара повна, обоє отримують 20; якщо одного немає, наявний файл отримує 0 за паритет).

## Фаза 5: Якість метаданих (20 балів на файл)

**Мета**: перевірити повноту frontmatter, формати полів і узгодженість між файлами одного типу.

### Основні whitepapers (макс. 20 балів)

| Критерій | Бали | Виявлення |
|-----------|--------|-----------|
| Обов'язкові поля присутні | 6 | Є всі: `title`, `subtitle`, `author`, `date`, `version`, `wp-version`, `series` |
| `version` відповідає шаблону semver | 3 | Відповідає `\d+\.\d+\.\d+` |
| `wp-version` відповідає шаблону semver | 3 | Відповідає `\d+\.\d+\.\d+` |
| `date` розбирається й не в майбутньому | 3 | Валідна дата, не пізніше за сьогодні |
| Значення `series` узгоджене | 2 | Дорівнює "Claude Code Ultimate Guide" |
| `wp-version` не відсутнє (не порожнє й не пропущене) | 3 | Поле має непорожнє значення |

### Картки-резюме (макс. 20 балів)

| Критерій | Бали | Виявлення |
|-----------|--------|-----------|
| Обов'язкові поля присутні | 5 | Є всі: `title`, `subtitle`, `card-number`, `category`, `difficulty`, `guide-version`, `author`, `version`, `date` |
| `card-number` збігається з префіксом імені файлу | 4 | напр., `C01` у `card-number` відповідає `c01-` в імені файлу |
| `category` валідна для мови | 4 | FR: одне з "Technique", "Methodologie", "Conception"; EN: одне з "Technical", "Methodology", "Design" (познач "Conceptual" як неузгоджене в EN) |
| `difficulty` має валідне значення | 3 | Одне з: "beginner", "intermediate", "advanced" |
| Поля `guide-version` і `version` збігаються | 4 | Обидва поля існують і мають однакове значення в одному файлі |

**Відома проблема для автоматичного виявлення**: картки EN C-серії використовують два різні значення категорії ("Conceptual" у c01-c05, "Design" у c06+). Явно познач цю неузгодженість у розділі Metadata Issues звіту.

## Фаза 6: Оцінювання та виставлення оцінок

### Формула оцінки (на файл)

```
Total = Version Gap (40) + Content Staleness (20) + FR/EN Parity (20) + Metadata Quality (20)
Score = (Total / 100) * 100  [as a percentage]
```

### Шкала оцінок

| Оцінка | Бали | Статус |
|-------|-------|--------|
| A | 90-100 | Свіжий, повністю синхронізований |
| B | 80-89 | Добре (поріг продакшену) |
| C | 70-79 | Незабаром потребує оновлення |
| D | 60-69 | Застарілий, варто пріоритезувати |
| F | <60 | Критично: імовірно застарілий вміст |

### Загальна оцінка здоров'я

```
Weighted Health = (Sum of WP scores * 2 + Sum of card scores * 1) / (WP count * 2 + card count * 1)
```

Whitepapers мають вагу 2x, бо мають 20-80 сторінок кожен проти 2-сторінкових карток-резюме. Застарілий whitepaper несе більший ризик.

## Режим виправлень (`--fix`)

Коли передано `--fix`, додай розділ **Fix Suggestions** після звіту. Цей розділ містить конкретні патчі, але НЕ змінює жодних файлів.

### Патчі версії frontmatter

Для кожного файлу із застарілою версією посібника виведи:
```yaml
# File: whitepapers/fr/00-introduction-serie.qmd
# Change:
version: "3.27.6"  ->  version: "{current_VERSION}"
date: 2026-02-12   ->  date: {today}
```

### Патчі категорій (картки-резюме EN)

```
Files to update (category: "Conceptual" -> "Design"):
- whitepapers/recap-cards/en/c01-trust-calibration.qmd
- whitepapers/recap-cards/en/c02-*.qmd
- whitepapers/recap-cards/en/c03-*.qmd
- whitepapers/recap-cards/en/c04-*.qmd
- whitepapers/recap-cards/en/c05-*.qmd
```

### Чек-лист команд оновлення

На основі виявлених застарілих WP виведи команди `/update-whitepapers`, які слід виконати по порядку:
```
Suggested update sequence:
1. /update-whitepapers --since {oldest_stale_version} --wp 00,01,02,03,04,05,06,07,08,09
2. /update-whitepapers --since {oldest_stale_version} --wp 10
3. Review and bump wp-version for each updated WP (patch = content corrections, minor = new sections)
4. Bump guide-version in all recap cards to {current_VERSION}
5. Re-run /audit-whitepapers to verify
```
