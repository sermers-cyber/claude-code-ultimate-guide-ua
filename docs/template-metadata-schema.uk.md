# Схема метаданих шаблонів

Повна специфікація метаданих для всіх шаблонів у `examples/`.

---

## Призначення

Метадані шаблонів дають змогу:
- **Знаходити**: шукати шаблони за складністю, часом, доменом
- **Автоматизувати**: генерувати каталоги, індекси та документацію
- **Контролювати якість**: перевіряти узгодженість у понад 181 шаблоні
- **Навчати**: допомагати користувачам знаходити шаблони, що відповідають їхньому рівню

---

## Формат YAML frontmatter

Усі шаблони (`agents/`, `commands/`, `skills/`, `hooks/`, `workflows/`, `scripts/`) мають містити метадані у YAML frontmatter:

```yaml
---
name: template-name
description: One-line description of what this template does
complexity: beginner|intermediate|advanced
time: 5 min|15 min|30 min|1 hour|2 hours|4+ hours|varies
domain: security|testing|deployment|performance|architecture|automation|general
prerequisites: []
status: stable|experimental|deprecated
keywords: [tag1, tag2, tag3]
---
```

### Правила формату файлів

**Markdown** (`.md`):
```markdown
---
name: code-reviewer
description: Code review agent with security and quality checks
...
---

# Code Reviewer Agent

Content starts here...
```

**Bash/PowerShell** (`.sh`, `.ps1`):
```bash
#!/bin/bash
# ---
# name: pre-commit-validator
# description: Validates code before commit
# ...
# ---

# Script content starts here
```

## Специфікація полів

### `name` (обов'язкове)

Унікальний ідентифікатор шаблону. Має бути безпечним для URL і записаним у kebab-case.

**Правила:**
- Лише малі літери, цифри, дефіси
- Без пробілів і спеціальних символів
- Має збігатися з назвою файлу (без розширення)
- Приклади: `code-reviewer`, `unit-test-generator`, `security-auditor`

**Використання:**
- Стає текстом посилання в каталозі
- Використовується в командах `/agent code-reviewer`
- На нього посилаються в документації

---

### `description` (обов'язкове)

Однорядковий опис того, що робить шаблон.

**Правила:**
- Не більше 100 символів
- Конкретно, а не розпливчасто
- За можливості починати з дієслова
- Зосереджуватися на результаті, а не на деталях реалізації

**Приклади:**
```yaml
# ✅ Добре
description: Automated code review for security and performance issues

# ❌ Погано
description: A tool for reviewing code
description: Code analyzer that checks things
```

---

### `complexity` (обов'язкове)

Рівень навичок, потрібний для ефективного використання шаблону.

**Допустимі значення:**
- `beginner`: попередні знання не потрібні
- `intermediate`: потрібен базовий досвід роботи з Claude Code
- `advanced`: глибокі знання Claude Code або спеціалізована предметна експертиза

**Рекомендації:**
- **Beginner**: прості агенти/skills, що не потребують налаштування
  - Приклади: прості агенти для тестування, базові генератори документації
- **Intermediate**: шаблони, що потребують певного налаштування або предметних знань
  - Приклади: агенти для code review, шаблони команд CI/CD, поширені воркфлоу
- **Advanced**: складна оркестрація, спеціалізовані домени або системи з багатьох компонентів
  - Приклади: мультиагентні системи, аудит безпеки, оптимізація продуктивності, кіберзахист

**Використання:**
- Допомагає користувачам фільтрувати в навчальному шляху та `/self-assessment`
- Визначає рівень складності документації
- Підказує рекомендовані передумови

---

### `time` (обов'язкове)

Орієнтовний час, потрібний, щоб зрозуміти шаблон і адаптувати його до вашого проєкту.

**Допустимі значення:**
- `5 min`: швидкий довідник, мінімальне налаштування
- `15 min`: простий шаблон, невелика адаптація
- `30 min`: стандартний шаблон, потрібне певне налаштування
- `1 hour`: помірна складність або значне навчання
- `2 hours`: складний шаблон або крута крива навчання
- `4+ hours`: дуже складні системи або кілька компонентів
- `varies`: сильно залежить від контексту (наприклад, предметно-специфічні шаблони)

**Що входить у «час»:**
- Читання/розуміння шаблону
- Адаптація до вашого проєкту
- Тестування шаблону
- Перевірка, що він працює

**Що НЕ входить у «час»:**
- Вивчення основ Claude Code (охоплено модулями 01-02)
- Предметні знання (наприклад, вивчення Kubernetes перед використанням шаблону DevOps)

**Приклади:**
- агент `code-reviewer`: `30 min` (розібратися з чеклістом, адаптувати правила)
- команда `test-writer`: `15 min` (вибрати фреймворк для тестів, невелике налаштування)
- Мультиагентний кіберзахист: `4+ hours` (кілька агентів, схема подій, пайплайн)

---

### `domain` (необов'язкове)

Категорія/домен, до якого належить шаблон.

**Поширені домени:**
- `security`: сканування вразливостей, виявлення загроз, аудити безпеки
- `testing`: генерація тестів, валідація тестів, аналіз покриття
- `deployment`: CI/CD, автоматизація релізів, інфраструктура
- `performance`: оптимізація, профілювання, виявлення вузьких місць
- `architecture`: рев'ю дизайну, рефакторинг, аналіз патернів
- `automation`: оркестрація воркфлоу, автоматизація повторюваних завдань
- `general`: без конкретного домену, широко застосовний

**Правила:**
- Використовуйте один домен (бажано основний)
- Якщо шаблон охоплює кілька доменів, оберіть той, що підходить найбільше
- У разі сумніву використовуйте `general`

**Використання:**
- Дає змогу фільтрувати каталоги за доменами
- Допомагає користувачам знаходити інструменти за експертизою
- Організовує розділи документації

---

### `prerequisites` (необов'язкове)

Які знання або налаштування потрібні перед використанням шаблону.

**Формат:**
```yaml
prerequisites: [skill-name, agent-name, module-number]
```

**Приклади:**
```yaml
# Security auditor потребує розуміння Module 02 (контекст)
prerequisites: [Module-02-Core-Loop]

# Цей агент побудований поверх code-reviewer
prerequisites: [code-reviewer agent]

# Потребує знайомства з концепціями тестування
prerequisites: [testing-patterns skill]
```

**Правила:**
- Перелічуйте конкретні модулі, skills або інших агентів
- Тримайте список коротким (максимум 3 передумови)
- Якщо їх більше 3, подумайте, чи не надто складний шаблон
- Мають відповідати реальним елементам навчального шляху

**Використання:**
- Автоматично згенеровані ланцюжки передумов у каталозі
- Валідація в `/self-assessment` (пропонує передумови)
- Документація може показувати передумови

---

### `status` (необов'язкове)

Статус життєвого циклу шаблону.

**Допустимі значення:**
- `stable` (за замовчуванням): протестований, задокументований, готовий до продакшену
- `experimental`: новий, ще не повністю протестований, може змінитися
- `deprecated`: більше не рекомендований, розгляньте альтернативи

**Правила:**
- Пропустіть, якщо `stable` (значення за замовчуванням)
- Для `experimental` або `deprecated` чітко позначайте в каталозі значком попередження
- Експериментальні шаблони мають містити нотатки про шлях міграції

**Приклади:**
```yaml
# Експериментальна нова функція
status: experimental
# Consider alternatives: code-reviewer agent

# Застарілий, замінений новішою версією
status: deprecated
# Use instead: security-auditor-v2 agent
```

---

### `keywords` (необов'язкове)

Пошукові теги для зручності знаходження.

**Формат:**
```yaml
keywords: [keyword1, keyword2, keyword3, ...]
```

**Приклади:**
```yaml
# Ключові слова code reviewer
keywords: [review, quality, security, performance, linting]

# Ключові слова генератора тестів
keywords: [testing, jest, unit-test, tdd, bdd, coverage]
```

**Правила:**
- Використовуйте максимум 3-5 ключових слів
- Робіть їх короткими (1-2 слова)
- Включайте поширені пошукові терміни (фреймворки, патерни, практики)
- Включайте предметну лексику домену

**Використання:**
- Дає змогу виконувати повнотекстовий пошук у розширеному каталозі
- Покращує знаходження через теги
- Підтримує відображення синонімів (наприклад, «reviews» → «code-reviewer»)

## Правила валідації

Інструмент `scripts/generate-template-catalog.py --validate` перевіряє:

1. **Обов'язкові поля** існують: `name`, `description`, `complexity`, `time`
2. **Допустимі значення** для переліків: `complexity`, `time`, `status`
3. **Правила формату**: `name` у kebab-case, `description` до 100 символів
4. **Узгодженість файлу**: назва файлу збігається з полем `name`
5. **Коректність посилань**: передумови, домени, ключові слова правильно сформовані

## Автоматична генерація

Каталог автоматично генерується з метаданих:

```bash
# Generate CATALOG.md from all template metadata
python3 scripts/generate-template-catalog.py

# Validate all templates have correct metadata
python3 scripts/generate-template-catalog.py --validate

# Generate and save to specific file
python3 scripts/generate-template-catalog.py --output examples/CATALOG.md
```

Точки інтеграції:
- **Pre-commit hook**: перевіряє метадані перед комітом
- **Release workflow**: автоматично генерує каталог під час `/release`
- **CI/CD**: перевіряє метадані при кожному push

## Посібник із міграції

### Наявні шаблони

Якщо оновлюєте наявний шаблон:

1. Додайте frontmatter на початок файлу
2. Запустіть валідацію: `python3 scripts/generate-template-catalog.py --validate`
3. Закоміть із повідомленням: `docs: add metadata to [template-name]`

### Пакетні оновлення

Оновіть кілька шаблонів одночасно:

```bash
# Find all templates without metadata
find examples -name "*.md" -exec grep -L "^---" {} \;

# Add minimal metadata to all
find examples -name "*.md" | xargs -I {} \
  python3 scripts/add-default-metadata.py {}
```

## FAQ

**П: Чи має кожен шаблон містити всі поля?**  
В: Ні. Обов'язкові: `name`, `description`, `complexity`, `time`. Необов'язкові поля можна пропустити, якщо вони не застосовні.

**П: Чи можна додавати власні поля?**  
В: Так, але інструмент каталогу їх не індексуватиме. Корисно для внутрішнього обліку (наприклад, `author`, `date_added`).

**П: Як часто слід оновлювати метадані?**  
В: Оновлюйте, коли: шаблон суттєво змінено, змінився статус, змінилися передумови або змістився домен.

**П: Що робити, якщо шаблон охоплює кілька доменів?**  
В: Оберіть основний/найсильніший домен. Якщо шаблон справді мультидоменний, подумайте про поділ на окремі шаблони або використайте `general`.
