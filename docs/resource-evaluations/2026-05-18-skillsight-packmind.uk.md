## Зміст ресурсу

Skillsight це дашборд для самостійного розгортання, що приймає телеметрію OTEL з Claude Code і візуалізує, які skills насправді викликаються в команді чи організації. Два шляхи отримання даних: push через OTLP HTTP/JSON (Claude Code → Skillsight напряму) або pull через Loki (ретранслятор Grafana Cloud). Використання skills видно за користувачем, сесією, плагіном, із сегментацією за когортами.

**Що він реально постачає (перевірено за кодом):**
- Дашборд із графіками використання skills, розбивкою за командами, відстеженням плагінів
- Синхронізація marketplace: підтягує каталоги skills із Git-джерел (GitHub PAT або на основі токена)
- Автентифікація: JWT HS256 (jose) + хешування паролів argon2, cookie сесій і окремі токени для прийому даних
- Сторінка подій SSE в реальному часі (`/live-events`)
- Журнал аудиту всіх адміністративних дій
- Сегментація за когортами (є в Roadmap, але вже реалізована)
- Сторінка онбордингу, що автоматично генерує фрагмент settings.json для Claude Code

**Стек:** монорепозиторій Bun, бекенд Hono, Drizzle ORM + PostgreSQL, React 18 + Vite 7 + Tailwind 4 + Recharts. Гексагональна архітектура. 28K LOC, 33 тестові файли, лінтер Biome, CI на GitHub Actions (lint+test+build+docker), багатоетапний Dockerfile, Apache 2.0.

**Автор:** Cédric Teyton, Packmind (див. також [#076](076-packmind-contextops-platform.uk.md)).

Оцінка відображає поточний стан; підвищити до 4/5, коли три критичні проблеми безпеки буде розв'язано.

## Рекомендація щодо інтеграції

**Ціль:** `guide/ecosystem/third-party-tools.md`: новий підрозділ «Skills Observability»

**Коли інтегрувати:** Зараз, з прямими застереженнями. Підвищити до повної рекомендації (4/5), коли три критичні проблеми буде виправлено (див. Умови нижче).

**Подання в посібнику:**
- Позиціонувати як єдиний інструмент із відкритим кодом для відстеження того, які skills Claude Code ваша команда насправді використовує, а які, на вашу думку, використовує.
- Обов'язкові застереження:
  1. Ніколи не розгортати без перевизначення `JWT_SECRET` і `ADMIN_PASSWORD_INITIAL`: значення за замовчуванням публічні, а попередження під час запуску немає.
  2. Запускати міграції Drizzle вручну при оновленнях, доки не додано автоматичний entrypoint.
  3. Задати `PUBLIC_BASE_URL` у `.env`, навіть без балансувальника навантаження: це впливає і на політику CORS, і на коректність фрагмента онбордингу.
- Згадати пов'язану платформу Packmind ContextOps (оцінка #076) щодо додаткового ракурсу розповсюдження стандартів.

**Умови підвищення до 4/5:**
1. Збій запуску або явне попередження, якщо `JWT_SECRET` збігається з постачуваним значенням за замовчуванням
2. Окремий `ENCRYPTION_KEY` для шифрування облікових даних у стані спокою (відокремлений від ротації JWT)
3. Автоматичне виконання міграцій Drizzle під час запуску контейнера

## Висновки щодо безпеки (підсумок аудиту)

Про чотири висновки варто попередити будь-якого оператора перед самостійним розгортанням:

**Ризик значень розгортання за замовчуванням.** `JWT_SECRET=change-me-in-production-please-at-least-32-chars` і `ADMIN_PASSWORD_INITIAL=admin` є дослівними значеннями за замовчуванням у `docker-compose.yml`. Попередження під час запуску немає. Валідація Zod приймає значення JWT за замовчуванням, бо воно відповідає мінімальній кількості символів. `docker compose up` без `.env` за лічені секунди створює екземпляр із повним доступом. README попереджає, але нічого не забезпечує цього під час виконання.

**Спільний ключ шифрування.** `JWT_SECRET` також є ключем шифрування для зберігання облікових даних Loki і GitHub у стані спокою (`encrypt.ts`: `getKey() = SHA-256(JWT_SECRET)`). Ротація секрету JWT (підтримується через `JWT_SECRET_PREVIOUS`) непомітно робить усі збережені облікові дані нерозшифровуваними. Витік секрету JWT також розкриває зовнішні облікові дані. Відсутність AAD для кожного рядка означає, що збережені блоби взаємозамінні між інтеграціями.

**Надто вільний CORS.** `PUBLIC_BASE_URL` за замовчуванням відображає origin запиту з `credentials: true` (`app.ts:55-65`). Цієї змінної немає в `.env.example`. Адміністратор, підключений до екземпляра Skillsight, який відвідає сторінку під контролем зловмисника, може стати об'єктом міждоменного запиту до адміністративного API.

**Немає обмеження частоти запитів.** Ні `/api/auth/login`, ні ендпоінт прийому OTLP `/api/v0/telemetry/v1/logs` не мають rate limiting. Розмір тіла запиту на ендпоінті прийому не обмежено.

## Основні моменти архітектури

Гексагональна архітектура справжня, а не карго-культ: порти це інтерфейси, use cases залежать від абстракцій, покриття тестами використовує in-memory фейки зі змістовними поведінковими перевірками. Схема PostgreSQL має належні обмеження (FK, NOT NULL, функціональні індекси, зокрема часткові індекси JSONB).

Варто відзначити три структурні проблеми:

- Конвеєр прийому не обгортає свої 6 послідовних кроків upsert у транзакцію БД: частковий збій непомітно створює неузгоджений стан.
- Планувальники Loki та marketplace ковтають помилки через `.catch(() => {})`: збійна інтеграція не залишає слідів ні в логах, ні в UI.
- Конфігурація джерела marketplace фіксується під час створення розкладу (застаріває після будь-якого редагування в UI до перезапуску).

## Висновки щодо документації та DX

Дві проблеми напряму блокують першу настройку:

1. **Невідповідність назви образу**: README використовує `ghcr.io/packmindhub/skills-obs:latest` у 7 місцях. Фактичний образ у `docker-compose.yml` це `ghcr.io/packmindhub/skillsight:latest`. Користувачі, що слідують Quick Start, одразу з цим зіткнуться.

2. **Неузгодженість змінної ендпоінта OTLP**: README документує `OTEL_EXPORTER_OTLP_ENDPOINT` (загальна). UI онбордингу генерує `OTEL_EXPORTER_OTLP_LOGS_ENDPOINT` (специфічна для логів, вищого пріоритету). Два джерела, різні результати конфігурації.

Досвід онбордингу в іншому добре продуманий: сторінка UI автоматично генерує повний фрагмент `settings.json` із наперед створеним токеном прийому. Час до робочого стану для підготовленого розробника: 30-75 хвилин залежно від того, чи трапляться наведені вище проблеми.
