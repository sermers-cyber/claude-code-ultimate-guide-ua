# Оцінка ресурсу: claude-swarm-monitor

**Дата**: 2026-03-17
**Оцінювач**: Claude (автоматично через /eval-resource)
**Статус**: Список спостереження: повторно оцінити за 50+ зірок або після звіту про перевірку на macOS

---

## 📄 Підсумок змісту

- **TUI-дашборд** (Rust + Ratatui) для моніторингу кількох агентів Claude Code, що паралельно працюють у git worktrees
- **Одна «доріжка» на агента**: спочатку головний репозиторій, потім кожен worktree, відсортовані й візуально розділені
- **Живий статус зі стрімінгу JSONL-файлів сесій** (`~/.claude/projects/`): Working / Waiting For You / Idle / Done / Error
- **Відстеження субагентів**: агенти, запущені через інструмент Task, з'являються як вкладені картки в доріжці батьківського агента (твердження не перевірене, див. розділ «Фактчекінг»)
- **Видимість Docker-стеку на кожен worktree**: зіставляє стеки Compose через `COMPOSE_PROJECT_NAME` у `docker/.env`, показує живе завантаження CPU у % і пам'ять

**Джерело**: [github.com/oinant/claude-swarm-monitor](https://github.com/oinant/claude-swarm-monitor)
**Мова**: Rust (≥ 1.80) | **Ліцензія**: MIT | **Зірки**: 10 (березень 2026) | **Платформа**: протестовано на Linux; Windows/Docker Desktop ще не підтримуються

| Оцінка | Значення |

**Обґрунтування**: claude-swarm-monitor закриває дві реальні прогалини, які не покриває жоден інструмент у посібнику: (1) моніторинг через нативні JSONL-файли сесій замість SSE/опитування та (2) видимість Docker-стеку на кожен worktree. Підхід на JSONL архітектурно відрізняється від agent-chat (що орієнтований на Gas Town/multiclaude). Однак за 10 зірок (6 тижнів існування) і підтримки лише Linux сигнал про впровадження надто слабкий для рекомендації з високою впевненістю. Оцінку обмежено на 3 до підтвердження спільнотою.

## 📍 Рекомендації

**Поточна дія**: додати до списку спостереження. У головний посібник поки не інтегрувати.

**Умови підвищення до 4/5 та інтеграції**:
1. Повторно оцінити за 50+ зірок або після достовірного звіту спільноти про використання в продакшені
2. Перевірити твердження про відстеження субагентів інструмента Task (як відстежуються внутрішні запуски, якщо вони не пишуть окремих JSONL-файлів?)
3. Додати примітку з безпеки щодо обсягу читання `~/.claude/projects/` (файли сесій містять повну історію розмов, зокрема випадково введені секрети)
4. Підтвердити або задокументувати сумісність із macOS як жорстке обмеження
5. Виміряти накладні витрати ресурсів при 10+ worktrees і живому опитуванні Docker

**Розміщення після інтеграції**: `guide/ecosystem/third-party-tools.md` у розділі Multi-Agent Orchestration, з явним рядком порівняння з agent-chat, що відзначає ключові відмінності (нативний JSONL проти SSE, видимість Docker, Rust проти JS, Linux проти кросплатформності).

## 🔥 Виклик (technical-writer agent)

Агент-опонент знизив початково запропоновану оцінку з 4 до 3, посилаючись на таке:

- **Сигнал про впровадження найслабший у розділі екосистеми**: 10 зірок проти multiclaude (383+) і Ruflo (18.9k); навіть Athena Flow (явно позначений «поки не рекомендовано») має більше зовнішньої валідації
- **Обмеження лише Linux є реальним** для цільової аудиторії (користувачі мультиагентних систем переважно на macOS)
- **Обсяг безпеки не розглянуто**: інструмент читає `~/.claude/projects/`, де зберігається повна історія сесій із чутливим контекстом; це узгоджується з практикою посібника позначати обсяг доступу до даних (див. записи Straude, Packmind)
- **Твердження про відстеження субагентів не перевірене**: запуски через Task внутрішні для процесу Claude Code, і незрозуміло, чи пишуть вони окремі JSONL-файли

- **Оцінку скориговано**: 3/5 (з запропонованих 4/5), погоджено
- **Пропущені моменти**: споживання ресурсів (накладні витрати опитування), наслідки для безпеки, відсутність підтримки macOS, перевірка відстеження субагентів
- **Ризик неінтеграції**: низький, адже agent-chat уже покриває моніторинг; підходи через JSONL/Docker переконливі, але обслуговують вузьку просунуту підгрупу
