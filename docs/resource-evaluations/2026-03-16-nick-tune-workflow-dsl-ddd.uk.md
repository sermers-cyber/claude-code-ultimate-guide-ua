## Підсумок змісту

- Представляє DSL на TypeScript для декларативного опису станів робочого процесу Claude Code: кожен стан задає емодзі-ідентифікатор, шлях до файлу інструкцій агента, дозволені переходи між станами, дозволені операції та функції-запобіжники для переходів.
- Архітектура з трьох модулів: `workflow-engine` (виконує правила, не залежить від предметної області), `workflow-dsl` (мова для опису кроків), `workflow-definition` (корінь агрегату з фактичною логікою процесу та інваріантами).
- Безпека типів через об'єднані типи TypeScript з `as const`: недопустимі переходи між станами дають помилку на етапі компіляції, а не під час виконання.
- Подача через Domain-Driven Design: робочий процес як явний корінь агрегату, патерн адаптера відокремлює його від інфраструктури Claude Code.
- Вбудована спостережуваність: кожна операція додається до внутрішнього журналу подій (тип операції, часова мітка, контекстні деталі). Це дає змогу відтворювати й аудитувати запуски процесу.
- «Принцип володіння станом»: кожен стан сам перевіряє свої передумови, а не покладається на захисні перевірки в рушії.
- Повторне впровадження інструкцій при кожному переході між станами ТА при збої команди; це окремий механізм від повторного впровадження після компакції контексту (компенсує втрату контексту агентом під час виконання, а не стиснення).
- Тестування методом чорної скриньки через публічні методи класу `Workflow`; внутрішній стан не тестується.
- Посилається на репозиторій GitHub `NTCoding/autonomous-claude-agent-team` з повною реалізацією.
- Продовження статті: https://nick-tune.me/blog/2026-02-28-hook-driven-dev-workflows-with-claude-code/ (уже оцінена окремо).

## Рекомендації щодо інтеграції

**Вибіркове вилучення: новий файл верхнього рівня не потрібен, доки немає впровадження спільнотою.**

Три точкові інтеграції в порядку пріоритету:

### 1. Патерн спостережуваності через журнал подій (пріоритет: високий)
**Де:** документація з hooks або `guide/workflows/event-driven-agents.md`
**Що:** патерн додавання кожної операції агента до внутрішнього журналу подій (тип + часова мітка + контекст) — техніка налагодження й аудиту, якої посібник ніде не описує. Винести це як самостійний патерн, незалежно від подачі через DDD.

### 2. Повторне впровадження інструкцій при збої (пріоритет: середній)
**Де:** `guide/workflows/event-driven-agents.md` або найкращі практики роботи з hooks
**Що:** повторне впровадження інструкцій агента при збої команди (а не лише при компакції контексту) протидіє дрейфу контексту під час виконання. Відрізняється від наявного патерну повторного впровадження після компакції; варто присвятити абзац, де ця різниця сформульована явно.

### 3. Примітка про перевірку станів на етапі компіляції (пріоритет: низький)
**Де:** `guide/core/architecture.md` біля рядка 1227 (розділ про скінченні автомати)
**Що:** посібник з архітектури застерігає від складних скінченних автоматів. Примітка про те, що об'єднані типи TypeScript можуть зробити прості переходи між станами безпечними на етапі компіляції, — корисний нюанс, і при цьому вона не схвалює весь патерн із трьох модулів.

## Перевірка (агент technical-writer)

**Головний висновок перевірки:** спочатку оцінку змішали з попередньою статтею Nick Tune (2026-02-28, робочі процеси на hooks). Це два різні дописи, і стаття про DSL архітектурно інша: стаття про hooks — про зв'язування, а ця — про мову опису станів.

**Оцінка оцінки:** 3/5 лишається. Аргумент за 4/5: перевірка станів на етапі компіляції через об'єднані типи з `as const` справді нова. Аргументи проти: жодного підтвердження спільнотою, реальна когнітивна складність дизайну з трьох модулів, а подача через DDD — академічне навантаження для більшості користувачів Claude Code.

**Ключове виправлення з перевірки:** спостережуваності через журнал подій у первинному прочитанні надали замало ваги. Це найпрактичніше, що можна винести, і саме з цього варто починати будь-яку пропозицію щодо інтеграції. Подача через DDD другорядна.

**Ризик неінтеграції:** загалом низький. Єдина реальна втрата — пропущений патерн спостережуваності через журнал подій. Повну архітектуру можна сміливо пропустити, доки не зросте впровадження.
