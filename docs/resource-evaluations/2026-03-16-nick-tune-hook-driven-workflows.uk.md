## Стислий підсумок

Nick Tune (його попередню статтю на Medium посібник уже цитує 4 рази) представляє новий патерн, у якому hooks Claude Code використовуються як **рушій примусового дотримання робочого процесу** з типізованим скінченним автоматом, збереженням стану в JSON і впровадженням контексту залежно від стану. Посібник описує окремі типи hooks ізольовано й має диспетчер з однією точкою входу на bash (§7.5). Стаття додає поверх hooks шар скінченного автомата на TypeScript, якого посібник не описує. Найкорисніший самостійний патерн, повторне впровадження ідентичності після компакції, можна інтегрувати вже зараз без повного скінченного автомата.

**Рекомендація**: **ПОМІРНА (оцінка 3/5)**: негайно інтегрувати патерн повторного впровадження ідентичності в §7.5. Повну архітектуру скінченного автомата підготувати як посібник із робочого процесу рівня 3 з явними передумовами. Переоцінити повну інтеграцію на 4/5 через 60-90 днів, коли з'явиться підтвердження від спільноти.

## Підсумок змісту

Стаття представляє патерн робочого процесу на hooks, побудований на п'яти основних ідеях:

- **Hooks як скінченний автомат**: hooks SubagentStart, SubagentStop, PreToolUse і TeammateIdle передають дані в рушій робочого процесу на TypeScript, який керує переходами між станами (SPAWN → PLANNING → RESPAWN → DEVELOPING → REVIEWING → COMMITTING → CR_REVIEW → PR_CREATION → FEEDBACK → COMPLETE)
- **Диспетчеризація з однієї точки входу**: один обробник hooks для всіх подій через мапу `HOOK_HANDLERS`, що диспетчеризує за `hook_event_name`; концепція схожа на bash-диспетчер з §7.5 посібника, але на TypeScript і зі станом
- **Впровадження контексту залежно від стану**: SubagentStart читає файли `/states/<state>.md` і впроваджує їх у контекст агента; агенти бачать лише інструкції, що стосуються поточного стану, і системні промпти не роздуваються
- **Патерн перезапуску**: після кожної ітерації агенти-розробник і рецензент завершуються, і запускаються нові екземпляри, тож кожна ітерація отримує чисте context window
- **Повторне впровадження ідентичності після компакції**: hooks виявляють, що агент забув свій префікс ідентичності (після компакції), і повторно впроваджують інструкції щодо ідентичності; це найсамостійніший і найпереносніший патерн у статті

## Детальний аналіз

### Точність і надійність (4/5)

Технічні твердження узгоджуються з задокументованою поведінкою hooks у Claude Code:
- Hooks SubagentStart, SubagentStop, PreToolUse, TeammateIdle існують і задокументовані
- Поле `hook_event_name` у вхідних даних hook відповідає документації в §7.4 посібника
- Патерн `exitCode: EXIT_ALLOW` / `EXIT_BLOCK` коректний
- Zod для валідації схем — стандартна практика в TypeScript
- Збереження у JSON-файл із ключем за ID сесії — практичний і коректний підхід

Одне суттєве застереження: автор прямо пише «1 week of experimentation, cannot 100% recommend yet» (1 тиждень експериментів, поки не можу рекомендувати на 100%). Це чесне застереження — не дрібниця: воно означає, що підхід не перевірено в жодному суттєвому масштабі.

### Глибина та повнота (5/5)

Повний код диспетчера на TypeScript, розібраний приклад `/states/developing.md`, схема збереження в JSON з реальними полями, мапа переходів на Zod, подача через DDD. Існує репозиторій GitHub із повним кодом. Це найсильніша сторона статті: не порожні обіцянки, а справді придатне до реалізації рішення.

### Практична цінність (4/5)

Основна проблема реальна: як отримати узгоджені робочі процеси в кодових базах, які ви не повністю контролюєте. Уже лише патерн повторного впровадження ідентичності вартий прочитання. Повний скінченний автомат складніший, але теж реалізовний.

Бар'єр: підхід потребує середовища виконання Node.js + TypeScript (`npx tsx`). Розділ посібника про hooks свідомо орієнтований на bash. Будь-яка інтеграція має явно врахувати це тертя.

### Оригінальність і унікальність (3/5)

Диспетчер з однією точкою входу вже є в §7.5 на bash. Можливість команд агентів уже задокументовано. Справді нове: (1) прив'язка типізованого скінченного автомата до hooks, (2) впровадження контексту з файлів через SubagentStart залежно від стану, (3) перезапуск для гігієни context window, (4) повторне впровадження ідентичності після компакції. Значна різниця в 4 конкретних патернах, але не в загальному підході.

### Готовність до продакшену (2/5)

1 тиждень тестування. Слова самого автора: «cannot fully recommend» (не можу повністю рекомендувати). Відома складність зв'язування («ugly and fragile at times», тобто часом потворно й крихко). Конфігурація hooks у JSON вимагає повторювати той самий запис для кожного типу подій, що визнано проблемою UX. Перш ніж подавати це як рекомендований патерн, потрібні місяці перевірки спільнотою.

### Підтвердження спільнотою (2/5)

Nick Tune — надійний практик (відомий автор, спільнота DDD). Метрик впровадження для цієї конкретної статті немає. Репозиторій GitHub існує, але даних про активність у статті немає.

## Передумови (не згадані в оцінці v1)

Будь-яка інтеграція має позначити ці жорсткі залежності:

1. **Експериментальний прапорець команд агентів**: `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS=1`: SubagentStart, SubagentStop, TeammateIdle — це події команд агентів. Без цього прапорця більшість патернів зі статті недоступні.
2. **Потрібна Opus 4.6**: команди агентів потребують Opus 4.6+, а це значно дорожче за Sonnet.
3. **Інструментарій Node.js + TypeScript**: у проєкті має бути доступний `npx tsx`. Claude Code за замовчуванням цього не передбачає.

## Рекомендована інтеграція

### Рівень 1: інтегрувати зараз (самостійний патерн)

**Повторне впровадження ідентичності після компакції** → `guide/ultimate-guide.md` §7.5 (Hook Examples)

Цей патерн одразу корисний усім, хто використовує hooks у довгих сесіях: не потрібні ні прапорець команд агентів, ні TypeScript. Дрейф ідентичності через компакцію — відомий біль. Обхідний шлях із виявленням через hook і повторним впровадженням належить до §7.5 незалежно від решти статті.

```
### Handling Identity Drift After Compaction
When Claude's context compacts, agents in long sessions can "forget" their
role. A hook can detect this and re-inject identity instructions.
```

### Рівень 2: інтегрувати з перевіркою передумов (3-4 тижні)

**Впровадження контексту через SubagentStart залежно від стану** → додати до agent-teams.md як розділ із просунутим патерном. Передумова: прапорець команд агентів. Ключова ідея: впроваджувати файли для конкретного стану під час виконання, а не пакувати все в системний промпт; це зменшує роздутість системного промпту й тримає агентів зосередженими.

### Рівень 3: новий посібник із робочого процесу (60-90 днів, після підтвердження спільнотою)

**`guide/workflows/hook-driven-workflows.md`**: повна архітектура скінченного автомата, коли патерн отримає більше підтвердження від спільноти. Чіткий заголовок із передумовами (прапорець команд агентів, Opus 4.6, Node.js + TypeScript). Подати як експериментальне / просунуте.

### Що НЕ документувати

Конкретний процес із CodeRabbit + GitHub issue + 10 станами надто суб'єктивний. Документуйте архітектурні патерни; читачі визначать власні стани.

## Результати перевірки (технічне рев'ю)

Агент перевірки виявив кілька проблем у початковій оцінці v1:

**Виправлення оцінки**: початкова оцінка 4/5 («інтегрувати протягом 1 тижня») була надто агресивною для того, що автор не перевіряв довше за 1 тиждень. Правильна оцінка зараз 3/5, із запланованою переоцінкою через 60-90 днів.

**Оригінальність перебільшено**: диспетчер з однією точкою входу вже є в §7.5 на bash. Посібник уже 4 рази посилається на попередню роботу цього автора. Реальна різниця вужча: скінченний автомат, впровадження залежно від стану, перезапуск, повторне впровадження ідентичності.

**Пропущені передумови**: прапорець команд агентів, Opus 4.6, Node.js + TypeScript — нічого з цього не було у v1. Будь-яка інтеграція без позначення цих передумов розчарувала б читачів.

**Повторне впровадження ідентичності — найнагальніший патерн**: самостійний, не потребує експериментального прапорця, безпосередньо розв'язує задокументований біль (дрейф через компакцію). Оцінка v1 згадувала його, але не визначила пріоритетною ціллю для негайної інтеграції.

**Рекомендація щодо інтеграції була розмитою**: «інтегрувати в розділ про hooks + новий посібник із робочого процесу» без визначення, що куди йде. Поетапний підхід (рівень 1 зараз / рівень 2 через 3-4 тижні / рівень 3 через 60-90 днів) практичніший.
