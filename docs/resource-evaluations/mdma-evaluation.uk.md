# Оцінка ресурсу: MDMA (MobileReality)

**URL (тригер)**: https://github.com/MobileReality/mdma
**Первинні джерела**: [репозиторій вихідного коду MDMA](https://github.com/MobileReality/mdma), включно з README, документацією, оцінками та реалізацією
**Тип**: бібліотека з відкритим кодом / DSL для інтерактивного UI, згенерованого агентом
**Оцінено**: 2026-07-07
**Оцінка**: 3/5 (ПОМІРНО, інтегрувати, коли є час)

---

## Стислий підсумок

MDMA — проєкт із відкритим кодом, що визначає діалект Markdown із вбудованим YAML для інтерактивного UI (форми, кнопки, таблиці, бар'єри схвалення), розроблений так, щоб його надійно генерували малі або донавчені LLM і детерміновано валідували перед рендерингом. Три незалежні агенти-аудитори дослідили дерево вихідного коду й дійшли узгодженої картини: базова інженерія (парсер, валідатор, конвеєр виправлень, методологія оцінювання) справді якісна, але кілька маркетингових тверджень не витримують зіткнення з кодом, а в компоненті форми, що постачається, є реальна функціональна помилка.

**Чому 3/5**: архітектуру валідатора/виправлювача та чесне подання результатів оцінювання варто задокументувати як еталонний патерн для всіх, хто будує подібний конвеєр надійності виводу малих моделей. Але розрив між заявленою та фактичною поведінкою (компонент форми, чиї «обов'язкові» поля не перевіряються, «працює будь-де», що не стосується рендерингу, некриптографічні хеші, які рекламують поряд із ключовими словами «audit-log»/«pii») означає, що це не рекомендація «будуйте на цьому в продакшені» без попереднього самостійного виправлення прогалини у валідації.

## Аналіз змісту

### Ключові факти (перевірено)

1. **Детермінований конвеєр валідації/виправлення**: один прохід, без додаткового виклику LLM, видобування на основі регулярних виразів, стійке до некоректного markdown, 22 файли правил у `packages/validator/src/rules` (19 задокументовано в README, 22 пораховано у вихідному коді на момент аудиту), упорядковані виправлювачі для визначення типу поля, виправлення одруківок у ключах YAML і відновлення прив'язок.
2. **Стандартний парсинг**: побудовано на remark/unified як повноцінний plugin, з явною обробкою стану потокової генерації (розрізняє блок, що ще генерується, і блок, який справді некоректний).
3. **Методологія оцінювання**: використовує promptfoo з власними перевірками (assertions), задокументовано з поданням «не 100%, спостереження, а не висновки» в `evals/own-model/README.md`. Виміряний результат: 41% успіху з голим prompt проти 90,5% з DSL і валідатором разом, на їхній власній донавченій моделі, що обслуговується через Modal/Hugging Face.
4. **«Працює будь-де» для базових пакетів**: пакети `spec`, `parser`, `validator` і `runtime` не містять жодного специфічного для Node імпорту (`fs`, `path`, `crypto`), що підтверджено grep по деревах вихідного коду всіх чотирьох пакетів.
5. **Гігієна CI**: GitHub Actions зафіксовано за SHA коміту в `.github/workflows/ci.yml` і `release.yml` (напр. `actions/checkout@de0fac2e4500dabe0009e67214ff5f5447ce83dd # v6`), версіонування окремих пакетів на основі changesets, набір тестів `turbo run test`, що охоплює всі пакети.
6. **Структура пакетів**: 10 пакетів (`spec`, `parser`, `validator`, `runtime`, `attachables-core`, `renderer-react`, `cli`, `mcp`, `agui`, `prompt-pack`), кожен незалежно версіонується й публікується в npm-організації `@mobile-reality`.

### Перевірка фактів: твердження проти коду

| Твердження | Статус | Доказ |
|-------|--------|----------|
| «Guarantees valid UI» | ❌ Перебільшено | Виміряно 90,5%, а не 100% (`evals/own-model/README.md`) |
| Власний файл результатів оцінювання показує 100% | ⚠️ Внутрішня суперечність | `evals/own-model/results.json`: 95/95 успішних (100%) від 2026-06-30, не узгоджено з цифрою 90,5% у README для того самого треку оцінювання |

| Компонент Webhook виконує вебхуки | ❌ Вводить в оману | `WebhookRenderer.tsx` надсилає UI-подію (`INTEGRATION_CALLED`), яку має обробити застосунок-хост; жодного HTTP-виклику всередині MDMA не відбувається (`packages/renderer-react/src/components/WebhookRenderer.tsx`, рядок 29). Слід віддати належне проєкту: цю прогалину вказано в їхній власній дорожній карті як ще не реалізовану |
| «On-device / mobile models» | ⚠️ Оманливе подання | Стосується розміру LLM-генератора (розміщеного на Modal, розповсюджуваного через Hugging Face), не пов'язано з рендерингом. CSS рендерера не має жодного запиту `@media`, що підтверджено в усіх файлах `.css` у `packages/renderer-react` |
| «Accessible by design» (демосторінка) | ❌ Не підтверджено | Нативні мітки/кнопки й один `role="alert"` існують (`CalloutRenderer.tsx`), але ніде немає `aria-invalid`/`aria-live`, а клітинка таблиці з маскуванням PII — клікабельний `<span>` без `role="button"`/`tabIndex` (`packages/renderer-react/src/components/TableRenderer.tsx`, рядки 4-15) |
| Валідація форм (required/pattern/min/max) застосовується | ❌ Хибно, функціональна помилка | Див. окремий розділ нижче |
| Цілісність журналу аудиту захищена від підробки | ❌ Не криптографічно | Хеш FNV-1a, коментар у коді каже «non-cryptographic» (`packages/runtime/src/core/event-log-integrity.ts`, рядок 10) |
| Хеш редагування PII безпечний | ❌ Не криптографічно | Ковзний хеш у стилі djb2, коментар каже «non-cryptographic, for logging only» (`packages/runtime/src/redaction/hash.ts`) |

## Помилка валідації форм (незалежно знайдена двома агентами-аудиторами)

Це найвагоміший висновок, бо він суперечить власній документації проєкту, а не маркетинговому гаслу.

- `FormRenderer.tsx` обгортає кожне поле у звичайний `<div className="mdma-form">`, а не в елемент `<form>` (`packages/renderer-react/src/components/FormRenderer.tsx`, рядок 152).
- Елемент надсилання — це `<button type="button">` з `onClick`, що безпосередньо надсилає дію `ACTION_TRIGGERED`, оминаючи будь-яку подію надсилання форми (той самий файл, рядки 119-125 і 247-258).
- Нативна валідація обмежень HTML5 (атрибут `required`, переданий кожному полю вводу) спрацьовує лише на справжній події надсилання форми. Оскільки немає ні `<form>`, ні кнопки `type="submit"`, вона ніколи не спрацьовує.
- Об'єкт `validation` на рівні поля (`pattern`, `min`, `max`, `message`) визначено в схемі в `packages/spec/src/schemas/components/form.ts` (рядок 18), і його ніде не читають ні в рендерері, ні в обробнику форм attachables-core (`packages/attachables-core/src/form/form-handler.ts`).
- `docs/reference/component-catalog.md` документує саме цей об'єкт `validation` з робочим прикладом (`pattern`, що відповідає корпоративному поштовому домену, рядки 71-72), і та сама конструкція з'являється у власному `examples/approval-workflow/document.md` репозиторію.

**Підсумковий ефект**: поле з позначкою `required: true` та обмеженням `pattern` можна надіслати порожнім або невідповідним, без жодної помилки для користувача, попри те що документація подає це як робочу поведінку з конкретними прикладами з самого репозиторію. Це інший за природою випадок, ніж прогалина з вебхуками, яку чесно вказано як майбутню роботу у власній дорожній карті проєкту. Прогалину у валідації ніде не розкрито.

## Рекомендація щодо інтеграції

### Де

**Розділ 7.1** у `guide/ecosystem/ai-ecosystem.md`, одразу після розділу 7 (UI Prototypers) і перед розділом 8 (Workflow Orchestration).

### Що включено

1. Чому існує категорія генеративного UI (агентові потрібен інтерактивний вивід у межах одного ходу чату, а не окремий артефакт)
2. Таблиця порівняння: A2UI проти MCP Apps проти генеративного UI у Vercel AI SDK проти MDMA
3. Аналіз кейсу MDMA: що витримує перевірку, що перебільшено, помилка валідації форм, примітка щодо безпеки хешів
4. Чесна примітка, що категорія молода (2025–2026), жоден стандарт не переміг, а розповсюдження (за ким стоїть вендор) важить не менше за технічні переваги

### Що НЕ включено

- Жодного туторіалу чи покрокового «як впровадити MDMA». Цей посібник документує Claude Code, а не рекомендує будувати на конкретному сторонньому DSL.
- Жодного глибокого розбору плану інтеграції MDMA-AG-UI (`mdma-agui-integration-plan.md`), надто спекулятивного й доімплементаційного, щоб цитувати як факт.
- Жодного порівняння з MCP-UI (окремим, пов'язаним, але відмінним проєктом, на який посилаються співавтори MCP Apps), поза обсягом цієї оцінки.

### Пріоритет

**Помірний**. Не терміново (жоден читач без цього не заблокований), але це реальна прогалина у змісті: посібник докладно охоплює MCP Apps, але не мав нічого, що порівнювало б їх з A2UI, патерном Vercel AI SDK чи MDMA, і нічого про цей конкретний патерн надійності для генерації UI малими моделями.

## Виклик (technical-writer)

- **Оцінку обґрунтовано**: 3/5 правильно, а не 4/5, бо практичний висновок для користувача Claude Code обмежений (MDMA — стороння бібліотека для конкретного стеку рендерингу, лише React, не те, що більшість читачів упроваджуватимуть напряму). Не 2/5, бо архітектура валідатора/виправлювача та чесна методологія оцінювання малих моделей — справді корисний еталонний патерн, а ширше порівняння генеративного UI (A2UI проти MCP Apps проти Vercel AI SDK проти MDMA) саме по собі було реальною прогалиною, яку варто заповнити незалежно від вад самого MDMA.
- **Ризик переоцінки**: перший прохід агентів-аудиторів схилявся до похвали інженерії валідатора, недостатньо зважаючи на помилку валідації форм. Цю помилку свідомо винесено на перше місце в тексті аналізу кейсу саме тому, що вона суперечить задокументованій поведінці, а це серйозніша категорія проблем, ніж амбітний маркетинговий рядок.
- **Скоригована оцінка**: 3/5 (не змінилася після виклику).
