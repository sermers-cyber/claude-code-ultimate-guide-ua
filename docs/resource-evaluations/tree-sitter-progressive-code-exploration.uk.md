## Короткий підсумок

**Оцінка: 4/5** (висока цінність: інтегрувати протягом тижня)

Патерн «smart explore» використовує парсинг AST через tree-sitter, щоб стиснути дослідження коду з 10-15 тис. токенів на файл до ~200-500 токенів: спершу показуються сигнатури функцій і структура, а заглиблення в конкретні функції відбувається лише за потреби. RTK опрацьовує виводи команд (економія 60-90%); цей патерн опрацьовує читання коду (економія 90-97%). Разом вони охоплюють обидва головні джерела витрати токенів у сесії Claude Code.

Єдиної «офіційної» реалізації немає: skill Alex Newman приватний. Але в екосистемі є кілька робочих реалізацій, від суто CLI-підходу до готових до продакшену MCP-серверів.

---

## Патерн: прогресивне дослідження коду

Три шари, що виконуються по черзі:

```
Layer 1 — Structure (~200 tokens)
  tree-sitter parse file.rs → function signatures, types, fields
  Claude sees: "what exists?" without reading any body

Layer 2 — Search (~300 tokens)
  "Show me the body of filter_output()"
  tool returns lines 47-120 only, not the whole file

Layer 3 — Context (~500 tokens)
  "Who calls filter_output()?"
  cross-reference table, not file dumps
```

**Порівняно з наївним підходом** (прочитати файл, прочитати ще один файл, прочитати ще один файл):
- Наївно: 10 файлів × ~1 400 токенів = 14 000 токенів
- Прогресивно: 10 структур (2 000) + 2 функції (1 000) = 3 000 токенів
- **Скорочення: у середньому ~78%, до 97% для великих репозиторіїв**

Той самий патерн використовує Aider (понад 40 тис. зірок) для своєї мапи репозиторію, і він перевірений у масштабі.

### 5. Aider Repo Map (еталонна реалізація)

**Проєкт**: Aider (https://aider.chat), понад 40 тис. зірок (станом на 2026-07-28 уже 47 733)
**Підхід**: tree-sitter + граф NetworkX + ранжування PageRank + бінарний пошук для бюджету токенів

**Як це працює**:
1. Розбір кожного файлу через tree-sitter → видобування символів і місць, де на них посилаються
2. Побудова графа залежностей (файли = вузли, перехресні посилання = ребра)
3. PageRank: файли, на які посилається багато інших, отримують вищий бал (публічний API > приватний хелпер)
4. Підгонка під бюджет: бінарний пошук, щоб умістити все в ліміт `--map-tokens` (за замовчуванням: 1 000 токенів)

**Чому це важливо**: Це найкраще технічно задокументована реалізація патерну. Створена 2023 року, перевірена в масштабі понад 40 тис. зірок. MCP-сервера немає, але вона показує, як має виглядати ідеальна реалізація.

**Бюджет токенів за замовчуванням**: `--map-tokens 1000` дає структуру всього репозиторію в 1 тис. токенів.

## Оцінка доречності: 4/5

### Чому 4/5?

**Сильні сторони на користь інтеграції**:

1. **Сигнал від надійного джерела**: Alex Newman (Claude-MEM, понад 38 тис. зірок) прямо називає це патерном, що дає «14k → 200 tokens». Це не маркетинг, а сигнал від колеги.
2. **Кілька продакшен-реалізацій**: code-review-graph має 2 тис. зірок і ліцензію MIT, jCodeMunch встановлюється однорядковою командою `uvx`, Aider підтверджує патерн у масштабі понад 40 тис. зірок.
3. **Справжня прогалина в поточному посібнику**: Посібник документує RTK (економія на виводі команд), але не економію на читанні коду. Ці дві проблеми доповнюють одна одну, і охоплення обох дає повну картину.
4. **Патерну можна навчити**: Поступове розкриття (структура → пошук → заглиблення) працює навіть без зовнішніх інструментів, лише з дисциплінованим використанням інструмента Read у Claude.
5. **Довіра до Aider**: Патерн не експериментальний: мапа репозиторію Aider працює в продакшені з 2023 року.

**Чому не 5/5**:

1. **Skill «smart explore» від Alex не публічний**: На нього неможливо прямо послатися. Посібник має документувати патерн і доступні реалізації, а не «skill Alex Newman».
2. **Бенчмарки сильно різняться**: від 6.8x до 49x і до 95%; чесну цифру для типових воркфлоу визначити складніше, ніж виміряні 60-90% для RTK.
3. **grepai уже частково це робить**: Посібник уже рекомендує grepai для семантичного пошуку коду. Tree-sitter додає структурне розуміння (не лише семантичне), але перетин реальний.
4. **MCP-сервери на ранній стадії**: mcp-server-tree-sitter не має бенчмарків, CodeRLM має відому проблему з автономністю, jCodeMunch бере гроші за комерційне використання.

## Технічні примітки (для авторів посібника)

### Чим tree-sitter Є і чим НЕ Є

**Є**: Бібліотекою-парсером, що перетворює вихідний код на AST (абстрактне синтаксичне дерево). Той самий рушій, який VSCode/Neovim/Zed використовують для підсвічування синтаксису та згортання коду.

**Не є**: Семантичним аналізатором. Він розуміє синтаксис, а не значення. `tree-sitter` може сказати «це функція з назвою X і такими параметрами», але не «цю функцію викликає Y у кодовій базі» (це робить граф grepai/Aider).

### Аналогія з DOM (для документації)

«Tree-sitter робить із кодом те саме, що браузер з HTML: перетворює плаский текст на структуру, якою можна переміщатися. Замість дерева DOM ви отримуєте AST: кожна функція, клас, структура й поле стають типізованим вузлом із точною позицією у файлі.»

### Чесна математика токенів

| Операція | Токени | Метод |
|---|---|---|
| Прочитати файл на 500 рядків | ~3 500 | Інструмент Read у Claude |
| Отримати лише структуру файлу | ~200 | Сигнатури tree-sitter |
| Прочитати одну функцію (50 рядків) | ~350 | Пошук за зміщенням через tree-sitter |
| Дослідити модуль із 10 файлів (наївно) | ~35 000 | Read × 10 |
| Дослідити модуль із 10 файлів (прогресивно) | ~3 500 | Структура × 10 + заглиблення × 2 |

Реальне скорочення для типової роботи над фічами: **70-90%**. Цифри на рівні 97% потребують гігантських кодових баз і вдалих патернів доступу.
