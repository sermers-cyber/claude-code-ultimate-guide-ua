# Оцінка: стаття про повторення промпту (arXiv:2512.14982)

**Дата**: 2026-01-25
**Стаття**: «Prompt Repetition Improves Non-Reasoning LLMs»
**Автори**: Yaniv Leviathan, Matan Kalman, Yossi Matias (Google Research)
**Опубліковано**: 17 грудня 2025
**arXiv**: https://arxiv.org/abs/2512.14982

---

## 1. Підсумок висновків

### Основне твердження
Повторення вхідного промпту 2x покращує точність LLM **без режиму міркування**, не збільшуючи довжини виводу чи затримки.

### Протестовані моделі (безпосередньо зі статті)
- Gemini 2.0 Flash / Flash Lite
- GPT-4o / GPT-4o-mini
- **Claude 3 Haiku**
- **Claude 3.7 Sonnet**
- Deepseek V3

### Бенчмарки
ARC (Challenge), OpenBookQA, GSM8K, MMLU-Pro, MATH, NameIndex, MiddleMatch

### Ключові результати
| Метрика | Значення |
|--------|-------|
| Перемоги (без міркування) | 47/70 комбінацій бенчмарк-модель |
| Поразки | 0 |
| З CoT/міркуванням | 5 перемог, 1 поразка, 22 нейтрально |

### Примітки щодо Claude (зі статті)
- Протестовано на Claude 3 Haiku і Claude 3.7 Sonnet
- Для моделей Claude на дуже довгих запитах спостерігалося **зростання затримки** (повторення x3 або кастомні бенчмарки)
- Імовірно, через довший етап prefill

## 2. Релевантність для Claude Code

### Ситуація з моделями (січень 2026)

| Модель | Режим thinking | Чи застосовне повторення промпту? |
|-------|---------------|-------------------------------|
| Opus 4.5 | Увімкнено за замовчуванням (максимальний бюджет) | НІ — thinking уже максимізує міркування |
| Sonnet 4 | Недоступний | ТАК — може дати користь |
| Haiku 3.5 | Недоступний | ТАК — може дати користь |

### Проблема

Claude Code використовує:
- **Sonnet за замовчуванням** (85% використання за статистикою посібника)
- **Haiku для простих задач** (оптимізація вартості)
- **Opus для складних задач** (уже має режим thinking)

Техніка зі статті призначена саме для сценаріїв **без міркування**. Це робить її потенційно релевантною для Sonnet/Haiku у Claude Code.

### Підступ

1. **Вартість вхідних токенів подвоюється**: повторення промпту = 2x вхідних токенів
2. **Контекст Claude Code і так під тиском**: посібник наголошує на керуванні контекстом (практична межа 100K)
3. **Величина виграшу неясна**: стаття показує перемоги/поразки, але не абсолютний відсоток покращення
4. **Проблема затримки, специфічна для Claude**: стаття зазначає зростання затримки для Claude на довгих промптах

## 4. Практичні міркування для Claude Code

### Гіпотетична реалізація через hook

```bash
# pre-prompt-hook.sh (EXPERIMENTAL)
#!/bin/bash
# Double the prompt for Sonnet/Haiku
if [[ "$CLAUDE_MODEL" != "opus"* ]]; then
  echo "${1}

---
(Repeated for accuracy)
${1}"
else
  echo "$1"
fi
```

### Проблеми цього підходу

1. **У Claude Code немає API для зміни промптів** — hooks не можуть перехоплювати введення користувача
2. **Знадобилися б зміни на рівні SDK** — це не функція, яку налаштовує користувач
3. **Подвоєння вартості** — подвоює вхідні токени, що може звести нанівець будь-який виграш у точності
4. **Роздування контексту** — прямо суперечить принципам гігієни контексту з посібника

## 6. Рекомендація

### Оцінка: 2/5 — НЕ ІНТЕГРУВАТИ

### Обґрунтування

1. **Не та ціль**: техніка спрямована на LLM без міркування, але складні задачі в Claude Code вже використовують Opus (з thinking). Простим задачам на Sonnet/Haiku потрібна не оптимізація точності, а швидкість.

2. **Користувачі не можуть це реалізувати**: у Claude Code неможливо перехопити власні промпти. Для цього потрібні зміни в SDK, а не документація.

3. **Нульове підтвердження**: жодних відтворень, жодного прийняття спільнотою, жодних звітів про реальне використання за 5 тижнів.

4. **Надмірна вартість**: подвоєння вхідних токенів суперечить наголосу Claude Code на ефективності контексту й керуванні вартістю.

5. **Нішеве застосування**: навіть якщо техніка валідна, вона допомагає лише на специфічних задачах у стилі бенчмарків (вибір відповіді, математика), а не на відкритих задачах із кодом, які розв'язує Claude Code.

### Що могло б це змінити

- Незалежні відтворення на Claude Sonnet 4
- Звіти про реальне використання від користувачів Claude Code
- Визнання або інтеграція з боку Anthropic
- Докази того, що виграш у точності переважає 2x вартість вхідних токенів

### Альтернативна рекомендація

Якщо користувачі хочуть кращої точності на Sonnet:
- Використовувати **OpusPlan** (Opus для планування, Sonnet для виконання) — уже задокументовано
- Перемикатися на Opus для критичних рішень — уже задокументовано
- Використовувати структурований промптинг (XML-теги) — уже задокументовано

Це перевірені техніки з посібника, які не подвоюють витрат.
