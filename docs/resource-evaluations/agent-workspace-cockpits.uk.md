# Десктопні робочі простори для агентів: вибіркова оцінка «кокпітів»

**Переглянуто:** 17 жовтня 2026 року; додаткова перевірка Escouade під час виконання 22 жовтня 2026 року; додатковий перегляд документації Orca 27 жовтня 2026 року. **Рішення:** оновити Conductor і Vibe Kanban; додати короткі порівняльні згадки про Emdash, Superset, Escouade та Orca. Залишити Opcode в цій оцінці без окремого профілю в посібнику. Редакційна оцінка Escouade після випробування лишається 3/5.

Оцінки відображають редакційну цінність для цього посібника, а не надійність, безпеку чи очікувану продуктивність продукту. Огляд 17 жовтня спирався на офіційну документацію, зафіксовані README та ліцензії репозиторіїв, а також на цільову перевірку допоміжної функції Escouade. Під час додаткової перевірки 22 жовтня Escouade 1.8.8 запускали локально з Claude Code та наявною підпискою Claude Max. Інші десктопні застосунки, інших провайдерів, віддалені інтеграції та повні набори тестів upstream не перевіряли.

### Orca

**Перегляд документації: 27 жовтня 2026 року. Застосунок не випробовували.** Ця оцінка стосується [stablyai/orca](https://github.com/stablyai/orca), десктопного середовища під ліцензією MIT, а не інших репозиторіїв з назвою Orca. Воно запускає наявні агентні CLI у worktrees і пропонує анотації diff, контекст елементів браузера, виконання через SSH та мобільний застосунок-компаньйон. Усе це перетинається з наявними профілями робочих просторів і не виправдовує другого каталогу функцій.

Корисне порівняння дає конкретний цикл доставки. [Документація хостованих рев'ю](https://www.onorca.dev/docs/review/github) Orca пов'язує worktrees з PR/MR і показує перевірки та гілки обговорень рев'ю. Для PR на GitHub, що не проходить перевірки, дія **Fix broken checks** передає агентові назви й посилання на невдалі перевірки. Це документує дію зворотного зв'язку, а не доводить автономне виправлення, коректну атрибуцію комітів чи успішний CI. Підтримку рев'ю в GitLab також задокументовано; у цій оцінці жоден із провайдерів не перевіряли.

Два налаштування за замовчуванням впливають на впровадження за наявного десктопного воркфлоу Codex:

- [Інтеграція з Codex](https://www.onorca.dev/docs/agents/codex) документує окремий фоновий сервер для кожного термінала Codex у версії Codex 0.157 і новіших. Функції спільного сервера та сесії, відкриті через десктопний застосунок Codex або IDE, за замовчуванням не бачать цих сесій Orca. Налаштування «сервер на термінал» можна вимкнути перед відкриттям нових терміналів. Передача роботи іншому агентові запускає нову сесію з обмеженим попереднім контекстом; це не нативне відновлення. Безперервність між застосунками тут не перевіряли.
- [Дозволи агентів](https://www.onorca.dev/docs/agents/supported) заздалегідь підставляють аргументи обходу дозволів для нових запусків термінала, зокрема обхід і підтверджень, і пісочниці для Codex. Налаштування термінала **Agent Permissions** підтримує ручний режим; нативні чати мають окреме значення за замовчуванням для нових чатів, а власні аргументи агентів і далі мають пріоритет. Перед випробуванням перевірте фактичні параметри запуску. Розділення на worktrees не є обмеженням процесів.

[Зафіксована документація з оркестрації](https://github.com/stablyai/orca/blob/3ddaa8df6f61e77ef095fba03532b2a13b3b2fdf/docs/site/content/docs/cli/orchestration.mdx), перевірена 27 жовтня, позначає свої задачі, залежності, керованих виконавців, повідомлення та точки ухвалення рішень як експериментальні. Довготривалий Run описано як простір імен для координації, а не як самостійний автоматичний планувальник.

**Редакційна оцінка: 3/5.** Включити механізм відгуків рев'ю та межі впровадження з Codex у спільне порівняння. Випробовувати Orca, коли проблема в єдиному щоденному робочому просторі; порівнювати з AO, коли проблема в координації PR/CI/рев'ю на рівні проєкту. Обидва інструменти перетинаються, тож це гіпотеза для вибору тестів, а не рейтинг продуктів. Локальне випробування Escouade із залежностями та тестовим бар'єром нічого не встановлює щодо поведінки жодної з альтернатив. Жодної виміряної переваги в продуктивності, безпеці, зручності чи надійності не заявлено.

### Emdash

[Зафіксований README](https://github.com/generalaction/emdash/blob/761520624f1cafa740f5c88ddaf083b4fde2cc59/README.md) документує десктопний застосунок для macOS, Windows і Linux, який використовує встановлені CLI агентів програмування та окремий worktree для кожної задачі. Його локальний/SSH-воркфлоу є корисним критерієм вибору для читачів, які вже мають власну віддалену машину. Ліцензія: [Apache-2.0](https://github.com/generalaction/emdash/blob/761520624f1cafa740f5c88ddaf083b4fde2cc59/LICENSE.md).

Впровадження змінює конфігурацію: для агентів із підтримкою lifecycle hooks Emdash встановлює позначені маркером hooks у конфігурацію рівня користувача для статусу, сповіщень і сесій з можливістю відновлення. README стверджує, що поза сесіями Emdash вони нічого не роблять; у цьому огляді ні цю поведінку, ні сумісність з наявними hooks не перевіряли. Агентні CLI можуть надсилати промпти, код і контекст своїм провайдерам, хоча Emdash документує локальне сховище SQLite та необов'язкову телеметрію.

Оцінка лишається 3/5: це корисна відмінність у воркфлоу без виміряної переваги над наявними профілями. Не варто стверджувати, що підтримка SSH унікальна для всього ринку.

### Superset

[Зафіксований README](https://github.com/superset-sh/superset/blob/e547103d8570a39327c051b80144e45c59203052/README.md) описує worktrees із терміналами, рев'ю diff, визначенням портів і попереднім переглядом у браузері для кожного робочого простору. Режим дизайну надсилає агентові контекст вибраного елемента UI. Відгуки на рядки diff у PR можна передати в запущену або нову сесію агента; публікація цих відгуків на GitHub необов'язкова. Ці механізми дають конкретний приклад для розробки UI, а не ще один перелік паралельних терміналів.

Те саме джерело описує віддалений доступ, хмарні робочі простори, мобільну версію Pro, планування, а також CLI, SDK і MCP. Тому інтеграція не називає весь продукт суто локальним чи безкоштовним. Основна платформа: macOS; підтримка Linux AppImage експериментальна, а Windows у цьому знімку недоступна.

Поточна [ліцензія: Elastic License 2.0](https://github.com/superset-sh/superset/blob/e547103d8570a39327c051b80144e45c59203052/LICENSE.md). Посібник використовує позначку **source-available**, а не загальну позначку open source. Умови ліцензії обмежують надання суттєвої функціональності як хостованого/керованого сервісу та втручання у функціональність ліцензійних ключів; для будь-якого перерозповсюдження чи сервісної пропозиції звіртеся з ліцензією.

Оцінка лишається 3/5: включити механізм браузера/рев'ю, а не вичерпний другий профіль продукту чи рейтинг зручності.

### Escouade

[README версії 1.8.8](https://github.com/guillaume-gagnaire/escouade/blob/9383ada96cf91190fc719a1fcac7ac72ab00c7c4/README.md) документує Windows, macOS і Linux, французький/англійський інтерфейс, фронтенд на Svelte 5, бекенд на Tauri 2/Rust та підтримку Claude Code, Codex, OpenCode і GitHub Copilot CLI. Описане нижче випробування стосувалося лише Claude Code, процеси якого використовують `stream-json`; інші адаптери та передачу роботи між провайдерами воно не перевіряє.

Внесок інструмента в тікетному воркфлоу: критерії приймання, залежності, worktrees, повторні спроби агентів і налаштовувані дії тестування/доставки. MCP-сервер дає агентам змогу керувати робочим простором. Це шар керування воркфлоу; звіт про виконання критеріїв не є незалежним доказом приймання. Поточний опис MCP охоплює валідацію тікетів, дії тестування/злиття, видалення тікетів і відповіді на запити дозволів. Отже, затвердження людиною не є безумовним інваріантом кожного шляху.

Ліцензія: [GPL-3.0-or-later](https://github.com/guillaume-gagnaire/escouade/blob/9383ada96cf91190fc719a1fcac7ac72ab00c7c4/README.md#licence); README прямо зберігає ліцензію MIT для версій до 1.7.7 включно. Старіший знімок під MIT не повинен визначати позначку ліцензії для поточного проєкту.

#### Випробування Escouade під час виконання: 22 жовтня 2026 року

**Обсяг і метод.** Escouade [1.8.8](https://github.com/guillaume-gagnaire/escouade/releases/tag/v1.8.8) зібрали з незміненого вихідного коду релізу та запустили на macOS з Apple Silicon у режимі розробки. Оцінювач працював через офіційний MCP-сервер десктопного застосунку, операції з тікетами якого викликають ті самі базові функції, що й UI. Так перевірено воркфлоу застосунку, а не навігацію мишею чи візуальну зручність. Випробування обмежували одноразовий Git-репозиторій, окремі дані застосунку, вимкнене автоматичне копіювання файлів і явна команда тестування перед злиттям. Нічого не публікували віддалено.

Завданням була невелика програма перевірки документації на стандартній бібліотеці Python із синтетичними документами Markdown. Два агенти Claude Sonnet працювали паралельно: один витягав заголовки поза огородженими блоками коду, інший перевіряв відносні посилання на файли. Третій тікет залежав від обох і збирав JSON CLI. Кожен тікет мав окремі файли реалізації та тестів. Підсумкова гілка пройшла **19 тестів пілотного проєкту** (18 написали агенти, ще одна початкова перевірка фікстури), а також **3 приймальні тести, написані оцінювачем** до запуску агентів. Це не кількість тестів upstream-набору Escouade і не незалежний аудит продукту. Приймальні тести перевіряли рядки заголовків, виключення огородженого коду, закодовані шляхи та фрагменти, вивід JSON і коди виходу для коректних і зламаних посилань.

| Перевірена поведінка | Спостережуваний результат |
|---|---|
| Дотримання залежностей | Спробу запустити інтеграційний тікет до завершення передумов відхилено із зазначенням обох залежностей |
| Паралельна робота | Два агенти працювали в окремих автоматично створених worktrees і гілках |
| Переривання та перезапуск | Після переривання обох агентів і перезапуску застосунку тікети, гілки та сесії з можливістю відновлення залишилися доступними |
| Обробка дозволів | Запити на виконання команд з'являлися в спільному списку запитів MCP й отримували одноразові підтвердження |
| Негативний тестовий бар'єр | Навмисно доданий оцінювачем тест, що не проходить, заблокував перше злиття; цільова гілка лишилася незмінною. Escouade повернув тікет агентові на виправлення навіть з вимкненим автопілотом |
| Доставка та планування | Після того як оцінювач прибрав навмисну помилку й переглянув результати, тести та злиття завершилися. З увімкненим автопілотом інтеграційний тікет далі запустився автоматично від бази, що містила обидві передумови |
| Кінцевий стан | Усі три тікети завершено й локально злито, жодних агентів чи запитів дозволів у списку; автопілот вимкнено |

Отриманий CLI повідомив про навмисно відсутній файл, проігнорував посилання всередині огородженого коду й повернув очікувані коди виходу. Це був обмежений прототип для перевірки оркестрації, а не заміна наявних перевірок документації в посібнику.

**Виявлені обмеження.** Один тікет зупинився з повідомленням «Bilan des critères manquant», хоча агент надав звіт. Рядок JSON містив три зворотні апострофи: [`last_block`](https://github.com/guillaume-gagnaire/escouade/blob/9383ada96cf91190fc719a1fcac7ac72ab00c7c4/src-tauri/src/board.rs#L137-L143) обриває звіт на першому їх входженні, навіть усередині рядка. Повторна подача звіту без цих символів розблокувала рев'ю. Це спостережена помилка звітування, а не провалений тест реалізації.

- **Тести потребують явного налаштування.** [`BoardSettings::default`](https://github.com/guillaume-gagnaire/escouade/blob/9383ada96cf91190fc719a1fcac7ac72ab00c7c4/src-tauri/src/model.rs#L924-L946) вимикає тести перед доставкою й не задає команди тестування. Для випробування налаштували і те, і інше; самі лише позначені агентом критерії такого бар'єра не забезпечують.
- **Зведення файлів потребують звірки з Git.** Зведення агента в MCP повернуло `touchedFiles: []`, тоді як Git показував нові файли, записані через Bash. Панель Git у десктопному застосунку не оцінювали, тож це спостереження стосується лише зведення.
- **Перевірка дистрибутива на тестовій машині не пройшла.** `codesign --verify --deep --strict` повідомив про недійсний підпис arm64 для застосунків, видобутих з обох офіційних завантажень для macOS, tar.gz і DMG. Збирання з вихідного коду релізу, з CMake, доданим до тимчасового середовища збирання, дало змогу продовжити випробування. Причину невдалої перевірки підпису та поведінку на інших машинах не встановлено.
- **Налаштування запуску оцінювача потребувало виправлення.** Власний лаунчер спершу завантажував особисті hooks. Обох агентів перервали ще до редагування файлів проєкту; лаунчер виправили й перевірили фактичні параметри процесів перед відновленням. Ця помилка налаштування не є дефектом Escouade, а ізольоване налаштування MCP/облікового запису не відображає звичайних зусиль на встановлення.

**Висновок щодо впровадження.** Підтверджений внесок полягає в постійному воркфлоу, що пов'язує тікети, worktrees, рев'ю та доставку з примусовим дотриманням залежностей. У поточному воркфлоу оцінювача з Codex ці кроки координуються через розмови та явні операції Git. Тож Escouade є кандидатом для черги відокремлюваних задач із подальшою інтеграцією. Цей невеликий прототип можна було б виконати й за одну сесію: випробування не доводить, що така декомпозиція чи перехід на інший інструмент заради однієї зміни виправдані.

Не було ні еквівалентного A/B-запуску з Codex, ні виміряної переваги в часі чи вартості, ні навмисної перевірки конфлікту злиття, ні зміни провайдера, ні сценарію вичерпання квоти, ні тесту обмеження на рівні ОС. Записи виконання та пілотний репозиторій збережено локально, але разом з цією оцінкою не опубліковано; наведені вище спостереження є звітом оцінювача, а не публічно відтворюваним бенчмарком. Публічні постійні посилання на вихідний код підтверджують висновки щодо парсера та налаштувань за замовчуванням, але не результати виконання.

**Попередній висновок щодо копіювання файлів, не перевірений повторно на 1.8.8:** перевірка 17 жовтня [зафіксованої допоміжної функції `copy_one`](https://github.com/guillaume-gagnaire/escouade/blob/b74b6526b3ba94df049a9a8ad1466e37706fe175/src-tauri/src/testlaunch.rs#L126) показала, що вона створює батьківські каталоги призначення й викликає `std::fs::copy`, не відхиляючи символьне посилання в місці призначення. Окрема перевірочна програма на Rust з точно цією функцією та фіктивними файлами відтворила перезапис поза worktree. Функція `copy_worktree_files`, що її викликає, копіює ігноровані файли, які відповідають налаштованим шаблонам на кшталт `.env*`. Під час випробування 22 жовтня автоматичне копіювання було вимкнене, тож воно ні повторно не підтверджує цей висновок, ні не демонструє виправлення.

Щоб відтворити вузький результат на Unix у тимчасовому каталозі:

1. Створіть `project/`, `worktree/` та `outside-sentinel` з фіктивним текстом.
2. Запишіть інший фіктивний текст у `project/dummy.env`.
3. Зробіть `worktree/dummy.env` символьним посиланням на контрольний файл поза `worktree/`.
4. Скомпілюйте зафіксовану функцію `copy_one` без змін в окремій програмі на Rust і викличте її з цими двома шляхами до каталогів та `dummy.env`.
5. Переконайтеся, що зовнішній контрольний файл тепер містить вихідний текст, потім видаліть тимчасовий каталог.

Це підтверджує поведінку допоміжної функції щодо посилань у місці призначення, а не наскрізний експлойт, поведінку з junction у Windows чи кожен шлях входу в застосунку. Жодних справжніх секретів чи репозиторіїв не використовували. Попередню кількість тестів з іншої ревізії Escouade не перенесено як поточний доказ.

Редакційна оцінка лишається 3/5: обмежене випробування під час виконання підтверджує корисну поведінку тікетів/MCP, але не дає порівняльних доказів щодо продуктивності чи безпеки. Для випробування використовуйте одноразовий репозиторій і фіктивну конфігурацію з вимкненим автоматичним копіюванням секретів; перевірте тести й дозволи на доставку, перш ніж застосовувати інструмент до важливої роботи. Ця згадка не є рекомендацією з безпеки.

## Виправлення під час супроводу

**Conductor:** оновлений профіль підтверджують офіційні [вступ](https://www.conductor.build/docs), [документація з хмари](https://www.conductor.build/docs/cloud), [переглядач diff](https://www.conductor.build/docs/reference/diff-viewer) і [документація Checks](https://www.conductor.build/docs/reference/checks). Продукт документує Claude Code, Codex, Cursor і OpenCode, клієнт для macOS і хмарне виконання на Linux. Локальні worktrees забезпечують розділення розробки, а не межу безпеки; доступ із хмари до локальної машини можна явно ввімкнути. Див. [безпека та дозволи](https://www.conductor.build/docs/reference/security-and-permissions). Сусіднє порівняння з AO більше не стверджує, що Conductor підтримує лише двох агентів, і не заявляє про кращу відшліфованість без доказів.

**Vibe Kanban:** офіційне [оголошення про закриття від 10 квітня](https://www.vibekanban.com/blog/shutdown) розмежовує закриття Bloop і заплановане продовження як open-source/спільнотного проєкту. Воно передбачало вимкнення віддалених сервісів через 30 днів і повідомляло, що локальні робочі простори продовжать працювати. Це не поточна перевірка сервісу й не доказ активного супроводу спільнотою. Посібник зберігає згенерований історичний каталог без змін і розміщує датовану примітку про життєвий цикл поруч із його записом control plane; жоден знімок upstream чи глобальну дату актуальності не переписано.

**Windows:** твердження Piebald про «єдиний нативний GUI для Windows» прибрано, оскільки Emdash і Escouade документують збірки для Windows. Жодного нового твердження про ексклюзивність не додано.

## Незалежна технічна перевірка

Окремий агент — технічний письменник — переглянув рішення щодо кандидатів від 17 жовтня та первинні джерела, не редагуючи посібник. Він зберіг оцінки 3/3/3/2 і поставив під сумнів початкове подання в чотирьох пунктах: обмежувальна ліцензія Superset і його гібридні поверхні; поточна ліцензія GPL Escouade та повноваження його MCP; змінена підтримка агентів/хмари в Conductor і застарілі сусідні порівняння; різниця між планом закриття Vibe Kanban і спостережуваним станом сервісу. Ці виправлення відображено вище. Перевірку допоміжної функції Escouade 17 жовтня виконано після цього рев'ю; про неї звітовано окремо від документальної перевірки агента.

Для додаткової перевірки 22 жовтня окремий агент — технічний письменник — звірив ревізію зі збереженими записами випробування та зафіксованим вихідним кодом. Він зберіг оцінку Escouade 3/5 і попросив чіткіше вказати авторство тестів, умову ввімкненого автопілота для планування та вужче сформулювати опис збережених записів. Ці уточнення внесено вище. Це був перегляд доказів, а не незалежний повторний запуск випробування застосунку.

27 жовтня окремий агент — технічний письменник — звірив доповнення щодо Orca з пов'язаною офіційною документацією. Він зберіг оцінку 3/5, підтвердив різницю між дозволами термінала й чату та обмеження спільного доступу до сесій Codex і попросив явно вказати джерело оцінки в індексі оцінок. Це була документальна перевірка, а не випробування Orca під час виконання.

## Що мають встановити подальші порівняльні випробування

Для кожного інструмента з короткого списку використовуйте той самий невеликий репозиторій і обмежене завдання. Фіксуйте, чи може користувач знайти робочу гілку, агента, що очікує введення, змінені файли, фактичну команду та результат тестів і наступну дію доставки. Включіть переривання/відновлення та випадок конфліктних змін. Для SSH/хмари перевірте, де розміщено код, облікові дані, hooks і процеси. Додаткова перевірка Escouade пройшла частину цього протоколу через MCP, зокрема переривання/відновлення, але не порівнювала еквівалентні запуски й не оцінювала візуальну зручність і конфлікти. Ці прогалини треба закрити, перш ніж стверджувати порівняльну перевагу.
