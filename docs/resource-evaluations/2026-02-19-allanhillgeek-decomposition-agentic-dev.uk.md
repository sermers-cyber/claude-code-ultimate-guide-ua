## 📄 Підсумок

Allan Hill описує продакшен-конвеєр агентної розробки, побудований на тезі, що дисципліна декомпозиції важливіша за витонченість AI:

- **Головна теза**: «AI - це легка частина. Декомпозиція - важка». Вузьке місце агентної розробки - розбиття роботи на зрозумілі для AI одиниці перед передаванням агентам, а не оптимізація промптів
- **Ключова одиниця роботи**: вертикальний зріз (Vertical Slice) - тонка наскрізна функція через усі шари стеку для однієї завершеної поведінки користувача (наприклад, «скидання пароля через email»); ідеальна для агентів, бо чіткі межі → PR, який можна переглянути
- **Триетапний конвеєр**: Phase 0 (PM-агенти створюють Small PRD з перевіркою якості за 6 вимірами) → Phase 1 (оркестратор декомпозує PRD на впорядковані незалежні зрізи, потрібне схвалення людиною в Slack) → Phase 2 (для кожного зрізу: сценарії Gherkin → ATDD → реалізація → PR)
- **Інфраструктура**: віртуальні машини Multipass (1 на тікет), диспетчер на Node.js, що опитує GitHub API кожні 60 с, детермінований CI (ESLint/Playwright/SonarQube) + AI CI (5 паралельних агентів рев'ю через GitHub Actions)
- **Визнані відкриті проблеми**: крихкість стану відновлення, баланс між правилом бойскаута і обсягом PR, налаштування хибнопозитивних спрацювань агентів рев'ю

## 🎯 Оцінка: 3/5 - доречно, цільова інтеграція

### Обґрунтування

**Аргументи за 3 (а не 4):**
- Конвеєр надто тісно прив'язаний до конкретного стеку (Multipass/GCP/Jira/Slack) → ~80% довелося б переписати для загального використання; низька повторна використовуваність
- Немає продакшен-метрик: даних про cycle time, частоту дефектів, пропускну здатність - це архітектурна оповідь, а не перевірений кейс
- Ключові концепції (вертикальні зрізи, декомпозиція насамперед) походять з Agile-літератури (Dan North, BDD, 2003; David Hussman) - це Agile, застосований до AI-агентів, а не нова теорія
- Відкриті проблеми не розв'язані (крихкість стану відновлення, налаштування хибнопозитивних спрацювань) - документувати нестабільні практики як еталон ризиковано
- Claude Code прямо не згадано; автор вживає «агенти» узагальнено - зв'язок із посібником непрямий

**Аргументи проти 5 (підтверджені прогалини реальні, але не критичні):**
- Прогалина «декомпозиція завдань» слушна, але частково закривається наявним `spec-first.md`
- Чекліст перевірки PRD за 6 вимірами можна виокремити, і він загальний - це найпрактичніший вміст статті
- ATDD справді відсутній у посібнику (охоплено лише TDD)

## 📍 Рекомендації

**Пріоритет: середній - інтегрувати 2 конкретні патерни, а не весь конвеєр**

### Інтеграція 1: `guide/workflows/spec-first.md` - додати розділ «Task Granularity»

Виокремити чекліст якості PRD за 6 вимірами як загальний чекліст перед написанням коду:

```markdown
## PRD Quality Checklist (before handing to agents)

Before assigning work to an agent, verify the task definition covers:

1. **Problem Clarity** — Is the problem statement unambiguous?
2. **Testable Acceptance Criteria** — Can completion be verified automatically?
3. **Scope Boundaries** — What is explicitly OUT of scope?
4. **Observable Done Definition** — What does "done" look like to an end user?
5. **Requirements Clarity** — No ambiguous terms, no implementation details
6. **Terminology Consistency** — Same terms used throughout (not "user" and "account" interchangeably)
```

**Розташування**: після розділу «The Pattern» у `spec-first.md` (~рядок 60)
**Зусилля**: низькі (20-30 рядків)

### Інтеграція 2: `guide/core/methodologies.md` - додати розділ про ATDD

ATDD справді відсутній. Додати розділ, що пояснює, як ATDD розширює TDD для агентних процесів:
- Сценарії Gherkin як контракт між наміром PM і реалізацією
- Спочатку пишемо Gherkin → агент пише тести, що падають → реалізація

**Розташування**: після розділу TDD у `guide/core/methodologies.md`
**Зусилля**: середні (50-80 рядків)

### Чого НЕ робити

❌ НЕ створювати `guide/workflows/agentic-pipeline.md` - конвеєр надто прив'язаний до стеку, проблеми автора не розв'язані, і це задокументувало б нестабільний патерн як авторитетний. Перш ніж створювати окремий посібник із робочого процесу, варто дочекатися другого незалежного джерела.
