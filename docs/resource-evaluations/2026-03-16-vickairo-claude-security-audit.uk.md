## Стислий підсумок

Однофайлова slash-команда `/security-audit` для Claude Code, яка проводить аудит вебзастосунку з 16 розділів із прив'язкою до OWASP та оцінкою /10. Репозиторію 18 днів. Посібник уже має повне покриття OWASP через `security-audit.md`, `security-check.md`, агента `security-auditor.md` і `security-hardening.md` на 41 КБ. Два патерни в цьому ресурсі справді кращі за наші: крок визначення контексту середовища (dev/staging/prod) перед аудитом і фактична перевірка проти хибних спрацювань перед повідомленням про секрети (перш ніж заявити про знахідку, перевіряє реальну історію git). Одна ділянка — справжня прогалина: аудит логіки платного доступу та білінгу. Усе інше перетинається.

## Підсумок змісту

- **16 розділів аудиту** з OWASP Top 10 (2021) + ідентифікаторами CWE: HTTP-заголовки, автентифікація, CSRF, відкрите перенаправлення, ін'єкції (SQL/XSS/команди), IDOR/контроль доступу, секрети й криптографія, платний доступ/білінг, вразливі залежності (npm audit + pip-audit), CORS, файли/конфігурація, WebSocket, SSRF, журналювання/моніторинг, цілісність даних, цілісність програмного забезпечення
- **Попередній крок з урахуванням контексту**: перед початком питає dev/staging/prod, щоб уникнути хибних спрацювань на прапорцях налагодження, CORS `*` і конфігураціях лише з HTTP, які нормальні для локальної розробки
- **Вимога фактичної перевірки**: перед повідомленням про будь-який секрет виконує `git log --all -p -- '*.env'` і перевіряє `.gitignore`; жодної знахідки без конкретного доказу
- **Оцінка /10** зі структурованою таблицею серйозності (CRITIQUE → HAUTE → MOYENNE → BASSE), file:line і рекомендованим виправленням із кодом
- **Застереження**: звіт містить явне нагадування, що перед будь-якими діями його має переглянути людина
- **258 рядків**, промпти французькою, MIT

## Оцінка

**Оцінка: 2/5** (маргінально)

Перетин із наявним змістом посібника значний. Більшість із 16 розділів уже покрито поєднанням `security-audit.md`, `security-auditor.md` і `security-hardening.md`. Команді 18 днів, у неї 60 зірок; для інструментів безпеки, де хибне відчуття захищеності гірше за відсутність інструмента, цього замало. Подача в дописі LinkedIn («vibe coding security») — влучний маркетинг, але технічної суті вона не змінює.

Два патерни, які можна винести (крок визначення контексту середовища + фактична перевірка історії git перед повідомленням про секрети), і прогалина щодо платного доступу/білінгу варті дій, але їх можна закрити покращенням нашої наявної команди без посилання на цей репозиторій.

## Рішення

**Оцінка: 2/5: не інтегрувати як зовнішній ресурс**

**Дія: непомітно перенести два патерни в наявні команди**

1. Додати попередній крок визначення контексту середовища до `examples/commands/security-audit.md` (питати dev/staging/prod перед фазою 1)
2. Посилити вимогу щодо хибних спрацювань у фазі 2 (вимагати `git log --all -p` перед повідомленням про секрети)
3. Додати розділ аудиту платного доступу/білінгу до `examples/agents/security-auditor.md`
4. Переглянути репозиторій через 3 місяці, якщо він набере 200+ зірок з активними issues/PR

**Без згадки в посібнику.** Ресурс не досягає порогу для посилання як ресурс спільноти з огляду на вік, мінімальний профіль автора та відсутність формального файлу LICENSE. Посібник уже має покриття безпеки, ширше за кількома вимірами (загрози, специфічні для Claude Code, безпека hooks, prompt injection). Перенести корисні патерни до себе чистіше, ніж відправляти читачів до незрілого репозиторію.

**Впевненість**: висока: файл команди переглянуто повністю, усі твердження перевірено за джерелом.
