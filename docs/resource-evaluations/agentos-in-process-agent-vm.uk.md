## Короткий зміст

agentOS: це віртуалізовані Linux VM, що працюють усередині вашого власного процесу Node; проєкт позиціонується як заміна хмарних пісочниць для виконання коду (E2B, Daytona, Modal) для агентних навантажень, яким не потрібне справжнє ядро Linux. `npm install @rivet-dev/agentos` дає вам VM без завантаження microVM, без завантаження контейнера й без облікового запису в провайдера.

Архітектура: довірений процес-sidecar на Rust володіє ядром (`crates/kernel`, `crates/vfs`, `crates/execution`) з багаторівневою віртуальною файловою системою (overlay плюс монтування S3, Google Drive, каталогів хоста), віртуальною таблицею процесів із `fork`/`exec`/`wait` і справжніми сигналами, таблицею сокетів, каналами, PTY, DNS. Жоден системний виклик гостя не звертається до хоста напряму: гість робить запит, ядро ухвалює рішення, ядро виконує. Недовірений виконавець запускає JavaScript гостя на нативному V8 з повним JIT (а не в інтерпретаторі), а скомпільовані інструменти працюють у WASM.

`software/` (42 пакети) компілює справжні upstream-інструменти Linux (GNU coreutils, grep, sed, gawk, curl, sqlite3, duckdb, vim, git, ripgrep) під `wasm32-wasip1` з sysroot, яким команда повністю володіє, з пропатченими Rust std і libc. Це не стандартний WASI, а Linux-у-WASM, де відсутні виклики POSIX реалізовано на рівні libc або як імпорти з хоста.

Головна відмінність: **прив'язки** (bindings) до хоста. Визначена на хості JS-функція зі схемою Zod з'являється всередині VM як команда оболонки (`/usr/local/bin/agentos-weather forecast --city Paris`). Агент викликає її, як будь-який інший CLI-інструмент. API-ключі ніколи не потрапляють у VM: агент бачить вхід і вихід, але ніколи не бачить секрету. Агенти (Pi, Claude Code, Codex, OpenCode) працюють як гостьові процеси, що спілкуються через ACP, з довготривалими сесіями (завершені події ACP потрапляють у SQLite, VM засинає після 15 хвилин неактивності й прокидається від з'єднання або cron; кожна VM є Rivet Actor). Шість областей дозволів (`fs`, `network`, `childProcess`, `process`, `env`, `binding`): мережу за замовчуванням заборонено, усе інше дозволено, бо вже віртуалізовано; відмова повертає `EACCES` ще до звернення до будь-якого ресурсу хоста.

## Бенчмарки постачальника: позначені, не перевірені

Виміряно командою на i7-12700KF, задокументовано в `benchmarks/`, дата 2026-03-30: 4,8 мс на створення VM за p50, приблизно 22 МБ для простої оболонки, приблизно 131 МБ для повноцінного агента програмування з MCP. Команда наводить для E2B/Daytona холодний старт 440 мс і мінімум 1 ГБ RAM. Це числа, повідомлені постачальником для однієї машини; ні ця оцінка, ні, наскільки вдалося з'ясувати, будь-яка третя сторона їх незалежно не відтворювала. Заголовне порівняння «холодний старт у 92 рази швидший» до того ж зіставляє дві різні речі: запуск ізолята V8 і завантаження повної Linux microVM. Обидва факти слід згадувати під час будь-якого цитування цих чисел.

## Застереження щодо чесності, і воно важливе

«VM» є маркетинговим вибором. У цьому стеку немає ні KVM, ні Firecracker, ні апаратної віртуалізації. Ізоляція повністю тримається на ізолятах V8 та пісочниці WASM, які забезпечує sidecar на Rust. Власна заявлена модель загроз проєкту розміщує межу безпеки між sidecar і виконавцем, а не на гіпервізорі. Цього достатньо для звичайного недовіреного коду агентів, але це суттєво слабше за апаратну ізоляцію проти вмотивованого зловмисника, що шукає спосіб вийти з V8. Свідомо поза межами: браузер, нативний бінарний файл x86, важкий dev-сервер, нативна компіляція. Для таких випадків сама документація радить запускати поверх справжню пісочницю.

## Місце щодо наявного покриття в посібнику

`guide/security/sandbox-isolation.md` §5, у назві якого є слова «cloud sandboxes» (Fly.io Sprites, Cloudflare Sandbox SDK, Vercel Sandboxes, E2B), перелічує чотирьох постачальників, і кожен виставляє рахунки через хмарного провайдера. agentOS є відсутнім контрприкладом: без провайдера, без облікового запису, працює всередині власного процесу Node на хості. Це справжня прогалина в розділі в його поточному вигляді, а не поступове доповнення наявного переліку.

Технічно він також іде глибше, ніж те, що зараз охоплює `sandbox-isolation.md` §7b («WebAssembly-based MCP Tool Sandboxing, Experimental»). Той розділ обмежено ізоляцією окремих викликів MCP-інструментів на рівні доступу до ОС (інструменти на кшталт Wassette). WASM-sysroot agentOS компілює суттєву частину користувацького простору Linux (42 пакети, зокрема git, ripgrep, sqlite3, duckdb) з власною libc, що за обсягом значно більше за надання можливостей окремим інструментам.

Одна незалежна, не пов'язана точка даних із власного дослідницького корпусу посібника на основі транскриптів YouTube (`yt-insights`, 2026-07-29): доповідь Rene Brandel «How we hacked YC Spring 2025 batch's AI agents» (DevCon Fall 2025, 2025-11-21) радить протилежне значення за замовчуванням: використовувати наявного провайдера пісочниць (E2B, Daytona), а не будувати власну. agentOS якраз і є тим проєктом, від створення якого ця порада зазвичай застерігає, від команди, яка, схоже, все одно його збудувала. Варто згадувати його як живий контрприклад, коли цитують цю пораду.

## Рішення

**Інтегрувати в `guide/security/sandbox-isolation.md` §5 як явний контрприклад «всередині процесу» до чотирьох хмарних постачальників розділу, плюс один новий рядок TL;DR.**

Подавати кожне число з бенчмарків як повідомлене постачальником, датоване й виміряне на одній машині, відповідно до висновків цієї оцінки. Прямо зазначати застереження «без гіпервізора», а не дозволяти слову «VM» натякати на апаратну ізоляцію, якої немає. Додати перехресне посилання на §7b, щоб читач, порівнюючи agentOS з ізоляцією MCP-інструментів у стилі Wassette, розумів, що вони розв'язують задачі, які перетинаються, але мають різний обсяг.

**Тригер для повторного перегляду**: позначений тегом реліз `1.0.0`, незалежно відтворений бенчмарк або другий мейнтейнер, частка якого перевищить 20% комітів за ковзний квартал.
