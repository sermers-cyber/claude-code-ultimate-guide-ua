# Три доповіді про рев'ю змін, написаних агентами (Litt, Gupta, Lopopolo)

**Переглянуто**: 2026-11-08. **Оцінки**: Litt 4/5, Gupta 3/5, Lopopolo 3/5. Ціль: запланована сторінка робочого процесу про зміни агентів, придатні для рев'ю; сама по собі ця оцінка нічого не інтегрує. Пов'язане: [Resisting Cognitive Surrender](knlb-cognitive-surrender.uk.md), [#077 Comprehension debt](077-comprehension-debt-ai-coding.uk.md).

Три доповіді відповідають на одне питання з різних позицій: як людині-рецензенту зберігати розуміння коду, який написав агент? Жодна з них не наводить контрольованого вимірювання якості рев'ю. Усі цитати нижче прочитано в опублікованих субтитрах 2026-11-08; помилки субтитрів залишено так, як їх транскрибовано.

## Litt: пояснювальний документ, який автор має пройти, перш ніж просити рев'ю (4/5)

- [84 с](https://www.youtube.com/watch?v=WkBPX-oDMnA&t=84): "there are lots of ways to understand. Be, you know, the days of just reading code line by line and that's not the only way anymore."
- [480 с](https://www.youtube.com/watch?v=WkBPX-oDMnA&t=480): skill доповідача `explainedif` створює документ-пояснення коду. "We start with background. We do not start with what happened in this change." Далі інтуїція перед деталями: "You can think of this sort of as like a well-written commit message, a little deeper."
- [577 с](https://www.youtube.com/watch?v=WkBPX-oDMnA&t=577): "literate code diffs. Give me prose. Explain it to me in the right order. Tell me before each file what's going on."
- [663 с](https://www.youtube.com/watch?v=WkBPX-oDMnA&t=663): тест із п'яти запитань наприкінці пояснення. "my rule is I don't send code to uh others on my team to review unless I can pass the quiz about what my agents wrote."

**Що це додає**: конкретну структуру документа (контекст, інтуїція, інтерактивні ілюстрації там, де вони корисні, впорядкований текст до кожного файлу, тест) і бар'єр для автора, а не для рецензента. **Обмеження**: одна демонстрація на проєкті відеогри; "shocking the number of times this has caught me" — це самозвіт без кількісних даних. Litt застерігає, що інтерактивність "can just be a crutch, and it can be kind of slop".

## Gupta: борг рев'ю та критерій «чому, а не що» (3/5)

- [288 с](https://www.youtube.com/watch?v=TJPInBjhE4Q&t=288): "Review debt. It's the accumulating gap between code your agent has produced and the code humans have actually reviewed, trusted, and understood."
- [684 с](https://www.youtube.com/watch?v=TJPInBjhE4Q&t=684): "Does the PR explain the why or just the what?" Приклад опису з малим розривом містить "the symptom, the diagnosis, the change, and the link to the benchmark".
- [636 с](https://www.youtube.com/watch?v=TJPInBjhE4Q&t=636): текстові сигнали авторства (футер co-authored, префікси гілок, фрази «generated by») перевірено на "three public repos, which comprised of 524 PRs". Найсильнішим сигналом був футер co-authored; у репозиторії C сигнал із найнижчим результатом "was 0% on the repo C. Even though it was done by coding agent", і доповідач додає, що репозиторій "might have blocked it". Який саме сигнал дав 0%, не сказано, а авторство агента є твердженням доповідача.

**Цифри з других рук, не перевірено**: на [83 с](https://www.youtube.com/watch?v=TJPInBjhE4Q&t=83) доповідач посилається на бенчмарк Faros AI 2026 (медіанний час рев'ю PR зріс на 441,5%, на 31% більше PR злито без рев'ю) і виводить, що PR із рев'ю займають у 5,4 раза більше часу ("if you calculate"); на [136 с](https://www.youtube.com/watch?v=TJPInBjhE4Q&t=136) цифра «на 16% більше PR на розробника» походить із "the Faros AI acceleration Whiplash benchmark" за квітень 2026. Жоден із цих звітів для цієї оцінки не відкривали; не використовуйте ці числа повторно, не прочитавши їх.

**Що це додає**: термін-конкурент для comprehension debt, практичний критерій для описів PR і описаний доповідачем випадок, коли один текстовий сигнал авторства дав 0% у репозиторії, який, можливо, пригнічував такі маркери. **Обмеження**: ваги оцінювання визначив доповідач; перевірка на 524 PR використовує неназвані репозиторії, і її неможливо відтворити.

## Lopopolo: дозвольте агенту відкладати зауваження рев'ю або заперечувати їм (3/5)

- [972 с](https://www.youtube.com/watch?v=CeOXx-XTYek&t=972): "on the code authoring agent side, we also gave it the flexibility to either defer or push back against review feedback". Коментар, який "could blow up the scope by a factor of two", — це "more of an FYI, right? File it to the backlog". "without the context that this is permissible, the coding agents are going to bias toward what they do, which is following instructions."
- [947 с](https://www.youtube.com/watch?v=CeOXx-XTYek&t=947): "the reviewer agents were instructed to bias toward merging the thing, to not surface anything greater than a P2 in priority"; це додали, бо агенти-автори й агенти-рецензенти "not converging".

**Що це додає**: аргумент на користь типізації зауважень рев'ю, щоб агент міг відрізнити запитання чи побіжну ремарку від обов'язкової зміни. **Обмеження**: середовище, де агенти рецензують і зливають код автономно; «P2» формально не визначали ("We didn't really define P2"), але агенти отримали "a framework within which to uh score its output", де P0 — найгірший рівень. У незмінному вигляді це не переноситься на merge request, які рецензують люди.

## Тут не перевірено

- Будь-який вплив цих практик на кількість знайдених дефектів, час рев'ю чи розуміння. Жодна доповідь його не вимірює.
- Цифри Faros AI та те, які саме три репозиторії використав Gupta.
- Чи опубліковано skill `explainedif`.

## Рішення

Використати три доповіді як практику з указанням авторства на запланованій сторінці: Litt — для структури пояснення та тесту як бар'єра на боці автора, Gupta — для критерію «чому, а не що» в описі та меж атрибуції через трейлери, Lopopolo — для типізованих зауважень із явним дозволом їх відкладати. Подавати кожну як практику однієї команди, а цифри Faros не включати в посібник, доки звіт не прочитано.
