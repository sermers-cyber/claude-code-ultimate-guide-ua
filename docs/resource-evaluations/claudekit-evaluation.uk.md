## Що таке ClaudeKit

ClaudeKit це npm-обгортка навколо Claude Code, яка:
- Дає 32 готові шаблони subagent
- Реалізує керування чекпоінтами через git stash
- Додає hooks конвеєра перевірок (typecheck, lint, test)
- Реалізує захист файлів через `.agentignore`
- Додає команди для spec-driven development
- Дає DSL codebase-map для статичної ін'єкції контексту
- Містить hook «thinking-level» (ключові слова megathink/ultrathink)

**Основна ідея**: автоматизувати поширені шаблони, які Claude Code підтримує, але не налаштовує за замовчуванням.

## Розбір оцінки

### Точність: 4/5

**Що правильно**:
- Git stash як механізм чекпоінтів ✅
- Шаблони hooks PreToolUse/PostToolUse ✅
- Концепція захисту файлів ✅
- Концепція конвеєра перевірок ✅

**Що неправильно**:
- Hook «thinking-level» **фактично застарів** з часу Opus 4.5 (thinking завжди ввімкнено, ключові слова декоративні)
- Codebase-map суперечить архітектурі Claude Code «Search Don't Index»

**Висновок**: здебільшого точні концепції, але 2 суттєві помилки.

### Глибина: 2/5

**Поверхові місця**:
- 32 subagent є однорядковими («You are a Rust expert»)
- Немає обговорення режимів збою hooks, продуктивності чи граничних випадків
- Немає пояснення, коли використовувати чекпоінти, а коли гілки
- Немає порад щодо асинхронних і синхронних hooks

**Висновок**: ширина замість глибини. Корисні шаблони, але поверхові пояснення.

### Практичність: 3/5

**Практично**:
- Воркфлоу чекпоінтів можна використовувати одразу ✅
- Hooks є робочими шаблонами ✅
- npm install спрощує налаштування ✅

**Непрактично**:
- Потребує глобального встановлення через npm (залежність)
- Ламається, якщо пакет закинуть або в ньому будуть несумісні зміни
- Codebase-map додає 9K+ статичного контексту (марнування token)

**Висновок**: добре для швидкого прототипування, ризиковано для довгострокового використання.

### Унікальність: 2/5

**Не унікальне**:
- Hooks задокументовано в нашому посібнику (розділ 7)
- Subagents охоплено в розділі 9.18
- Spec-driven dev є в methodologies.md

**Унікальне**:
- Автоматичний чекпоінт на подію Stop (у нас цього не було)
- Єдиний file-guard з виявленням обходу (у нас були частини, а не єдине ціле)
- Test-on-change з розумним виявленням (ми цього не автоматизували)

**Висновок**: 70% перетину з наявним посібником, 30% нової автоматизації.

### Підтримуваність: 2/5

**Занепокоєння**:
- Остання активність: січень 2026 (нещодавно, але сповільнюється?)
- Hook thinking-level уже застарів (свідчить про відставання в підтримці)
- npm-обгортка створює залежність від стороннього пакета
- Несумісні зміни в Claude Code можуть зламати ClaudeKit

**Висновок**: ризик підтримки для довгострокових проєктів.

### Прогалина 1: воркфлоу автоматичних чекпоінтів ⭐ ВИСОКИЙ ПРІОРИТЕТ

- Найменування: `claude-checkpoint-{branch}-{timestamp}`

**Чого нам бракувало**:
- Шаблону hook для автоматичного чекпоінту
- Структурованого воркфлоу: створити → експериментувати → відновити
- Порад щодо чекпоінтів проти гілок

**Що зроблено**:

- ✅ Додано розділ 2.4 "Checkpoint Pattern" (~40 рядків)

**Вплив**: дає змогу безпечно експериментувати без накладних витрат на гілки.

## Рекомендація: шаблони, а не пакет

**НЕ згадувати ClaudeKit у посібнику**. Причини:

1. **Ризик підтримки**: пакет може бути закинутий (остання активність: січень 2026)
2. **Застарілі функції**: hook thinking-level уже застарів (свідчить про хитку підтримку)
3. **Антипатерни**: codebase-map суперечить архітектурі Claude Code
4. **Прив'язка до залежності**: npm-пакет створює крихку залежність
5. **Ми кращі**: наша документація переживе застарівання пакета

**Натомість**: реалізувати 3 прогалини як **оригінальний вміст**, натхненний шаблонами (а не інструментом).
