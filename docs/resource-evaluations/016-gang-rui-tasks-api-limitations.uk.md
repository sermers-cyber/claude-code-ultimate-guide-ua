## Підсумок

Технічний аналіз обмежень видимості полів у Claude Code Tasks API (v2.1.16+), виявлених на практиці. Документує, що `TaskList` пропускає `description` і всі поля `metadata`, тому для доступу до повної інформації про завдання потрібні окремі виклики `TaskGet`.

**Ключова думка**: у Tasks API є недокументоване архітектурне обмеження: операції зі списком (`TaskList`) показують лише підмножину полів (`id`, `subject`, `status`, `owner`, `blockedBy`), тоді як операції з деталями (`TaskGet`) показують усі поля. Це створює патерн накладних витрат через багаторазові виклики, який не згадано в офіційній документації чи наявних матеріалах посібника.

## Оцінка: 5/5 (КРИТИЧНО)

### Обґрунтування оцінки

**Чому КРИТИЧНО (а не просто «висока цінність»)**:

1. **Ламає рекомендований воркфлоу**: посібник прямо рекомендує «TaskList → показати всі завдання» для відновлення сесії (MODE_Task_Management.md:37). Без видимості `description` цей воркфлоу непомітно ламається.

2. **Прихований множник витрат**: щоб переглянути 10 описів завдань, потрібно 1 TaskList + 10 TaskGet = **11-кратні накладні витрати API**. Для 20 завдань: 21-кратні. Це безпосередньо впливає на:
   - Вартість API (у 11 разів більше round-trips)
   - Затримку сесії (у 11 разів довше очікування)
   - Споживання токенів (метадані отримуються окремо)

3. **Ширше, ніж здається спочатку**: автор стверджує «Metadata is NEVER visible in any output» — це охоплює:
   - `description` (деталі реалізації)
   - `activeForm` (текст індикатора прогресу)
   - УСІ користувацькі поля `metadata` (пріоритет, оцінки, пов'язані файли, теги)

4. **Наслідки для безпеки**: без видимості полів у TaskList користувачі не можуть попередньо відфільтрувати чутливі завдання перед викликом TaskGet. Ризик випадково розкрити чутливі деталі реалізації, ділячись ID списків завдань.

5. **Калібрування довіри**: якщо користувачі самостійно виявлять це обмеження, дотримуючись воркфлоу з посібника, це зашкодить репутації посібника («Ultimate Guide не попередив мене про цю пастку»).

6. **Час**: виявлено через 2 дні після запуску Tasks API (v2.1.16: 2026-01-22), що вказує на тертя в ранніх користувачів. Швидка інтеграція цього зворотного зв'язку запобігає масовому розчаруванню.

## Ключові висновки

### 1. Обмеження видимості полів

**З допису (точна цитата)**:
> "TaskList shows ID, subject, status, and blockedBy but NO description"

**Технічна деталь зі скриншота**:
- TaskList виводить: `id`, `subject`, `status`, `owner`, `blockedBy`
- TaskList приховує: `description`, `activeForm`, `metadata` (усі користувацькі поля)
- TaskGet виводить: усі поля (повний об'єкт завдання)

### 2. Вплив на витрати

**Патерн накладних витрат через багаторазові виклики**:
```
Review N tasks with descriptions = 1 TaskList + N TaskGet calls
```

**Приклади**:
- 5 завдань: 6 викликів API (6x накладних)
- 10 завдань: 11 викликів (11x)
- 20 завдань: 21 виклик (21x)
- 50 завдань: 51 виклик (51x)

### 3. Рекомендований обхідний шлях

**З допису (точна цитата)**:
> "Use tasks for status tracking, not knowledge storage. For implementation plans that persist across sessions, stick with markdown files in your repo."

**Патерн**: гібридний підхід
- Tasks API → статус, залежності, координація
- Markdown-файли → детальні плани реалізації, нотатки щодо контексту

### 4. Рекомендації щодо сценаріїв використання

**Добрі сценарії** (з допису):
- Відстеження статусу між сесіями
- Відображення прогресу для користувача
- Розбиття роботи на позначені кроки

**Погані сценарії** (з допису):
- Зберігання планів реалізації (description не видно)
- Зберігання знань, що вимагає швидкого перегляду
- Фільтрація/сортування завдань на основі метаданих
