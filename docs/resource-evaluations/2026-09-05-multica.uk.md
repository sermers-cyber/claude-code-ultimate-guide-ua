## Вердикт

Multica закриває реальну прогалину в документації між термінальними мультиплексорами та середовищами виконання агентів програмування. Він дає людям і агентам спільний шар для issues, чату, розкладів і керування запусками, тоді як підключені комп'ютери виконують наявні CLI агентів програмування. У посібнику йому місце як суміжній керівній площині, а не як runtime harness, що володіє циклом «модель-інструмент».

Інтеграція має лишатися в межах доказів. Огляд вихідного коду підтверджує архітектуру й важливі межі дозволів, але під час цієї оцінки застосунок не запускали й жодного реального завдання агентом не виконали. Популярність на GitHub показує охоплення, а не надійність чи якість результату.

## Спостережувана архітектура

```text
Web, desktop, or mobile client
            |
            v
Multica server + PostgreSQL
issues, chat, agents, schedules, run records
            |
      WebSocket queue
            |
            v
Daemon on a connected computer
            |
worktree or working directory
            |
            v
Claude Code, Codex, Cursor, OpenCode, or another agent CLI
```

Сервер координує роботу й зберігає стан продукту. Демон виявляє встановлені середовища виконання, отримує роботу з черги, готує каталог репозиторію або worktree, викликає вибраний зовнішній CLI і повідомляє логи, прогрес, вартість і результати. Перевірений вихідний код заявляє 25 сімейств протоколів середовищ виконання плюс ідентичність OMP, разом 26 інтеграцій. Див. закріплені [посібник з архітектури](https://github.com/multica-ai/multica/blob/7a438bd5b8bf39afd54259a7eb0971390e50a8ef/apps/docs/content/docs/how-multica-works.mdx) і [довідник середовищ виконання](https://github.com/multica-ai/multica/blob/7a438bd5b8bf39afd54259a7eb0971390e50a8ef/apps/docs/content/docs/daemon-runtimes.mdx).

## Межі даних, дозволів і Git

Перевірена архітектура не завантажує автоматично локальні репозиторії й локальні файли облікових даних цілком. Але це не означає, що рівень координації вільний від даних: issues, коментарі, конфігурація агентів, розклади, контекст запусків, записи, логи, вартість і результати можуть зберігатися на сервері. Власні змінні середовища й конфігурація MCP теж можуть стати даними під керуванням сервера. Командам варто класифікувати цей вміст, перш ніж обирати хмарну топологію.

Демон працює з дозволами свого облікового запису операційної системи. Перевірений шлях для Claude використовує `bypassPermissions`, а шлях для Codex — `danger-full-access`, за винятком задокументованої опції нативної пісочниці Windows. Multica не додає загальної пісочниці файлової системи навколо цих CLI. Тому його [модель безпеки](https://github.com/multica-ai/multica/blob/7a438bd5b8bf39afd54259a7eb0971390e50a8ef/docs/guide/security-model.mdx) слід розуміти як межу облікового запису виконання, а не як доказ ізоляції репозиторію.

Стан `in_review` у продукті є метаданими воркфлоу. Він не налаштовує захист гілок, обов'язкове рев'ю чи політику злиття на Git-хостингу. Агент може використовувати облікові дані Git, доступні обліковому запису демона. Точкою примусового застосування правил лишаються правила на боці репозиторію.

## Межа ліцензії

[`LICENSE`](https://github.com/multica-ai/multica/blob/7a438bd5b8bf39afd54259a7eb0971390e50a8ef/LICENSE) починається з умов Apache 2.0, але додає обмеження щодо хмарних сервісів, вбудовування, брендингу й атрибуції. Тому ця оцінка описує Multica як source-available з обмежувальною ліцензією, а не як звичайний відкритий код за OSI. Це класифікація для посібника, а не юридична порада.

## Сильні сторони

- Чіткий поділ між командною координацією та локальним виконанням.
- Широкий набір адаптерів для наявних CLI агентів програмування.
- Поняття issues, чату, розкладів, повторних спроб та історії запусків в одній керівній площині.
- Вихідний код сервера, демона, вебзастосунку, десктопного й мобільного клієнтів доступний для перевірки.

## Обмеження та умова впровадження

- Під час цього огляду застосунок локально не запускали й наскрізного завдання реальним агентом не виконували.
- Немає незалежних доказів надійності, стану безпеки чи приросту продуктивності в продакшені.
- Обліковий запис демона є межею виконання з високим рівнем довіри.
- Хмарне використання потребує свідомої перевірки класифікації та зберігання даних.
- Обмежувальну ліцензію треба перевірити для хмарного використання, вбудовування чи поширення.

Перед впровадженням проведіть пілот саме тієї хмарної чи власної топології, яку плануєте, з непродакшеновими обліковими даними, захистом гілок, одним одноразовим репозиторієм, обмеженим завданням і відпрацьованим сценарієм відновлення після від'єднання демона.
