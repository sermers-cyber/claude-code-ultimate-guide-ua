## Стислий підсумок

**Підсумкова оцінка**: **4/5 (ВИСОКА ЦІННІСТЬ)**

Compound Engineering — перевірена в продакшені інженерна філософія від Every.to, реалізована як повноцінний plugin для Claude Code: 29 спеціалізованих агентів для рев'ю, 22 команди робочих процесів, 20 предметних skills. Філософія формалізує цикл Plan → Work → Review → Compound із явним розподілом 50/50 між роботою над фічами та покращенням системи. Кілька патернів відсутні в посібнику, і їх можна перенести без встановлення plugin: Named Perspective Agents (DHH, Kent Beck як скорочення для набору поглядів), Swarm Mode (ситуативні паралельні рецензенти), Skill Quality Gates (явний чекліст, що виходить за межі frontmatter) і робочий процес Brainstorm-before-planning. Мультиінструментний AI-конвертер (синтаксис Claude → GPT-4 → Gemini) інноваційний, але виходить за межі цього посібника.

## Огляд ресурсу

### Структура plugin

| Компонент | Кількість | Приклади |
|-----------|-------|---------|
| Агенти | 29 | DHH reviewer, Kent Beck reviewer, swarm orchestrator |
| Команди | 22 | /workflows:plan, /workflows:work, /workflows:review, /workflows:compound |
| Skills | 20 | security, performance, architecture, accessibility |
| Структура каталогів | 4 | docs/brainstorms/, docs/plans/, docs/solutions/, todos/ |

### Основні концепції

- **Цикл Plan → Work → Review → Compound**: 40% планування, 10% реалізація, 40% рев'ю, 10% compound (закріплення знань)
- **Правило 50/50**: половина часу на створення фіч, половина на покращення системи
- **Named Perspective Agents**: агенти, названі на честь відомих інженерів (DHH, Kent Beck), як компактне скорочення для набору поглядів
- **Swarm Mode**: паралельне рев'ю спеціалістами на вимогу, без заздалегідь визначеної структури команди
- **Brainstorm-before-planning**: перед створенням плану перевірити наявні брейнштормінги, щоб не розв'язувати вже розв'язані проблеми
- **Документація як пам'ять**: структурована ієрархія каталогів замінює хаотичне розростання CLAUDE.md

### Контекст продакшену

Compound Engineering працює в продакшені в Every.to на Cora — їхньому AI-нативному продукті для нотаток і знань. Kieran Klaassen — один із перших інженерів компанії. Описані патерни походять із живої кодової бази, а не з теоретичного фреймворку.

## Оцінювання

### Оцінка: 4/5 (ВИСОКА ЦІННІСТЬ)

**Обґрунтування**:

1. **Надійне джерело**: Every.to — серйозна AI-нативна компанія. Kieran Klaassen — практик, а не блогер. Plugin має відкритий код і містить реальних агентів із реальними промптами, а не маркетинговий текст.

2. **Переносні патерни**: Named Perspective Agents, Swarm Mode, Skill Quality Gates і процес Brainstorm-before-planning працюють із будь-яким налаштуванням Claude Code. Жодної залежності від самого plugin.

3. **Реальна реалізація**: 29 агентів — це 29 справжніх системних промптів, які можна прочитати й повчитися на них. Більшість матеріалів про Claude Code описують патерни, не показуючи реальних реалізацій. Тут показано код.

4. **Нові патерни**: Named Perspective Agents і Swarm Mode ніде не задокументовані в поточному посібнику. Обидва можна застосувати одразу, і вони відрізняються від наявних патернів (агенти з фокусом на зоні відповідальності, команди агентів).

5. **Глибина філософії**: правило розподілу 50/50 і драбина впровадження (етапи 0-5) — конкретні інструменти ухвалення рішень, а не розмиті рекомендації.

**Чому не 5/5**:

- Немає кількісних метрик: жодного «покращення на X%» у швидкості постачання, частці виявлених на рев'ю проблем чи рівні дефектів. Усі твердження якісні.
- Named Perspective Agents ґрунтуються на поглядах: чи надійно агент DHH відтворює принцип «товсті моделі, тонкі контролери», залежить від навчання Claude, яке змінюється від версії до версії.
- Кілька агентів короткі (<20 рядків) і можуть бути не ефективнішими за добре складений вбудований промпт.
- Мультиінструментний AI-конвертер — найоригінальніша функція, але вона повністю виходить за межі цього посібника.

### Застереження

- **Іменовані персони ризикують дрейфувати**: погляди DHH змінюються. Статичний «агент DHH» може застаріти або розійтися з його поточними поглядами, коли зміняться навчальні дані Claude.
- **Swarm і Teams**: Swarm Mode (ситуативний) і Agent Teams (постійні, скоординовані) розв'язують різні задачі. Їх часто плутають.
- **Встановлювати plugin не обов'язково**: встановлення додає 29 агентів + 22 команди в кожен проєкт, що може бути надмірним. Патерни працюють і без нього.

## Переносні патерни

### 1. Named perspective agents

Замість загальних агентів-«рецензентів» називайте агентів на честь інженерів, чиї погляди ви хочете представити:

```markdown
---
name: dhh-reviewer
description: Review code from DHH's perspective (Rails conventions, fat models, thin controllers, pragmatic REST)
---
```

Ім'я працює як стиснений промпт: воно пакує впізнаваний набір поглядів в один token замість того, щоб розписувати їх. Працює для: DHH (Rails, REST), Kent Beck (TDD, простота), Martin Fowler (рефакторинг, патерни).

**Обмеження**: працює лише для інженерів, на поглядах яких навчався Claude і чиї погляди відповідають чіткому, стабільному стилю.

### 2. Swarm mode

Паралельне рев'ю кількома спеціалістами на вимогу, без заздалегідь визначеної координації:

```bash
/slfg                      # Запустити swarm
/workflows:review --swarm  # Запустити всіх релевантних рецензентів паралельно
```

На відміну від Agent Teams (зі сталою структурою «лідер + учасники»), swarm не має стану: кожен рецензент отримує PR/diff незалежно, повідомляє знахідки, а людина зводить їх докупи. Найкраще підходить для: фінального рев'ю перед злиттям, незнайомих ділянок кодової бази, ситуацій, де ретельність важливіша за координацію.

### 3. Skill quality gates

Окрім валідації frontmatter, Compound Engineering визначає явні критерії якості змісту skills:

- Frontmatter має містити name, description, allowed-tools
- Розділ «When to Apply» обов'язковий (а не опціональний)
- Методологія має бути структурованою (кроки, а не абзаци)
- Жодних TODO чи тексту-заповнювача
- allowed-tools обмежено мінімально необхідним
- Формат виводу має бути задокументовано
- Жодного AskUserQuestion у кросплатформних skills

### 4. Робочий процес Brainstorm-before-planning

Перед створенням плану перевірте, чи вже існує брейнштормінг:

```
docs/brainstorms/    <- Документи-роздуми (дослідження проблеми)
docs/plans/          <- Активні плани реалізації
docs/solutions/      <- Розв'язані проблеми з контекстом
todos/               <- Відстеження задач
```

Інструкція для агента: «Before creating a plan for X, check docs/brainstorms/ for existing thinking on this topic.» (Перш ніж створювати план для X, перевір docs/brainstorms/ на наявні роздуми з цієї теми.)
