## Підсумок змісту

Executor це шар інтеграції між ШІ-агентами і зовнішніми API: ліцензія MIT, монорепозиторій на Bun + Turborepo, версія `1.4.0-beta.0`. Ідея: оголосити інтеграцію один раз (автентифікацію і правила API), і кожен MCP-сумісний агент (Claude Code, Cursor, ChatGPT) користується тим самим каталогом, замість того щоб кожен мав власну копію тих самих облікових даних і підключень інструментів.

Чотири концепції в порядку залежностей:

1. **Integration** (специфікація: OpenAPI, GraphQL, наявний MCP-сервер, Google Discovery), проіндексована в каталог інструментів.
2. **Connection**, налаштований автентифікований екземпляр інтеграції, ідентифікований як `(scope, integration, name)`. Одна інтеграція може мати багато з'єднань (дві організації GitHub, `work` і `perso`).
3. **Policy**, для кожного інструмента одне з `allowed` / `require_approval` / `blocked`, зі значеннями за замовчуванням, виведеними зі специфікації (запис не трактується як читання).
4. **MCP exposure**, один ендпоінт (`/mcp?toolkit=...`); агенти бачать увесь каталог через метаінструменти (`search` + `describe` + `execute`), а не завантажують заздалегідь кожну схему.

Механізм, який варто сприйняти серйозно: Connection ніколи не зберігає сирих облікових даних, лише `SecretRef` (`op://`, `keychain://`, `env://`, `vault://`), який провайдер розв'язує в момент виклику за проксі інструментів. `vision.md` стверджує, що лазівки немає: `SecretRef` ніколи не з'являється у схемі вводу/виводу інструмента чи в будь-якій відповіді MCP. Виконання можна призупиняти: виклик, заблокований через відсутню автентифікацію чи очікуване схвалення, повертає призупинений Run, який відновлюють через `executor resume --execution-id exec_123`.

Чотири способи запуску з однаковою функціональністю: Executor Cloud (хостинг), CLI + демон (`apps/cli` + `apps/local`), застосунок для робочого столу, власний хостинг (Docker або Cloudflare Worker).

## Ключовий механізм, перевірений у коді

Твердження про `SecretRef` найважливіше, бо на ньому тримається вся цінність. `packages/core/sdk/src/` містить `connection.ts`, `integration.ts` і повну поверхню OAuth (`oauth-flow.ts`, `oauth-client.ts`, `oauth-discovery.ts`, `oauth-callback-state.ts`, `oauth-gc.ts`, `migration-oauth-metadata.ts`). `packages/hosts/mcp/src/tool-server.ts` (41.9 KB, з тестовим файлом на 63.3 KB, найбільше співвідношення тестів до коду серед усіх перевірених файлів) є власне поверхнею MCP. Plugins бекендів секретів існують окремо для кожного провайдера: `packages/plugins/onepassword/`, `keychain/`, `workos-vault/`, `encrypted-secrets/`, `file-secrets/`.

Ця оцінка не відстежила кожне місце виклику, що торкається `SecretRef`, щоб підтвердити, що він ніколи не потрапляє в серіалізовану відповідь; для цього довелося б запустити набір тестів і інструментувати шлях проксі, що виходило за межі проходу лише з читанням коду. Підтверджено: шаблон архітектурно послідовний (окремі plugins бекендів секретів, окремий модуль OAuth, великий тестовий файл для поверхні MCP), а `vision.md` явно формулює інваріант як правило дизайну, а не як деталь реалізації, виявлену заднім числом. Сприймайте твердження «ніколи не доходить до агента» як добре підкріплене архітектурно, але не доведене незалежно цим проходом.

Виміряно на `main` на коміті `2f09b13e0` (2026-07-28).

**Bus factor 1.** Ритм упав на 76% від квітневого піку до липня. Ззовні проєкту однаково правдоподібні два прочитання, і жодне не можна з'ясувати з репозиторію: зміцнення перед стабільним релізом 1.0 або перемикання уваги засновника на Executor Cloud і вихід на ринок. Другий супровідник чи тег `1.0.0` розв'язали б це; поки немає ні того, ні іншого.

**Прив'язка до Effect.** SDK надає API на основі Promise (`@executor-js/sdk/promise`) поряд із нативним для Effect, тож для використання не треба вивчати Effect. А от для внеску чи глибшого обгортання, ніж задокументована поверхня Promise, треба: 35% файлів вихідного коду імпортують `effect` напряму, а `AGENTS.md` вимагає Effect Vitest для всіх тестів (`bun test` явно заборонено). Продакшен-користувач, який повідомив, що використовує його як ядро MCP для зовнішніх harness агентів, незалежно вказав саме на цю напругу: "velocity is very high, something to constantly stay on top of, especially if you run wrappers around it."

## Конфігурація агентної інженерії в самому репозиторії

Окремо від продукту варто назвати власну конфігурацію репозиторію для роботи з ШІ-агентами програмування, бо вона узагальнюється за межі цієї кодової бази. Співіснують три каталоги skills: `.claude/skills/` (3 skills), `.agents/skills/` і `.skills/` (6, зокрема `effect-atom-optimistic-updates`, `warden-security-review`, `effect-http-testing`, `cli-release`, `effect-use-pattern`, `graphite`), плюс `.codex/environments/`. `AGENTS.md` є контрактом для контриб'юторів на 58 рядків із жорсткими правилами (обов'язковий Effect Vitest, заборонений `bun test`, e2e запускати останніми й ощадливо, ніколи повторно не вендорити пакет `@executor-js/emulate`). Три файли пам'яті агента свідомо внесено до gitignore: `MISTAKES.md`, `DESIRES.md`, `LEARNINGS.md`, це приватна робоча пам'ять, а не спільна пам'ять команди. `warden.toml` обмежує сканування безпеки warden-skills від Sentry за шляхами. Розділ "References" у README називає кодові бази, які подавали агентові як зразки: FumaDB, Effect, OpenCode, OpenClaw, Emdash, Pi.

Це розглядається окремо від оцінки продукту, бо зберігає цінність незалежно від того, чи досягне успіху сам Executor. Де опиниться кожна частина, див. у рішенні щодо інтеграції в посібник нижче.

## Місце відносно наявного охоплення в посібнику

`guide/security/enterprise-governance.md` §3 ("MCP Governance Workflow") уже вручну документує саме цю категорію: воркфлоу схвалення (§3.1), реєстр YAML із полями `risk`/`restrictions` для кожного інструмента (§3.2), hook, що його застосовує (§3.3). Executor є продуктизованою версією того самого шаблону, а не новою категорією: його чотири концепції лягають на поля цього реєстру (Integration ≈ `source` + `config` запису реєстру, Connection ≈ іменований автентифікований екземпляр цього запису, Policy ≈ поле `risk` реєстру, узагальнене до allow/approval/block для кожного інструмента, MCP exposure ≈ один ендпоінт замість одного запису на сервер).

Таблиця "Tooling in this space" у `guide/ecosystem/mcp-vs-cli.md` (RTK, mcporter, mcp2cli, Klavis AI/Strata, Arcade.dev) для нього не підходить: спільна вісь цієї таблиці це вартість token, а Executor не конкурує за вартістю token. Його вісь це управління доступом, найближче до боку OAuth/каталогу в Klavis, а не до трюку з усуненням схем у mcp2cli.

## Рішення

**Інтегрувати як перехресне посилання в `enterprise-governance.md` §3, подане як порівняння, а не як рекомендація замінити. Не створювати окремої сторінки про управління інтеграціями.**

Реєстр YAML з `enterprise-governance.md` §3.2 команди, що читають посібник, активно копіюють у власний `.claude/mcp-registry.yaml`. Новий підрозділ у дусі «використовуйте натомість Executor» підштовхнув би читачів до бета-продукту з bus factor один для воркфлоу, який посібник зараз документує як YAML-файл без залежностей плюс hook. Підрозділ має звучати як «ось як зрештою виглядає автоматизація цього шаблону реєстру вручну у вигляді продукту», з прямо, а не натяком, висловленим застереженням про стадію до 1.0 і bus factor 1.

Конфігурація агентної інженерії (три каталоги skills, файли пам'яті агента в gitignore) реальна і придатна до повторного використання незалежно від долі самого Executor. Її задокументовано окремо: `MISTAKES.md`/`DESIRES.md`/`LEARNINGS.md` у gitignore як четверту точку даних у порівнянні файлової пам'яті в `guide/core/memory-systems.md` §3.7, а три співіснуючі каталоги skills як новий запис шаблону в `guide/core/skill-design-patterns.md`. `warden.toml` і список "References" з README у цей прохід не включено: жоден наявний розділ не підходить для них чисто, а нав'язувати розділ на підставі одного репозиторію передчасно.

**Тригер повторного перегляду**: тегований реліз `1.0.0` або другий супровідник, що перевищить 20% комітів за ковзний квартал, що настане раніше.
