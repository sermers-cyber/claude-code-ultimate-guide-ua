**Дата**: 2026-03-17
**Оцінювач**: Claude Sonnet 4.6
**URL ресурсу**: https://circleci.com/blog/mcp-vs-cli/
**Тип ресурсу**: технічний допис у блозі
**Автор**: Jacob Schmitt (CircleCI)
**Опубліковано**: 2026-03-11

---

## Стислий підсумок

Jacob Schmitt пропонує фреймворк для вибору між MCP-серверами та CLI-інструментами в агентних робочих процесах, поклавши в основу розрізнення внутрішнього та зовнішнього циклів (inner loop / outer loop). Допис містить бенчмарк автоматизації браузера (CLI на 33% ефективніший щодо token, 77 проти 60 за виконанням задач), посібник для ухвалення рішення з 6 питань і приклад гібридної архітектури з власних інструментів CircleCI. Фреймворк узгоджується з тим, як посібник уже позиціонує RTK і гібридний підхід CLI+MCP. Допис додає корисне зовнішнє підтвердження й чіткіший словник для ухвалення рішень, ніж наявний зараз у посібнику, але не відкриває нового технічного підґрунтя для досвідчених користувачів Claude Code.

---

## Підсумок змісту

- **Головна теза**: внутрішній цикл (часті, локальні ітерації розробки з низькою затримкою) сприяє CLI; зовнішній цикл (спільні системи, CI/CD, міжкомандна інфраструктура) сприяє MCP
- **Бенчмарк автоматизації браузера**: один тест, що порівнює агентну автоматизацію браузера через CLI і через MCP. CLI: 77% виконаних задач, на 33% краща ефективність щодо token. MCP: 60% виконаних задач. Методологію не розкрито (один тест, внутрішній для CircleCI)
- **Фреймворк ухвалення рішення з 6 питань**:
  1. Хто володіє циклом зворотного зв'язку? (лише розробник → CLI; кілька агентів/команда → MCP)
  2. Як часто змінюється схема? (часто → накладні витрати CLI нижчі; стабільна → інвестиція в MCP виправдана)
  3. Чи потребує інструмент автентифікації/керування секретами під час виконання? (так → MCP; ні → CLI простіший)
  4. Чи потрібен структурований вивід, який споживатиме інший агент? (так → MCP; ні → CLI)
  5. Це інструмент для команди чи для однієї людини? (команда → стандартизація MCP; одна людина → гнучкість CLI)
  6. Який у вас бюджет контексту? (обмежений → CLI; достатній → MCP прийнятний)
- **Гібридна модель CircleCI**: Chunk CLI (локальні операції з файлами) + Local CLI (оболонка + git) + CircleCI MCP Server (доступ до системи CI/CD); кожен рівень зіставлено з внутрішнім/зовнішнім циклом
- **НЕ згадує**: Claude Code, Anthropic, RTK чи будь-який конкретний інструмент поза стеком CircleCI

## Оцінка якості

**Сильні сторони**:
- Розрізнення внутрішнього / зовнішнього циклу добре усталене в літературі про продуктивність розробників (відокремлення швидких локальних ітерацій від операцій зі спільними системами) і чисто застосовується до вибору між MCP і CLI
- Фреймворк із 6 питань практичний і прямо відповідає реальним рішенням щодо робочих процесів
- Власна гібридна архітектура CircleCI — переконливий розібраний приклад
- Опубліковано в популярному інженерному блозі, тож практики на нього посилатимуться

**Слабкі сторони**:
- Бенчмарк автоматизації браузера — один внутрішній тест без розкриття методології. Різниця 77% проти 60% у виконанні задач може відображати якість реалізації не меншою мірою, ніж архітектуру CLI чи MCP
- Допис не розрізняє різні хости LLM. Інтеграція MCP у Claude Code має інші характеристики накладних витрат, ніж, скажімо, власний агент на чистому API
- Рекомендація MCP-сервера CircleCI наприкінці — це вендорський контент (м'який, але присутній)
- Не розглядає вартість (ціну token за виклик): лише кількість token, а не долари

---

## Оцінка

**Оцінка: 3/5** (помірна: посилатися як на зовнішнє підтвердження)

Добротний фреймворк із надійного джерела. Словник внутрішнього / зовнішнього циклу варто запозичити. Дані бенчмарку надто скупі, щоб цитувати їх як доказ, але корисні як сигнал напрямку. Фреймворк ухвалення рішення був би вагомим доповненням до розділу посібника про оптимізацію витрат або про MCP: або як натхнення для нового розділу, або як зовнішнє посилання.

---

## Перевірка

**Заперечення**: «Бенчмарк методологічно слабкий, а CircleCI продає свій MCP-сервер. Це маркетинг, вбраний в інженерію. Оцінка має бути 2/5.»

**Відповідь**: маркетинговий аспект реальний, але м'який: основний зміст допису (фреймворк ухвалення рішення, модель внутрішнього/зовнішнього циклу) стоїть незалежно від рекламування продукту CircleCI MCP наприкінці. Бенчмарк тут не цитується як доказ; його зазначено як сигнал напрямку із застереженням, що методологію не розкрито. Головна цінність — фреймворк ухвалення рішення та словник, і вони чисті. 3/5 лишається. Якщо посібник посилатиметься на цей ресурс, то на фреймворк, а не на цифри бенчмарку.

## Рішення

**Оцінка: 3/5: посилатися як на зовнішнє підтвердження; запозичити словник внутрішнього / зовнішнього циклу.**

**Негайні дії**:
1. Розглянути додавання подачі «внутрішній цикл / зовнішній цикл» до розділу посібника про компроміси між CLI і MCP: це чіткіша ментальна модель, ніж та, якою посібник користується зараз
2. Фреймворк ухвалення рішення з 6 питань — гарний шаблон; версія, специфічна для Claude Code, буде ціннішою, ніж цитування оригіналу (аудиторії посібника потрібні поради саме щодо Claude Code, а не загальні поради щодо агентних фреймворків)

**Чого НЕ робити**: не цитувати цифри бенчмарку (77% проти 60%), не вказавши, що методологію не розкрито, а тест внутрішній для CircleCI.

**Розміщення**: примітка або «See also» у розділі `guide/core/` про оптимізацію витрат, або в розділі про екосистему MCP там, де обговорюється, коли використовувати патерни MCP, а коли CLI.

**Впевненість**: висока щодо якості фреймворку. Низька щодо надійності бенчмарку.
