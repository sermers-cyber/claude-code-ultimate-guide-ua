### Спершу трієж парку

Аудит тридцяти репозиторіїв по одному марнує перші двадцять запусків на відкриття того самого. Спершу пройдіться по всьому парку, ранжуйте за ступенем вразливості, а потім запускайте повний prompt лише на тих, що позначила розвідка. Вкажіть у `ROOTS` каталоги, у яких справді лежать ваші репозиторії.

```bash
ROOTS="$HOME/Sites $HOME/dev $HOME/work"   # adjust
find $ROOTS -maxdepth 5 -name node_modules -prune -o -name .worktrees -prune \
     -o -path "*/.claude/settings*.json" -print 2>/dev/null | sort -u > /tmp/cc-settings.txt
wc -l < /tmp/cc-settings.txt

python3 - <<'PY'
import json,re,os
BLANK=re.compile(r'^Bash\((bash|sh|zsh|fish|dash|python3?|perl|ruby|node|deno|bun|npm|pnpm|yarn|npx|bunx|make|just|env|xargs|eval|uv|poetry|docker run|docker exec)\s*(-[ce])?\s*(:\*|\*|\))')
files=[l.strip() for l in open('/tmp/cc-settings.txt') if l.strip()]
rows=[]; broken=[]; totals=[0,0,0,0]
for p in files:
    try: d=json.load(open(p))
    except Exception as e: broken.append((p,str(e)[:60])); continue
    perm=d.get("permissions",{})
    a,dn,ak=perm.get("allow",[]),perm.get("deny",[]),perm.get("ask",[])
    sb="sandbox" in d
    totals[0]+=len(a); totals[1]+=len(dn); totals[2]+=len(ak); totals[3]+=sb
    hits=sorted({r for r in a if BLANK.match(r)})
    tracked = p.endswith("settings.json")
    if hits or not dn:
        rows.append((len(hits), tracked, len(a), len(dn), len(ak), sb, p, hits))
print(f"files={len(files)} allow={totals[0]} deny={totals[1]} ask={totals[2]} sandbox={totals[3]}")
for p,e in broken: print("UNPARSEABLE", p, e)
for n,tracked,a,dn,ak,sb,p,hits in sorted(rows, reverse=True):
    tag = "TRACKED" if tracked else "local  "
    print(f"[{tag}] blank={n:2d} allow={a:5d} deny={dn:3d} ask={ak} sandbox={'y' if sb else 'n'}  {p.replace(os.path.expanduser('~'),'~')}")
    if hits: print("          " + "  ".join(hits))
PY
```

Читайте вивід у такому порядку. Безумовний дозвіл у **відстежуваному** `settings.json` важить більше за все інше, бо потрапляє до кожного, хто клонує репозиторій. Далі йде безумовний дозвіл у `settings.local.json`: один рядок на кожен постраждалий репозиторій. Репозиторій без жодного правила `deny` і без sandbox не має меж, окрім вбудованих типових, хоч би яка була кількість allow. Висока кількість allow без безумовного дозволу є шумом, а не ризиком, і її слід планувати останньою.

Потім запустіть повний prompt на двох-трьох репозиторіях, де відповідь справді неочевидна, і застосуйте виправлення для всього парку з плану, а не перевіряйте кожен заново.

## Базові факти, які ти маєш використовувати

Матчер дозволів Claude Code має конкретну семантику. Більшість поганих аудитів виникає з її вгадування. Використовуй наведене нижче, що є задокументованою поведінкою, а не міркуй лише з тексту правила.

**Форма правила.** Правила мають вигляд `Tool` або `Tool(specifier)`. Голе `Bash` і `Bash(*)` збігаються з кожною командою. Підстановки працюють у будь-якій позиції, включно з серединою: `Bash(git * main)` збігається з `git push origin main`. Кінцевий ` *` забезпечує межу слова, тож `Bash(ls *)` збігається з `ls -la`, але не з `lsof`, тоді як `Bash(ls*)` збігається з обома. Суфікс `:*` дорівнює кінцевому ` *` і розпізнається **лише в кінці шаблону**; у `Bash(git:* push)` двокрапка є літеральним символом, і правило не збігається ні з чим.

**Складені команди.** Розпізнавані розділювачі: `&&`, `||`, `;`, `|`, `|&`, `&` та нові рядки. Правило має збігатися з кожною підкомандою незалежно, тому `Bash(safe *)` не авторизує `safe && rm -rf .`.

**Обгортки, що знімаються перед зіставленням.** `timeout`, `time`, `nice`, `nohup`, `stdbuf`, вбудовані `command` і `builtin`, `noglob` із zsh та голий `xargs` без прапорців. Тому правило, написане для внутрішньої команди, охоплює й обгорнуту форму.

**Обгортки, що НЕ знімаються, і саме тут виникають діри.** `npx`, `docker exec`, `devbox run`, `mise exec`, `direnv exec` та кожен інтерпретатор, викликаний із `-c` або `-e`. Вони виконують свої аргументи як команду, тому правило на кшталт `Bash(devbox run *)` авторизує `devbox run rm -rf .`, а `Bash(bash *)` авторизує `bash -c '<будь-що>'`. Це найважливіший механізм у цьому аудиті.

**Префікси змінних середовища.** Правило `allow` не збігається після присвоєння змінної поза відомим безпечним набором. Правило `deny` або `ask` збігається після будь-якого ведучого присвоєння, тож `Bash(rm *)` у deny усе одно ловить `FOO=bar rm -rf tmp/`.

**Exec-обгортки, що завжди запитують** і не можуть бути схвалені за префіксом: `watch`, `setsid`, `ionice`, `flock` та `find` із `-exec` або `-delete`.

**Вбудований набір лише для читання**: ніколи не запитується в жодному режимі й не налаштовується: `ls`, `cat`, `echo`, `pwd`, `head`, `tail`, `grep`, `find`, `wc`, `which`, `diff`, `stat`, `du`, `cd` та форми `git` лише для читання. Правило `allow` для будь-якого з них є баластом, а не ризиком.

**Захищені шляхи**: ніколи не схвалюються автоматично поза `bypassPermissions` і **не** можуть бути попередньо схвалені правилом `allow` у налаштуваннях: `.git`, `.config/git`, `.vscode`, `.idea`, `.husky`, `.cargo`, `.devcontainer`, `.yarn`, `.mvn`, `.claude` (крім `.claude/worktrees`), а також rc-файли оболонки, `.npmrc`, `.gitconfig`, `.mcp.json`, `.claude.json` та подібні. Перевірка безпеки виконується до оцінювання налаштувань.

**Порядок у режимі auto.** Дії, що збігаються з правилом `allow`, `ask` або `deny`, розв'язуються негайно, **до** запуску класифікатора. Під час входу в режим auto Claude Code скидає лише широкі дозволи на виконання: безумовний `Bash(*)`, інтерпретатори з підстановками, команди запуску менеджерів пакетів і правила allow для `Agent`. Вузьке правило, як-от `Bash(git push:*)`, зберігається і тим самим прибирає перевірку класифікатором для цієї дії. У режимі auto список allow не є нейтральним: він віднімає нагляд.

**Правила ask.** Правило `ask`, обмежене за вмістом, наприклад `Bash(git push *)`, примушує запитувати в кожному режимі, включно з режимом auto і включно з командами в sandbox. Голе правило ask для `Bash` пропускається для команд, що виконуються в sandbox. Правила ask є єдиною точкою людського контролю, що переживає кожне інше налаштування.

**Sandbox.** Вимкнений, доки `sandbox.enabled` не дорівнює true. Два незалежні шари. Файлова система: запис обмежено робочим каталогом і тимчасовим каталогом сесії; читання охоплює **всю машину**, включно з `~/.ssh` і `~/.aws`, бо вбудованого списку заборони облікових даних немає. Мережа: жоден домен не дозволено наперед, запит під час першого використання. `autoAllowBashIfSandboxed` автоматично схвалює команди в sandbox, і саме це замінює довгий список allow. `allowUnsandboxedCommands: false` вимикає лише повторну спробу `dangerouslyDisableSandbox`; він **не** обмежує `excludedCommands`, що лишається повним обходом межі ОС. Вбудований проксі не термінує TLS, тож широкий запис `allowedDomains`, як-от `github.com`, є шляхом виходу, а не обмеженням.

**Пріоритет областей дії** для масивів дозволів: managed, потім project local, потім project, потім user, причому ключі-масиви зливаються й дедублікуються в кожній області, а не замінюються. `deny`, доданий будь-де, діє всюди; жодна область не може прибрати deny іншої області. Кілька ключів свідомо ігноруються, коли надходять із налаштувань проєкту: `defaultMode: "auto"`, `sandbox.filesystem.disabled`, записи `mask` у `sandbox.credentials`, `network.tlsTerminate`, `network.strictAllowlist` і `allowAppleEvents`.

Якщо ти не впевнений, чи певна поведінка досі діє у встановленій версії, скажи про це у звіті в розділі «Not verified», а не стверджуй. Запиши версію з `claude --version`.

Зазнач, які файли відстежуються git. `settings.json` під контролем версій є політикою для всієї команди; `settings.local.json` є особистим і в gitignore. Правила не в тому файлі є висновком у Фазі 5.

## Фаза 1. Безумовні дозволи на виконання (P0)

Ця фаза сама вирішує, чи має решта конфігурації якесь значення.

Знайди в кожному масиві `allow` правила, чий специфікатор зводиться до інтерпретатора, менеджера пакетів, запускача середовища або наскрізного виклику. Почни з цього списку й розшир його будь-чим специфічним для проєкту, що знайдеш, наприклад внутрішнім запускачем задач або проксі-CLI:

`bash`, `sh`, `zsh`, `fish`, `dash`, `python`, `python3`, `perl`, `ruby`, `node`, `deno`, `bun`, `npm`, `pnpm`, `yarn`, `npx`, `bunx`, `make`, `just`, `task`, `env`, `xargs`, `eval`, `source`, `docker`, `kubectl`, `ssh`, `devbox`, `mise`, `direnv`, `nix-shell`, `uv`, `poetry`, `cargo run`, `go run`, `dotnet run`.

```bash
python3 - <<'PY'
import json,re,os
PAT=re.compile(r'^(Bash|PowerShell)\((bash|sh|zsh|fish|dash|python3?|perl|ruby|node|deno|bun|npm|pnpm|yarn|npx|bunx|make|just|task|env|xargs|eval|source|docker|kubectl|ssh|devbox|mise|direnv|nix-shell|uv|poetry)\b')
for p in ("~/.claude/settings.json","~/.claude/settings.local.json",
          ".claude/settings.json",".claude/settings.local.json"):
    p=os.path.expanduser(p)
    if not os.path.exists(p): continue
    try: rules=json.load(open(p)).get("permissions",{}).get("allow",[])
    except Exception: continue
    hits=[r for r in rules if PAT.match(r)]
    if hits:
        print(f"--- {p} ({len(hits)} of {len(rules)})")
        for r in sorted(set(hits)): print("   ", r)
PY
```

Для кожного збігу визнач, чи справді він надає довільне виконання, і поясни чому:

| Вердикт | Як виглядає | Наслідок |
|---|---|---|
| Довільне | `Bash(bash *)`, `Bash(node:*)`, `Bash(env:*)`, `Bash(xargs:*)` | Кожне інше правило в кожній області можна обійти |
| Довільне через підкоманду | `Bash(npm:*)`, `Bash(pnpm *)`, `Bash(make *)` | `run`, `exec` і скрипти життєвого циклу встановлення виконують довільний код |
| Обмежене, прийнятне | `Bash(npm run build:*)`, `Bash(pnpm vitest run:*)` | Обмежене іменованим скриптом |
| Наскрізне | будь-який CLI-обгортка, що пересилає свій argv без фільтрації | Рівнозначне обгорнутій оболонці |

Потім доведи наслідок, а не стверджуй. Візьми найсуворіше правило `deny` у репозиторії, зазвичай читання секрету, і випиши точну команду, що обходить його через знайдений дозвіл. Форма прикладу: за `deny: ["Read(**/.env*)", "Bash(cat .env)"]` і `allow: ["Bash(bash *)"]` обхід є `bash -c 'cat .env'`, що зіставляється як команда `bash`, а ніколи як `cat`. Назви правило, дозвіл і рядок обходу. **Не виконуй його.**

Якщо Фаза 1 нічого не знаходить, скажи про це прямо. Це справді добрий результат, і про нього варто сказати.

## Фаза 2. Здоров'я популяції правил

Спершу порахуй, потім охарактеризуй. Проблема не в обсязі, а в тому, що він приховує.

```bash
python3 - <<'PY'
import json,re,os,collections
for p in (".claude/settings.local.json",".claude/settings.json"):
    if not os.path.exists(p): continue
    a=json.load(open(p)).get("permissions",{}).get("allow",[])
    if not a: continue
    exact=[r for r in a if r.startswith("Bash(") and not r.rstrip(")").endswith(("*",":*"))]
    heads=collections.Counter()
    for r in a:
        m=re.match(r'Bash\(([^\s:)]+)',r)
        if m: heads[m.group(1)]+=1
    print(f"--- {p}: {len(a)} allow, {len(exact)} exact-match Bash")
    print("   heads:", heads.most_common(15))
PY
```

Повідом три речі. Скільки правил є точними збігами, що ніколи більше не спрацюють: залишки одноразових схвалень. Які голови команд накопичили багато майже однакових записів, які замінило б одне правило-префікс. І чи не є якесь правило вже мертвим: покритим вбудованим набором лише для читання, затіненим ширшим правилом у тій самій чи ширшій області або некоректним, як-от `:*`, що не в кінці.

Відома особливість матчера, яку варто перевірити тут: команди з префіксом змінної середовища, наприклад `TEST_DB_URL="..." pytest`, ніколи не консолідуються в правило-префікс, бо матчер allow не заглядає за невідоме присвоєння. Кластер майже однакових записів, що відрізняються лише префіксом env, є саме цією помилкою, а не помилкою користувача.

## Фаза 3. Покриття deny та ask

Порожній масив `ask` означає, що конфігурація не містить жодної точки людського контролю. Скажи це прямо, якщо це так.

Перевір покриття дій, які дорого скасовувати, і повідом про кожну як наявну або відсутню з текстом правила:

Переписування історії та руйнівний git: `git push --force` та його форми `-f` і `--force-with-lease`, примусові refspec на кшталт `git push origin +main`, `git reset --hard`, `git clean -fd` і видалення гілок чи remote.

Публікація та злиття: `npm publish`, `gh pr merge`, `gh repo delete`, `gh repo edit`, пуші в реєстри та команди розгортання, специфічні для цього проєкту.

Витік секретів: читання `.env` і варіантів, `*.pem`, `*.key`, `~/.ssh`, `~/.aws`, `~/.gnupg` та будь-якого каталогу облікових даних, який цей проєкт справді використовує.

Коли `deny` існує, перевір його за наведеною вище семантикою, а не приймай за чисту монету. Шаблон, прив'язаний до `git push`, пропускає `git -c key=value push --force`, бо команда вже не починається зі зіставленого префікса. Повідом це як обмеження правила й зазнач, що зіставлення шаблонів у цій грі програє: межею, що справді тримає, є захист гілок на сервері. Правило `deny` усе одно варто зберегти як локальну охорону від випадковості.

Нарешті, назви принаймні одне правило `ask`, яке цей проєкт мав би мати, але не має, обравши з того, що репозиторій справді робить. Обґрунтуй це кодом або конфігурацією CI, а не загальним контрольним списком.

## Фаза 4. Стан sandbox

Якщо жодна область не визначає `sandbox`, констатуй, що sandbox вимкнений, а потім кількісно оціни, чого це коштує **тут**, а не абстрактно. Спирайся на Фазу 1: за наявності дозволу на інтерпретатор і без sandbox немає жодної межі для Bash. Без дозволу на інтерпретатор і без sandbox межею є лише список правил, який тримається, лише доки жодне майбутнє правило її не відкриє.

Якщо `sandbox` визначено, проаудитуй його за цим:

`excludedCommands` є повним обходом межі ОС, і `allowUnsandboxedCommands: false` його не обмежує. Для кожного запису запитай, чи може ця команда дістатися до файлової системи хоста. `docker` може: через монтування томів і сокет демона. `kubectl`, `ssh` і `make` зазвичай можуть. Повідом кожну виключену команду з тим, до чого вона все ще може дістатися, і перевір, чи покриває її правило `deny` або `ask`. Також познач записи, синтаксис яких не перевірено для цього поля: задокументовані форми це голе ім'я або `name *`, а суфікс `:*` тут не є тим самим полем, що й матчер Bash. Перевір розв'язану конфігурацію на вкладці Config у `/sandbox`, а не вгадуй.

`network.allowedDomains` є списком дозволеного виходу, що оцінюється за іменем хоста, яке заявляє клієнт, без інспекції TLS за замовчуванням. Широкі записи, як-от `github.com` або підстановка на домени користувацького вмісту, дозволяють ексфільтрацію. Перелічи кожен домен із причиною, чому він там; усе, що не можеш обґрунтувати, є висновком. Рекомендуй `network.strictAllowlist: true` там, де версія це підтримує, і зазнач, що він має жити в налаштуваннях користувача або managed, бо налаштування проєкту для цього ключа ігноруються.

Відсутність `credentials` є висновком щоразу, коли sandbox увімкнений, бо типова політика читання охоплює всю машину. Запропонуй конкретні записи `files` для deny щодо шляхів облікових даних, які ця машина справді має, і записи `envVars` для токенів, які цей проєкт справді використовує.

`filesystem.allowWrite` слід звірити з реальністю. Якщо власні workflow проєкту пишуть поза робочим каталогом (сусідні репозиторії, спільний вивід збірки, каталог кешу), ці шляхи мають бути перелічені, інакше sandbox зламає workflow і підштовхне когось до його вимкнення. Огляни скрипти, `package.json` і конфігурацію CI, щоб їх знайти. Повідом кожен як обов'язковий запис.

Ключі, які налаштування проєкту встановлювати не можуть, варто позначити, якщо вони присутні у файлі проєкту, бо їх мовчки ігнорують: `defaultMode: "auto"`, `filesystem.disabled`, записи `mask` у `credentials`, `network.tlsTerminate`, `network.strictAllowlist`, `allowAppleEvents`.

## Фаза 5. Гігієна областей дії

Визнач для кожного важливого правила, чи живе воно в правильному файлі.

`deny` на читання облікових даних належить налаштуванням користувача, бо воно має слідувати за оператором у кожен проєкт, а не оголошуватися заново в кожному репозиторії. Правило, специфічне для інструментарію цього проєкту, належить відстежуваному `.claude/settings.json`, щоб команда його успадкувала. Правило, що відображає звички однієї людини, належить `.claude/settings.local.json`.

Познач неправильне розміщення в обох напрямках. Deny облікових даних, що існує лише в цьому проєкті, залишає неприкритим кожен інший проєкт. Абсолютний шлях, специфічний для машини, у відстежуваному файлі ламається в усіх інших. Безумовний дозвіл у налаштуваннях користувача є найгіршим випадком, бо застосовується до кожного репозиторію, включно з недовіреними.

Зазнач, чи `settings.local.json` тут справді в gitignore, і скажи про це, якщо ні.

## Фаза 6. Взаємодія з режимом

Визнач ефективний режим дозволів: `permissions.defaultMode` у найближчій області, якій дозволено його встановлювати, інакше Manual. Пам'ятай, що `defaultMode: "auto"` ігнорується з налаштувань проєкту та local.

Потім оціни список allow **відносно цього режиму**, бо той самий список має протилежні наслідки в різних режимах.

У Manual або `acceptEdits` правило allow прибирає запит, на який ви б інакше відповідали. Ризиком є широкі дозволи.

У режимі auto правило allow повністю прибирає класифікатор із рішення, бо allow, ask і deny розв'язуються до запуску класифікатора. Правила на кшталт `Bash(git push:*)`, `Bash(git commit:*)` або `Bash(gh pr:*)` тому вимикають саме ті перевірки, в яких класифікатор найсильніший, включно з тим, чи пуш несе секрети за межі репозиторію. Якщо проєкт працює в режимі auto, перелічи кожне правило allow, що пригнічує перегляд класифікатором, і рекомендуй перенести його в `ask` або видалити. Зазнач також, які широкі дозволи режим auto скидає під час входу, щоб читач знав, які висновки Фази 1 у цьому режимі нейтралізовано, а які ні.

Якщо hooks налаштовано, перевір, чи hook `PreToolUse` завершується з ненульовим кодом, щоб щось блокувати. Hook, що перевіряє розв'язану команду, є жорсткішою межею, ніж шаблон, і варто підтвердити, що він ловить форми інтерпретаторів, знайдені у Фазі 1, а не лише буквальні назви команд.

**Ранжовані висновки**, найгірші першими. Кожен містить: серйозність, файл і правило, що з цим робить зловмисник або випадковість, команду відтворення та виправлення. Жодного висновку без кроку відтворення.

**Готовий до застосування патч** у вигляді блоку JSON на файл, що показує лише те, що змінюється, із зазначенням, якій області він належить. Не застосовуй його.

**Not verified**: перелік усього, що ти не зміг підтвердити: поведінка, що залежить від версії, поля, синтаксис яких ти не зміг перевірити, усе, що потребує панелі `/sandbox` або `/permissions`. Явність тут цінніша за звіт, що виглядає повним.

**Одне речення**, що називає єдину зміну з найвищим співвідношенням усунутого ризику до витрачених зусиль.

## Правила для твого звіту

Будь конкретним або мовчи. «Consider tightening permissions» не є висновком; «`Bash(node:*)` у `.claude/settings.local.json`, рядок 412, робить `Read(**/.env*)` deny у `.claude/settings.json`, рядок 5, обхідним через `node -e 'console.log(require("fs").readFileSync(".env","utf8"))'`» є.

Не роздувай звіт, щоб він здавався ґрунтовним. Якщо фаза нічого не знаходить, правильний вивід: один рядок про це.

Не рекомендуй `bypassPermissions` чи `--dangerously-skip-permissions` як ліки від втоми від запитів. Sandbox з `autoAllowBashIfSandboxed` є механізмом, що прибирає запити, зберігаючи межу.

Прямо кажи, коли конфігурація хороша. Аудит, що вигадує висновки, щоб виправдати себе, гірший за відсутність аудиту.
