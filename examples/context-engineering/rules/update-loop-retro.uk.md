# Шаблон ретроспективи сесії

Структурований prompt для запуску наприкінці сесій Claude Code. Мета — зафіксувати
знання, поки вони свіжі, і перетворити їх на сталі правила, щоб ваш `CLAUDE.md`
залишався точним у міру розвитку проєкту.

## Prompt

Скопіюйте це й вставте в Claude наприкінці сесії:

```
Сесію завершено. Перш ніж закрити, проведи коротку ретроспективу:

1. Які патерни ми встановили, що мають стати постійними правилами в CLAUDE.md?
2. Що я виправив із того, що Claude зробив неправильно? Чи має правило запобігти цьому?
3. Що спрацювало добре й варто повторювати в майбутніх сесіях?
4. Чи ухвалено архітектурні рішення, які має зафіксувати CLAUDE.md?
5. Чи є зараз у CLAUDE.md щось, що ця сесія показала хибним або застарілим?

Виведи поповнення знань — максимум від 3 до 5 пунктів, лише найважливіше.
Пропускай усе очевидне, загальне або те, що вже є в CLAUDE.md.
Оформи кожен пункт як дієве правило, готове до копіювання.
```

## Коли запускати

| Тригер | Запускати ретро? |
|---------|-----------|
| Завершено функцію або великий рефакторинг | Так |
| Сесія налагодження виявила системну прогалину | Так |
| Ухвалено архітектурне рішення | Так |
| Сесія онбордингу, де хтось помітив брак контексту | Так |
| Щомісяця, навіть якщо нічого значного не сталося | Так — виявляє накопичення |
| Тривіальна сесія (виправлення одруківки, правка документації) | Ні |

Щомісячна ретроспектива — мінімальна частота навіть для спокійних проєктів. Дрібні відхилення накопичуються непомітно.

## Як виглядає добрий результат

Claude має повернути щось подібне (не дослівно, але з таким рівнем конкретики):

```
Поповнення знань — 2025-09-15

1. Встановлено патерн: усі запити до бази даних проходять через шар репозиторіїв і ніколи не викликаються
   безпосередньо з обробників маршрутів. Правило для додавання: "Ніколи не викликай Prisma безпосередньо з обробників
   маршрутів — використовуй функції репозиторію в src/db/."

2. Виправлення: я запропонував lodash для роботи з масивами. Ти перенаправив на нативні методи
   масивів. Правило для додавання: "Не імпортуй lodash — використовуй нативні методи масивів JS. Вартість
   бандла не виправдана для нашого випадку."

3. Архітектурне рішення: ми вирішили тримати логіку автентифікації в middleware, а не в окремих
   обробниках маршрутів. Правило для додавання: "Перевірки автентифікації належать до src/middleware/auth.ts — а не до
   обробників маршрутів. Якщо маршруту потрібна особлива логіка автентифікації, розширюй middleware."

4. Застаріле правило: CLAUDE.md досі посилається на стару сигнатуру обробника помилок Express v4.
   Ми на v5. Вилучити: "Обробники помилок Express приймають 4 аргументи (err, req, res, next)."
   Оновити на: "Обробники помилок Express v5: асинхронні помилки передаються автоматично — не потрібно
   викликати next(err)."
```

## Після ретро

### Перегляньте результат

Не все, що виявляє Claude, має потрапити в `CLAUDE.md`. Запитайте себе:

- Це специфічне для нашого проєкту чи загальна порада, яку Claude вже знає?
- Чи це дієве правило? Чи зробить нова сесія Claude ту саму помилку без цього правила?
- Чи це вже охоплено? Пошукайте, перш ніж додавати — дублікати знижують дотримання.

### Оновіть CLAUDE.md

Додайте нові правила до найдоречнішого розділу. Вилучіть усі застарілі правила, які позначив Claude.

### Закомітьте з простежуваним повідомленням

```bash
git add CLAUDE.md
git commit -m "context: [what changed and why]"
```

Змістовні повідомлення комітів створюють простежувану історію того, як розвивався ваш AI-контекст. Це корисно
для налагодження: «Claude почав неправильно робити X після того, як ми внесли зміну Y» стає можливо діагностувати
з git log.

Приклади добрих повідомлень комітів:

```
context: add lodash ban — use native array methods
context: clarify auth middleware pattern after refactor
context: remove Express v4 error handler rule — now on v5
context: document payment webhook idempotency requirement
context: add Prisma-direct query ban after code review
```

## Використання в команді

Коли кілька людей працюють із Claude над одним проєктом, ретроспективи стають особливо цінними.
Кожен розробник може отримувати різні виправлення — різні прогалини в `CLAUDE.md` виявляються з
різних боків. Варто:

- Проводити ретро наприкінці кожного PR, у якому була значна робота з допомогою Claude
- Включати `CLAUDE.md` до рев'ю PR як постійний пункт порядку денного
- Раз на квартал проводити спільне ретро всією командою, щоб переглянути накопичені зміни

Файл `CLAUDE.md` — це спільний актив. Його якість відображає те, наскільки добре команда його підтримує.
