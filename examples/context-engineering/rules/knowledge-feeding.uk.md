# Протокол поповнення знань

Context engineering — це не одноразове налаштування: його цінність накопичується з часом, у міру того як Claude дізнається, що працює для вашого проєкту. Цей файл визначає, коли й як переносити ці знання назад у ваш `CLAUDE.md`.

## Коли поповнювати знання

Виконуйте цей протокол наприкінці будь-якої сесії, у якій:

- Завершено функцію або значущу зміну коду
- Виявлено новий патерн, який добре спрацював і має стати стандартом
- Трапилася помилка, що потребувала виправлення (особливо якщо помилка повторювалася)
- Ухвалено архітектурне рішення, яке вплине на майбутню роботу
- Закріпилася перевага певної бібліотеки, інструмента чи підходу

Пропускайте його для тривіальних сесій (виправлення одруківок, правки документації, дрібні зміни конфігурації).

## Prompt для поповнення знань

Вставте це в Claude наприкінці відповідних сесій:

```
Перш ніж ми закриємо цю сесію, виконай поповнення знань:

1. Які патерни ми встановили, що мають стати постійними правилами?
2. Що я виправив або перенаправив, що має стати правилом, аби це не повторилося?
3. Чи ухвалено архітектурні рішення, які має зафіксувати CLAUDE.md?
4. Чи є в CLAUDE.md щось, що ця сесія показала хибним або застарілим?

Виведи лише найважливіші пункти (максимум 3-5). Використовуй формат поповнення знань нижче.
Пропускай усе очевидне або вже охоплене.
```

## Формат виводу поповнення знань

Claude має виводити знахідки в такій структурі:

```markdown
## Поповнення знань — [YYYY-MM-DD]

### Новий патерн (якщо є)
**Що**: [Одне речення з описом патерну]
**Чому**: [Чому це правильний підхід для цього проєкту]
**Правило для додавання**:
> [Точний текст для вставлення в CLAUDE.md, готовий до копіювання]

### Знайдений антипатерн (якщо є)
**Що сталося**: [Що Claude зробив неправильно або що було виправлено]
**Чому тут це неправильно**: [Причина, специфічна для проєкту, а не загальна найкраща практика]
**Правило для додавання**:
> Ніколи: [конкретна поведінка, якої слід уникати, і чому]

### Архітектурне рішення (якщо є)
**Рішення**: [Що вирішили]
**Обґрунтування**: [Чому — особливо якщо це суперечить поширеній практиці]
**Правило для додавання**:
> [Точний текст для вставлення в CLAUDE.md]

### Застаріле правило для вилучення (якщо є)
**Правило**: [Поточне правило в CLAUDE.md]
**Чому вилучити**: [Що змінилося, через що воно застаріло]
```

## Процес інтеграції

Після отримання поповнення знань:

1. **Перегляньте, перш ніж додавати**: не всі патерни узагальнюються. Запитайте себе: «Чи потрібно це знати новому учасникові команди, чи це контекст, специфічний лише для цієї сесії?»
2. **Скопіюйте доречні правила** у відповідний розділ `CLAUDE.md`
3. **Вилучіть усі правила**, які Claude позначив як застарілі
4. **Закомітьте оновлення** зі змістовним повідомленням:

```bash
git add CLAUDE.md
git commit -m "context: [short description of what was learned]"

# Examples:
# context: add zod validation rule after form refactor
# context: remove Redux rule — migrated to Zustand
# context: document payment webhook idempotency pattern
```

## Фільтр якості

Перш ніж додати будь-яке правило до `CLAUDE.md`, перевірте:

- **Чи воно специфічне для цього проєкту?** Загальним найкращим практикам тут не місце — Claude їх уже знає.
- **Чи воно дієве?** «Будь обережним з асинхронним кодом» — марне. «Завжди перевіряй стани гонитви в скінченному автоматі замовлень» — корисне.
- **Чи воно вже охоплене?** Перш ніж додавати, пошукайте схожі правила. Дублікати послаблюють дотримання.
- **Чи буде воно правдивим за 6 місяців?** Уникайте правил, прив'язаних до тимчасових станів («ми мігруємо на X, тож поки не використовуй Y»).

## Відповідальність

Поповнення знань найкраще працює, коли це командна звичка, а не робота однієї людини. Будь-хто з команди, хто працює з Claude, може зробити свій внесок. Відповідальність за фільтрацію якості несе той, хто рецензує PR зі змінами `CLAUDE.md`.
