### TypeScript

- Увімкнено strict mode (`"strict": true` у tsconfig). Ніколи не використовуй `any` — використовуй `unknown` і звужуй тип.
- Усі сигнатури публічних функцій мають мати явні типи повернення.
- Використовуй `type` для об'єднань і перетинів, `interface` — для форм об'єктів, які можуть розширюватися.
- [ДОДАЙТЕ СВОЇ ПРАВИЛА]

## Процес розробки

### Домовленості щодо Git

- Іменування гілок: `[type]/[short-description]` — наприклад, `feat/add-refund-flow`, `fix/order-status-race`
- Формат комітів: [Conventional Commits](https://www.conventionalcommits.org/)
  - `feat:` нова функція
  - `fix:` виправлення бага
  - `chore:` обслуговування, оновлення залежностей
  - `docs:` лише документація
  - `test:` лише тести
  - `refactor:` без зміни поведінки
- Коміти мають бути атомарними — одна логічна зміна на коміт

### Фреймворк і розташування

- Фреймворк: [наприклад, Vitest]
- Файли тестів: поруч із кодом (`foo.ts` → `foo.test.ts`) АБО в `__tests__/` [оберіть одне]
- Запуск тестів: `[TEST COMMAND]`
- Запуск із покриттям: `[COVERAGE COMMAND]`

### Що потребує тестів

- Усі функції сервісного шару (модульні тести з mock-залежностями)
- Усі маршрути API (інтеграційні тести з supertest або аналогом)
- Усі утилітарні функції з розгалуженою логікою
- **Не потрібно**: функції, що просто передають дані далі, прості getters/setters, визначення моделей Prisma

### Структура тестів

```typescript
// Follow this pattern:
describe('[unit under test]', () => {
  describe('[method or scenario]', () => {
    it('[expected behavior in plain English]', async () => {
      // Arrange
      // Act
      // Assert
    })
  })
})
```

### Mocking

- Підміняй на межі: mock для зовнішніх сервісів, ніколи для внутрішніх модулів
- [ДОДАЙТЕ СВОЇ ДОМОВЛЕНОСТІ ЩОДО MOCKING — наприклад, "Використовуй vi.mock() на рівні файлу, а не всередині тестів"]
