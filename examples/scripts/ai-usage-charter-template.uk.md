## 1. Мета

Ця хартія визначає, як працівники [Організації] можуть використовувати AI-асистентів для програмування, які інструменти схвалено, які дані можна з ними використовувати і хто відповідає за дотримання вимог. Мета — уможливити продуктивну розробку з допомогою AI, водночас керуючи ризиками безпеки, приватності та регуляторними ризиками.

## 3. Правила класифікації даних

Усі дані в [Організації] поділено на чотири рівні. Використання вами AI-інструментів має відповідати цій класифікації.

| Класифікація | Приклади | Чи дозволено Claude Code? | Примітки |
|----------------|----------|----------------------|-------|
| **PUBLIC** | Код з відкритим вихідним кодом, публічна документація | Так — без обмежень | |
| **INTERNAL** | Внутрішні інструменти, нечутливий бізнес-код | Так — стандартна конфігурація | Використовуйте облікові записи компанії |
| **CONFIDENTIAL** | Дані клієнтів (не PII), комерційні таємниці, пропрієтарні алгоритми | Так — лише план Enterprise зі схваленою конфігурацією | |
| **RESTRICTED** | Дані платіжних карток PCI, PHI, облікові дані, токени автентифікації, ключі шифрування | **Ніколи** | Без винятків |

### Жорсткі правила

- Дані RESTRICTED **ніколи** не потрапляють у context window AI — ні в промптах, ні у файлах, які читає Claude, ні як приклади.
- Особисті AI-акаунти (особисті підписки Pro) можна використовувати лише з даними PUBLIC або INTERNAL.
- Облікові дані та API-ключі компанії належать до RESTRICTED. Ніколи не вставляйте їх у промпти.

### Технічне забезпечення

Проєкти, що працюють із даними CONFIDENTIAL або RESTRICTED, мають налаштувати `permissions.deny` у `.claude/settings.json`, щоб заблокувати AI доступ до чутливих файлів. Готові конфігурації дивіться в [конфігурації рівнів Standard або Regulated](../../guide/security/enterprise-governance.md#4-guardrail-tiers).

## 4. Схвалені сценарії використання

Такі способи використання AI-асистентів для програмування схвалено без додаткового розгляду:

- Автодоповнення та генерація коду для схвалених класифікацій даних
- Рев'ю коду й аналіз якості
- Генерація тестів і мутаційне тестування
- Підготовка та оновлення документації
- Налагодження, аналіз першопричин, аналіз логів
- Аналіз архітектури внутрішніх систем
- CLI-скрипти, автоматизація, інструменти збирання
- Рефакторинг і прибирання коду

---

## 5. Заборонені сценарії використання

Наведене нижче **не дозволено** без явного письмового схвалення:

| Заборонене використання | Причина | Процес винятку |
|----------------|--------|------------------|
| Обробка сирих даних власників карток PCI | Регуляторна (PCI DSS) | Жодного — забезпечено технічно |
| Генерація коду, що обробляє незашифровані PHI, без перевірки безпеки | Регуляторна (HIPAA) | Потрібна перевірка безпеки |
| Автономне розгортання в продакшен | Вимога людського нагляду | Схвалення Eng Director |
| Використання особистих AI-акаунтів для даних CONFIDENTIAL | Резидентність даних/приватність | Перехід на обліковий запис компанії |
| Надсилання даних клієнтів як прикладів у промптах | Приватність, поводження з даними | Використовуйте синтетичні дані |
| Обхід засобів governance (hooks, правила deny) | Порушення політики | Жодного |

## 6. Governance MCP-серверів

MCP-сервери (Model Context Protocol) розширюють можливості Claude Code і створюють додаткову поверхню ризику. Усі MCP-сервери, що використовуються в проєктах компанії, мають бути:

1. Внесені до реєстру схвалених (`.claude/mcp-registry.yaml` у репозиторії платформної конфігурації)
2. Закріплені на точній версії (ніколи `@latest`)
3. Повторно переглянуті кожні 6 місяців або при підвищенні мажорної версії

**Процес схвалення**: надішліть запит із назвою сервера, URL джерела, передбачуваним сценарієм використання та обсягом даних на [platform-team@company.com] або в [Slack-канал #claude-code-requests].

Несхвалені MCP, виявлені в конфігураціях проєктів, позначатимуться на початку сесії. Розробники мають 48 годин, щоб видалити їх або отримати схвалення.

## 7. Рев'ю коду та атрибуція

### Атрибуція AI

Усі pull request, у яких AI допомагав писати код, мають містити розділ про розкриття участі AI:

```markdown
## AI Assistance
- AI tool used: Claude Code
- Scope: [e.g., "Generated tests for auth module", "Refactored payment handler"]
- Human review: Reviewer checked logic, security implications, and edge cases
```

Стандартний трейлер коміту `Co-Authored-By: Claude <noreply@anthropic.com>` (Claude Code додає його автоматично) задовольняє вимогу атрибуції для рутинних змін. Явне розкриття в PR обов'язкове для:
- Будь-якої зміни автентифікації чи авторизації
- Будь-якої зміни платіжної чи фінансової логіки
- Будь-якої зміни схеми бази даних
- Будь-якої нової інтеграції із зовнішнім API

### Очікування щодо рев'ю коду

Код, згенерований AI, не звільняється від рев'ю. Рецензенти мають застосовувати таку саму — або суворішу — прискіпливість до згенерованих AI фрагментів, зокрема щодо:
- Чутливих до безпеки шляхів (автентифікація, криптографія, контроль доступу)
- Поводження з даними (PII, фінансові дані)
- Граничних випадків і умов помилок, які AI-інструменти часто пропускають

## 8. Відповідальність

### Обов'язки розробника

Використовуючи Claude Code в системах компанії, ви погоджуєтеся:
- Дотримуватися цієї хартії
- Повідомляти про підозру на розкриття даних на [security@company.com] протягом 24 годин
- Брати участь у щоквартальних переглядах доступу
- Проходити чеклист онбордингу AI-інструментів під час приєднання до команди чи зміни команди
- Не обходити засоби governance (hooks, правила deny, реєстр)

### Обов'язки тімліда

- Забезпечувати налаштування проєктів із відповідним рівнем guardrails
- Щоквартально переглядати реєстр MCP
- Включити AI-хартію до онбордингу команди
- Ескалювати порушення хартії згідно з §9

### Обов'язки платформної команди

- Підтримувати спільну конфігурацію governance (шаблони settings.json, hooks)
- Розглядати запити на схвалення MCP протягом 1 тижня
- Оновлювати хартію, коли змінюються інструменти, рівні чи ризики
- Проводити піврічний аудит governance

## 9. Реагування на інциденти

### Якщо ви підозрюєте розкриття даних

1. **Зупиніть** поточну AI-сесію негайно
2. **Задокументуйте**, які дані могли потрапити в контекст (які файли, які промпти)
3. **Повідомте** на [security@company.com] з темою "AI Data Exposure" протягом 24 годин
4. **Не намагайтеся** розслідувати чи виправляти ситуацію без вказівок служби безпеки

### Порушення хартії

| Серйозність | Приклади | Реакція |
|----------|----------|---------|
| **Незначне** | Забули атрибуцію AI в PR, недовго використовували несхвалений MCP | Наставництво, виправлення |
| **Помірне** | Використали особистий акаунт із даними CONFIDENTIAL, обійшли hook | Офіційне попередження, повторне навчання |
| **Серйозне** | Обробляли дані RESTRICTED за допомогою AI, систематично обходили засоби контролю | Залучення HR/юристів |

## 10. Відповідність нормативним вимогам

Ця хартія охоплює такі вимоги відповідності:

| Фреймворк | Релевантні контролі | Що охоплює ця хартія |
|-----------|------------------|----------------------|
| **SOC 2** | CC6.1 (Logical access), CC7.1 (Monitoring), CC9.2 (Vendor risk) | Класифікація даних, реєстр MCP, журналювання аудиту |
| **ISO 27001** | A.8.3 (Access restriction), A.8.25 (Secure dev lifecycle), A.5.23 (Cloud services) | Схвалені інструменти, рівні governance, поводження з даними |
| **HIPAA** (за потреби) | Security Rule §164.312 (Access control, Audit controls) | Заборона даних RESTRICTED, журналювання в режимі відповідності |
| **PCI DSS** (за потреби) | Req 6.3 (Security vulnerabilities), Req 12 (Policy) | Заборона даних PCI, вимоги до рев'ю коду |
| **GDPR/CCPA** | Мінімізація даних, обмеження мети | Класифікація CONFIDENTIAL/RESTRICTED, правила обсягу даних |
