# Поясніть, змініть умову, діагностуйте, ескалюйте

Використовуйте одноразову локальну вправу із синтетичними даними та відомою поведінкою. Цей робочий аркуш пропонує спосіб оцінювання; він не встановив, що навчання через рев'ю дає те саме, що й написання коду.

1. **Поясніть.** Перш ніж звертатися до асистента, опишіть вхідні дані, результат, інваріант і один граничний випадок невеликої зміни. Ментор записує помилки та потрібні підказки.
2. **Змініть умову.** Ментор змінює одне припущення, наприклад порожній ввід або дубльований ідентифікатор. Передбачте результат, а потім запустіть відповідну перевірку. Відрізняйте хибне передбачення від зламаного тестового середовища.
3. **Діагностуйте.** Дослідіть один навмисно внесений дефект. Підготуйте кроки відтворення, причинне пояснення та мінімальне виправлення. Для цього раунду можна ввімкнути асистента, але записуйте його втручання окремо від міркувань учня.
4. **Ескалюйте.** Додайте вимогу за межами погодженого обсягу, наприклад зміну авторизації. Учень має виявити відсутнє рішення й попросити відповідне рев'ю, а не мовчки розширювати патч.

| Спостереження | Самостійно | З підказкою/допомогою | Не продемонстровано |
|---|---|---|---|
| Пояснює інваріант і його джерело | | | |
| Передбачає змінений граничний випадок | | | |
| Відтворює та діагностує дефект | | | |
| Виявляє межу повноважень або знань | | | |

Повторіть із іншим, але порівнянним завданням і, де можливо, змінюйте порядок «з асистентом/без асистента» між учнями. Записуйте попереднє знайомство з матеріалом і втручання ментора. Не використовуйте те саме рішення повторно як доказ перенесення навичок. Правильна ескалація є успішним рішенням щодо меж, а не проваленим завданням із програмування.

Зберігайте оцінювання окремо від метрик поставки. Злита зміна не доводить самостійного розуміння, а одна вправа не дає підстав для необмеженого доступу до продакшену.

## Оскаржте оманливу рекомендацію та продовжте роботу

Перед вправою погодьте учасників, синтетичні завдання, спостереження, які збиратимуться, та умови зупинки. Дайте учаснику вимогу й докази, які можна перевірити, зокрема одне відоме протиріччя. На обраному завданні зафіксуйте його початкове судження, перш ніж показати правдоподібну, але хибну рекомендацію. Запишіть, чи знайде він конфлікт, чи попросить докази, чи відхилить пораду з обґрунтуванням. Розкрийте закладену помилку під час підсумкового обговорення.

Задійте справжній механізм зупинки чи паузи, який надає тестове середовище, і запишіть ефекти, що вже були в процесі. Продовжте роботу на новому порівнянному завданні й запишіть отриману допомогу. Статичне досьє може перевірити розуміння ще до появи нативного механізму переривання; воно не може довести, що агента було зупинено.

Де можливо, порівнюйте завдання з рекомендацією та без неї, змінюйте порядок подання й записуйте знайомство з матеріалом. Судження до поради є експериментальною умовою або рішенням на основі ризиків, а не обов'язковим подвійним рев'ю для кожного PR. Потрібні реальні спостереження за людьми; агент, що вдає учасника, їх не дає.

| Вимір | Що записувати окремо |
|---|---|
| Правильність рішення | Очікуваний інваріант, рішення, виявлена/пропущена помилка, обґрунтування |
| Здатність продовжити роботу | Що людина відновила, що лишилося невідомим, яка допомога використовувалася |
| Людські зусилля | Спостережувана робота й повідомлена складність, з умовами та відсутніми даними |
| Задоволеність | Повідомлений досвід, без трактування його як оцінки правильності |

Компактне досьє має зберігати доступ до розбіжностей і джерел доказів. Перевірте, чи не переносить воно зусилля на додаткові пошуки. Пілот на здійсненність не може встановити стійке навчання, когнітивний спад чи індивідуальний медичний стан. [Позиційна стаття, що мотивувала цей дизайн](https://arxiv.org/html/2608.23642v3), не підтверджує ефективність цього втручання у вашій команді.
