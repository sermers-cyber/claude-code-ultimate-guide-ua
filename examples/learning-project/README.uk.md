# Proofpack: один проєкт на весь семимодульний шлях навчання

Proofpack — це CLI на Node.js без залежностей, який вирішує, чи достатньо в кандидата на реліз доказів, щоб його випустити. Його кінцевий стан є еталонним рішенням. Учень може відтворити той самий результат у модулях 01–07, не перемикаючись між проєктами й не вигадуючи щоразу нову вправу.

Обмежене робоче завдання описано в [ISSUE.md](ISSUE.md). CLI приймає JSON-кандидата, перевіряє обов'язкові докази `tests`, `security` і `package`, друкує машинозчитуваний звіт і повертає окремий код виходу для неповних доказів або некоректних вхідних даних.

## Запуск без встановлення пакетів

Node.js 20 або новіша версія — єдина залежність для тестів.

```bash
node --version
npm test
npm run verify
```

`npm run verify` має завершитися з кодом `0`. Порівняйте це з навмисно невдалою фікстурою:

```bash
npm run verify:incomplete
```

Ця команда має завершитися з кодом `1` і назвати невдалі та відсутні перевірки. Некоректний JSON завершується з кодом `2`.

## Контракт доказів

Валідатор вимагає по одній унікальній перевірці для кожної з цих назв:

- `tests`
- `security`
- `package`

Кожна перевірка потребує `status: "pass"` та опису збереженого результату. Порожні докази й нечутливі до регістру маркери `UNKNOWN`, `failed`, `not executed`, `unverified`, `NOT RUN` і `no retained output` спричиняють невдачу. Це консервативний фільтр рядків, тож текст на кшталт `0 failed` теж не пройде. Схема кандидата не розбирає з цього рядка команду, код виходу чи контрольну суму. Записуйте ці структуровані факти в [evidence/PROOF-LOG.md](evidence/PROOF-LOG.md). Версія має бути у форматі `MAJOR.MINOR.PATCH`. Дубльована назва вважається невдачею, бо пізніші докази не повинні затіняти раніший результат.

[fixtures/release-ready.json](fixtures/release-ready.json) демонструє прийнятну схему. [fixtures/release-incomplete.json](fixtures/release-incomplete.json) демонструє невдалу перевірку безпеки й відсутні докази для пакета. CLI не звертається до реєстру, не виконує рядки доказів і не робить висновку, що згадана команда справді виконувалася.

## Перевірка та пакування

Запустіть повний локальний шлюз, перш ніж стверджувати, що еталонне рішення проходить:

```bash
npm test
npm run verify
npm run package:check
```

Шлюз пакування перевіряє обидва JavaScript-файли за допомогою `node --check`, а потім збирає npm-маніфест без завантаження залежностей і без публікації артефакту. Окремий [тест package-check](test/package-check.test.mjs) вставляє некоректний JavaScript у тимчасову копію й вимагає ненульового коду виходу. Це доводить межу синтаксису, а не виконання запакованого CLI. [Dockerfile](Dockerfile) дає додаткову форму для розгортання. Його збирання може потребувати базового образу `node:22-alpine` із реєстру, тож успішний прогін тестів Node.js не доводить, що образ збирається чи працює на іншому хості.

[Шаблон журналу доказів TESTING.md](../claude-md/TESTING.md) у репозиторії пояснює повний формат доказів. Цей приклад містить заповнений [журнал доказів](evidence/PROOF-LOG.md), специфічний для проєкту. Для дорожчих рішень дотримуйтеся [воркфлоу Best-of-N](../../guide/workflows/best-of-n.md) і зберігайте як обраного кандидата, так і відхилених.

## Межа безпеки

Release guard блокує прямі виклики інструментів `npm publish` і `docker push`, виклики з прапорцями та обфусковані порожніми лапками. Він також відхиляє будь-яку команду, у якій `npm` трапляється разом із `publish` або `docker` разом із `push`, навіть коли ці слова лише друкуються чи обговорюються. Ці консервативні хибні спрацьовування навмисні. Hook не ловить аліаси, закодовані команди, розгортання змінних, інші клієнти реєстрів або конструкції оболонки, що розбивають слова непорожнім текстом у лапках. Він ніколи не розблоковується автоматично після успішної перевірки. Сприймайте його як навчальний засіб контролю, а не як парсер оболонки чи універсальний брандмауер команд. Перш ніж адаптувати hooks для продакшену, застосуйте [рекомендації з посилення безпеки](../../guide/security/security-hardening.md) з репозиторію.

Публікація також потребує власника каналу, облікових даних місця призначення та явного рішення. [Воркфлоу розповсюдження посібника](https://github.com/FlorianBruniaux/claude-code-ultimate-guide/blob/main/docs/workflows/guide-distribution.md) відокремлює ці зовнішні дії від локальних перевірок пакування. Цю сторінку надає батьківська інтеграція в `main`; ця ізольована гілка зберігає посилання на зовнішній репозиторій, доки обидва коміти не буде об'єднано.
