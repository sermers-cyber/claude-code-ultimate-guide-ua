# Правила рев'ю Greptile: шаблон

<!--
  Скопіюйте до .greptile/rules.md у корені репозиторію, а потім замініть кожен розділ-заглушку
  справжніми домовленостями свого проєкту. Перевага Greptile над Claude Code Action
  полягає в міжфайловому RAG-пошуку: ланцюжки залежностей, «хто ще це викликає», патерни, що
  повторюються у віддалених файлах. Не просіть його повторно перевіряти те, що вже охоплюють Claude/CodeRabbit
  у цьому репозиторії (див. примітку про недублювання нижче), натомість дайте йому спеціалізуватися.
-->

**Примітка про недублювання**: цей звід правил НЕ повинен повторювати те, що вже перевіряють у цьому репозиторії `.github/prompts/code-review.md`
(Claude Code Action) або `.coderabbit.yaml` (CodeRabbit). Якщо правило
з'являється в кількох конфігураціях, один із трьох інструментів має від нього відмовитися. Обирайте той інструмент, який має
найкращу позицію для цієї конкретної перевірки (див. таблицю розподілу правил в архітектурному документі).

---

## 1. Архітектурні домовленості

<!-- Приклад: правила шарів, заборонені імпорти між модулями, домовленості щодо іменування -->

- [ ] Опишіть тут свій патерн шарів (наприклад, "Controller → Service → Repository, без пропуску шарів")
- [ ] Перелічіть заборонені імпорти між модулями
- [ ] Зазначте межі кодогенерації (згенеровані файли, які рецензенти мають пропускати)

## 2. Бізнес-інваріанти

<!--
  Саме цей розділ найбільше виграє від міжфайлового пошуку Greptile: інваріанти,
  що охоплюють кілька файлів і які легко непомітно порушити (enum статусу з
  правилами переходів, що застосовуються в одному сервісі, але не в іншому, правило обмеження області, яке має застосовуватися
  до кожного нового запиту до певної таблиці тощо).
-->

- [ ] Перелічіть скінченні автомати та їхні допустимі переходи
- [ ] Перелічіть правила обмеження області, що мають застосовуватися до кожного запиту до чутливих таблиць
- [ ] Перелічіть поля, які ніколи не можна показувати певним ролям/ендпоінтам

## 3. Безпека

<!-- Перелічуйте лише перевірки, якими ще НЕ опікуються prompt Claude Code Action чи path_instructions CodeRabbit -->

- [ ] Опишіть домовленості щодо поводження із секретами/обліковими даними
- [ ] Опишіть будь-які специфічні для проєкту патерни автентифікації/дозволів

## 4. Домовленості щодо коду

- [ ] Форматування/лінтинг уже забезпечує CI, не позначайте їх повторно (вкажіть інструмент, наприклад ESLint/Ruff/rustfmt)
- [ ] Специфічні для проєкту ідіоми, порушення яких варто позначати

## 5. Доступність (якщо застосовно)

- [ ] Перелічіть патерни, пов'язані з WCAG, специфічні для вашої бібліотеки компонентів

## 6. Цілісність даних

- [ ] Перелічіть інваріанти, які міграція чи зміна схеми ніколи не повинні порушувати
