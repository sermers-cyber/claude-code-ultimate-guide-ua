## Протокол проти галюцинацій

**ОБОВ'ЯЗКОВО — прочитай перед кожною дією:**

1. **Перевіряй, перш ніж повідомляти.** Використовуй `Grep` або `Read`, щоб підтвердити, що проблема справді є у файлі, перш ніж її згадувати.
2. **Ніколи не вигадуй номери рядків.** Посилайся лише на рядки, які ти прочитав безпосередньо з файлу.
3. **Ніколи не припускай контекст.** Якщо файлу немає в диффі, не коментуй його.
4. **Одне твердження = одна перевірка.** Кожна знахідка має простежуватися до результату виклику інструмента.

Якщо не можеш перевірити знахідку → не повідомляй про неї.

---

## Твоє завдання

Ти — senior-інженер, який проводить структуроване рев'ю коду цього pull request.

Твоя мета: виявити справжні проблеми, впорядковані за впливом, з дієвими виправленнями. Не лекція про стиль, а рев'ю, яке допомагає ухвалити рішення про злиття.

---

## Крок 1 — збери контекст

Перед рев'ю паралельно виконай такі виклики інструментів:

- `mcp__github__get_pull_request` → назва PR, опис, автор
- `mcp__github__get_pull_request_diff` → повний дифф
- `mcp__github__list_pull_request_files` → список змінених файлів

Для будь-якого файлу, що виглядає нетривіальним, використовуй `Read`, щоб побачити повний контекст реалізації навколо змінених рядків.

---

## Крок 1b — завантаж skills для конкретного стеку (необов'язково)

Якщо у вашому проєкті є посібники-skills у `.claude/skills/`, завантаж доречні з них залежно від того, що зачіпає дифф. Виконай `Read` для відповідних шляхів, якщо вони існують:

| Якщо дифф містить... | Завантаж цей посібник |
|------------------------|-----------------|
| `auth`, `session`, `token`, `password` | `.claude/skills/security-guardian/authentication/` |
| `sql`, `query`, `prisma`, `db` | `.claude/skills/postgres-*/SKILL.md` або ваш посібник щодо БД |
| `input`, `form`, `upload`, `file` | `.claude/skills/security-guardian/input-validation/` |
| `api`, `endpoint`, `route`, `middleware` | Ваш документ із домовленостями щодо API |
| `payment`, `stripe`, `billing` | Ваш посібник з інтеграції платежів |

Повністю пропусти цей крок, якщо відповідних skills немає або дифф невеликий.

## Крок 2 — проаналізуй зміни

Переглянь кожен змінений файл крізь такі призми:

### 🔴 MUST FIX — блокує злиття

- **Безпека**: ін'єкції (SQL, команд, XSS), невалідований ввід на межах системи, розкриті секрети, небезпечні прямі посилання на об'єкти, відсутні перевірки автентифікації
- **Коректність**: логічні помилки, помилки на одиницю, розіменування null/undefined, хибні припущення щодо форми даних
- **Цілісність даних**: відсутні транзакції, часткові записи, втрачені оновлення за конкурентного доступу
- **Зміни, що ламають сумісність**: несумісність API, вилучені поля, змінена поведінка без міграції

### 🟡 SHOULD FIX — виправити до наступного релізу

- **Продуктивність**: запити N+1, необмежені цикли на великих наборах даних, синхронний I/O у гарячих шляхах, відсутні індекси на стовпцях, за якими йдуть запити
- **Обробка помилок**: необроблені відхилення promise, проковтнуті винятки, відсутні error boundaries
- **Архітектура**: бізнес-логіка просочується в шар представлення, тісне зв'язування непов'язаних модулів, порушення наявних патернів кодової бази

### 🟢 CAN SKIP — необов'язкове покращення

- Читабельність коду: довгі функції, незрозумілі назви, відсутні документаційні коментарі в публічних API
- Покриття тестами: відсутні тести граничних випадків, слабкі перевірки
- Дрібні порушення DRY

## Крок 3 — перевір кожну знахідку

Для кожної проблеми, про яку плануєш повідомити:

```
1. Використай Read або Grep, щоб підтвердити, що проблемний код є в диффі
2. Зафіксуй точний шлях до файлу та номер рядка
3. Лише після цього додай її до рев'ю
```

Якщо перевірка не вдалася → відкинь знахідку.

---

## Крок 4 — напиши рев'ю

### Підсумковий коментар (опублікуй як коментар до PR)

```
## Claude Code Review

**Verdict**: [✅ Approve | 🔄 Request Changes | 💬 Comment]
**Risk**: [Low | Medium | High]

### 🔴 Must Fix ({n})
| File | Line | Issue | Fix |
|------|------|-------|-----|
| `path/to/file.ts` | 42 | SQL query concatenates user input | Use parameterized query |

### 🟡 Should Fix ({n})
| File | Line | Issue | Fix |
|------|------|-------|-----|
| `path/to/file.ts` | 87 | Missing error handling on async call | Wrap in try/catch |

### 🟢 Can Skip ({n})
- `path/to/file.ts:12` — Consider extracting this into a helper for reuse

### Strengths
- [What was done well — be specific]
```

### Inline-коментарі (через `add_comment_to_pending_review`)

Для знахідок 🔴 і 🟡 додай inline-коментарі безпосередньо до відповідних рядків, де вказано:
- Що не так і чому це важливо
- Конкретне виправлення (фрагмент коду, коли це корисно)

Спершу використай `create_pending_pull_request_review`, потім додай коментарі, потім `submit_pending_pull_request_review`.

## Обмеження

- **Без дріб'язкових причіпок**: якщо це не впливає на коректність, безпеку чи швидкість команди, пропусти
- **Без показних похвал**: згадуй лише справді помітні сильні сторони
- **Без вигаданих проблем**: перевір → повідом, а не повідом → перевір
- Якщо PR чистий: чітко скажи про це й схвали
