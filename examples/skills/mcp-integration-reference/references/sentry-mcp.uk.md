# Довідник із Sentry MCP-сервера

Довідковий файл для Sentry MCP-сервера. Прочитайте його перед будь-якими викликами Sentry MCP. Він містить синтаксис запитів, відомі підводні камені та робочі приклади, що зменшують кількість збоїв викликів.

> Це шаблонний довідковий файл. Замініть вміст, специфічний для Sentry, еквівалентом для вашого MCP-сервера.

---

## Доступні інструменти

### `mcp__sentry-mcp__list_issues`

**Призначення**: отримати список issues з одного чи кількох проєктів.

**Ключові параметри**:
- `organization_slug` (обов'язковий): slug вашої організації в Sentry, а не її назва. Візьміть його з URL Sentry: `sentry.io/organizations/<slug>/`.
- `project_slug` (необов'язковий): обмежити одним проєктом. Пропустіть, щоб отримати з усіх проєктів.
- `query` (необов'язковий): пошуковий запит Sentry. Підтримує `is:unresolved`, `level:error`, `has:user`. За замовчуванням: `is:unresolved`.
- `limit` (необов'язковий): максимум повернених issues. За замовчуванням: 25. Максимум: 100.

**Підводні камені**:
- Slug організації та проєкту пишуться малими літерами через дефіс. Не використовуйте відображувану назву.
- Без `query` ви отримаєте всі статуси, включно з `resolved`. Завжди додавайте `is:unresolved`, якщо вам спеціально не потрібні вирішені issues.
- Верхня межа `limit` становить 100 за виклик. Для великих організацій використовуйте `cursor` для пагінації (див. нижче).

### `mcp__sentry-mcp__get_issue`

**Призначення**: отримати повні деталі однієї issue, включно з останньою подією та стек-трейсом.

**Ключові параметри**:
- `issue_id` (обов'язковий): числовий ID issue в Sentry. Візьміть його з `list_issues`.
- `organization_slug` (обов'язковий): те саме, що вище.

**Підводні камені**:
- Повертає лише найновішу подію. Якщо потрібна конкретна подія, скористайтеся `get_event` з ID події.
- Кадри стека за замовчуванням упорядковано від зовнішнього до внутрішнього. Нижній кадр зазвичай є точкою краху.

### `mcp__sentry-mcp__get_event`

**Призначення**: отримати повні деталі конкретної події в межах issue.

**Ключові параметри**:
- `event_id` (обов'язковий): повний 32-символьний ID події (формат UUID, без дефісів).
- `organization_slug` (обов'язковий): те саме, що вище.
- `issue_id` (обов'язковий): ID батьківської issue.

**Підводні камені**:
- ID подій нечутливі до регістру, але API чутливий до регістру. Використовуйте малі літери.
- Події старші за 90 днів можуть бути недоступні за стандартного плану зберігання.

### `mcp__sentry-mcp__search_events`

**Призначення**: шукати сирі події по issues. Повільніший за `list_issues`, але підтримує повнотекстові запити.

**Ключові параметри**:
- `query` (обов'язковий): повнотекстовий пошук. Підтримує фільтри за полями: `message:`, `level:`, `user.id:`, `url:`, `transaction:`.
- `project_slug` (необов'язковий): обмежити одним проєктом. Обов'язковий, якщо в організації багато проєктів (продуктивність).
- `start` / `end` (необов'язкові): мітки часу ISO 8601. За замовчуванням: останні 24 години.
- `limit` (необов'язковий): за замовчуванням: 10. Максимум: 100.

**Підводні камені**:
- Повнотекстовий пошук нечутливий до регістру, але фільтри за полями вимагають точного збігу. `level:ERROR` не спрацює; використовуйте `level:error`.
- Часові діапазони мають бути в ISO 8601: `2026-04-10T00:00:00Z`. Відносні формати на кшталт `now-24h` тут не підтримуються (для відносних діапазонів використовуйте `list_issues`).
- Без `project_slug` у великих організаціях `search_events` завершується тайм-аутом. Під час пошуку подій завжди обмежуйте проєктом.

## Синтаксис запитів

### Пошуковий запит Sentry (для параметра `query` у `list_issues` і `search_events`)

```
is:unresolved                          # Unresolved issues only
is:unresolved level:error              # Unresolved errors (not warnings)
is:unresolved has:user                 # Issues affecting identified users
is:unresolved times_seen:>100          # High-frequency issues
project:api-service is:unresolved      # Scope to one project
assigned:me is:unresolved              # Issues assigned to current user
!has:assignee is:unresolved            # Unassigned issues
```

### Пагінація

Для організацій з багатьма issues використовуйте курсорну пагінацію:
1. Перший виклик: `list_issues(..., limit=100)` - відповідь містить поле `cursor`
2. Наступна сторінка: `list_issues(..., limit=100, cursor="<cursor from previous response>")`
3. Зупиніться, коли у відповіді немає поля `cursor` або кількість issues < limit

## Відомі патерни та винятки

Під час аналізу issues ці патерни зазвичай є шумом і їх слід виключати зі звітів, якщо не запитано інше:

| Патерн | Причина виключення |
|---------|-------------------|
| Помилки `404` на `/static/` або `/assets/` | Очікувана поведінка: браузер запитує застарілі URL ресурсів після деплою |
| `ChunkLoadError` у фронтенд-бандлах | Зазвичай спричинена тим самим таймінгом деплою, а не багом у коді |
| `ResizeObserver loop limit exceeded` | Попередження на рівні браузера, дій не потребує |
| Помилки ендпоінта health check | Інфраструктура моніторингу, не видима користувачам |

Якщо ви виключаєте issue, явно вкажіть це в розділі «Out of Scope» звіту.

## Робочі приклади

### Отримати топ невирішених помилок у продакшені

```
list_issues(
  organization_slug="your-org",
  query="is:unresolved level:error",
  limit=50
)
```

### Отримати issues із конкретного проєкту за останній тиждень

```
list_issues(
  organization_slug="your-org",
  project_slug="api-service",
  query="is:unresolved",
  limit=100
)
```

### Отримати повний стек-трейс конкретної issue

```
get_issue(
  organization_slug="your-org",
  issue_id="1234567"
)
```

## Адаптація цього файлу

Коли робите форк цього шаблону для іншого MCP (Datadog, PagerDuty, Linear тощо):

1. Замініть «Sentry» на назву вашого MCP-сервера скрізь
2. Замініть назви інструментів (`mcp__sentry-mcp__*`) на справжні назви інструментів вашого MCP
3. Задокументуйте 2-3 найпоширеніші помилки параметрів для кожного інструмента
4. Додайте синтаксис запитів, специфічний для вашого MCP (діалект SQL, синтаксис фільтрів тощо)
5. Додайте розділ «Відомі патерни та винятки» для шуму у вашому джерелі даних
6. Включіть 3-5 робочих прикладів, що покривають 80% випадків використання

Мета: після прочитання цього файлу Claude не повинен робити жодних синтаксичних помилок і жодних повторних викликів через хибний формат параметрів.
