# Виявлення сценаріїв використання Routines

Аналізує цю кодову базу та виявляє придатних кандидатів у Routine за трьома типами тригерів.

**Використання**: `/routines-discover` - аргументи не потрібні. Запустіть у корені будь-якого проєкту.

---

## Що таке Routines

Routine — це автономна сесія Claude Code, що працює в хмарній інфраструктурі, керованій Anthropic, і запускається трьома способами:

| Тригер | Як спрацьовує |
|--------|---------------|
| **Розклад** | Повторювана каденція cron (мінімум 1 година) |
| **API** | HTTP POST на ендпоінт конкретного routine з bearer-токеном |
| **Події GitHub** | Події репозиторію: PR відкрито/змерджено, push, issue, запуск workflow тощо |

Кожен запуск клонує свіжу копію репозиторію GitHub, виконує повноцінну сесію Claude Code з налаштованими конекторами MCP (Slack, Linear, GitHub, Google Drive…) і може створювати гілки, відкривати PR, публікувати повідомлення та викликати зовнішні API. Локальний комп'ютер не потрібен.

**Добові ліміти**: Pro 5/день · Max 15/день · Team/Enterprise 25/день.

## Інструкції

### Крок 1: Прочитайте кодову базу

Перед генерацією будь-якого виводу мовчки прочитайте:
- `README.md` або `CLAUDE.md`, щоб зрозуміти призначення проєкту та стек
- `package.json`, `Cargo.toml`, `pyproject.toml` або еквівалент для залежностей
- `.github/workflows/`, щоб зрозуміти наявну CI/CD-автоматизацію
- Будь-яку конфігурацію моніторингу, деплою чи операцій, яку знайдете

Якщо конектори MCP налаштовано в `.claude/settings.json`, зазначте, які зовнішні сервіси підключено.

### Крок 2: Проаналізуйте за п'ятьма вимірами

Для кожного виміру конкретно подумайте про цей проєкт, перш ніж щось писати.

**1. Регулярна підтримка за розкладом**
Яку повторювану роботу наразі людина виконує вручну або має пам'ятати про неї?
Подумайте: аудити залежностей, тріаж застарілих issue/PR, звіти про нестабільність тестів, дрейф покриття, відстеження TODO-коментарів, виявлення мертвого коду, щоденні чи щотижневі підсумки.

**2. Реакції на події**
Що має відбуватися автоматично, коли PR відкрито, змерджено чи закрито, але сьогодні не відбувається, бо ні в кого не доходять руки?
Подумайте: чеклісти рев'ю, оновлення changelog, синхронізація між репозиторіями, сповіщення в Slack із контекстом, примусове застосування міток, оновлення документації при зміні API.

**3. Реагування на алерти та інциденти**
Які сигнали моніторингу існують? Коли щось ламається, що розробник робить першим?
Подумайте: зіставлення алерта з нещодавніми комітами, тріаж збірки, що падає, чернетка каркаса постмортему, маршрутизація помилки до потрібної команди.

**4. Синхронізація між системами**
Що розходиться сьогодні, бо синхронізація між двома системами ручна?
Подумайте: синхронізація двох SDK, оновлення сайту документації при зміні API, синхронізація GitHub issues з Linear, підтримання актуальності розділу зі статистикою в README.

**5. Автоматизація релізів і деплою**
Які кроки до або після деплою людина виконує вручну?
Подумайте: smoke-тести, нотатки до релізу, підвищення версій, сповіщення стейкхолдерів, підсумки go/no-go.

### Крок 3: Вивід

Для кожного виявленого сценарію створіть картку в такому форматі:

---

**[Назва]** · `schedule` / `api` / `github`

*Тригер*: [що його запускає: вираз cron, яка подія, яка зовнішня система]

*Вхід*: [що отримує Claude: стан репозиторію, payload події, тіло алерта]

*Вихід*: [що створює Claude: відкритий PR, опубліковане повідомлення, оновлений файл, створений issue]

*Цінність*: [заощаджений час або знижений ризик, конкретно]

*Блокери*: [відсутній конектор, потрібні секрети, потрібен GitHub App тощо, або "немає"]

---

Відсортуйте картки за **співвідношенням цінності до зусиль**, найвище першим.

Після всіх карток додайте розділ **Quick Wins**: два-три сценарії, які можна налаштувати менш ніж за 15 хвилин із поточним репозиторієм і конфігурацією конекторів.

*Цінність*: Заощаджує ~15 хв ручного тріажу щоранку, зменшує «гниття» PR

*Блокери*: Потрібен конектор Slack MCP
