# Розблокування сесії, сповільненої sandbox

Звіт про блокер писати дешево, а діяти за ним дорого. Цей skill виносить
перевірку наперед, щоб звіт, який дійде до мейнтейнера, був вартий його часу.

Наведені нижче виміри отримано на одній машині macOS, на Claude Code
2.1.220 (липень 2026) по 2.1.302 (жовтень 2026). Сприймайте цифри як
ілюстрацію, а метод як суть.

## Самодіагностика, усі одинадцять перевірок, перш ніж скаржитися

Виконуйте їх по порядку. Кожен крок каже, що запустити, що прочитати і який
висновок дозволяє зробити результат. Кроки 3, 3b, 5b і 5c окупаються найшвидше.

**1. Нічого не виводьте з опису sandbox у вашому системному prompt.**

Він перелічує шаблони `permissions.deny Read(...)` у `read.denyOnly`, на кшталт
`**/*.pem` чи `**/.env*`. Те, чи досягають ці шаблони підпроцесу Bash, змінювалося
між версіями й досі залежить від розташування: на 2.1.302 sandboxed `wc -c` прочитав
`.env` поза проєктом, який покривало таке правило, тоді як вересневий білд відмовив
`ls` для `.env` проєкту. Одна сесія дійшла висновку, що цілий Python-конвеєр не
можна запустити, лише за цим списком; насправді кожен його крок працював, коли
його виміряли. Вимірюйте саме те читання, яке вас цікавить.

**2. Переконайтеся, що команда, яку ви тестуєте, справді виконалася в sandbox.**

```bash
echo $TMPDIR
```

Шлях у корені тимчасового каталогу sandbox (`/tmp/claude-NNN`) означає, що вимір
зараховується. Системний тимчасовий каталог (`/var/folders/.../T/`) означає, що
виклик вийшов за межі sandbox, і нічого з подальшого нічого не доводить про
поведінку в sandbox. Виконуйте це окремим викликом: поєднання з тестованою
командою змінює відповідь (крок 3).

**3. Тестуйте команду окремо, нічого до неї, нічого після.**

Починаючи з v2.1.277, кожна команда у виклику має збігатися із записом
`excludedCommands`. `cd ... &&`, `;`, pipe, перенаправлення у файл або підстановка
`$(...)` залишають весь виклик у sandbox, навіть коли запис для вашого інструмента
існує й правильний.

Робоча директорія shell зберігається між викликами Bash усередині проєкту, тож
`cd` в тому ж рядку не потрібен. Передавайте шлях як аргумент, коли команда його
приймає.

```bash
# wrong: the call no longer matches any entry, everything stays sandboxed
cd /path/to/project && pnpm exec prisma migrate status
pnpm exec prisma migrate status | head -20
pnpm exec prisma migrate status > out.log 2>&1

# right: one command, bare, read the raw output
pnpm exec prisma migrate status
```

Попередня версія цього skill рекомендувала `cd /path && command` як правильну
форму. Кожен зонд подальшої діагностики містив `| head` або `&& echo`, і сесія
помилково дійшла висновку, що `excludedCommands` не діє.

**3b. Жодного inline-коду в лапках у вимірюваній команді.**

`node -e "console.log(require('fs').readdirSync('/path'))"` залишався в sandbox, тоді
як `node probe.js`, що робить точно те саме, виходив із нього. Лапки й дужки
ламають аналіз рядка. Запишіть код у файл інструментом Write, потім запустіть
його за шляхом.

**3c. Ніколи не приймайте зонд, введений користувачем у prompt `!`.**

Команда, введена з префіксом `!`, у більшості сесій виконується поза sandbox.
Вона вдається незалежно від стану `excludedCommands`, тож її успіх нічого не
доводить. Виміряно: той самий зонд повернув список каталогу, коли його ввели
через `!`, і `EPERM scandir`, коли його запустив agent у той самий момент.

**4. Перевірте, що бінарний файл існує, перш ніж звинувачувати sandbox.**

Обгортки, що стискають вивід, часто замінюють чітке повідомлення голим errno.
Тоді відсутній бінарний файл і відмова безпеки виглядають на екрані однаково.

```bash
command -v <binary>
```

Якщо нічого не повернуто, у вас проблема встановлення, а не політики.

**5. Читайте справжній код виходу, а не pipe.**

`cmd | head` повертає статус виходу `head`, ніколи не `cmd`. Відмовлене читання
раніше в сесії також видає попередження на кожній наступній команді, включно з
успішними, тож читайте останнє повідомлення, а не перше.

Це суперечить кроку 3: перенаправлення також залишає виклик у sandbox. Для
команди, що залежить від `excludedCommands`, беріть просту форму й приймайте
сирий вивід. Використовуйте перенаправлення нижче лише для команди, яка й так у
sandbox.

```bash
cmd > out.log 2>&1
echo "exit: $?"
```

**5b. Перевірте, чи не стоїть між вами та matcher переписувач команд.**

Саме це пояснило більшість блокерів у день, коли його було виявлено. Якщо hook
`PreToolUse` переписує команди Bash, наприклад проксі для стиснення токенів, що
перетворює `pnpm exec tsx x.ts` на `proxy pnpm exec tsx x.ts`, то запис
`excludedCommands` у вигляді `pnpm exec *` більше нічому не відповідає. Збігається
лише переписана форма.

Ознака — неузгодженість: деякі виключені команди виходять із sandbox, а інші ні,
без очевидної закономірності. Перевірте, чи ті, що працюють, випадково мають
префіксований запис у списку. Також можна подати hook синтетичний payload і
прочитати, чи переписує він команду; спершу перевірте команду, яку він точно
переписує, щоб порожню відповідь не сплутали зі зламаним зондом.

Будь-який запис, який ви просите, слід просити в обох формах, простій і з
префіксом, і з однаково вузьким охопленням в обох: префіксований `proxy git *`
покриває кожну підкоманду git.

**5c. Запис збігається з командою саме так, як вона написана.**

`git fetch origin` збігається з `git fetch *`. `git -C /path fetch origin` і
`git -c key=value fetch origin` не збігаються, бо опція стоїть перед дієсловом.
`pnpm --dir /path exec tsx x.ts` не збігається з `pnpm exec *`. Виклик бінарного
файлу за абсолютним шляхом теж не збігається. Кінцева зірочка вимагає принаймні
одного аргументу, тож простий `git fetch` не збігається з `git fetch *` і залишається
в sandbox. Перепишіть команду в канонічній формі, перш ніж щось вирішувати.

**5d. Зіставлення не проходить крізь скрипти чи цикли.**

Запис для `ps *` звільняє `ps`, набраний безпосередньо, а не скрипт, що викликає
`ps` всередині: рядок, поданий matcher, — це `bash script.sh`. Діагностичний
скрипт потребує власного запису, за власним шляхом, в обох формах (з ` *` і без).
Так само `for c in "top -l 1" "pgrep -x zsh"; do eval "$c"; done` залишається в
sandbox, навіть коли обидва інструменти виключено. Групування зондів для
економії часу дає хибні негативи.

**6. Якщо конфігурація змінилася після відкриття сесії, перезапустіть, якщо не знаєте, що ключ перезавантажується.**

Списки файлової системи, `credentials.files`, `excludedCommands` і мережевий
allowlist, за вимірами, застосовувалися до наступної команди без перезапуску.
Для будь-якого іншого ключа залишайте перезапуск як типовий варіант.

Якщо всі одинадцять перевірок пройдено, а блокер лишається, переходьте до шаблону
звіту.

## Мережа: заблокований хост чи неіснуючий хост

Allowlist доменів фільтрує навіть коли strict mode вимкнено. Вимірюйте з хостом,
про який ви знаєте, що він поза вашим списком і вбудованими типовими значеннями
продукту.

В auto mode на v2.1.271 і новіших хост, який команда не оголосила, відхиляється і
називається в результаті команди; прочитайте назву, перш ніж про щось просити. В
інших режимах тривалість підкаже, з якою невдачею ви зіткнулися: відмова через
allowlist зависала приблизно на 5-7 секунд на 2.1.220, тоді як ім'я хоста, що не
розв'язується, завершувалося менш ніж за 30 мілісекунд, зокрема коли шаблон із
символом підстановки в списку його вже покривав. Переконайтеся, що apex
відповідає, перш ніж просити додати домен.

Сирий TCP до зовнішнього хоста — окреме питання. Усе, що ігнорує змінні проксі, не
має виходу назовні: хмарні Postgres, MySQL, Redis і звичайний SSH усі падають, і
жоден запис домену цього не виправить. На macOS git через SSH теж падає, навіть
якщо хост дозволено. Команду потрібно виключити або запустити поза sandbox.

## Шаблон звіту

Заповнюйте його буквально. Не переказуйте помилку: перефразоване повідомлення
коштувало цілого дня хибно спрямованої роботи в проєкті, з якого походить цей skill.

```
Exact command typed: <literal copy-paste, every argument included>
Raw error received: <literal copy-paste, not summarized>
$TMPDIR at test time: <exact value, from a separate call>
Sandboxed: <yes if under the sandbox temp root, no otherwise>
Claude Code version: <claude --version>
Session opened before or after the last config change: <before / after / unknown>
Protocol steps already run: <1, 2, 3, 3b, 3c, 4, 5, 5b, 5c, 5d, 6, with each result>
Workarounds already tried: <list, or "none">
Real impact: <which task is blocked, since when>
```

## Ескалація

Передайте заповнений шаблон тому, хто може редагувати файл налаштувань. Не
редагуйте його самі з Bash: записи у файли налаштувань відхиляються для команди в
sandbox. В auto mode класифікатор також може відмовити в Edit власних налаштувань
як самомодифікації; підготуйте файл-кандидат деінде, покажіть diff і дайте людині
застосувати його.

Ключі, які варто знати в `sandbox`: `excludedCommands`, `credentials.files`,
`credentials.envVars`, `filesystem.allowWrite`, `filesystem.denyRead`,
`network.allowedDomains` і `network.strictAllowlist`. Два з них вводять в оману.

`credentials.envVars` у режимі `deny` скидає змінну перед кожною командою в
sandbox, але файл запуску shell може встановити її знову. zsh читає `~/.zshenv` при
кожному старті, тож на 2.1.302 дві заборонені змінні, експортовані там, усе одно
були встановлені всередині sandbox, тоді як заборонена змінна, присутня лише в
середовищі запуску Claude Code, зникла. Перевіряйте зондом, що друкує лише `set`
чи `unset`, ніколи значення, і порівнюйте `zsh -c` із `zsh -f -c`. Виправлення:
захистіть експорт через `[[ -n $CLAUDECODE ]] ||`, потім повторіть зонд.

`allowUnsandboxedCommands: false` не нейтралізує `excludedCommands` із ваших
власних налаштувань. Перший закриває аварійний вихід на рівні виклику, другий
виключає іменовані команди. Коли `false` походить із managed settings або
`--settings`, sandbox стає таким, що вимагає адміністратора, і `excludedCommands`
репозиторію ігноруються (v2.1.282 і новіші).

## Обмеження без виправлення в налаштуваннях усередині sandbox

Перевірено. Не відкривайте розслідування з цих питань знову. Кожне з них зникає,
коли команда виконується поза sandbox через простий збіг `excludedCommands`, ціною
повного доступу для цієї команди.

| Обмеження | Знахідка | Відомий обхідний шлях |
|---|---|---|
| Setuid-бінарні файли | `ps`, `top`, `su`, `login` не можуть виконатися в sandbox | виключіть просту команду (`ps *`) або `lsof -nP -iTCP -sTCP:LISTEN` без зміни конфігурації |
| Сокети `AF_UNIX` | `bind()` відхиляється в sandbox, налаштування локального прив'язування покривають лише TCP | запустіть просту команду під її виключенням або зберіть bundle і запустіть звичайний `node` |
| Прямий DNS | відрізаний для всіх, увесь HTTP іде через локальний проксі | виключіть інструмент, якщо йому потрібні сирі сокети |
| `.idea/` і `.vscode/` | запис файлу всередині відхиляється в поточному проєкті (захищені шляхи) | виключіть команду встановлення в обох формах |

Тож збій setuid-бінарного файлу чи сокета часто є проблемою кроку 3: команду було
виключено, але з'єднано з чимось іншим.

Щодо DNS: ніколи не пропонуйте додавати загальний діагностичний інструмент на
кшталт `dig` до списку виключень. Він повертатиме правильні розв'язання, поки
решта сесії залишається відрізаною, а це створює саме той вид хибного діагнозу, який
цей skill покликаний запобігти.

Обмеження `.idea` важливіше, ніж здається. Відмова стосується поточного проєкту,
тож аудит із сусіднього репозиторію повідомить, що нічого не заблоковано, і буде
хибним.
