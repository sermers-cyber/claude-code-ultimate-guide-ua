# Guide recap

Генерує контент для соцмереж із записів CHANGELOG.md. За замовчуванням створює 8 результатів (4 формати x 2 мови).

## Коли використовувати

- Після виконання `/release`, щоб підготувати анонси для соцмереж
- Щотижня, щоб підсумувати кілька релізів
- Перед публікацією у LinkedIn, Twitter/X, розсилці чи Slack

## Використання

```
/guide-recap latest              # Latest released version
/guide-recap v3.20.5             # Specific version
/guide-recap week                # Current week (Monday to today)
/guide-recap week 2026-01-27     # Specific week (Monday to Sunday)
```

### Прапорці

| Прапорець | Ефект | За замовчуванням |
|------|--------|---------|
| `--interactive` | Покроковий режим: вибір ракурсу, аудиторії, акценту | Вимкнено (автоматична чернетка) |
| `--format=X` | Один формат: `linkedin`, `twitter`, `newsletter`, `slack` | Усі 4 формати |
| `--lang=X` | Одна мова: `fr`, `en` | Обидві: FR + EN |
| `--save` | Зберегти результат у `[project-docs]/social-posts/` | Лише показати |
| `--force` | Генерувати, навіть якщо є лише записи про супровід | Пропускати низькі оцінки |

## Робочий процес (7 кроків)

### Крок 1: Розбір вхідних даних

Розберіть `$ARGUMENTS`, щоб визначити режим:

| Вхід | Режим | Ціль |
|-------|------|--------|
| `latest` | Одна версія | Перший `## [X.Y.Z]` після `[Unreleased]` |
| `vX.Y.Z` або `X.Y.Z` | Одна версія | Точний збіг версії |
| `week` | Діапазон тижня | Понеділок поточного тижня -> сьогодні |
| `week YYYY-MM-DD` | Діапазон тижня | Той понеділок -> наступна неділя |

Якщо аргументу немає або він некоректний, покажіть інструкцію з використання й завершіть роботу.

### Крок 2: Витяг записів CHANGELOG

Прочитайте `CHANGELOG.md` із кореня проєкту.

**Одна версія:**
1. Знайдіть рядок, що збігається з `## [{version}]`
2. Витягніть увесь вміст до наступного рядка `## [`
3. Розберіть розділи `### Added`, `### Changed`, `### Fixed`

**Діапазон тижня:**
1. Зберіть усі записи `## [X.Y.Z] - YYYY-MM-DD`, дата яких потрапляє в діапазон
2. Розберіть усі розділи з усіх відповідних версій

**Помилка: версію не знайдено** -> виведіть 5 останніх версій і запропонуйте `latest`.
**Помилка: за тиждень немає записів** -> покажіть дату останнього релізу й запропонуйте цю версію.

### Крок 3: Категоризація записів

Для кожного запису верхнього рівня (маркер першого рівня під `###`) призначте категорію:

| Категорія | Вага | Ознаки |
|-----------|--------|-----------|
| `NEW_CONTENT` | 3 | Нові файли, нові розділи, нові діаграми, нові питання вікторини |
| `GROWTH_METRIC` | 2 | Зростання кількості рядків, зміни кількості елементів |
| `RESEARCH` | 1 | Оцінювання ресурсів, інтеграції зовнішніх джерел |
| `FIX` | 1 | Під `### Fixed`, виправлення |
| `MAINTENANCE` | 0 | Оновлення README, синхронізація бейджів, синхронізація лендингу, оновлення лічильників |

Докладні правила класифікації дивіться в `references/changelog-parsing-rules.md`.

### Крок 4: Перетворення на цінність для користувача

Застосуйте відповідності з `references/content-transformation.md`:

- Технічна мова -> користь для користувача
- Витягніть конкретні числа
- Вказуйте названі джерела
- Групуйте пов'язані записи

Перевірте результат за чеклістом DO/DON'T у `references/tone-guidelines.md`.

### Крок 4b: Інтерактивний режим (лише з `--interactive`)

Якщо задано прапорець `--interactive`, вставте між кроками 4 і 5:

1. Покажіть кандидатів на акцент з оцінками:
   ```
   Highlights (by score):
   [14] 4 new ASCII diagrams (16 -> 20)     [NEW_CONTENT]
   [ 9] 30 new quiz questions (227 -> 257)   [NEW_CONTENT]
   [ 6] Docker sandbox isolation guide        [NEW_CONTENT]
   [ 1] README updated                        [MAINTENANCE]
   ```

2. Запитайте про ракурс:
   - Авто (запис із найвищою оцінкою стає гачком)
   - Користувач обирає конкретний запис як гачок
   - Власний ракурс (користувач задає тему)

3. Запитайте про цільову аудиторію:
   - `devs` (технічна глибина)
   - `tech-leads` (акцент на впливі)
   - `general` (доступна мова)
   - `all` (за замовчуванням, збалансовано)

4. Запитайте про основний акцент:
   - Авто (найвища оцінка)
   - Користувач обирає зі списку

5. Підтвердьте вибір і переходьте до кроку 5.

### Крок 5: Оцінювання та відбір

Обчисліть оцінку для кожного запису:

```
score = (category_weight * 3)
      + (has_number * 2)
      + (named_source * 1)
      + (new_file * 1)
      + (min(impact_files, 3))
      + (breaking * 2)
```

Оберіть 3-4 записи з найвищими оцінками. Найвища оцінка = рядок-гачок.

**Якщо всі оцінки < 3**: виведіть «No social content recommended for this version. Use `--force` to generate anyway.» і завершіть роботу (якщо не задано `--force`).

### Крок 6: Генерація контенту

Для кожного запитаного формату (за замовчуванням усі 4) і мови (за замовчуванням обидві):

1. Прочитайте відповідний шаблон з `assets/`
2. Заповніть поля шаблону за допомогою оцінених і перетворених записів
3. Застосуйте чекліст якості з tone-guidelines.md

**Посилання:**

| Формат | Ціль посилання |
|--------|-------------|
| LinkedIn | URL сайту-лендингу |
| Twitter | URL репозиторію GitHub |
| Розсилка | Обидва (лендинг + GitHub) |
| Slack | URL репозиторію GitHub |

**URL:**
- Лендинг: `https://{DOMAIN}/`
- GitHub: `https://github.com/{OWNER}/{REPO}`

### Крок 7: Вивід

Покажіть кожен згенерований допис у блоці коду, позначеному форматом і мовою:

```
## LinkedIn (FR)

```text
[content]
`` `

## LinkedIn (EN)

```text
[content]
`` `

## Twitter/X (FR)

```text
[content]
`` `

...
```

З прапорцем `--save`: запишіть усі результати в `[project-docs]/social-posts/YYYY-MM-DD-vX.Y.Z.md` (для версії) або `[project-docs]/social-posts/YYYY-MM-DD-week.md` (для тижня). Створіть директорію `[project-docs]/social-posts/`, якщо її немає.

## Обробка помилок

| Помилка | Реакція |
|-------|----------|
| Немає аргументу | Показати блок з використанням |
| Некоректний аргумент | Показати блок з використанням і прикладами |
| Версію не знайдено | Вивести 5 найновіших версій, запропонувати `latest` |
| За тиждень немає записів | Показати дату останнього релізу, запропонувати версію |
| Усі записи MAINTENANCE (оцінка 0) | «No social content recommended. Use `--force` to override.» |
| CHANGELOG.md не знайдено | «CHANGELOG.md not found in project root.» |

## Довідкові файли

- `references/tone-guidelines.md` - правила DO/DON'T, бюджет емодзі, регістр мови
- `references/changelog-parsing-rules.md` - формат CHANGELOG, витяг, алгоритм оцінювання
- `references/content-transformation.md` - відповідності «технічне -> цінність для користувача» (30+)
- `assets/linkedin-template.md` - ~1300 символів, гачок + маркери + CTA + хештеги
- `assets/twitter-template.md` - 280 символів: один твіт або тред із 2-3 твітів
- `assets/newsletter-template.md` - ~500 слів, структуровані розділи
- `assets/slack-template.md` - компактно, багато емодзі, форматування Slack
- `examples/version-output.md` - повний приклад результату для v3.20.5
- `examples/week-output.md` - повний приклад результату для тижня 2026-01-27

## Поради

- Запускайте `/guide-recap latest` одразу після `/release`, щоб підготувати дописи для соцмереж
- Кілька перших разів використовуйте `--interactive`, щоб зрозуміти оцінювання
- Використовуйте `--format=linkedin --lang=fr`, коли потрібен лише один конкретний результат
- Результати `--save` ігноруються git через конвенцію `[project-docs]/`
- Перегляньте й персоналізуйте перед публікацією (це чернетки, а не фінальний текст)
