# Skill воркфлоу TDD

## Цикл TDD

```
RED → GREEN → REFACTOR
 ↑__________________|
```

### 1. RED: напишіть тест, що падає
- Напишіть найменший тест, який падає
- Тест має падати з правильної причини
- Переконайтеся, що тест справді запускається

### 2. GREEN: змусьте його пройти
- Напишіть мінімум коду, щоб тест пройшов
- Поки не оптимізуйте
- Нічого страшного, якщо код негарний

### 3. REFACTOR: наведіть лад
- Покращте структуру коду
- Приберіть дублювання
- Тримайте тести зеленими

## Найкращі практики TDD

### Угода про іменування тестів
```
should_[expected behavior]_when_[condition]
```

Приклади:
- `should_return_empty_array_when_no_items`
- `should_throw_error_when_invalid_input`
- `should_calculate_total_when_items_present`

### Структура тесту (AAA)
```typescript
it('should calculate discount when coupon applied', () => {
  // Arrange - Підготуйте тестові дані
  const cart = new Cart();
  cart.addItem({ price: 100 });
  const coupon = new Coupon('10OFF', 10);

  // Act - Виконайте поведінку
  cart.applyCoupon(coupon);

  // Assert - Перевірте результат
  expect(cart.total).toBe(90);
});
```

### Ізоляція тестів
- Кожен тест має бути незалежним
- Жодного спільного стану між тестами
- Використовуйте `beforeEach` для спільного налаштування
- Прибирайте в `afterEach`

## Приклад воркфлоу TDD

### Функція: додати товар до кошика

**Крок 1: RED**
```typescript
describe('Cart', () => {
  it('should add item to cart', () => {
    const cart = new Cart();
    cart.addItem({ id: 1, name: 'Book', price: 29.99 });
    expect(cart.items).toHaveLength(1);
  });
});
```
Запустіть тест → ПАДАЄ (Cart не існує)

**Крок 2: GREEN**
```typescript
class Cart {
  items = [];

  addItem(item) {
    this.items.push(item);
  }
}
```
Запустіть тест → ПРОХОДИТЬ

**Крок 3: REFACTOR**
```typescript
class Cart {
  private _items: CartItem[] = [];

  get items(): ReadonlyArray<CartItem> {
    return this._items;
  }

  addItem(item: CartItem): void {
    this._items.push(item);
  }
}
```
Запустіть тест → Усе ще ПРОХОДИТЬ

### Наступна ітерація: обчислення підсумку
Повторюйте цикл для кожної нової поведінки.

## Коли використовувати TDD

### Добре підходить для TDD
- Бізнес-логіка
- Складні алгоритми
- Кінцеві точки API
- Керування станом
- Утилітні функції

### Менш придатне
- Розмітка UI (краще візуальне тестування)
- Міграції бази даних
- Зовнішні інтеграції (використовуйте інтеграційні тести)
- Дослідницький/прототипний код

## Типові помилки TDD

1. **Занадто великий тест** - починайте з найменшого тесту, що падає
2. **Занадто багато коду** - лише стільки, щоб тест пройшов
3. **Пропуск рефакторингу** - технічний борг накопичується
4. **Тестування реалізації** - тестуйте поведінку, а не внутрішню будову
5. **Ігнорування тестів, що падають** - виправте або видаліть, ніколи не пропускайте

## Тестові дублери

| Тип | Призначення | Приклад |
|------|---------|---------|
| Stub | Повертає фіксовані дані | `jest.fn().mockReturnValue(42)` |
| Mock | Перевіряє взаємодії | `expect(mock).toHaveBeenCalled()` |
| Spy | Відстежує виклики | `jest.spyOn(obj, 'method')` |
| Fake | Спрощена реалізація | База даних в пам'яті |
