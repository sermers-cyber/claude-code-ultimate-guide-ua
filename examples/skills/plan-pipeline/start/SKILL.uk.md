# /plan-pipeline:start: 5-фазове планування

Проаналізуйте запит і створіть повний план реалізації через структуровані фази. Код не пишеться. Кожне значуще рішення фіксується. Виконайте `/clear` після цієї команди, перш ніж запускати `/plan-pipeline:validate`.

---

## Фаза 1: Аналіз PRD і дизайну

### Крок 1.1: Аналіз PRD

*Пропустіть, якщо PRD немає (рефакторинг, зміна інфраструктури, виправлення бага).*

Прочитайте всі файли PRD і `docs/INFORMATION_ARCHITECTURE.md`, якщо він є. Проскануйте кодову базу, щоб зрозуміти поточний стан реалізації.

Подайте висновки у 3 групах:

**Відсутні вимоги**: критерії прийняття, яких немає або які неповні
**Неоднозначні вимоги**: пункти з кількома допустимими інтерпретаціями
**Питання відповідності**: безпека, приватність даних, наслідки для контрактів API

Для кожного висновку: запропонуйте варіанти з конкретними плюсами/мінусами. Обговоріть із користувачем. Зафіксуйте кожне рішення у файлі плану в розділі `## Decisions`, перш ніж рухатися далі. Не переходьте далі за нерозв'язані неоднозначності.

### Крок 1.2: Аналіз дизайну

*Пропустіть, якщо UI-змін немає в обсязі.*

Прочитайте: `DESIGN_SYSTEM.md`, наявні UX ADR, UX-правила з CLAUDE.md.

Підготуйте специфікації для:
- **Інвентар екранів**: нові/змінені екрани, розміщення маршрутів, аудит повторного використання компонентів
- **Каталог станів**: порожній, завантаження, заповнений, помилка та частковий стани для кожного інтерактивного елемента
- **Специфікації взаємодії**: користувацькі потоки (щасливий шлях + альтернативи), поведінка фокусу/клавіатури
- **Специфікації анімацій**: зіставте кожну взаємодію з наявними keyframes або опишіть нові, включно з fallback для `prefers-reduced-motion`
- **Адаптивна поведінка**: breakpoints, рішення щодо розбіжностей web/mobile
- **Доступність**: вибір патерна WAI-ARIA, live regions, видимість помилок

Створіть Design ADR для значущих UX-рішень (вибір патерна взаємодії, нова конвенція анімації, розбіжність платформ). Дрібні рішення щодо розмітки записуйте безпосередньо у файл плану.

---

## Фаза 2: Технічний аналіз

Запустіть 1-2 Explore agents для цільового дослідження кодової бази. Запускайте їх у фоні через інструмент Task.

Поки agents працюють, перевірте:
- Наявні ADR у `docs/adr/`: якщо 3+ ADR підтверджують рішення → розв'язати автоматично без запитань
- PATTERNS.md: застосовуйте підтверджені патерни напряму

Коли agents повернуться: представте архітектурні рішення з 2-3 варіантами кожне, конкретними плюсами/мінусами та рекомендацією. Запитайте думку користувача щодо кожного нерозв'язаного рішення.

Для кожного значущого рішення:
1. Створіть `docs/adr/ADR-XXXX.md` у стандартному форматі Нігарда (Context / Decision / Status / Consequences)
2. Оновіть `docs/adr/PATTERNS.md` новим спостереженням

---

## Фаза 3: Оцінка обсягу

Застосуйте правила тригерів, щоб визначити, які дослідницькі agents потрібні. Представте запропоновану команду з обґрунтуванням кожного включення.

**Пул дослідницьких agents:**

| Agent | Тригер | Модель |
|-------|--------|--------|
| `code-explorer` | Завжди | Sonnet |
| `arch-researcher` | Зміни торкаються 2+ архітектурних шарів | Sonnet |
| `database-analyst` | Будь-яка зміна схеми БД | Sonnet |
| `security-analyst` | Auth, платежі, PII, RBAC, rate limiting | Opus |
| `test-analyzer` | Нетривіальна функція (не лише виправлення бага) | Sonnet |
| `cross-platform-specialist` | Потрібна паритетність web + mobile | Sonnet |
| `native-app-specialist` | Завдання торкаються mobile/native UI-пакета | Sonnet |
| `design-system-researcher` | У обсязі є зміни UI | Sonnet |
| `dependency-researcher` | Додаються нові пакети | Sonnet |
| `devops-specialist` | Зміни Docker, змінних середовища, CI/CD | Sonnet |
| `integration-researcher` | Нові сервіси, бібліотеки, конфігурація OTEL | Opus |
| `planning-coordinator` | Завжди, коли обрано 2+ agents | Opus |

**Позначки рівнів** (описові, не приписові):
- Рівень 0 (0 agents): Соло (дослідження inline, без запуску agents)
- Рівень 1 (1-3 agents): Цільовий
- Рівень 2 (4-6 agents): Стандартний
- Рівень 3 (7-9 agents): Комплексний
- Рівень 4 (10+ agents): Повний спектр

Скажіть користувачу: "Рекомендую команду **[Рівень N - Назва]**: [список agents з однорядковим обґрунтуванням кожного]. Бажаєте додати або прибрати якихось agents?"

Дочекайтеся схвалення перед Фазою 4.

---

## Фаза 4: Дослідження та створення плану

**Рівень 0**: Проведіть дослідження inline. Напишіть план безпосередньо без запуску agents.

**Рівень 1+**: Запустіть схвалених agents паралельно через інструмент Task (run_in_background: true). Для кожного agent надайте:
- Його конкретну дослідницьку область
- Відповідні файли/зони для вивчення
- Запитання, на які він має відповісти

Стежте за agents, читаючи їхні вихідні файли напряму (TaskOutput видалено у v2.1.278; натомість використовуйте `Read` для шляху виводу, про який повідомив agent). Повідомляйте про прогрес: "3/6 agents завершили..."

Коли всі agents повернуться: якщо запускали `planning-coordinator`, передайте йому всі звіти agents і доручіть синтезувати фінальний план. Інакше синтезуйте самостійно.

**Структура файлу плану** (`docs/plans/plan-{name}.md`):

```markdown
# Plan: {feature-name}
Created: {date} | Branch: {branch-name} | Tier: {N}

## Summary
One paragraph: what this implements and why.

## Decisions
Decisions recorded during Phase 1 (PRD analysis).

## Architecture
ADRs created, patterns applied, architectural choices made.

## Tasks
Ordered task list with layers (1 = foundation, 2 = depends on 1, etc.)

### Layer 1
- [ ] Task A: description, files affected, acceptance criteria
- [ ] Task B: description, files affected, acceptance criteria

### Layer 2
- [ ] Task C (depends on A): description, files affected, acceptance criteria

## Test Plan
How each task will be verified. TDD tasks marked explicitly.

## Integration Verification
Smoke test commands to run post-execution (if backend/services in scope).

## Out of Scope
What this plan explicitly does not address.
```

Коміт: файл плану + файли ADR + маніфести звітів agents.

## Фаза 5: Фіналізація метрик

Запишіть часові мітки, тривалість фаз, кількість agents і оцінки вартості в `docs/plans/metrics/{name}.json`. Закомітьте.

## Автоматичний перехід

Якщо Фаза 1 не дала нерозв'язаних неоднозначностей, а Фаза 2 не дала нерозв'язаних рішень: автоматично запустіть `/plan-pipeline:validate` без запитання.

Якщо було будь-яке обговорення з людиною: запитайте "Готові перевірити цей план?" перед продовженням.

---

## Використання

```
/plan-pipeline:start
```

Надайте опис функції або вкажіть файл PRD, коли команда запитає. Решту команда робить інтерактивно.

## Коли використовувати

Використовуйте для будь-якої нетривіальної функції: усього, що зачіпає понад 2 файли, містить архітектурні рішення або де помилка планування буде дорогою для виправлення.

Для простих змін (одруківки, тривіальні рефакторинги): натомість використовуйте режим `/plan`.

## Позиція в конвеєрі

```
/plan-pipeline:ceo-review    → продуктовий напрям зафіксовано
/plan-pipeline:eng-review    → архітектуру зафіксовано
/plan-pipeline:start         → створити план реалізації   ← ви тут
/plan-pipeline:validate      → перевірити перед виконанням
/plan-pipeline:execute       → виконати до змердженого PR
```
