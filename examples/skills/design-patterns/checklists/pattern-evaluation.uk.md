# Чеклист оцінювання якості дизайн-патернів

Систематичні критерії для оцінювання якості реалізацій дизайн-патернів.

## Критерії оцінювання

Кожен критерій оцінюється за шкалою **0-10**, де:
- **9-10**: зразкова, еталонна реалізація
- **7-8**: добра, можливі незначні покращення
- **5-6**: прийнятна, є помітні проблеми, які слід виправити
- **3-4**: проблемна, потрібен суттєвий рефакторинг
- **0-2**: неправильна або з серйозними вадами

**Загальна оцінка** = середнє арифметичне оцінок за всіма критеріями

---

## 1. Коректність (0-10)

**Питання**: чи правильно реалізація відтворює канонічну структуру патерну?

### Рекомендації щодо оцінювання

| Оцінка | Опис |
|-------|-------------|
| 9-10  | Ідеальне дотримання структури патерну, усі ролі присутні й реалізовані правильно |
| 7-8   | Незначні відхилення, що не шкодять задуму патерну |
| 5-6   | Є структурні проблеми, але патерн впізнаваний і працює |
| 3-4   | Суттєві структурні проблеми, патерн реалізований лише частково |
| 0-2   | Неправильна реалізація, зовсім не відповідає патерну |

### Чеклист

**Singleton**:
- [ ] Приватний конструктор
- [ ] Статичний метод getInstance()
- [ ] Приватне статичне поле екземпляра
- [ ] Потокобезпечність (якщо доречно)
- [ ] Щоразу повертає той самий екземпляр

**Observer**:
- [ ] Інтерфейс Subject з attach/detach/notify
- [ ] Інтерфейс Observer з методом update
- [ ] Subject зберігає список observers
- [ ] Notify викликає update у всіх observers
- [ ] Observers можна додавати й видаляти динамічно

**Strategy**:
- [ ] Інтерфейс Strategy, що описує алгоритм
- [ ] Context тримає посилання на strategy
- [ ] Context делегує виконання strategy
- [ ] Strategies взаємозамінні
- [ ] Клієнт може задати strategy під час виконання

**Factory Method**:
- [ ] Factory method повертає інтерфейс/абстрактний клас
- [ ] Підкласи перевизначають factory method
- [ ] Клієнтський код залежить від інтерфейсу, а не від конкретних класів
- [ ] Логіка створення інкапсульована

**Decorator**:
- [ ] Decorator реалізує той самий інтерфейс, що й обгорнутий об'єкт
- [ ] Decorator тримає посилання на обгорнутий об'єкт
- [ ] Decorator делегує виклики обгорнутому об'єкту
- [ ] Можна складати кілька decorators у стек
- [ ] Дотримується контракт інтерфейсу

### Типові помилки (штрафи)

- **-2**: відсутній ключовий компонент (наприклад, Singleton без приватного конструктора)
- **-3**: неправильне делегування (наприклад, Decorator не викликає обгорнутий об'єкт)
- **-4**: порушення інваріантів патерну (наприклад, Singleton повертає різні екземпляри)

## 2. Тестованість (0-10)

**Питання**: наскільки легко написати unit-тести для цієї реалізації?

### Рекомендації щодо оцінювання

| Оцінка | Опис |
|-------|-------------|
| 9-10  | Легко мокається, залежності ін'єктуються, немає глобального стану |
| 7-8   | Тестується з невеликим налаштуванням, є деяке зчеплення |
| 5-6   | Потребує значного налаштування тестів, помірне зчеплення |
| 3-4   | Важко тестувати, жорстке зчеплення, глобальний стан |
| 0-2   | Майже неможливо тестувати, статичні залежності, немає точок ін'єкції |

### Чеклист

- [ ] Залежності ін'єктуються (не створюються всередині)
- [ ] Використовуються інтерфейси (можна замокати)
- [ ] Немає жорстко прописаних залежностей
- [ ] Немає доступу до глобального стану (або мінімальний)
- [ ] Можлива ізоляція тестів (тести не впливають один на одного)
- [ ] Немає статичних методів, які не можна замокати
- [ ] Побічні ефекти мінімізовані або контрольовані

### Тривожні ознаки (штрафи)

- **-2**: використання `getInstance()` замість dependency injection
- **-2**: жорстко прописане створення екземплярів конкретних класів
- **-3**: доступ до глобального стану (window, global, process.env у бізнес-логіці)
- **-3**: статичні методи з побічними ефектами
- **-4**: немає способу ін'єктувати test doubles

### Приклади

**Погана тестованість (оцінка: 2/10)**:
```typescript
class PaymentService {
  processPayment(amount: number) {
    // Важко тестувати: залежність створюється всередині
    const gateway = PaymentGateway.getInstance();
    // Важко тестувати: доступ до глобальної конфігурації
    const apiKey = process.env.PAYMENT_API_KEY;
    return gateway.charge(amount, apiKey);
  }
}
```

**Добра тестованість (оцінка: 9/10)**:
```typescript
class PaymentService {
  constructor(
    private gateway: IPaymentGateway,
    private config: Config
  ) {}

  processPayment(amount: number) {
    const apiKey = this.config.getPaymentApiKey();
    return this.gateway.charge(amount, apiKey);
  }
}

// Легко тестувати з моками
const mockGateway = { charge: jest.fn() };
const mockConfig = { getPaymentApiKey: () => 'test-key' };
const service = new PaymentService(mockGateway, mockConfig);
```

## 3. Принцип єдиної відповідальності (0-10)

**Питання**: чи має компонент одну чітко визначену відповідальність?

### Рекомендації щодо оцінювання

| Оцінка | Опис |
|-------|-------------|
| 9-10  | Єдина сфокусована відповідальність; у класу одна причина для змін |
| 7-8   | Здебільшого сфокусований, є незначні другорядні задачі |
| 5-6   | Кілька пов'язаних відповідальностей |
| 3-4   | Кілька непов'язаних відповідальностей |
| 0-2   | God class з багатьма відповідальностями |

### Чеклист

- [ ] Клас/модуль має одне чітке призначення
- [ ] Усі методи стосуються основної відповідальності
- [ ] Зміна однієї вимоги не вимагає змінювати цей клас
- [ ] Назва класу чітко відображає його відповідальність
- [ ] У назві чи описі класу немає «і» / «and» (наприклад, «UserManagerAndLogger» погано)

### Тривожні ознаки (штрафи)

- **-2**: клас обробляє 2 різні задачі
- **-3**: клас обробляє 3 і більше задач
- **-4**: God class (>20 методів, >300 рядків)
- **-1**: методи, не пов'язані з основною відповідальністю

### Приклади

**Погана SRP (оцінка: 3/10)**:
```typescript
class UserService {
  createUser(data: UserData) { /* ... */ }
  validateEmail(email: string) { /* ... */ }
  sendWelcomeEmail(user: User) { /* ... */ }
  logUserActivity(activity: string) { /* ... */ }
  generateReport(userId: string) { /* ... */ }
  // Забагато відповідальностей: створення, валідація, email, логування, звітність
}
```

**Добра SRP (оцінка: 9/10)**:
```typescript
class UserService {
  constructor(
    private validator: UserValidator,
    private emailService: EmailService,
    private logger: Logger
  ) {}

  createUser(data: UserData): User {
    // Зосереджений лише на оркестрації створення користувача
    this.validator.validate(data);
    const user = new User(data);
    this.emailService.sendWelcomeEmail(user);
    this.logger.logActivity('user_created', user.id);
    return user;
  }
}
```

## 4. Принцип відкритості/закритості (0-10)

**Питання**: чи можна розширити компонент, не змінюючи його вихідний код?

### Рекомендації щодо оцінювання

| Оцінка | Опис |
|-------|-------------|
| 9-10  | Повністю розширюваний через наслідування чи композицію, зміни не потрібні |
| 7-8   | Здебільшого розширюваний, можуть знадобитися незначні зміни |
| 5-6   | Є певні точки розширення, але обмежені |
| 3-4   | Важко розширювати, потрібні зміни в кількох місцях |
| 0-2   | Закритий для розширення, треба змінювати вихідний код |

### Чеклист

- [ ] Використовує інтерфейси або абстрактні класи
- [ ] Нову поведінку можна додати через нові класи, а не зміни
- [ ] Конфігурація або патерн strategy для змінної поведінки
- [ ] Немає switch за типами (якщо додавання нового типу вимагає змін)
- [ ] Інверсія залежностей (залежить від абстракцій)

### Тривожні ознаки (штрафи)

- **-2**: switch за типом (додавання нового типу вимагає змін)
- **-3**: немає інтерфейсів (скрізь конкретні залежності)
- **-3**: жорстко прописана поведінка (немає точок розширення)
- **-4**: єдиний спосіб додати можливості: змінити наявні методи

### Приклади

**Закритий для розширення (оцінка: 2/10)**:
```typescript
class PaymentProcessor {
  process(type: string, amount: number) {
    switch (type) {
      case 'credit': return this.processCreditCard(amount);
      case 'paypal': return this.processPaypal(amount);
      // Щоб додати криптоплатежі, треба змінювати цей клас
    }
  }
}
```

**Відкритий для розширення (оцінка: 9/10)**:
```typescript
interface PaymentStrategy {
  process(amount: number): Promise<Receipt>;
}

class PaymentProcessor {
  constructor(private strategies: Map<string, PaymentStrategy>) {}

  process(type: string, amount: number) {
    const strategy = this.strategies.get(type);
    if (!strategy) throw new Error(`Unknown payment type: ${type}`);
    return strategy.process(amount);
  }
}

// Новий спосіб оплати додається без зміни PaymentProcessor
class CryptoPaymentStrategy implements PaymentStrategy {
  process(amount: number) { /* ... */ }
}
```

## 5. Документація (0-10)

**Питання**: чи добре задокументована реалізація, чи зрозумілі її задум і використання?

### Рекомендації щодо оцінювання

| Оцінка | Опис |
|-------|-------------|
| 9-10  | Вичерпна документація: задум, використання, приклади, граничні випадки |
| 7-8   | Добра документація, охоплює основні сценарії використання |
| 5-6   | Базова документація, мінімальна, але присутня |
| 3-4   | Мізерна документація, задум незрозумілий |
| 0-2   | Документації немає або вона вводить в оману |

### Чеклист

- [ ] Клас/інтерфейс має коментар JSDoc/TSDoc, що пояснює призначення
- [ ] Задум патерну задокументований («Це Singleton, тому що...»)
- [ ] Публічні методи задокументовані
- [ ] Складна логіка має inline-коментарі
- [ ] Наведено приклади використання (у README або коментарях)
- [ ] Інваріанти та обмеження задокументовані
- [ ] Іменування самодокументоване (зрозумілі, описові назви)

### Тривожні ознаки (штрафи)

- **-2**: немає документації на рівні класу
- **-2**: методи публічного API без документації
- **-3**: незрозумілі назви (x, foo, temp, data)
- **-1**: складна логіка без пояснень

### Приклади

**Погана документація (оцінка: 2/10)**:
```typescript
class S {
  private static i: S;
  private constructor() {}
  static get() {
    if (!S.i) S.i = new S();
    return S.i;
  }
  do(x: any) { /* ... */ }
}
```

**Добра документація (оцінка: 9/10)**:
```typescript
/**
 * Configuration service implemented as a Singleton to ensure
 * all components share the same configuration state.
 *
 * Use `ConfigService.getInstance()` to access the singleton instance.
 *
 * @example
 * const config = ConfigService.getInstance();
 * const apiUrl = config.get('API_URL');
 */
class ConfigService {
  private static instance: ConfigService;

  /**
   * Private constructor prevents direct instantiation.
   * Use `getInstance()` instead.
   */
  private constructor() {
    // Load configuration from environment
  }

  /**
   * Returns the singleton instance of ConfigService.
   * Creates the instance on first call (lazy initialization).
   *
   * @returns The singleton ConfigService instance
   */
  public static getInstance(): ConfigService {
    if (!ConfigService.instance) {
      ConfigService.instance = new ConfigService();
    }
    return ConfigService.instance;
  }

  /**
   * Retrieves a configuration value by key.
   *
   * @param key - Configuration key
   * @returns Configuration value or undefined if not found
   */
  public get(key: string): string | undefined {
    return process.env[key];
  }
}
```

## Оцінювання, специфічне для патерну

### Специфіка Singleton

**Додатковий чеклист**:
- [ ] Лінива ініціалізація (якщо доречно)
- [ ] Враховано потокобезпечність (менш критично в JS)
- [ ] Створення підкласів заборонене або контрольоване
- [ ] Немає публічного конструктора
- [ ] Є механізм скидання для тестів (або згадано альтернативу на DI)

**Штрафи**:
- **-3**: публічний конструктор (нівелює сенс патерну)
- **-2**: кілька методів getInstance(), що повертають різні екземпляри
- **-2**: не враховано ізоляцію тестів

### Специфіка Observer

**Додатковий чеклист**:
- [ ] Observers можуть відписатися
- [ ] Немає витоків пам'яті (observers коректно видаляються)
- [ ] Порядок сповіщень детермінований (якщо це важливо)
- [ ] Observers не залежать від порядку сповіщень
- [ ] Subject не знає конкретних типів observers

**Штрафи**:
- **-3**: немає механізму відписки (ризик витоку пам'яті)
- **-2**: Subject залежить від конкретних типів observers
- **-2**: порядок сповіщень важливий, але не гарантований

### Специфіка Strategy

**Додатковий чеклист**:
- [ ] Strategies реалізують спільний інтерфейс
- [ ] Context не залежить від конкретних strategies
- [ ] Strategies взаємозамінні
- [ ] Strategy можна задати під час виконання
- [ ] Strategies не мають спільного стану (якщо це не закладено свідомо)

**Штрафи**:
- **-3**: Context залежить від конкретних strategies
- **-2**: strategies не є по-справжньому взаємозамінними
- **-2**: немає способу змінити strategy під час виконання

## Формула загальної оцінки

```
Overall Score = (
  Correctness × 0.30 +
  Testability × 0.25 +
  Single Responsibility × 0.20 +
  Open/Closed × 0.15 +
  Documentation × 0.10
) / 5
```

**Ваги** використано тому, що коректність найважливіша, далі йде тестованість.

## Приклад звіту про оцінювання

### Патерн: Singleton
**Файл**: `src/services/config-singleton.ts`
**Рядки**: 5-34

#### Оцінки

| Критерій | Оцінка | Обґрунтування |
|-----------|-------|-----------|
| Коректність | 8/10 | Singleton реалізовано правильно, дрібниця: немає потокобезпечності (у JS не критично) |
| Тестованість | 4/10 | Важко мокати, немає механізму скидання, глобальний стан робить тести взаємозалежними |
| Єдина відповідальність | 9/10 | Зосереджений виключно на керуванні конфігурацією |
| Відкритість/закритість | 7/10 | Можна додавати нові ключі конфігурації, але джерела конфігурації жорстко прописані |
| Документація | 6/10 | Є JSDoc, але бракує обґрунтування вибору singleton |

**Загальна оцінка**: **6.8/10** (Прийнятно)

#### Виявлені проблеми

1. **Високий пріоритет**: додати метод `resetInstance()` для ізоляції тестів
   - Зараз: тести мають виконуватися в певному порядку
   - Виправлення: додати `public static resetInstance()` із перевіркою середовища

2. **Середній пріоритет**: задокументувати обґрунтування singleton
   - Зараз: незрозуміло, навіщо потрібен глобальний стан
   - Виправлення: додати JSDoc, що пояснює вибір (наприклад, «Singleton забезпечує узгоджену конфігурацію в усіх сервісах»)

3. **Низький пріоритет**: розглянути альтернативу з dependency injection
   - Зараз: важко тестувати, жорстке зчеплення
   - Рекомендація: оцінити використання DI-контейнера або React Context

#### Рекомендації

```typescript
// Add test-friendly reset
public static resetInstance(): void {
  if (process.env.NODE_ENV === 'test') {
    ConfigService.instance = null!;
  }
}

// Better yet: refactor to DI
class ConfigService {
  constructor(private envVars: EnvVars) {}
}

// Inject in DI container or provider
const config = new ConfigService(process.env);
```

4. Обчислює зважену загальну оцінку
5. Формує докладний звіт, що містить:
