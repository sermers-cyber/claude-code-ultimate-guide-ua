# Оцінювач skills

Знайдіть кожен skill в межах обсягу, класифікуйте його профіль розповсюдження, оцініть за вісьмома критеріями й тримайте структурну коректність окремо від доказів маршрутизації. Кожна оцінка вказує хост і профіль, до яких вона застосовується.

## Коли використовувати

- Перед комітом або публікацією skill
- Після масового імпорту skills з іншого проєкту чи бібліотеки
- Коли skill спрацьовує надто часто, надто рідко або лише на одному хості
- Коли вирішуєте, чи можна випустити skill для Claude Code, Codex або завантаження Agent Skills

Прочитайте кожен skill у вибраному обсязі. Не робіть висновків про якість усієї колекції за вибіркою. Коли аргумент називає шлях, аудитуйте лише цей шлях.

## Виявлення

### Розташування в Claude Code

| Розташування | Шлях | Примітка для аудиту |
|---|---|---|
| Особисті | `~/.claude/skills/<name>/SKILL.md` | Пропускайте `.trash/`. `synced/` містить skills, завантажені з claude.ai: повідомляйте про них, ніколи не редагуйте |
| Проєкт | `.claude/skills/` у стартовому каталозі й кожному батьківському аж до кореня репозиторію | Спільні через коміти |
| Вкладені | `<subdir>/.claude/skills/<name>/SKILL.md` | Завантажуються, щойно Claude працює з файлами в `<subdir>`. За збігу імен завантажуються обидва, і вкладений стає `/<subdir>:<name>` |
| Додатковий каталог | `.claude/skills/` у каталозі, переданому через `--add-dir` | У межах сесії |
| Файл команди | `.claude/commands/**/*.md` | Застарілий формат. Той самий frontmatter, крім `name` і `paths` |
| Plugin | `<plugin>/skills/<name>/SKILL.md` або `SKILL.md` у корені plugin | Простір імен `/<plugin>:<name>` |
| Корпоративні | `.claude/skills/` у каталозі керованих налаштувань | Лише звітувати |

Зарезервовані назви каталогів: каталог із назвою `synced` (у будь-якому регістрі) пропускається в корпоративному, особистому й проєктному розташуваннях. Поза plugin каталог або файл команди з назвою `anthropic-skills` чи такою, що починається з `anthropic-skills:`, не завантажується.

### Розташування в Codex

| Обсяг | Шлях |
|---|---|
| Репозиторій | `.agents/skills` у кожному каталозі від робочого до кореня репозиторію |
| Користувач | `~/.agents/skills` |
| Адміністратор | `/etc/codex/skills` |
| Система | Постачається разом із Codex |

Codex іде за каталогами skills-симлінками. Skill, вимкнений записом `[[skills.config]]` (`enabled = false`) у `~/.codex/config.toml`, подається як вимкнений, а не оцінюється як зламаний.

```bash
find .claude/skills .agents/skills -name SKILL.md -not -path '*/.trash/*' 2>/dev/null
find .claude/commands -name '*.md' ! -name 'README*' 2>/dev/null
```

**Готово, коли:** кожен файл в обсязі перелічено з його хостом, розташуванням і правилом виявлення, яке його завантажує.

## Профілі розповсюдження

Класифікуйте кожен skill перед оцінюванням. Профіль визначає, які поля дійсні.

| Профіль | Де працює | Які поля frontmatter може використовувати |
|---|---|---|
| Нативний Claude Code | Claude Code на будь-якому локальному рівні, включно зі skills у plugins | Кожне поле з таблиці Claude Code нижче |
| Специфікація Agent Skills | Завантаження на claude.ai, Skills API, пакування через `package_skill.py` | `name`, `description`, `license`, `compatibility`, `metadata`, `allowed-tools`. Будь-який інший ключ спричиняє жорстку помилку завантаження |
| Codex | Codex CLI, розширення IDE, десктопний застосунок ChatGPT | `name` і `description` обов'язкові. Метадані відображення, політика виклику й залежності інструментів ідуть в `agents/openai.yaml` |

Skill, опублікований для кількох профілів, дотримується їхнього перетину. Зберігання специфічних для хоста полів усередині `metadata` для фіксації походження є коректним для переносимого skill і не є дефектом.

**Готово, коли:** кожен skill має один оголошений або виведений профіль із доказами для виведення.

## Довідка з frontmatter Claude Code

Claude Code читає frontmatter лише тоді, коли відкривальний `---` є першим рядком файлу. Невідоме поле він ігнорує без повідомлення про помилку. Коли YAML не парситься, skill завантажується без жодного встановленого поля: `/name` усе ще працює, але Claude не може зіставити опис. Виявляйте збої парсингу командою `claude plugin validate <skills-dir>` (Claude Code v2.1.233 або новіша). Булеві поля приймають `yes`, `no`, `on`, `off`, `1` і `0` у будь-якому регістрі, починаючи з v2.1.218.

| Поле | Примітки |
|---|---|
| `name` | В особистому чи проєктному каталозі skill задає команду, що показується в `/` і вводиться для виклику; назва каталогу також викликає його. За замовчуванням дорівнює назві каталогу. У plugin задає останній сегмент після префікса plugin. Файли команд беруть назву з файлу |
| `description` | Що робить skill і коли його використовувати. Якщо не вказано, використовується перший непорожній рядок тіла |
| `when_to_use` | Додається до `description` у списку й рахується в межах того самого обмеження |
| `argument-hint` | Підказка автодоповнення, як-от `[issue-number]` |
| `arguments` | Іменовані позиційні аргументи для підстановки `$name`. Рядок через пробіл або YAML-список |
| `disable-model-invocation` | `true` прибирає опис із контексту: викликати може лише користувач. Також блокує попереднє завантаження в subagents і виклик із запланованих завдань |
| `user-invocable` | `false` приховує skill з `/`; Claude однаково може його викликати |
| `allowed-tools` | Попередньо схвалює перелічені інструменти для ходу, що викликає skill. Не обмежує інструменти: кожен інструмент лишається доступним. Рядок через пробіл чи кому або YAML-список. Довіра до робочого простору на нього не впливає |
| `disallowed-tools` | Вилучає інструменти з пулу, поки skill активний. Скидається з наступним повідомленням |
| `model` | Модель для решти поточного ходу або `inherit`. Значення, виключене через `availableModels`, не використовується |
| `effort` | `low`, `medium`, `high`, `xhigh` або `max`. Доступні рівні залежать від моделі |
| `context` | `fork` запускає тіло як промпт нового subagent, який не бачить розмови |
| `agent` | Тип subagent, що використовується з `context: fork` |
| `background` | З `context: fork` значення `false` чекає результату в ході виклику. За замовчуванням `true` (v2.1.218 або новіша) |
| `hooks` | Реєструються під час виклику skill і зберігаються до кінця сесії. `once: true` прибирає hook після його першого успішного запуску |
| `paths` | Glob-шаблони, що обмежують автоматичне завантаження. YAML-список або рядок через кому |
| `shell` | `bash` (за замовчуванням) або `powershell` для вбудованого впровадження команд |
| `metadata` | Довільна map, яку читають ваші власні інструменти. Значення, що не є map, відкидається. Не використовуйте назви полів frontmatter як ключі |
| `license` | Приймається, але ні на що не впливає |
| `compatibility` | Рядок до 500 символів. Приймається, але ні на що не впливає |

Поля поза цією таблицею, як-от `tags`, `category`, `keywords`, `usage` чи `args`, не мають ефекту в Claude Code і ламають завантаження Agent Skills. Позначайте їх.

### Підстановки в рядках

| Плейсхолдер | Значення |
|---|---|
| `$ARGUMENTS` | Повний рядок аргументів. Коли жоден плейсхолдер не отримує аргументів, Claude Code додає `ARGUMENTS: <value>` |
| `$ARGUMENTS[N]` | Аргумент з індексом N (від 0) |
| `$N` | Скорочення для `$ARGUMENTS[N]`. Дійсне без поля `arguments:` |
| `$name` | Іменований аргумент, оголошений в `arguments:`. Розкривається в порожній рядок, коли аргумент відсутній |
| `${CLAUDE_SESSION_ID}` | ID поточної сесії |
| `${CLAUDE_EFFORT}` | Активний рівень effort |
| `${CLAUDE_SKILL_DIR}` | Каталог, що містить цей `SKILL.md`. Також підставляється в правилах Bash у `allowed-tools` |
| `${CLAUDE_PROJECT_DIR}` | Корінь проєкту (v2.1.196 або новіша). Також підставляється в правилах Bash у `allowed-tools` |
| `${CLAUDE_PLUGIN_ROOT}`, `${CLAUDE_PLUGIN_DATA}` | Каталоги встановлення plugin і його постійних даних. Лише для skills у plugins |

Індексований плейсхолдер без відповідного аргументу лишається в тексті без змін. Екрануйте буквальний `$` перед цифрою, `ARGUMENTS` або оголошеним іменем одним зворотним слешем, як у `\$1.00`. Плейсхолдери на кшталт `${ARGS}` чи `%ARGUMENTS%` передаються як буквальний текст. Документація Codex про skills не описує підстановку аргументів: фіксуйте поведінку Codex для цих плейсхолдерів як `UNKNOWN`, а не припускайте.

### Бюджет списку

- **Claude Code:** список skills отримує 1% контекстного вікна моделі. Сумарні `description` і `when_to_use` кожного запису обмежено 1536 символами, що налаштовується через `skillListingMaxDescChars`. `skillListingBudgetFraction` або `SLASH_COMMAND_TOOL_CHAR_BUDGET` збільшують бюджет. У разі переповнення першими відкидаються описи найрідше викликаних skills. `skillOverrides` зі значенням `"name-only"` звільняє бюджет. `/skill-doctor` (v2.1.252 або новіша) показує вартість і використання кожного skill.
- **Codex:** початковий список використовує щонайбільше 2% контекстного вікна або 8000 символів, коли розмір вікна невідомий. Codex спершу скорочує описи і може пропустити skills із попередженням.

На обох хостах ставте ключовий сценарій використання на початок, щоб скорочений опис усе ще збігався.

## Критерії оцінювання (25 балів на skill)

| # | Критерій | Макс. | Що перевіряється |
|---|-----------|-----|-----------------|
| 1 | **ідентичність** | 2 | `name` присутнє й складається з малих літер, цифр і дефісів (1), як вимагає Codex; немає нерозв'язаної колізії імен на тому самому хості (1) |
| 2 | **вказівник контексту** | 4 | Опис визначає можливість (1), називає окремі гілки спрацювання (1), починається з розрізнювальних термінів (1) і вміщається в обмеження списку без напихання синонімів (1) |
| 3 | **відповідність профілю** | 3 | Профіль оголошено або його можна вивести (1); кожне поле дійсне для цього профілю (1); дозволи інструментів пропорційні воркфлоу (1) |
| 4 | **виклик і effort** | 2 | Контроль виклику відповідає побічним ефектам (1); `effort`, якщо оголошено, відповідає виведеному рівню, і цільова модель його підтримує (1) |
| 5 | **контракт воркфлоу** | 4 | Призначення або межа явні (1), упорядкована робота придатна до виконання (1), кожен крок має спостережуваний критерій завершення (1), і не лишилося тексту-заглушки (1) |
| 6 | **замкненість ресурсів** | 3 | Обов'язкові локальні посилання розв'язуються (1), обов'язкові скрипти й шаблони існують (1), і жоден ресурс не виходить за корінь skill без явного переносимого контракту (1) |
| 7 | **економність інструкцій** | 3 | Одне джерело істини на правило (1), жодна інструкція не просто повторює поведінку моделі за замовчуванням (1), а матеріал лише для окремих гілок розкривається за потреби, а не завантажується завжди (1) |
| 8 | **докази маршрутизації** | 4 | Корпус має щонайменше 8 позитивних і 2 близьких негативних прикладів (1), використовує реалістичну мову й граничні випадки (1), докази для Claude Code зафіксовано (1), докази для Codex зафіксовано (1) |

**Пороги** як частка застосовних балів:

- ✅ Добре: 80% або більше (від 20 до 25 з 25)
- ⚠️ Потребує роботи: від 60% до 79% (від 15 до 19 з 25)
- ❌ Виправити: менше 60% (14 або менше з 25)

Обгортка команди, що викликається явно, може не мати доказів автоматичної маршрутизації. Зафіксуйте її як `explicit-only`, перевірте, що кожен запитаний хост може її виявити, і оцініть із 21: Добре 17 або більше, Потребує роботи від 13 до 16, Виправити 12 або менше.

### Перегляд ідентичності

Розв'язуйте колізії за правилом кожного хоста. Claude Code: корпоративні над особистими над проєктними; skill над файлом команди; локальний skill замінює вбудовану команду, але не її псевдоніми; вкладений і кореневий skill завантажуються обидва; skills у plugins мають простір імен. Codex не об'єднує skills з однаковим `name`: обидва можуть з'являтися в селекторах, і це колізія, про яку треба повідомити.

### Перегляд вказівника контексту

Розглядайте текст `description` і `when_to_use` як вказівник, що вирішує, чи завантажиться skill. Перелічуйте гілки, а не купи синонімів. Гілка є іншим видом запиту, який обробляється іншими інструкціями. Якщо два описи можуть претендувати на той самий промпт, зафіксуйте колізію як дефект коректності.

### Перегляд відповідності профілю

- **Нативний Claude Code:** `allowed-tools` є попереднім схваленням, тож необмежений запис `Bash` дозволяє кожній shell-команді виконуватися без запиту протягом цього ходу, навіть у недовіреному репозиторії. Для воркфлоу лише на читання попередньо схвалюйте тільки ті команди, які він запускає, як-от `Bash(git status *)` або `Bash(${CLAUDE_SKILL_DIR}/scripts/check.sh *)`. Використовуйте `disallowed-tools`, коли автономний skill ніколи не повинен викликати інструмент, як-от `AskUserQuestion` у фоновому циклі. Нативний skill без `allowed-tools` не штрафується: діють налаштування дозволів користувача.
- **Специфікація Agent Skills:** будь-яке поле поза шістьма дозволеними ключами провалює критерій.
- **Codex:** `name` і `description` присутні; `agents/openai.yaml`, якщо є, парситься, і його записи `dependencies.tools` називають доступні інструменти.
- **Переносимий між хостами:** поля примусового виконання хоста відсутні або зберігаються всередині `metadata`. Не рекомендуйте додавати `allowed-tools` чи `effort` у frontmatter переносимого skill.

### Перегляд виклику й effort

Воркфлоу з побічними ефектами, як-от розгортання, публікація, надсилання чи видалення, встановлює `disable-model-invocation: true` для Claude Code і `policy.allow_implicit_invocation: false` в `agents/openai.yaml` для Codex або пояснює, чому автоматичний виклик безпечний. Відсутність `effort` не є дефектом. Оголошений `effort` має відповідати наведеному нижче виведенню й підтримуватися цільовою моделлю: наприклад, посібник не наводить параметра effort для застарілої Haiku 4.5, тоді як Haiku 5.5 його підтримує.

### Перегляд завершення воркфлоу

Для кожного упорядкованого кроку визначте умову, що дозволяє почати наступний крок. Приймайте запущені команди, створені файли, пройдені перевірки, зафіксовані рішення або явні повідомлення про заблоковані докази. Відкидайте критерії на кшталт «аналіз завершено» чи «досягнуто розуміння», коли агент не може їх перевірити.

### Перегляд замкненості ресурсів

Розв'язуйте локальні Markdown-посилання відносно файлу, що їх містить. Також перевіряйте скрипти, шаблони, фікстури й довідкові матеріали, оголошені в тексті чи прикладах коду, коли від них залежить виконання. На вбудовані скрипти в Claude Code слід посилатися через `${CLAUDE_SKILL_DIR}`, а не через шлях, що залежить від робочого каталогу. Відсутній обов'язковий ресурс є блокером, навіть коли frontmatter і текст мають добрі оцінки.

### Перегляд економності інструкцій

Застосовуйте три перевірки до кожного речення:

1. Чи змінило б вилучення цієї інструкції ймовірну поведінку? Якщо ні, позначте її як порожню.
2. Чи це саме правило вже авторитетно задано деінде? Якщо так, залиште одне джерело й посилайтеся на нього.
3. Чи потрібен цей матеріал під час кожного виклику? Якщо ні, винесіть його за вказівник для конкретної гілки.

## Отримання доказів маршрутизації

Ніколи не присуджуйте бал за маршрутизацію без зафіксованого запуску. Фіксуйте `UNKNOWN` для хоста, який не тестувався.

- **Порівняння з базовою лінією (обидва хости):** запускайте кожен промпт у новій сесії з доступним skill і ще раз із вимкненим (`skillOverrides` зі значенням `"off"` у Claude Code, `[[skills.config]]` з `enabled = false` у Codex). Нова сесія важлива, бо контекст, що залишився після написання skill, маскує прогалини.
- **Skills у plugins Claude Code:** `claude plugin eval` запускає кожен промпт в ізольованій сесії з plugin і без нього; грейдер `tool_used: Skill` вимірює спрацювання, і команда завершується з ненульовим кодом нижче свого порога.
- **Налаштування описів у Claude Code:** офіційний plugin `skill-creator` з `claude-plugins-official` генерує промпти, які мають і не мають спрацьовувати, і вимірює частку влучань.
- **Codex:** документація Codex про skills не описує спеціальної команди для оцінювання. Відтворіть кожен промпт у новій сесії Codex і зафіксуйте, чи було обрано skill.

**Готово, коли:** кожен skill із маршрутизацією має результат для кожного хоста або `UNKNOWN` із причиною.

## Виведення рівня effort

Виведіть рівень з опису й тіла. Подавайте його як рекомендацію лише для нативних skills Claude Code.

- **`low`:** механічне виконання без проєктних рішень. Створення з шаблону, форматування, синхронізація, завантаження. Короткий послідовний воркфлоу, без subagents.
- **`medium`:** обмежений аналіз і категоризація. Рев'ю одного diff, тріаж issues, створення структурованої таблиці. Щонайбільше один-два обмежені subagents.
- **`high`:** проєктні рішення, змагальне або міжсистемне міркування. Аудити безпеки, рев'ю архітектури, оцінювання з урахуванням компромісів. Кілька subagents або явні розділи про невизначеність.
- **`xhigh` або `max`:** вичерпний тривалий синтез. Розгалуження на багато паралельних агентів, динамічні воркфлоу, обсяг на кілька репозиторіїв.

Ultracode є окремим перемикачем в `/effort`, починаючи з Claude Code v2.1.284, і більше не означає рівень effort. Не вважайте слово `ultracode` в тілі skill сигналом effort.

Якщо оголошений `effort` відрізняється від виведеного, позначте це:

> ⚠️ Невідповідність effort: оголошено `low`, виведено `high`. Skill запускає чотири subagents і виконує аналіз безпеки.

## Інструкції з виконання

### Крок 1: Виявлення

Перелічіть кожен файл skill в обсязі з його хостом і розташуванням, використовуючи таблиці виявлення вище. **Готово, коли:** інвентаризація повна, і кожен запис називає своє правило виявлення.

### Крок 2: Класифікація та розбір

Для кожного skill:

1. Прочитайте весь файл і витягніть frontmatter між першими двома рядками `---`.
2. Зафіксуйте збій парсингу, коли YAML не парситься, і підтвердьте його командою `claude plugin validate <skills-dir>`, якщо доступний Claude Code v2.1.233 або новіший.
3. Призначте профіль розповсюдження.
4. Позначте поля, невідомі або недійсні для цього профілю.
5. Звірте плейсхолдери підстановки з таблицею.
6. Розв'яжіть обов'язкові локальні посилання, скрипти, шаблони, фікстури й довідкові матеріали.
7. Зафіксуйте упорядковані кроки й спостережуваний критерій завершення для кожного.
8. Прочитайте `evals/scenarios.json`, якщо він є, і порахуйте позитивні й негативні приклади.

**Готово, коли:** кожен skill має розібраний запис, профіль і список ресурсів, де кожен елемент розв'язано або позначено відсутнім.

### Крок 3: Оцінювання й виведення

Застосуйте вісім критеріїв, виведіть effort і порівняйте його з оголошеним значенням, якщо воно є. Перевірте skills з `context: fork` на наявність придатного до виконання тіла завдання й поля `agent` і зверніть увагу, що фоновий fork працює з вужчим фоновим набором інструментів. **Готово, коли:** кожен критерій має оцінку й однорядкове обґрунтування.
